# Как разделить входной DTO, выходной DTO и внутреннюю модель backend?

Входной DTO описывает разрешённые данные клиента, выходной — публичное представление результата, внутренняя модель — правила и состояние приложения. Они могут отличаться составом полей, типами и жизненным циклом.

Например, вход содержит `productId` и количество, а цену и владельца определяет сервер. Выход не включает password hash или ORM metadata. Отдельные формы полезны, когда защищают контракт и правила; механическое копирование одинаковых структур без причины увеличивает сопровождение.

# Почему TypeScript-типы DTO не заменяют runtime-валидацию запроса?

TypeScript проверяет код до выполнения, но не подтверждает тип байтов из HTTP. Аннотация `body: CreateUserDto` не превращает произвольный объект в валидный DTO и не удаляет неизвестные поля.

Нужен runtime-parser или validator со схемой, либо конкретный class-based механизм, который действительно вызывается на границе. Классы и декораторы тоже не работают автоматически без настроенного pipeline. Проверяют вложенные объекты, массивы, неизвестные поля и ограничения размера.

# В каком порядке выполнять parsing, transformation, validation и бизнес-проверки входных данных?

Сначала ограничивают тело и разбирают выбранный формат, затем выполняют строго определённые безопасные преобразования и проверяют структуру. После получения валидной формы проверяют полномочия, существование сущностей и бизнес-условия в подходящем сценарии.

Последовательность зависит от проверки: authentication часто возможна до разбора body. Нормализация не должна незаметно исправлять опасные входы. Проверки, зависящие от текущего состояния, подтверждают при записи, потому что между предварительной проверкой и commit возможна гонка.

# Как различать отсутствующее поле, null и пустое значение в PATCH DTO?

Отсутствующее поле обычно означает «не изменять», `null` может означать «очистить», а пустая строка — новое пустое значение, если оно разрешено. Это разные случаи, и их нужно зафиксировать в контракте PATCH.

Optional-тип говорит о допустимом отсутствии, но не обязательно о допустимости null. Также учитывают формат: JSON Merge Patch придаёт null специальный смысл удаления члена. Проверяют присутствие свойства отдельно от truthiness, иначе `0`, `false` и пустая строка потеряются.

# Как whitelist полей и явный mapping защищают от mass assignment?

**Mass assignment** возникает, когда произвольные поля клиента напрямую попадают во внутреннюю модель: например, `isAdmin`, `ownerId` или `status`. Входная схема должна разрешать только допустимые поля, а application code — явно переносить их в нужную операцию.

Неизвестные поля удаляют или отклоняют по контракту. Одного whitelist недостаточно: доступ к изменению конкретного ресурса и разрешённые переходы состояния проверяют отдельно. Поля, вычисляемые сервером, не принимают на доверии даже при корректном типе. [ValidationPipe и whitelist](https://docs.nestjs.com/techniques/validation).

# Какие проверки стоит выполнять на границе API, в бизнес-сценарии и в базе данных?

Граница API проверяет форму, тип, диапазоны и максимальные размеры. Бизнес-сценарий проверяет предметные правила и полномочия, а БД обеспечивает ограничения, которые должны выдерживать конкурентные записи: уникальность, внешние ключи и необходимые атомарные условия.

Проверка «email свободен» перед insert улучшает сообщение, но только уникальное ограничение защищает от двух одновременных созданий. Дублировать каждый уровень механически не нужно: они решают разные риски и должны возвращать согласованные ошибки.

# Какие ошибки создаёт неявное приведение query-параметров к boolean и number?

Query-параметры приходят строками: `Boolean('false')` возвращает `true`, а `Number('')` — `0`. Неявное преобразование способно принять отсутствие значения за действительное число или изменить смысл флага.

Определяют допустимые записи, например строго `true`/`false`, проверяют конечность, целочисленность, диапазон и обработку повторных параметров. Преобразование должно предшествовать проверке нормализованного значения, но не принимать лишние формы без контракта. Ограничения самого framework-validator проверяют явно.

# Как сериализовать даты, BigInt, decimal и циклические ссылки в API-ответе?

Даты передают в согласованном формате с timezone или как чётко определённый timestamp. Для больших целых и точных decimal часто выбирают строки с ограничениями, поскольку JSON number и клиентские runtime могут терять точность.

В JavaScript обычный `JSON.stringify` не сериализует `BigInt` без специального преобразования и падает на циклических ссылках. Поэтому наружу формируют явный DTO, а не весь ORM graph. Сериализация должна сохранять различие null и отсутствующего поля и соответствовать схеме API.

# Как возвращать ошибки валидации без утечки секретов и внутренних деталей?

Возвращают стабильный код, путь поля и безопасное описание нарушенного правила. Невалидные пароли, токены, полное тело запроса, имена SQL-таблиц и stack trace в ответ не включают. Количество ошибок можно ограничить, чтобы ответ не стал источником нагрузки.

Для подробной диагностики используют correlation identifier и защищённые логи с redaction. Сообщение об ошибке также может раскрывать существование пользователя или ресурса, поэтому его детализацию выбирают с учётом доступа, а не только удобства разработчика.

# Как singleton, request и transient lifetimes влияют на DI в backend?

`Singleton` обычно создаётся один раз на контейнер приложения, `request/scoped` — на scope, часто HTTP-запрос, `transient` — при разрешении зависимости по правилам контейнера. Точная семантика различается между frameworks.

Singleton не должен хранить данные конкретного пользователя и должен безопасно обслуживать конкурентные обращения. Request scope удобен для контекста операции, но повышает число создаваемых объектов. Scoped lifetime не обеспечивает транзакцию сам по себе и требует отдельного scope для фоновой задачи. [Lifetimes в .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection/overview).

# Что такое captive dependency и как обнаружить неверное смешение DI scopes?

**Captive dependency** возникает, когда долгоживущий объект удерживает зависимость, рассчитанную на более короткий scope. Например, singleton хранит request-specific контекст или session БД и затем использует их для другого запроса.

Проверяют граф lifetimes, включают scope validation контейнера и создают scope для отдельной фоновой операции. Контекст не должен сохраняться в глобальном поле. Некоторые контейнеры отклоняют такое сочетание, другие меняют scope зависимого объекта, поэтому правила проверяют для конкретной реализации DI.

# Как runtime-токены, factories и декораторы связывают зависимости при DI в TypeScript?

TypeScript interfaces и type aliases стираются, поэтому контейнеру нужен runtime-токен: класс, `Symbol` или согласованная строка. Provider связывает токен с объектом, классом либо factory; factory может получать другие зависимости и асинхронно создавать ресурс.

Декораторы и metadata помогают некоторым контейнерам, но не восстанавливают любую generic-структуру и зависят от режима компиляции и поддержки декораторов. Контракты задают явно, а конфигурацию и создание соединений сосредоточивают в сборке приложения. Это делает зависимости видимыми и заменяемыми в проверках.
