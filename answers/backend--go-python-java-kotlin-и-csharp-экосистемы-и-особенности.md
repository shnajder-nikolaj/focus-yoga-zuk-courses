# По каким критериям выбирать Go, Python, Java/Kotlin или C# для backend-сервиса?

Сначала оценивают бизнес-нагрузку, библиотеки и интеграции, требования к задержке, памяти, запуску и размещению. Затем учитывают опыт команды, доступность поддержки и операционные инструменты.

Go часто удобен для конкурентных сетевых программ и простого распространения бинарников, Python — для богатой data/ML-экосистемы и быстрой разработки, JVM и .NET — для развитых серверных платформ и инструментов. Эти свойства не определяют победителя заранее: выбранный runtime проверяют на representative-сценарии вместе с драйверами и framework.

# Как goroutines, channels и context организуют конкурентность и отмену в Go?

Goroutine — лёгкая конкурентная задача, multiplexed runtime поверх потоков ОС. Channels позволяют передавать данные и координировать работу, но не делают всю программу автоматически безопасной. Количество активных задач и очереди нужно ограничивать.

`context.Context` переносит deadline и сигнал отмены; функция должна сама наблюдать отмену или вызывать API, которое её поддерживает. Потерянные получатели, незакрытые пути завершения и заблокированные send могут оставлять goroutine leaks. Обычно закрывает channel сторона, ответственная за отправку. [Pipelines и cancellation в Go](https://go.dev/blog/pipelines).

# Как errors, interfaces и нулевые значения влияют на проектирование Go-сервиса?

В Go ошибки обычно возвращаются значением `error`; вызывающий код обязан их обработать или передать выше с контекстом. Для классификации wrapped errors используют подходящие механизмы вроде `errors.Is` и `errors.As`, а не сравнение текста.

Небольшие interfaces выражают потребность потребителя и реализуются неявно. Нулевые значения полезны, когда тип имеет осмысленное начальное состояние, но `nil` map нельзя использовать для записи без инициализации. Interface с typed nil тоже может быть не равен `nil`. Такие особенности проверяют на границах сервиса.

# Как GIL и free-threaded builds CPython влияют на многопоточную серверную обработку?

В обычной сборке CPython с GIL несколько потоков не исполняют Python bytecode параллельно; I/O и часть нативных расширений могут освобождать GIL. Поэтому потоки полезны для многих I/O-сценариев, но не гарантируют ускорения CPU-bound Python-кода.

Начиная с CPython 3.13 доступны free-threaded builds; поддержка зависит от версии и расширений. В CPython 3.14 неподдерживающее расширение может вновь включить GIL. Отсутствие GIL не устраняет гонки и не гарантирует ускорение. [Free threading CPython 3.14](https://docs.python.org/3.14/howto/free-threading-python.html).

# Как выбирать между asyncio, потоками и процессами для Python backend?

`asyncio` подходит для конкурентного I/O с неблокирующими библиотеками. Блокирующий вызов внутри coroutine задерживает event loop; его заменяют async API либо выносят в ограниченный executor.

Потоки полезны для блокирующего I/O и нативной работы с подходящей поддержкой, процессы — для изоляции и CPU-параллелизма, особенно при GIL-enabled CPython. Межпроцессная передача и память имеют цену. `async def` сам по себе не делает вычисление параллельным; отмену, cleanup и предел числа задач проектируют явно. [Asyncio tasks](https://docs.python.org/3/library/asyncio-task.html).

# Как JIT, garbage collection и прогрев JVM влияют на Java/Kotlin-сервис?

JVM может оптимизировать горячий код во время работы, поэтому показатели сразу после запуска отличаются от прогретого steady state. Загрузка классов, framework initialization и compilation влияют на startup и первые запросы.

Garbage collector управляет памятью и вносит расходы, зависящие от allocation rate, heap и выбранного collector. Измеряют p99, pauses, RSS и CPU в реальных container limits. Нельзя сравнивать runtime только по размеру heap или одному короткому прогону. Native/AOT-варианты меняют эти компромиссы и требуют отдельной проверки.

# Чем Kotlin coroutines и Java virtual threads отличаются как модели конкурентности?

Kotlin coroutine — приостанавливаемое вычисление; `suspend` и библиотеки coroutines позволяют строить отмену и structured concurrency поверх выбранных dispatchers. Блокирующий вызов не становится неблокирующим только из-за `suspend`.

Java virtual threads, доступные в Java 21, дают лёгкие `Thread` для большого числа преимущественно ожидающих задач, сохраняя привычный последовательный стиль. Они не ускоряют CPU-работу сверх доступных ядер. Поддержка блокирующих операций и особенности runtime зависят от версии JDK. [Kotlin coroutines](https://kotlinlang.org/docs/coroutines-basics.html), [virtual threads Java](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html).

# Как Task, async/await и CancellationToken используются в ASP.NET Core?

`Task` представляет асинхронную операцию, а `await` позволяет дождаться её без блокировки потока на период поддерживаемого I/O. Асинхронность не означает обязательного создания нового потока. `.Result` и `.Wait()` в горячем request path могут блокировать thread pool.

`CancellationToken`, включая сигнал отмены запроса, передают в поддерживающие его API. Отмена кооперативна и не откатывает уже выполненный commit. CPU-нагрузку не следует безгранично оборачивать в `Task.Run` внутри сервера. [ASP.NET Core: избегание блокирующих вызовов](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/best-practices?view=aspnetcore-10.0).

# Почему shared mutable state остаётся источником гонок во всех серверных языках?

Несколько задач могут прочитать старое состояние и записать противоречивый результат, даже если язык защищает отдельные операции контейнера. В Python и single-threaded event loop логическая гонка возможна между точками ожидания; несколько процессов добавляют распределённую конкуренцию.

Используют ownership, immutability, mutex/atomic operations и транзакции на нужной границе. Concurrent map не делает атомарной последовательность «проверить, затем изменить». Выбор синхронизации определяется инвариантом, а не только моделью потоков языка.

# Как сравнивать startup time, память и пропускную способность разных backend-runtime?

Используют одинаковый функциональный сценарий, данные, оборудование, лимиты контейнера, сетевые зависимости и уровень параллелизма. Фиксируют версии runtime, framework, GC и режимы компиляции; отдельно измеряют cold start и прогретую работу.

Считают RPS при целевой p95/p99 и доле ошибок, RSS, CPU и поведение при перегрузке. Одни библиотеки могут использовать нативный код или другую сериализацию, поэтому результат характеризует конкретный стек, а не язык вообще. Важна стоимость работы и сопровождения при требуемом качестве сервиса.

# Как различия типов, чисел, времени и сериализации влияют на контракты полиглотных сервисов?

У языков различаются диапазоны целых, точность decimal, поведение float, nullability, timezone и представление даты. Например, значение `int64` может потерять точность в JavaScript-клиенте при передаче как JSON number.

Контракт задаёт формат, единицы и допустимые значения независимо от внутреннего типа. Проверяют round-trip, нули, большие числа, missing/null и временные границы. Генерация типов помогает, но не доказывает совпадения семантики. Для денег и времени формат выбирают явно, а не по умолчанию сериализатора.

# Как ограничивать стоимость поддержки нескольких языков в одной backend-платформе?

Задают поддерживаемый набор runtime и версий, общие требования к API, telemetry, сборке, обновлениям и безопасности. Предоставляют шаблоны сервисов, стандартный deployment и ясное ownership, не заставляя все языки иметь одинаковую внутреннюю структуру.

Новый язык добавляют ради измеримой выгоды и с планом поддержки библиотек, дежурства и найма. Стоимость включает не только написание endpoint, но и обновления, расследования и передачу сервиса другой команде. Для небольшой платформы один знакомый стек часто снижает эту нагрузку.
