# Как анализировать размер образа по слоям и находить ненужные runtime-зависимости?

Проверяют общий размер image и вклад отдельных layers, например через `docker image history`, затем состав final filesystem. Ищут compiler, package cache, test fixtures, исходники и зависимости, не нужные для выполнения приложения.

**Multi-stage build** позволяет переносить в runtime только результат сборки. Уменьшение image ускоряет transfer и снижает число лишних компонентов, но минимальный размер не доказывает безопасность или быстродействие. Сравнивают также cold start, доступные библиотеки, отладку и регулярность обновлений выбранной базы.

# Почему удаление файла в следующем слое не удаляет его из истории образа?

Filesystem image состоит из неизменяемых layers. Удаление файла позднее создаёт запись, скрывающую его в объединённом представлении, но байты остаются в предыдущем слое и могут быть извлечены.

Поэтому секрет нельзя безопасно передать через `COPY key` и удалить следующим `RUN`. Для временных build-файлов используют один подходящий шаг, mounts или отдельный stage, не попадающий в final image. Если credential уже опубликован в layer, его считают раскрытым и отзывают, а не ограничиваются новой версией Dockerfile.

# Как выбирать base image между full distribution, slim, Alpine и distroless?

Полный distribution image даёт привычные библиотеки и инструменты; **slim** сокращает набор пакетов. **Alpine** обычно использует musl, что может отличаться от ожидаемой glibc и влиять на native dependencies. **Distroless** оставляет минимальный runtime и обычно не содержит shell или package manager.

Выбор проверяют на конкретном artifact: динамическую линковку, сертификаты, DNS, locale и профилирование. Отсутствие shell усложняет диагностику, но не исключает возможность исполнять вредоносный код внутри приложения. Предпочтительнее поддерживаемая и обновляемая база с известным составом, чем минимальный неподдерживаемый image.

# Как порядок COPY и RUN влияет на cache invalidation и скорость пересборки?

Cache зависит от инструкции и её входных данных. Если сначала скопировать весь source tree, любое изменение кода может инвалидировать дорогую установку зависимостей. Обычно сначала копируют manifest и lockfile, устанавливают dependencies, затем добавляют часто меняющийся код.

Для package cache применяют BuildKit cache mounts, а context уменьшают через `.dockerignore`. Результат сборки должен оставаться корректным при пустом cache. Если шаг скачивает изменяемые внешние данные, неизменный Dockerfile не гарантирует их свежесть; обновления требуют управляемого изменения входов или политики cache. [Оптимизация build cache](https://docs.docker.com/build/cache/optimize/).

# Как non-root user, rootless Docker и user namespaces уменьшают разные риски?

**Non-root user** ограничивает права процесса внутри контейнера, но Docker daemon на host при этом может оставаться root. **Rootless Docker** запускает daemon и контейнеры от непривилегированного пользователя с соответствующим использованием user namespaces.

**User namespaces** отображают UID/GID контейнера в другие IDs host, поэтому контейнерный UID 0 не обязан быть host root. Эти меры дополняют друг друга и зависят от поддержки ядра, storage и resource control. Проверяют права mounts и нужные приложению операции; non-root не отменяет доступ к общему ядру. [Rootless mode](https://docs.docker.com/engine/security/rootless/).

# Как capabilities, seccomp и запрет privilege escalation ограничивают контейнер?

**Linux capabilities** делят полномочия root на отдельные права; ненужные capabilities удаляют и добавляют только подтверждённо необходимые. **Seccomp** ограничивает системные вызовы, а `no-new-privileges` запрещает процессу получать новые привилегии через предусмотренные механизмы exec, например setuid.

Эти ограничения не заменяют user permissions, MAC-профили и обновления ядра. Отключать seccomp целиком ради одной ошибки опасно: сначала выясняют нужный syscall и причину. Профиль должен соответствовать runtime приложения и проверяться на реальных сценариях. [Seccomp Docker](https://docs.docker.com/engine/security/seccomp/).

# Как read-only root filesystem и минимальные mounts сокращают доступный для изменения объём?

**Read-only root filesystem** запрещает обычную запись в корневой filesystem контейнера. Приложению явно выделяют нужные writable paths через tmpfs или volumes, например для временных файлов и рабочих данных.

Mounts задают с минимальной областью и при возможности read-only. Иначе процесс с ограниченным image всё ещё может менять важные файлы через широкий writable bind mount. Такая схема уменьшает возможность закрепления и случайного изменения runtime, но не запрещает кражу данных, сетевые запросы и изменения на специально подключённых writable volumes. Проверяют также скрытые write paths библиотек.

# Почему Docker socket, privileged mode и host namespaces ослабляют изоляцию?

Доступ к **Docker socket** часто позволяет создавать контейнеры с host mounts и другими привилегиями, фактически расширяя права до уровня daemon. Это существенно шире обычного доступа к одному приложению.

`--privileged` снимает многие стандартные ограничения и даёт широкий доступ к devices. Host PID, network и другие namespaces уменьшают соответствующую изоляцию. Каждое исключение должно иметь конкретную необходимость и ограниченную область. Контейнер с rootless daemon имеет другую границу риска, но доступ к его API всё равно открывает все доступные этому daemon ресурсы.

# Как CPU quota, CPU shares и cpuset влияют на использование процессора контейнером?

**CPU quota** ограничивает доступное CPU-время за период: процесс может быть throttled даже при кратком интенсивном burst. **CPU shares** задают относительный вес при конкуренции, а не гарантированный абсолютный максимум. **Cpuset** ограничивает, на каких CPU процесс может выполняться.

Например, лимит в половину CPU не означает выделение физического ядра: это бюджет времени в соответствующем механизме cgroups. Для latency-sensitive приложения измеряют throttling, параллелизм и работу runtime под лимитом. Точные настройки зависят от cgroup version и возможностей host. [CPU constraints](https://docs.docker.com/engine/containers/resource_constraints/#cpu).

# Как memory limit, swap и OOM влияют на завершение контейнера?

**Memory limit** ограничивает потребление, учитываемое cgroup. При невозможности удовлетворить запрос памяти может сработать OOM killer и завершить процесс; последующий restart зависит от restart policy или orchestrator, а не от самого факта OOM.

Swap может отсрочить отказ ценой latency и зависит от настроек host и Docker. Runtime heap limit задают с запасом на native memory, stacks, buffers и другие расходы. Контролируют working set, cache, OOM events и рост памяти. Отключение OOM protection без понимания общей ёмкости способно повлиять на весь host. [Memory constraints](https://docs.docker.com/engine/containers/resource_constraints/#memory).

# Как ограничивать процессы, файловые дескрипторы, логи и рост диска контейнера?

Число процессов ограничивают PID limit, файловые дескрипторы — соответствующим `ulimit`, а logs — параметрами выбранного logging driver, rotation и внешнего сбора. Иначе исправное приложение может заполнить host log files.

Диск контролируют отдельно: writable layer, volumes, images и build cache растут по разным причинам. Quota и storage options зависят от backend и filesystem; CPU и memory limits не ограничивают автоматически все эти данные. Для production задают мониторинг свободного места, retention и проверяемые процедуры очистки, учитывающие данные и необходимые rollback images.

# Как обновлять base images и проверять уязвимости без потери воспроизводимости релиза?

Base image и зависимости фиксируют по версии и digest, связывают с SBOM и регулярно проверяют доступные исправления. Обновление базы оформляют новым build с тестами и новым digest, а ранее опубликованный release сохраняют неизменным.

Scanner сообщает известные находки в пределах своего coverage; отсутствие CVE не доказывает безопасность. Оценивают применимость уязвимости, наличие исправления и риск runtime, но не оставляют старую базу бессрочно ради pinning. Проверяют подпись и provenance там, где они доступны, а также не только OS packages, но и зависимости приложения.
