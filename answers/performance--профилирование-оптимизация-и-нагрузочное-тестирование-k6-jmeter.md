# Как сформулировать проверяемую гипотезу оптимизации и выбрать baseline backend?

Гипотеза связывает наблюдаемую задержку с механизмом: например, «повторная сериализация занимает 30% CPU; устранение копирования снизит CPU на запрос при прежнем результате». Заранее фиксируют критерии успеха и ограничения по памяти, ошибкам и корректности.

Baseline получают на известной версии кода с заданными ресурсами, данными, смесью операций и состоянием кэшей. Выполняют несколько сопоставимых запусков, чтобы оценить разброс. Сравнение разных машин или одновременного изменения нескольких факторов не позволяет уверенно приписать результат конкретной оптимизации.

# Как сопоставлять CPU, wall-clock и allocation profiles с трассировками запросов?

`CPU profile` показывает затраты процессорного времени; `wall-clock profile` помогает увидеть время, включающее ожидание, в зависимости от возможностей profiler. `Allocation profile` выявляет места выделения памяти, но большой объём выделений не равен большому объёму удерживаемой памяти: для утечки исследуют heap и пути удержания.

Профиль связывают с конкретным периодом и видом нагрузки. Traces уточняют, какие запросы ждут pool, lock или удалённый сервис. Учитывают sampling bias, наличие symbols, overhead и прогрев runtime: широкая полоса flame graph показывает накопленную стоимость, а не автоматически ошибку.

# Как закон Амдала помогает оценить предел ускорения backend-операции?

**Закон Амдала** оценивает ускорение как `S = 1 / ((1 − p) + p / s)`, где `p` — доля исходного времени, затронутая улучшением, а `s` — ускорение этой части. Если сериализация занимает 20%, её ускорение в пять раз даёт примерно `1 / 0,84 = 1,19`, то есть около 19% общего ускорения.

Оценка предполагает неизменность остальных затрат. В backend уменьшение времени удержания lock или соединения может дополнительно снизить очереди, поэтому эффект под высокой нагрузкой отличается. Рассчитывают ожидаемый выигрыш, затем измеряют его в том же режиме работы.

# Чем load, stress, spike, soak и breakpoint tests различаются по цели?

`Load test` проверяет поведение при ожидаемой нагрузке. `Stress test` выводит систему за обычный диапазон и проверяет деградацию и восстановление. `Spike test` исследует резкое изменение трафика, а `soak test` — длительную работу, утечки, накопление очередей и исчерпание ресурсов.

`Breakpoint test` целенаправленно ищет границу, после которой нарушаются критерии приёмки. Названия не заменяют сценарий: для каждого запуска задают профиль, длительность, данные, ожидаемые свойства и условия прекращения. Максимальный достигнутый RPS без acceptable latency и error rate не характеризует полезную ёмкость.

# Как выбрать открытую или закрытую модель нагрузки и избежать coordinated omission?

В **закрытой модели** заданные виртуальные пользователи начинают новую итерацию после завершения предыдущей. При замедлении сервиса интенсивность автоматически падает. Это реалистично для фиксированной группы пользователей, но может скрыть задержки, если реальный входящий поток продолжает поступать независимо.

В **открытой модели** новые итерации планируются с заданной интенсивностью. В k6 для этого используют arrival-rate executors. Проверяют число доступных VUs и `dropped_iterations`: недостаток генератора не должен незаметно уменьшить предъявляемую нагрузку. Модель выбирают по поведению источника трафика. [k6: Open and closed models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

# Как воспроизвести в k6 или JMeter смесь операций, авторизацию и реалистичные данные?

Из production-наблюдений получают доли операций, размеры payload, think time, распределение ключей и долю cache hits. В сценарий добавляют получение credentials и корреляцию динамических значений: идентификаторов, cookies, CSRF-токенов. У разных виртуальных пользователей должны быть реалистичные права и данные.

Read-only тест на одном ID часто измеряет горячий кэш. Создание уникальных объектов без очистки, напротив, постепенно меняет размер БД. Фиксируют правила подготовки и жизненного цикла данных, проверяют бизнес-результат ответов и не включают случайно внешние оплачиваемые операции в массовую нагрузку.

# Как в k6 связать scenarios, executors, checks и thresholds с критериями приёмки?

`Scenario` задаёт отдельный поток поведения, а `executor` — способ планирования итераций или VUs. `Check` проверяет результат конкретного действия; провал check сам по себе не делает весь запуск неуспешным. `Threshold` задаёт критерий pass/fail для агрегированной метрики.

Например, `http_req_duration: ['p(95)<300']` требует p95 ниже 300 мс, а `http_req_failed: ['rate<0.01']` ограничивает долю HTTP-ошибок. При необходимости добавляют threshold на `checks` и выделяют endpoints через tags. Бизнес-ошибку внутри HTTP 200 нужно проверять отдельно. [k6: Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/).

# Как организовать нагрузочный запуск JMeter через CLI без искажения результатов listeners?

GUI используют для разработки и малой отладки test plan, основной нагрузочный запуск выполняют через CLI: `jmeter -n -t plan.jmx -l results.jtl -e -o report`. Каталог HTML-отчёта должен соответствовать требованиям запуска, обычно быть пустым. Версии JMeter, Java и plugins фиксируют.

Отключают тяжёлые listeners и сохранение всех response bodies: иначе измеряется ограничение генератора. Наблюдают CPU, heap, GC и сеть машины JMeter. Для распределённой нагрузки согласуют данные, часы и конфигурацию генераторов; timestamps и client-side latency не заменяют серверную телеметрию. [JMeter: Best Practices](https://jmeter.apache.org/usermanual/best-practices.html).

# Как анализировать p95, p99, ошибки и achieved load при сравнении нагрузочных запусков?

Сравнивают одновременно offered load, реально начатые и завершённые операции, ошибки, timeouts и распределение задержек. Снижение p99 из-за быстрого отклонения половины запросов не означает улучшения обслуживания. Отдельно рассматривают успешные ответы и весь поток.

Перцентили считают по совместимым raw observations или объединяемым histogram buckets: усреднять p99 разных узлов нельзя. Для редких операций нужна достаточная выборка. Различают end-to-end время и метрику HTTP duration инструмента, которая может исключать получение соединения. Отчёт содержит нагрузку, продолжительность, ресурсы и разброс повторных запусков.

# Как доказать устойчивость оптимизации и встроить performance regression checks в CI?

Повторяют baseline и изменённую версию на сопоставимых данных, по возможности чередуя порядок запусков. Проверяют не только обычный режим, но и холодный кэш, длительную работу и замедленные зависимости. Подтверждают, что выигрыш не оплачен ростом ошибок, памяти или нарушением результата.

В CI оставляют ограниченный воспроизводимый сценарий с порогами, превышающими обычный шум измерений; тяжёлые тесты запускают отдельно по расписанию или перед значимыми релизами. После выкладки проверяют эффект на пользовательских метриках и стоимости операции. Один удачный benchmark не доказывает устойчивую регрессионную защиту.
