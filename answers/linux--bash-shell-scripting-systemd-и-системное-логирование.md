# Как shell выполняет подстановки и почему quoting определяет корректность Bash-скрипта?

Bash выполняет несколько видов expansion: parameters, command substitution, arithmetic, а в подходящих контекстах — word splitting и pathname expansion. Некавыченное значение с пробелами или `*` способно превратиться в несколько аргументов либо список файлов.

**Double quotes** сохраняют значение одним аргументом, допуская основные подстановки; **single quotes** сохраняют текст буквально. Например, `"$path"` и `$path` не эквивалентны. Исключения контекста, такие как assignments и arrays, изучают отдельно. Quoting не делает безопасным `eval` с недоверенным содержимым.

# Чем shell variables, exported environment и positional parameters отличаются по области действия?

Обычная **shell variable** существует в текущем shell. `export` включает значение в environment будущих дочерних процессов; изменение environment ребёнком не меняет родительский shell.

**Positional parameters** представляют аргументы вызова. `"$@"` сохраняет отдельные аргументы, включая пустые и содержащие пробелы; `"$*"` объединяет их по особым правилам. `local` ограничивает variable внутри Bash function, но имеет собственную семантику scope. Конфигурацию передают явно, избегая случайной зависимости от интерактивного environment и глобальных переменных.

# Как stdin, stdout, stderr, pipes и redirections связывают процессы?

Процесс получает file descriptors `0`, `1` и `2` для **stdin**, **stdout** и **stderr**. Pipe обычно соединяет stdout одной команды со stdin другой; stderr без отдельного перенаправления туда не попадает.

Redirections обрабатываются последовательно, поэтому `>file 2>&1` и `2>&1 >file` направляют stderr по-разному. Вывод данных отделяют от diagnostics, чтобы pipeline не принял сообщение об ошибке за результат. Закрытие pipe другой стороной может вызвать broken pipe или `SIGPIPE`; это учитывают при оценке exit status.

# Как exit status, pipefail и ограничения set -e влияют на обработку ошибок?

Нулевой **exit status** обычно означает успех, ненулевой — ошибку или другой предусмотренный исход. Без `pipefail` status pipeline обычно определяется последней командой, что может скрыть сбой раннего этапа. С `pipefail` учитывается правый ненулевой результат.

`set -e` имеет исключения для условий, логических списков, pipelines и других контекстов; он не заменяет явную обработку критичных операций. `$?` и `PIPESTATUS` считывают до команды, которая их изменит. Сначала определяют допустимые коды результата конкретной утилиты: ненулевой status не всегда является аварией. [Bash manual](https://man7.org/linux/man-pages/man1/bash.1.html).

# Как безопасно обрабатывать имена файлов, пробелы, arrays и ввод через read?

Не разбивают имена файлов через некавыченные подстановки и не разбирают `ls` как надёжный формат данных. Для списков аргументов используют **arrays** и расширение `"${items[@]}"`, сохраняющее границы элементов.

Для построчного ввода часто нужен `IFS= read -r`, а для произвольных имён с переводами строки — NUL-разделители и поддерживающие их утилиты. Опция `--`, где она поддерживается, отделяет имена с начальным дефисом от flags. Проверяют пустой список, пробелы, Unicode и специальные символы, а не только простые имена.

# Как functions, subshells и command substitution влияют на состояние и результаты скрипта?

**Function** обычно выполняется в текущем shell и может менять его состояние. **Subshell**, например блок в круглых скобках, изолирует изменения variables и рабочего каталога от родителя. Элементы pipeline в Bash тоже часто исполняются в subshell, с зависящими от настроек исключениями.

**Command substitution** получает stdout команды и удаляет завершающие переводы строки. Поэтому она не подходит для точной передачи произвольных бинарных данных. `return` передаёт exit status function, а не произвольную строку; данные возвращают через явно выбранный канал. [Bash execution](https://man7.org/linux/man-pages/man1/bash.1.html).

# Как trap, сигналы и временные файлы помогают завершать скрипт без утечки ресурсов?

`trap` назначает действие для предусмотренного события, например `EXIT`, `INT` или `TERM`. Cleanup удаляет созданный временный ресурс и сохраняет нужный exit status, не скрывая исходную ошибку.

Временные файлы создают механизмом вроде `mktemp`, избегая предсказуемого имени и гонки проверки с созданием. Обработчик должен знать, какие ресурсы действительно принадлежат этому запуску. `SIGKILL` и авария системы не дают выполнить cleanup, поэтому временное состояние должно оставаться безопасным и быть пригодным к дальнейшей уборке. Trap сам по себе не откатывает внешнюю транзакцию.

# Как сделать shell-скрипт повторяемым и исключить гонки одновременных запусков?

Проверяют фактическое состояние до изменения и выполняют операцию так, чтобы повтор не дублировал результат. Для общего локального ресурса может понадобиться **advisory lock**, например через `flock`; все участвующие writers должны соблюдать одну схему.

Файл результата формируют отдельно и заменяют подходящим atomic rename, учитывая filesystem и durability. Проверка «файл ещё не существует» перед записью не исключает конкурента между этими действиями. Для распределённых процессов локальный lock недостаточен. Timeout внешней операции означает неизвестный исход, поэтому повтор требует idempotency или сверки результата.

# Как unit files, targets, dependencies и ordering управляют сервисами systemd?

**Unit file** описывает управляемый объект: service, socket, timer, mount и другие типы. **Target** группирует units и задаёт точки системного lifecycle. Drop-ins позволяют менять нужные параметры, сохраняя основную конфигурацию пакета.

`Wants` и `Requires` описывают зависимости активации, а `After` и `Before` — порядок, не включая зависимый service сами по себе. Ordering не означает готовность удалённого API или БД. После изменения configuration manager должен перечитать units предусмотренным способом; изменение файла ещё не гарантирует обновление работающего процесса. [systemd.service](https://man7.org/linux/man-pages/man5/systemd.service.5.html).

# Как Type, ExecStart, Restart и ограничения частоты перезапуска определяют поведение сервиса?

`Type` определяет, какой момент systemd считает стартом сервиса: запуск процесса, успешный exec, уведомление readiness или завершение oneshot по правилам выбранного типа. `ExecStart` описывает команду и не является обычной строкой shell со всеми его операторами.

`Restart` задаёт реакцию на подходящие завершения, а start-rate limits предотвращают бесконечный быстрый restart loop. Также задают пользователя, рабочий каталог, environment и timeouts. Успешный запуск процесса не доказывает готовность бизнес-функции; для этого нужны подходящий service protocol и проверки. [Service options](https://man7.org/linux/man-pages/man5/systemd.service.5.html).

# Как journalctl, persistent journal и log rotation помогают исследовать сбой сервиса?

`journalctl` позволяет отбирать records по unit, boot, времени и другим metadata. При сбое сопоставляют сообщения приложения, systemd и kernel, учитывая timestamps и restart boundaries.

Сохранение journal между boots зависит от configuration и доступного persistent storage. Retention и размер журнала задают средствами journald; обычные текстовые application logs могут требовать отдельной rotation policy. Переименование log file не заставляет процесс автоматически открыть новый. Контролируют disk usage и доступ: logs могут содержать чувствительные данные, а отсутствующая запись иногда означает rate limiting или потерю collector, а не отсутствие ошибки.

# Как systemd timers отличаются от cron по расписанию, окружению и пропущенным запускам?

**systemd timer** активирует unit по календарному или monotonic schedule и использует service-модель с отдельными credentials, logging и dependencies. **Cron** запускает команды по своим правилам расписания и обычно с ограниченным environment; shell startup files не стоит считать гарантированными.

`Persistent=true` может компенсировать пропущенное календарное срабатывание timer, но не воспроизводит автоматически каждую историческую операцию. Если service уже активен, повторная активация имеет свои ограничения, а не обязательно создаёт параллельный экземпляр. Timezone, DST, randomized delay и длительность работы учитывают явно. [systemd.timer](https://man7.org/linux/man-pages/man5/systemd.timer.5.html).
