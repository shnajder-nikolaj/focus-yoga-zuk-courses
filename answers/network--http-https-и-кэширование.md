# Как устроено HTTP-сообщение запроса и ответа?

HTTP работает по модели request-response: клиент отправляет запрос, сервер возвращает ответ.

HTTP-сообщение состоит из:

1. Start line - метод, путь и версия протокола в запросе (`GET /users HTTP/1.1`) либо версия, статус и пояснение в ответе (`HTTP/1.1 200 OK`).
2. Headers - метаданные сообщения: тип содержимого, авторизация, кэширование и другие параметры.
3. Пустая строка - отделяет заголовки от тела в HTTP/1.x.
4. Body - необязательное содержимое, например JSON, HTML или файл.

В HTTP/2 и HTTP/3 сообщения передаются в бинарных фреймах, используются псевдозаголовки (`:method`, `:status`), но семантика запросов, ответов и заголовков сохраняется.

HTTPS - HTTP поверх защищённого соединения с TLS, обеспечивающим шифрование, целостность и проверку подлинности сервера.

# Какие HTTP-методы существуют и какие из них безопасные и идемпотентные?

Основные HTTP-методы:

- `GET` - получение представления ресурса.
- `HEAD` - получение метаданных ответа без тела.
- `POST` - передача данных для обработки, часто создание ресурса.
- `PUT` - создание или полная замена состояния ресурса по указанному URI.
- `PATCH` - частичное изменение ресурса.
- `DELETE` - удаление связи ресурса с указанным URI.
- `OPTIONS` - получение информации о поддерживаемых способах взаимодействия.
- `TRACE` - диагностическое отражение запроса, часто отключённое из соображений безопасности.
- `CONNECT` - установка туннеля через прокси.

Безопасные (safe) методы по определению не запрашивают изменения состояния сервера: `GET`, `HEAD`, `OPTIONS`, `TRACE`.

Идемпотентные методы при повторении одинакового запроса сохраняют тот же предполагаемый эффект: `GET`, `HEAD`, `OPTIONS`, `TRACE`, `PUT`, `DELETE`.

`POST` и `PATCH` не гарантируют идемпотентность, но конкретная реализация может её обеспечивать.

Безопасность здесь не означает защищённость: безопасный метод может создавать логи и метрики, но не должен выполнять запрошенные пользователем изменения состояния.

# Чем PUT отличается от PATCH?

`PUT` предназначен для создания или полной замены состояния ресурса по конкретному URI. Повторение идентичного запроса должно приводить к одинаковому результату, поэтому метод идемпотентен.

`PATCH` применяет к ресурсу набор изменений, не требуя передачи полного представления.

Например, для пользователя с полями `name` и `age`:

- `PUT /users/1` с полным объектом заменяет его состояние.
- `PATCH /users/1` с `{"name":"Alex"}` может обновить только имя.

Семантика `PATCH` зависит от формата документа изменений: например, JSON Patch (`application/json-patch+json`) или JSON Merge Patch (`application/merge-patch+json`).

`PATCH` может быть неидемпотентным: операция увеличения счётчика при каждом повторении изменяет значение. При этом простое присваивание конкретного значения обычно идемпотентно.

# Когда использовать POST вместо GET?

`GET` используют для получения данных без запрашиваемых изменений состояния. Его запросы можно кэшировать, сохранять в закладках и безопасно повторять.

`POST` используют, когда сервер должен обработать отправленные данные, например создать заказ, загрузить файл или выполнить операцию с побочными эффектами.

`POST` также подходит для сложных поисковых запросов, когда параметры неудобно или невозможно передать через URL. Однако такие запросы сложнее кэшировать стандартными механизмами.

Важно:

- Не использовать `GET` для операций изменения состояния.
- Не передавать секреты в URL: они могут оказаться в истории браузера, логах и аналитике.
- `POST` сам по себе не гарантирует ни конфиденциальности, ни защиты от повторного выполнения.

# Что означает идемпотентность запроса?

Идемпотентность означает, что многократное выполнение одного и того же запроса имеет такой же предполагаемый эффект на состояние сервера, как однократное.

Например:

- `PUT /users/1` с `{"name":"Alex"}` - повторная установка того же имени не меняет результат.
- `DELETE /users/1` - повторное удаление не должно вызывать дополнительных изменений состояния ресурса.
- `POST /payments` - повторный запрос может создать два платежа.

Идемпотентность не требует одинаковых HTTP-ответов. Например, первый `DELETE` может вернуть `204`, а повторный - `404`.

Это свойство важно для безопасных повторных попыток (retry) при сетевых сбоях. Для неидемпотентных операций часто используют `Idempotency-Key`, позволяющий серверу распознавать повторные запросы.

# Чем статусы 200, 201, 202 и 204 различаются?

Все четыре статуса обозначают успешную обработку запроса, но имеют разную семантику.

- `200 OK` - запрос успешно обработан. Обычно возвращается результат операции или представление ресурса.
- `201 Created` - создан один или несколько ресурсов. Заголовок `Location` может указывать URI основного созданного ресурса.
- `202 Accepted` - запрос принят к обработке, но выполнение ещё не завершено. Итог может оказаться неуспешным.
- `204 No Content` - запрос успешно обработан, но тело ответа отсутствует.

Например, создание пользователя обычно возвращает `201`, постановка длительной задачи в очередь - `202`, а успешное обновление без возвращаемых данных - `204`.

# Когда сервер должен возвращать 301, 302, 307 и 308?

Все эти статусы перенаправляют клиента на другой URI, обычно передаваемый через `Location`.

- `301 Moved Permanently` - ресурс постоянно перемещён. Клиентам и поисковым системам следует использовать новый адрес.
- `302 Found` - временное перенаправление, исходный URI остаётся актуальным.
- `307 Temporary Redirect` - временное перенаправление с обязательным сохранением метода и тела запроса.
- `308 Permanent Redirect` - постоянное перенаправление с обязательным сохранением метода и тела.

Ключевое отличие: при `301` и `302` браузер может преобразовать `POST` в `GET`, тогда как `307` и `308` запрещают такое преобразование.

Для перенаправления после успешного `POST` на страницу результата часто используют `303 See Other`, который предписывает получение результата через `GET` (кроме `HEAD`).

# Чем 401 отличается от 403?

`401 Unauthorized` означает, что запрос не содержит действительных учётных данных для доступа к ресурсу. Например, токен отсутствует, истёк или недействителен.

Ответ `401` должен содержать `WWW-Authenticate` с информацией о применимой схеме аутентификации.

`403 Forbidden` означает, что сервер понял запрос, но отказывается его выполнять. Причиной могут быть недостаточные права, политика безопасности или другое ограничение.

Например:

- Пользователь не передал токен - `401`.
- Пользователь авторизован, но не имеет прав администратора - `403`.

Для сокрытия существования защищённого ресурса сервер может вместо `403` возвращать `404`.

# Чем 404 отличается от 410?

`404 Not Found` означает, что сервер не нашёл актуальное представление ресурса либо не хочет раскрывать его существование. Статус не сообщает, является ли отсутствие временным или постоянным.

`410 Gone` означает, что ресурс больше недоступен и его отсутствие, вероятно, постоянное.

Примеры:

- Запрос несуществующего пользователя - `404`.
- Страница была окончательно удалена без замены - `410`.

Оба ответа могут кэшироваться при соблюдении правил HTTP-кэширования.

# Какие случаи подходят для 409, 412, 422 и 429?

- `409 Conflict` - запрос конфликтует с текущим состоянием ресурса. Например, попытка создать объект с уже существующим уникальным идентификатором.
- `412 Precondition Failed` - не выполнено условие запроса, заданное HTTP-заголовком, например `If-Match`. Используется для защиты от перезаписи изменений другого клиента.
- `422 Unprocessable Content` - сервер понимает тип содержимого и синтаксис корректен, но не может обработать инструкции. Например, указанное значение нарушает бизнес-правило.
- `429 Too Many Requests` - клиент превысил ограничение частоты запросов (rate limit). Заголовок `Retry-After` может указывать время ожидания.

Разница между `409` и `412`: первый описывает конфликт состояния, второй - конкретно невыполненное HTTP-предусловие.

# Чем 500, 502, 503 и 504 отличаются?

- `500 Internal Server Error` - сервер столкнулся с непредвиденной ошибкой при обработке запроса.
- `502 Bad Gateway` - сервер, работающий как шлюз или прокси, получил некорректный ответ от вышестоящего сервера (upstream).
- `503 Service Unavailable` - сервер временно не может обслужить запрос, например из-за перегрузки или технического обслуживания.
- `504 Gateway Timeout` - шлюз или прокси не получил необходимый ответ от upstream вовремя.

Например, если приложение выбросило необработанное исключение, возможен `500`. Если Nginx не смог получить корректный ответ от приложения - `502`, если приложение перегружено - `503`, а если ожидание upstream превысило тайм-аут - `504`.

Для временной недоступности можно использовать `Retry-After`, особенно с `503`.

# Для чего служат `Content-Type`, `Accept` и `Content-Encoding`?

`Content-Type` указывает медиа-тип содержимого сообщения, например `application/json`, `text/html` или `image/png`. Может дополнительно содержать кодировку символов, например `charset=utf-8`.

`Accept` указывает, какие медиа-типы ответа клиент готов принять. Например, `Accept: application/json` сообщает о предпочтении JSON. Если сервер не может предоставить подходящий формат, он может вернуть `406 Not Acceptable`.

`Content-Encoding` указывает преобразование, применённое к содержимому, например `gzip` или `br`. Клиент должен декодировать содержимое перед использованием.

Не путать `Content-Encoding` с `Transfer-Encoding`: первый описывает кодирование представления, второй - механизм передачи сообщения.

# Чем request headers отличаются от response headers?

Request headers передаются клиентом серверу и описывают запрос, возможности клиента и контекст обращения.

Примеры: `Authorization`, `Accept`, `Origin`, `If-None-Match`, `User-Agent`.

Response headers передаются сервером клиенту и описывают ответ, ресурс или правила его обработки.

Примеры: `Location`, `WWW-Authenticate`, `Set-Cookie`, `Cache-Control`, `ETag`.

Некоторые заголовки используются в обоих направлениях, но могут иметь разное значение. Например, `Cache-Control` в запросе задаёт требования клиента к кэшу, а в ответе - правила хранения и повторного использования ответа.

# Что делают `Origin`, `Referer` и `Host`?

- `Origin` указывает источник запроса: схему, хост и порт, без пути. Используется прежде всего для CORS и проверки источника потенциально опасных запросов.
- `Referer` указывает URL страницы, с которой был инициирован переход или запрос. Может включать путь и параметры, но его содержимое ограничивается `Referrer-Policy`.
- `Host` указывает целевой хост и необязательный порт, позволяя серверу обслуживать несколько сайтов на одном адресе.

В HTTP/2 и HTTP/3 целевой authority обычно передаётся через псевдозаголовок `:authority`.

`Origin` и `Referer` нельзя использовать как самостоятельное доказательство аутентификации: они могут отсутствовать, а вне браузера клиент способен устанавливать их самостоятельно.

# Как работают `Authorization` и `WWW-Authenticate`?

`Authorization` передаёт учётные данные клиента для доступа к защищённому ресурсу.

Например:

- `Authorization: Bearer <token>` - токен доступа.
- `Authorization: Basic <credentials>` - логин и пароль в Base64, а не в зашифрованном виде.

`WWW-Authenticate` передаётся сервером, обычно вместе с `401`, и сообщает клиенту, какая схема аутентификации применяется и какие параметры необходимы.

Типичный процесс:

1. Клиент запрашивает защищённый ресурс.
2. Сервер возвращает `401` с `WWW-Authenticate`.
3. Клиент повторяет запрос с подходящим `Authorization`.
4. Сервер проверяет учётные данные и права доступа.

В API с Bearer-токенами клиент часто отправляет `Authorization` сразу, без предварительного `401`.

Учётные данные нужно передавать через HTTPS и не записывать в логи.

# Как браузер обрабатывает редиректы?

Получив ответ `3xx` с заголовком `Location`, браузер определяет новый URL и выполняет следующий запрос.

При этом:

1. Относительный `Location` преобразуется в абсолютный URL.
2. Метод и тело запроса сохраняются или изменяются в соответствии со статусом перенаправления.
3. Для нового адреса заново применяются правила cookies, аутентификации, CORS и безопасности.
4. Браузер следует цепочке редиректов, пока не получит конечный ответ или не обнаружит ошибку, например цикл.

Постоянные редиректы могут кэшироваться.

В `fetch()` перенаправления по умолчанию обрабатываются автоматически (`redirect: "follow"`). Также доступны режимы `error` и `manual`, но последний в браузере ограничивает доступ к деталям ответа перенаправления.

# Чем `gzip`, `br` и `zstd` отличаются на уровне HTTP-сжатия?

Все три алгоритма применяются для уменьшения размера передаваемых данных и обозначаются через `Content-Encoding`.

- `gzip` - широко совместимый алгоритм на основе DEFLATE. Обычно обеспечивает хорошую скорость при умеренном сжатии.
- `br` (Brotli) - часто обеспечивает лучшее сжатие текстовых ресурсов, особенно при предварительном сжатии статических файлов.
- `zstd` (Zstandard) - сочетает высокую скорость сжатия и распаковки с хорошей степенью сжатия, особенно полезен для динамических данных.

Клиент сообщает о поддерживаемых алгоритмах через `Accept-Encoding`, например `gzip, br, zstd`. Сервер выбирает подходящий алгоритм и возвращает его в `Content-Encoding`.

Оптимальный выбор зависит от типа данных, размера, CPU и уровня сжатия. Уже сжатые изображения и видео обычно почти не выигрывают от дополнительного сжатия.

# Как работают range requests и заголовок `Range`?

Range requests позволяют клиенту запрашивать только часть представления ресурса, а не скачивать его целиком. Используются для возобновления загрузок, перемотки видео и частичного чтения файлов.

Например, `Range: bytes=0-1023` запрашивает первые 1024 байта.

Возможные ответы:

- `206 Partial Content` - сервер вернул запрошенный диапазон с `Content-Range`.
- `200 OK` - сервер проигнорировал `Range` и вернул ресурс целиком.
- `416 Range Not Satisfiable` - запрошенный диапазон не может быть удовлетворён.

`Accept-Ranges: bytes` сообщает о поддержке байтовых диапазонов.

Заголовок `If-Range` позволяет скачать оставшуюся часть только при условии, что ресурс не изменился; иначе сервер возвращает полное представление.

Диапазоны относятся к байтам передаваемого представления, поэтому при `Content-Encoding` учитываются байты сжатой формы.

# Для чего нужен `Vary` и какие риски возникают при его неверной настройке?

`Vary` сообщает HTTP-кэшу, какие заголовки запроса влияют на содержимое ответа и должны учитываться при выборе кэшированной версии.

Например, `Vary: Accept-Encoding` позволяет отдельно хранить версии ресурса, сжатые с помощью `gzip`, `br` и других алгоритмов.

Другой пример - `Vary: Accept-Language`, когда сервер возвращает разные языковые версии одного ресурса.

Неправильная настройка может привести к:

- Утечке данных - один пользователь получает закэшированный ответ, предназначенный другому.
- Некорректному содержимому - возвращается неподходящий язык или формат.
- Низкой эффективности кэша - слишком много вариантов ответа уменьшают cache hit rate.

Особенно важно корректно учитывать `Origin` при кэшировании ответов с динамическими CORS-заголовками.

`Vary` не заменяет контроль доступа и `Cache-Control: private` для персонализированных данных.

# Как использовать correlation/request ID при диагностике API?

Correlation ID - уникальный идентификатор, позволяющий связать события и логи, относящиеся к одному запросу, даже если он проходит через несколько сервисов.

Обычно процесс выглядит так:

1. API Gateway принимает запрос и генерирует идентификатор, если его нет.
2. Идентификатор передаётся downstream-сервисам через заголовок, например `X-Request-ID`.
3. Каждый сервис записывает его в структурированные логи.
4. Идентификатор можно вернуть клиенту для последующей диагностики.

При ошибке разработчик ищет этот ID в логах и восстанавливает последовательность обработки запроса.

Для полноценной распределённой трассировки используют стандарт W3C Trace Context с заголовками `traceparent` и `tracestate`. Он позволяет объединять операции в trace, состоящий из отдельных span.

Входящие идентификаторы следует проверять, ограничивать по длине и не использовать для передачи чувствительных данных.

# Какие уровни кэша бывают между браузером и сервером?

Кэширование может происходить на нескольких уровнях:

1. Browser HTTP Cache - кэш браузера в памяти или на диске. Сохраняет HTTP-ответы согласно правилам кэширования.
2. Service Worker Cache - управляемое приложением хранилище через Cache API. Позволяет реализовать собственную стратегию, включая offline-first.
3. Proxy Cache - промежуточный кэш, например на Nginx, который сокращает количество обращений к backend.
4. CDN Cache - распределённый кэш на географически близких к пользователям узлах.
5. Application Cache - кэш внутри приложения, например Redis или in-memory cache, для данных и результатов вычислений.

Первые четыре уровня могут хранить HTTP-ответы, но Service Worker использует собственную логику. Application Cache обычно работает с данными, а не непосредственно с HTTP-представлениями.

Cache hit означает, что данные получены из кэша. Cache miss - что их пришлось запрашивать у следующего уровня.

# Что означают `Cache-Control: no-cache`, `no-store`, `max-age` и `immutable`?

`Cache-Control` управляет хранением и повторным использованием HTTP-ответов.

- `no-cache` - разрешает хранение ответа, но требует успешной проверки актуальности перед повторным использованием.
- `no-store` - запрещает HTTP-кэшам сохранять запрос или ответ для последующего использования.
- `max-age=3600` - устанавливает время свежести ответа в секундах. В данном случае - один час.
- `immutable` - сообщает, что содержимое не изменится, пока ответ считается свежим, позволяя избегать лишней проверки актуальности.

Например:

`Cache-Control: public, max-age=31536000, immutable`

Подходит для статического файла с хэшем в имени, содержимое которого никогда не изменяется по тому же URL.

Важно: `no-cache` не означает запрет кэширования. Для этого предназначен `no-store`.

# Чем private cache отличается от shared cache?

Private cache предназначен для одного пользователя или клиентского контекста. Типичный пример - HTTP-кэш браузера.

Shared cache обслуживает нескольких пользователей. Примеры - CDN и кэширующий reverse proxy.

Директивы:

- `Cache-Control: private` - разрешает хранение в приватном кэше, но запрещает хранение полного ответа в shared cache.
- `Cache-Control: public` - явно разрешает кэширование в shared cache при соблюдении остальных правил.
- `Cache-Control: no-store` - запрещает хранение в обоих типах кэша.

Ответы на запросы с `Authorization` по умолчанию нельзя сохранять в shared cache, если специальные директивы не разрешают это.

Ключевой риск shared cache - возможность передачи персонализированного ответа другому пользователю при неправильной конфигурации.

# Как работают `ETag` и `If-None-Match`?

`ETag` - идентификатор версии представления ресурса, который сервер возвращает в заголовке ответа.

Например, `ETag: "v123"`.

При повторном обращении клиент может отправить `If-None-Match: "v123"`.

Сервер сравнивает полученный идентификатор с текущим:

- Если представление не изменилось - возвращает `304 Not Modified` без тела.
- Если изменилось - возвращает `200 OK` с актуальными данными и новым `ETag`.

Существуют два вида ETag:

- Strong ETag (`"abc"`) - предполагает байтовую эквивалентность представлений.
- Weak ETag (`W/"abc"`) - допускает байтовые различия при сохранении семантической эквивалентности.

Для защиты от потерянных обновлений используют `If-Match` со strong ETag. Если версия изменилась, сервер может вернуть `412 Precondition Failed`.

# Чем `Last-Modified` отличается от `ETag`?

Оба механизма позволяют выполнять условные HTTP-запросы и избегать повторной передачи неизменившихся данных.

`Last-Modified` содержит дату последнего изменения представления. Клиент проверяет её через `If-Modified-Since`.

`ETag` содержит идентификатор версии представления. Клиент проверяет его через `If-None-Match`.

Основные различия:

- `Last-Modified` использует время с точностью до секунды, поэтому может пропустить несколько изменений за одну секунду.
- `ETag` может точнее отражать изменение содержимого, если сервер правильно генерирует идентификаторы.
- `ETag` не обязан быть хэшем файла. Это может быть версия из базы данных или другой идентификатор.

Если клиент передаёт одновременно `If-None-Match` и `If-Modified-Since`, сервер должен отдавать приоритет `If-None-Match`.

# Почему сервер возвращает 304 Not Modified?

`304 Not Modified` означает, что сохранённое клиентом представление ресурса всё ещё актуально и его не нужно передавать повторно.

Обычно это происходит при условном `GET` или `HEAD` с `If-None-Match` либо `If-Modified-Since`.

Например:

1. Клиент получает ресурс с `ETag: "abc"`.
2. Когда требуется проверить его актуальность, отправляет `If-None-Match: "abc"`.
3. Сервер подтверждает, что ресурс не изменился, и возвращает `304`.
4. Клиент использует ранее сохранённое тело ответа и обновляет необходимые метаданные кэша.

Преимущество - экономия трафика.

Но `304` всё равно требует сетевого обращения к серверу, поэтому он обычно медленнее использования свежего ответа непосредственно из кэша.

# Как работает stale-while-revalidate?

`stale-while-revalidate` позволяет временно отдавать устаревший ответ из кэша, одновременно проверяя или обновляя его в фоне.

Например:

`Cache-Control: max-age=60, stale-while-revalidate=300`

Поведение:

1. Первые 60 секунд ответ считается свежим.
2. Следующие 300 секунд кэш может немедленно отдавать устаревшую версию.
3. При обращении в этот период запускается фоновая ревалидация.
4. После обновления кэша следующие запросы получают актуальную версию.

Если допустимый период устаревания закончился, требуется обычная проверка актуальности или получение нового ответа.

Преимущество - низкая задержка для пользователя. Недостаток - возможность временного отображения устаревших данных.

Подходит для публичного контента, но требует осторожности с данными, которые должны быть строго актуальными.&#x20;

# Как организовать кэширование файлов с хэшами в имени?

Используется подход content hashing (cache busting): в имя файла добавляется хэш его содержимого.

Например:

`app.a1b2c3.js`

При изменении содержимого сборщик генерирует новый хэш и новый URL:

`app.d4e5f6.js`

Такие файлы можно кэшировать надолго:

`Cache-Control: public, max-age=31536000, immutable`

При этом:

- HTML-документ должен получать актуальную версию ссылок, поэтому для него обычно используют `no-cache` с ревалидацией.
- Старые версии файлов нужно сохранять некоторое время, поскольку открытые страницы могут продолжать их запрашивать.
- При новом релизе браузер скачает изменившиеся файлы, а неизменившиеся возьмёт из кэша.

Это позволяет эффективно кэшировать статические ресурсы без ручной очистки браузерного кэша.&#x20;

# Почему нельзя бездумно кэшировать персонализированные HTTP-ответы?

Персонализированный ответ может содержать личные данные, токены, сведения о заказах или настройках пользователя.

Если shared cache сохраняет такой ответ по общему ключу, например только по URL, другой пользователь может получить чужие данные.

Дополнительные проблемы:

- Пользователь может видеть устаревшие права доступа после их изменения.
- После выхода из аккаунта в кэше могут оставаться чувствительные данные.
- Неправильно настроенный `Vary` может смешивать ответы разных пользователей.

Для персонализированных данных используют `Cache-Control: private` либо `no-store`, если сохранение недопустимо.

Если персонализированное кэширование всё же необходимо, ключи должны учитывать контекст пользователя, а стратегия инвалидации - изменения авторизации и данных.

Важно: `private` запрещает shared cache, но не запрещает браузеру сохранять ответ.

# Что такое cache poisoning?

Cache poisoning - атака, при которой злоумышленник заставляет кэш сохранить вредоносный или некорректный ответ, который затем получают другие пользователи.

Частая причина - несоответствие между параметрами, влияющими на формирование ответа, и параметрами, входящими в ключ кэша.

Например:

1. Сервер формирует абсолютные ссылки на основе недоверенного `X-Forwarded-Host`.
2. Кэш не учитывает этот заголовок в своём ключе.
3. Злоумышленник отправляет запрос с подставленным значением.
4. Сервер возвращает ответ с вредоносной ссылкой.
5. Кэш сохраняет его и раздаёт обычным пользователям.

Последствия могут включать XSS, подмену ссылок и нарушение доступности.

Защита: проверка входных заголовков, корректные cache keys, настройка `Vary`, исключение пользовательских данных из публичного кэша и ограничение кэшируемых ответов.

# Чем CDN отличается от обычного reverse proxy?

Reverse proxy принимает запросы от клиентов и перенаправляет их на внутренние серверы. Может выполнять балансировку нагрузки, TLS termination, маршрутизацию и кэширование.

CDN (Content Delivery Network) - географически распределённая сеть серверов, предназначенная для доставки содержимого пользователям с низкой задержкой.

Главные различия:

- Reverse proxy обычно развёрнут перед определённой инфраструктурой приложения.
- CDN имеет множество распределённых точек присутствия (PoP), расположенных ближе к пользователям.
- CDN может обслуживать запросы из локального edge cache без обращения к origin-серверу.
- CDN часто предоставляет дополнительные возможности: защиту от DDoS, управление кэшем, оптимизацию контента.

CDN технически использует механизмы reverse proxy, но отличается распределённой архитектурой и масштабом.

# Как выполнять инвалидацию CDN-кэша после релиза?

Инвалидация - удаление или пометка устаревших объектов в CDN-кэше, чтобы последующие запросы получили актуальные данные.

Основные подходы:

- Versioned URLs - использование хэшей в именах файлов. Новая версия получает новый URL, поэтому старый кэш не мешает обновлению.
- Purge by URL - точечная очистка конкретных адресов через API CDN.
- Purge by tag - очистка группы ресурсов по специальному тегу, если CDN поддерживает такую возможность.
- TTL expiration - ожидание окончания срока свежести ответа.

Для frontend-приложений обычно используют хэшированные JS/CSS-файлы с длительным кэшированием, а HTML обновляют через короткий TTL или обязательную ревалидацию.

Важно: очистка CDN не очищает кэш браузеров пользователей. Кроме того, массовая инвалидация может резко увеличить нагрузку на origin.

# Что такое edge caching и какие ограничения у него есть?

Edge caching - хранение HTTP-ответов на серверах, расположенных географически или топологически ближе к пользователям.

Когда пользователь обращается к ресурсу:

1. Запрос поступает на подходящий edge-сервер.
2. При cache hit ответ возвращается непосредственно с edge.
3. При cache miss сервер обращается к origin или другому уровню кэша.
4. Полученный ответ сохраняется при соблюдении правил кэширования.

Преимущества: меньшая задержка, снижение нагрузки на origin и экономия сетевого трафика.

Ограничения:

- Разные edge-узлы могут временно хранить разные версии данных.
- Инвалидация распределённого кэша может занимать время.
- Персонализированные данные требуют осторожной изоляции.
- Большое количество вариантов ответа снижает эффективность кэша.
- Не каждый ответ подходит для edge caching, особенно если требуется строго актуальное состояние.

# Какие механизмы приоритизации ресурсов доступны браузеру?

Браузер самостоятельно определяет приоритет загрузки ресурсов с учётом их типа, расположения и влияния на отображение страницы.

Разработчик может влиять на загрузку несколькими механизмами:

- `fetchpriority="high|low|auto"` - подсказка браузеру об относительном приоритете загрузки. Например, `high` для LCP-изображения.
- `preload` - раннее обнаружение и начало загрузки ресурса, который понадобится в ближайшее время.
- `modulepreload` - предварительная загрузка JavaScript-модулей.
- `preconnect` - заблаговременное установление соединения с другим origin.
- `dns-prefetch` - предварительное разрешение DNS.
- `loading="lazy"` - откладывание загрузки изображений и iframe, которые пока не нужны.
- `async` и `defer` - управление загрузкой и выполнением скриптов без обычной блокировки HTML-парсера.

`fetchpriority` не гарантирует абсолютного приоритета: итоговое решение остаётся за браузером.

Важно различать: `preload` влияет прежде всего на момент обнаружения ресурса, а `fetchpriority` - на его относительный приоритет.&#x20;

# Как настроить preload критичных шрифтов без лишних запросов?

Font preload позволяет начать загрузку шрифта раньше, чем браузер обнаружит его использование после обработки CSS.

Пример:

```
<link
  rel="preload"
  href="/fonts/main.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
```

Ключевые правила:

1. Использовать `as="font"`, чтобы браузер правильно классифицировал ресурс.
2. Указывать `type="font/woff2"`, чтобы браузер мог проверить поддержку формата.
3. Указывать `crossorigin` даже для шрифтов с того же origin, поскольку шрифты загружаются в CORS-режиме.
4. URL должен точно совпадать с адресом шрифта, используемым в `@font-face`.
5. Предзагружать только шрифты, действительно необходимые для первоначального отображения страницы.

При несовпадении URL или режима CORS браузер может выполнить двойную загрузку.

Свойство `font-display: swap` позволяет отображать текст резервным шрифтом до завершения загрузки основного, уменьшая время появления текста.&#x20;

# Как анализировать waterfall в Network DevTools?

Waterfall в Chrome DevTools показывает последовательность HTTP-запросов, их длительность и зависимости при загрузке страницы.

Основные этапы запроса:

- Queueing / Stalled - ожидание перед отправкой запроса из-за приоритетов, ограничений соединений или других факторов.
- DNS Lookup - определение IP-адреса сервера.
- Initial Connection / SSL - установка сетевого соединения и согласование TLS.
- Request Sent - отправка запроса.
- Waiting (TTFB) - ожидание первого байта ответа, включающее сетевую задержку и обработку сервером.
- Content Download - получение тела ответа.

При анализе важно проверять:

1. Длинный TTFB - возможные проблемы с серверной обработкой, кэшем или сетевой задержкой.
2. Большое Content Download - крупные ресурсы или низкая пропускная способность сети.
3. Позднее начало загрузки - ресурс обнаружен слишком поздно, например из-за цепочки JavaScript-зависимостей.
4. Длинные Queueing/Stalled - конкуренция запросов за доступные ресурсы.
5. Повторные загрузки и редиректы - лишние сетевые обращения.
6. Размеры и кэширование - сравнение transferred size, resource size, статусов и источника ответа: сеть, memory cache, disk cache или Service Worker.

Для корректного анализа используют `Disable cache`, `Preserve log` и network throttling, сравнивают холодную и повторную загрузку.

Главная задача - найти ресурсы и зависимости, которые задерживают критический путь отображения страницы, особенно LCP (Largest Contentful Paint).&#x20;
