# Чем SLI, SLO и SLA различаются в управлении надёжностью сервиса?

**SLI** — измеримый показатель качества сервиса, например доля успешно завершённых пользовательских операций. **SLO** — целевое значение этого показателя с определённым окном: например, не менее 99,9% успешных операций за 30 дней.

**SLA** — соглашение об уровне сервиса с формально определёнными обязательствами и последствиями нарушения. Оно может использовать иные окна и исключения, чем внутренний SLO. Рабочие цели выбирают так, чтобы успевать реагировать до нарушения внешних обязательств. SLO полезен только при однозначном способе измерения. [Google SRE: Service Level Objectives](https://sre.google/sre-book/service-level-objectives/).

# Как определить good events и valid events для пользовательского SLI?

Для event-based SLI задают `SLI = good events / valid events`. **Valid events** — согласованная совокупность операций, к которым относится обещание; **good events** — операции, удовлетворяющие критерию успеха. Например, оформление заказа успешно, если оно завершилось корректно в пределах deadline.

Заранее определяют учёт retries, отмен, клиентских ошибок, timeout и неполной телеметрии. Источник измерения должен видеть и операции, не дошедшие до приложения, если они входят в обещание. Исключение неуспешных запросов из знаменателя делает показатель красивым, но отрывает его от пользовательского опыта.

# Как выбрать availability, latency, freshness и correctness SLIs для разных сценариев?

`Availability` показывает возможность успешно выполнить нужную операцию. `Latency` отражает долю операций, уложившихся в порог времени. `Freshness` важна для потоков данных и аналитики: насколько свежи доступные результаты. `Correctness` проверяет, соответствует ли результат ожидаемым правилам, даже если сервер вернул HTTP 200.

Для batch pipeline важнее своевременно обработанные данные, чем доступность HTTP endpoint. Для оплаты одной availability недостаточно без корректности и защиты от повторного списания. Критичные сценарии получают отдельные показатели, чтобы большой объём простых чтений не скрыл отказ редкой важной операции. [Implementing SLOs](https://sre.google/workbook/implementing-slos/).

# Как rolling и calendar windows меняют оценку SLO и error budget?

**Calendar window** привязано к фиксированному периоду, например месяцу; новый период начинает новый расчёт. **Rolling window** постоянно сдвигается, например охватывает последние 30 дней: старые события постепенно выходят из него.

Calendar window удобно для регулярной отчётности, но близость границы может резко менять остаток бюджета. Rolling window лучше сохраняет связь с недавним опытом, однако бюджет восстанавливается по мере выхода плохих событий и изменения состава трафика. Правила расчёта, timezone и трактовку частично прошедшего периода фиксируют явно; сравнивать разные окна как одинаковые нельзя.

# Как рассчитать request-based error budget и почему его нельзя автоматически переводить в downtime?

При request-based SLO `S` и `N` valid events допустимое число bad events равно `(1 − S) × N`. Например, при SLO 99,9% и миллионе операций бюджет составляет 1000 плохих событий. Если уже было 700, для этого объёма остаётся 300; по мере поступления новых valid events знаменатель тоже меняется.

Такой бюджет нельзя автоматически назвать числом минут простоя: минута пикового трафика может затронуть больше запросов, чем час ночью. Время получается непосредственно из time-based availability с определёнными bad intervals либо из дополнительных предположений о трафике и характере отказа.

# Что такое burn rate и как оценить время исчерпания error budget?

**Burn rate** равен наблюдаемой доле bad events, делённой на допустимую долю: `B = error_ratio / (1 − SLO)`. При SLO 99,9% и текущих 2% ошибок получается `B = 20`.

При стационарном трафике полный бюджет 30-дневного окна с таким темпом расходуется примерно за `30 / 20 = 1,5` дня. Это оценка, а не обещание: уже потраченный бюджет уменьшает срок, изменение интенсивности и rolling window меняют расчёт. Для оперативной оценки также считают остаток bad events и текущую скорость их появления. [Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/).

# Как multi-window burn-rate alerts обнаруживают быстрые и медленные нарушения SLO?

Длинное окно подтверждает существенное расходование бюджета, а короткое проверяет, что нарушение продолжается сейчас. Для одной пары окон условия связывают через `AND`; разные пары для быстрого и медленного расхода — через `OR`.

Например, быстрый page может требовать повышенный burn rate одновременно за час и за пять минут; более медленное устойчивое нарушение — более длинные окна или ticket. Пороги выбирают по доле бюджета, которую готовы потратить до реакции, и времени работы команды. Учитывают низкий трафик, пропуски данных и подавление дублирующих alerts. [Multi-window alerts](https://sre.google/workbook/alerting-on-slos/).

# Как error budget policy влияет на релизы и приоритет reliability work?

**Error budget policy** заранее определяет действия при разных уровнях расходования: усиление наблюдения, уменьшение риска релизов, приоритет исправлений, а при исчерпании — временное ограничение обычных изменений. Критические исправления и аварийные действия должны иметь явно согласованные правила.

Политику принимают вместе владельцы продукта и сервиса. Она превращает спор «быстрее выпускать или повышать надёжность» в решение по данным и допустимому риску. Это не наказание команде и не требование никогда не ошибаться. После восстановления обсуждают причины расхода и пересматривают приоритеты. [Example Error Budget Policy](https://sre.google/workbook/error-budget-policy/).

# Как зависимости и частичные отказы влияют на достижимость пользовательского SLO?

Если пользовательская операция требует последовательного успеха нескольких зависимостей, её доступность ограничена всей цепочкой. В упрощённой модели независимых отказов три обязательных компонента с доступностью 99,9% дают около `0,999³ = 99,7%` для операции. Коррелированные отказы и различие моделей измерения делают простое произведение ненадёжным прогнозом.

Fallback, caching и optional dependencies могут уменьшить влияние, если их результат удовлетворяет пользовательскому SLI. Shared DNS, identity или control plane способны создать общий failure domain. Поэтому SLO измеряют end-to-end и проверяют реальную деградацию, а не складывают обещания поставщиков.

# Как пересматривать SLO при низком трафике, изменении продукта и неполной телеметрии?

При низком трафике одна ошибка сильно меняет долю; отсутствие запросов не доказывает доступность. В зависимости от цены отказа используют более подходящие окна, отдельные критичные сценарии и synthetic probes, сохраняя различие между probes и реальными пользовательскими событиями.

Пропавшие метрики не трактуют автоматически как успех: наблюдают полноту измерений. При изменении продукта проверяют актуальность population и ожиданий, согласуют новую цель и версию определения. Нельзя менять знаменатель задним числом только ради прохождения отчёта. Более строгий SLO оправдан, когда дополнительная надёжность приносит ценность соразмерно стоимости. [Embracing Risk](https://sre.google/sre-book/embracing-risk/).
