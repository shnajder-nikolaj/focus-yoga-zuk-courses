# Как layered architecture распределяет обязанности backend-приложения?

В типичной layered architecture транспортный слой принимает запрос и формирует ответ, application layer координирует сценарий, domain layer содержит бизнес-правила, а data access или infrastructure работает с БД и внешними системами. Конкретный набор слоёв зависит от сложности приложения.

Нужно явно задать допустимые зависимости: строгие слои разрешают обращения через соседний слой, более свободная схема допускает пропуски. Одно наличие папок `controllers`, `services`, `repositories` не защищает границы, если бизнес-логика свободно обращается к HTTP и SQL.

# Чем логический слой отличается от физического tier развёртывания?

**Layer** — логическое разделение обязанностей и зависимостей в коде. **Tier** — физическая граница размещения, например отдельный процесс или сервер. Несколько слоёв могут выполняться внутри одного backend-процесса.

Перенос слоя в отдельный сервис добавляет сетевые задержки, частичные отказы, версионирование контракта и отдельную эксплуатацию. Поэтому выделение application и domain layers не означает обязательных микросервисов. Физическую границу выбирают по потребности в изоляции, масштабировании и независимом жизненном цикле.

# Как правило зависимостей Clean Architecture применяется к backend use case?

Исходные зависимости направляют к более внутренним правилам. Use case может зависеть от доменной модели и нужного ему интерфейса хранилища, но не от HTTP-фреймворка, ORM или SDK поставщика. Внешний адаптер реализует этот интерфейс.

Например, `ConfirmOrder` вызывает порт `OrderRepository`, а `SqlOrderRepository` использует БД. Во время выполнения управление может уходить наружу через интерфейс; это не меняет направление зависимостей исходного кода. Структуры данных на границе не должны требовать инфраструктурных типов. [Dependency Rule](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html).

# Как Hexagonal Architecture разделяет входные и выходные порты backend-сервиса?

Входной порт задаёт возможность приложения, например оформить заказ; HTTP controller, обработчик сообщения и CLI выступают входными адаптерами. Выходной порт описывает потребность приложения, например сохранить заказ или запросить курс валют, а SQL repository и HTTP-клиент реализуют её.

Порты выражают назначение и контракт, а не конкретный транспорт. Один use case можно вызвать разными адаптерами без дублирования бизнес-правил. Количество сторон на рисунке не диктует число интерфейсов или слоёв. [Оригинальная Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture).

# Как Onion Architecture организует зависимости вокруг доменной модели?

В **Onion Architecture** центральное положение занимает доменная модель. Вокруг располагают доменные и прикладные сервисы, а инфраструктура и способы взаимодействия находятся снаружи. Код внешних колец может зависеть от внутренних, обратное направление ограничивается.

Например, домен определяет необходимый контракт repository, а БД-адаптер реализует его и подключается при запуске. Подход родственен Clean и Hexagonal Architecture; различаются акценты и терминология. Его ценность — управляемые зависимости, а не обязательное количество колец и проектов. [Onion Architecture автора](https://jeffreypalermo.com/2008/07/the-onion-architecture-part-1/).

# Как MVC соотносится со слоями backend-приложения?

**MVC** разделяет взаимодействие пользователя с представлением: model описывает состояние и поведение, view формирует отображение, controller обрабатывает вход и координирует ответ. В web backend view может быть HTML-шаблоном; для JSON API роль представления выполняется сериализацией ответа.

MVC не задаёт всю архитектуру приложения. За controller могут находиться application services, доменная модель и data access. Model не обязательно означает ORM entity. Тонкий controller передаёт выполнение бизнес-сценарию, чтобы правила не зависели от маршрутов и формата HTTP.

# Как отделить HTTP DTO, доменную модель и ORM-модель без лишнего дублирования?

HTTP DTO описывает внешний контракт, доменная модель — поведение и инварианты, ORM-модель — хранение и связи. Разделение полезно, когда эти формы эволюционируют независимо: например, внешний ответ скрывает внутренние поля, а aggregate хранится в нескольких таблицах.

Преобразования делают на явных границах и проверяют для важных полей. Копия каждого объекта в трёх слоях без различий добавляет работу и ошибки. В простом CRUD допустима общая структура, если она не раскрывает секреты и не связывает бизнес-правила с нежелательным инфраструктурным контрактом.

# Где размещать бизнес-валидацию, проверку прав и обработку ошибок?

Транспорт проверяет синтаксис и форму входа, а домен — бизнес-инварианты, которые должны сохраняться при любом способе вызова. Application layer проверяет право исполнить сценарий, загружает необходимые данные и координирует действия; контекстные бизнес-ограничения остаются в модели.

Ошибки БД и внешних сервисов адаптер переводит в понятный приложению контракт, а HTTP-адаптер — в статус и безопасное тело ответа. Нельзя полагаться только на UI-валидацию или проверку роли в одном маршруте: тот же сценарий может запускаться worker.

# Где определять границу транзакции и как передавать её нескольким repository?

Граница транзакции обычно соответствует прикладному сценарию или отдельному атомарному шагу. Use case определяет требуемую атомарность, а инфраструктура предоставляет соединение, transaction context или `Unit of Work`.

Все repository, участвующие в этой локальной транзакции, должны использовать один подходящий transaction context. Если каждый открывает своё соединение и делает commit независимо, общая атомарность исчезает. Не следует держать транзакцию БД открытой на время долгого внешнего вызова; такой процесс лучше разделить на сохраняемые шаги с восстановлением.

# Как composition root связывает use cases и инфраструктурные адаптеры?

**Composition root** — место сборки приложения, обычно код запуска. Здесь создают конфигурацию, подключения, repository и внешние клиенты, после чего передают зависимости use cases и транспортным адаптерам.

DI-контейнер автоматизирует сборку, но не является обязательным: явные конструкторы часто достаточны. Домен и use cases не должны искать произвольные зависимости через глобальный контейнер, иначе реальные требования скрываются. Также здесь определяют lifetime объектов и корректное завершение работы соединений и workers.

# Как тестировать бизнес-сценарий отдельно от HTTP, брокера и базы данных?

Use case вызывают напрямую, подставляя fake или stub для выходных портов. Проверяют наблюдаемое бизнес-поведение: допустимый переход состояния, отказ при нарушении инварианта и согласованное сохранение результата. Fake должен воспроизводить существенные свойства контракта, включая ошибки и конкуренцию, если они важны.

Отдельные интеграционные проверки нужны для SQL-ограничений, маппинга, сериализации и реального транспорта. Успешный тест с in-memory repository не доказывает правильность транзакции в БД. Проверки границ и адаптеров дополняют тесты домена.

# Когда достаточно простой layered architecture и как избежать церемониальных абстракций?

Простых слоёв достаточно, когда сценарии понятны, бизнес-правил немного и команда может безопасно менять код без множества согласованных правок. Выделяют интерфейсы и модели там, где есть реальная граница, необходимость независимого тестирования или изменяемая зависимость.

Если каждый запрос проходит через несколько классов, которые только передают одинаковые аргументы дальше, проверяют пользу этих переходов. Архитектуру можно усложнять постепенно по мере появления поведения. Число файлов и названия паттернов не являются показателями качества.
