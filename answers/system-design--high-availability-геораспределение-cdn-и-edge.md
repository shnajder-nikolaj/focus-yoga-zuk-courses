# Как связать требования High Availability с пользовательскими сценариями и допустимой деградацией?

Сначала выделяют критичные пользовательские операции, аудитории, регионы и допустимую длительность нарушения. Затем для каждой операции определяют успех: доступность устаревшего чтения, например, может быть приемлемой для каталога, но недостаточной для подтверждения остатка товара.

Из этого выводят необходимые failure scenarios, целевые показатели и degraded modes: read-only, отключение необязательной функции или обслуживание из кэша. HA оценивают по end-to-end результату. Наличие нескольких replicas полезно только тогда, когда routing, данные, authentication и ёмкость позволяют действительно продолжить сценарий.

# Как построить карту зональных, региональных и глобальных зависимостей HA-системы?

На карте показывают data path и обязательные зависимости: load balancers, identity, DNS, keys, databases, queues и внешние APIs. Для каждого компонента отмечают scope отказа и расположение копий. Отдельно показывают control plane, release и configuration paths.

Один глобальный credential service или ошибочный rollout может одновременно затронуть физически независимые регионы. Поэтому проверяют shared dependencies, механизмы изоляции и поэтапность изменений. Карта помогает отличить защиту от потери узла от защиты от отказа zone, region или общего поставщика.

# Как выбрать home region tenant и разместить write path в геораспределённом сервисе?

Home region задаёт основной путь работы tenant или конкретного набора данных. Его выбирают по расположению пользователей, требованиям к данным, latency и operational constraints. Запись обычно направляют к определённому владельцу, а remote reads обслуживают по выбранной модели свежести.

Нужны routing metadata, версия назначения и процедура переноса. При смене владельца старый write path блокируют и проверяют актуальность данных, иначе два региона могут независимо изменять один инвариант. Разные tenants можно распределить по разным home regions, сохранив понятное владение записью внутри каждого scope.

# Как межрегиональная репликация и quorum влияют на latency и поведение при partition?

Синхронное межрегиональное подтверждение добавляет сетевую задержку и зависит от доступности нужного quorum. Размещение голосующих replicas определяет, потерю каких регионов система переживает. Само большинство не гарантирует нужную consistency без корректного протокола чтения, записи и выбора leader.

Асинхронная replication уменьшает задержку локального commit, но допускает lag и потерю последних записей при аварийном promotion. Во время partition заранее выбирают поведение по операциям: отказ, stale read или запись по согласованному ownership. Фраза «active-active» не определяет разрешение конфликтов и сохранение бизнес-инвариантов.

# Как DNS routing, Anycast и global load balancing переключают пользовательский трафик?

**DNS routing** меняет адреса в ответах, но resolver caches и уже открытые соединения задерживают эффект; малый TTL не даёт мгновенного переключения всех клиентов. **Anycast** публикует один адрес из нескольких мест и использует выбор сетевого маршрута, который не обязательно совпадает с географической близостью.

Global load balancing может учитывать health и ёмкость backend на уровне сервиса. Для каждого механизма нужны корректный health signal, предотвращение flapping и понимание поведения длительных sessions. Недоступность приложения должна быть связана с исключением плохого назначения из маршрутизации. [RFC 4786: Anycast Services](https://www.rfc-editor.org/rfc/rfc4786.html).

# Как capacity reserve и независимость от control plane влияют на готовность к потере региона?

После потери региона оставшиеся площадки должны принять перераспределённую нагрузку с допустимой latency. Рассчитывают не только compute, но и DB connections, storage throughput, network quotas, workers и последствия cold cache. Autoscaling не гарантирует немедленной выдачи ресурсов во время общей аварии.

**Static stability** означает способность продолжить существенную работу при недоступности управляющих зависимостей. Поэтому критичный failover не должен полностью зависеть от срочного создания instances, изменения IAM или ручной настройки через неисправный control plane. Ёмкость и механизмы переключения проверяют заранее. [AWS: Static stability](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/).

# Как спроектировать CDN cache key и отделить public content от private responses?

Cache key включает все параметры, от которых зависит представление: host, path, значимые query parameters и необходимые варианты headers. Если origin и CDN по-разному нормализуют запрос, разные ответы могут ошибочно получить один ключ. Избыточная детализация ключа, напротив, уменьшает cache hit ratio.

Для public content явно задают подходящую cache policy. Private responses не должны попадать в общий CDN cache без специальной безопасной схемы; `private` запрещает shared-cache storage, а `no-store` запрещает сохранение соответствующего сообщения. Проверяют CDN overrides, cookies, Authorization и доступ до выдачи cached object. [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html), [Cache keys](https://developers.cloudflare.com/cache/how-to/cache-keys/).

# Как TTL, purge, versioned URLs и origin shielding влияют на доступность через CDN?

TTL определяет freshness; короткий TTL чаще обращается к origin, длинный увеличивает допустимую устарелость. Purge помогает удалить копии, но требует понимания охвата и времени распространения. Versioned URLs удобны для immutable assets: новая версия получает новое имя, а старые ссылки остаются согласованными.

Origin shielding добавляет промежуточный cache и может объединять одновременные misses, уменьшая всплеск запросов на origin. Отдельно проектируют stale serving и revalidation там, где это допустимо. Истёкший TTL не доказывает немедленного физического удаления, а invalidation не заменяет проверку отозванного доступа. [CloudFront Origin Shield](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/origin-shield.html).

# Какие state, consistency и security ограничения возникают при выполнении логики на Edge?

Edge уменьшает путь до пользователя, но локальная memory и cache конкретной точки обычно не являются надёжным общим storage. Для shared state определяют владельца, replication и consistency. Например, локальные counters разных точек не обеспечивают единый строгий global rate limit.

Проверяют ограничения CPU, memory, duration, network APIs и deployment propagation конкретного runtime. Secrets и права Edge-функции ограничивают необходимыми operations, а identity и authorization проверяют независимо от близости точки к пользователю. Изменение логики на всём Edge требует поэтапного rollout и recovery, поскольку общий ошибочный deploy способен затронуть все регионы.

# Как проверить HA-архитектуру под нагрузкой при отказе региона, CDN или общей зависимости?

Испытание задаёт входную нагрузку, пользовательские критерии, модель отказа и условия остановки. Отключают выбранный регион или зависимость и наблюдают routing, переходную latency, retries, queue growth, свежесть и корректность данных. Тест продолжают до стабилизации и возврата в штатную topology.

Для CDN проверяют массовый cache miss, недоступность origin и потерю CDN-path. Fallback должен сохранять authorization и не превращать origin в незащищённый endpoint. Подтверждают ёмкость оставшихся компонентов и независимость от control plane; результат документируют с границами проверенного сценария. [AWS: Reliability design principles](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/design-principles.html).
