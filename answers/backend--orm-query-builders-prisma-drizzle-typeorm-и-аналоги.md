# Чем ORM, SQL query builder и прямой SQL отличаются по уровню контроля и ответственности?

**ORM** связывает модель приложения с хранением и обычно предоставляет отношения, mapping и операции чтения/записи. **Query builder** помогает составлять SQL через программный API, сохраняя более явную структуру запроса. Прямой SQL даёт полный доступ к возможностям движка, но требует самостоятельного mapping и контроля типов.

Границы пересекаются: ORM может включать builder и raw SQL. Любой вариант требует понимания индексов, транзакций и реального плана выполнения. Уровень абстракции не отменяет ответственность за стоимость запроса.

# Как сравнивать Prisma, Drizzle и TypeORM для конкретного backend-проекта?

Сравнивают поддерживаемые БД и версии, модель схемы, миграции, отношения, транзакции, pooling и возможность исследовать SQL. Для привычных версий Prisma характерен генерируемый клиент, Drizzle — близкий к SQL типизированный API, TypeORM — entity mapping и разные способы построения запросов; конкретные возможности меняются между major versions.

Проверяют несколько реальных сценариев: сложную выборку, конкурентную запись, миграцию и ошибку драйвера. Выбор не стоит основывать только на объёме boilerplate. Важны удобство команды и возможность выйти за стандартный API без потери контроля.

# Почему типобезопасный ORM-запрос не гарантирует корректную схему и результат во время выполнения?

Type safety проверяет совместимость запроса с типами, известными компилятору или генератору. Рабочая БД может иметь другую схему, новые constraints, исторически некорректные данные или неподдерживаемый клиентом тип.

Также типы не доказывают бизнес-инвариант: две корректно типизированные записи могут нарушить общий лимит. Нужны миграции, проверка внешнего ввода, ограничения БД и обработка ошибок во время выполнения. Raw SQL и небезопасные assertions могут дополнительно ослабить гарантии типизированного API.

# Как связи, eager loading и lazy loading приводят к N+1 и избыточной загрузке данных?

Eager loading сразу загружает связи и способен вернуть слишком большой graph. Lazy loading откладывает запрос до обращения к отношению, поэтому цикл по объектам может незаметно выполнить N дополнительных запросов. Явные отдельные обращения создают ту же проблему.

Выбирают нужные поля и ограничивают коллекции, измеряют число SQL-запросов и объём результата. Решением могут быть batching, relation loading или отдельная проекция. Важно проверить реальный SQL: название `include` не определяет единственный способ загрузки во всех версиях ORM. [Query optimization Prisma v7](https://www.prisma.io/docs/orm/v7/prisma-client/queries/advanced/query-optimization-performance).

# Как выбрать между JOIN, несколькими запросами и batching при загрузке связанных данных?

`JOIN` удобен для выборки связанных данных, но несколько отношений «один ко многим» могут многократно размножить строки. Отдельные ограниченные запросы или batching уменьшают дублирование, ценой дополнительных обращений и необходимости объединить результат.

Учитывают cardinality, сетевую задержку, размер результата и согласованность чтения. Пагинация родительских объектов должна происходить без случайного ограничения строк размноженного JOIN. Если несколько запросов должны видеть одно состояние, выбирают подходящую транзакцию и isolation level, а не полагаются на последовательное выполнение.

# Как передать одну транзакцию через несколько ORM-операций и не выйти из её контекста?

Внутри транзакции используют предоставленный transaction client, manager или connection и передают его всем участвующим repository. Вызов глобального клиента может открыть другую транзакцию или выполнить запрос вне нужного контекста.

Фиксация происходит после успешного завершения всей операции, ошибка должна приводить к rollback. Не держат транзакцию во время долгого внешнего HTTP-вызова. API callbacks, nested transactions и savepoints зависят от ORM, версии и драйвера; возможности проверяют явно. [Transactions Drizzle](https://orm.drizzle.team/docs/transactions), [transactions Prisma](https://www.prisma.io/docs/orm/fundamentals/transactions).

# Как isolation level, optimistic locking и database constraints защищают изменения через ORM?

ORM использует гарантии выбранной БД. Isolation level определяет допустимые взаимодействия транзакций, version check помогает обнаружить конкурентное изменение, а unique/check/foreign-key constraints защищают ограничения на стороне хранения.

Например, `UPDATE ... WHERE id = ? AND version = ?` с увеличением версии должен изменить ожидаемое число строк; ноль означает конфликт, а не успешное сохранение. Deadlock и serialization failure требуют повторить всю допустимую транзакцию, перечитав состояние. Наличие метода `save` само по себе не защищает от lost update.

# Как применять миграции ORM по схеме expand-and-contract без остановки приложения?

При **expand** сначала добавляют совместимую структуру, затем выпускают код, который может работать в переходном состоянии, и переносят данные. После проверки и обновления всех читателей/писателей выполняют **contract**: удаляют старое поле или ограничивают старый путь.

Генератор миграций не знает требования к доступности: переименование может превратиться в удаление и создание. SQL проверяют на реальных данных, блокировках и поддержке online-операций движком. Откат бинарника возможен только пока данные и схема остаются совместимыми со старой версией.

# Как connection pool ORM ведёт себя при нескольких экземплярах приложения и serverless-запусках?

Каждый процесс или клиент может создать свой pool, поэтому суммарное число соединений растёт с числом экземпляров и параллельных serverless-запусков. Избыточные clients внутри одного процесса тоже умножают подключения.

Задают лимит pool, срок ожидания и общую ёмкость БД с запасом для миграций и служебных задач. При необходимости используют совместимый proxy/pooler, проверяя session state, prepared statements и транзакции. Увеличение pool не лечит медленный SQL и способно усилить перегрузку.

# Как безопасно сочетать ORM с raw SQL и динамической сортировкой?

Пользовательские значения передают параметрами, а не конкатенацией строк. Идентификаторы таблиц, столбцов и направление сортировки обычно нельзя заменить обычным value-параметром: их выбирают из разрешённого набора и корректно формируют средствами библиотеки.

Raw SQL должен сохранять tenant/access-фильтры и transaction context. Результат raw-запроса проверяют и преобразуют явно, особенно для decimal, дат и nullable-полей. Название helper с пометкой `unsafe` требует внимания, но сам по себе шаблонный literal не доказывает безопасность любого построения запроса.

# Как исследовать медленный ORM-запрос через SQL logs и execution plan?

Сначала находят конкретный SQL, параметры нужной формы, частоту вызова и время ожидания pool. Затем исследуют план выполнения на представительном объёме: оценки и фактические строки, scans, JOIN, сортировки и работу индексов.

`EXPLAIN ANALYZE` выполняет запрос, поэтому для изменяющих операций и тяжёлого production-запроса нужен контролируемый способ проверки. Измеряют также объём переданных данных и mapping в приложении. Секреты и персональные значения в SQL logs маскируют. Оптимизация ORM-кода должна подтверждаться изменением реального bottleneck.

# Как тестировать mapping, транзакции и миграции ORM без привязки теста к внутренним вызовам клиента?

Проверяют наблюдаемый результат на целевом движке: mapping типов, constraints, согласованность нескольких изменений и конфликт версии. Для миграций нужны создание схемы с нуля и переход с поддерживаемой предыдущей версии с данными.

Тест не обязан знать последовательность внутренних методов ORM. Важнее, что после сбоя нет частичной записи и повтор корректно обрабатывает конфликт. Unit-тесты доменных правил дополняют integration tests; mock ORM-клиента не доказывает поведение SQL и транзакций.
