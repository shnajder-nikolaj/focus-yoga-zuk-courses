# Как вы объясняете принятое архитектурное решение команде?

Объяснение начинаю с проблемы и требований, которые привели к решению, а не с выбранной технологии.

Последовательно раскрываю:

1. Контекст - какую проблему решаем, какие есть функциональные и нефункциональные требования.
2. Ограничения - сроки, производительность, масштабируемость, существующая архитектура, компетенции команды.
3. Альтернативы - какие варианты рассматривались и почему были отклонены.
4. Компромиссы (trade-offs) - что выигрываем и чем жертвуем.
5. Последствия - как решение повлияет на разработку, тестирование, поддержку и дальнейшее развитие системы.

Для сложных решений использую архитектурные схемы, примеры кода и ADR (Architecture Decision Record) - документ, фиксирующий контекст, решение и его обоснование.

Важно убедиться, что команда понимает причины выбора и может аргументированно его оспорить. Цель - не добиться формального согласия, а сформировать общее понимание.

# Как определить, что код готов к code review?

Код готов к review, когда разработчик самостоятельно проверил его соответствие требованиям и устранил очевидные проблемы.

Основные критерии:

- Функциональность - реализованы acceptance criteria, обработаны основные граничные случаи.
- Корректность - код собирается, проходит необходимые тесты и статические проверки.
- Качество - соблюдены соглашения проекта, отсутствуют случайные изменения, отладочный код и ненужные зависимости.
- Тестирование - добавлены или обновлены тесты для изменённого поведения.
- Безопасность - отсутствуют секреты, небезопасная обработка данных и очевидные уязвимости.
- Проверяемость - PR имеет понятное описание, инструкции для проверки и ссылки на связанные задачи.

Перед отправкой выполняю self-review - просматриваю собственный diff так, как его увидит другой разработчик.

Code review должен быть сосредоточен на корректности решений, архитектуре и поддерживаемости, а не на проблемах, которые автоматически обнаруживаются линтером.

# Как разрешить конфликт мнений по технологии или архитектуре?

Перевожу обсуждение из субъективных предпочтений в сравнение решений по заранее согласованным критериям.

Последовательность:

1. Формулирую проблему и требования, которые должно удовлетворять решение.
2. Выясняю аргументы сторон и их исходные предположения.
3. Определяю критерии сравнения: сложность, производительность, поддерживаемость, стоимость внедрения, риски.
4. Если аргументов недостаточно, предлагаю ограниченный по времени PoC (Proof of Concept) или технический эксперимент.
5. Принимаем решение в соответствии с установленной зоной ответственности и фиксируем аргументацию в ADR.

Важно учитывать обратимость решения. Для легко изменяемых решений длительное обсуждение часто обходится дороже возможной ошибки. Для труднообратимых архитектурных решений требуется более тщательная проверка.

После принятия решения команда должна придерживаться согласованного подхода, даже если первоначально мнения расходились.

# Как оценить задачу с неизвестными требованиями?

Нельзя достоверно оценить реализацию, пока неизвестны её границы. Поэтому сначала отделяю известную работу от неопределённости.

Порядок действий:

1. Выявляю неизвестные требования и фиксирую вопросы к заказчику или Product Owner.
2. Определяю минимальный ожидаемый результат и критерии приёмки.
3. Выделяю технические неизвестные: интеграции, ограничения API, зависимости, особенности существующего кода.
4. При необходимости провожу spike - ограниченное по времени исследование для устранения технической неопределённости.
5. Декомпозирую понятную часть задачи и оцениваю её отдельно.

Пока неопределённость сохраняется, использую диапазон оценки с явно указанными допущениями, а не одно точное число.

Например: «3-5 дней при условии, что API уже поддерживает необходимые операции; интеграция с новой системой требует отдельной оценки».

Оценку пересматриваю после уточнения требований. Неопределённость не следует маскировать дополнительными часами без объяснения причин.

# Как выявлять риски релиза до начала реализации?

Начинаю с анализа того, какие изменения затрагивает релиз и что может пойти не так.

Основные категории рисков:

- Технические - несовместимость API, миграции данных, изменения зависимостей, нарушения обратной совместимости.
- Архитектурные - высокая связанность модулей, изменения общих компонентов, сложность интеграции.
- Производительность - увеличение bundle size, сетевых запросов, времени загрузки и выполнения JavaScript.
- Безопасность - изменение авторизации, обработки пользовательских данных и разрешений.
- Организационные - внешние зависимости, отсутствие ответственных, неопределённые требования.
- Эксплуатационные - отсутствие мониторинга, сложность отката, несовместимость разных версий frontend и backend.

Для каждого существенного риска оцениваю вероятность, последствия и способы снижения.

Применяю ранние интеграционные проверки, контрактные тесты, feature flags, staged rollout и проверку rollback-сценариев.

Критически важно заранее определить, как обнаружить проблему после релиза и как безопасно ограничить её влияние.

# Как работать с legacy-кодом без тестового покрытия?

Основной принцип - сначала зафиксировать существующее поведение, затем изменять реализацию.

Последовательность:

1. Изучаю зависимости, точки входа, побочные эффекты и бизнес-логику изменяемого участка.
2. Проверяю текущее поведение вручную или через доступные интеграционные сценарии.
3. Добавляю characterization tests - тесты, фиксирующие фактическое поведение системы, включая неожиданные особенности.
4. По возможности создаю изолируемые границы вокруг изменяемого кода.
5. Вношу небольшие изменения с проверкой после каждого шага.

Не пытаюсь переписать весь legacy-модуль ради одной задачи. Масштаб рефакторинга должен соответствовать рискам и ожидаемой пользе.

Важно различать рефакторинг и изменение поведения. Рефакторинг должен сохранять наблюдаемое поведение, поэтому исправление старых ошибок лучше выполнять отдельными контролируемыми изменениями.

Если автоматизированные тесты пока невозможны, документирую ручные сценарии проверки и явно фиксирую остаточные риски.

# Как расставлять приоритеты между функциональностью и техническим долгом?

Приоритизирую обе категории задач по их влиянию на бизнес, стоимость разработки и технические риски.

Технический долг оцениваю по нескольким критериям:

- Частота влияния - насколько часто проблемный участок приходится изменять.
- Стоимость поддержки - сколько времени теряется из-за сложности кода.
- Риск - вероятность дефектов, инцидентов или проблем безопасности.
- Эффект устранения - насколько улучшатся скорость разработки, стабильность и сопровождаемость.
- Срочность - блокирует ли долг запланированную функциональность.

Если технический долг регулярно замедляет разработку или создаёт существенные риски, его устранение становится приоритетной задачей.

Если проблема локальна и практически не влияет на продукт, масштабный рефакторинг может быть неоправданным.

Предпочитаю инкрементальное погашение технического долга при работе с соответствующими модулями. Отдельные технические инициативы планирую, когда локальных улучшений недостаточно.

Важно формулировать технический долг через измеримые последствия, а не через субъективное «код написан некрасиво».

# Как организовать работу над крупной feature несколькими разработчиками?

Сначала определяю архитектуру feature, её зависимости и границы ответственности, затем распределяю работу.

Основные шаги:

1. Декомпозиция - разделяю feature на небольшие задачи с проверяемым результатом.
2. Контракты - заранее согласовываю API, структуры данных, интерфейсы компонентов и правила обработки ошибок.
3. Зависимости - определяю критический путь и задачи, которые можно выполнять параллельно.
4. Ответственность - назначаю владельцев отдельных частей и ответственного за общую интеграцию.
5. Интеграция - обеспечиваю регулярное объединение изменений через небольшие PR и CI.
6. Контроль - отслеживаю блокировки, изменения требований и готовность сквозных сценариев.

Если backend ещё не готов, использую согласованные моки или контрактные тесты для параллельной разработки.

Крупную feature удобно разрабатывать через trunk-based development и feature flags, чтобы изменения регулярно попадали в основную ветку, не открывая незавершённую функциональность пользователям.

Главный риск - независимая разработка частей, которые слишком поздно начинают интегрировать друг с другом.

# Как вы проводите декомпозицию требований и выделяете границы модулей?

Начинаю с анализа бизнес-сценариев, ответственности компонентов и потоков данных, а не с разделения файлов по техническим типам.

Сначала выделяю пользовательские сценарии и разбиваю их на небольшие функциональные части, каждая из которых имеет понятный результат и критерии приёмки.

Затем определяю границы модулей, руководствуясь принципами:

- High cohesion - внутри модуля находится функциональность с общей ответственностью.
- Low coupling - модули минимально зависят от внутренних деталей друг друга.
- Encapsulation - внутренние детали скрыты за публичным интерфейсом.
- Separation of concerns - независимые обязанности разделены.
- Направление зависимостей - зависимости между слоями и модулями понятны и не образуют циклов.

Например, модуль `checkout` может содержать UI, бизнес-логику и операции работы с данными, относящиеся к оформлению заказа, вместо распределения всей его логики по глобальным папкам `components`, `hooks` и `services`.

Общие компоненты выделяю только при наличии действительно общей ответственности. Преждевременное создание универсальных абстракций часто увеличивает связанность.

Хорошая граница модуля позволяет изменять его внутреннюю реализацию без необходимости модифицировать множество других частей системы.

# Как управлять breaking changes в общем пакете?

Breaking change - изменение публичного контракта пакета, которое требует адаптации существующих потребителей.

Управление такими изменениями включает:

1. Контроль публичного API - определяю, какие экспорты, типы, компоненты и варианты поведения являются поддерживаемыми.
2. Оценку влияния - выявляю проекты и компоненты, использующие изменяемый контракт.
3. Версионирование - применяю Semantic Versioning, если пакет следует SemVer: несовместимые изменения стабильного API требуют новой major-версии.
4. Миграцию - предоставляю migration guide, примеры изменений и при возможности codemod.
5. Проверку совместимости - запускаю тесты пакета и потребителей, включая интеграционные и контрактные проверки.
6. Планирование выпуска - согласовываю порядок обновления зависимых проектов.

Если возможно, применяю промежуточный этап deprecation: старый API временно сохраняется, а потребители получают предупреждения о предстоящем удалении.

При разработке в монорепозитории полезно проверять изменения пакета сразу на зависимых приложениях.

Важно учитывать, что SemVer описывает совместимость публичного контракта, а не гарантирует отсутствие ошибок. Для версий `0.x` правила совместимости могут отличаться.

# Как проводить техническое интервью с frontend-разработчиком?

Строю интервью вокруг компетенций, необходимых для конкретной роли, а не проверки случайных фактов.

Обычно оцениваю:

1. JavaScript и TypeScript - язык, асинхронность, работа с данными, типизация.
2. Браузерные технологии - DOM, rendering pipeline, HTTP, безопасность, производительность.
3. Frontend-фреймворк - модель обновления UI, управление состоянием, жизненный цикл, архитектурные ограничения.
4. Проектирование - декомпозиция задач, разделение ответственности, работа с API.
5. Качество - тестирование, отладка, доступность, обработка ошибок.
6. Командную работу - code review, обсуждение решений, взаимодействие с другими специалистами.

Использую реальные инженерные задачи: разбор кода, поиск ошибки, проектирование небольшого решения или обсуждение архитектурного сценария.

Оцениваю не только итоговый ответ, но и ход рассуждений, способность выявлять ограничения и аргументировать компромиссы.

Для объективности заранее составляю критерии оценки и применяю сопоставимую структуру интервью ко всем кандидатам на одну позицию.

Не делаю вывод об уровне разработчика исключительно по знанию редких API или способности быстро решать алгоритмические головоломки.

# Как помогать junior-разработчику развивать самостоятельность?

Использую постепенное увеличение ответственности с регулярной обратной связью.

Основные практики:

- Понятные задачи - формулирую ожидаемый результат, ограничения и критерии готовности, не предписывая каждый шаг.
- Наводящие вопросы - помогаю разобраться в проблеме, а не сразу предоставляю готовое решение.
- Code review - объясняю причины замечаний, архитектурные принципы и возможные последствия.
- Pair programming - показываю способы анализа проблем, отладки и принятия решений.
- Рост сложности - постепенно передаю более самостоятельные задачи и небольшие зоны ответственности.
- Обратная связь - регулярно обсуждаю сильные стороны, ошибки и конкретные направления развития.

Важно научить разработчика самостоятельно исследовать проблему и своевременно запрашивать помощь.

Для этого полезно договориться, сколько времени разумно потратить на самостоятельное исследование и какую информацию подготовить перед обращением за помощью.

Самостоятельность не означает отсутствие поддержки. Цель - постепенно сокращать необходимый объём контроля без снижения качества работы.

# Как выстраивать единые практики тестирования и код-ревью?

Начинаю с согласования общих стандартов качества и Definition of Done, применимых ко всей команде.

Для тестирования определяю:

- Какие сценарии покрываются unit-, integration- и E2E-тестами.
- Какие изменения обязательно требуют обновления тестов.
- Как использовать моки и тестовые данные.
- Как организованы запуск тестов, CI и обработка нестабильных тестов.
- Какие критические пользовательские сценарии должны проверяться перед релизом.

Для code review фиксирую:

- Требования к размеру и описанию PR.
- Критерии проверки: корректность, архитектура, безопасность, производительность, доступность и поддерживаемость.
- Правила обязательных approvals и распределения ответственных.
- Различие между блокирующими замечаниями и необязательными предложениями.

Автоматизирую всё, что можно проверить без участия человека: форматирование, linting, type checking, тесты и базовые проверки безопасности.

Стандарты закрепляю в документации и CI, а затем периодически пересматриваю на основе реальных проблем.

Важно избегать формального подхода: высокий процент покрытия или большое количество approvals сами по себе не гарантируют качество.

# Как проводить postmortem после инцидента?

Postmortem - структурированный анализ инцидента, направленный на выявление причин и предотвращение повторения.

Провожу его после стабилизации системы.

Основные этапы:

1. Описание инцидента - что произошло, какие пользователи и функции пострадали, как долго продолжалось воздействие.
2. Timeline - хронология событий от появления проблемы до восстановления.
3. Обнаружение - как выявили инцидент и почему существующий мониторинг сработал или не сработал.
4. Анализ причин - непосредственные причины, сопутствующие факторы и системные недостатки.
5. Оценка реакции - что помогло восстановить сервис и что замедлило процесс.
6. Action items - конкретные улучшения с ответственными, приоритетами и сроками.

Использую подход blameless postmortem - анализирую условия, процессы и технические причины, а не ищу виновного.

Например, если разработчик случайно выпустил некорректную конфигурацию, важно выяснить, почему CI, проверки конфигурации или механизмы выкладки не предотвратили ошибку.

Результат postmortem - не сам документ, а выполненные действия, снижающие вероятность или последствия аналогичного инцидента.

# Как определить, что для проекта оправдан переход на новую технологию?

Переход оправдан, когда измеримая польза превышает полную стоимость миграции и связанные риски.

Оцениваю:

1. Существующие проблемы - какие ограничения текущей технологии реально мешают продукту.
2. Ожидаемые преимущества - производительность, возможности, поддерживаемость, безопасность, скорость разработки.
3. Стоимость миграции - переписывание кода, тестирование, обучение команды, адаптация инфраструктуры.
4. Совместимость - интеграция с текущими библиотеками, платформами и внутренними инструментами.
5. Зрелость технологии - стабильность API, экосистема, поддержка и долгосрочные риски.
6. Альтернативы - можно ли решить проблему обновлением или локальным улучшением существующей системы.

Перед масштабной миграцией провожу PoC с измеримыми критериями успеха на репрезентативном участке проекта.

Предпочтителен инкрементальный переход, если архитектура позволяет безопасно сосуществовать старой и новой реализации.

Сам факт появления более современной технологии недостаточен. Миграция должна решать конкретные проблемы, а не создавать технический долг другого типа.

# Как оценить последствия выбора SSR, микрофронтендов или монорепозитория?

Оцениваю каждое решение через требования продукта, архитектурные компромиссы и стоимость эксплуатации.

SSR (Server-Side Rendering)

Преимущества:

- Возможность раньше предоставить браузеру содержательный HTML.
- Упрощение индексации контента некоторыми поисковыми системами.
- Потенциальное улучшение первоначального отображения страницы.

Недостатки:

- Дополнительная серверная инфраструктура и стоимость выполнения запросов.
- Сложность hydration, кеширования и управления серверным состоянием.
- Риск hydration mismatch и увеличения нагрузки на сервер.

SSR не гарантирует улучшения Core Web Vitals: итог зависит от архитектуры, объёма JavaScript, кеширования и реализации.

Микрофронтенды

Преимущества:

- Независимая разработка и потенциально независимые релизы отдельных частей приложения.
- Чёткие границы ответственности команд.
- Возможность постепенной миграции крупных систем.

Недостатки:

- Сложность интеграции, маршрутизации и обмена состоянием.
- Риски дублирования зависимостей и увеличения объёма загружаемого кода.
- Дополнительные требования к согласованности UI, версиям контрактов и мониторингу.

Микрофронтенды обычно оправданы при наличии нескольких достаточно независимых команд и функциональных областей.

Монорепозиторий

Преимущества:

- Единое управление общими библиотеками, инструментами и конфигурациями.
- Удобные сквозные изменения в нескольких пакетах.
- Возможность централизованных проверок совместимости.

Недостатки:

- Более сложная настройка CI/CD и инструментов сборки.
- Необходимость управлять зависимостями и границами пакетов.
- Рост времени проверок без эффективного кеширования и определения затронутых проектов.

Монорепозиторий сам по себе не означает единый деплой и не требует микрофронтендов.

Ключевой критерий выбора - соответствует ли архитектура реальным требованиям к производительности, масштабированию команд, независимости релизов и сложности сопровождения.

# Как использовать feature flags при совместной работе нескольких команд?

Feature flags позволяют отделить доставку кода от включения функциональности для пользователей.

При совместной разработке нескольких команд они помогают:

- Интегрировать незавершённый код в основную ветку.
- Независимо включать функциональность в разных окружениях.
- Постепенно открывать изменения отдельным группам пользователей.
- Проводить controlled rollout и эксперименты.
- Оперативно отключать проблемную функциональность без нового деплоя, если архитектура это допускает.

Для каждого флага определяю владельца, назначение, условия включения и срок удаления.

Особенно важно учитывать совместимость: frontend, backend и общие API должны корректно работать при допустимых комбинациях состояний флагов.

Флаги, влияющие на доступ к данным и безопасность, должны контролироваться на стороне сервера. Клиентский feature flag не является механизмом авторизации.

После завершения rollout временные флаги и устаревшие ветви кода удаляю, иначе они создают дополнительную сложность и технический долг.

# Как избежать критической зависимости от одного разработчика или компонента?

Главная задача - снизить bus factor: риск потери критических знаний или возможностей разработки при недоступности отдельных участников команды.

Для уменьшения зависимости от разработчика использую:

- Документирование - ADR, описание архитектуры, инструкции по разработке, деплою и восстановлению.
- Распределение знаний - pair programming, совместные архитектурные обсуждения, внутренние технические сессии.
- Перекрёстное code review - изменения регулярно проверяют разработчики из разных частей команды.
- Ротацию ответственности - несколько специалистов участвуют в сопровождении критических модулей.
- Коллективное владение кодом - знания и право на изменения не сосредоточены у одного человека.

Для уменьшения зависимости от компонента применяю:

- Явные интерфейсы и контракты.
- Снижение связанности модулей.
- Изоляцию внешних интеграций.
- Автоматизированные тесты и мониторинг.
- Механизмы деградации функциональности при отказах, когда это необходимо.

Важно различать два риска: зависимость от знаний конкретного человека и техническую зависимость от единого компонента.

Первый устраняется распространением знаний и распределением ответственности. Второй - архитектурными решениями, ограничением области отказа и обеспечением возможности безопасно изменять или заменять компонент.
