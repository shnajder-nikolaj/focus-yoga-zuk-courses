# Как path, directory entry, inode и open file description представляют файл в Linux?

**Path** задаёт поиск через каталоги, **directory entry** связывает имя с inode, а **inode** хранит metadata и ссылки на данные объекта в пределах filesystem. Имя не является неизменной identity файла: один inode может иметь несколько имён.

**Open file description** хранит состояние конкретного открытого доступа, например offset, и может оставаться живым после удаления имени. File descriptor процесса ссылается на него. Эти уровни объясняют, почему rename, unlink и уже открытые handles могут вести себя иначе, чем повторное открытие по старому path.

# Чем hard link отличается от symbolic link при удалении и перемещении файла?

**Hard link** создаёт ещё одно имя того же inode в одной filesystem; удаление одного имени не уничтожает данные, пока остаются другие links или удерживающие открытые references. Обычно нельзя произвольно создавать hard links на directories.

**Symbolic link** хранит путь к другому объекту и может пересекать границы filesystems. После удаления target symlink остаётся, но разрешение пути не находит прежний объект. Relative symlink разрешается относительно содержащего его каталога, поэтому перемещение может изменить результат. Права и security policy проверяются при фактическом доступе к target.

# Как UID, GID, supplementary groups и effective identity определяют доступ процесса?

Linux использует числовые **UID/GID**, а имена пользователей и групп — их отображение через configured identity sources. У process есть несколько identities; для обычного filesystem access важны filesystem/effective IDs и supplementary groups по правилам kernel.

Поэтому одинаковое имя пользователя на двух hosts не доказывает одинаковые права на общие данные. Изменение membership может не обновить уже работающий process без новой сессии или restart. Проверяют identity самого service, а не интерактивного администратора. Некоторые API, например проверяющие доступ, могут использовать другую identity, чем последующий `open`.

# Как права r, w и x различаются для обычного файла и каталога?

Для обычного файла **r** разрешает читать данные, **w** — менять их, **x** — выполнять файл при выполнении остальных условий. Для каталога **r** позволяет перечислять имена, **x** — искать объект и проходить через каталог, **w** вместе с нужными условиями — менять entries.

Удаление файла обычно определяется правами родительского каталога, а не только write bit самого файла. Sticky bit, ACL, immutable flags, mount и MAC могут добавлять ограничения. Поэтому read-only file в writable directory не является достаточной защитой от замены или удаления.

# Как umask, setgid directory и sticky bit влияют на совместную работу с файлами?

**Umask** убирает разрешения из запрошенного mode при создании по обычным правилам; наличие default ACL может менять конкретный алгоритм наследования. Она не исправляет права уже существующих файлов.

**Setgid directory** помогает новым объектам наследовать group каталога, но сам по себе не выдаёт нужный group write. **Sticky bit** ограничивает удаление и rename чужих entries в shared directory, сохраняя предусмотренные исключения для владельцев и privileged operations. Для общей рабочей папки согласуют group, defaults и реальную identity writers, а не только ставят один mode.

# Как POSIX ACL и ACL mask расширяют и ограничивают обычные mode bits?

**POSIX ACL** добавляет named user/group entries и default ACL для наследования в каталогах. **ACL mask** ограничивает эффективные права named users и group-class entries; owner entry и other регулируются отдельно.

При расширенной ACL group-class mode bits связаны с mask, поэтому обычный `chmod` может изменить effective access нескольких ACL entries. Диагностируют и mode, и полный ACL, включая effective permissions. ACL не предоставляет общее правило deny поверх любых других прав и не заменяет ограничения родительского каталога или MAC. [acl](https://man7.org/linux/man-pages/man5/acl.5.html).

# Почему удалённый файл может продолжать занимать место и как найти удерживающий его процесс?

`unlink` удаляет directory entry, но процесс может продолжать держать открытый файл или mapping. Его blocks освобождаются только после исчезновения соответствующих удерживающих references и других hard links.

Из-за этого `df` показывает занятое место, которое обычный обход `du` по доступным именам не объясняет. Проверяют открытые удалённые файлы через предусмотренные tools или `/proc/<pid>/fd` с нужными правами. Для logs организуют правильный reopen или rotation; простое удаление имени не гарантирует освобождение места и может скрыть текущий вывод от привычного пути.

# Как mount points, filesystem types и mount options влияют на доступ и поведение файлов?

**Mount point** подключает filesystem или subtree в дерево paths; mount поверх каталога скрывает его прежнее содержимое в этом представлении, но не обязательно удаляет данные. Mount namespace может давать процессам разные деревья.

Filesystem type определяет возможности links, ACL, snapshots и durability, а options вроде `ro`, `nodev`, `nosuid` и `noexec` ограничивают отдельные операции по своей семантике. `noexec` не является универсальным запретом обработки содержимого interpreter. Проверяют реальную mount configuration и альтернативные paths к тем же данным, а не только видимый mode одного каталога.

# Как page cache, writeback, fsync и rename связаны с надёжным сохранением файла?

Успешный `write` часто означает передачу данных в **page cache**, а не завершённую запись на устойчивый носитель. **Writeback** выполняет её позже; `fsync` запрашивает нужную синхронизацию файла по правилам filesystem и storage.

Для атомарной замены обычно записывают temporary file в подходящем месте, синхронизируют его, выполняют rename в той же filesystem и обеспечивают нужную синхронизацию parent directory. Atomic visibility rename и durability после crash — разные свойства. Проверяют ошибки и поведение конкретной платформы; один `close` не равен гарантированному сохранению. [fsync](https://man7.org/linux/man-pages/man2/fsync.2.html).

# Как disk space, inode exhaustion и quotas вызывают разные ошибки записи?

Нехватка **disk space** означает отсутствие нужных свободных blocks, **inode exhaustion** — невозможность создать дополнительные filesystem objects при исчерпании соответствующих структур. Файл может не создаваться даже при видимых свободных гигабайтах.

**Quota** ограничивает потребление конкретного user, group или project раньше общего заполнения filesystem. Отдельно учитывают reserved capacity, metadata и writable layer контейнера. Смотрят error code, blocks, inode usage и quotas в контексте фактического mount. Очистка случайного большого файла не решает автоматически проблему миллионов мелких объектов или удерживаемых references.

# Как sparse files, copy-on-write и reflinks влияют на реальный расход места?

**Sparse file** может иметь большой logical size, но не хранить blocks для holes; при чтении там возвращаются нули. **Copy-on-write** позволяет разделять physical extents между версиями, копируя изменяемые данные при записи. **Reflink** создаёт отдельный file object с таким sharing на поддерживаемой filesystem.

Logical size и реально выделенное место поэтому различаются. Последующая запись или копирование без сохранения sparseness может резко увеличить usage. Snapshots и shared extents также усложняют оценку освобождаемого места: удаление одного имени не обязано освободить все видимые ему blocks.

# Как безопасно выдавать сервису доступ к данным без широких прав на весь каталог?

Выделяют service отдельную identity и ограничивают нужные paths: configuration для чтения, отдельные directories для state и временных данных. Права дают через ownership, подходящую group или узкий ACL, проверяя traversal по всем parent directories.

Не делают всю иерархию writable ради одного файла и не полагаются на `chmod 777`. Проверяют умолчания новых файлов, rotation, backup и runtime UID в контейнере. Для secrets отдельно ограничивают читателей и логирование, а systemd или container mounts могут дополнить filesystem permissions. Итог проверяют от имени фактически работающего process.
