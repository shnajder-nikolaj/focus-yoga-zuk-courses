# Какую проблему решает Redux?

Redux решает проблему управления общим состоянием приложения, особенно когда данные используются множеством компонентов и должны изменяться предсказуемо.

Без централизованного управления состоянием возникают проблемы:

- Prop drilling - передача данных через множество промежуточных компонентов.
- Рассинхронизация - разные компоненты хранят собственные копии одних данных.
- Сложная отладка - трудно определить, какое событие изменило состояние.
- Связанность компонентов - логика изменения общих данных распределена по приложению.

Redux предоставляет централизованный `store`, единый механизм изменения состояния через `actions` и `reducers`, а также инструменты отслеживания изменений.

При этом Redux не заменяет локальное состояние React и не обязателен для каждого приложения.

# Что означает single source of truth?

Single source of truth (единый источник истины) - принцип, согласно которому состояние, управляемое Redux, хранится в одном централизованном `store`.

Компоненты получают данные из одного источника, а не поддерживают независимые копии общего состояния.

Например, если информация о текущем пользователе хранится в Redux, разные компоненты читают её из `store`, а не создают собственные копии.

Это обеспечивает согласованность данных, упрощает отладку и позволяет отслеживать изменения состояния.

Принцип не означает, что абсолютно всё состояние приложения должно находиться в Redux. Локальное состояние компонентов и серверные данные могут управляться отдельно.

# Какие ограничения накладывает однонаправленный поток данных?

Однонаправленный поток данных (unidirectional data flow) означает, что изменение состояния проходит через последовательность:

`Action -> Dispatch -> Reducer -> Store -> UI`

Основные ограничения:

- Компоненты не должны напрямую изменять состояние `store`.
- Изменения описываются через `actions`.
- `Reducers` вычисляют новое состояние синхронно и без побочных эффектов.
- Асинхронные операции выполняются вне `reducers`, например в `thunks` или `middleware`.

Благодаря этому каждое изменение имеет понятную причину, а переходы между состояниями можно воспроизводить и тестировать.

# Что такое action, reducer, store и dispatch?

Action - объект, описывающий произошедшее событие. Обязательно содержит строковое поле `type`, может содержать `payload`.

Reducer - чистая функция `(state, action) => newState`, определяющая, как состояние изменяется в ответ на событие.

Store - объект, который хранит текущее состояние приложения, предоставляет `getState()`, `dispatch()` и `subscribe()`.

Dispatch - метод отправки действия в Redux. Запускает обработку `action` через middleware и reducer, после чего подписчики получают уведомление об изменении.

Пример:

```
const action = { type: 'counter/increment' };

function reducer(state = { count: 0 }, action) {
  switch (action.type) {
    case 'counter/increment':
      return { ...state, count: state.count + 1 };
    default:
      return state;
  }
}

store.dispatch(action);
```

`dispatch()` запускает обновление, но сам не определяет, каким должно стать состояние - это ответственность `reducer`.

# Почему reducer должен быть чистой функцией?

Чистая функция при одинаковых аргументах всегда возвращает одинаковый результат и не создаёт побочных эффектов.

Reducer должен:

- Зависеть только от `state` и `action`.
- Не изменять исходное состояние напрямую.
- Не выполнять HTTP-запросы, таймеры и другие побочные эффекты.
- Не использовать непредсказуемые значения вроде `Date.now()` или `Math.random()` непосредственно при вычислении результата.

Это обеспечивает детерминированность: последовательность одинаковых действий над одинаковым начальным состоянием даёт одинаковый результат.

Благодаря этому работают воспроизведение действий, time-travel debugging и простое модульное тестирование.

В Redux Toolkit допускается мутабельно выглядящий синтаксис благодаря Immer, но исходное состояние остаётся неизменным.

# Что такое middleware в Redux?

Middleware - промежуточный обработчик, который перехватывает вызовы `dispatch()` до передачи действия в reducer.

Middleware может:

- Логировать действия.
- Запускать асинхронные операции.
- Отменять или перенаправлять действия.
- Отправлять дополнительные действия.
- Реализовывать аналитику и обработку побочных эффектов.

Middleware имеет доступ к `dispatch`, `getState` и следующему обработчику `next`.

```
const logger = store => next => action => {
  console.log('Action:', action);

  const result = next(action);

  console.log('State:', store.getState());

  return result;
};
```

Вызов `next(action)` передаёт действие дальше по цепочке. Если его не вызвать, действие не достигнет следующих middleware и reducer.

Redux Toolkit по умолчанию подключает `redux-thunk`, позволяющий передавать в `dispatch` функции для выполнения асинхронной логики.

# Чем Redux отличается от Flux?

Flux - архитектурный подход к однонаправленному потоку данных, а Redux - конкретная библиотека, реализующая похожие идеи с более строгими правилами.

Основные различия:

- Flux допускает несколько stores, Redux обычно использует один.
- Flux использует отдельный `Dispatcher`, Redux - метод `store.dispatch()`.
- Flux позволяет stores самостоятельно обрабатывать действия и обновлять своё состояние.
- Redux использует чистые reducers, вычисляющие новое состояние на основе предыдущего.
- Redux требует иммутабельного обновления состояния, что упрощает отслеживание изменений.

Redux делает переходы состояния более предсказуемыми и удобными для тестирования и отладки.

# Когда достаточно React Context и локального состояния?

Локального состояния (`useState`, `useReducer`) достаточно, когда данные используются одним компонентом или небольшой группой связанных компонентов.

React Context подходит для передачи общих значений по дереву компонентов без `prop drilling`, например темы, локали или настроек интерфейса.

Redux полезнее, когда:

- Сложная логика изменения общего состояния распределена между многими компонентами.
- Нужно централизованно обрабатывать действия и побочные эффекты.
- Важны DevTools, отслеживание событий и воспроизводимость изменений.
- Состояние содержит множество взаимосвязанных сущностей.

Context сам по себе не является полноценным менеджером состояния: он передаёт значение, а обновления обычно реализуются через `useState` или `useReducer`.

При изменении значения Context React обновляет потребителей этого контекста. Redux через `useSelector()` позволяет подписываться на конкретные производные значения, что помогает уменьшать лишние рендеры.

# Как выбирать, что хранить в Redux, а что не нужно?

В Redux стоит хранить состояние, которое действительно должно быть общим и централизованно управляемым.

Подходящие примеры:

- Текущий пользователь и состояние авторизации.
- Глобальные настройки приложения.
- Общие фильтры и параметры интерфейса.
- Сложное клиентское состояние, используемое разными частями приложения.

Обычно не стоит хранить в Redux:

- Состояние отдельного поля формы.
- Открытие локального выпадающего меню.
- Состояние наведения курсора.
- Временные значения, нужные одному компоненту.
- Данные, которые легко вычисляются из уже существующего состояния.

Серверные данные часто лучше хранить в специализированном кэше, например RTK Query, а не вручную управлять ими через обычные slices.

Основной критерий - область использования данных и сложность управления ими, а не размер приложения.

# Почему не следует без необходимости дублировать вычисляемое состояние?

Вычисляемое состояние (derived state) - данные, которые можно получить из уже существующего состояния.

Например, если в `store` есть массив товаров, необязательно дополнительно хранить количество товаров и отфильтрованный массив.

Дублирование создаёт проблемы:

- При изменении исходных данных нужно обновлять все зависимые значения.
- Возникает риск рассинхронизации.
- Усложняются reducers и тестирование.
- Увеличивается объём состояния.

Вместо сохранения вычисляемых значений используют selectors, которые получают необходимые результаты из исходного состояния.

Если вычисление дорогое, его можно мемоизировать через `createSelector()`.

Исключения возможны, когда вычисленное значение должно сохраняться независимо от исходных данных или представляет отдельный снимок состояния.

# Что такое нормализация данных в store?

Нормализация - организация связанных данных в плоскую структуру, где сущности хранятся по уникальным идентификаторам, а связи представлены через ID.

Вместо вложенных объектов:

```
{
  posts: [
    {
      id: 1,
      author: { id: 10, name: 'Alex' }
    }
  ]
}
```

Используется структура:

```
{
  posts: {
    ids: [1],
    entities: {
      1: { id: 1, authorId: 10 }
    }
  },
  users: {
    ids: [10],
    entities: {
      10: { id: 10, name: 'Alex' }
    }
  }
}
```

Преимущества:

- Быстрый доступ к сущностям по ID.
- Отсутствие дублирования связанных объектов.
- Более простое обновление отдельных сущностей.
- Меньше изменений ссылок при иммутабельных обновлениях.

В Redux Toolkit для работы с нормализованными коллекциями используется `createEntityAdapter()`.

# Что такое selector и как его мемоизировать?

Selector - функция, извлекающая или вычисляющая данные из состояния Redux.

```
const selectUser = state => state.auth.user;
```

Selectors позволяют скрыть структуру `store` от компонентов и переиспользовать логику получения данных.

Мемоизация нужна, когда selector выполняет затратные вычисления или создаёт новые объекты и массивы.

```
import { createSelector } from '@reduxjs/toolkit';

const selectTodos = state => state.todos.items;

const selectCompletedTodos = createSelector(
  [selectTodos],
  todos => todos.filter(todo => todo.completed)
);
```

Если входные данные не изменились, `createSelector()` возвращает закэшированный результат с прежней ссылкой.

Это предотвращает повторные вычисления и может уменьшить количество рендеров компонентов.

Простые selectors, которые только возвращают существующее значение, обычно не требуют мемоизации.

# Как работает Reselect?

Reselect - библиотека для создания мемоизированных selectors. В Redux Toolkit её API доступен через `createSelector()`.

Механизм работы:

1. Входные selectors извлекают необходимые значения из `state`.
2. Reselect сравнивает их с предыдущими входными значениями.
3. Если подходящий результат уже есть в кэше, возвращает его без повторного вычисления.
4. Иначе выполняет результирующую функцию и сохраняет результат.

Ключевой момент - сравнение по ссылкам, а не глубокое сравнение содержимого.

Поэтому мутация существующего объекта без изменения его ссылки может привести к устаревшему результату.

В Reselect 5 используется двухуровневая мемоизация:

- `argsMemoize` - кэширование по аргументам вызова selector.
- `memoize` - кэширование результирующей функции по значениям входных selectors.

По умолчанию с версии 5 применяется `weakMapMemoize`, позволяющий кэшировать множество комбинаций аргументов.

Reselect особенно полезен для фильтрации, сортировки, агрегации и преобразования данных.

# Как организовать подписки на store и минимизировать рендеры?

В React для подписки на Redux используют `useSelector()` из React Redux.

```
const userName = useSelector(state => state.auth.user.name);
```

`useSelector()` отслеживает выбранное значение и по умолчанию сравнивает предыдущий и новый результат через `===`.

Если результат не изменился, обновление Redux само по себе не вызывает повторный рендер компонента через эту подписку.

Основные способы оптимизации:

- Выбирать только необходимые данные, а не весь `state`.
- Использовать мемоизированные selectors для вычисляемых объектов и массивов.
- Использовать `shallowEqual`, если selector возвращает объект с несколькими полями.
- Разделять крупные компоненты на более мелкие с независимыми подписками.
- Сохранять неизменными ссылки на данные, которые не обновлялись.

```
import { shallowEqual, useSelector } from 'react-redux';

const user = useSelector(
  state => ({
    name: state.auth.name,
    role: state.auth.role
  }),
  shallowEqual
);
```

React Redux использует механизм внешних подписок, совместимый с React 18+ через `useSyncExternalStore`.

Важно: `useSelector()` предотвращает лишние рендеры из-за изменений Redux, но не блокирует рендеры, вызванные родительским компонентом или локальным состоянием.

# Как DevTools использует предсказуемость состояний Redux?

Redux DevTools отслеживает отправленные `actions` и изменения состояния `store`.

Поскольку reducers детерминированы, последовательность действий можно воспроизводить для анализа переходов состояния.

Основные возможности:

- Просмотр истории действий.
- Сравнение состояния до и после действия.
- Просмотр `payload` и других данных action.
- Time-travel debugging - переход между сохранёнными состояниями.
- Повторное воспроизведение последовательностей действий.

Например, можно найти действие, после которого возник некорректный результат, и изучить соответствующее изменение состояния.

Для корректной работы важны чистые reducers, иммутабельность и сериализуемость данных.

DevTools не откатывает внешние побочные эффекты: HTTP-запросы, изменения файлов или действия на сервере не отменяются при переходе между состояниями.

# Какие проблемы возникают при хранении несериализуемых значений?

Несериализуемые значения - объекты, которые нельзя надёжно представить и восстановить в стандартном формате данных, используемом Redux-инструментами.

Примеры: функции, `Promise`, `Map`, `Set`, `Date`, экземпляры классов.

Потенциальные проблемы:

- Некорректная сериализация и восстановление состояния.
- Ограничения Redux DevTools и time-travel debugging.
- Ошибки при сохранении состояния через persistence.
- Нарушение ожидаемого сравнения ссылок при изменении объектов.

Например, `JSON.stringify(new Map())` возвращает `{}`, теряя содержимое коллекции.

Обычно лучше хранить:

- Для `Date` - ISO-строку или timestamp.
- Для `Map` - обычный объект или массив записей.
- Для экземпляра класса - простой объект с необходимыми данными.

Redux Toolkit в режиме разработки проверяет сериализуемость `actions` и `state` через `serializableCheck`.

# Как тестировать reducer и selector?

Reducer тестируется как обычная чистая функция: передаются начальное состояние и `action`, затем проверяется результат.

```
test('increment', () => {
  const state = { count: 1 };

  const result = counterReducer(state, {
    type: 'counter/increment'
  });

  expect(result.count).toBe(2);
  expect(state.count).toBe(1);
});
```

Важно проверять не только правильность результата, но и отсутствие мутации исходного состояния.

Selector тестируется передачей подготовленного состояния и сравнением результата с ожидаемым.

Для мемоизированных selectors дополнительно проверяют:

- Повторное использование ссылки на результат при одинаковых входных данных.
- Пересчёт при изменении зависимостей.
- Корректность вычисления для разных аргументов.

В Reselect доступен метод `recomputations()` для проверки количества выполнений результирующей функции.

Для тестирования reducers и selectors обычно не требуется запускать React или создавать настоящий Redux store.

# Зачем появился Redux Toolkit и какие проблемы классического Redux он устраняет?

Redux Toolkit (RTK) - официальный рекомендуемый набор инструментов для разработки с Redux.

Он устраняет основные недостатки ручной настройки классического Redux:

- Большое количество шаблонного кода.
- Необходимость вручную объявлять action types и action creators.
- Сложность иммутабельных обновлений вложенного состояния.
- Ручную настройку middleware и DevTools.
- Повторяющийся код обработки асинхронных запросов.

Основные инструменты:

- `configureStore()` - создание store с готовыми настройками.
- `createSlice()` - совместное определение reducers и actions.
- `Immer` - упрощение иммутабельных обновлений.
- `createAsyncThunk()` - управление жизненным циклом асинхронных операций.
- `createEntityAdapter()` - работа с нормализованными коллекциями.
- `RTK Query` - получение и кэширование серверных данных.

RTK использует тот же Redux и сохраняет его архитектурные принципы, но значительно сокращает количество ручного кода.

# Как устроен `configureStore()`?

`configureStore()` - функция Redux Toolkit для создания и настройки Redux store.

```
import { configureStore } from '@reduxjs/toolkit';

const store = configureStore({
  reducer: {
    auth: authReducer,
    todos: todosReducer
  }
});
```

Она автоматически:

1. Объединяет переданные reducers через `combineReducers()`, если указан объект reducers.
2. Подключает `redux-thunk` для асинхронной логики.
3. Добавляет проверки иммутабельности, сериализуемости и корректности actions в режиме разработки.
4. Настраивает поддержку Redux DevTools.
5. Подключает стандартные enhancers.

Дополнительные middleware добавляются через `middleware`:

```
const store = configureStore({
  reducer: rootReducer,
  middleware: getDefaultMiddleware =>
    getDefaultMiddleware().concat(logger)
});
```

`getDefaultMiddleware()` возвращает стандартный набор middleware. Использование `.concat()` позволяет сохранить их и добавить собственные.

# Как работает `createSlice()`?

`createSlice()` создаёт reducer и action creators для отдельной части Redux state.

```
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment(state) {
      state.value += 1;
    },
    add(state, action) {
      state.value += action.payload;
    }
  }
});

export const { increment, add } = counterSlice.actions;
export default counterSlice.reducer;
```

На основе `name` и названий reducers автоматически создаются типы действий:

- `counter/increment`
- `counter/add`

`createSlice()` также генерирует action creators, например `increment()` возвращает `{ type: 'counter/increment' }`.

Обновления внутри reducers обрабатывает Immer, обеспечивая иммутабельность.

Дополнительно `createSlice()` поддерживает `extraReducers` для обработки внешних действий и `selectors` для объявления selectors, связанных со slice.

# Как Immer позволяет писать мутабельно выглядящий код?

Immer - библиотека, позволяющая описывать иммутабельные обновления через обычные операции изменения объектов.

```
state.user.name = 'Alex';
```

Внутри Immer:

1. Создаёт `Proxy`-обёртку над исходным состоянием, называемую `draft`.
2. Перехватывает операции чтения и записи.
3. Отслеживает внесённые изменения.
4. Формирует новое состояние, сохраняя ссылки на неизменённые части структуры.

Таким образом, исходный объект не изменяется, а вложенные данные копируются только там, где это необходимо.

Важные ограничения:

- Нельзя одновременно изменять draft и возвращать отдельное новое значение из одного reducer.
- Для замены примитивного состояния нужно возвращать новое значение.
- Immer не делает автоматически иммутабельными произвольные внешние объекты.
- Мутации за пределами Immer reducers по-прежнему запрещены правилами Redux.

# Что делает `createAsyncThunk()`?

`createAsyncThunk()` создаёт thunk для выполнения асинхронной операции и автоматически отправляет actions, отражающие её жизненный цикл.

```
const fetchUser = createAsyncThunk(
  'users/fetch',
  async (userId, thunkAPI) => {
    const response = await fetch(`/api/users/${userId}`);

    if (!response.ok) {
      throw new Error('Failed to fetch user');
    }

    return response.json();
  }
);
```

При вызове `dispatch(fetchUser(1))` RTK:

1. Отправляет `pending`.
2. Выполняет асинхронную функцию.
3. При успехе отправляет `fulfilled` с результатом в `payload`.
4. При ошибке отправляет `rejected`.

`thunkAPI` предоставляет `dispatch`, `getState`, `signal`, `requestId` и другие инструменты.

`createAsyncThunk()` не создаёт reducers и не реализует кэширование. Обработка результатов определяется разработчиком, обычно через `extraReducers`.

# Какие состояния и действия генерирует `createAsyncThunk()`?

`createAsyncThunk()` создаёт три action creators, соответствующие жизненному циклу операции:

- `pending` - операция запущена.
- `fulfilled` - операция успешно завершена.
- `rejected` - операция завершилась ошибкой или была отменена.

Например, для `createAsyncThunk('users/fetch', ...)` будут созданы типы:

```
'users/fetch/pending'
'users/fetch/fulfilled'
'users/fetch/rejected'
```

Каждое действие содержит `meta` с информацией о запросе, включая `requestId` и исходный аргумент `arg`.

При успехе результат передаётся в `action.payload`. При ошибке используется `action.error`, а вызов `rejectWithValue()` позволяет передать собственные данные ошибки через `action.payload`.

Важно: значения состояния вроде `idle`, `loading`, `succeeded`, `failed` автоматически не создаются. Разработчик самостоятельно определяет их в slice.

Также доступен matcher `thunk.settled`, срабатывающий для `fulfilled` и `rejected`.

# Как обработать отмену асинхронного thunk?

`createAsyncThunk()` поддерживает отмену через AbortController и `AbortSignal`.

После вызова `dispatch()` возвращается promise с методом `abort()`.

```
const request = dispatch(fetchUser(1));

request.abort();
```

Внутри thunk нужно передать `signal` асинхронной операции:

```
const fetchUser = createAsyncThunk(
  'users/fetch',
  async (id, { signal }) => {
    const response = await fetch(`/api/users/${id}`, {
      signal
    });

    return response.json();
  }
);
```

После отмены RTK отправляет `rejected` с `meta.aborted === true`.

Если асинхронная операция не поддерживает `AbortSignal`, фактическое выполнение внешней операции может продолжиться, хотя RTK уже считает thunk отменённым.

Дополнительно:

- `condition()` позволяет предотвратить запуск thunk.
- `dispatchConditionRejection: true` позволяет отправлять `rejected` при отмене через `condition`.
- `meta.condition` помогает отличить пропущенный запуск от обычной ошибки.

Отмена полезна при размонтировании компонентов, смене параметров запроса и предотвращении обработки устаревших результатов.

# Когда полезен `createEntityAdapter()`?

`createEntityAdapter()` используется для управления коллекциями сущностей с уникальными идентификаторами.

Он создаёт нормализованную структуру:

```
{
  ids: [],
  entities: {}
}
```

И предоставляет готовые операции:

- `addOne`, `addMany` - добавление.
- `setAll` - замена коллекции.
- `updateOne`, `updateMany` - обновление.
- `removeOne`, `removeMany` - удаление.
- `upsertOne`, `upsertMany` - добавление или обновление.

Также создаются selectors, например `selectAll`, `selectById`, `selectIds`, `selectTotal`.

```
const usersAdapter = createEntityAdapter({
  selectId: user => user.id,
  sortComparer: (a, b) => a.name.localeCompare(b.name)
});
```

`sortComparer` позволяет поддерживать отсортированный массив `ids`.

Адаптер особенно полезен для больших коллекций пользователей, товаров, сообщений и других сущностей с частыми обновлениями.

Он не управляет серверным кэшем, запросами или синхронизацией с API.

# Как работают `createSelector()` и memoized selectors в RTK?

Redux Toolkit экспортирует `createSelector()` из Reselect, позволяя создавать мемоизированные производные данные.

```
const selectItems = state => state.cart.items;

const selectTotal = createSelector(
  [selectItems],
  items => items.reduce(
    (sum, item) => sum + item.price * item.quantity,
    0
  )
);
```

При неизменных входных значениях результирующая функция не выполняется повторно.

Это важно для:

- Дорогих вычислений.
- Фильтрации и сортировки.
- Создания новых массивов и объектов.
- Стабильности ссылок, используемых `useSelector()`.

RTK также предоставляет `createDraftSafeSelector()`, который корректно работает с Immer drafts внутри reducers.

В `createSlice()` можно объявить selectors через поле `selectors`; однако само по себе это не делает их мемоизированными. Для мемоизации вычислений по-прежнему используется `createSelector()`.

# Что такое `extraReducers` и builder callback?

`extraReducers` - механизм обработки действий, которые не определены непосредственно в `reducers` текущего slice.

Чаще всего применяется для обработки `createAsyncThunk()` и действий из других slices.

```
const usersSlice = createSlice({
  name: 'users',
  initialState: {
    data: [],
    status: 'idle'
  },
  reducers: {},
  extraReducers: builder => {
    builder
      .addCase(fetchUsers.pending, state => {
        state.status = 'loading';
      })
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.data = action.payload;
        state.status = 'succeeded';
      })
      .addCase(fetchUsers.rejected, state => {
        state.status = 'failed';
      });
  }
});
```

Builder callback предоставляет методы:

- `addCase()` - обработка конкретного action type.
- `addMatcher()` - обработка actions, удовлетворяющих условию.
- `addDefaultCase()` - обработка действий, не совпавших с предыдущими обработчиками.

В отличие от `reducers`, поле `extraReducers` не создаёт action creators.

Builder callback обеспечивает корректный вывод типов TypeScript и позволяет нескольким slices реагировать на одно действие.

# Как организовать typed hooks `useAppDispatch` и `useAppSelector`?

В TypeScript рекомендуется создавать заранее типизированные версии React Redux hooks.

Сначала типы выводятся из `store`:

```
// store.ts
export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;
```

Затем создаются hooks:

```
// hooks.ts
import { useDispatch, useSelector } from 'react-redux';
import type { RootState, AppDispatch } from './store';

export const useAppDispatch =
  useDispatch.withTypes<AppDispatch>();

export const useAppSelector =
  useSelector.withTypes<RootState>();
```

Преимущества:

- `useAppSelector()` автоматически знает структуру `RootState`.
- `useAppDispatch()` поддерживает типы обычных actions и thunks.
- Не требуется повторять типы в каждом компоненте.
- TypeScript обнаруживает некорректные обращения к состоянию.

Метод `.withTypes()` доступен начиная с React Redux 9.1.

Файл `hooks.ts` лучше отделять от `store.ts`, чтобы избежать циклических зависимостей. Типы импортируются через `import type`.

# Когда использовать listener middleware?

Listener middleware - механизм запуска побочных эффектов в ответ на Redux actions или изменения состояния.

Подходит для сценариев:

- Реакция на авторизацию или выход пользователя.
- Сохранение настроек после изменения.
- Отложенная обработка действий.
- Запуск связанных асинхронных операций.
- Реализация `debounce`, `takeLatest` и других асинхронных сценариев.

```
const listenerMiddleware = createListenerMiddleware();

listenerMiddleware.startListening({
  actionCreator: userLoggedOut,
  effect: async (action, api) => {
    api.dispatch(clearCart());
  }
});
```

В отличие от обычного thunk, который запускается явным вызовом `dispatch(thunk())`, listener реагирует на соответствующие действия автоматически.

Он поддерживает `take`, `condition`, `delay`, `fork`, `cancelActiveListeners` и другие инструменты управления асинхронными задачами.

Listener middleware удобен для координации действий между slices и считается лёгкой альтернативой Redux Saga для многих сценариев.

# Как задать поведение `serializableCheck` и когда это допустимо?

`serializableCheck` - middleware Redux Toolkit, проверяющий наличие несериализуемых значений в actions и state во время разработки.

Настраивается через `getDefaultMiddleware()`:

```
const store = configureStore({
  reducer: rootReducer,
  middleware: getDefaultMiddleware =>
    getDefaultMiddleware({
      serializableCheck: {
        ignoredActions: ['some/action'],
        ignoredActionPaths: ['meta.arg'],
        ignoredPaths: ['temporary.value']
      }
    })
});
```

Основные параметры:

- `ignoredActions` - исключение определённых типов действий.
- `ignoredActionPaths` - исключение отдельных полей actions.
- `ignoredPaths` - исключение полей состояния.
- `isSerializable` - собственная проверка сериализуемости.
- `warnAfter` - порог предупреждения о медленной проверке.

Полностью отключить проверку можно через `serializableCheck: false`.

Это допустимо в исключительных случаях, когда несериализуемые данные действительно необходимы и их использование контролируется.

Отключение проверки не делает данные сериализуемыми и не устраняет возможные проблемы с DevTools или сохранением состояния.

Предпочтительнее исключать конкретные пути, а не отключать механизм целиком.

# Как разделять store на slices без циклических зависимостей?

Slices следует разделять по предметным областям или функциональным модулям, например `auth`, `cart`, `products`.

Каждый slice отвечает за собственное состояние и операции его изменения.

Чтобы избегать циклических зависимостей:

- Не импортировать `store` непосредственно в slices.
- Использовать `getState()` внутри thunks для чтения общего состояния.
- Выносить общие action creators в отдельные модули через `createAction()`.
- Обрабатывать внешние действия через `extraReducers`.
- Выносить общие типы и независимые функции в отдельные файлы.
- Использовать `import type` для зависимостей, нужных только TypeScript.

Например, при выходе пользователя несколько slices могут обрабатывать общий `userLoggedOut` action, не импортируя reducers друг друга.

При этом slices не обязаны быть полностью независимыми: они могут реагировать на одни и те же события.

Главное - не создавать циклические зависимости между модулями и не связывать логику состояния с конкретным экземпляром `store`.

# Как реализовать динамическое подключение reducers?

Динамическое подключение reducers позволяет добавлять части Redux state во время выполнения приложения.

Это полезно при `lazy loading`, разделении приложения на модули и `code splitting`.

В Redux Toolkit 2.x для этого используется `combineSlices()`:

```
import { combineSlices, configureStore } from '@reduxjs/toolkit';

const rootReducer = combineSlices(authSlice);

const store = configureStore({
  reducer: rootReducer
});

// После динамической загрузки модуля
rootReducer.inject(productsSlice);
```

`combineSlices()` поддерживает внедрение reducers без вызова `store.replaceReducer()`.

Важная особенность: после `inject()` начальное состояние нового slice появится в реальном `store` только после следующего действия.

Для безопасного чтения ещё не инициализированного состояния предусмотрен `rootReducer.selector()`.

В классическом Redux динамическое подключение обычно реализуют через реестр reducers, повторный `combineReducers()` и `store.replaceReducer()`.

# Как мигрировать с классического Redux на RTK?

Миграцию можно выполнять постепенно, поскольку RTK полностью совместим с обычным Redux.

Основные этапы:

1. Заменить `createStore()` на `configureStore()`, сохранив существующие reducers.
2. Перенести стандартные middleware в настройки `configureStore()`.
3. Постепенно переписать reducers и action creators через `createSlice()`.
4. Заменить ручные иммутабельные обновления на синтаксис Immer.
5. Перевести типовые асинхронные операции на `createAsyncThunk()` там, где это оправданно.
6. Для серверных данных рассмотреть RTK Query.

Существующие actions, reducers, thunks и middleware продолжают работать.

Не требуется переписывать приложение целиком: обычные reducers и reducers, созданные через `createSlice()`, могут одновременно использоваться в одном `store`.

Важно проверить конфигурацию middleware, поскольку при миграции можно случайно подключить `redux-thunk` дважды.

# Почему не стоит хранить все серверные ответы в обычных slices?

Серверное состояние отличается от клиентского: оно принадлежит серверу, может устаревать и требует синхронизации.

При хранении всех ответов API в обычных slices разработчик самостоятельно реализует:

- Кэширование ответов.
- Предотвращение дублирующихся запросов.
- Инвалидацию устаревшего кэша.
- Повторные запросы и обновление данных.
- Обработку ошибок и загрузки.
- Управление временем жизни данных.
- Согласование результатов параллельных запросов.

Это создаёт значительный объём повторяющейся логики.

RTK Query решает большинство этих задач автоматически и хранит серверные данные в собственном управляемом кэше Redux.

Обычные slices лучше подходят для клиентского состояния: настроек интерфейса, локальных сценариев и бизнес-логики.

При этом хранение серверных данных в slice не запрещено - оно может быть оправданно, когда требуется специфическая модель хранения или управления данными.

# Как организовать optimistic update в RTK без RTK Query?

Optimistic update - обновление интерфейса до подтверждения операции сервером.

Основная последовательность:

1. Сохранить предыдущее значение или информацию для отмены изменения.
2. Немедленно отправить action, обновляющий Redux state.
3. Выполнить запрос к серверу.
4. При успехе подтвердить изменение.
5. При ошибке выполнить rollback.

Пример с `createAsyncThunk()`:

```
const updateName = createAsyncThunk(
  'users/updateName',
  async ({ id, name }, { dispatch, getState }) => {
    const previousName =
      getState().users.entities[id].name;

    dispatch(userNameChanged({ id, name }));

    try {
      await api.updateUser(id, { name });
    } catch (error) {
      dispatch(userNameChanged({
        id,
        name: previousName
      }));

      throw error;
    }
  }
);
```

Пользователь сразу видит обновлённое имя. Если запрос завершится ошибкой, значение восстанавливается.

Главная сложность - конкурентные обновления.

Если пользователь несколько раз изменил значение, простой rollback может случайно перезаписать более новое изменение.

Для защиты используют `requestId`, версии сущностей или проверку актуальности операции перед откатом.

Для сложных обновлений можно применять обратные Immer patches, но их также нужно согласовывать с параллельными изменениями.

# Как типизировать Redux dispatch, selector и thunk?

В Redux Toolkit с TypeScript основные типы обычно выводятся автоматически из созданного `store`.

Типизация state и dispatch:

```
export const store = configureStore({
  reducer: rootReducer
});

export type RootState =
  ReturnType<typeof store.getState>;

export type AppDispatch =
  typeof store.dispatch;
```

`RootState` описывает структуру Redux state, а `AppDispatch` учитывает middleware и поддерживаемые типы действий.

Типизация selector:

```
const selectUser = (state: RootState) =>
  state.auth.user;
```

Тип возвращаемого значения обычно выводится автоматически.

Типизация async thunk:

```
const fetchUser = createAsyncThunk<
  User,
  number,
  { rejectValue: string }
>(
  'users/fetch',
  async (id, { rejectWithValue }) => {
    try {
      return await api.getUser(id);
    } catch {
      return rejectWithValue('Request failed');
    }
  }
);
```

Здесь:

- `User` - тип успешного результата.
- `number` - тип аргумента thunk.
- `rejectValue: string` - тип пользовательской ошибки.

Для обычных thunks можно объявить тип:

```
type AppThunk<ReturnType = void> = ThunkAction<
  ReturnType,
  RootState,
  unknown,
  UnknownAction
>;
```

Для многократного использования одинаковой конфигурации `createAsyncThunk()` также предоставляет метод `.withTypes()`.

Основной принцип: выводить типы из реальной конфигурации `store`, а не вручную дублировать структуру состояния и типы `dispatch`.
