# Что измеряют LCP, INP и CLS?

LCP (Largest Contentful Paint) - время от начала загрузки страницы до отрисовки самого крупного видимого элемента контента, например изображения, видео или текстового блока. Характеризует скорость появления основного содержимого.

INP (Interaction to Next Paint) - отзывчивость страницы на действия пользователя: клики, нажатия клавиш и касания. Измеряет время от взаимодействия до следующей отрисовки, отражающей реакцию интерфейса. Учитывает взаимодействия за время жизни страницы, оценивая наиболее медленные с возможным исключением редких выбросов.

CLS (Cumulative Layout Shift) - визуальную стабильность страницы. Измеряет неожиданные смещения видимых элементов, не вызванные недавним взаимодействием пользователя. Рассчитывается на основе величины смещения и доли затронутой области экрана.

Рекомендуемые значения Core Web Vitals:

- LCP - не более 2,5 секунды
- INP - не более 200 мс
- CLS - не более 0,1

Для оценки качества обычно используется 75-й перцентиль реальных посещений.&#x20;

# Чем lab data отличается от field data?

Lab data - результаты синтетических тестов в контролируемом окружении: с заданными параметрами устройства, сети и сценария взаимодействия. Позволяют воспроизводить проблемы и исследовать причины замедления. Инструменты: `Lighthouse`, `Chrome DevTools`, `WebPageTest`.

Field data - данные реальных пользователей, собранные в различных браузерах, устройствах и сетевых условиях. Показывают фактический пользовательский опыт. Источники: `Chrome UX Report (CrUX)` и системы `RUM`.

Основные различия:

- Lab data удобнее для отладки и сравнения изменений.
- Field data отражают реальные условия, но зависят от состава аудитории.
- Некоторые метрики, например полноценный `INP`, невозможно получить без реальных или специально воспроизведённых взаимодействий.

Обычно field data используют для обнаружения проблем, а lab data - для исследования их причин.

# Как найти причину большого LCP?

Сначала необходимо определить LCP-элемент и выяснить, на каком этапе возникает задержка.

В `Chrome DevTools` используют вкладки `Performance` и `Network`, а также диагностику `Lighthouse`.

LCP условно разделяется на четыре составляющие:

1. TTFB - ожидание первого байта HTML. Большое значение указывает на возможные проблемы сети, сервера, CDN или редиректов.
2. Resource load delay - задержка перед началом загрузки LCP-ресурса. Причины: позднее обнаружение изображения, зависимость от JavaScript, низкий приоритет запроса.
3. Resource load duration - продолжительность загрузки ресурса. Причины: большой размер изображения, медленное соединение.
4. Element render delay - задержка между окончанием загрузки ресурса и его отрисовкой. Причины: блокирующие стили, JavaScript, длительные задачи или ожидание рендеринга компонентов.

Типичные решения:

- Сделать LCP-ресурс доступным непосредственно из HTML.
- Использовать `fetchpriority="high"` для приоритетного изображения.
- Не применять `loading="lazy"` к LCP-изображению.
- Оптимизировать размер ресурсов и серверный ответ.
- Уменьшить блокирующие операции на `main thread`.

Важно оптимизировать именно проблемную составляющую: уменьшение размера изображения не поможет существенно, если основная задержка возникает при его отрисовке.&#x20;

# Что такое long task и как он влияет на отзывчивость?

Long task - задача на главном потоке браузера (`main thread`), выполняющаяся более 50 мс без возможности прерывания.

Пока JavaScript выполняет такую задачу, браузер не может нормально обрабатывать другие задачи главного потока, включая пользовательские события и обновление интерфейса.

Последствия:

- Задержка обработки кликов и ввода.
- Увеличение `INP`.
- Пропуск кадров анимации и подёргивания интерфейса.
- Задержка отрисовки контента.

Для диагностики используют `Performance` в Chrome DevTools, `Long Tasks API` и `Long Animation Frames API`.

Для устранения разбивают вычисления на более короткие задачи с передачей управления браузеру, например через `scheduler.yield()` при поддержке браузером, сокращают синхронную работу или выносят вычисления в `Web Workers`.

# Чем TTFB отличается от FCP?

TTFB (Time to First Byte) - время от начала навигации до получения первого байта HTML-ответа сервера. Включает сетевые задержки, установление соединения, редиректы и серверную обработку, если они присутствуют.

FCP (First Contentful Paint) - время от начала навигации до первой отрисовки содержимого страницы: текста, изображения, SVG или другого учитываемого браузером контента.

Разница принципиальная:

- `TTFB` показывает, насколько быстро браузер начинает получать HTML.
- `FCP` показывает, насколько быстро пользователь видит первый контент.

Низкий `TTFB` не гарантирует быстрый `FCP`: браузер может долго загружать CSS, выполнять JavaScript или ожидать формирования интерфейса.

# Как уменьшить объём JavaScript, выполняемого при старте приложения?

Основная задача - сократить не только размер загружаемого JavaScript, но и время его парсинга, компиляции и выполнения.

Основные методы:

- Code splitting - разделение приложения на чанки, загружаемые по необходимости.
- Dynamic import - отложенная загрузка модулей через `import()`.
- Tree shaking - удаление неиспользуемого кода при сборке.
- Lazy loading компонентов - загрузка тяжёлых компонентов только перед их использованием.
- Удаление тяжёлых зависимостей - замена или исключение библиотек, создающих значительную нагрузку.
- Отложенная инициализация - перенос аналитики, редакторов и других необязательных функций на более поздний этап.
- SSR и selective hydration - уменьшение работы, необходимой для первичного отображения, и выборочная активация интерактивности там, где это поддерживает фреймворк.

Для анализа используют `Bundle Analyzer`, `Coverage` и `Performance` в Chrome DevTools.

Важно: `code splitting` не обязательно уменьшает общий объём JavaScript. Он позволяет не загружать и не выполнять ненужный код при старте.

# Как работают lazy loading изображений и responsive images?

Lazy loading - отложенная загрузка изображений до момента, когда они приближаются к видимой области страницы.

Нативно реализуется через `loading="lazy"`. Браузер самостоятельно определяет, когда начать загрузку, ориентируясь на расстояние до viewport и другие условия.

Для более сложных сценариев используют `IntersectionObserver`.

Responsive images - механизм выбора изображения подходящего размера или формата в зависимости от устройства и условий отображения.

Основные инструменты:

- `srcset` - набор доступных вариантов изображения.
- `sizes` - предполагаемая ширина отображения изображения при разных размерах viewport.
- `<picture>` и `<source>` - выбор изображения по медиазапросам или поддерживаемому формату.

Браузер выбирает подходящий ресурс с учётом параметров отображения, плотности пикселей и собственных алгоритмов.

Важно не применять lazy loading к LCP-изображениям, поскольку это может задерживать появление основного контента.&#x20;

# Как оптимизировать загрузку web fonts?

Основные задачи - уменьшить время загрузки шрифтов и предотвратить задержку отображения текста или смещение макета.

Способы оптимизации:

- Использовать `WOFF2` - эффективный формат сжатия шрифтов.
- Применять `font-display: swap` для немедленного отображения текста системным шрифтом.
- Использовать `font-display: optional`, если допустимо отказаться от web font при медленной загрузке.
- Подключать только необходимые начертания и веса.
- Использовать font subsetting и `unicode-range` для сокращения количества загружаемых символов.
- Предзагружать критически важные шрифты через `<link rel="preload" as="font" crossorigin>`.
- Настраивать метрики резервного шрифта через `size-adjust`, `ascent-override` и другие CSS-дескрипторы.

Важно учитывать два эффекта:

FOIT (Flash of Invisible Text) - текст временно не отображается до загрузки шрифта.

FOUT (Flash of Unstyled Text) - сначала отображается резервный шрифт, затем происходит замена.

`font-display: swap` уменьшает задержку отображения текста, но может вызвать `CLS`, если метрики основного и резервного шрифтов сильно различаются.&#x20;

# Как предотвратить layout shift при асинхронном контенте?

Основной принцип - зарезервировать место под контент до его загрузки, чтобы появление новых элементов не смещало существующие.

Методы:

- Задавать изображениям `width`, `height` или CSS `aspect-ratio`.
- Использовать skeleton-компоненты с размерами, соответствующими будущему содержимому.
- Резервировать высоту под рекламу, виджеты и асинхронные блоки.
- Не вставлять динамические элементы над уже отображённым контентом без заранее выделенного пространства.
- Подбирать резервные шрифты с близкими метриками.
- Для анимаций использовать `transform` вместо изменения геометрических свойств, например `top` или `height`.

Например, если карточка товара сначала имеет высоту 100 px, а после загрузки данных становится 400 px, расположенные ниже элементы сместятся.

Если заранее выделить необходимую высоту, смещения можно избежать.

Для диагностики используют события `layout-shift` через `PerformanceObserver` и соответствующие записи в Chrome DevTools.

# Как измерять реальную производительность через RUM?

RUM (Real User Monitoring) - сбор данных о производительности непосредственно в браузерах реальных пользователей.

Обычно применяют библиотеку `web-vitals`, браузерные `Performance API` или специализированные системы мониторинга.

Процесс:

1. При посещении страницы браузер собирает метрики `LCP`, `INP`, `CLS`, `FCP`, `TTFB`.
2. Дополнительно фиксируются обезличенные характеристики окружения: тип устройства, браузер, сетевые условия и маршрут приложения.
3. Метрики отправляются на сервер аналитики, часто с использованием `navigator.sendBeacon()`.
4. На сервере данные агрегируются по маршрутам, версиям приложения и сегментам пользователей.
5. Анализируются распределения, особенно `p75` и `p95`, а также динамика после релизов.

Для SPA важно отдельно отслеживать клиентские переходы: стандартные метрики загрузки документа не пересчитываются автоматически при каждой смене маршрута.

При сборе необходимо учитывать семплирование, ограничения браузерных API, согласие пользователя и защиту персональных данных.&#x20;

# Какие возможности даёт PerformanceObserver?

`PerformanceObserver` - браузерный API для асинхронного получения записей о производительности страницы.

Позволяет отслеживать:

- `navigation` - характеристики навигации.
- `resource` - время загрузки ресурсов.
- `paint` - события отрисовки, включая `FCP`.
- `largest-contentful-paint` - кандидатов на LCP.
- `layout-shift` - изменения расположения элементов.
- `longtask` - длительные задачи главного потока.
- `event` - длительность обработки пользовательских событий.
- `long-animation-frame` - длительные кадры и связанные с ними операции.
- `mark` и `measure` - пользовательские измерения через Performance API.

Пример:

```
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.startTime, entry.duration);
  }
});

observer.observe({
  type: "longtask",
  buffered: true,
});
```

`buffered: true` позволяет получить уже сохранённые браузером записи поддерживаемого типа, если это предусмотрено соответствующим API.

Набор доступных типов зависит от браузера. Проверить поддержку можно через `PerformanceObserver.supportedEntryTypes`.

Сам `PerformanceObserver` предоставляет исходные измерения, а полноценные метрики вроде `CLS` и `INP` требуют дополнительной логики расчёта.&#x20;

# Когда нужно виртуализировать списки и таблицы?

Виртуализация - техника отображения только элементов, находящихся в видимой области прокрутки, и небольшого дополнительного диапазона (`overscan`).

Применяется, когда большой список создаёт значительную нагрузку на DOM, память, layout или рендеринг.

Например, вместо одновременного создания 20 000 строк таблицы приложение отображает только несколько десятков строк около viewport.

Преимущества:

- Меньше DOM-элементов.
- Быстрее первоначальный рендеринг.
- Меньше затрат на layout и обновления.
- Ниже потребление памяти.

Ограничения:

- Сложнее работать с элементами переменной высоты.
- Требуется корректное управление прокруткой и фокусом.
- Возможны проблемы с доступностью, поиском по странице и навигацией с клавиатуры.
- Нужна аккуратная обработка динамического изменения размеров элементов.

Для React используются, например, `TanStack Virtual` и `react-window`.

Виртуализация полезна при большом количестве элементов, но конкретный порог зависит от сложности компонентов и производительности устройств.

# Как web workers помогают убрать тяжёлые вычисления с main thread?

Web Worker выполняет JavaScript в отдельном потоке, не блокируя основной поток, отвечающий за пользовательские события и обновление интерфейса.

Подходит для:

- Обработки больших массивов данных.
- Сложных математических вычислений.
- Парсинга крупных документов.
- Сортировки, фильтрации и преобразования данных.
- Обработки изображений, если необходимые API доступны в worker.

Взаимодействие происходит через `postMessage()` и события `message`.

Пример:

```
// main.js
const worker = new Worker(
  new URL("./worker.js", import.meta.url),
  { type: "module" }
);

worker.postMessage(1000000);

worker.onmessage = ({ data }) => {
  console.log(data);
};

// worker.js
self.onmessage = ({ data }) => {
  const result = heavyCalculation(data);
  self.postMessage(result);
};
```

Ограничения:

- Worker не имеет прямого доступа к DOM.
- Передача данных обычно использует structured clone, что может требовать дополнительного времени и памяти.
- Для крупных бинарных данных можно использовать Transferable objects, например `ArrayBuffer`, чтобы избежать копирования.
- Создание worker и обмен сообщениями имеют накладные расходы.

Web Workers не ускоряют автоматически сами вычисления, но позволяют выполнять их без блокировки главного потока.&#x20;

# Что такое critical CSS?

Critical CSS - минимальный набор CSS-правил, необходимых для первоначальной отрисовки видимой части страницы.

Обычно эти стили встраивают непосредственно в HTML через `<style>`, чтобы браузер мог начать отображение контента без ожидания загрузки основного CSS-файла.

Остальные стили загружаются отдельно.

Преимущества:

- Уменьшение задержки первой отрисовки.
- Возможное улучшение `FCP` и `LCP`.
- Сокращение влияния блокирующих CSS-ресурсов.

Ограничения:

- Инлайновый CSS увеличивает размер HTML.
- Большой объём critical CSS снижает пользу оптимизации.
- Требуется актуализировать набор правил при изменении интерфейса.
- Некорректное разделение может вызвать изменение внешнего вида после загрузки остальных стилей.

Особенно полезен для страниц, где первоначальное отображение задерживается из-за больших блокирующих таблиц стилей.

# Почему оптимизация bundle size не всегда улучшает пользовательские метрики?

Bundle size показывает объём JavaScript, но пользовательская производительность зависит также от времени загрузки, выполнения кода, отрисовки и реакции на взаимодействия.

Например, уменьшение bundle на 30% может не улучшить `LCP`, если основная задержка связана с медленным ответом сервера или загрузкой изображения.

Основные причины:

- Уменьшение размера файла не обязательно сокращает время выполнения JavaScript.
- Основная нагрузка может приходиться на layout, paint или обработчики событий.
- Удалённый код мог находиться в чанке, который не загружается при старте.
- Сжатие и кеширование уменьшают влияние размера файла на сетевые затраты.
- Дополнительное разделение bundle может увеличить число запросов и зависимости между чанками.
- Разные устройства имеют существенно различающуюся скорость выполнения JavaScript.

Поэтому размер bundle - промежуточная техническая метрика, а конечный результат оценивают через `LCP`, `INP`, `CLS` и другие показатели реального пользовательского опыта.

# Как найти memory leak в SPA при многократной навигации?

Утечка памяти возникает, когда объекты больше не нужны приложению, но продолжают удерживаться ссылками и не могут быть удалены сборщиком мусора (`Garbage Collector`).

Для диагностики:

1. Открыть SPA и перейти в `Chrome DevTools → Memory`.
2. Выполнить сборку мусора (`Collect garbage`) и создать первый `Heap snapshot`.
3. Несколько раз перейти между маршрутами приложения.
4. Вернуться в исходное состояние, повторить сборку мусора и создать второй snapshot.
5. Сравнить снимки через `Comparison`, обращая внимание на количество сохранившихся объектов и `Retained size`.
6. Найти объекты, которые должны были освободиться, и исследовать их `Retainers` - цепочки ссылок, удерживающих их в памяти.

Дополнительно используют `Performance Monitor` для отслеживания размера JS heap, количества DOM-узлов и обработчиков событий.

Если после многократных циклов навигации количество удерживаемых объектов постоянно увеличивается, это признак возможной утечки.

Однако рост памяти сам по себе не доказывает утечку: приложение может намеренно сохранять данные в кеше.

# Как найти причину ошибки, воспроизводящейся только в production?

Начинают со сбора контекста ошибки: stack trace, версия приложения, маршрут, браузер, действия пользователя и связанные сетевые запросы.

Порядок диагностики:

1. Проверить source maps - восстановить исходные файлы и строки кода по production stack trace.
2. Воспроизвести production-сборку локально - использовать те же переменные окружения и конфигурацию, насколько это безопасно и возможно.
3. Сравнить окружения - API-адреса, feature flags, версии зависимостей, конфигурацию CDN и кеширование.
4. Изучить сетевые запросы - ошибки API, авторизации, CORS, таймауты и некорректные ответы.
5. Проверить особенности сборки - minification, tree shaking, code splitting и динамическую загрузку модулей.
6. Исследовать условия выполнения - race conditions, медленные сети, устаревшие браузеры и различия в данных.

Типичные production-only проблемы:

- Несоответствие версий HTML и JavaScript после деплоя.
- Загрузка устаревших чанков из кеша.
- Ошибки в переменных окружения.
- Неправильные пути к ресурсам.
- Различия в данных и правах доступа.
- Ошибки, связанные с порядком выполнения асинхронных операций.

Важно воспроизводить проблему на конкретной версии сборки, а не только на текущей ветке разработки.

# Какие вкладки Chrome DevTools наиболее полезны при диагностике SPA?

Основные инструменты:

- Console - ошибки JavaScript, предупреждения, отладочные сообщения и выполнение команд.
- Network - HTTP-запросы, статусы, заголовки, инициаторы запросов, кеширование и время загрузки.
- Performance - анализ выполнения JavaScript, long tasks, отрисовки, layout и пользовательских взаимодействий.
- Memory - поиск утечек памяти, анализ heap snapshots и удерживаемых объектов.
- Sources - отладка JavaScript, breakpoints, source maps и анализ call stack.
- Application - исследование `localStorage`, `sessionStorage`, `IndexedDB`, cookies, Cache Storage и Service Workers.
- Elements - DOM, CSS, размеры элементов, изменения стилей и состояния интерфейса.
- Security - проверка HTTPS, сертификатов и информации о безопасности соединения.

Для React дополнительно используют расширение React Developer Tools, позволяющее анализировать дерево компонентов, props, state и производительность рендеринга через Profiler.

# Как обнаружить неожиданные повторные сетевые запросы?

Основной инструмент - вкладка `Network` в Chrome DevTools.

Порядок диагностики:

1. Включить `Preserve log`, чтобы запросы сохранялись при навигации.
2. Отфильтровать запросы по `Fetch/XHR`.
3. Найти повторения одного endpoint с одинаковыми параметрами.
4. Открыть вкладку `Initiator`, чтобы определить код или цепочку вызовов, запускающую запрос.
5. Сопоставить время запросов с рендерами компонентов, эффектами и действиями пользователя.

Типичные причины:

- `useEffect` с некорректными зависимостями.
- Повторное монтирование компонента.
- Несколько подписчиков, независимо вызывающих один API.
- Автоматические `retry` и `refetch` в библиотеках запросов.
- Повторные запросы при изменении фокуса окна.
- Некорректная логика инвалидации кеша.
- Циклические обновления состояния.

В React `StrictMode` в development может дополнительно запускать эффекты при монтировании для проверки корректности очистки. Само по себе это не означает, что production отправляет такие же запросы.

Также важно отличать дублирующий запрос приложения от CORS preflight (`OPTIONS`) и проверки кеша (`304 Not Modified`).

# Как искать memory leak через heap snapshots?

Heap snapshot фиксирует граф объектов JavaScript в памяти и ссылки между ними в конкретный момент времени.

Основной метод - сравнение снимков до и после подозрительной операции.

1. Создать исходный snapshot.
2. Выполнить действие, например открыть и закрыть модальное окно несколько раз.
3. Вернуть приложение в исходное состояние.
4. Создать второй snapshot после сборки мусора.
5. Открыть `Comparison` и найти объекты, количество которых увеличилось.
6. Исследовать `Retainers`, чтобы понять, почему объекты остаются достижимыми.

Особенно полезно искать:

- `Detached DOM elements` - удалённые из DOM элементы, удерживаемые JavaScript.
- Объекты размонтированных компонентов.
- Крупные массивы, `Map` и другие структуры данных.
- Обработчики и замыкания, удерживающие ненужные объекты.

Retained size помогает оценить объём памяти, который может быть освобождён после устранения удерживающей ссылки.

Важно анализировать несколько повторений операции, чтобы отличить настоящую утечку от временных объектов и прогрева кешей.&#x20;

# Как анализировать performance trace и long tasks?

Performance trace - временная запись работы браузера: выполнения JavaScript, сетевой активности, рендеринга, обработки событий и других операций.

В `Chrome DevTools → Performance`:

1. Начать запись.
2. Воспроизвести медленное действие.
3. Остановить запись и найти проблемный интервал.
4. Исследовать длинные задачи на дорожке `Main`.
5. Открыть `Call tree`, `Bottom-up` или flame chart, чтобы определить функции, потребляющие больше всего времени.

Особое внимание уделяют:

- Scripting - выполнению JavaScript.
- Recalculate Style - пересчёту CSS-стилей.
- Layout - вычислению геометрии элементов.
- Paint - подготовке графического содержимого.
- Long tasks - задачам продолжительностью более 50 мс.
- Long animation frames - кадрам с длительной обработкой и отрисовкой.

Например, если после клика выполняется обработчик продолжительностью 180 мс, необходимо изучить его call stack и выяснить, какая операция занимает основное время.

Если задержка связана не с JavaScript, а с layout, оптимизация обработчика может не решить проблему.

Flame chart помогает найти конкретные вызовы, а `Bottom-up` - агрегировать затраты времени по функциям независимо от того, откуда они вызывались.

# Что такое structured logging и correlation ID?

Structured logging - запись логов в машинно-читаемом формате с отдельными полями вместо произвольных текстовых сообщений.

Обычно применяется JSON:

```
{
  "level": "error",
  "event": "api_request_failed",
  "requestId": "req_7f82a1",
  "route": "/products",
  "status": 503,
  "durationMs": 820
}
```

Такой формат позволяет фильтровать, группировать и анализировать события по конкретным атрибутам.

Correlation ID - идентификатор, связывающий события, относящиеся к одному запросу или логической операции.

Например, frontend отправляет запрос, API вызывает другой сервис, а тот обращается к базе данных. Общий идентификатор позволяет найти связанные записи в логах разных компонентов.

Для распределённой трассировки также используют `trace_id` и `span_id`, часто в соответствии с `W3C Trace Context`.

Разница:

- `correlation ID` связывает события логически.
- `trace_id` идентифицирует распределённую трассу.
- `span_id` идентифицирует отдельную операцию внутри трассы.

Структурированные логи облегчают автоматический поиск, а correlation ID позволяет восстановить цепочку событий при диагностике ошибок.

# Как организовать сбор frontend-ошибок через Sentry или аналог?

Система мониторинга должна автоматически собирать необработанные ошибки JavaScript и предоставлять контекст, необходимый для их диагностики.

Основные шаги:

1. Подключить SDK - например, `@sentry/react` для React.
2. Настроить окружение и релиз - передавать `environment` и версию сборки.
3. Подключить source maps - для восстановления исходных stack traces.
4. Организовать перехват ошибок - использовать глобальные обработчики, `unhandledrejection` и механизмы фреймворка, например `Error Boundary`.
5. Добавить контекст - маршрут, действие пользователя, версию приложения и безопасные диагностические параметры.
6. Настроить фильтрацию и семплирование - исключить шумные и ожидаемые ошибки.
7. Создать алерты - уведомлять об увеличении частоты ошибок и появлении новых критичных проблем.

Sentry группирует похожие события в issues, сохраняя stack trace, окружение, breadcrumbs и другой диагностический контекст.

Не все ошибки попадают в мониторинг автоматически. Например, обработанная ошибка HTTP-запроса не обязательно создаёт JavaScript exception. Для таких ситуаций требуется явная регистрация события.

Перед отправкой данных необходимо настроить очистку персональной информации и ограничить сбор чувствительного содержимого.

# Как безопасно связывать frontend-ошибку с серверным request ID?

Сервер генерирует или назначает идентификатор запроса и возвращает его в заголовке ответа, например `X-Request-ID`.

Frontend считывает заголовок и добавляет значение в событие системы мониторинга.

```
const response = await fetch("/api/products");

if (!response.ok) {
  const requestId = response.headers.get("X-Request-ID");

  Sentry.captureMessage("API request failed", {
    level: "error",
    tags: {
      requestId: requestId ?? "unknown",
    },
    extra: {
      status: response.status,
    },
  });
}
```

В серверных логах тот же идентификатор используется для поиска соответствующего запроса.

Требования безопасности:

- Использовать случайные идентификаторы, не содержащие персональных данных.
- Не включать в ID токены, email, идентификаторы сессий или секреты.
- Не считать request ID доказательством личности или полномочий пользователя.
- Ограничивать длину и допустимый формат идентификаторов, приходящих от клиента.
- Не записывать чувствительные заголовки и тела запросов в диагностические события.

При кросс-доменных запросах необходимо разрешить чтение заголовка через `Access-Control-Expose-Headers`.

Если сетевой запрос завершился без доступного HTTP-ответа, frontend может не получить серверный request ID. Для таких случаев полезна распределённая трассировка или собственный безопасный идентификатор клиентской операции.

# Как не утекать персональным данным в логи и аналитику?

Основной принцип - собирать только те данные, которые действительно необходимы для диагностики, и исключать чувствительную информацию до отправки.

Практические меры:

- Allowlist полей - явно определять, какие атрибуты разрешено отправлять.
- Маскирование - скрывать или удалять email, телефоны, адреса и другие персональные данные.
- Исключение секретов - никогда не логировать пароли, access tokens, refresh tokens, cookies авторизации и API-ключи.
- Очистка URL - удалять чувствительные query-параметры и идентификаторы из путей.
- Фильтрация ошибок - проверять `error.message`, stack traces, breadcrumbs и дополнительные поля перед отправкой.
- Защита Session Replay - маскировать пользовательский ввод и чувствительные элементы интерфейса.
- Ограничение доступа и хранения - применять политики доступа, удаления и сроки хранения данных.

В Sentry для фильтрации событий можно использовать `beforeSend`.

Важно: хеширование персональных идентификаторов не всегда делает данные анонимными. Если значение позволяет повторно идентифицировать пользователя, оно может оставаться персональными данными.

Дополнительно необходимо учитывать требования применимого законодательства, например GDPR.

# Что такое source map upload и release artifacts?

Source map - файл, связывающий скомпилированный или минифицированный JavaScript с исходным кодом.

Например, production stack trace может указывать на `app.min.js:1:48291`. Source map позволяет определить соответствующий исходный файл, функцию и строку.

Source map upload - загрузка source maps в систему мониторинга ошибок, например Sentry, во время CI/CD.

Типичный процесс:

1. Сборщик создаёт production JavaScript и соответствующие `.map`-файлы.
2. CI/CD загружает артефакты в систему мониторинга.
3. При возникновении ошибки система сопоставляет stack trace с нужными source maps.
4. Разработчик получает трассировку с исходными именами файлов и функций.

Release artifacts - файлы, связанные с конкретной версией приложения, например собранные JavaScript-бандлы и source maps.

Для сопоставления Sentry может использовать версию релиза и пути файлов либо Debug IDs - идентификаторы, связывающие собранный файл с его source map независимо от имени пути.

Debug IDs позволяют выполнять сопоставление без обязательной привязки к release.

Source maps желательно загружать в защищённое хранилище мониторинга, не публикуя их в открытом доступе без необходимости. Важно загружать карты именно от той сборки, которая развёрнута в production.&#x20;

# Как отличать пользовательскую ошибку от инфраструктурной?

Для классификации необходимо определить источник проблемы и понять, является ли поведение ожидаемым.

Пользовательские или бизнес-ошибки возникают при действиях, которые приложение не может выполнить по предусмотренным правилам.

Примеры:

- Некорректный формат введённых данных.
- Недостаточно прав для выполнения действия.
- Попытка выполнить запрещённую бизнес-операцию.
- Отсутствие запрашиваемого ресурса.

Инфраструктурные и системные ошибки возникают из-за недоступности или неправильной работы технических компонентов.

Примеры:

- Недоступность API.
- Таймаут соединения.
- Ошибка базы данных.
- Сбой DNS.
- Ошибки прокси, балансировщика или CDN.

Для диагностики используют HTTP-статусы, коды ошибок API, логи и distributed tracing.

Условно:

- `4xx` часто связаны с некорректным запросом или правами доступа.
- `5xx` указывают на ошибку серверной стороны.

Однако HTTP-статуса недостаточно. Например, `401` может возникнуть из-за истечения токена, а `500` - из-за программной ошибки backend, не связанной с инфраструктурой.

Лучше использовать структурированные коды ошибок API, позволяющие отличать ожидаемые бизнес-ситуации от технических сбоев.

# Как организовать метрики ошибок и пользовательских сессий?

Метрики должны показывать не только количество ошибок, но и какая доля пользователей сталкивается с проблемами.

Основные показатели:

- Error count - количество зарегистрированных ошибок.
- Error rate - частота ошибок относительно определённого числа операций, запросов или просмотров.
- Affected users - количество уникальных пользователей, столкнувшихся с ошибками.
- Affected sessions - количество сессий, в которых возникли ошибки.
- Crash-free sessions - доля сессий без критических сбоев.
- Crash-free users - доля пользователей, не столкнувшихся с критическими сбоями.

Например, 10 000 ошибок могут быть вызваны одной неисправной сессией. Поэтому одного общего количества ошибок недостаточно для оценки масштаба проблемы.

Метрики необходимо сегментировать по:

- Версии приложения и релизу.
- Маршруту.
- Браузеру и устройству.
- Окружению.
- Типу и критичности ошибки.

Для алертов используют резкий рост частоты ошибок, увеличение доли затронутых сессий и появление новых критических issues.

Важно согласовать определения сессии, критического сбоя и знаменателя error rate. При семплировании также необходимо учитывать, что выборка может не отражать все пользовательские сессии.

# Как диагностировать нестабильное воспроизведение race condition?

Race condition - ошибка, при которой результат зависит от порядка или времени выполнения нескольких операций.

Во frontend часто возникает при асинхронных запросах, обновлениях состояния и жизненном цикле компонентов.

Например:

1. Пользователь вводит поисковый запрос `React`.
2. Приложение отправляет запрос A.
3. Пользователь изменяет запрос на `Vue`.
4. Приложение отправляет запрос B.
5. Ответ B приходит первым, затем ответ A перезаписывает актуальные результаты устаревшими данными.

Методы диагностики:

- Использовать `Network throttling` для изменения времени выполнения запросов.
- Применять `CPU throttling` для воспроизведения проблем синхронизации.
- Логировать начало, завершение и идентификаторы асинхронных операций.
- Добавлять временные метки к событиям.
- Проверять порядок обновления состояния.
- Многократно воспроизводить сценарий с разными задержками.
- Использовать автоматизированные тесты с управляемыми ответами API.

Типичные способы устранения:

- `AbortController` - отменять неактуальные запросы, если используемый API поддерживает отмену.
- Проверять идентификатор операции перед применением результата.
- Использовать последовательные номера запросов, чтобы игнорировать устаревшие ответы.
- Корректно очищать эффекты при размонтировании или изменении зависимостей.

Простое добавление `setTimeout` обычно не устраняет race condition, а лишь меняет вероятность её проявления.

# Какие типовые причины утечек памяти существуют в SPA?

Наиболее распространённые причины:

- Неудалённые обработчики событий - подписки через `addEventListener` остаются после размонтирования компонентов.
- Таймеры - `setInterval` и отложенные задачи продолжают удерживать ссылки на данные.
- Незакрытые соединения - `WebSocket`, `EventSource` и другие долгоживущие соединения.
- Незавершённые подписки - RxJS, внешние stores и пользовательские системы событий.
- Detached DOM nodes - удалённые из DOM элементы, на которые остаются ссылки.
- Замыкания - функции удерживают большие объекты через своё лексическое окружение.
- Неограниченные кеши - массивы, `Map` и другие структуры постоянно накапливают данные.
- Неосвобождённые ресурсы - Web Workers, object URLs, графические ресурсы и другие объекты, требующие явного управления жизненным циклом.

Например, React-компонент может подписаться на событие `resize`, но не удалить обработчик при размонтировании.

Корректная очистка:

```
useEffect(() => {
  const handleResize = () => {
    console.log(window.innerWidth);
  };

  window.addEventListener("resize", handleResize);

  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
```

Главный принцип - ресурсы, созданные компонентом или модулем, должны освобождаться, когда они больше не нужны.

При этом не всякое длительное хранение данных является утечкой. Например, ограниченный кеш может намеренно сохранять объекты между переходами.

# Что такое heap snapshot и как его читать?

Heap snapshot - снимок графа объектов JavaScript, находящихся в памяти в определённый момент времени.

Позволяет определить, какие объекты существуют, сколько памяти они занимают и какие ссылки препятствуют их удалению сборщиком мусора.

В Chrome DevTools snapshot создаётся через `Memory → Heap snapshot`.

Основные представления:

- Summary - группировка объектов по типам и конструкторам.
- Comparison - сравнение двух снимков для обнаружения появившихся и сохранившихся объектов.
- Containment - исследование структуры объектов и связей между ними.

Ключевые показатели:

Shallow size - память, непосредственно занимаемая самим объектом.

Retained size - память, которая может быть освобождена вместе с объектом, если устранить удерживающие ссылки.

Distance - кратчайшее расстояние по ссылкам от объекта до корня графа достижимости.

Retainers - объекты и ссылки, удерживающие исследуемый объект в памяти.

Например, если snapshot показывает `Detached HTMLDivElement`, необходимо исследовать его retainers.

Цепочка может выглядеть следующим образом:

`Window → Event Listener → Closure → Detached HTMLDivElement`

Она показывает, что обработчик события через замыкание удерживает удалённый DOM-элемент.

Для поиска утечек особенно полезно сравнивать несколько snapshots после одинаковых операций и сборки мусора.&#x20;

# В каких случаях нужна виртуализация длинного списка?

Виртуализация нужна, когда одновременный рендеринг большого количества элементов заметно ухудшает производительность.

Например, таблица с десятками тысяч строк может создавать слишком много DOM-узлов, увеличивать время первоначального рендеринга, затраты на layout и потребление памяти.

Виртуализация отображает только видимые элементы и небольшой запас вокруг них. При прокрутке элементы переиспользуются или заменяются новыми.

Использовать её целесообразно, когда:

- Список содержит тысячи элементов.
- Отрисовка отдельных элементов достаточно тяжёлая.
- Прокрутка сопровождается задержками.
- Частые обновления списка вызывают значительные затраты на рендеринг.
- Одновременное присутствие всех DOM-элементов приводит к высокому потреблению памяти.

При небольшом количестве простых элементов виртуализация обычно не нужна, поскольку добавляет сложность управления размерами, прокруткой, фокусом и доступностью.

Виртуализация уменьшает количество одновременно отображаемых элементов, но не сокращает автоматически объём данных, загруженных с сервера. Для этого отдельно применяют пагинацию или инкрементальную загрузку.
