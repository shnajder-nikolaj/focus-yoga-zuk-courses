# Как Compose project объединяет services, networks, volumes и конфигурацию окружения?

**Compose project** — именованная группа ресурсов одного приложения. `services` описывают запускаемые контейнеры, `networks` — их связь, `volumes` — подключаемое хранилище. Общая конфигурация позволяет согласованно создать, обновить и остановить окружение.

Compose описывает несколько сервисов, но сам по себе не превращает один Docker host в отказоустойчивый multi-node scheduler. Имя project участвует в именовании обычных ресурсов и изоляции нескольких запусков. Внешние ресурсы и явно заданные имена могут намеренно выходить за эти границы.

# Как compose.yaml, override files и profiles описывают разные режимы запуска?

Базовый `compose.yaml` содержит общую структуру приложения, а дополнительные files меняют настройки для разработки, тестов или другого окружения. **Profiles** включают необязательные сервисы, например инструменты диагностики, без постоянного запуска всего набора.

Правила merge зависят от типа поля: списки и maps не всегда просто заменяются. Поэтому перед запуском просматривают итог через `docker compose config` и проверяют mounts, команды, ports и variables. Вывод может содержать чувствительные значения. Версию Compose фиксируют, если конфигурация использует новые поля или особенности merge.

# Чем подстановка переменных Compose отличается от передачи environment в контейнер?

**Interpolation** подставляет значения в Compose-модель до создания контейнера, например меняет tag образа или опубликованный port. Источниками могут быть shell environment, `.env` и явно выбранный env file по правилам Compose.

`environment` и `env_file` у сервиса задают окружение самого контейнера. Наличие значения в `.env` для interpolation не означает, что оно автоматически доступно процессу приложения. Учитывают precedence и значения по умолчанию, а обязательные параметры проверяют явно. Секреты не стоит без необходимости передавать через обычные environment variables. [Environment variables Compose](https://docs.docker.com/compose/how-tos/environment-variables/).

# Как depends_on и healthcheck управляют готовностью зависимостей при запуске Compose?

Обычный `depends_on` определяет порядок запуска, но состояние «контейнер запущен» не означает готовность БД принимать соединения. В расширенной записи условие `service_healthy` позволяет ждать успешного `healthcheck`, а `service_completed_successfully` — успешного завершения одноразового сервиса.

Проверка должна отражать нужную готовность и иметь разумные timeout и retries. Она не обеспечивает вечную доступность зависимости после старта. Приложение всё равно должно переживать её перезапуск, потерю соединения и временные ошибки. [Startup order Compose](https://docs.docker.com/compose/how-tos/startup-order/).

# Как service discovery и DNS работают внутри Compose network?

В общей пользовательской сети Compose сервисы обычно доступны по **service name**, например приложение подключается к `db:5432`. Встроенный DNS разрешает имя в актуальные адреса контейнеров этой сети.

IP контейнера может меняться после пересоздания, поэтому его не фиксируют в конфигурации клиента. Общение между services использует внутренний port, а не обязательно опубликованный host port. Сервисы должны разделять нужную сеть; одинаковое имя в разных независимых networks не создаёт связь автоматически. Приложение должно переоткрывать устаревшие соединения после замены зависимости.

# Чем container port отличается от published port и как ограничить доступ с хоста?

**Container port** — порт процесса в сетевом окружении контейнера. **Published port** — правило доступа через адрес и порт Docker host. Например, `127.0.0.1:8080:80` публикует внутренний `80` как host `8080` только на loopback.

Публикация без конкретного host address может открыть сервис на внешних интерфейсах. `EXPOSE` в image и `expose` в Compose не равнозначны публикации на host. Внутри контейнера процесс должен слушать подходящий интерфейс: listener только на собственном loopback обычно недоступен другим контейнерам. Firewall и внешние сети проверяют отдельно.

# Как named volume, bind mount и tmpfs различаются по хранению и переносимости?

**Named volume** управляется Docker и обычно переживает удаление контейнера. **Bind mount** подключает конкретный host path, поэтому зависит от структуры каталогов и прав host. **Tmpfs** хранит данные в памяти на поддерживаемой платформе и не предназначен для долговременного хранения.

Volume не является автоматической резервной копией или общим диском для всех hosts. При mount поверх существующего пути содержимое image в этом месте скрывается. Явно задают права записи и план backup. Операции удаления volumes рассматривают отдельно от обычного пересоздания services. [Docker volumes](https://docs.docker.com/engine/storage/volumes/).

# Как смена имени Compose project влияет на сети, volumes и изоляцию окружений?

У обычных project-scoped ресурсов имя включает имя Compose project. Запуск с новым project name может создать другую сеть и другой named volume, из-за чего приложение увидит пустую БД, хотя прежние данные остаются в старом volume.

`external` resources и явно заданное `name` меняют это поведение и могут привести к совместному использованию ресурса несколькими окружениями. Для тестов задают уникальные project names и ports, а для устойчивых данных документируют фактические имена и владельца. Изоляцию нельзя оценивать только по папке, из которой запущен Compose.

# Как организовать миграции БД и одноразовые задачи в Compose без гонки запуска?

Миграцию оформляют одноразовой задачей с явной зависимостью от готовой БД. Приложения, которым нужна новая схема, запускают после её успешного завершения, если используемая конфигурация Compose поддерживает соответствующее условие.

В самой БД мигратор сериализует применение версий и умеет корректно продолжать после сбоя. `depends_on` одного project не защищает от параллельного запуска другого project или внешнего pipeline. Если Compose пересоздаёт задачу, повтор должен быть безопасен. Для production отдельно продумывают совместимость схемы с уже работающими версиями приложения.

# Как registry, repository, tag и digest идентифицируют контейнерный образ?

**Registry** — сервис хранения образов, **repository** — именованная коллекция в нём. **Tag** — удобная изменяемая ссылка, например `app:1.4`, а **digest** идентифицирует содержимое manifest или image index.

Один tag может быть переназначен, поэтому для воспроизводимого deployment сохраняют digest. Multi-platform index ссылается на manifests конкретных платформ; фиксируют, какой именно объект проверен. В registry раздельно ограничивают pull и push, защищают credentials и задают retention, чтобы очистка не удалила образ, нужный для восстановления.

# Как передавать runtime secrets в Compose и какие ограничения есть у локальной схемы?

Compose `secrets` разрешает выбранным services получать секрет как файл, обычно в `/run/secrets/…`. Приложение должно уметь читать этот файл либо использовать предусмотренный image механизм вроде `_FILE`.

Локальная Compose-схема не предоставляет автоматически все свойства распределённого secret manager. Исходный файл на host, его права, backup и доставка остаются под управлением пользователя. Это также отличается от secret store Swarm. Обновление файла и reload приложения проектируют явно; значение не копируют в image или логи. [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

# Как диагностировать связь и сохранность данных после пересоздания Compose services?

Сначала проверяют итоговую Compose-модель, выбранное имя project, status контейнеров и logs. Затем — healthcheck, общие networks, DNS-имя, внутренний listener и соответствие published ports. После пересоздания соединение могло остаться привязанным к старому IP.

Для данных сопоставляют фактические mounts и имена volumes с ожидаемыми, проверяют host path и права процесса. Пустой новый volume легко принять за потерю старого. До исправления не удаляют ресурсы вслепую: сначала находят исходное хранилище и проверяют его состояние. Для backup работающей БД соблюдают её требования согласованности.
