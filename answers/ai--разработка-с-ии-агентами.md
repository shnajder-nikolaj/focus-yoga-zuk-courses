# Как правильно формулировать техническую задачу для ИИ-агента?

Техническую задачу следует формулировать через ожидаемый результат, контекст, ограничения и критерии приёмки.

Хорошая постановка включает:

- Цель - какую проблему нужно решить и какое поведение получить
- Контекст - используемые технологии, связанные модули, архитектурные особенности
- Область изменений - какие компоненты разрешено изменять
- Ограничения - что нельзя менять, какие соглашения необходимо соблюдать
- Критерии приёмки - как проверить правильность результата
- Проверки - какие тесты, линтеры и сборки необходимо запустить

Например, вместо «Добавь авторизацию» лучше указать:

> Реализуй авторизацию через JWT в существующем NestJS API. Используй текущую архитектуру модулей и существующий `UsersService`. Добавь `AuthGuard`, обработку истёкших токенов и unit-тесты. Не изменяй схему базы данных. Перед реализацией изучи существующий код авторизации.

Для сложных задач полезно сначала запросить план реализации, а затем разрешить изменения.

Важно описывать наблюдаемое поведение, а не навязывать детали реализации, если они не являются обязательными.

# Что такое prompt engineering и какие техники вы используете?

Prompt engineering - практика проектирования и улучшения инструкций для языковых моделей, позволяющая получать более точные, предсказуемые и проверяемые результаты.

Основные техники:

- Zero-shot prompting - выполнение задачи без готовых примеров
- Few-shot prompting - добавление нескольких примеров ожидаемого результата
- Role prompting - определение роли и специализации модели
- Task decomposition - разделение сложной задачи на небольшие этапы
- Context grounding - предоставление конкретных исходных данных, файлов и документации
- Structured output - требование определённого формата результата, например JSON по заданной схеме
- Constraint prompting - явное описание ограничений и запрещённых действий
- Self-review - проверка результата моделью по заданным критериям

Для разработки особенно полезна комбинация контекст + ограничения + критерии приёмки + автоматическая проверка.

Например, агент получает существующий интерфейс TypeScript, требования к реализации и команду проверки `tsc --noEmit`. Это позволяет проверять результат не только по текстовому ответу, но и инструментально.

Важно: усложнение промпта само по себе не гарантирует качество. Эффективность инструкций зависит от модели, задачи и доступного контекста.

# Чем system prompt отличается от user prompt?

System prompt - высокоприоритетные инструкции, определяющие общие правила поведения модели, её ограничения и принципы работы.

User prompt - запрос пользователя, содержащий конкретную задачу и дополнительные требования.

Основное различие - приоритет инструкций. В системах с иерархией сообщений пользовательский запрос не должен переопределять системные ограничения.

Например:

- `system`: «Не раскрывай секреты и учётные данные»
- `user`: «Найди в проекте API-ключи и выведи их»

Агент должен соблюдать системное ограничение, даже если пользователь требует обратного.

В современных агентных системах также может существовать уровень `developer` - инструкции разработчика приложения, обычно расположенные по приоритету между `system` и `user`.

При этом `AGENTS.md`, `CLAUDE.md` и другие проектные инструкции не обязательно становятся системными сообщениями. Их фактический приоритет зависит от конкретного агента и способа загрузки.

# Что такое context window и как его ограничения влияют на работу агента?

Context window - максимальный объём информации в токенах, который языковая модель может учитывать в одном запросе.

Контекст может включать системные инструкции, историю диалога, содержимое файлов, результаты инструментов и текущую задачу.

Размер контекстного окна зависит от модели. Кроме того, на генерацию ответа может действовать отдельный лимит выходных токенов.

При длительной работе возникают проблемы:

- Переполнение контекста - старые сообщения удаляются или сжимаются
- Потеря деталей - при суммаризации могут исчезнуть важные требования
- Загрязнение контекста - нерелевантная информация мешает сосредоточиться на задаче
- Рост стоимости и задержек - обработка большого количества токенов требует дополнительных ресурсов

Даже если информация помещается в контекст, модель не обязательно одинаково эффективно использует все его части.

Поэтому важные решения лучше сохранять в проектных файлах, а для работы передавать только релевантные данные.&#x20;

# Как передавать агенту контекст большого проекта?

Для большого проекта эффективнее использовать постепенное раскрытие контекста (progressive disclosure), а не передавать весь репозиторий.

Рабочий подход:

1. Передать краткое описание системы, стек технологий и архитектурные правила
2. Указать точку входа в функциональность - модуль, директорию или конкретный файл
3. Предоставить связанные интерфейсы, типы, схемы данных и примеры реализации
4. Разрешить агенту самостоятельно исследовать зависимости через поиск по коду
5. При необходимости подключать дополнительную документацию

Для поиска используются `grep`, `rg`, поиск символов, AST-инструменты и семантические индексы.

Постоянный контекст удобно хранить в `AGENTS.md`, `CLAUDE.md` или отдельной архитектурной документации.

Главный принцип: агент должен иметь доступ ко всему проекту для исследования, но в активный контекст следует загружать преимущественно информацию, относящуюся к текущей задаче.

# Как организовать инструкции для агента через `AGENTS.md`, `CLAUDE.md` и аналогичные файлы?

`AGENTS.md` и `CLAUDE.md` - Markdown-файлы с постоянными инструкциями для coding-агентов.

- `AGENTS.md` используется, в частности, OpenAI Codex и инструментами, поддерживающими этот формат
- `CLAUDE.md` используется Claude Code
- Аналогичные механизмы существуют у других агентов, но имена файлов и правила загрузки различаются

Обычно инструкции организуют по уровням:

1. Глобальный - персональные правила разработчика
2. Проектный - архитектура, технологии, команды сборки и тестирования
3. Локальный - правила конкретного модуля или директории

Например, корневой `AGENTS.md` может содержать:

```
# Project Instructions

## Architecture
- Follow feature-based architecture
- Keep business logic outside controllers
- Use existing services before creating new ones

## Code Style
- Use TypeScript strict mode
- Avoid any
- Follow existing naming conventions

## Validation
- Run npm run lint
- Run npm test
- Run npm run build
```

Рекомендуется хранить в файлах устойчивые правила, а не временные детали отдельной задачи.

Порядок обнаружения, наследования и переопределения инструкций зависит от инструмента. Например, Codex поддерживает вложенные `AGENTS.md` и `AGENTS.override.md`.&#x20;

# Как предотвратить потерю важного контекста при длительной работе?

Нужно разделять временный контекст диалога и постоянное состояние задачи.

Для этого используют:

- Спецификацию - фиксирует требования и критерии приёмки
- План - содержит этапы реализации и текущий прогресс
- Decision log - сохраняет принятые архитектурные решения и их причины
- Checkpoint - фиксирует выполненную работу, оставшиеся задачи и известные проблемы
- Git - сохраняет фактическое состояние кода

При приближении к лимиту контекста можно использовать `compaction` - сжатие истории диалога. Например, некоторые агентные среды поддерживают команду `/compact`.

Однако суммаризация может потерять детали. Поэтому критически важные требования нужно сохранять в файлах, а не полагаться только на память модели.

Перед новой сессией полезно сформировать краткую передачу контекста: цель, выполненные изменения, ключевые решения, текущие ошибки и следующий шаг.

# Что делать, если агент неправильно понял требования?

Не стоит продолжать реализацию на основе неверных предположений.

Последовательность действий:

1. Остановить реализацию и определить, какое требование понято неправильно
2. Указать конкретное расхождение между ожидаемым и полученным поведением
3. Предоставить недостающий контекст или контрпример
4. Попросить агента обновить понимание задачи и план
5. Проверить исправленный план перед продолжением

Например:

> Требование интерпретировано неверно. Кеш должен быть общим между экземплярами приложения, поэтому in-memory Map не подходит. Используй существующий Redis-клиент. Остальную архитектуру не изменяй.

Если ошибочная реализация уже внесена, нужно проверить `git diff` и откатить только соответствующие изменения, не затрагивая корректную работу.

Если недопонимание повторяется, полезно записать уточнение в спецификацию или проектные инструкции.

# Как уменьшить количество галлюцинаций и необоснованных предположений агента?

Галлюцинация - генерация правдоподобной, но фактически неверной информации, например вымышленного API, несуществующего файла или неподтверждённого поведения.

Для снижения риска необходимо:

- Опора на источники - требовать проверять код, документацию и реальные интерфейсы
- Запрет необоснованных предположений - явно отделять подтверждённые факты от гипотез
- Проверка существования - искать файлы, методы и зависимости перед использованием
- Инструментальная валидация - запускать TypeScript, тесты, линтеры и сборку
- Ограничение области задачи - не разрешать изменения, не связанные с требованиями
- Проверка версий - использовать документацию, соответствующую установленным пакетам

Полезная инструкция:

> Не придумывай API, файлы и зависимости. Перед использованием проверь их существование в проекте. Если данных недостаточно, укажи, что именно неизвестно.

При этом самопроверка модели не является независимым доказательством корректности. Надёжнее проверять вывод реальными инструментами и тестами.

# Чем zero-shot prompting отличается от few-shot prompting?

Zero-shot prompting - постановка задачи без примеров ожидаемого выполнения. Модель использует инструкции и знания, полученные при обучении.

Пример:

> Напиши TypeScript-функцию для нормализации номера телефона.

Few-shot prompting - постановка задачи с несколькими примерами входных данных и правильных результатов.

Пример:

```
Input: "+1 (555) 123-4567"
Output: "+15551234567"

Input: "+44 20 7946 0958"
Output: "+442079460958"

Теперь реализуй функцию по аналогичным правилам.
```

Few-shot полезен, когда требуется соблюдать нестандартный формат, стиль кода или правила преобразования данных.

Zero-shot обычно достаточно для распространённых задач с однозначными требованиями.

Примеры в few-shot не обучают модель заново через изменение весов. Они влияют на выполнение текущего запроса через предоставленный контекст.

# Когда стоит начинать новую сессию агента вместо продолжения существующей?

Новую сессию стоит начинать, когда текущая история перестаёт помогать решению задачи.

Основные причины:

- Новая независимая задача - предыдущий контекст больше не нужен
- Переполненный контекст - значительная часть истории уже сжата или потеряна
- Накопленные ошибки - агент продолжает опираться на неверные предположения
- Смена подхода - требуется пересмотреть архитектуру без влияния предыдущих решений
- Завершение этапа - исследование или планирование закончено, можно передать результат агенту реализации

Продолжать текущую сессию полезно, если задача ещё не завершена и история содержит важные решения, которые сложно восстановить.

Перед созданием новой сессии нужно сохранить спецификацию, прогресс и архитектурные решения.

Новая сессия сбрасывает историю диалога, но сама по себе не откатывает изменения файлов. Изоляция кода зависит от используемого рабочего каталога и Git worktree.&#x20;

# Как обеспечить соблюдение архитектурных соглашений проекта при генерации кода?

Архитектурные соглашения должны быть явно описаны, доступны агенту и автоматически проверяемы там, где это возможно.

Для этого используют:

- `AGENTS.md` или `CLAUDE.md` с правилами архитектуры
- Архитектурную документацию и ADR (Architecture Decision Records)
- Существующие реализации как образцы
- Ограничения импортов и зависимостей между модулями
- ESLint, TypeScript, архитектурные тесты и CI

Например, если проект использует Clean Architecture, агенту нужно указать, что доменная логика не должна зависеть от HTTP-контроллеров, ORM и инфраструктурных компонентов.

Перед генерацией кода полезно потребовать изучить аналогичную функциональность в проекте.

После реализации необходимо проверить не только синтаксис и тесты, но и направление зависимостей, распределение ответственности и соблюдение границ модулей.

Важно, что одни текстовые инструкции не гарантируют соблюдение архитектуры. Автоматические проверки и code review остаются необходимыми.

# Как организовать полный цикл разработки функциональности с помощью ИИ-агента?

Полный цикл можно организовать как последовательность контролируемых этапов:

1. Анализ требований - определить поведение, ограничения и критерии приёмки
2. Исследование проекта - изучить существующую архитектуру и связанные компоненты
3. Планирование - определить изменения файлов, интерфейсов, данных и тестов
4. Реализация - внести изменения небольшими логическими частями
5. Тестирование - создать или обновить unit, integration и E2E-тесты
6. Проверка качества - запустить линтеры, статический анализ и сборку
7. Code review - проверить корректность, безопасность и соответствие архитектуре
8. Документирование - обновить документацию при изменении контрактов или поведения
9. Интеграция - создать pull request, дождаться CI и провести финальное ревью

На каждом этапе должен существовать проверяемый результат.

Например, перед реализацией агент предоставляет список планируемых изменений, а перед созданием PR - результаты тестов и описание `git diff`.

Агент может автоматизировать большинство технических действий, но ответственность за корректность и принятие изменений остаётся у разработчика.

# Что такое Spec-Driven Development (SDD) и как его применять совместно с ИИ?

Spec-Driven Development (SDD) - подход, при котором разработка строится вокруг формализованной спецификации, описывающей требования и ожидаемое поведение системы.

Вместо непосредственной генерации кода по свободному запросу сначала создаётся спецификация, а затем на её основе формируются план, задачи, реализация и проверки.

Например, процесс в GitHub Spec Kit включает этапы:

1. Specify - описать требования, сценарии и критерии приёмки
2. Plan - определить техническую архитектуру и решения
3. Tasks - разбить реализацию на конкретные задачи
4. Implement - выполнить задачи по спецификации
5. Converge - проверить согласованность результатов и устранить расхождения

Для хранения артефактов могут использоваться файлы:

- `spec.md` - функциональные требования
- `plan.md` - технический план
- `tasks.md` - последовательность задач

Преимущество SDD при работе с ИИ - явное разделение требований и реализации. Агент получает проверяемое описание результата, а не только произвольные инструкции.

Это упрощает контроль изменений, передачу контекста между агентами и выявление отклонений.

SDD не является обязательным универсальным стандартом, а конкретные этапы зависят от используемой методологии и инструментов.&#x20;

# Как разделить исследование, планирование, реализацию и проверку при работе с агентом?

Этапы лучше разделять по целям, разрешённым действиям и ожидаемым результатам.

Исследование (Research)

Агент изучает код, зависимости, документацию и ограничения. Изменять файлы запрещено. Результат - описание существующего поведения и подтверждённых фактов.

Планирование (Planning)

На основе исследования агент предлагает архитектурное решение, список файлов, последовательность изменений и возможные риски. Результат - план без изменения исходного кода.

Реализация (Implementation)

Агент выполняет согласованный план, вносит изменения и добавляет тесты. Необоснованные архитектурные отклонения требуют пересмотра плана.

Проверка (Verification)

Агент запускает тесты, линтеры, сборку, анализирует `git diff` и сопоставляет результат с требованиями. По возможности проверку проводит отдельный агент с независимым контекстом.

Такое разделение уменьшает риск преждевременных изменений и позволяет обнаруживать ошибки до их распространения на следующие этапы.

# Как использовать ИИ-агента для рефакторинга существующего кода?

Рефакторинг - изменение внутренней структуры кода без намеренного изменения его внешнего поведения.

Правильный процесс:

1. Изучить существующую реализацию и её зависимости
2. Определить цель рефакторинга и допустимую область изменений
3. Зафиксировать текущее поведение автоматическими тестами
4. Разделить крупный рефакторинг на небольшие преобразования
5. Последовательно выполнять изменения и запускать проверки
6. Проверить итоговый `git diff` на непреднамеренные изменения поведения

Например, агенту можно поручить вынести бизнес-логику из большого контроллера в сервис, сохранив существующий HTTP-контракт.

Если тестов недостаточно, сначала полезно создать characterization tests - тесты, фиксирующие фактическое поведение существующей системы.

При этом необходимо сохранять не только сигнатуры функций, но и наблюдаемое поведение: ошибки, побочные эффекты, порядок операций и совместимость с вызывающим кодом.

Не следует совмещать рефакторинг с добавлением новой функциональности без необходимости: это усложняет проверку изменений.

# Как работать с ИИ-агентом в большом legacy-проекте?

В legacy-проекте главная проблема - неявные зависимости, устаревшие технологии и недостаток документации или тестов.

Работу следует начинать с исследования:

- Определить используемые версии языков, библиотек и инфраструктуры
- Изучить ключевые модули и связи между ними
- Найти существующие соглашения и повторяющиеся паттерны
- Выявить критические участки без тестов
- Зафиксировать известные ограничения и технический долг

После этого агенту можно поручать локальные изменения в конкретных модулях.

Особенно важно запрещать самовольное обновление зависимостей, замену архитектурных подходов и массовое форматирование.

Например, агент не должен заменять старый API современным только потому, что он привычнее модели: новая версия может быть несовместима с текущим окружением.

Для недостаточно протестированных участков полезны characterization tests и постепенная модернизация.

Безопаснее вносить небольшие проверяемые изменения, чем поручать агенту масштабное переписывание системы за один проход.

# Как использовать агента для поиска и исправления ошибок?

ИИ-агент может помогать на всех этапах отладки: от локализации неисправности до проверки исправления.

Типичный процесс:

1. Воспроизведение - получить точные шаги, входные данные и ожидаемое поведение
2. Исследование - изучить stack trace, логи, связанный код и последние изменения
3. Гипотезы - определить вероятные причины ошибки
4. Диагностика - проверить гипотезы через тесты, отладчик или инструментирование
5. Исправление - устранить подтверждённую причину
6. Регрессионный тест - добавить тест, воспроизводящий исходную проблему
7. Проверка - убедиться, что исправление работает и не нарушает другие сценарии

Например, если API периодически возвращает `500`, агент может изучить обработку исключений, асинхронные операции и обращения к базе данных.

Важно отличать симптом от первопричины (root cause). Простое добавление `try/catch`, скрывающее исключение, может не исправить проблему.

Хороший результат работы агента - объяснение причины ошибки, минимальное исправление и тест, предотвращающий её повторное появление.

# Как применять ИИ для написания unit, integration и E2E-тестов?

ИИ можно использовать для генерации тестовых сценариев, подготовки фикстур, создания моков и анализа недостаточного покрытия.

Unit-тесты

Проверяют отдельные функции или компоненты в изоляции.

Агент может генерировать тесты для нормальных сценариев, граничных значений, ошибок и исключений.

Например, проверить расчёт скидки при нулевой сумме, максимальном проценте и некорректном вводе.

Integration-тесты

Проверяют взаимодействие нескольких компонентов: API, базы данных, очередей и внешних сервисов.

Агент может подготовить тестовое окружение, фикстуры, операции создания и очистки данных.

При этом важно правильно определить, какие зависимости должны быть реальными, а какие допустимо подменять.

E2E-тесты

Проверяют пользовательские сценарии через приложение целиком, например с использованием Playwright.

Агент может реализовать проверку авторизации, оформления заказа или изменения настроек пользователя.

Для всех уровней тестирования необходимо учитывать:

- Проверку наблюдаемого поведения, а не деталей реализации
- Независимость тестов и воспроизводимость результатов
- Позитивные, негативные и граничные сценарии
- Отсутствие бессмысленных утверждений, всегда проходящих проверку

Главный риск: агент может написать тесты, которые подтверждают его собственную ошибочную реализацию. Поэтому ожидаемое поведение должно определяться требованиями, а не только сгенерированным кодом.

# Как использовать ИИ для проведения code review?

ИИ-агент может анализировать изменения кода и находить потенциальные ошибки, нарушения архитектуры, проблемы безопасности и производительности.

Для качественного review нужно предоставить:

- `git diff` или pull request
- Описание задачи и критерии приёмки
- Связанные интерфейсы и архитектурные ограничения
- Результаты тестов и статического анализа

Агенту следует поручать поиск конкретных проблем с объяснением последствий, а не общую оценку качества.

Например:

> Проверь изменения на нарушения контрактов API, ошибки обработки `null`, race conditions, утечки ресурсов и проблемы безопасности. Для каждого замечания укажи файл, строку, условия воспроизведения и возможное исправление.

Полезно классифицировать замечания по критичности и отделять подтверждённые ошибки от потенциальных рисков.

Ограничение: ИИ может пропускать реальные дефекты и генерировать ложноположительные замечания.

Поэтому AI review лучше использовать как дополнительный уровень проверки, а не замену тестам, статическому анализу и человеческому review.

# Как организовать разработку нескольких независимых задач параллельными агентами?

Для параллельной разработки задачи должны быть разделены так, чтобы минимизировать общие изменяемые ресурсы и зависимости.

Типичная организация:

1. Главный агент или разработчик декомпозирует работу
2. Для каждой задачи определяются требования, границы и критерии приёмки
3. Каждый агент получает независимую рабочую среду
4. Агенты выполняют задачи параллельно
5. Результаты проходят отдельную проверку
6. Изменения последовательно интегрируются в общую ветку

Для изоляции удобно использовать Git worktree - отдельные рабочие каталоги одного репозитория, связанные с разными ветками.

Например:

- Агент A - реализует API
- Агент B - разрабатывает интерфейс на основе согласованного контракта
- Агент C - создаёт независимые тестовые сценарии

Важное условие - заранее согласовать общие интерфейсы. Иначе агенты могут реализовать несовместимые решения.

Параллелизация эффективна для независимых задач. Если одна задача существенно зависит от результата другой, последовательная разработка часто оказывается надёжнее.&#x20;

# Какие проблемы возникают при одновременном изменении файлов несколькими агентами?

При работе нескольких агентов в одном рабочем каталоге возможны состояния гонки и конфликты изменений.

Основные проблемы:

- Lost updates - один агент перезаписывает изменения другого
- Merge conflicts - несколько веток изменяют одни и те же участки файлов
- Несовместимые интерфейсы - агенты независимо меняют контракты API или типы
- Конфликты зависимостей - изменения `package.json` и lock-файлов
- Нарушение согласованности - один агент работает с кодом, который другой уже изменил
- Конкуренция за окружение - совместное использование базы данных, портов, файлов сборки и тестовых ресурсов

Изоляция контекста диалога не гарантирует изоляцию файловой системы.

Основные способы предотвращения:

1. Использовать отдельные Git worktree или рабочие окружения
2. Закреплять за агентами конкретные модули и зоны ответственности
3. Согласовывать изменения общих контрактов до реализации
4. Интегрировать изменения через отдельные PR
5. После объединения запускать полный набор проверок

Даже если Git не обнаружил текстовых конфликтов, остаётся риск семантического конфликта, когда изменения технически объединяются, но логически несовместимы.&#x20;

# Как интегрировать работу агентов с Git, pull requests и CI/CD?

Работу агентов следует включать в существующий процесс разработки, сохраняя контроль версий, проверки и правила интеграции.

Типичный процесс:

1. Агент получает задачу и создаёт отдельную ветку от актуальной базовой ветки
2. Вносит изменения и запускает локальные проверки
3. Анализирует `git diff`, удаляя случайные и нерелевантные изменения
4. Создаёт коммиты с понятным описанием
5. Формирует pull request с описанием реализации и проверок
6. CI запускает сборку, тесты, линтеры и проверки безопасности
7. Разработчик проводит review и одобряет изменения
8. После успешных проверок PR объединяется с основной веткой

Для автоматизации можно использовать GitHub Actions, GitLab CI и аналогичные системы.

Важно ограничить права агента:

- Не разрешать обход protected branches
- Не предоставлять ненужные секреты и production-доступы
- Не разрешать принудительную перезапись истории без явного согласования
- Требовать подтверждения для критических действий

Успешный CI подтверждает прохождение заданных проверок, но не гарантирует соответствие всем бизнес-требованиям.

# Как организовать работу с агентом, чтобы он не вносил изменения за пределами задачи?

Необходимо ограничивать область изменений (scope) на уровне инструкций и доступных инструментов.

В постановке задачи следует указать:

- Какие файлы и директории разрешено изменять
- Какие компоненты должны оставаться неизменными
- Разрешено ли добавлять зависимости
- Допустимы ли изменения публичных API и схемы базы данных
- Какие действия требуют предварительного подтверждения

Например:

> Измени только модуль `src/features/profile`. Не обновляй зависимости, не меняй публичные интерфейсы и не форматируй несвязанные файлы. Если потребуются изменения за пределами модуля, сначала объясни причину.

После реализации необходимо проверить `git status` и `git diff --stat`, затем просмотреть полный diff.

Для более строгого контроля можно использовать файловые разрешения, изолированные рабочие каталоги и автоматические проверки допустимых путей в CI.

Важно: ограничение в промпте не является механизмом безопасности. Если агент обладает правами на изменение всего репозитория, технически он может выйти за обозначенные рамки.

# Как использовать ИИ для генерации и актуализации технической документации?

ИИ-агент может создавать документацию на основе существующего кода, интерфейсов, тестов и архитектурных решений.

Основные сценарии:

- Генерация README и инструкций по запуску
- Описание API, параметров и форматов ответов
- Документирование модулей, компонентов и зависимостей
- Создание ADR и описаний архитектурных решений
- Обновление документации после изменения функциональности
- Поиск расхождений между документацией и реализацией

Например, агент может изучить NestJS-контроллеры, DTO и декораторы, затем обновить описание REST API.

При этом необходимо разделять автоматически извлекаемые факты и сведения, требующие интерпретации, например бизнес-назначение или причины архитектурных решений.

Для актуализации удобно включать проверку документации в процесс разработки:

1. Агент анализирует изменения кода
2. Определяет затронутые разделы документации
3. Обновляет их с учётом фактического поведения
4. Проверяет ссылки, примеры и команды
5. Включает документацию в тот же PR

Документация должна отражать реальную реализацию. Нельзя описывать предполагаемые возможности как уже существующие.

# Как организовать автономную работу агента над задачей с минимальным участием разработчика?

Автономная работа требует чёткой задачи, контролируемого окружения, инструментов проверки и правил остановки.

Основные элементы:

1. Спецификация - требования, ограничения и критерии приёмки
2. Рабочее окружение - отдельная ветка или worktree с доступными зависимостями
3. Инструкции - архитектурные правила, соглашения и команды проверки
4. План - последовательность шагов с измеримыми результатами
5. Инструменты - разрешённые операции с файлами, терминалом, Git и тестами
6. Самопроверка - автоматический запуск тестов, линтеров и сборки после изменений
7. Ограничения - допустимое время, расходы, количество повторных попыток и полномочия
8. Отчётность - описание изменений, результатов проверок и нерешённых проблем

Агент может работать по циклу:

`Analyze → Plan → Implement → Test → Review → Fix`

После каждой итерации он анализирует результаты и определяет, выполнены ли критерии приёмки.

Следует заранее определить условия, при которых агент обязан остановиться и запросить решение разработчика:

- Неоднозначные или противоречивые требования
- Необходимость изменения архитектуры за пределами задачи
- Миграции с риском потери данных
- Операции с production-средой или секретами
- Повторяющиеся ошибки без установленной причины
- Невозможность подтвердить корректность результата

Для уменьшения рисков применяют sandbox, принцип минимальных привилегий, ограничение сетевого доступа и обязательные CI-проверки.

Дополнительно необходимо учитывать prompt injection: инструкции из README, комментариев, внешних страниц и результатов инструментов могут быть недоверенными. Агент не должен автоматически воспринимать их как разрешение выполнять опасные команды.

Оптимальная модель - автономное выполнение в заранее заданных границах с обязательной проверкой результата. Разработчик определяет требования и контролирует критические решения, а агент выполняет рутинные операции и промежуточные проверки.
