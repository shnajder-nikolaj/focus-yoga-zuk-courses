# Как GraphQL schema и resolvers определяют выполнение запроса по сравнению с REST API?

GraphQL schema задаёт доступные типы, поля, аргументы и операции. Клиент выбирает нужные поля, а execution engine вызывает resolvers и собирает ответ выбранной формы. Schema не определяет автоматически, откуда берутся данные и сколько запросов сделает backend.

REST API обычно организует взаимодействие через ресурсы и HTTP-операции с заранее определёнными представлениями. GraphQL удобен для разнообразных запросов клиентов, но требует контроля стоимости, авторизации и загрузки данных. Он не заменяет бизнес-модель и не гарантирует один SQL-запрос. [GraphQL execution](https://graphql.org/learn/execution/).

# Почему в GraphQL возникает N+1 и как request-scoped batching решает эту проблему?

N+1 возникает, когда сначала загружают список N объектов, а затем resolver каждого делает отдельный запрос связанного значения. **Batching** собирает ключи нескольких обращений и загружает их одним запросом; memoization позволяет не повторять загрузку одного ключа.

DataLoader обычно создают для отдельного запроса с нужным auth context. Глобальный кэш без учёта доступа может раскрыть чужие данные. Batch function должна вернуть результаты в порядке исходных ключей и корректно представить отсутствующие значения. [DataLoader](https://github.com/graphql/dataloader).

# Как проектировать авторизацию и ограничения стоимости GraphQL-запроса?

Authentication устанавливает пользователя, а авторизацию проверяют на доступ к объектам и операциям, включая вложенные resolvers. Проверки только корневого поля недостаточно, если тот же объект достижим другим путём.

Ограничивают размер запроса, глубину, aliases, pagination и вычисленную стоимость, а также реальную конкурентность и время выполнения. Один лимит HTTP-запросов не защищает от дорогого запроса с множеством полей. Для известных клиентов могут использоваться разрешённые persisted operations; отключение introspection не заменяет эти меры. [GraphQL security](https://graphql.org/learn/security/).

# Как nullability и error propagation определяют частичный ответ GraphQL?

GraphQL-ответ может содержать одновременно `data` и `errors`, если часть полей вычислена успешно. Ошибка nullable-поля обычно даёт `null` в этом месте; ошибка non-null поля распространяется вверх до ближайшего nullable-предка, иногда делая всё `data` равным null.

Nullability списка и его элементов задаётся отдельно. Клиент должен проверять и данные, и ошибки, а не только HTTP-статус. Non-null означает сильное обещание и может увеличить область недоступного результата при сбое зависимости. [GraphQL response](https://graphql.org/learn/response/).

# Какие гарантии порядка дают GraphQL mutations и означают ли они транзакцию?

Корневые поля одной mutation-операции выполняются последовательно в порядке, установленном execution semantics. Это позволяет одному полю завершиться перед следующим, но не сериализует все mutation-запросы всех пользователей и не задаёт общую транзакцию БД.

Если первое действие завершилось, а второе упало, автоматического rollback нет. Атомарный бизнес-сценарий лучше представить отдельной mutation и реализовать транзакцию или иной механизм внутри приложения. Вложенные поля подчиняются своим правилам execution. [Serial execution GraphQL](https://spec.graphql.org/September2025/#sec-Normal-and-Serial-Execution).

# Как эволюционировать GraphQL schema через добавления и deprecation?

Обычно добавляют новые поля и типы, а устаревшие помечают `@deprecated` с объяснением альтернативы. Удаление планируют после анализа использования и согласованного переходного периода. GraphQL не запрещает версионирование, но позволяет многие изменения выполнять внутри одной evolving schema.

Новое обязательное input-поле, смена смысла, типа или nullability требуют анализа совместимости. Добавление enum value тоже может ломать клиент с exhaustive-обработкой. Проверяют реальные операции поддерживаемых клиентов и generated code, а не только валидность schema. [Эволюция GraphQL schema](https://graphql.org/learn/schema-design/#versioning).

# Как gRPC service definition и Protocol Buffers используются для генерации клиентов и серверов?

В `.proto` описывают сообщения, service и его RPC-методы. `protoc` с подходящими plugins генерирует типы сообщений, client stubs и серверные интерфейсы для поддерживаемых языков. Реализация заполняет бизнес-обработчики.

Protocol Buffers отвечает за структуру и сериализацию сообщений, а gRPC — за RPC-взаимодействие и связанный lifecycle. Это разные части стека: Protobuf можно использовать без gRPC. Генерация сокращает ручное согласование типов, но не проверяет смысл операций и бизнес-права. [gRPC core concepts](https://grpc.io/docs/what-is-grpc/core-concepts/).

# Чем unary, server streaming, client streaming и bidirectional streaming отличаются в gRPC?

`Unary` передаёт один запрос и один ответ. При `server streaming` сервер возвращает поток сообщений, при `client streaming` клиент отправляет поток и получает итоговый ответ, а `bidirectional streaming` допускает потоки в обе стороны.

Порядок сообщений сохраняется внутри соответствующего потока, но не создаёт глобального порядка разных RPC. Для потоков проектируют flow control, ограничения памяти, отмену и поведение при частичном результате. Уже полученные сообщения не исчезают при ошибке финального status. [Типы gRPC RPC](https://grpc.io/docs/what-is-grpc/core-concepts/).

# Как gRPC deadlines, cancellation, status codes и retries влияют на результат RPC?

Deadline ограничивает ожидание RPC, cancellation сообщает о прекращении интереса к результату, а status code классифицирует завершение. Сервер должен кооперативно прекращать ненужную работу; client timeout не доказывает, что изменение на сервере не произошло.

Retries зависят от client implementation, service config и стадии вызова. Даже `UNAVAILABLE` не делает произвольную операцию идемпотентной. Для изменяющих RPC нужны бизнес-ключи повторов и проверка результата. В потоковом RPC отдельно учитывают уже доставленные сообщения и невозможность простого полного повтора. [gRPC retry](https://grpc.io/docs/guides/retry/).

# Как field numbers, reserved и неизвестные поля обеспечивают эволюцию Protobuf-схемы?

В бинарном Protobuf поле идентифицируется номером, поэтому удалённые номера нельзя использовать для другого смысла. Их и прежние имена помечают `reserved`, чтобы избежать случайного повторного применения. Добавление нового поля обычно совместимо на wire-уровне при соблюдении правил.

Неизвестные поля могут сохраняться при parse/serialize поддерживаемым runtime, но преобразование через JSON или ручную сборку объекта способно их потерять. Wire compatibility не доказывает семантической совместимости: изменение единиц или значения enum требует отдельного анализа. [Эволюция proto3](https://protobuf.dev/programming-guides/proto3/).

# Чем explicit field presence отличается от default values в Protobuf?

При **implicit presence** чтение скалярного поля с default, например `0`, не позволяет отличить его отсутствие от явно переданного нуля. Это важно для частичного изменения данных: «установить ноль» и «не менять» являются разными командами.

В proto3 `optional` для basic types включает explicit presence; message fields и `oneof` также отслеживают присутствие. Repeated fields и maps обычно не различают отсутствие и пустоту. В Protobuf Editions действуют собственные настройки presence, поэтому формат и generated API проверяют явно. [Field presence](https://protobuf.dev/programming-guides/field_presence/).

# Какие ограничения возникают при использовании GraphQL subscriptions и gRPC из браузера?

GraphQL subscriptions требуют транспорта и server/client реализации для длительного потока, например WebSocket или SSE. Нужно определить auth lifecycle, reconnect, пропуски, ограничения соединений и доставку: сам GraphQL не обещает durable replay.

Обычный браузерный API не предоставляет все механизмы нативного gRPC. Часто используют gRPC-Web и совместимый proxy/server; доступные streaming modes зависят от клиента и транспорта. Нельзя автоматически переносить возможности bidirectional gRPC из серверного SDK в браузер. [GraphQL subscriptions](https://graphql.org/learn/subscriptions/), [gRPC-Web](https://grpc.io/docs/platforms/web/basics/).
