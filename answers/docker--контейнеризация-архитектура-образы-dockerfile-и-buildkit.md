# Как контейнер использует namespaces и cgroups и чем отличается от виртуальной машины?

В Linux **namespaces** дают процессам отдельные представления PID, сети, mounts и других ресурсов, а **cgroups** учитывают и ограничивают потребление CPU, памяти и других ресурсов. Контейнер использует ядро host, вместо запуска собственного полноценного гостевого ядра, как обычная VM.

Поэтому совместимость userspace зависит от ядра, архитектуры и runtime, а изоляция не тождественна аппаратной виртуализации. На macOS и Windows Linux-контейнеры обычно работают внутри Linux VM, управляемой Docker Desktop. Это добавляет границу VM между контейнерами и основной ОС, но не отдельную VM на каждый контейнер.

# Как Docker CLI, daemon, containerd и OCI runtime участвуют в запуске контейнера?

**Docker CLI** отправляет запросы API в **Docker daemon**, который управляет images, контейнерами, сетями и volumes. Для жизненного цикла контейнеров Docker Engine использует **containerd**, а низкоуровневый **OCI runtime**, например `runc`, создаёт процессы и их окружение по OCI-спецификации.

Конкретные детали зависят от платформы и runtime. CLI может работать с удалённым daemon: локальная команда не обязательно запускает контейнер на той же машине. Доступ к API daemon является привилегированным инфраструктурным доступом, особенно если разрешено создавать mounts host и privileged containers.

# Чем image, container, layer и writable layer отличаются по жизненному циклу?

**Image** содержит неизменяемые filesystem layers и конфигурацию запуска. **Layer** описывает изменения относительно предыдущего слоя; одинаковые слои могут использоваться несколькими images. **Container** — экземпляр запуска с процессами, настройками и собственным writable layer.

Изменение файла внутри контейнера обычно затрагивает его writable layer, а не исходный image. Удаление контейнера теряет такие изменения, если данные не вынесены в отдельное хранилище. Остановка контейнера сама по себе слой не удаляет. Новый image не обновляет уже работающий контейнер автоматически.

# Как build context и .dockerignore влияют на входные данные сборки?

**Build context** — доступный сборщику набор входных файлов. `COPY` и локальный `ADD` берут данные из разрешённого контекста или явно указанных дополнительных источников. Случайно включённые `.git`, dependencies и секреты увеличивают передачу, cache churn и риск утечки.

`.dockerignore` исключает ненужные файлы до использования контекста сборки. Он не исправит секрет, уже скопированный в предыдущий image. Для воспроизводимости контекст должен содержать необходимые versioned inputs и не зависеть от случайных локальных artifacts. Для remote builder особенно важны размер передаваемых данных и границы доступа.

# Как FROM, RUN, COPY и WORKDIR формируют файловую систему образа?

`FROM` выбирает базу или начинает stage; `RUN` выполняет build-команду и сохраняет её файловые изменения. `COPY` переносит файлы из контекста или другого stage, а `WORKDIR` задаёт рабочий каталог для следующих инструкций и процесса по умолчанию.

Файловые слои образуют историю изменений, а часть инструкций меняет image metadata. `RUN cd …` не переносит рабочий каталог в следующий независимый `RUN`; для устойчивого эффекта используют `WORKDIR` или одну связанную команду. Внешние загрузки и package repositories тоже являются входами сборки, даже если не видны в контексте.

# Чем ARG отличается от ENV и какие данные сохраняются в результате сборки?

`ARG` задаёт build-time параметр в пределах своей области видимости. `ENV` записывает переменную в конфигурацию image, поэтому она по умолчанию доступна и запущенному контейнеру, если не переопределена.

`ARG` не становится runtime environment автоматически, но это не безопасный канал для секретов: значение может попасть в команды, history, provenance или результат сборки. `ENV` с credential сохраняет его ещё очевиднее. Для параметров без чувствительных значений документируют defaults; для secrets используют специализированные BuildKit mounts. [Build secrets](https://docs.docker.com/build/building/secrets/).

# Как ENTRYPOINT и CMD взаимодействуют в exec form и shell form?

`ENTRYPOINT` задаёт основной executable, а `CMD` часто предоставляет default arguments к нему. Аргументы запуска после image обычно заменяют `CMD`, сохраняя exec-form `ENTRYPOINT`; сам entrypoint можно переопределить отдельно.

**Exec form** использует JSON-массив аргументов и запускает процесс без неявного shell. **Shell form** выполняется через shell и меняет поведение подстановки, аргументов и сигналов. Переменные не раскрываются автоматически в JSON-массиве как в shell. Для предсказуемого graceful shutdown обычно выбирают exec form или завершают wrapper через `exec`. [Dockerfile reference](https://docs.docker.com/reference/dockerfile/).

# Почему PID 1, сигналы и zombie processes важны для контейнерного приложения?

Главный процесс контейнера обычно получает PID 1 в его PID namespace и отвечает за завершение контейнера. У PID 1 есть особенности обработки сигналов по умолчанию; приложение должно явно поддерживать нужное завершение, а wrapper — передавать сигналы или заменять себя через `exec`.

Осиротевшие дочерние процессы требуют **reaping**, иначе остаются zombie entries. Небольшой init, например через Docker `--init`, помогает передавать сигналы и собирать детей, но не исправляет неправильную бизнес-логику остановки. Проверяют `SIGTERM`, timeout и выход всех дочерних процессов, а не только успешный старт.

# Как multi-stage Dockerfile отделяет toolchain от runtime-артефактов?

В **multi-stage build** отдельные stages содержат compiler, package manager и test tools, а финальный stage получает только нужные runtime artifacts через `COPY --from=…`. Так в production image не попадает весь toolchain и исходный build workspace.

Проверяют runtime libraries, сертификаты, timezone data, пользователя и архитектуру: скопированный binary может зависеть от отсутствующей libc. Build stage не становится безопасным только потому, что его нет в final image — он всё ещё может иметь доступ к credentials и сети. [Multi-stage builds](https://docs.docker.com/build/building/multi-stage/).

# Как BuildKit строит граф сборки и использует cache mounts и внешние кеши?

**BuildKit** рассматривает сборку как граф зависимостей, переиспользует подходящие результаты и может параллельно выполнять независимые части. Изменение входов узла инвалидирует связанные результаты, поэтому структура Dockerfile влияет на повторную работу.

`RUN --mount=type=cache` сохраняет кеш package manager между подходящими сборками без обязательного включения его целиком в image layer. External cache переносит reuse между builders и CI jobs. Кеш должен быть ускорением, а не единственным источником обязательных данных; его доступ и доверие контролируют отдельно. [Build cache](https://docs.docker.com/build/cache/optimize/).

# Как secret mounts и SSH mounts BuildKit передают доступ без включения ключа в слой?

`--mount=type=secret` делает секрет временно доступным конкретной build-инструкции, а SSH mount позволяет использовать SSH agent или предусмотренный SSH-доступ без обычного копирования приватного ключа в filesystem image.

Это защищает способ доставки, но сама команда может записать секрет в artifact, cache или stdout. Такие эффекты исключают отдельно. Изменение значения secret обычно не инвалидирует BuildKit cache автоматически: при необходимости задают безопасный дополнительный cache-busting input. Для private dependency не следует заменять mount на `COPY` ключа с последующим удалением. [Secrets и SSH mounts](https://docs.docker.com/build/building/secrets/).

# Как buildx и multi-platform manifests связывают архитектуру сборки с платформой запуска?

`buildx` предоставляет работу с BuildKit builders и целевыми platforms. Multi-platform image index ссылается на отдельные manifests, например для `linux/amd64` и `linux/arm64`; runtime выбирает подходящий вариант.

Собирать можно на native nodes, через emulation либо cross-compilation. `BUILDPLATFORM` и `TARGETPLATFORM` помогают разделить платформу build-инструмента и результата. Один лишь tag `arm64` не меняет архитектуру binary. Проверяют native dependencies, динамический linker и исполнение тестов на нужной платформе; QEMU может заметно замедлять сборку. [Multi-platform builds](https://docs.docker.com/build/building/multi-platform/).
