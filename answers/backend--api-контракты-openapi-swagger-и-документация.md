# Что входит в API-контракт кроме JSON-схемы тела запроса?

Контракт включает методы и пути, параметры, headers, форматы request/response, статусы, ошибки, authentication, семантику операций и совместимость. Также фиксируют пагинацию, ограничения, идемпотентность, конкурентные изменения и допустимые сроки ответа.

Например, одинаковая схема `status: string` не объясняет, означает ли `accepted` окончательный результат или начало асинхронной работы. Клиенты зависят и от такого поведения. Документированный контракт должен соответствовать реализации и иметь понятного владельца.

# Чем OpenAPI Specification отличается от Swagger UI и генераторов клиентов?

**OpenAPI Specification** задаёт машиночитаемый формат описания HTTP API. **Swagger UI** отображает такое описание и позволяет исследовать API, а генераторы строят клиентские библиотеки, серверные заготовки или документацию.

Это разные инструменты вокруг одного описания. Наличие красивой страницы не доказывает соответствие работающего сервера контракту. Сгенерированный SDK также требует проверки: поддержка версии OpenAPI, security schemes, nullable и составных схем различается между генераторами.

# Как описывать required, nullable, форматы и ограничения полей с учётом версии OpenAPI?

`required` определяет обязательность присутствия свойства, а допустимость `null` — отдельное ограничение. В OpenAPI 3.0 используют `nullable: true` вместе с подходящим типом; в 3.1 null описывают средствами JSON Schema, например `type: [string, 'null']`.

`format` не во всех инструментах является проверяемым ограничением. Явно задают диапазоны, длины и шаблоны, проверяют диалект и поддержку валидатора. Отсутствующее поле и поле с null не должны случайно означать одно и то же. [OAS 3.1.1](https://spec.openapis.org/oas/v3.1.1.html), [типы OAS 3.0](https://swagger.io/docs/specification/v3_0/data-models/data-types/).

# Как документировать HTTP-статусы и единый формат ошибок API?

Для операции описывают успешные и ожидаемые ошибочные ответы с общим форматом: стабильный машинный код, безопасное описание, correlation identifier и детали полей при необходимости. HTTP-статус отражает класс результата, а бизнес-код уточняет причину.

Можно использовать Problem Details, сохраняя предсказуемые расширения. В примерах различают неверный формат, отсутствие доступа, конфликт версии, бизнес-отказ и внутреннюю ошибку. Stack trace и SQL не являются частью внешнего контракта. Клиент не должен разбирать текст сообщения для принятия решения.

# Как описать authentication schemes и требования авторизации в OpenAPI?

В `components.securitySchemes` описывают механизм, например HTTP bearer, API key или OAuth2, а `security` связывает его с API либо конкретной операцией. Альтернативы механизмов и совместное требование нескольких схем имеют разную структуру и смысл.

Такая декларация документирует способ доступа, но не реализует защиту. Права на конкретный объект, tenant и предметные ограничения описывают дополнительно и проверяют на сервере. OAuth scopes не заменяют всю ресурсную авторизацию. [Security в OpenAPI](https://spec.openapis.org/oas/v3.1.1.html#security-requirement-object).

# Как фиксировать контракт пагинации, фильтрации и сортировки API?

Задают допустимые поля и операторы фильтра, порядок сортировки, default/max page size и формат следующей страницы. Для устойчивой сортировки нужен уникальный tie-breaker, например `(created_at, id)`.

У cursor-based пагинации описывают связь cursor с фильтром, срок действия и поведение при изменении данных. У offset-based — возможные пропуски или повторы на меняющемся наборе. Также фиксируют, возвращается ли точное total count: его вычисление может быть дорогим и не всегда необходимо.

# Как описывать идемпотентность, конкурентные изменения и ограничения частоты запросов?

Для изменяющей операции описывают область и срок хранения idempotency key, повтор с тем же payload и реакцию на другой payload под тем же ключом. Для конкурентных правок задают версию или `ETag`/`If-Match` и ответ при конфликте.

Rate limit включает единицу ограничения, область пользователя или клиента, заголовки и поведение при исчерпании, включая `Retry-After`, если он используется. Неизвестный исход после timeout нужно отличать от гарантированного отказа. Такие правила важны для безопасного SDK и retry-политики.

# Какие изменения API являются breaking changes даже при сохранении типов полей?

Breaking change может изменить смысл поля, единицы измерения, сортировку, default, статус ошибки, authentication или гарантию идемпотентности. Тип `number` останется прежним, если секунды заменили миллисекундами, но поведение клиента сломается.

Удаление поля или новое обязательное поле обычно несовместимы; новое значение enum тоже может ломать exhaustive-клиент. Изменение nullability оценивают отдельно для входа и выхода. Совместимость проверяют по реальным потребителям и направлению обмена, а не только структурным diff.

# Чем design-first подход отличается от code-first при работе с OpenAPI?

При **design-first** контракт обсуждают до реализации и используют для согласования, mocks и генерации. При **code-first** описание получают из маршрутов, типов или аннотаций работающего кода. Оба подхода требуют одного понятного источника истины.

Design-first рискует отстать от сервера, code-first — пропустить семантику и экспортировать внутренние типы. В обоих случаях изменения проходят review и автоматические проверки. Выбор зависит от организации команд и возможностей стека, а не от обязательного превосходства одного подхода.

# Как проверять соответствие реализации OpenAPI-контракту в CI?

Проверяют синтаксис и правила описания, ищут несовместимые изменения относительно поддерживаемого контракта, затем выполняют запросы к приложению и валидируют статусы, headers и тела ответов. Для code-first проверяют, что сгенерированное описание обновлено.

Нужны позитивные и ошибочные сценарии, authentication и реальные формы данных. Схемный тест не доказывает правильность бизнес-правил или поведение всех клиентов; consumer contracts и интеграционные проверки дополняют его. Проверки должны падать на реальном расхождении, а не только на невалидном YAML.

# Как поддерживать примеры, SDK и пользовательскую документацию API в актуальном состоянии?

Примеры делают исполняемыми или проверяют их данные по схемам. SDK генерируют закреплённой версией инструмента и проверяют на ключевых сценариях, включая ошибки и повторные запросы. Публикуют changelog и сроки deprecation для потребителей.

В документации используют фиктивные ключи и обезличенные значения. Ссылка на актуальное описание связывается с версией API или релиза; одна страница без указания версии вводит клиентов в заблуждение при параллельной поддержке нескольких контрактов.

# Как описывать webhooks и границы применимости OpenAPI для асинхронного взаимодействия?

В OpenAPI 3.1 есть top-level `webhooks`; `callbacks` описывают вызовы, связанные с конкретной операцией и адресом, определяемым её контекстом. Нужно зафиксировать payload, подпись, идентификатор доставки, повторы и ожидаемые ответы получателя.

OpenAPI описывает HTTP-границу, но не всю модель брокера, партиций и доставки событий. Для более общего event-driven контракта применяют подходящий формат, например AsyncAPI, согласуя общие схемы. Версию и поддержку инструментов проверяют отдельно. [Webhooks и callbacks OAS](https://spec.openapis.org/oas/v3.1.1.html#openapi-object).
