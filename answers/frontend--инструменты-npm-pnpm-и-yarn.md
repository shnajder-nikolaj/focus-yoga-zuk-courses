# Какую роль выполняет `package.json`?

`package.json` - основной файл конфигурации Node.js-проекта, описывающий его метаданные, зависимости и команды.

Содержит:

- `name`, `version` - название и версию пакета
- `dependencies`, `devDependencies` - зависимости проекта
- `scripts` - команды для запуска, сборки, тестирования
- `type` - режим интерпретации `.js` файлов (`module` или `commonjs`)
- `main`, `exports`, `types` - точки входа и публичный API пакета
- `engines` - требования к версиям Node.js и других инструментов
- `workspaces` - конфигурацию монорепозитория

`package.json` описывает требования к зависимостям, но не обязательно фиксирует их точные установленные версии. Для этого используется lockfile.

# Чем `dependencies`, `devDependencies`, `peerDependencies` и `optionalDependencies` отличаются?

- `dependencies` - пакеты, необходимые приложению или библиотеке для работы. Например, `react-router`.
- `devDependencies` - инструменты разработки, сборки и тестирования. Например, `typescript`, `vite`, `eslint`. Обычно исключаются при установке с `--omit=dev`.
- `peerDependencies` - зависимости, совместимую версию которых должен предоставлять потребитель пакета. Например, библиотека React-компонентов объявляет `react` как peer dependency, чтобы использовать React приложения.
- `optionalDependencies` - необязательные зависимости. Если их установка завершается ошибкой, npm может продолжить установку. Код должен учитывать их отсутствие.

Начиная с npm 7, `peerDependencies` по умолчанию устанавливаются автоматически, если npm может корректно разрешить дерево зависимостей. Поэтому они не просто информационные требования.&#x20;

# Как работает semver и диапазоны `^` и `~`?

Semantic Versioning (SemVer) - система версионирования `MAJOR.MINOR.PATCH`:

- `MAJOR` - несовместимые изменения публичного API
- `MINOR` - новая функциональность с сохранением обратной совместимости
- `PATCH` - исправления с сохранением обратной совместимости

Диапазоны определяют допустимые версии:

- `^1.2.3` - от `1.2.3` до `2.0.0` (не включительно). Разрешает `MINOR` и `PATCH`.
- `~1.2.3` - от `1.2.3` до `1.3.0` (не включительно). Разрешает только `PATCH`.
- `1.2.3` - строго указанная версия.

Важная особенность: для версий `0.x` оператор `^` строже. Например, `^0.2.3` разрешает версии от `0.2.3` до `0.3.0` (не включительно), поскольку API считается нестабильным.

Предрелизные версии (`alpha`, `beta`, `rc`) по умолчанию не входят в обычные диапазоны без соответствующего указания предрелиза. SemVer также предполагает, что автор библиотеки соблюдает правила совместимости.&#x20;

# Чем `npm install` отличается от `npm ci`?

`npm install` предназначен преимущественно для разработки:

- Устанавливает зависимости согласно `package.json` и существующему lockfile
- Может изменять `package-lock.json`, если обнаруживает несоответствия
- Позволяет добавлять новые зависимости
- Обычно сохраняет существующий `node_modules`, изменяя его по необходимости

`npm ci` предназначен для воспроизводимой чистой установки:

- Требует существующий lockfile
- Проверяет соответствие lockfile и `package.json`, иначе завершает работу с ошибкой
- Удаляет существующий `node_modules` перед установкой
- Не изменяет `package.json` и lockfile
- Не позволяет добавлять отдельные пакеты

Практика: `npm install` используют при разработке, `npm ci` - в CI/CD и при автоматизированной сборке.

Для одинакового результата важны также версии инструментов, конфигурация установки и окружение.&#x20;

# Для чего нужен lockfile и почему его коммитят в репозиторий?

Lockfile фиксирует разрешённое дерево зависимостей, включая транзитивные пакеты, их версии, источники и контрольные суммы.

Основные форматы:

- npm - `package-lock.json`
- pnpm - `pnpm-lock.yaml`
- Yarn - `yarn.lock`

Например, `package.json` допускает `^1.2.3`, но lockfile фиксирует конкретную версию `1.4.2`.

Lockfile коммитят, чтобы:

- Обеспечить воспроизводимость установки между разработчиками и CI/CD
- Избежать неожиданных обновлений транзитивных зависимостей
- Контролировать изменения дерева зависимостей через Git
- Упростить анализ безопасности и откат обновлений

Lockfile фиксирует зависимости, но не гарантирует идентичное поведение на разных платформах, поскольку могут отличаться Node.js, операционная система и платформозависимые пакеты.

# Чем pnpm отличается от npm по способу хранения пакетов?

npm по умолчанию устанавливает зависимости в проектный `node_modules`, используя hoisting - размещение совместимых зависимостей ближе к корню дерева. Разные проекты могут иметь отдельные физические копии установленных файлов.

pnpm использует общее content-addressable хранилище, где файлы идентифицируются по содержимому.

Механизм:

1. Пакеты загружаются в общее хранилище.
2. Их файлы размещаются в проекте преимущественно через hard links.
3. Символические ссылки формируют структуру доступных зависимостей внутри `node_modules`.

Преимущества:

- Экономия дискового пространства между проектами
- Повторное использование уже загруженных файлов
- Более строгая изоляция зависимостей
- Меньше случайных обращений к незадекларированным пакетам

При этом npm тоже использует кэш и поддерживает альтернативные стратегии размещения. Главное отличие стандартной модели pnpm - повторное использование содержимого файлов и изолированная структура зависимостей.&#x20;

# Какие проблемы решает Yarn Plug'n'Play?

Yarn Plug'n'Play (PnP) - механизм разрешения зависимостей без традиционного каталога `node_modules`.

Вместо поиска модулей по файловой системе Yarn создаёт `.pnp.cjs`, содержащий информацию о зависимостях и расположении пакетов.

Решает несколько проблем:

- Ghost dependencies - использование пакетов, не объявленных в `package.json`, но случайно доступных благодаря hoisting.
- Избыточные файловые операции - не требуется создавать большое дерево `node_modules`.
- Неоднозначность разрешения - зависимости разрешаются согласно явно описанному графу.

Ограничение - некоторые инструменты ожидают физический `node_modules` и требуют дополнительной настройки.

PnP используется по умолчанию в современных версиях Yarn для новых проектов, но может быть отключён через `nodeLinker: node-modules`.&#x20;

# Что такое транзитивные зависимости?

Транзитивные зависимости - пакеты, которые устанавливаются не напрямую по требованию проекта, а как зависимости других пакетов.

Например:

`app -> package-a -> package-b`

Здесь `package-a` - прямая зависимость приложения, а `package-b` - транзитивная.

Транзитивные зависимости могут иметь собственные зависимости, формируя многоуровневый граф.

Они влияют на размер установки, безопасность, лицензирование и совместимость проекта, даже если приложение не импортирует их напрямую.

Для анализа используются `npm ls --all` и `npm explain <package>`.

# Почему разные версии зависимостей могут привести к дублированию React?

Если две библиотеки требуют несовместимые версии React через `dependencies`, пакетный менеджер может установить несколько экземпляров React.

Например:

- Приложение использует `react@19`
- Сторонняя библиотека требует `react@18` как обычную зависимость
- Обе версии оказываются в дереве зависимостей

Проблема возникает, когда компонент использует один экземпляр React, а `react-dom` - другой. Идентичность React-модуля должна совпадать между компонентом и рендерером, иначе возможна ошибка `Invalid hook call`.

Дублирование также может возникнуть из-за `npm link`, монорепозиториев или неправильной конфигурации сборщика.

Решение - объявлять React в библиотеках через `peerDependencies`, исключать его из библиотечной сборки и проверять дерево командой `npm ls react`.

Наличие нескольких независимых React-приложений на странице само по себе не является ошибкой.&#x20;

# Что такое npm workspaces?

npm workspaces - механизм управления несколькими взаимосвязанными пакетами внутри одного репозитория (monorepo).

Корневой `package.json` определяет расположение пакетов:

```
{
  "private": true,
  "workspaces": ["packages/*"]
}
```

Каждый пакет имеет собственный `package.json`, но использует общую инфраструктуру установки.

Возможности:

- Автоматическое связывание локальных пакетов
- Управление зависимостями из корня репозитория
- Общий lockfile
- Запуск команд для отдельных пакетов через `npm run build -w package-name`

Workspaces упрощают управление монорепозиторием, но сами по себе не предоставляют полноценную систему оркестрации сборок, кэширования и определения затронутых проектов.

# Как правильно публиковать библиотеку с peer dependency на React?

React необходимо объявить в `peerDependencies`, а для локальной разработки и тестирования - также в `devDependencies`.

Пример:

```
{
  "name": "my-react-library",
  "version": "1.0.0",
  "peerDependencies": {
    "react": "^18.0.0 || ^19.0.0"
  },
  "devDependencies": {
    "react": "^19.0.0"
  }
}
```

Диапазон совместимости должен включать только протестированные версии React.

Основные правила:

- Не помещать React в обычные `dependencies` без особой необходимости
- Исключить `react` и `react/jsx-runtime` из библиотечной сборки через `external`
- Если библиотека использует `react-dom`, также корректно объявить его как peer dependency
- Настроить `exports`, `types` и публикуемые файлы
- Проверить содержимое публикации через `npm pack --dry-run`
- Протестировать установленную библиотеку в отдельном приложении

Цель - использовать экземпляр React приложения, а не включать собственную копию в библиотеку.

# Чем `overrides` отличается от обычного указания версии зависимости?

Обычная запись в `dependencies` определяет требуемую версию прямой зависимости.

`overrides` позволяет принудительно изменять разрешение зависимостей внутри всего дерева, включая транзитивные пакеты.

Например:

```
{
  "dependencies": {
    "package-a": "^1.0.0"
  },
  "overrides": {
    "lodash": "4.17.21"
  }
}
```

Если `package-a` использует `lodash`, npm применит переопределение к соответствующим вхождениям `lodash` в дереве.

Используется для устранения уязвимостей, исправления конфликтов и принудительного выбора версий.

Важно: `overrides` не гарантирует совместимость переопределённой зависимости. Кроме того, npm учитывает это поле только из корневого `package.json`, а прямые зависимости нельзя произвольно переопределять на другую спецификацию версии.&#x20;

# Как диагностировать конфликт peer dependencies?

Конфликт возникает, когда требования разных библиотек к общей зависимости невозможно удовлетворить совместимой конфигурацией.

Например, одна библиотека требует `react@^18`, другая - `react@^19`.

Порядок диагностики:

1. Изучить ошибку `ERESOLVE`, особенно блоки `Found` и `Could not resolve dependency`.
2. Выполнить `npm ls react` для просмотра установленных версий и конфликтов.
3. Использовать `npm explain react`, чтобы понять, какие пакеты требуют React.
4. Проверить `peerDependencies` конфликтующих библиотек.
5. Найти совместимые версии библиотек или обновить зависимости согласованно.

`--legacy-peer-deps` не исправляет конфликт, а отключает проверку peer dependencies при построении дерева. Это может скрыть несовместимость и привести к ошибкам во время выполнения.

# Как безопасно обновлять зависимости с breaking changes?

Breaking changes - изменения, нарушающие совместимость с предыдущими версиями API или поведения.

Последовательность обновления:

1. Изучить changelog, release notes и migration guide новой версии.
2. Проверить требования к Node.js, peer dependencies и другим библиотекам.
3. Обновлять крупные зависимости по отдельности, по возможности переходя через промежуточные версии.
4. Адаптировать код под изменённые API.
5. Запустить проверку типов, линтер, unit-, integration- и E2E-тесты.
6. Проверить production-сборку и поведение приложения.
7. Зафиксировать обновлённые `package.json` и lockfile.

Для проверки доступных обновлений используется `npm outdated`.

Главный принцип - контролируемое обновление с возможностью отката. Даже `PATCH` и `MINOR` требуют тестирования, поскольку библиотеки не всегда строго соблюдают SemVer.

# Для чего нужен `npm audit` и почему его результат требует анализа?

`npm audit` проверяет дерево зависимостей на известные уязвимости, сопоставляя версии установленных пакетов с данными security advisories.

Он показывает:

- Уязвимые пакеты и затронутые версии
- Уровни серьёзности
- Цепочки зависимостей, через которые они попали в проект
- Доступные варианты исправления

Однако наличие уязвимой зависимости не обязательно означает, что приложение можно атаковать.

Необходимо оценивать:

- Используется ли уязвимый код
- Присутствует ли зависимость в production или только при разработке
- Достижим ли уязвимый сценарий
- Существует ли исправленная совместимая версия

`npm audit fix --force` может вызвать breaking changes, поэтому его нельзя использовать без проверки последствий.

Кроме того, `npm audit` обнаруживает известные уязвимости, но не гарантирует отсутствие неизвестных проблем или вредоносного кода.&#x20;

# Как регистры npm и корпоративные proxy registry влияют на установку пакетов?

npm registry - сервер, предоставляющий метаданные пакетов и архивы для установки.

По умолчанию npm использует `https://registry.npmjs.org/`.

Через `.npmrc` можно настроить другой registry:

```
registry=https://registry.example.com/
@company:registry=https://registry.company.com/
```

Корпоративные proxy registry (например, Verdaccio, Nexus, Artifactory) могут:

- Кэшировать публичные пакеты
- Предоставлять доступ к приватным пакетам
- Ограничивать установку определённых версий
- Проверять пакеты на соответствие политикам безопасности
- Требовать аутентификацию

Это влияет на доступность версий, скорость установки и доверие к источнику.

Возможные проблемы - устаревший кэш, ошибки авторизации, TLS-сертификаты и несовпадение registry с URL в lockfile.

Важно: содержимое lockfile может привязывать загрузку к конкретному registry, поэтому смена конфигурации не всегда перенаправляет все запросы. Токены доступа нельзя хранить в репозитории.&#x20;

# Что такое lifecycle scripts и какие угрозы они могут создавать?

Lifecycle scripts - команды из `package.json`, автоматически вызываемые пакетным менеджером на определённых этапах жизненного цикла пакета.

Примеры:

- `preinstall` - действия перед установкой
- `install` - действия при установке
- `postinstall` - действия после установки
- `prepare` - подготовка пакета, например сборка перед публикацией
- `prepack`, `postpack` - действия при упаковке пакета

Основной риск - выполнение произвольного кода из стороннего пакета.

Вредоносный скрипт потенциально может читать файлы, извлекать секреты из переменных окружения, отправлять данные по сети и изменять рабочее окружение.

Меры защиты:

- Проверять новые зависимости и их установочные скрипты
- Ограничивать доступ к секретам при установке
- Использовать `--ignore-scripts`, когда выполнение скриптов не требуется
- Устанавливать зависимости в изолированном окружении

Поведение зависит от версии менеджера. В современных выпусках npm 11 установочные скрипты зависимостей по умолчанию блокируются до одобрения через `allowScripts` / `npm install-scripts approve`. Старые версии npm выполняют их по умолчанию.&#x20;

# Как проверить происхождение и лицензии транзитивных зависимостей?

Для проверки необходимо определить полное дерево зависимостей, источники пакетов и условия их лицензирования.

Основные инструменты:

- `npm ls --all` - просмотреть дерево зависимостей
- `npm explain package-name` - определить, почему пакет установлен
- `npm view package@version repository license` - проверить заявленный репозиторий и лицензию
- `npm sbom --sbom-format=spdx` - сформировать перечень компонентов в формате SPDX
- `npm audit signatures` - проверить доступные подписи registry и provenance-аттестации

Для анализа происхождения также проверяют `resolved` и `integrity` в lockfile, сведения о публикации и исходный репозиторий.

Важно различать:

- `integrity` подтверждает соответствие загруженного архива ожидаемому хешу, но не безопасность кода
- `provenance` помогает установить происхождение сборки, если пакет опубликован с соответствующей аттестацией
- Поле `license` содержит заявленную лицензию, но для юридической проверки необходимо изучить её полный текст, включая лицензии вложенных компонентов

Для коммерческих проектов особенно важно проверять совместимость лицензий, например MIT, Apache-2.0, GPL и AGPL, с моделью распространения продукта.&#x20;
