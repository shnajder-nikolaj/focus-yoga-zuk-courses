# Какие риски проверяют contract tests по сравнению с unit, integration и E2E tests?

**Contract tests** проверяют согласованность взаимодействия на границе: отправляемый запрос, ожидаемый ответ или сообщение и важные правила их интерпретации. Они позволяют обнаружить несовместимость без запуска всего продукта.

Unit tests проверяют локальную логику, integration tests — работу частей вместе, E2E — пользовательский путь через систему. Термины могут пересекаться, поэтому важен конкретный риск. Контракт не заменяет проверку транзакций, авторизации и результата бизнес-процесса.

# Как устроен consumer-driven contract testing и верификация provider?

Consumer выполняет свой код против контролируемого provider substitute и сохраняет используемые взаимодействия как контракт. Затем provider verification воспроизводит эти запросы против реального provider с подготовленным состоянием и проверяет согласованные ожидания.

Контракты связывают с версиями участников, а результаты проверки используют при решении о совместимом деплое. Проверять только mock на стороне consumer недостаточно: он может обещать поведение, которого нет на сервере. [Как работает Pact](https://docs.pact.io/getting_started/how_pact_works).

# Чем проверка OpenAPI-схемы отличается от проверки потребительского контракта?

OpenAPI-schema test проверяет соответствие ответов общему описанию типов, статусов и ограничений. Потребительский контракт отражает конкретные взаимодействия, от которых зависит определённый клиент, включая используемые поля и подходящие значения.

Сервер может удовлетворять слишком широкой схеме, но ломать клиент, например изменив согласованный код ошибки. И наоборот, набор consumer contracts может не покрывать весь публичный API. Два подхода дополняют друг друга; важно не путать соответствие схеме с полной семантической совместимостью.

# Что такое provider states и как готовить данные для проверки контракта?

**Provider state** описывает предусловие отдельного взаимодействия: например, «заказ существует и доступен этому пользователю». Подготовщик состояния создаёт нужные данные, после чего проверяется запрос и ответ без зависимости от предыдущих тестов.

Используют контролируемые идентификаторы, изоляцию и очистку; состояние не должно зависеть от общей mutable staging-БД. Оно объясняет, почему provider обязан вернуть конкретный результат, а не жёстко привязывает контракт к внутренним таблицам. Настоящую бизнес-логику provider не подменяют ожидаемым ответом.

# Какие зависимости полезно запускать через Testcontainers?

Testcontainers полезен для реальных БД, кэшей, брокеров и других доступных контейнерных зависимостей. Тест получает временный экземпляр с нужной версией и проверяет SQL, ограничения, сериализацию и протокол, которые in-memory substitute может не воспроизвести.

Приложение не обязательно запускать в контейнере: оно может работать в тестовом процессе и подключаться по выданному адресу. Контейнер должен отражать важные свойства production-сервиса, но не обязательно всю топологию. Для managed API локальный эмулятор имеет отдельные ограничения. [Testcontainers для Node.js](https://testcontainers.com/guides/getting-started-with-testcontainers-for-nodejs/).

# Почему готовность контейнера нельзя определять только по запущенному процессу или открытому порту?

Процесс может уже работать и слушать порт, пока сервис ещё выполняет recovery, миграции или регистрацию metadata. Поэтому тест способен нестабильно падать сразу после старта контейнера.

Выбирают readiness по реальному протоколу: health endpoint, успешное подключение и минимальный запрос либо другой подходящий сигнал. Ограничивают ожидание и сохраняют diagnostic logs при отказе. Фиксированный `sleep` тратит время и не гарантирует готовности медленного окружения. [Wait strategies](https://java.testcontainers.org/features/startup_and_waits/).

# Как изолировать данные и ресурсы при параллельных интеграционных тестах?

Для параллельных тестов используют отдельные БД, schemas, tenants, очереди или уникальные namespaces, в зависимости от реальной границы изоляции. Cleanup должен удалять только ресурсы своего теста. Данные и порядок выполнения соседей не должны влиять на результат.

Rollback после теста подходит лишь для работы внутри той же транзакции и соединения; HTTP handler, worker и фоновый consumer могут писать независимо. Контейнер можно разделять для скорости, если модель изоляции остаётся достоверной и не скрывает гонки.

# Как проверять миграции и поведение repository на реальной базе данных?

Проверяют создание схемы с нуля и переход с поддерживаемой предыдущей версии. Добавляют реальные данные, проверяют преобразования, ограничения, индексы и поведение приложения во время переходного совместимого периода.

Repository тестируют на выбранном движке с настоящими типами, уникальностью, timezone, isolation и конкурентными правками. SQLite или fake не являются универсальной заменой PostgreSQL. Успешная миграция пустой таблицы не доказывает корректность на старых данных или приемлемое время блокировок.

# Когда использовать mock, stub или fake, а когда нужен реальный сервис?

**Stub** возвращает подготовленные результаты, **mock** обычно проверяет взаимодействия, **fake** реализует упрощённое рабочее поведение, например in-memory store. Конкретные библиотеки используют термины по-разному, поэтому назначение фиксируют в тесте.

Такие substitutes полезны для локальной логики, редких ошибок и дорогих внешних вызовов. Реальный сервис нужен там, где риск связан с его семантикой: SQL-транзакциями, блокировками, сериализацией или протоколом. Не стоит проверять последовательность внутренних вызовов, если важен только наблюдаемый результат.

# Как моделировать задержки, обрывы соединений и неожиданные ответы внешнего API в тестах?

Управляемый HTTP stub или proxy может задержать ответ, вернуть `429`, некорректный JSON, оборвать поток или закрыть соединение после получения запроса. Сценарии должны воспроизводимо проверять timeout, retries и обработку частичного ответа.

Особенно важен сбой после внешнего эффекта, но до подтверждения: он выявляет ошибочные повторы. Отдельно проверяют отмену и освобождение соединений. Неограниченный случайный сбой делает тест нестабильным; случайность используют с фиксируемым seed и диагностикой.

# Как организовать Testcontainers в CI с воспроизводимыми образами и ограниченными ресурсами?

Runner должен иметь поддерживаемый container runtime и доступ к нужным image registries. Образы закрепляют версией или digest, задают лимиты времени и ресурсов, сохраняют логи и обеспечивают cleanup при падении теста.

Не полагаются на `localhost` и фиксированные порты: используют адреса и mapped ports, выданные библиотекой. Параллелизм выбирают по памяти и диску runner. Доступ к Docker socket даёт серьёзные полномочия, поэтому окружения для недоверенных изменений изолируют от production-секретов.

# Какие гарантии нельзя получить только с помощью contract tests и контейнерных тестов?

Они не доказывают требуемую производительность, отсутствие гонок, безопасность, пригодность к региональному отказу и полное соответствие managed-сервису. Одиночная контейнерная БД обычно не воспроизводит failover и распределённую репликацию.

Контракт проверяет выбранные взаимодействия, а не все значения и бизнес-процессы. Нужны проверки, соответствующие оставшимся рискам: конкурентные сценарии, нагрузка, ограниченные E2E и восстановление. Увеличение числа тестов без понимания этих границ создаёт ложную уверенность.
