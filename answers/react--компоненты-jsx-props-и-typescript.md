# Какие задачи решает React и в чём его декларативный подход?

React - JavaScript-библиотека для создания пользовательских интерфейсов на основе компонентов.

Основные задачи React:

- Компонентная архитектура - разделение интерфейса на независимые, переиспользуемые части
- Декларативное описание UI - интерфейс описывается как функция данных и состояния
- Управление обновлениями - React сравнивает результаты рендеринга и применяет необходимые изменения к целевому окружению, например DOM
- Управление состоянием - компоненты хранят данные, изменение которых влияет на интерфейс

Декларативный подход означает, что разработчик описывает, каким должен быть интерфейс при определённом состоянии, а не последовательность операций по его изменению.

Например:

```
function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(c => c + 1)}>
      {count}
    </button>
  );
}
```

При изменении `count` React повторно вызывает компонент и обновляет отображаемое значение.

В императивном подходе пришлось бы самостоятельно находить DOM-элемент и изменять его содержимое.

# Что такое JSX и как он преобразуется при сборке?

JSX (JavaScript XML) - синтаксическое расширение JavaScript, позволяющее описывать структуру интерфейса с помощью разметки, похожей на HTML.

JSX не является HTML и не выполняется браузером напрямую. При сборке Babel, SWC или другой трансформатор преобразует его в вызовы JavaScript-функций.

Например:

```
const element = <h1>Hello</h1>;
```

С современным JSX Transform преобразуется примерно в:

```
import { jsx } from "react/jsx-runtime";

const element = jsx("h1", {
  children: "Hello"
});
```

В классическом преобразовании использовался `React.createElement()`.

JSX поддерживает JavaScript-выражения внутри `{}`, передачу props и вложенные компоненты.

Важно: JSX создаёт описание React-элементов, а не DOM-узлы. Созданием и обновлением DOM занимается React DOM.

# Чем React-элемент отличается от React-компонента?

React-элемент - объект, описывающий, что React должен отобразить. Он содержит тип элемента, props и служебную информацию, включая `key`.

React-компонент - функция или класс, определяющие поведение и структуру части интерфейса.

Пример:

```
function Button() {
  return <button>Click</button>;
}

const element = <Button />;
```

Здесь:

- `Button` - React-компонент
- `<Button />` - JSX, создающий React-элемент
- `<button>Click</button>` - элемент, возвращаемый компонентом

React использует полученные элементы для формирования дерева интерфейса.

Ключевое различие: компонент определяет, как получить интерфейс, а элемент представляет конкретное описание интерфейса.

# Чем функциональный компонент отличается от классового?

Функциональный компонент - функция, принимающая props и возвращающая React-узлы.

```
function Counter() {
  const [count, setCount] = useState(0);

  return <button>{count}</button>;
}
```

Классовый компонент наследуется от `React.Component` и реализует метод `render()`.

```
class Counter extends React.Component {
  state = { count: 0 };

  render() {
    return <button>{this.state.count}</button>;
  }
}
```

Основные отличия:

- Состояние: функциональные компоненты используют `useState`, `useReducer` и другие хуки, классовые - `this.state` и `this.setState()`
- Жизненный цикл: функциональные компоненты используют хуки, например `useEffect`, классовые - методы `componentDidMount`, `componentDidUpdate`, `componentWillUnmount`
- Контекст выполнения: функциональным компонентам не нужен `this`, классовые работают с экземпляром класса
- Повторное использование логики: функциональные компоненты используют пользовательские хуки, классовые обычно применяют HOC и render props

В современной разработке предпочтительны функциональные компоненты. Классовые продолжают поддерживаться и используются, в частности, для реализации Error Boundaries.

# Как связаны props, state и повторный рендер?

Props - входные данные компонента, передаваемые родителем. State - данные, которыми управляет сам компонент и изменение которых может инициировать обновление.

Повторный рендер может происходить, когда:

- Обновляется состояние компонента через `setState` или setter из `useState`
- Повторно рендерится родитель и React обрабатывает дочерний компонент
- Изменяется значение контекста, который компонент использует

При рендере React вызывает компонент, получает новое описание интерфейса и сравнивает его с предыдущим результатом.

Повторный рендер не равен обновлению DOM. Если результат не требует изменений, React может оставить DOM без изменений.

Также React может пропустить рендер, например при обновлении состояния тем же значением по сравнению `Object.is` или при успешной мемоизации через `React.memo`.

# Почему нельзя напрямую изменять состояние React?

React рассматривает state как неизменяемый снимок данных для конкретного рендера.

Прямое изменение объекта или массива в состоянии не уведомляет React об обновлении и может нарушить корректность сравнения предыдущего и нового состояния.

Неправильно:

```
user.name = "Alex";
setUser(user);
```

Ссылка на объект осталась прежней, поэтому React может пропустить обновление по сравнению `Object.is`.

Правильно:

```
setUser(prev => ({
  ...prev,
  name: "Alex"
}));
```

Создаётся новый объект, поэтому React может определить изменение состояния.

Иммутабельность также важна для корректной работы мемоизации, предсказуемости рендеров и конкурентных возможностей React.

Для обновлений, зависящих от предыдущего состояния, рекомендуется функциональная форма setter.

# Что означает однонаправленный поток данных?

Однонаправленный поток данных означает, что данные в React передаются от родительских компонентов к дочерним через props.

Дочерний компонент не может непосредственно изменить props родителя. Для инициирования изменения он вызывает переданную родителем функцию.

```
function Parent() {
  const [count, setCount] = useState(0);

  return <Child count={count} onIncrement={() => setCount(c => c + 1)} />;
}

function Child({ count, onIncrement }) {
  return <button onClick={onIncrement}>{count}</button>;
}
```

Последовательность работы:

1. Родитель передаёт данные через props
2. Дочерний компонент вызывает callback
3. Родитель обновляет состояние
4. React передаёт дочернему компоненту актуальные props

Такой подход делает источники данных и причины изменений более предсказуемыми.

# Что такое lifting state up?

Lifting state up - перенос общего состояния из дочерних компонентов в их ближайшего общего родителя.

Используется, когда нескольким компонентам необходимо работать с одними и теми же данными и поддерживать их синхронизацию.

Например, два поля ввода должны отображать одно значение. Вместо независимого `useState` в каждом поле состояние хранится в родителе, а дочерние компоненты получают:

- Текущее значение через props
- Функцию изменения через callback

Таким образом, родитель становится единым источником истины (single source of truth) для общего состояния.

Недостаток - при большом количестве уровней вложенности передача props может стать неудобной.

# Что такое prop drilling и какие есть способы его избежать?

Prop drilling - передача props через несколько промежуточных компонентов, которым эти данные непосредственно не нужны.

Например:

```
App → Layout → Sidebar → Profile → Avatar
```

Если `Avatar` требуется объект `user`, его приходится передавать через все промежуточные компоненты.

Основные способы избежать prop drilling:

- Context API - предоставляет данные компонентам-потребителям без передачи через каждый уровень props
- Композиция компонентов - позволяет передавать готовые элементы через `children` или другие props
- Локализация состояния - хранит данные ближе к компонентам, которые действительно их используют
- Внешние хранилища - Zustand, Redux и другие решения для управления разделяемым состоянием

Prop drilling сам по себе не является ошибкой. При небольшой глубине вложенности явная передача props часто проще и понятнее.

Также Context не исключает повторные рендеры: изменение его значения приводит к обновлению компонентов, читающих этот контекст.

# Как работает `children` и композиция компонентов?

`children` - специальный prop, через который компонент получает содержимое, размещённое между его открывающим и закрывающим JSX-тегами.

```
function Card({ children }) {
  return <div className="card">{children}</div>;
}

<Card>
  <h2>Title</h2>
  <p>Content</p>
</Card>
```

В этом примере `Card` не знает заранее, какие элементы будут находиться внутри него.

`children` может содержать React-элементы, строки, числа, массивы и другие допустимые React-узлы.

Композиция - способ построения сложных компонентов из более простых путём их вложения или передачи через props.

Она позволяет создавать гибкие компоненты без наследования и уменьшает связанность между частями интерфейса.

При этом `children` не обязан быть единственным способом композиции: компоненты можно передавать и через именованные props, например `header` или `footer`.

# Для чего React использует `key` при отображении списка?

`key` - специальный идентификатор, с помощью которого React сопоставляет элементы одного списка между рендерами.

```
users.map(user => (
  <UserCard key={user.id} user={user} />
));
```

При изменении списка React использует `key`, чтобы определить, какие элементы сохранились, добавились или удалились.

Это помогает:

- Сохранять правильную идентичность компонентов
- Корректно сохранять их локальное состояние
- Обрабатывать перестановку элементов
- Избегать ненужного пересоздания компонентов и DOM-узлов

Требования к `key`: он должен быть уникальным среди соседних элементов списка и стабильным между рендерами.

`key` используется самим React и не доступен компоненту через обычный `props.key`. Если идентификатор нужен внутри компонента, его передают отдельным prop.

# Почему индекс массива часто является плохим ключом?

Индекс массива зависит от позиции элемента, а не от идентичности данных.

```
items.map((item, index) => (
  <Item key={index} value={item} />
));
```

При добавлении, удалении или сортировке элементов индексы изменяются. React может сопоставить существующий экземпляр компонента с другими данными.

В результате возможны:

- Перенос локального состояния на другой элемент
- Некорректное поведение полей ввода
- Повторное использование DOM-узлов для других данных

Например, если список содержит редактируемые строки, после удаления первой строки состояние её соседей может оказаться связано с неправильными элементами.

Индекс допустим, когда список статичен: элементы не добавляются, не удаляются и не меняют порядок.

Для динамических списков предпочтительнее стабильный идентификатор из данных, например `item.id`.

# Как React сохраняет или сбрасывает состояние компонента?

React связывает состояние с позицией компонента в дереве интерфейса, учитывая его тип и `key`.

Состояние сохраняется, когда при повторном рендере React сопоставляет новый компонент с предыдущим экземпляром.

Оно сбрасывается, когда:

- Компонент удаляется из дерева и затем монтируется заново
- В той же позиции появляется компонент другого типа
- Изменяется его `key`
- Изменяется структура родительского дерева так, что прежняя идентичность компонента теряется

Например:

```
<Profile key={user.id} user={user} />
```

При изменении `user.id` React размонтирует предыдущий `Profile` и создаст новый с начальным состоянием.

Важно: изменение обычных props само по себе не сбрасывает состояние, если идентичность компонента сохраняется.

Также не следует объявлять компоненты внутри других компонентов: новая функция при каждом рендере создаёт новый тип компонента и может вызывать непреднамеренный сброс состояния.

# Когда помогает условный рендеринг?

Условный рендеринг позволяет отображать разные части интерфейса в зависимости от состояния, props или других условий.

Используется для отображения загрузки, ошибок, авторизации, модальных окон и динамических разделов интерфейса.

Основные способы:

```
// Тернарный оператор
{isLoggedIn ? <Profile /> : <Login />}

// Логическое И
{isOpen && <Modal />}

// Возврат null
if (!visible) return null;
```

Нюансы:

- `null`, `false` и `undefined` не создают видимого содержимого
- При удалении компонента из дерева его локальное состояние обычно сбрасывается
- Выражение `{count && <List />}` при `count === 0` отобразит `0`, поэтому безопаснее использовать `{count > 0 && <List />}`

Если необходимо сохранить состояние скрытого компонента, обычное размонтирование может быть неподходящим решением.

# Для чего нужны React Fragments?

React Fragment позволяет объединить несколько элементов без создания дополнительного DOM-узла.

```
function User() {
  return (
    <>
      <h2>Alex</h2>
      <p>Developer</p>
    </>
  );
}
```

В отличие от оборачивающего `<div>`, Fragment не влияет на DOM-структуру, CSS-раскладку и семантику HTML.

Существуют две формы:

- `<>...</>` - сокращённая запись
- `<Fragment>...</Fragment>` - полная запись, позволяющая передать `key`

Например, при отображении списка из нескольких соседних элементов:

```
items.map(item => (
  <Fragment key={item.id}>
    <dt>{item.name}</dt>
    <dd>{item.value}</dd>
  </Fragment>
));
```

Fragment особенно полезен в таблицах, списках определений и компонентах, где лишняя DOM-обёртка нежелательна.

# Чем controlled component отличается от uncontrolled component?

Разница заключается в том, где хранится текущее значение элемента формы.

Controlled component (управляемый компонент) - значение контролируется состоянием React.

```
const [value, setValue] = useState("");

<input
  value={value}
  onChange={e => setValue(e.target.value)}
/>
```

React передаёт значение через `value`, а обработчик синхронизирует состояние с вводом пользователя.

Uncontrolled component (неуправляемый компонент) - текущее значение хранится в DOM.

```
const inputRef = useRef(null);

<input ref={inputRef} defaultValue="Hello" />
```

Значение можно прочитать через `inputRef.current.value`.

Основные отличия:

- Controlled: удобен для валидации при вводе, зависимых полей и динамического управления значениями
- Uncontrolled: требует меньше обновлений React и подходит для простых форм с чтением значений при отправке

Для управляемых текстовых полей используют `value`, для checkbox и radio - `checked`. В неуправляемых полях начальные значения задают через `defaultValue` и `defaultChecked`.

Важно: нельзя переключать одно и то же поле между управляемым и неуправляемым режимами на протяжении его существования.

# Как реализовать форму с управляемыми полями?

Для управляемой формы значения полей хранятся в React state, передаются через `value` или `checked` и обновляются обработчиками `onChange`.

```
function LoginForm() {
  const [form, setForm] = useState({
    email: "",
    password: ""
  });

  function handleChange(e) {
    const { name, value } = e.currentTarget;

    setForm(prev => ({
      ...prev,
      [name]: value
    }));
  }

  function handleSubmit(e) {
    e.preventDefault();
    console.log(form);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        name="email"
        type="email"
        value={form.email}
        onChange={handleChange}
      />

      <input
        name="password"
        type="password"
        value={form.password}
        onChange={handleChange}
      />

      <button type="submit">Submit</button>
    </form>
  );
}
```

Механизм работы:

1. React хранит значения формы в `form`
2. При вводе `onChange` получает новое значение
3. `setForm` создаёт обновлённый объект состояния
4. React повторно рендерит форму с актуальными значениями
5. При отправке `onSubmit` получает данные из состояния

`e.preventDefault()` предотвращает стандартную отправку формы с перезагрузкой страницы.

Для checkbox используют `checked` и `e.currentTarget.checked`.

React 19 дополнительно поддерживает обработку форм через `action`, `useActionState` и `useFormStatus`, но это отдельный механизм и не заменяет controlled inputs во всех сценариях.

# Как работают события в React и чем они отличаются от нативных DOM-событий?

React использует собственную систему обработки событий, предоставляющую обработчикам объект SyntheticEvent - обёртку над нативным событием с унифицированным интерфейсом.

```
<button onClick={handleClick}>Click</button>
```

Основные особенности:

- Имена обработчиков записываются в `camelCase`: `onClick`, `onChange`, `onSubmit`
- В JSX передаётся функция, а не строка с JavaScript-кодом
- Обработчик получает `SyntheticEvent` с методами `preventDefault()` и `stopPropagation()`
- Нативное событие доступно через `event.nativeEvent`
- React использует делегирование большинства событий на корневом DOM-контейнере приложения, начиная с React 17

Отличия от нативных событий:

1\. Поведение отдельных событий нормализовано.

Например, `onChange` у текстового поля React вызывается при изменении значения пользователем, обычно на каждом вводе, тогда как нативный `change` срабатывает иначе.

2\. Всплытие учитывает дерево React.

Это особенно заметно при использовании порталов, где DOM-структура отличается от дерева React.

3\. Система распространения событий не полностью совпадает с DOM.

Например, `onFocus` и `onBlur` в React поддерживают всплытие, хотя соответствующие нативные события `focus` и `blur` не всплывают.

Начиная с React 17, объекты `SyntheticEvent` больше не используют прежний механизм pooling, поэтому `event.persist()` не требуется.

# Для чего используются refs?

Refs позволяют сохранять изменяемые значения между рендерами без инициирования повторного рендера при их изменении.

Чаще всего refs используются для:

- Получения доступа к DOM-элементам
- Программного управления фокусом, прокруткой и выделением текста
- Хранения идентификаторов таймеров
- Сохранения значений, которые не должны влиять на отображение
- Предоставления ограниченного императивного API через `useImperativeHandle`

Пример:

```
function Search() {
  const inputRef = useRef(null);

  return (
    <>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current?.focus()}>
        Focus
      </button>
    </>
  );
}
```

React заполняет `inputRef.current` ссылкой на DOM-элемент после его создания.

Главное отличие от state: изменение `ref.current` не вызывает рендер.

Refs не следует использовать вместо состояния для данных, изменение которых должно обновлять интерфейс. Также не рекомендуется читать или изменять `ref.current` во время рендера, кроме допустимой предсказуемой инициализации.

# Чем `createRef` отличается от `useRef`?

Оба API создают объект с изменяемым свойством `current`, но отличаются поведением при повторном рендере.

`createRef()` при каждом вызове возвращает новый объект. Обычно используется в классовых компонентах:

```
class Input extends React.Component {
  inputRef = React.createRef();

  render() {
    return <input ref={this.inputRef} />;
  }
}
```

Поле экземпляра класса сохраняет созданный ref.

`useRef()` возвращает один и тот же объект между рендерами функционального компонента:

```
function Input() {
  const inputRef = useRef(null);

  return <input ref={inputRef} />;
}
```

Если вызывать `createRef()` непосредственно внутри функционального компонента, при каждом рендере будет создаваться новый ref, что обычно нежелательно.

Практическое правило: в функциональных компонентах используют `useRef`, в классовых - `createRef`.

# Зачем нужны порталы React?

React Portal позволяет отображать дочерние элементы в другом месте DOM, сохраняя их логическую принадлежность исходному дереву React.

Создаётся через `createPortal()` из `react-dom`.

```
import { createPortal } from "react-dom";

function Modal({ children }) {
  return createPortal(
    <div className="modal">{children}</div>,
    document.body
  );
}
```

Порталы используются для модальных окон, всплывающих меню, подсказок и других элементов, которые необходимо разместить вне обычной DOM-иерархии.

Особенности:

- DOM-узел создаётся в указанном контейнере
- Компонент сохраняет доступ к Context исходного дерева React
- События всплывают по дереву React, а не по физической DOM-иерархии
- Состояние компонента продолжает управляться React

Порталы помогают избежать некоторых проблем с `overflow`, наложением и вложенностью элементов, но не гарантируют автоматического решения всех проблем с CSS stacking context.

# Что делает `StrictMode` в режиме разработки?

`StrictMode` - инструмент React для обнаружения потенциальных ошибок и небезопасных практик разработки.

```
<StrictMode>
  <App />
</StrictMode>
```

В режиме разработки React выполняет дополнительные проверки:

- Повторно вызывает функции рендеринга компонентов, чтобы обнаружить побочные эффекты
- Выполняет дополнительный цикл настройки и очистки Effects
- Дополнительно запускает callback refs для проверки корректности очистки
- Предупреждает об использовании устаревших API

Например, дополнительный запуск `useEffect` помогает обнаружить забытое отключение подписки или закрытие соединения.

Важно:

- Дополнительные проверки не выполняются в production
- Повторный вызов рендера не означает обязательное повторное изменение DOM
- Если `StrictMode` включён не на уровне корня, дополнительный цикл Effects при первоначальном монтировании имеет ограничения

Главная цель - выявить код, который зависит от побочных эффектов во время рендера или неправильно освобождает ресурсы.&#x20;

# Как реализовать Error Boundary и какие ошибки он не перехватывает?

Error Boundary - компонент, который перехватывает ошибки в дочернем дереве React и отображает запасной интерфейс вместо аварийно завершившейся части приложения.

Классическая реализация:

```
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    console.error(error, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return <p>Something went wrong</p>;
    }

    return this.props.children;
  }
}
```

Использование:

```
<ErrorBoundary>
  <Profile />
</ErrorBoundary>
```

Здесь:

- `getDerivedStateFromError()` обновляет состояние для отображения fallback UI
- `componentDidCatch()` позволяет логировать ошибку и информацию о дереве компонентов

Error Boundary перехватывает ошибки рендеринга и методов жизненного цикла дочерних компонентов.

Не перехватывает:

- Ошибки в обработчиках событий
- Ошибки асинхронных callback, например `setTimeout`
- Ошибки серверного рендеринга
- Ошибки самого Error Boundary

Исключение для асинхронной работы - ошибки, возникающие непосредственно внутри функции, переданной `startTransition`, могут перехватываться Error Boundary.

В React 19 полноценного встроенного функционального аналога Error Boundary нет. Можно использовать классовый компонент или библиотеку `react-error-boundary`.&#x20;

# Чем `ReactDOM` отличается от пакета `react`?

`react` содержит основные API библиотеки, не привязанные к конкретной платформе.

Например:

- `useState`, `useEffect`, `useContext`, `useRef`
- `createContext`
- `memo`
- `Suspense`
- `Component`

`react-dom` - реализация рендерера React для браузерного DOM.

Он отвечает за создание и обновление DOM, обработку взаимодействия с браузером и гидратацию серверной разметки.

В современном React API распределены по нескольким точкам входа:

```
import { useState } from "react";

import { createRoot, hydrateRoot } from "react-dom/client";

import { createPortal, flushSync } from "react-dom";
```

Пример инициализации приложения:

```
const root = createRoot(document.getElementById("root"));

root.render(<App />);
```

При серверном рендеринге используются API `react-dom/server`, а `hydrateRoot()` позволяет подключить React к уже существующей HTML-разметке.

Ключевое различие: `react` описывает модель компонентов и состояния, а `react-dom` связывает её с браузерным DOM.

# Как типизировать React props с discriminated union?

Discriminated union - объединение типов, в котором специальное поле-дискриминатор определяет допустимые свойства объекта.

Подход полезен для компонентов с несколькими режимами работы.

```
type ActionProps =
  | {
      kind: "link";
      href: string;
      onClick?: never;
    }
  | {
      kind: "button";
      onClick: () => void;
      href?: never;
    };

function Action(props: ActionProps) {
  if (props.kind === "link") {
    return <a href={props.href}>Open</a>;
  }

  return <button onClick={props.onClick}>Run</button>;
}
```

TypeScript использует значение `kind` для сужения типа (type narrowing).

Например:

```
<Action kind="link" href="/profile" />

<Action kind="button" onClick={() => {}} />
```

Передача `href` компоненту с `kind="button"` приведёт к ошибке типов.

Преимущества:

- Запрещает недопустимые комбинации props
- Обеспечивает корректную типизацию каждого режима
- Упрощает проверку исчерпывающей обработки вариантов

Свойства с типом `never` помогают явно запретить передачу несовместимых props.

# Как правильно типизировать `children`?

Тип `children` зависит от того, какое содержимое компонент должен принимать.

`React.ReactNode` - наиболее универсальный тип для отображаемого содержимого React.

```
type CardProps = {
  children: React.ReactNode;
};
```

Он допускает React-элементы, строки, числа, массивы, пустые значения и другие поддерживаемые React-узлы.

`React.ReactElement` применяется, когда ожидается именно React-элемент, а не произвольный текст или число.

```
type WrapperProps = {
  children: React.ReactElement;
};
```

`React.PropsWithChildren<T>` добавляет к типу props необязательное поле `children`.

```
type CardProps = React.PropsWithChildren<{
  title: string;
}>;
```

Выбор типа:

- `ReactNode` - для большинства компонентов-контейнеров
- `ReactElement` - когда требуется React-элемент
- `PropsWithChildren<T>` - для удобного добавления необязательного `children`

Если `children` обязателен, его лучше объявить явно.

Не стоит использовать `JSX.Element` вместо `ReactNode` для произвольного содержимого: `JSX.Element` не охватывает строки, числа и остальные допустимые React-узлы.

# Как типизировать `useRef` и DOM-события?

Для `useRef` указывают тип значения, которое будет храниться в `current`.

Например, ref на HTMLInputElement:

```
const inputRef = useRef<HTMLInputElement>(null);
```

Использование:

```
<input ref={inputRef} />

<button onClick={() => inputRef.current?.focus()}>
  Focus
</button>
```

Так как DOM-элемент до монтирования может отсутствовать, необходимо учитывать `null`.

Для хранения изменяемых значений:

```
const timerRef = useRef<number | null>(null);
```

Для DOM-событий React используются типы из пространства имён `React`:

```
function handleChange(
  event: React.ChangeEvent<HTMLInputElement>
) {
  console.log(event.currentTarget.value);
}

function handleClick(
  event: React.MouseEvent<HTMLButtonElement>
) {
  console.log(event.currentTarget);
}

function handleSubmit(
  event: React.FormEvent<HTMLFormElement>
) {
  event.preventDefault();
}
```

Можно типизировать и сам обработчик:

```
const handleChange: React.ChangeEventHandler<HTMLInputElement> =
  event => {
    console.log(event.currentTarget.value);
  };
```

Важно:

- `React.ChangeEvent` - тип события, `React.ChangeEventHandler` - тип функции-обработчика
- `currentTarget` типизирован как элемент, на котором зарегистрирован обработчик
- `target` может указывать на вложенный элемент, где событие возникло
- Для обработчиков, объявленных непосредственно в JSX, TypeScript обычно выводит тип автоматически

# Как описать полиморфный React-компонент с пропсом `as`?

Полиморфный компонент может отображаться как разные HTML-элементы или React-компоненты в зависимости от пропса `as`.

Например:

```
<Text as="span">Hello</Text>

<Text as="a" href="/profile">Profile</Text>
```

Для типизации используют:

- `React.ElementType` - допустимый тип элемента или компонента
- `React.ComponentPropsWithoutRef<C>` - props выбранного элемента
- `Omit` - исключение конфликтующих свойств
- Generic-параметр `C` - сохранение зависимости между `as` и допустимыми props

Пример:

```
type TextProps<C extends React.ElementType> = {
  as?: C;
  children?: React.ReactNode;
} & Omit<
  React.ComponentPropsWithoutRef<C>,
  "as" | "children"
>;

function Text<C extends React.ElementType = "span">({
  as,
  children,
  ...props
}: TextProps<C>) {
  const Component = as ?? "span";

  return <Component {...props}>{children}</Component>;
}
```

TypeScript определяет допустимые props на основе `as`.

```
<Text as="a" href="/home">Home</Text>

// Ошибка: href не является prop элемента button
<Text as="button" href="/home">Home</Text>
```

Главный принцип: тип props должен зависеть от выбранного элемента, чтобы компонент сохранял проверку типов и автодополнение.

Если компонент также должен передавать `ref`, используют `React.ComponentPropsWithRef<C>` и учитывают тип ref выбранного элемента.

# Как типизировать `forwardRef` и generic-компоненты?

`forwardRef` позволяет передавать ref через компонент к вложенному элементу. В React 18 и более ранних версиях это основной способ предоставления ref из функционального компонента.

Типизация:

```
type InputProps = React.ComponentPropsWithoutRef<"input">;

const Input = React.forwardRef<
  HTMLInputElement,
  InputProps
>((props, ref) => {
  return <input {...props} ref={ref} />;
});
```

Параметры generic у `forwardRef`:

1. `HTMLInputElement` - тип элемента, на который ссылается ref
2. `InputProps` - тип props компонента

Начиная с React 19, функциональные компоненты могут получать `ref` как обычный prop, поэтому `forwardRef` больше не требуется для новых компонентов.

```
type InputProps = React.ComponentPropsWithRef<"input">;

function Input({ ref, ...props }: InputProps) {
  return <input {...props} ref={ref} />;
}
```

`forwardRef` остаётся доступным для совместимости, но в документации React отмечен как API, запланированный к устареванию.&#x20;

Generic-компоненты позволяют сохранять тип данных при передаче массивов, callback и других параметризованных props.

Пример:

```
type ListProps<T> = {
  items: T[];
  getKey: (item: T) => React.Key;
  renderItem: (item: T) => React.ReactNode;
};

function List<T>({
  items,
  getKey,
  renderItem
}: ListProps<T>) {
  return (
    <ul>
      {items.map(item => (
        <li key={getKey(item)}>
          {renderItem(item)}
        </li>
      ))}
    </ul>
  );
}
```

Использование:

```
<List
  items={[{ id: 1, name: "Alex" }]}
  getKey={user => user.id}
  renderItem={user => user.name}
/>
```

TypeScript автоматически выводит тип `T` из `items`, поэтому `user` получает корректный тип без явного указания generic.

Особенность: при оборачивании generic-компонента в `forwardRef` TypeScript обычно теряет возможность автоматически выводить исходный generic-параметр компонента. Для сохранения типизации применяют явную generic-сигнатуру с проверенным приведением типа или вспомогательную типизированную обёртку.

В React 19 эту проблему часто можно избежать, передавая `ref` непосредственно как prop generic-компонента.
