# Как встроить security requirements и проверки в жизненный цикл разработки сервиса?

Для сервиса фиксируют защищаемые данные, границы доверия, ожидаемые роли и проверяемые security requirements. На проектировании проводят threat modeling, при разработке используют безопасные API и review, в CI проверяют код и зависимости, перед релизом — конфигурацию и поведение работающей системы.

У требований должны быть владельцы и критерии проверки. После выкладки продолжаются обновления, мониторинг и разбор уязвимостей. Один scanner не покрывает этот цикл: DevSecOps связывает предотвращение, обнаружение, исправление и обратную связь. [NIST SSDF](https://csrc.nist.gov/projects/ssdf).

# Чем SAST, DAST, SCA и IaC scanning различаются по входным данным и ограничениям?

**SAST** анализирует исходный или промежуточный код без запуска приложения и ищет опасные конструкции и data flows. **DAST** обращается к работающему приложению и проверяет наблюдаемое поведение. **SCA** исследует состав зависимостей и сопоставляет компоненты с известными проблемами. **IaC scanning** проверяет декларации инфраструктуры и policies.

У каждого метода есть пропуски: SAST ограничен моделью языка, DAST — доступными маршрутами и состояниями, SCA — качеством inventory и сведений об уязвимостях. Безопасность бизнес-логики и реальную конфигурацию production проверяют дополнительно.

# Как настроить SAST для поиска опасных data flows без чрезмерного числа ложных срабатываний?

В taint analysis выделяют sources недоверенных данных, sinks опасных операций и корректные sanitizers для конкретного контекста. Например, значение HTTP-параметра, попадающее в конкатенацию SQL, требует внимания, а корректный bind parameter меняет смысл потока.

Настраивают framework models, исключения generated code и проверенные собственные wrappers. Подавление finding сопровождают причиной и ограниченным scope. Качество оценивают на известных уязвимых и безопасных примерах: уменьшение числа предупреждений не должно достигаться выключением полезного правила. Finding проверяют по реальному execution path и доступным атакующему входам.

# Как организовать DAST аутентифицированного API в изолированном тестовом окружении?

Для DAST создают изолированное окружение с синтетическими данными и контролируемыми внешними интеграциями. Scanner получает отдельные accounts разных ролей, корректно проходит login и обновление сессии. API schema и сценарии помогают найти endpoints, но не гарантируют покрытие всех состояний.

Заранее ограничивают target hosts, интенсивность и разрушительные операции, например удаление данных или массовую отправку сообщений. Проверяют доступность нужных маршрутов для scanner и сохраняют воспроизводимые findings. Отсутствие результатов при истёкшей сессии может означать тестирование одной страницы входа, а не безопасности API.

# Как учитывать транзитивные зависимости, reachability и контекст эксплуатации при SCA?

SCA должен видеть реально разрешённые версии, включая transitive dependencies, системные packages и состав выпускаемого image. Одного списка прямых dependencies недостаточно. Finding связывают с advisory, уязвимым диапазоном и экземплярами сервиса, где компонент используется.

Reachability и условия эксплуатации помогают расставить приоритеты, но «путь не найден» не доказывает невозможность вызова через reflection, plugins или иной маршрут. Проверяют доступный fix, совместимость обновления и компенсирующие меры. Исключение фиксируют с доказательством, владельцем и сроком пересмотра. [OWASP: Vulnerable Dependency Management](https://cheatsheetseries.owasp.org/cheatsheets/Vulnerable_Dependency_Management_Cheat_Sheet.html).

# Как границы доверия CI runners и pull requests влияют на безопасность pipeline?

Pipeline исполняет код, поэтому изменение test script, build configuration или dependency install hook может получить права runner. Недоверенный pull request не должен автоматически получать production secrets, privileged tokens и доступ к доверенной сети.

Разделяют проверку внешних изменений и release jobs, минимизируют permissions и используют изолированные runners. Cache и artifacts тоже пересекают границы доверия: нельзя без проверки исполнять или выпускать результат недоверенной сборки. Credentials выдаются нужному job на ограниченное время, а изменение самого workflow проходит review. [OWASP: CI/CD Security](https://cheatsheetseries.owasp.org/cheatsheets/CI_CD_Security_Cheat_Sheet.html).

# Как IaC policies, cloud posture checks и drift detection дополняют друг друга?

IaC policy проверяет планируемую конфигурацию: например, запрещает публичное хранилище или избыточную IAM role до применения. Cloud posture checks исследуют реально существующие resources и их взаимодействие, включая изменения вне репозитория. **Drift detection** показывает расхождение фактического и декларативного состояния.

Эти проверки дополняют друг друга: корректный template не исключает ошибку ручного изменения или небезопасное сочетание ресурсов. Находку связывают с владельцем и источником настройки, после чего исправляют и фактическое состояние, и декларацию. Автоматическое исправление требует проверки влияния на работающий сервис. [OWASP: IaC Security](https://cheatsheetseries.owasp.org/cheatsheets/Infrastructure_as_Code_Security_Cheat_Sheet.html).

# Как проверять безопасность container image и runtime configuration перед релизом?

В image проверяют происхождение base image, состав packages, известные уязвимости и отсутствие credentials в files и layers. Обновление тега не меняет уже собранный image: нужен новый воспроизводимый build и проверка конкретного digest.

Отдельно проверяют deployment: непривилегированный пользователь, необходимые capabilities, filesystem permissions, mounts, ограничения ресурсов и network access. Доступ к container runtime socket способен обойти многие ограничения. Подпись image подтверждает происхождение при проверенной trust policy, но не доказывает отсутствие уязвимостей в содержимом. [OWASP: Docker Security](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html).

# Как построить security gates и ограниченные исключения на основе риска уязвимости?

Gate учитывает severity, доступность уязвимого пути, внешнюю экспозицию, ценность данных и наличие эксплуатации. Новый подтверждённый критичный риск может блокировать релиз; для исторического backlog нужен явный план, иначе постоянный шум делает проверки формальностью.

Exception задаёт конкретный finding, обоснование, компенсирующую меру, ответственного и срок истечения. Бессрочное исключение на весь repository скрывает будущие проблемы. Решение принимают уполномоченные владельцы риска, а не scanner. Режимы при отказе проверяющей системы и порядок аварийного релиза согласуют заранее.

# Как измерять результативность DevSecOps и проверять устранение найденных уязвимостей?

Наблюдают время до triage и исправления, возраст открытых рисков, долю повторных находок и покрытие важных путей. Сырые counts уязвимостей зависят от инструментов и объёма кода, поэтому не являются самостоятельной оценкой качества команды.

Исправление подтверждают воспроизведением исходного сценария, проверкой соседних путей и повторным анализом нужной версии artifact. Затем убеждаются, что именно этот artifact развёрнут. Разбор причин приводит к улучшению API, template, rule или обучения, чтобы похожий класс ошибок обнаруживался раньше. [NIST SSDF](https://csrc.nist.gov/projects/ssdf).
