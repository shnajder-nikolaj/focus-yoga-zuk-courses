# Чем DOM-дерево отличается от HTML-текста?

HTML - текстовая разметка, описывающая структуру документа. DOM (Document Object Model) - объектная модель документа, представленная деревом узлов, с которыми JavaScript может взаимодействовать через DOM API.

Основные отличия:

- HTML - исходный текст, DOM - объекты в памяти браузера
- Браузер строит DOM при парсинге HTML, исправляя некоторые ошибки разметки
- DOM может изменяться динамически без изменения исходного HTML-файла
- DOM содержит элементы, текстовые узлы, комментарии и другие типы узлов

Например, `document.createElement()` позволяет создать DOM-элемент, которого не было в исходном HTML.

# Как выбрать элементы с помощью DOM API?

Основные методы поиска:

- `document.getElementById('id')` - элемент по уникальному идентификатору
- `document.querySelector('.class')` - первый элемент по CSS-селектору
- `document.querySelectorAll('.class')` - все подходящие элементы
- `document.getElementsByClassName('class')` - элементы по классу
- `document.getElementsByTagName('div')` - элементы по тегу
- `element.closest('.class')` - ближайший подходящий элемент среди самого элемента и его предков

Методы `querySelector` и `querySelectorAll` поддерживают сложные CSS-селекторы, например `.card > button.active`.

Поиск также можно выполнять относительно конкретного элемента: `container.querySelector('button')`.

# Чем `querySelector` отличается от `getElementById` и `getElementsByClassName`?

`querySelector(selector)` принимает любой корректный CSS-селектор и возвращает первый подходящий элемент либо `null`.

`getElementById(id)` ищет элемент по точному значению `id` и возвращает элемент либо `null`. Вызывается у `document`.

`getElementsByClassName(className)` ищет элементы по классу и возвращает живую коллекцию `HTMLCollection`, автоматически отражающую изменения DOM.

Ключевые различия:

- `querySelector` - универсальный поиск по CSS-селекторам
- `getElementById` - специализированный поиск по идентификатору
- `getElementsByClassName` - поиск нескольких элементов с живой коллекцией

Специализированные методы могут быть быстрее, но в большинстве приложений выбирать API следует прежде всего по удобству и необходимому поведению коллекции.

# Что такое live и static DOM collections?

Live collection - коллекция, которая автоматически отражает изменения DOM.

Например, `getElementsByClassName()` возвращает живую `HTMLCollection`. Если добавить подходящий элемент, он появится в коллекции без повторного поиска.

Static collection - снимок набора узлов на момент выполнения запроса. `querySelectorAll()` возвращает статический `NodeList`.

При этом статическая коллекция сохраняет ссылки на сами DOM-узлы, поэтому изменения их свойств остаются видимыми.

Примеры:

- `getElementsByClassName()` - live `HTMLCollection`
- `getElementsByTagName()` - live `HTMLCollection`
- `querySelectorAll()` - static `NodeList`
- `element.childNodes` - live `NodeList`

Подводный камень: при удалении элементов во время обхода живой коллекции её индексы изменяются, из-за чего можно случайно пропустить элементы.

# Как работает распространение событий: capture, target, bubble?

При возникновении DOM-события браузер распространяет его по пути от предков к целевому элементу и обратно.

Выделяют три фазы:

1. Capture (перехват) - событие проходит от `window` через предков к целевому элементу. Срабатывают обработчики с `capture: true`
2. Target (цель) - событие достигает целевого элемента, где выполняются его обработчики
3. Bubble (всплытие) - событие поднимается от целевого элемента к предкам. Срабатывают обработчики без `capture: true`

По умолчанию `addEventListener()` регистрирует обработчик без перехвата.

Не все события всплывают. Например, `focus` и `blur` не всплывают, а `focusin` и `focusout` всплывают.

Свойство `event.eventPhase` позволяет определить текущую фазу.

# Что такое event delegation и какие у него ограничения?

Event delegation (делегирование событий) - паттерн, при котором один обработчик регистрируется на родительском элементе и обрабатывает события его потомков благодаря всплытию.

Вместо обработчика на каждой кнопке списка можно зарегистрировать один обработчик на контейнере и определять нужную кнопку через `event.target.closest('button')`.

Преимущества:

- Меньше обработчиков событий
- Работает с динамически добавленными элементами
- Упрощает управление обработчиками

Ограничения:

- Событие должно достигать делегирующего элемента. Невсплывающие события требуют других подходов, например `focusin` вместо `focus`
- `stopPropagation()` на промежуточном элементе может помешать обработчику родителя
- `event.target` может указывать на вложенный элемент, поэтому часто нужен `closest()`
- Shadow DOM может изменять видимую цель события или ограничивать его распространение

# Чем `event.target` отличается от `event.currentTarget`?

`event.target` - элемент, на который изначально было направлено событие, с учётом возможного retargeting в Shadow DOM.

`event.currentTarget` - элемент, на котором зарегистрирован выполняющийся обработчик.

Например, если обработчик `click` зарегистрирован на `div`, а пользователь нажал вложенную кнопку:

- `event.target` - кнопка
- `event.currentTarget` - `div`

При всплытии `target` обычно остаётся неизменным, а `currentTarget` меняется в зависимости от выполняемого обработчика.

Вне выполнения обработчика `currentTarget` имеет значение `null`.

# Как работают `preventDefault()`, `stopPropagation()` и `stopImmediatePropagation()`?

`event.preventDefault()` отменяет стандартное действие браузера, связанное с событием. Например, переход по ссылке или отправку формы.

Работает только для событий с `cancelable: true`. Не останавливает распространение события.

`event.stopPropagation()` останавливает дальнейшее распространение события по DOM, но не препятствует выполнению других обработчиков на текущем элементе.

`event.stopImmediatePropagation()` останавливает распространение события и предотвращает выполнение остальных обработчиков этого события на текущем элементе.

Важно: остановка распространения не отменяет стандартное действие браузера. Для этого нужен `preventDefault()`.

# Чем `addEventListener` с `once`, `passive` и `capture` отличается от обычного подписывания?

`addEventListener(type, handler, options)` позволяет управлять поведением обработчика через дополнительные параметры.

- `once: true` - автоматически удаляет обработчик после первого вызова
- `passive: true` - сообщает браузеру, что обработчик не отменит стандартное действие события. Вызов `preventDefault()` внутри такого обработчика не сработает
- `capture: true` - регистрирует обработчик для фазы перехвата вместо обычного всплытия

`passive` особенно полезен для событий прокрутки: браузер может не ожидать завершения обработчика перед началом прокрутки.

По умолчанию эти параметры равны `false`, но некоторые браузеры используют `passive: true` по умолчанию для определённых событий прокрутки на корневых элементах.

Также существует `signal`, позволяющий удалить обработчик через `AbortController`.&#x20;

# Как использовать `CustomEvent`?

`CustomEvent` позволяет создавать собственные DOM-события и передавать дополнительные данные через свойство `detail`.

```
const event = new CustomEvent('user:login', {
  detail: { userId: 123 },
  bubbles: true,
});

document.dispatchEvent(event);
```

Подписка выполняется обычным способом:

```
document.addEventListener('user:login', (event) => {
  console.log(event.detail.userId);
});
```

Основные параметры:

- `detail` - пользовательские данные
- `bubbles` - разрешает всплытие
- `cancelable` - позволяет отменить событие через `preventDefault()`
- `composed` - позволяет событию пересекать границу Shadow DOM

По умолчанию три последних параметра равны `false`.

`CustomEvent` полезен для взаимодействия между независимыми компонентами, особенно Web Components.

# Что такое Shadow DOM и event retargeting?

Shadow DOM - механизм инкапсуляции DOM-структуры компонента, позволяющий изолировать внутренние элементы и CSS-стили от обычного документа.

Создаётся через `element.attachShadow({ mode: 'open' })`.

Режимы:

- `open` - доступ к корню через `element.shadowRoot`
- `closed` - прямой доступ через `element.shadowRoot` недоступен

`closed` не является полноценной защитой данных от JavaScript.

Event retargeting - изменение видимого `event.target` при распространении события через границу Shadow DOM.

Например, если внутри Shadow DOM нажали кнопку, обработчик снаружи обычно увидит в `event.target` хост-компонент, а не внутреннюю кнопку.

Это скрывает детали внутренней реализации компонента.

Метод `event.composedPath()` позволяет получить путь распространения события, но закрытые Shadow DOM скрывают внутренние узлы от внешних обработчиков.

Не все события пересекают границу Shadow DOM. Это регулируется свойством `composed`.

# Чем `innerHTML`, `textContent` и `innerText` отличаются?

`innerHTML` читает или устанавливает HTML-разметку содержимого элемента.

При присваивании строки браузер парсит её как HTML и создаёт соответствующие DOM-узлы. Это потенциально опасно при работе с недоверенными данными.

`textContent` читает или устанавливает текстовое содержимое узла и его потомков.

HTML-теги при присваивании воспринимаются как обычный текст. Свойство также учитывает текст скрытых элементов.

`innerText` возвращает текст с учётом отображения элемента: CSS-стилей, видимости и переносов строк.

Основные различия:

- `innerHTML` - работа с HTML-разметкой
- `textContent` - работа с текстом без интерпретации HTML
- `innerText` - работа с текстом в представлении, близком к видимому пользователю

`innerText` может инициировать пересчёт стилей и layout, поэтому обычно дороже `textContent`.

Для безопасной вставки обычного текста предпочтителен `textContent`.

# Какие риски безопасности возникают при вставке HTML строкой?

Главный риск - XSS (Cross-Site Scripting), когда злоумышленник внедряет вредоносный HTML или JavaScript, который выполняется в контексте сайта.

Например:

```
element.innerHTML = userInput;
```

Если `userInput` содержит HTML с обработчиком `onerror`, злоумышленник может добиться выполнения JavaScript.

Последствия XSS:

- Кража доступных JavaScript токенов и пользовательских данных
- Выполнение действий от имени пользователя
- Подмена содержимого страницы
- Перенаправление на вредоносные сайты

Способы защиты:

- Использовать `textContent` для обычного текста
- Создавать DOM-элементы через безопасные API
- Очищать недоверенный HTML проверенными санитайзерами, например DOMPurify
- Применять CSP и Trusted Types как дополнительные уровни защиты

Важно: скрипты, вставленные через `innerHTML` в теге `<script>`, обычно не выполняются, но это не защищает от XSS через обработчики событий и другие опасные конструкции.&#x20;

# Как работает `MutationObserver`?

`MutationObserver` - Web API для отслеживания изменений DOM без постоянных проверок.

Позволяет наблюдать за:

- `childList` - добавлением и удалением дочерних узлов
- `attributes` - изменениями атрибутов
- `characterData` - изменениями текстовых узлов
- `subtree` - изменениями во всём поддереве

Пример:

```
const observer = new MutationObserver((mutations) => {
  console.log(mutations);
});

observer.observe(document.body, {
  childList: true,
  subtree: true,
});
```

Браузер собирает изменения в объекты `MutationRecord` и асинхронно передаёт их в callback через механизм microtasks.

`observer.disconnect()` прекращает наблюдение.

Подводный камень: если callback изменяет наблюдаемый DOM, он может вызвать новые уведомления и создать бесконечный цикл изменений.

# Когда использовать `IntersectionObserver`?

`IntersectionObserver` асинхронно отслеживает пересечение элемента с областью видимости или заданным контейнером.

Основные сценарии:

- Lazy loading изображений и других ресурсов
- Infinite scroll - загрузка данных при приближении к концу списка
- Запуск анимаций при появлении элементов
- Отслеживание приблизительной видимости контента

Основные параметры:

- `root` - контейнер, относительно которого проверяется пересечение
- `rootMargin` - расширение или сужение области пересечения
- `threshold` - порог доли пересечения, при переходе через который вызывается callback

В отличие от постоянной проверки `getBoundingClientRect()` при `scroll`, `IntersectionObserver` позволяет браузеру оптимизировать наблюдение.

Важно: обычный `IntersectionObserver` определяет геометрическое пересечение, а не гарантирует, что пользователь действительно видит элемент. Например, элемент может быть перекрыт другим.&#x20;

# Как использовать `ResizeObserver` и какие циклы изменений он может вызвать?

`ResizeObserver` позволяет отслеживать изменения размеров DOM-элементов независимо от изменения размеров окна.

```
const observer = new ResizeObserver((entries) => {
  for (const entry of entries) {
    console.log(entry.contentRect.width);
  }
});

observer.observe(element);
```

Используется для адаптивных компонентов, графиков и интерфейсов, размеры которых зависят от контейнера.

Проблема возникает, если callback меняет размеры наблюдаемого элемента:

1. Размер элемента изменяется
2. `ResizeObserver` вызывает callback
3. Callback снова меняет размер
4. Возникает новый цикл наблюдения

Браузер ограничивает обработку таких циклов и может выдать ошибку `ResizeObserver loop completed with undelivered notifications`.

Для предотвращения проблемы следует проверять, действительно ли требуется изменение размера, и при необходимости откладывать изменения через `requestAnimationFrame()`. Само откладывание не устраняет бесконечный цикл, если причина остаётся.&#x20;

# Как работает Clipboard API и почему ему нужен безопасный контекст?

Clipboard API предоставляет асинхронный доступ к системному буферу обмена через `navigator.clipboard`.

Основные методы:

- `writeText(text)` - записать текст
- `readText()` - прочитать текст
- `write()` - записать данные различных форматов
- `read()` - прочитать данные различных форматов

Пример:

```
await navigator.clipboard.writeText('Hello');
```

API требует secure context - обычно HTTPS или доверенное локальное окружение, например `localhost`.

Причина - защита конфиденциальности. Буфер обмена может содержать пароли, токены, персональные данные и другую чувствительную информацию.

Браузеры дополнительно ограничивают доступ разрешениями, фокусом документа и взаимодействием пользователя. Конкретные требования различаются: например, Firefox и Safari обычно требуют пользовательскую активацию для записи.&#x20;

# Что такое Fullscreen API и Pointer Lock API?

Fullscreen API позволяет перевести определённый элемент страницы в полноэкранный режим.

Основные методы:

- `element.requestFullscreen()` - перейти в полноэкранный режим
- `document.exitFullscreen()` - выйти
- `document.fullscreenElement` - получить текущий полноэкранный элемент

Pointer Lock API позволяет захватить указатель мыши, скрыть курсор и получать относительные перемещения через `movementX` и `movementY`.

Основные методы:

- `element.requestPointerLock()` - запросить захват
- `document.exitPointerLock()` - освободить указатель

Разница: Fullscreen управляет отображением элемента, а Pointer Lock - вводом с мыши.

Оба API часто используются в играх, 3D-приложениях и интерактивных интерфейсах.

Из соображений безопасности вход обычно требует действия пользователя. Выход из режимов контролируется браузером, в частности через `Escape`.

# Как использовать Web Worker и обмениваться сообщениями с ним?

Web Worker позволяет выполнять JavaScript в отдельном потоке, не блокируя основной поток браузера.

Создание:

```
const worker = new Worker('/worker.js');

worker.postMessage({ value: 10 });

worker.onmessage = (event) => {
  console.log(event.data);
};
```

Код внутри `worker.js`:

```
self.onmessage = (event) => {
  const result = event.data.value * 2;
  self.postMessage(result);
};
```

Обмен происходит через `postMessage()` и события `message`.

Данные обычно передаются с помощью structured clone algorithm, который поддерживает многие типы объектов, но не функции и DOM-узлы.

Для больших бинарных данных можно использовать transferable objects, например `ArrayBuffer`, передавая владение буфером без копирования.

Worker не имеет прямого доступа к DOM, но поддерживает `fetch`, таймеры и многие другие Web API.

Используется для CPU-intensive задач: вычислений, обработки больших данных, изображений и парсинга.

`worker.terminate()` завершает работу Worker.

# Чем Dedicated Worker отличается от Shared Worker?

Dedicated Worker принадлежит конкретному контексту, который его создал.

Создаётся через `new Worker()` и взаимодействует с владельцем через `postMessage()`.

Shared Worker может использоваться несколькими вкладками, окнами и другими контекстами с совместимыми origin и storage partition.

Создаётся через `new SharedWorker()` и взаимодействует с клиентами через `MessagePort`, используя событие `connect`.

Основные различия:

- Dedicated Worker - отдельный экземпляр для каждого создающего контекста
- Shared Worker - общий экземпляр для нескольких подключённых контекстов
- Dedicated Worker - простое взаимодействие с владельцем
- Shared Worker - взаимодействие через порты, с необходимостью координации нескольких клиентов

Shared Worker полезен для общего соединения с сервером, координации вкладок и совместного выполнения задач.

Поддержка и ограничения Shared Worker зависят от браузера.

# Какие задачи решают BroadcastChannel и `postMessage`?

`BroadcastChannel` обеспечивает обмен сообщениями между вкладками, окнами, iframe и Worker одного origin в пределах одной storage partition.

```
const channel = new BroadcastChannel('app');

channel.postMessage({ type: 'LOGOUT' });

channel.onmessage = (event) => {
  console.log(event.data);
};
```

Используется для синхронизации состояния, уведомлений о выходе из аккаунта и координации вкладок.

`postMessage()` - универсальный механизм передачи сообщений между определёнными контекстами выполнения.

Применяется для:

- Общения страницы с Web Worker
- Взаимодействия окна с iframe
- Обмена данными между окнами разных origin
- Передачи сообщений через `MessagePort`

Главное различие: `BroadcastChannel` рассылает сообщения всем другим слушателям канала в доступной области, а `postMessage()` отправляет сообщение определённому получателю.

# Как безопасно обрабатывать сообщения из другого origin?

При использовании `window.postMessage()` сообщение может поступить из другого origin, поэтому нельзя автоматически доверять содержимому `event.data`.

Основные правила:

- Проверять `event.origin` по точному списку разрешённых origin
- При необходимости проверять `event.source`, чтобы убедиться, от какого окна пришло сообщение
- Валидировать структуру и типы полей `event.data`
- Не передавать полученные данные напрямую в `innerHTML`, `eval()` или другие опасные API
- При отправке указывать точный `targetOrigin`, а не `'*'`, если origin получателя известен

Пример:

```
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://trusted.example') {
    return;
  }

  if (
    typeof event.data !== 'object' ||
    event.data === null ||
    event.data.type !== 'UPDATE' ||
    typeof event.data.value !== 'string'
  ) {
    return;
  }

  handleUpdate(event.data.value);
});
```

Важно: проверка `origin` подтверждает источник сообщения, но не гарантирует безопасность самих данных.&#x20;

# Когда использовать Geolocation API и Permissions API?

Geolocation API позволяет получить географическое положение устройства.

Основные методы:

- `navigator.geolocation.getCurrentPosition()` - однократное получение координат
- `navigator.geolocation.watchPosition()` - отслеживание изменений координат
- `navigator.geolocation.clearWatch()` - прекращение отслеживания

Используется в картах, навигации, поиске ближайших объектов и геозависимых сервисах.

Для доступа требуется безопасный контекст и разрешение пользователя. Точность зависит от GPS, Wi-Fi, сети и настроек устройства.

Permissions API позволяет проверять состояние разрешений для различных Web API.

```
const status = await navigator.permissions.query({
  name: 'geolocation',
});

console.log(status.state);
```

Возможные состояния:

- `granted` - разрешено
- `denied` - запрещено
- `prompt` - требуется запрос разрешения

Permissions API не заменяет запрос разрешения самим Geolocation API. Также набор поддерживаемых разрешений зависит от браузера.

# Какие ограничения браузер накладывает на Notifications API?

Notifications API позволяет показывать системные уведомления за пределами страницы браузера.

Основные ограничения:

- HTTPS - API доступен только в безопасных контекстах
- Разрешение пользователя - необходимо получить `Notification.permission === 'granted'`
- User activation - запрос разрешения обычно должен происходить после действия пользователя
- Cross-origin iframe - браузеры ограничивают или запрещают запрос разрешений из сторонних iframe
- Поддержка платформы - поведение различается между браузерами и операционными системами

Разрешение запрашивается через `Notification.requestPermission()`.

Для уведомлений, работающих в фоне, обычно используют Service Worker + Push API + `ServiceWorkerRegistration.showNotification()`.

На многих мобильных браузерах обычный конструктор `new Notification()` недоступен, даже если уведомления через Service Worker поддерживаются.&#x20;

# Чем `localStorage` отличается от `sessionStorage`?

Оба механизма относятся к Web Storage API и хранят данные в формате ключ-значение, где ключи и значения являются строками.

`localStorage`:

- Сохраняет данные между перезапусками браузера, пока они не будут удалены пользователем, приложением или браузером
- Доступен документам одного origin с учётом ограничений partitioned storage
- Подходит для небольших пользовательских настроек

`sessionStorage`:

- Привязан к origin и конкретной вкладке
- Сохраняется при перезагрузке страницы
- Обычно очищается при завершении сессии вкладки
- Подходит для временного состояния интерфейса

При открытии новой вкладки через `window.open()` её `sessionStorage` может первоначально копироваться из родительской вкладки, но затем хранилища независимы.

Оба API синхронные и не подходят для хранения больших объёмов данных.

# Почему Web Storage может быть проблемой для больших объёмов данных?

Главная проблема - синхронность операций.

Методы `localStorage.setItem()` и `getItem()` выполняются синхронно и могут блокировать основной поток браузера.

Основные ограничения:

- Небольшая квота, обычно до 5 MiB для каждого из `localStorage` и `sessionStorage` на origin
- Данные хранятся только как строки
- Для объектов необходимы `JSON.stringify()` и `JSON.parse()`
- Отсутствуют транзакции и индексы
- При превышении квоты возникает `QuotaExceededError`

Частая сериализация больших объектов дополнительно увеличивает нагрузку на CPU и память.

Для значительных объёмов структурированных данных предпочтительнее IndexedDB, предоставляющий асинхронные операции и транзакции.

# Как устроен IndexedDB и когда он нужен?

IndexedDB - встроенная в браузер асинхронная транзакционная база данных для хранения значительных объёмов структурированных данных.

Основные компоненты:

- Database - база данных с именем и версией схемы
- Object Store - хранилище записей, похожее на таблицу
- Key - ключ записи
- Index - индекс для поиска по дополнительным полям
- Transaction - группа операций с атомарным выполнением

В отличие от `localStorage`, IndexedDB поддерживает сложные объекты через structured clone algorithm без обязательной JSON-сериализации.

Операции выполняются асинхронно, поэтому не требуется синхронно обращаться к хранилищу из основного потока.

Для изменения структуры базы используется повышение версии и обработчик `onupgradeneeded`.

Применяется для:

- Offline-first приложений
- Хранения больших наборов данных
- Локального кеширования API-ответов
- Сохранения черновиков и очередей операций
- Приложений с необходимостью индексации и поиска

Подводные камни: квоты браузера, возможное удаление данных, конфликты версий между вкладками и необходимость правильно управлять транзакциями.

# Что такое Cache Storage API?

Cache Storage API - API для программного хранения пар HTTP-запрос/ответ (`Request` / `Response`).

Основной интерфейс - `caches`.

Пример:

```
const cache = await caches.open('app-v1');

await cache.add('/styles.css');

const response = await cache.match('/styles.css');
```

Основные методы:

- `caches.open(name)` - открыть или создать именованный кеш
- `cache.put(request, response)` - сохранить ответ
- `cache.match(request)` - найти сохранённый ответ
- `cache.delete(request)` - удалить запись
- `caches.delete(name)` - удалить именованный кеш

Используется совместно с Service Worker для offline-режима, кеширования статических ресурсов и реализации стратегий Cache First, Network First и Stale While Revalidate.

Cache Storage не обновляет записи автоматически. Приложение самостоятельно определяет, что кешировать, когда обновлять и удалять данные.

# Чем Cache Storage отличается от HTTP cache?

HTTP cache - встроенный кеш браузера, управляемый стандартными HTTP-заголовками, такими как `Cache-Control`, `ETag` и `Expires`.

Браузер самостоятельно определяет, можно ли использовать сохранённый ответ или необходимо обратиться к серверу.

Cache Storage - программно управляемое хранилище ответов, доступное через JavaScript.

Основные различия:

- HTTP cache - автоматическое кеширование согласно HTTP-семантике
- Cache Storage - явное сохранение и получение ответов приложением
- HTTP cache - поддерживает стандартные механизмы свежести и ревалидации
- Cache Storage - требует самостоятельной реализации политики актуальности данных

Cache Storage не применяет автоматически правила свежести из `Cache-Control` к сохранённым записям.

Оба механизма могут использоваться одновременно, но являются независимыми системами кеширования.

# Как работает partitioned storage и ограничения третьесторонних cookie?

Partitioned storage - механизм изоляции браузерных хранилищ для предотвращения отслеживания пользователя между разными сайтами.

Традиционно данные часто разделялись только по `origin`.

При partitioning ключ хранения дополнительно учитывает top-level site - сайт верхнего уровня, внутри которого загружен ресурс.

Например, если `widget.example` встроен на `site-a.example` и `site-b.example`, его данные могут храниться в разных разделах и быть недоступными между этими сайтами.

Это касается различных API, включая IndexedDB, Cache Storage и BroadcastChannel, в зависимости от реализации браузера.

Third-party cookies - cookie стороннего сайта, используемые при загрузке ресурсов в контексте другого сайта.

Современные браузеры могут блокировать или разделять такие cookie, чтобы ограничить cross-site tracking.

Существуют два важных механизма:

- CHIPS - позволяет создавать cookie с атрибутом `Partitioned`, изолированные по top-level site
- Storage Access API - позволяет встроенному стороннему контенту запрашивать доступ к непартиционированным cookie в разрешённых случаях

Ограничения отличаются между Chrome, Firefox и Safari. Поэтому нельзя полагаться на постоянный доступ к сторонним cookie или единому хранилищу между сайтами.&#x20;

# Что такое storage quota и как браузер удаляет данные при нехватке места?

Storage quota - ограничение на объём данных, который сайт может хранить в браузере.

Квоты распространяются на различные хранилища, включая IndexedDB, Cache Storage и другие механизмы хранения данных.

Браузер самостоятельно определяет доступный объём с учётом движка, свободного места и политики хранения.

Основные механизмы:

- Best-effort storage - стандартный режим, при котором браузер может удалить данные при нехватке места
- Persistent storage - режим, уменьшающий риск автоматического удаления данных

Для оценки доступного места используется:

```
const { usage, quota } = await navigator.storage.estimate();
```

Для запроса постоянного хранения:

```
const persisted = await navigator.storage.persist();
```

При превышении квоты операция записи обычно завершается ошибкой `QuotaExceededError`.

При нехватке дискового пространства браузер может удалять данные редко используемых origin. Во многих реализациях применяется стратегия, близкая к LRU.

При eviction обычно удаляются данные всего origin, а не отдельные записи.

Persistent storage защищает от обычного автоматического вытеснения, но пользователь всё равно может удалить данные вручную.&#x20;

# Как синхронизировать состояние между вкладками одного приложения?

Для обмена состоянием между вкладками одного приложения существуют несколько механизмов.

1\. BroadcastChannel

Предпочтителен для непосредственной передачи сообщений между вкладками в пределах одной storage partition.

```
const channel = new BroadcastChannel('app-state');

channel.postMessage({
  type: 'THEME_CHANGED',
  theme: 'dark',
});

channel.onmessage = (event) => {
  updateTheme(event.data.theme);
};
```

2\. `storage` event

Позволяет реагировать на изменения `localStorage` в других вкладках.

```
window.addEventListener('storage', (event) => {
  if (event.key === 'theme') {
    updateTheme(event.newValue);
  }
});
```

Событие `storage` не вызывается в той вкладке, которая сама изменила хранилище.

3\. Shared Worker

Позволяет централизовать состояние или управлять общими соединениями между вкладками.

Важно различать уведомление об изменении и согласованность данных.

`BroadcastChannel` передаёт сообщения, но не обеспечивает транзакционную синхронизацию состояния.

Если несколько вкладок одновременно изменяют одни данные, необходима стратегия разрешения конфликтов: версии, транзакции или авторитетное состояние на сервере.

# Как избежать конфликтов версии схемы IndexedDB после обновления приложения?

IndexedDB использует целочисленную версию схемы базы данных.

При вызове `indexedDB.open(name, version)` с более высокой версией запускается транзакция обновления через `onupgradeneeded`.

Проблема возникает, когда разные вкладки используют разные версии приложения.

Например:

1. Старая вкладка держит соединение с базой версии 1
2. Новая вкладка запрашивает версию 2
3. Обновление блокируется, пока старое соединение не закроется

Для корректной обработки:

- `onupgradeneeded` - выполнять миграции схемы
- `onversionchange` - закрывать старое соединение через `db.close()`
- `onblocked` - обнаруживать блокировку обновления и уведомлять пользователя
- Версионированные миграции - последовательно применять изменения от старой версии к новой

Дополнительно нужно учитывать совместимость старого кода с новой схемой и предусматривать обновление устаревших вкладок.

Если старое приложение явно запрашивает версию ниже текущей, открытие базы завершится `VersionError`.

Миграции должны сохранять существующие данные и корректно обрабатывать обновление сразу через несколько версий.&#x20;

# Что такое client-side routing?

Client-side routing - механизм навигации, при котором JavaScript управляет отображаемым содержимым страницы в зависимости от URL без полной перезагрузки документа.

Чаще всего используется в SPA (Single Page Application).

Принцип работы:

1. Пользователь переходит по внутренней ссылке
2. Роутер перехватывает навигацию
3. URL изменяется через History API или hash
4. Роутер определяет соответствующий маршрут
5. Приложение отображает нужный компонент или страницу

Преимущества:

- Навигация без полной перезагрузки документа
- Сохранение состояния приложения между переходами
- Возможность загружать данные и код по мере необходимости

Ограничения:

- Необходимость корректной обработки истории браузера
- Настройка сервера для прямого открытия вложенных маршрутов при History routing
- Необходимость обработки ошибок загрузки, состояний ожидания и неизвестных маршрутов

Client-side routing не исключает сетевых запросов - приложение по-прежнему может загружать данные и JavaScript при переходах.

# Чем History API отличается от hash routing?

Оба механизма позволяют реализовать клиентскую навигацию без полной перезагрузки страницы, но по-разному работают с URL.

History API использует обычные URL:

```
https://example.com/users/123
```

Основные методы:

- `history.pushState()` - добавить запись в историю
- `history.replaceState()` - заменить текущую запись
- `popstate` - событие при переходе по истории, например назад или вперёд

Преимущество - чистые URL.

Недостаток - сервер должен уметь обрабатывать прямые запросы на вложенные маршруты, обычно возвращая HTML приложения.

Hash routing использует часть URL после `#`:

```
https://example.com/#/users/123
```

Изменения отслеживаются через `hashchange`.

Преимущества:

- Не требует специальной серверной настройки маршрутов
- Фрагмент URL не отправляется серверу при HTTP-запросе

Недостатки:

- Менее удобный формат URL
- Конфликт с обычным использованием hash для якорной навигации

Важно: вызовы `pushState()` и `replaceState()` сами по себе не вызывают `popstate`. Роутер должен отдельно обновлять отображаемое состояние после программной навигации.

# Как работают Web Workers и почему они не заменяют асинхронность ввода-вывода?

Web Workers позволяют выполнять JavaScript в отдельных потоках, не блокируя основной поток интерфейса.

Каждый Worker имеет собственный event loop и может выполнять вычисления параллельно с основным потоком.

Однако нужно различать два типа задач:

CPU-bound задачи - ограничены производительностью процессора.

Например, обработка изображений, сложные вычисления или анализ больших массивов.

Web Worker позволяет выполнять такие задачи вне основного потока, сохраняя отзывчивость интерфейса.

I/O-bound задачи - ограничены ожиданием внешних операций.

Например, HTTP-запросы, чтение файлов и работа с базой данных.

Для них используются асинхронные API, такие как `fetch()` и IndexedDB.

Перенос `fetch()` в Worker не ускоряет сам сетевой запрос:

```
// Работает асинхронно и в основном потоке
const response = await fetch('/api/data');
```

Во время ожидания ответа основной поток не блокируется, поскольку `fetch()` использует асинхронную модель выполнения.

Worker полезен, если после получения данных требуется тяжёлая синхронная обработка, которую нежелательно выполнять в основном потоке.

Главное различие: Web Workers обеспечивают параллельное выполнение JavaScript, а асинхронные API позволяют не блокировать поток во время ожидания операций ввода-вывода.
