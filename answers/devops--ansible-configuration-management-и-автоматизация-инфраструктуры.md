# Как configuration management отличается от provisioning и создания неизменяемых образов?

**Provisioning** создаёт ресурсы: виртуальные машины, сети и диски. **Configuration management** приводит их содержимое и настройки к нужному состоянию: устанавливает пакеты, создаёт пользователей, обновляет конфигурацию. Сборка **immutable image** переносит эти изменения в заранее подготовленный образ, которым заменяют экземпляры.

Граница инструментов не абсолютна: Ansible может обращаться к облачным API, а система provisioning — запускать команды. Полезно назначить одного владельца каждому ресурсу или параметру и избежать ситуации, когда несколько инструментов регулярно перезаписывают настройки друг друга.

# Как control node, inventory, managed nodes и connection plugins взаимодействуют в Ansible?

**Control node** запускает Ansible, читает inventory и playbook, выбирает managed nodes и выполняет задачи через connection plugins. Для Linux часто используют SSH; для Windows и сетевых устройств доступны другие способы подключения. Постоянный Ansible-agent на обычном managed node не требуется.

Многие модули выполняют код на целевом узле, поэтому там нужны соответствующий runtime и права; для обычных POSIX-модулей часто необходим Python. Некоторые модули работают локально с внешним API. Поэтому формулировка «Ansible всегда исполняет всё по SSH» неверна: место выполнения зависит от подключения, модуля и delegation.

# Как inventory groups, group_vars, host_vars и dynamic inventory описывают окружения?

**Inventory** описывает узлы и группы, например `web` и `db`. Один узел может входить в несколько групп. `group_vars` задаёт общие переменные группы, `host_vars` — параметры конкретного узла; при пересечении учитывают правила precedence.

**Dynamic inventory** получает актуальные ресурсы из облака, CMDB или другого источника через inventory plugin. Группировку строят по устойчивым признакам: окружению, роли и региону. Разделение production и test проверяют до исполнения, например просмотром inventory и ограничением `--limit`. Кеш inventory и устаревшие метки тоже могут привести к неверному набору целей.

# Как playbook, play, task, module, role и collection разделяют ответственность?

**Playbook** содержит последовательность plays. **Play** связывает набор hosts с переменными, ролями и задачами. **Task** вызывает module или action; **module** реализует конкретную операцию, например управление пакетом или файлом.

**Role** объединяет tasks, handlers, templates, defaults и другие ресурсы в переиспользуемую структуру. **Collection** распространяет роли, модули и plugins под namespace и собственной версией. Для ясности используют полные имена вроде `ansible.builtin.template`, а зависимости collections фиксируют. Модуль решает отдельную техническую операцию; роль описывает связную часть конфигурации сервиса.

# Почему идемпотентность Ansible зависит от модуля и способа описания задачи?

Идемпотентная задача при повторном запуске с теми же входами сохраняет уже достигнутое состояние. Например, `ansible.builtin.package` с `state: present` проверяет наличие пакета, а повторяемый `shell` с добавлением строки через `>>` может каждый раз менять файл.

`changed_when` корректирует отчёт Ansible и уведомления handlers, но не делает побочный эффект идемпотентным. Для команд задают проверяемое предусловие, `creates` или `removes`, когда это соответствует смыслу операции, либо выбирают специализированный модуль. `state: latest` также зависит от текущего репозитория: одинаковый playbook в разные дни может установить разные версии.

# Как precedence переменных и факты влияют на воспроизводимость playbook?

Итоговое значение зависит от источника: конфигурации, CLI options, playbook keywords и разных уровней variables. Среди переменных `--extra-vars` имеет очень высокий приоритет, поэтому может неожиданно переопределить inventory и настройки роли. Нельзя считать, что любой CLI option автоматически сильнее любой переменной.

**Facts** — сведения об узлах, например ОС и адресах; они зависят от текущего состояния и свежести кеша. Для воспроизводимости ограничивают число переопределений, документируют входы роли, проверяют обязательные значения через `assert` и явно управляют сбором фактов. [Правила precedence Ansible](https://docs.ansible.com/projects/ansible/latest/reference_appendices/general_precedence.html).

# Как templates и handlers обновляют конфигурацию без лишних перезапусков сервиса?

`template` формирует файл из Jinja-шаблона и переменных. Если содержимое изменилось, задача сообщает `changed` и через `notify` ставит **handler** в очередь, например для reload сервиса. Повторные уведомления одного handler в пределах очереди не требуют повторять перезапуск для каждого изменённого файла.

Handlers обычно исполняются в предусмотренных точках play; `meta: flush_handlers` запускает ожидающие раньше. До замены конфигурацию желательно проверять валидатором сервиса. При последующей ошибке задачи handler может не выполниться, поэтому порядок и поведение при сбое проектируют явно. [Handlers Ansible](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_handlers.html).

# Что проверяют check mode и diff mode и почему они не заменяют запуск на тестовом окружении?

**Check mode** прогнозирует изменения для модулей, которые его поддерживают; неподдерживаемые задачи обычно пропускаются. **Diff mode** показывает различия до и после для поддерживающих его модулей. Вместе они помогают увидеть неожиданный объём изменений.

Симуляция не гарантирует корректность полного запуска: будущие результаты пропущенных задач, условия и внешние эффекты могут быть недоступны. Кроме того, задача с `check_mode: false` способна реально изменить систему даже при общем `--check`. Вывод diff может раскрыть секреты. После проверки нужны запуск в контролируемом окружении и проверка результата сервиса. [Check и diff modes](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_checkmode.html).

# Как serial, forks и throttle управляют параллелизмом и размером партии изменений?

`forks` ограничивает число параллельных workers Ansible. `serial` делит hosts play на партии и завершает play для одной партии перед переходом к следующей. `throttle` дополнительно ограничивает параллелизм отдельной задачи или блока в рамках общих ограничений.

Например, обновление `serial: 2` позволяет вывести два узла из балансировки, изменить их, проверить и вернуть, прежде чем переходить дальше. Размер партии выбирают по резерву мощности и отказоустойчивости. Эти параметры сами по себе не добавляют health checks, draining или автоматический откат: соответствующие шаги включают в playbook. [Управление выполнением](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_strategies.html).

# Как block, rescue, always и failed_when помогают обрабатывать частичный сбой?

`block` объединяет связанные задачи, `rescue` запускает восстановительные шаги после обрабатываемой ошибки, а `always` — завершающие действия, например очистку временного файла. `failed_when` определяет, какой результат задачи считать ошибкой, исходя из кода возврата и содержимого ответа.

Это не транзакция с автоматическим rollback: уже выполненные изменения сохраняются, пока их явно не компенсируют. Ошибки синтаксиса и недоступный host не обрабатываются как обычный failed task в `rescue`. После компенсации проверяют состояние и при необходимости явно завершают play с ошибкой, чтобы pipeline не принял неполное восстановление за успешный деплой. [Blocks](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_blocks.html).

# Как использовать become и хранить чувствительные данные при автоматизации Ansible?

`become` задаёт повышение или смену привилегий, например через `sudo`, а `become_user` — целевого пользователя. Его включают для нужных задач с минимальными правами; параметры подключения и elevation проверяют отдельно.

Чувствительные значения получают из secret manager или зашифрованных данных Ansible Vault. Пароль расшифрования не хранят рядом с ciphertext. `no_log: true` ограничивает вывод задачи, а `diff: false` предотвращает раскрытие содержимого через diff; это не заменяет защиту файлов, временных данных и прав доступа. Не используют `debug` для секретов и проверяют, какие значения попадают в CI artifacts.

# Как тестировать роли, выявлять configuration drift и фиксировать версии collections?

Фиксируют версии `ansible-core`, collections и окружения execution environment, чтобы одинаковый код не менял поведение из-за обновления зависимостей. Выполняют syntax check, lint и сценарии роли на поддерживаемых ОС, например через Molecule.

Проверяют первый запуск, повтор без неожиданных `changed`, обновление существующей конфигурации и частичный сбой. **Configuration drift** выявляют сравнением фактического состояния с ожидаемым, включая check mode для подходящих модулей. Успешный отчёт Ansible дополняют функциональной проверкой сервиса: файл может быть правильным, а приложение — неработоспособным.
