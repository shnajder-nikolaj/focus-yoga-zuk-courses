# Когда backend-операцию стоит переносить из HTTP-запроса в фоновую задачу?

Фоновая задача подходит для долгой обработки, временно недоступной зависимости, ресурсоёмкого экспорта или работы, которую нужно пережить после завершения HTTP-запроса. Клиент получает идентификатор и способ узнать статус вместо ожидания всей операции.

Перенос добавляет промежуточные состояния, retries и задержку завершения. Создание задания должно быть надёжно связано с принятием бизнес-намерения, например через локальную транзакцию и outbox. Detached promise в процессе сервера не является надёжной очередью.

# Как выбирать между очередью задач, cron и workflow scheduler?

Очередь задач распределяет поступившую работу между workers и буферизует пики. Cron инициирует работу по расписанию. Workflow scheduler координирует зависимости, ожидания и переходы многошагового процесса.

Механизмы можно сочетать: cron создаёт задание, очередь доставляет, workflow хранит этапы. Выбирают по длительности, восстановлению, требуемому порядку и календарной семантике. Расписание само по себе не гарантирует единственный запуск и успешный бизнес-эффект.

# Какие данные и версии контракта должны храниться в payload фоновой задачи?

Payload содержит тип и версию задачи, устойчивый operation ID, ссылки на необходимые данные и проверенный tenant/security context. Не следует сериализовать весь ORM object graph, долгоживущий access token или большой файл.

Решают, нужны ли данные на момент постановки или актуальное состояние на момент выполнения. Для первого сохраняют snapshot или версию; для второго worker заново читает данные и проверяет допустимость. Старые jobs могут пережить несколько релизов, поэтому handlers поддерживают предусмотренные версии контракта.

# Как visibility timeout, lease и heartbeat связаны с повторным запуском job?

Visibility timeout или lease временно закрепляет задачу за worker. Heartbeat продлевает право обработки; при отсутствии продления задача может стать доступной другому worker. Это позволяет восстановиться после падения, но допускает одновременное выполнение при задержке старого процесса.

Сроки выбирают по длительности и способности обновлять lease. В Node.js CPU-bound работа может блокировать heartbeat, поэтому её изолируют или ограничивают. Идемпотентность нужна даже при здоровой очереди. [Stalled jobs BullMQ](https://docs.bullmq.io/guide/jobs/stalled).

# Как сделать бизнес-эффект worker идемпотентным при повторной доставке задачи?

Идемпотентность связывают с бизнес-намерением, а не номером попытки. В одной локальной транзакции записывают уникальный operation ID, предметное изменение и результат; повтор возвращает уже известный исход или продолжает контролируемое состояние.

Для внешнего API используют стабильный внешний ключ и сверку неизвестного результата. Уникальный job ID в очереди не всегда защищает после удаления завершённой задачи. Worker должен выдержать падение после эффекта, но до подтверждения выполнения.

# Как проектировать retries, backoff и dead letter queue для фоновых задач?

Временные технические ошибки повторяют с ограниченными попытками, backoff, jitter и общим сроком задачи. Некорректный payload или окончательный бизнес-отказ обычно не исправляются повтором и требуют другого исхода.

После исчерпания попыток сохраняют job и причину в failed storage или DLQ, уведомляют владельца и поддерживают безопасный replay. Poison job не должна бесконечно блокировать очередь. Повтор после длительного ожидания заново проверяет актуальность задачи и её полномочия.

# Как ограничивать concurrency workers и учитывать квоты downstream-сервисов?

Ограничивают число активных операций на worker и суммарно по приложению, tenant или внешнему поставщику. Rate limit и concurrency limit решают разные задачи: один ограничивает частоту, другой — одновременно удерживаемые ресурсы.

Масштабирование workers согласуют с pool БД, CPU, памятью и внешними quotas. Возраст и длина очереди полезнее одного CPU-показателя для I/O-задач. При перегрузке применяют admission control, приоритеты или fair scheduling, не создавая неограниченный backlog.

# Как cron должен учитывать timezone, переходы времени, пропущенные и перекрывающиеся запуски?

Расписание задают с явной timezone и политикой календарных аномалий: локальное время при DST может отсутствовать или повториться. Также определяют catch-up после простоя и поведение, если предыдущий запуск ещё работает: разрешить overlap, пропустить или заменить.

Для каждого календарного периода полезен стабильный business key, чтобы повтор scheduler не повторил результат. UTC упрощает техническое расписание, но не всегда совпадает с бизнес-календарём. Даже Kubernetes CronJob может создать два Jobs или пропустить запуск. [CronJob semantics](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/).

# Почему распределённая блокировка не гарантирует единственное выполнение задачи после истечения lease?

Worker может остановиться дольше lease, потерять блокировку, а затем продолжить работу, когда новый владелец уже выполняет задачу. Проверка владения только перед записью оставляет ещё одно окно гонки.

**Fencing token** позволяет защищаемому хранилищу атомарно отвергать операции старого владельца, если оно поддерживает такую проверку. Уникальный owner ID для безопасного unlock решает другую задачу. Для внешнего эффекта без fencing нужны идемпотентность или иная предметная защита. [Leases и fencing](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html).

# Как durable progress, checkpoints и chunking помогают продолжить долгую задачу?

Долгую работу делят на ограниченные chunks и сохраняют подтверждённый прогресс: cursor, версии входа, результаты этапов и operation IDs. После перезапуска worker продолжает с известной точки вместо повторения всего объёма.

Checkpoint должен согласовываться с эффектом: сохранённый раньше результата пропустит работу, сохранённый позже допускает повтор. Поэтому используют локальную атомарность или идемпотентные chunks. Cursor по изменяемому набору требует понятной snapshot-семантики. Процент выполнения не является достаточным recovery-состоянием.

# Как останавливать worker без потери задачи и поддерживать отмену пользователем?

При shutdown worker прекращает брать новые jobs, завершает активные в пределах срока и подтверждает только надёжно сохранённый результат. После принудительного завершения очередь должна позволить повтор, а handler — выдержать его.

Пользовательская отмена — отдельное долговечное намерение, которое worker проверяет между безопасными этапами. Она не откатывает уже выполненный внешний эффект. Статусы `CancelRequested`, `Cancelled` и `Completed` требуют согласованных переходов; удаление сообщения из очереди не гарантирует остановку уже работающего процесса.

# Как наблюдать возраст очереди, зависшие задачи и успешность бизнес-результата?

Измеряют age oldest job, lag относительно расписания, длину очереди, active jobs, retries, stalled events и время до финального результата. Разделяют «задание принято», «worker завершился» и «бизнес-результат подтверждён».

Логи и traces связывают с job ID, operation ID и попыткой. Alert должен указывать значимое отклонение: отсутствие прогресса, рост возраста или failed compensation, а не просто непустую очередь. Для восстановления оператору нужны безопасные retry, reconcile и cancel с историей действий.
