# Чем стратегический DDD отличается от тактического и когда каждый из них полезен?

**Стратегический DDD** помогает выделить предметные области, bounded contexts и отношения между ними. Он полезен, когда команды используют разные модели одних понятий и неясно, кто за что отвечает.

**Тактический DDD** задаёт приёмы моделирования внутри контекста: entities, value objects, aggregates, repositories и domain services. Он полезен для сложных бизнес-правил, но не обязателен для каждой CRUD-операции. Начинают с понимания языка и границ, иначе набор классов с названиями из DDD не решит архитектурную проблему. [Domain analysis](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis).

# Как ubiquitous language помогает обнаруживать границы bounded context?

**Ubiquitous language** — общий язык экспертов и разработчиков внутри определённой модели. Термины используют в обсуждениях, примерах, коде и тестах, уточняя их при появлении неоднозначности.

Если «клиент» в продажах означает покупателя, а в биллинге — плательщика с другими правилами и жизненным циклом, это сигнал возможной границы контекстов. Различие слов не является достаточным основанием для отдельного сервиса: проверяют бизнес-ответственность и необходимость независимой эволюции.

# Чем bounded context отличается от микросервиса, модуля и схемы базы данных?

Bounded context задаёт границу применимости языка и модели. Микросервис — границу развёртывания и эксплуатации, модуль — границу кода, схема БД — организацию хранения. Эти границы могут совпадать, но не обязаны.

Один контекст можно реализовать несколькими процессами или модулем монолита. Отдельная таблица не создаёт отдельного контекста, а разделение каждой entity в микросервис часто разрушает связные бизнес-правила. Сначала определяют модель и ответственность, затем выбирают физическое размещение.

# Как context map описывает отношения между доменными контекстами?

**Context map** показывает, какие контексты взаимодействуют, кто поставляет контракт и кто вынужден адаптироваться. Важны не только потоки данных, но и отношения команд: upstream/downstream, customer/supplier, partnership или shared kernel.

Например, anti-corruption layer переводит модель внешнего поставщика в локальные понятия, защищая домен от его терминологии. Published language описывает общий формат обмена. Карта помогает заранее увидеть зависимость релизов и цену изменения чужого контракта; это не просто схема сетевых вызовов.

# Как различать entity и value object в доменной модели?

**Entity** сохраняет идентичность при изменении свойств: заказ остаётся тем же заказом после смены адреса. **Value object** определяется значениями: два одинаковых адреса или денежных значения в одной валюте взаимозаменяемы, если домен не требует их отдельной идентичности.

Value objects обычно неизменяемы и проверяют собственные ограничения при создании. Денежную сумму моделируют с валютой, чтобы исключить неосмысленное сложение. Наличие технического primary key в БД само по себе не определяет тип доменного объекта. [Entities и value objects](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/tactical-domain-driven-design).

# Как выбрать границу aggregate и какие инварианты он должен защищать?

**Aggregate** объединяет объекты, чьи инварианты должны сохраняться при изменении как единого целого. Aggregate root контролирует допустимые операции; внешний код не должен обходить его правила, напрямую меняя внутренние сущности.

Например, заказ и его позиции могут вместе защищать допустимые переходы статуса и расчёт суммы. Границу выбирают по инвариантам, частоте изменений и конкуренции, а не по всем связям таблиц. Слишком большой aggregate повышает конфликты и стоимость загрузки; слишком маленький заставляет постоянно согласовывать критические правила снаружи.

# Почему изменения разных aggregates обычно согласуют вне одной доменной транзакции?

Разные aggregates имеют самостоятельные жизненные циклы и границы согласованности. Их изменения часто связывают событиями или бизнес-процессом с eventual consistency, чтобы не создавать большие транзакции и скрытую связанность.

Если правило обязано выполняться атомарно между двумя объектами, сначала пересматривают модель: возможно, это один aggregate или нужен отдельный механизм резервирования. Несколько aggregates допустимо изменить локальной транзакцией при обоснованной потребности; DDD не запрещает возможности БД, но требует осознавать цену связи.

# Чем domain service отличается от application service и инфраструктурного сервиса?

**Application service** координирует сценарий: проверяет доступ, загружает aggregate, вызывает его поведение, управляет транзакцией и сохраняет результат. **Domain service** выражает бизнес-правило, которое естественно не принадлежит одной entity или value object.

Инфраструктурный сервис реализует техническую возможность — отправку письма, вызов платёжного API или работу с хранилищем. Бизнес-решение о допустимости скидки не должно случайно оказаться в HTTP-клиенте. При этом domain service не обязан превращаться в набор классов без состояния: важна ответственность, а не форма.

# Как проектировать repository для aggregate root без утечки деталей ORM?

Repository предоставляет доступ к aggregate roots через доменные операции: например, загрузить заказ по идентификатору и сохранить изменённый заказ. Контракт выражают терминами модели, а не типами ORM, SQL-строками или ленивыми query objects, привязанными к соединению.

Реализация преобразует данные хранения в модель и обратно. Не нужно создавать repository для каждой таблицы внутри aggregate. Сложные отчётные запросы могут использовать отдельную read model, чтобы не загружать весь aggregate ради списка на экране.

# Чем domain event отличается от integration event?

**Domain event** сообщает о значимом факте внутри модели, например `OrderConfirmed`. Он может обрабатываться в одном процессе и использовать внутренние типы домена. **Integration event** — внешний, версионируемый контракт для других контекстов после подтверждённого изменения.

Из одного domain event можно сформировать несколько внешних сообщений или не публиковать его вовсе. Не стоит сериализовать внутренний объект без контроля: изменение класса тогда сломает чужие сервисы или раскроет лишние данные. [Domain и integration events](https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/domain-events-design-implementation).

# Как согласовать сохранение aggregate и публикацию его integration event?

Состояние aggregate и запись предназначенного к публикации integration event сохраняют в **одной локальной транзакции**. После commit отдельный relay читает outbox и отправляет сообщения брокеру; неподтверждённые записи он повторяет.

Сбой между отправкой и отметкой об отправке создаёт дубли, поэтому consumer должен быть идемпотентным. Для одного aggregate сохраняют нужный порядок и версию. Простое выполнение «сначала commit, затем publish» оставляет окно потери события. [Transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html).

# Как постепенно внедрять DDD в существующее приложение и избегать избыточной модели?

Выбирают участок с дорогими бизнес-ошибками, собирают язык с экспертами и фиксируют несколько реальных сценариев с инвариантами. Затем выделяют границу модели и переводят один сценарий, сохраняя взаимодействие со старым кодом через явный интерфейс.

Не нужно переписывать весь продукт или вводить aggregates для справочника без поведения. Проверяют результат: стало ли проще менять правило, локализовать ошибку и объяснять поведение. Если большинство изменений требует синхронно менять несколько контекстов, границы или контракты стоит пересмотреть.
