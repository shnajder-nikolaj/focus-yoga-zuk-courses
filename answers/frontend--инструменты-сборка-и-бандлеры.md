# Что делает bundler и зачем он нужен браузерному приложению?

Bundler (сборщик модулей) - инструмент, который анализирует зависимости приложения и объединяет JavaScript, CSS и другие ресурсы в файлы, оптимизированные для загрузки браузером.

Основные задачи:

- Объединение модулей - формирует один или несколько файлов из зависимостей приложения
- Tree shaking - удаляет неиспользуемый код
- Code splitting - разделяет код на части для загрузки по требованию
- Минификация - уменьшает размер файлов
- Обработка ресурсов - преобразует CSS, изображения и другие assets

Bundler не обязателен для браузерного приложения: современные браузеры поддерживают ES Modules (ESM). Однако сборка позволяет уменьшить сетевые накладные расходы, оптимизировать загрузку и использовать инструменты и форматы, которые браузер напрямую не поддерживает.

Примеры: `Webpack`, `Rollup`, `esbuild`, `Rolldown`.

# Чем bundling отличается от transpilation?

Bundling - объединение модулей и их зависимостей в один или несколько выходных файлов.

Transpilation - преобразование исходного кода в другой синтаксис или диалект языка, обычно с сохранением его поведения.

Например:

- Bundling: несколько JS-модулей объединяются в `bundle.js`
- Transpilation: `TypeScript` преобразуется в `JavaScript`, а современный синтаксис JS - в синтаксис, совместимый со старыми браузерами

Bundling отвечает за организацию зависимостей и выходных файлов, а transpilation - за преобразование кода.

Оба процесса могут выполняться в рамках одной сборки.

# Как Webpack строит dependency graph?

Dependency graph (граф зависимостей) - структура, описывающая модули приложения и связи между ними.

Webpack строит его следующим образом:

1. Начинает с одного или нескольких entry points
2. Анализирует импорты (`import`, `require` и другие поддерживаемые механизмы)
3. Разрешает пути к зависимостям через механизм module resolution
4. Применяет необходимые loaders и анализирует полученные зависимости
5. Рекурсивно обрабатывает найденные модули
6. Формирует граф, на основании которого создаёт chunks и выходные файлы

Каждый модуль представляет узел графа, а зависимость между модулями - ребро.

Webpack использует этот граф для определения порядка загрузки, разделения кода, устранения дублирования и оптимизации сборки.

# Чем loader отличается от plugin в Webpack?

Loader - преобразует содержимое отдельных модулей при их обработке Webpack.

Примеры:

- `babel-loader` - преобразует JavaScript через Babel
- `css-loader` - обрабатывает CSS и его зависимости
- `sass-loader` - компилирует SCSS/Sass в CSS

Loaders настраиваются через `module.rules`. Для одного модуля может использоваться цепочка loaders, которая выполняется справа налево в массиве `use` (либо снизу вверх).

Plugin - расширяет работу Webpack через хуки жизненного цикла компилятора и компиляции.

Например, `HtmlWebpackPlugin` генерирует HTML-файл с подключением собранных ресурсов.

Главное отличие: loader преобразует модуль, plugin управляет или расширяет процесс сборки.

# Как работают entry points, output и chunks?

Entry point - начальная точка, с которой bundler строит граф зависимостей. Обычно это основной файл приложения, например `src/main.ts`.

Output - настройки выходных файлов: директория, имена, публичные URL и другие параметры.

Chunk - логическая группа модулей, сформированная сборщиком. Chunk обычно выводится в отдельный JS-файл, но связь между chunks и файлами не всегда строго один к одному.

В Webpack:

- `entry` задаёт начальные модули
- `output.path` определяет директорию сборки
- `output.filename` определяет имена файлов для начальных chunks
- `output.chunkFilename` задаёт имена файлов для дополнительных chunks

Например, основной код может оказаться в `main.js`, общие зависимости - в `vendors.js`, а динамически загружаемая страница - в `profile.js`.

Chunks позволяют разделять код, повторно использовать общие зависимости и загружать отдельные части приложения независимо.

# Что такое code splitting и когда его применять?

Code splitting - разделение JavaScript на несколько chunks, которые можно загружать независимо.

Основная цель - уменьшить объём кода, необходимого для первоначального отображения приложения.

Частые сценарии:

- Route-based splitting - отдельный chunk для страницы или маршрута
- Component-based splitting - отложенная загрузка тяжёлых компонентов
- Vendor splitting - выделение общих библиотек в отдельные chunks для повторного использования и кэширования

Например, редактор изображений не нужно загружать, пока пользователь не откроет соответствующий раздел.

Однако чрезмерное дробление создаёт дополнительные сетевые запросы и может увеличить задержки из-за цепочек загрузки.

Code splitting полезен, когда откладываемый код достаточно тяжёлый и не требуется при первоначальной загрузке.

# Как tree shaking определяет неиспользуемый код?

Tree shaking использует статический анализ графа модулей, чтобы определить, какие экспорты действительно используются приложением.

Например:

```
export const add = (a, b) => a + b;
export const multiply = (a, b) => a * b;
```

Если приложение импортирует только `add`, сборщик может исключить `multiply`.

Механизм состоит из двух основных этапов:

1. Анализ использования - сборщик отслеживает связи между `import` и `export` и отмечает используемые экспорты
2. Удаление кода - исключает ненужные модули или выражения, часто с помощью минификатора

Tree shaking наиболее эффективен с ES Modules, поскольку их импорты и экспорты имеют статическую структуру.

Главное ограничение - side effects. Если модуль при импорте изменяет глобальное состояние, регистрирует обработчики или выполняет другую побочную работу, его нельзя безопасно удалить только потому, что его экспорты не используются.

# Как `sideEffects` в `package.json` влияет на tree shaking?

Поле `sideEffects` сообщает сборщику, какие файлы пакета могут выполнять побочные действия при импорте.

Варианты:

- `"sideEffects": false` - пакет заявляет, что все его модули безопасно пропускать, если их результаты не используются
- `"sideEffects": true` - модули потенциально имеют побочные эффекты
- `"sideEffects": ["*.css", "./src/polyfills.js"]` - перечисляет файлы с побочными эффектами, остальные считаются безопасными для исключения

Это позволяет Webpack удалять целые неиспользуемые модули вместе с их зависимостями.

Важно: `sideEffects: false` не означает, что все экспорты можно удалить. Используемый код сохраняется, а внутри него могут дополнительно удаляться неиспользуемые выражения.

Неправильное значение может сломать приложение: например, сборщик удалит импорт CSS или полифила, поскольку их экспорты не используются.

# Чем Vite dev server отличается от production build?

Vite dev server ориентирован на скорость разработки:

- Использует нативные ES Modules браузера
- Преобразует исходные модули по запросу, без полной production-сборки
- Поддерживает HMR (Hot Module Replacement) для обновления модулей без полной перезагрузки страницы
- Предварительно обрабатывает зависимости, чтобы ускорить их загрузку

Production build ориентирован на производительность готового приложения:

- Собирает модули в оптимизированные chunks
- Выполняет tree shaking и минификацию
- Оптимизирует CSS и статические ресурсы
- Создаёт файлы для развёртывания

Версионная особенность: начиная с Vite 8 (март 2026 года), основным bundler для production и предварительной обработки зависимостей стал `Rolldown`. В Vite 7 и более ранних версиях для production использовался `Rollup`, а для предварительной обработки зависимостей - `esbuild`.&#x20;

# Как работает native ESM в режиме разработки Vite?

В режиме разработки Vite использует встроенную поддержку ES Modules браузером вместо предварительной сборки всего приложения в единый bundle.

Процесс:

1. Браузер запрашивает основной модуль через `<script type="module">`
2. Vite преобразует запрошенный файл при необходимости, например TS или JSX в JS
3. Переписывает пути импортов в URL, доступные браузеру
4. Браузер самостоятельно загружает зависимости через HTTP
5. При изменении файла Vite обновляет затронутые модули через HMR

Например, импорт `import { ref } from 'vue'` преобразуется в URL предварительно обработанной зависимости.

Vite использует dependency pre-bundling, поскольку браузеры не разрешают импорты по именам npm-пакетов самостоятельно, а некоторые зависимости распространяются в CommonJS или содержат множество внутренних модулей.

Результат - dev server может быстро запускаться и обрабатывать изменения без полной пересборки приложения.&#x20;

# Чем Rollup, esbuild и SWC отличаются по назначению?

Rollup - JavaScript bundler, ориентированный на ESM, tree shaking и формирование оптимизированных выходных файлов. Часто используется для сборки библиотек, которым нужны разные форматы модулей.

esbuild - быстрый bundler и транспилятор, написанный на Go. Поддерживает сборку модулей, преобразование TypeScript/JSX, минификацию и code splitting. Ориентирован на высокую скорость обработки.

SWC - компилятор JavaScript/TypeScript, написанный на Rust. Основные задачи - транспиляция, преобразование JSX/TS и минификация. Может использоваться как часть bundler-инфраструктуры, например через `swc-loader`.

Главное различие:

- Rollup - акцент на сборке и оптимизации графа модулей
- esbuild - быстрая сборка, транспиляция и минификация
- SWC - быстрая компиляция и преобразование исходного кода

Их возможности пересекаются, поэтому выбор зависит от требований проекта и используемого инструментария.&#x20;

# Для чего нужны Babel и browserslist?

Babel - компилятор JavaScript, который преобразует современный синтаксис в код, совместимый с целевыми окружениями. Также обрабатывает JSX и может использовать плагины для дополнительных преобразований.

Browserslist - инструмент для определения списка поддерживаемых браузеров по заданным правилам.

Например:

```
> 0.5%
not dead
```

Такой конфиг выбирает браузеры с долей использования больше 0,5%, исключая версии, признанные устаревшими по критериям Browserslist.

Связь между ними:

1. Browserslist определяет целевые версии браузеров
2. `@babel/preset-env` получает информацию об их возможностях
3. Babel применяет только необходимые синтаксические преобразования

Browserslist также используется другими инструментами, например `Autoprefixer`.

Важно: Babel сам по себе не обеспечивает поддержку отсутствующих браузерных API. Для них нужны полифилы. В Babel 8 их подключение вынесено в отдельные плагины, например `babel-plugin-polyfill-corejs3`.&#x20;

# Чем полифил отличается от syntax transform?

Syntax transform - преобразует синтаксис JavaScript в эквивалентную форму, которую понимает целевой движок.

Например, optional chaining:

```
const name = user?.name;
```

Может преобразовываться в:

```
const name = user == null ? undefined : user.name;
```

Полифил (polyfill) - добавляет реализацию отсутствующего API или возможности стандартной библиотеки.

Например, если браузер не поддерживает `Array.prototype.at()`, полифил может добавить этот метод.

Главное отличие:

- Syntax transform решает проблему неподдерживаемого синтаксиса
- Polyfill решает проблему отсутствующей функциональности

Полифилы не позволяют движку парсить неизвестный синтаксис, а синтаксические преобразования обычно не добавляют отсутствующие API.

# Как работают dynamic imports и lazy chunks?

Dynamic import - синтаксис `import()`, позволяющий загружать модуль асинхронно во время выполнения программы.

```
const module = await import('./editor.js');
module.openEditor();
```

`import()` возвращает `Promise`, который разрешается объектом пространства имён загруженного модуля.

При сборке bundler обычно создаёт для такого импорта отдельный lazy chunk - файл, который не входит в первоначальную загрузку.

Механизм:

1. Сборщик обнаруживает динамический импорт
2. Выделяет модуль и необходимые зависимости в отдельные chunks
3. Во время выполнения `import()` загружается соответствующий код
4. После загрузки и выполнения модуля разрешается `Promise`

При повторном импорте уже загруженный и вычисленный модуль обычно используется повторно без повторного выполнения.

Важно учитывать, что загрузка может завершиться ошибкой из-за сети, недоступного файла или проблем с выполнением модуля. Поэтому динамические импорты требуют обработки ошибок.

# Почему дублирующиеся версии библиотек увеличивают bundle size?

Если разные зависимости используют несовместимые версии одной библиотеки, пакетный менеджер может установить несколько её копий.

Например:

```
app
├── library-a → lodash@4.17
└── library-b → lodash@3.10
```

Bundler может включить обе версии в итоговую сборку, поскольку они представляют разные реализации и не всегда могут заменять друг друга.

Последствия:

- Увеличение размера JavaScript
- Дополнительные затраты на загрузку, парсинг и выполнение
- Возможное дублирование логики и внутреннего состояния библиотек
- Проблемы совместимости, если разные версии должны совместно использовать объекты или контекст

Проверять дублирование можно через `npm ls`, `npm dedupe`, `pnpm why` и анализаторы бандла.

Важно: две установленные версии не обязательно попадут в итоговый bundle. Это зависит от того, какие зависимости действительно используются и как bundler их обрабатывает.

# Как исследовать бандл с помощью bundle analyzer?

Bundle analyzer - инструмент для визуализации состава сборки, позволяющий определить, какие модули и библиотеки занимают больше всего места.

Например, для Webpack можно использовать `webpack-bundle-analyzer`:

```
npx webpack --analyze
```

При установленном анализаторе команда открывает визуальное представление сборки.

Что исследовать:

1. Крупные зависимости - библиотеки, значительно увеличивающие bundle size
2. Дублирование - несколько версий или копий одного пакета
3. Неожиданные модули - код, который не должен попадать в клиентскую сборку
4. Распределение chunks - какие зависимости находятся в начальной загрузке
5. Tree shaking - какие неиспользуемые модули или экспорты остались в сборке

Важно различать исходный размер модулей, размер после минификации и размер после gzip/Brotli. Они характеризуют разные затраты.

Основной результат анализа - понимание, что именно загружается пользователем и почему.&#x20;

# Как правильно обрабатывать assets из `public` и импортируемые assets?

В Vite статические ресурсы можно обрабатывать двумя способами.

1\. Assets из `public`

Файлы из `public` копируются в выходную директорию без преобразования и переименования.

Например:

```
public/favicon.ico
```

Доступен по URL `/favicon.ico` при размещении приложения в корне сайта.

Подходит для файлов, которым необходимо сохранить имя, или ресурсов, не импортируемых из исходного кода.

2\. Импортируемые assets

Ресурсы импортируются непосредственно в компоненты:

```
import logoUrl from './assets/logo.svg';
```

Bundler обрабатывает их как часть графа зависимостей и может:

- Добавлять хеш к имени файла для корректного кэширования
- Встраивать небольшие ресурсы непосредственно в bundle
- Преобразовывать пути с учётом директории развёртывания
- Исключать ресурсы, которые больше не используются, если это допускает обработка

Главное правило: импортируемые assets предпочтительны для ресурсов, связанных с кодом приложения. `public` подходит для файлов, которые необходимо копировать без обработки.

При развёртывании в поддиректории нужно учитывать `base` в Vite, иначе абсолютные пути к ресурсам могут оказаться неправильными.&#x20;

# Как настроить окружения и переменные для разных deployment targets?

Для разных окружений - `development`, `staging`, `production` - обычно используются отдельные конфигурации.

В Vite:

```
.env
.env.development
.env.staging
.env.production
```

Переменные с префиксом `VITE_` доступны в клиентском коде через `import.meta.env`.

Например:

```
const apiUrl = import.meta.env.VITE_API_URL;
```

Для сборки под определённое окружение:

```
vite build --mode staging
```

Vite загружает общие и соответствующие выбранному режиму `.env`-файлы. Переменные, заданные непосредственно в окружении процесса, имеют более высокий приоритет.

Важные особенности:

- Build-time configuration - значения встраиваются в клиентский код при сборке. Изменение переменной после деплоя не обновляет уже собранный JavaScript
- Runtime configuration - значения загружаются при запуске приложения, например из `/config.json` или серверного endpoint
- Secrets - нельзя размещать в клиентских переменных: значения `VITE_*` доступны пользователю

Если один и тот же артефакт должен развёртываться в нескольких окружениях без пересборки, удобнее использовать runtime configuration.&#x20;

# Чем source map полезен и какие риски возникают при публикации его в продакшене?

Source map - файл, связывающий скомпилированный или минифицированный код с его исходными версиями.

Позволяет:

- Отлаживать оригинальные TypeScript/JavaScript-файлы
- Получать осмысленные stack traces
- Определять точные места ошибок в исходном коде
- Анализировать production-ошибки через системы мониторинга

Основной риск - раскрытие исходного кода приложения.

Source maps могут содержать исходный код (`sourcesContent`), имена файлов, структуру проекта и другую внутреннюю информацию.

Для production существуют разные стратегии:

- Не публиковать source maps
- Загружать их только в защищённую систему мониторинга ошибок
- Использовать `hidden-source-map`, не размещая `.map` в публичном доступе
- Использовать `nosources-source-map`, если допустимо раскрытие структуры исходных файлов без их содержимого

Важно: отсутствие ссылки `sourceMappingURL` не защищает файл, если сам `.map` доступен по публичному URL.&#x20;

# Как настроить aliases для TypeScript и bundler согласованно?

Path aliases - псевдонимы путей импортов, позволяющие использовать короткие и стабильные пути вместо длинных относительных.

Например:

```
import Button from '@/components/Button';
```

Для TypeScript:

```
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}
```

Для Vite:

```
import { defineConfig } from 'vite';
import { fileURLToPath, URL } from 'node:url';

export default defineConfig({
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url))
    }
  }
});
```

Ключевой момент: `compilerOptions.paths` сообщает TypeScript, как находить модули при анализе типов, но не переписывает пути в сгенерированном JavaScript.

Поэтому alias должен быть согласован между TypeScript, bundler и другими инструментами, которые самостоятельно разрешают импорты, например тестовым раннером.

В современных версиях Vite также можно использовать `resolve.tsconfigPaths`, если нужно учитывать `paths` из `tsconfig.json` без ручного дублирования.&#x20;

# Как диагностировать ошибку сборки, проявляющуюся только в CI?

Если локальная сборка проходит, а в CI падает, причина обычно связана с различиями окружения или процесса установки зависимостей.

Порядок диагностики:

1. Проверить версии - сравнить Node.js, пакетный менеджер и системные зависимости
2. Проверить зависимости - выполнить чистую установку через `npm ci` или аналог с фиксированным lockfile
3. Проверить переменные окружения - убедиться, что необходимые переменные доступны и имеют корректные значения
4. Проверить регистр путей - Linux различает `Button.tsx` и `button.tsx`, а некоторые локальные файловые системы - нет
5. Проверить конфигурацию сборки - сравнить build mode, флаги, рабочую директорию и используемые конфигурационные файлы
6. Проверить кэши - исключить влияние устаревших артефактов и кэшей зависимостей

Также нужно учитывать платформенные пакеты с нативными бинарными файлами, права доступа и ограничения памяти CI.

Основной принцип диагностики - воспроизвести сборку в окружении, максимально близком к CI, используя те же команды и версии инструментов.

Например, в Docker-контейнере с той же версией Node.js.

# Что такое tree shaking и какие условия делают его возможным?

Tree shaking - оптимизация, при которой сборщик исключает код, не используемый приложением, на основании статического анализа зависимостей и экспортов.

Для эффективной работы необходимы:

- Статическая структура модулей - предпочтительно ESM с `import` и `export`
- Анализируемые зависимости - сборщик должен понимать, какие экспорты используются
- Безопасность удаления - удаляемый код не должен содержать обязательных побочных эффектов
- Корректная конфигурация - `sideEffects`, `/*#__PURE__*/` и другие метаданные должны соответствовать реальному поведению кода
- Оптимизации сборки - необходимо включить удаление неиспользуемых модулей и выражений, обычно при production-сборке

Tree shaking затрудняется при использовании динамического `require()`, непрозрачных побочных эффектов и некоторых CommonJS-паттернов.

Важно различать tree shaking и dead code elimination: первый обычно описывает анализ используемых экспортов и зависимостей между модулями, второй - более широкое удаление недостижимого или неиспользуемого кода.

# Чем полифил отличается от транспиляции?

Транспиляция - преобразование исходного кода в другую форму с сохранением его поведения.

Например:

```
const double = x => x * 2;
```

Может преобразовываться в:

```
var double = function (x) {
  return x * 2;
};
```

Полифил - реализация отсутствующей возможности среды выполнения, например `Promise`, `Array.from()` или `Object.assign()`.

Разница заключается в уровне изменений:

- Транспиляция изменяет исходный код перед выполнением
- Полифил добавляет функциональность, необходимую во время выполнения

Например, транспилятор может преобразовать `async/await` в совместимую форму, но если эта реализация использует `Promise`, а браузер его не поддерживает, дополнительно потребуется полифил.

Обычно оба механизма используются совместно для поддержки старых окружений.

# Как устроены source maps и почему они полезны при отладке?

Source maps - данные, описывающие соответствия между позициями сгенерированного JavaScript и исходного кода.

Обычно source map представляет собой JSON-файл со следующими полями:

- `version` - версия формата source map
- `sources` - список исходных файлов
- `sourcesContent` - необязательное содержимое исходных файлов
- `names` - имена идентификаторов, используемые в сопоставлениях
- `mappings` - закодированные соответствия между позициями исходного и сгенерированного кода

Поле `mappings` обычно использует Base64 VLQ для компактного хранения смещений строк, столбцов и индексов исходных файлов.

Когда возникает ошибка в минифицированном коде, инструменты отладки используют source map, чтобы определить исходный файл и позицию соответствующего выражения.

Например, ошибка в `bundle.js:1:4582` может быть сопоставлена с `src/components/Button.tsx:42:10`.

Source maps также могут формироваться последовательно: TypeScript преобразуется в JavaScript, затем код обрабатывается bundler и минификатором. Для корректной отладки их соответствия должны сохраняться и объединяться.

# Как выбирать границы code splitting?

Границы code splitting определяют, какие модули объединяются в один chunk, а какие загружаются отдельно.

При выборе учитывают несколько факторов.

1. Сценарии использования. Код страницы или функциональности, которая открывается редко, лучше загружать отдельно
2. Размер модулей. Тяжёлые библиотеки, например редакторы или визуализаторы, часто выгодно выделять в lazy chunks
3. Повторное использование. Общие зависимости можно выделять в отдельные chunks, если это улучшает кэширование и устраняет дублирование
4. Частоту изменений. Редко меняющиеся зависимости могут кэшироваться независимо от часто обновляемого кода приложения
5. Сетевые расходы. Слишком большое количество мелких chunks увеличивает число запросов и может создавать последовательные цепочки загрузки

Например, если приложение содержит личный кабинет, административную панель и редактор документов, логично разделить их по функциональным границам.

При этом небольшие компоненты, которые почти всегда используются вместе, обычно нет смысла разделять.

Основной критерий: code splitting должен сокращать критический путь загрузки приложения, а не просто уменьшать размер отдельных файлов.

Оценивать результат нужно по реальным метрикам загрузки, например `LCP`, `INP`, времени выполнения JavaScript и сетевому waterfall, а не только по количеству chunks.
