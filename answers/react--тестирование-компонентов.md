# Как тестировать React-компонент через пользовательское поведение?

Используют React Testing Library (RTL), которая позволяет проверять компонент с точки зрения пользователя, а не его внутренней реализации.

Основной подход:

1. Отрендерить компонент через `render()`.
2. Найти элементы через `screen` по роли, тексту или доступному имени.
3. Выполнить пользовательские действия через `userEvent`.
4. Проверить результат через `expect()` и матчеры `@testing-library/jest-dom`.

Пример:

```
test('увеличивает счётчик', async () => {
  const user = userEvent.setup();

  render(<Counter />);

  await user.click(
    screen.getByRole('button', { name: 'Увеличить' })
  );

  expect(screen.getByText('1')).toBeInTheDocument();
});
```

Тест проверяет, что нажатие кнопки изменяет отображаемое значение. Ему неважно, используется внутри `useState`, `useReducer` или Redux.

Главный принцип: тестировать наблюдаемое поведение компонента, а не его внутренние состояния, методы или последовательность вызовов.

# Почему React Testing Library рекомендует находить элементы по роли?

`getByRole()` ищет элементы по их семантической роли в дереве доступности (accessibility tree), приближая тест к тому, как интерфейс воспринимают вспомогательные технологии.

Например:

```
screen.getByRole('button', { name: 'Сохранить' });
```

Поиск учитывает:

- Роль - `button`, `textbox`, `checkbox`, `heading` и другие.
- Доступное имя (accessible name) - текст кнопки, связанный `label`, `aria-label` и другие источники.
- Состояние - например, `checked`, `selected`, `expanded`.

Преимущества:

- Устойчивость к рефакторингу. Тест не зависит от CSS-классов и структуры вложенных элементов.
- Проверка семантики. Некорректная HTML-разметка может привести к тому, что элемент не будет найден по ожидаемой роли.
- Близость к пользовательскому взаимодействию. Поиск использует доступные пользователю характеристики элемента.

Например, обычный `<button>` автоматически имеет роль `button`, поэтому явно добавлять `role="button"` не требуется.

При этом `getByRole()` не гарантирует полную доступность компонента. Для полей формы также может быть удобен `getByLabelText()`.

# Чем `getBy`, `queryBy` и `findBy` отличаются?

Все три семейства методов используются для поиска элементов, но отличаются поведением при отсутствии результата и поддержкой ожидания.

- `getBy*` - синхронно возвращает элемент. Если он не найден или найдено несколько совпадений, выбрасывает ошибку. Подходит для элементов, которые уже должны присутствовать.
- `queryBy*` - синхронно возвращает элемент или `null`, если совпадений нет. Подходит для проверки отсутствия элемента. При нескольких совпадениях выбрасывает ошибку.
- `findBy*` - асинхронно ожидает появления элемента и возвращает `Promise`. Если элемент не найден за установленное время или поиск остаётся неоднозначным, промис отклоняется.

Примеры:

```
// Элемент должен существовать
screen.getByRole('button', { name: 'Сохранить' });

// Элемента не должно быть
expect(
  screen.queryByText('Ошибка')
).not.toBeInTheDocument();

// Элемент появится асинхронно
expect(
  await screen.findByText('Данные загружены')
).toBeInTheDocument();
```

Для нескольких элементов существуют `getAllBy*`, `queryAllBy*` и `findAllBy*`, которые возвращают массив или промис с массивом.

Важно: `findBy*` использует механизм повторных проверок `waitFor()`. Стандартный таймаут составляет 1000 мс, но его можно изменить.

# Как использовать `userEvent` вместо ручного вызова обработчика?

`userEvent` из `@testing-library/user-event` имитирует пользовательские действия через DOM, а не вызывает React-обработчики напрямую.

Вместо:

```
props.onClick();
```

используют:

```
const user = userEvent.setup();

render(<LoginForm />);

await user.type(
  screen.getByRole('textbox', { name: 'Логин' }),
  'admin'
);

await user.click(
  screen.getByRole('button', { name: 'Войти' })
);
```

`userEvent` воспроизводит последовательность связанных событий. Например, при вводе текста учитываются фокус, клавиатурные события, изменение значения поля и события ввода.

Он также учитывает некоторые ограничения интерфейса, например невозможность обычного пользовательского клика по `disabled`-кнопке.

Отличие от `fireEvent`:

- `fireEvent` отправляет конкретное DOM-событие, например `click`.
- `userEvent` моделирует действие пользователя, которое может включать несколько событий и изменение состояния DOM.

В современной версии `user-event@14` рекомендуется создавать экземпляр через `userEvent.setup()` и использовать `await` для асинхронных методов.

`fireEvent` остаётся полезным для низкоуровневых событий, которые `userEvent` не поддерживает.

# Когда нужны `waitFor` и `findByRole`?

Оба инструмента используются для проверки асинхронных изменений интерфейса, но решают немного разные задачи.

`findByRole()` подходит, когда нужно дождаться появления конкретного элемента:

```
expect(
  await screen.findByRole('heading', {
    name: 'Профиль'
  })
).toBeInTheDocument();
```

`waitFor()` подходит, когда нужно дождаться выполнения произвольного условия:

```
await waitFor(() => {
  expect(onSuccess).toHaveBeenCalledTimes(1);
});
```

`waitFor()` повторно выполняет callback, пока он не перестанет выбрасывать ошибку или пока не истечёт таймаут.

Поэтому следующий вариант неверен:

```
await waitFor(() => {
  return isLoaded;
});
```

Возврат `false` не заставляет `waitFor()` повторить проверку. Нужно использовать утверждение:

```
await waitFor(() => {
  expect(isLoaded).toBe(true);
});
```

Если нужно дождаться исчезновения элемента, удобно использовать `waitForElementToBeRemoved()`.

Практическое правило: для появления элемента предпочитать `findByRole()`, для остальных асинхронных условий - `waitFor()`.

# Что такое `act()` и почему он иногда появляется в предупреждениях?

`act()` - вспомогательная функция React для тестирования, которая гарантирует обработку обновлений React, относящихся к тестируемому действию, перед выполнением проверок.

Она помогает убедиться, что React завершил необходимые обновления состояния, эффекты и рендеринг.

Пример:

```
await act(async () => {
  result.current.increment();
});

expect(result.current.count).toBe(1);
```

Предупреждение вида:

```
An update to Component inside a test
was not wrapped in act(...)
```

означает, что обновление React произошло вне корректно отслеживаемой тестовой операции.

Частые причины:

- Асинхронное обновление после завершения действия в тесте.
- Использование таймеров без правильного управления ими.
- Прямой вызов функции, обновляющей состояние.
- Отсутствие `await` при асинхронном пользовательском действии.

React Testing Library автоматически использует `act()` в своих основных операциях, поэтому обычно вызывать его вручную не требуется.

Если предупреждение возникает, сначала нужно проверить правильность ожидания асинхронных действий. Простое добавление `act()` без понимания причины может скрыть проблему в тесте.

В современном React рекомендуется асинхронная форма `await act(async () => ...)`.

# Как изолировать тесты, использующие React Context?

Компонент, использующий `useContext()`, должен рендериться внутри соответствующего `Provider`.

Для тестирования передают контролируемое значение контекста:

```
render(
  <ThemeContext.Provider value="dark">
    <ThemeButton />
  </ThemeContext.Provider>
);
```

Если контекст используется во многих тестах, создают общую обёртку:

```
function renderWithTheme(ui, theme = 'light') {
  return render(
    <ThemeContext.Provider value={theme}>
      {ui}
    </ThemeContext.Provider>
  );
}
```

Затем проверяют поведение компонента при разных значениях:

```
renderWithTheme(<ThemeButton />, 'dark');
```

Изоляция достигается за счёт независимых значений контекста для каждого теста.

Важно учитывать, что сам `Context` не хранит состояние. Если `Provider` управляет состоянием через `useState`, `useReducer` или внешнее хранилище, нужно создавать независимый экземпляр этого состояния.

Для сложных компонентов можно использовать параметр `wrapper` у `render()`, объединяя несколько провайдеров.

# Как тестировать компонент с React Router?

Компоненты, использующие `useNavigate()`, `useLocation()`, `useParams()` или `Link`, должны находиться внутри Router.

Для тестов обычно используют `MemoryRouter`, который хранит историю переходов в памяти и не зависит от адресной строки браузера.

Пример:

```
render(
  <MemoryRouter initialEntries={['/users/42']}>
    <Routes>
      <Route
        path="/users/:id"
        element={<UserProfile />}
      />
    </Routes>
  </MemoryRouter>
);

expect(
  screen.getByText('Пользователь 42')
).toBeInTheDocument();
```

`initialEntries` задаёт начальный URL, а `Routes` и `Route` позволяют проверить соответствие маршрута компоненту и работу параметров.

Для тестирования навигации:

1. Рендерят компонент с маршрутизатором.
2. Выполняют действие через `userEvent`.
3. Проверяют содержимое нового маршрута или значение `location`.

Если приложение использует Data Router с `loader`, `action` и другими возможностями, применяют `createMemoryRouter()` вместе с `RouterProvider`.

В React Router v7 основные API импортируются из `react-router`. В проектах на v6 обычно используется `react-router-dom`.

# Как тестировать компоненты с Redux Toolkit?

Рекомендуется использовать настоящее Redux-хранилище, созданное через `configureStore()`, и подключать его через `Provider`.

Для каждого теста создают отдельный `store`, чтобы состояние предыдущих тестов не влияло на последующие.

Пример:

```
const store = configureStore({
  reducer: {
    counter: counterReducer
  },
  preloadedState: {
    counter: { value: 5 }
  }
});

render(
  <Provider store={store}>
    <Counter />
  </Provider>
);
```

`preloadedState` позволяет задавать начальное состояние для конкретного сценария.

Проверки строят вокруг поведения компонента:

- Отображение данных из Redux.
- Изменение интерфейса после пользовательских действий.
- Обработка асинхронных операций и ошибок.

Обычно создают вспомогательную функцию `renderWithProviders()`, которая автоматически создаёт `store` и подключает `Provider`.

Не рекомендуется мокать `useSelector()` и `useDispatch()` в интеграционных тестах. Такие моки обходят настоящую логику Redux и делают тесты зависимыми от деталей реализации.

Для сетевых запросов можно использовать MSW, сохраняя реальную работу `dispatch`, middleware и reducers.

# Как создать изолированный QueryClient для каждого теста TanStack Query?

`QueryClient` управляет кешем запросов, повторными запросами и их состояниями. Если использовать один экземпляр между тестами, кешированные данные могут влиять на результаты других тестов.

Поэтому для каждого теста создают отдельный `QueryClient` и подключают его через `QueryClientProvider`.

```
function createTestQueryClient() {
  return new QueryClient({
    defaultOptions: {
      queries: {
        retry: false
      }
    }
  });
}

function renderWithQueryClient(ui) {
  const queryClient = createTestQueryClient();

  return render(
    <QueryClientProvider client={queryClient}>
      {ui}
    </QueryClientProvider>
  );
}
```

`retry: false` отключает автоматические повторные попытки при ошибках, чтобы тесты не ожидали завершения дополнительных запросов. Однако настройка не переопределяет `retry`, явно указанный в отдельном запросе.

Основные правила изоляции:

- Создавать новый `QueryClient` для каждого теста.
- Не использовать общий кеш между независимыми тестами.
- При необходимости очищать кеш через `queryClient.clear()` после размонтирования.
- Мокать сетевые запросы отдельно, например через MSW.

В TanStack Query v5 для управления временем хранения неактивного кеша используется `gcTime` вместо `cacheTime` из v4.

# Как проверять запросы и ответные состояния в RTK Query?

RTK Query автоматически управляет жизненным циклом запросов и предоставляет состояниям удобные флаги.

Основные состояния:

- `isUninitialized` - запрос ещё не запускался.
- `isLoading` - выполняется первая загрузка без доступных данных.
- `isFetching` - запрос выполняется, при этом ранее полученные данные могут оставаться доступными.
- `isSuccess` - имеются данные успешно выполненного запроса.
- `isError` - запрос завершился ошибкой.

Тестировать рекомендуется через интерфейс компонента, использующего RTK Query.

Например, для компонента `UserProfile`:

```
renderWithProviders(<UserProfile />);

expect(
  screen.getByText('Загрузка...')
).toBeInTheDocument();

expect(
  await screen.findByText('Иван')
).toBeInTheDocument();
```

Ответ сервера при этом можно контролировать через MSW.

Отдельно проверяют:

1. Успешный ответ - компонент отображает полученные данные.
2. Загрузку - показывается индикатор или skeleton.
3. Ошибку - отображается сообщение об ошибке.
4. Повторный запрос - корректно обрабатывается обновление данных.
5. Мутации - данные отправляются на сервер, а интерфейс обновляется согласно результату.

Важно различать `isLoading` и `isFetching`: повторное получение данных может устанавливать `isFetching: true`, сохраняя уже отображаемую информацию.

Для проверки кеширования и инвалидации можно дополнительно контролировать количество сетевых запросов.

# Как тестировать Error Boundary?

Error Boundary - React-компонент, который перехватывает ошибки дочерних компонентов при рендеринге и в некоторых других фазах жизненного цикла, позволяя показать резервный интерфейс (fallback UI).

Для проверки создают дочерний компонент, намеренно выбрасывающий ошибку:

```
function BrokenComponent() {
  throw new Error('Test error');
}
```

Затем проверяют, что Error Boundary отображает fallback:

```
render(
  <ErrorBoundary fallback={<p>Произошла ошибка</p>}>
    <BrokenComponent />
  </ErrorBoundary>
);

expect(
  screen.getByText('Произошла ошибка')
).toBeInTheDocument();
```

Пример предполагает, что `ErrorBoundary` принимает проп `fallback`.

Основные проверки:

- При отсутствии ошибки дочерний компонент отображается нормально.
- При ошибке отображается fallback.
- Если предусмотрена кнопка повторной попытки, она восстанавливает интерфейс после устранения причины ошибки.
- Если реализовано логирование, вызывается соответствующий обработчик.

Ограничения Error Boundary: он не перехватывает обычные ошибки обработчиков событий, асинхронных callback вроде `setTimeout`, ошибки серверного рендеринга и ошибки внутри самого Boundary. Исключение для асинхронной работы - некоторые ошибки, выброшенные внутри функции `startTransition`.

При тестировании ожидаемых ошибок React может выводить сообщения в консоль. Если они мешают тестам, допускается временно мокать `console.error` с обязательным восстановлением после проверки. В React 19 также можно использовать обработчик `onCaughtError` в настройках рендеринга.

# Как проверять доступность компонента автоматическими тестами?

Для автоматической проверки доступности (accessibility, a11y) обычно используют `axe-core` и интеграцию `jest-axe`.

Пример:

```
const { container } = render(<LoginForm />);

const results = await axe(container);

expect(results).toHaveNoViolations();
```

Для такого теста предварительно подключают `jest-axe` и его matcher `toHaveNoViolations()`.

`axe` анализирует DOM и обнаруживает распространённые нарушения правил доступности, например некорректные ARIA-атрибуты, отсутствие доступных имён у элементов управления и некоторые проблемы семантической разметки.

Дополнительно через React Testing Library проверяют:

- Наличие нужных ролей через `getByRole()`.
- Доступные имена через `toHaveAccessibleName()`.
- Состояния элементов через `toBeDisabled()`, `toBeChecked()` и другие матчеры.
- Возможность взаимодействия с клавиатуры через `userEvent.tab()` и `userEvent.keyboard()`.

Ограничение: автоматические проверки не гарантируют полной доступности. Например, `jest-axe` в JSDOM не проверяет цветовой контраст. Проверку с реальными вспомогательными технологиями они также не заменяют.

# Почему тесты не должны зависеть от внутренней структуры DOM?

Структура DOM - деталь реализации, которая может изменяться без изменения пользовательского поведения.

Например, тест:

```
container.querySelector(
  '.form > div:nth-child(2) > button'
);
```

зависит от классов, вложенности и порядка элементов.

Если добавить дополнительный контейнер или изменить CSS-класс, тест может сломаться, хотя интерфейс продолжит работать правильно.

Предпочтительнее:

```
screen.getByRole('button', { name: 'Отправить' });
```

Такой тест зависит от семантики интерфейса, а не его внутренней структуры.

Преимущества:

- Меньше ложных падений после рефакторинга.
- Возможность менять разметку без переписывания тестов.
- Более понятные проверки пользовательского поведения.

Это не означает, что DOM вообще нельзя проверять. Например, при тестировании таблицы может быть важно, что определённый текст находится внутри конкретной строки. Для этого можно использовать `within()` и семантические запросы.

Главное правило: зависеть от структуры DOM следует только тогда, когда сама структура является частью проверяемого требования.

# Как проверить custom hook тестами?

Для непосредственного тестирования пользовательских хуков используют `renderHook()` из `@testing-library/react`.

Он запускает hook внутри тестового React-компонента и предоставляет доступ к его результату через `result.current`.

Пример:

```
test('увеличивает счётчик', async () => {
  const { result } = renderHook(() => useCounter());

  expect(result.current.count).toBe(0);

  await act(async () => {
    result.current.increment();
  });

  expect(result.current.count).toBe(1);
});
```

`act()` обеспечивает обработку обновлений React после вызова метода хука.

Дополнительные возможности:

- `rerender()` - повторно вызывает hook с обновлёнными props.
- `unmount()` - размонтирует тестовый компонент для проверки очистки эффектов.
- `wrapper` - позволяет подключить необходимые Context-провайдеры.
- `waitFor()` - используется для ожидания асинхронных обновлений.

Например, при тестировании хука с асинхронной загрузкой:

```
await waitFor(() => {
  expect(result.current.isSuccess).toBe(true);
});
```

`renderHook()` удобен для проверки самостоятельной логики хуков. Если hook тесно связан с поведением конкретного компонента, полезнее тестировать его через сам компонент.

# Как тестировать RTK Query с MSW?

MSW (Mock Service Worker) перехватывает сетевые запросы и возвращает контролируемые ответы без обращения к реальному серверу.

Это позволяет тестировать RTK Query вместе с настоящими Redux middleware, кешированием и обработкой состояний запросов.

В MSW v2 обработчики HTTP-запросов создаются через `http` и `HttpResponse`:

```
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/users', () => {
    return HttpResponse.json([
      { id: 1, name: 'Иван' }
    ]);
  })
);
```

Для тестового окружения настраивают жизненный цикл сервера:

```
beforeAll(() => server.listen());

afterEach(() => server.resetHandlers());

afterAll(() => server.close());
```

После этого можно тестировать компонент, который использует RTK Query:

```
renderWithProviders(<UsersList />);

expect(
  await screen.findByText('Иван')
).toBeInTheDocument();
```

Для проверки ошибки переопределяют обработчик:

```
server.use(
  http.get('/api/users', () => {
    return HttpResponse.json(
      { message: 'Server error' },
      { status: 500 }
    );
  })
);
```

Затем проверяют, что компонент корректно отображает ошибку.

Важные особенности:

- В тестовом `store` должны быть подключены `api.reducer` и `api.middleware`.
- `server.resetHandlers()` сбрасывает временные обработчики MSW, но не очищает кеш RTK Query.
- Для независимости тестов лучше создавать новый Redux store для каждого теста.
- При повторном использовании store кеш можно сбросить через `store.dispatch(api.util.resetApiState())`, учитывая, что локальное состояние активных хуков может сохраняться.

Главное преимущество MSW - тест проходит через настоящую цепочку `RTK Query -> fetch -> ответ -> Redux -> React`, без подмены самих RTK Query hooks.

# Как тестировать компоненты с QueryClient и MSW?

Для компонентов, использующих TanStack Query, объединяют два инструмента:

- `QueryClientProvider` - предоставляет настоящий `QueryClient`, который управляет запросами и кешем.
- MSW - перехватывает HTTP-запросы и возвращает тестовые ответы.

Пример:

```
server.use(
  http.get('/api/users', () => {
    return HttpResponse.json([
      { id: 1, name: 'Иван' }
    ]);
  })
);

const queryClient = new QueryClient({
  defaultOptions: {
    queries: { retry: false }
  }
});

render(
  <QueryClientProvider client={queryClient}>
    <UsersList />
  </QueryClientProvider>
);

expect(
  await screen.findByText('Иван')
).toBeInTheDocument();
```

Такой подход позволяет проверить полный жизненный цикл запроса:

1. Начальная загрузка - компонент показывает индикатор.
2. Успешный ответ - данные появляются в интерфейсе.
3. Ошибка - отображается соответствующее состояние.
4. Повторная загрузка - компонент корректно обрабатывает `refetch`.
5. Кеширование - повторный запрос использует кеш или обращается к серверу в зависимости от настроек.
6. Инвалидация - после `invalidateQueries()` данные помечаются устаревшими и при соответствующих условиях обновляются.

Для проверки ошибок MSW может возвращать HTTP 500. При использовании стандартного `fetch` важно, чтобы `queryFn` самостоятельно проверяла `response.ok` и выбрасывала ошибку, поскольку `fetch` не отклоняет промис только из-за HTTP-статуса 500.

Главное отличие от мокирования `useQuery`: тест проверяет настоящую работу TanStack Query, включая кеширование, обновление данных и переходы между состояниями, а не заранее подставленный результат хука.

Каждый тест должен получать независимый `QueryClient`, а временные обработчики MSW необходимо сбрасывать после теста.
