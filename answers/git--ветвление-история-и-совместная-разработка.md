# Git: Ветвление, история и совместная разработка

Раздел посвящён работе с ветками, управлению историей коммитов и совместной разработке в Git.

# Чем Git отличается от GitHub и GitLab?

Git - распределённая система контроля версий, которая хранит историю изменений файлов, позволяет создавать ветки, объединять изменения и работать с репозиторием локально.

GitHub и GitLab - платформы для размещения Git-репозиториев и совместной разработки. Они предоставляют дополнительные возможности: pull/merge requests, code review, управление доступом, CI/CD и отслеживание задач.

Git работает независимо от GitHub и GitLab. Репозиторий можно использовать полностью локально или разместить на любом совместимом сервере.

# Что такое рабочая директория, index и Git repository?

Git использует три основные области:

- Working directory (рабочая директория) - файлы проекта, с которыми разработчик непосредственно работает.
- Index (staging area) - область подготовки изменений для следующего коммита. Хранит информацию о том, какие версии файлов войдут в коммит.
- Repository (репозиторий) - база данных Git, обычно расположенная в `.git`, содержащая коммиты, объекты, ссылки на ветки и другую служебную информацию.

Типичный процесс: изменение файлов в рабочей директории → `git add` для подготовки изменений в index → `git commit` для сохранения снимка в репозитории.

# Чем `git add` отличается от `git commit`?

`git add` добавляет текущее содержимое выбранных файлов в staging area, подготавливая его к следующему коммиту.

`git commit` создаёт коммит из содержимого staging area и перемещает текущую ветку на новый коммит.

Важно: `git add` фиксирует состояние файла на момент выполнения команды. Если после этого изменить файл, новые изменения не попадут в коммит без повторного `git add`.

# Для чего нужны ветки и как Git хранит коммиты?

Ветки позволяют независимо разрабатывать функции, исправлять ошибки и проводить эксперименты, не изменяя основную линию разработки.

В Git ветка представляет собой легковесную ссылку на определённый коммит. При создании нового коммита ссылка текущей ветки перемещается на него.

Каждый коммит содержит:

- Ссылку на дерево (`tree`) со снимком состояния файлов
- Ссылки на родительские коммиты
- Автора, дату, сообщение и другую метаинформацию

Коммиты образуют направленный ациклический граф (DAG). Объекты Git идентифицируются хешами своего содержимого.

Логически Git хранит снимки состояния файлов, а не последовательности изменений. Неизменившиеся объекты переиспользуются, а для экономии места Git может применять дельта-сжатие.

# Чем `git merge` отличается от `git rebase`?

Обе команды объединяют изменения из разных веток, но по-разному работают с историей.

`git merge` объединяет истории веток. Если fast-forward невозможен, обычно создаётся merge commit с двумя родителями. Исходные коммиты сохраняются без изменений.

`git rebase` переносит коммиты текущей ветки на новую базу, последовательно воспроизводя их изменения. При этом создаются новые коммиты с другими хешами.

Основные различия:

- `merge` сохраняет структуру ветвления и исходную историю
- `rebase` позволяет получить линейную историю без дополнительных merge commits
- `merge` безопаснее для общих веток
- `rebase` переписывает историю, поэтому его опасно применять к коммитам, на которые уже опираются другие разработчики

Обычно `rebase` используют для актуализации личной feature-ветки, а `merge` - для объединения общей истории.

# Как разрешать merge conflicts?

Merge conflict возникает, когда Git не может автоматически согласовать изменения, например если две ветки по-разному изменили один участок файла.

Порядок разрешения:

1. Выполнить `git status`, чтобы определить конфликтующие файлы.
2. Открыть файлы и найти конфликтующие участки с маркерами `<<<<<<<`, `=======`, `>>>>>>>`.
3. Вручную выбрать или объединить необходимые изменения и удалить маркеры.
4. Выполнить `git add` для разрешённых файлов.
5. Завершить операцию через `git commit` или `git merge --continue` для merge, либо `git rebase --continue` для rebase.

Перед завершением желательно запустить тесты, поскольку отсутствие текстовых конфликтов не гарантирует корректность результата.

Для отмены незавершённой операции используют `git merge --abort` или `git rebase --abort`.

# В каких случаях использовать fast-forward merge?

Fast-forward merge применяется, когда целевая ветка является предком ветки, изменения которой нужно объединить.

Git просто перемещает указатель целевой ветки вперёд, не создавая отдельный merge commit.

Подходит, когда:

- В целевой ветке не появилось новых коммитов после ответвления
- Требуется линейная история
- Нет необходимости сохранять факт объединения ветки отдельным коммитом

Если необходимо явно фиксировать факт объединения feature-ветки, используют `git merge --no-ff`.

# Чем `git reset` отличается от `git revert`?

`git reset` перемещает указатель текущей ветки на выбранный коммит и, в зависимости от режима, изменяет staging area и рабочую директорию. Может удалять коммиты из истории ветки.

`git revert` создаёт новый коммит, который отменяет изменения указанного коммита, сохраняя существующую историю.

Главное различие:

- `reset` изменяет историю ветки и подходит преимущественно для локальных коммитов
- `revert` не переписывает существующую историю и безопаснее для общих веток

Например, если ошибочный коммит уже опубликован и используется командой, предпочтительнее `git revert`.

# Как различаются `git reset --soft`, `--mixed` и `--hard`?

Режимы определяют, какие области Git изменяются при перемещении `HEAD`.

- `--soft` - перемещает `HEAD`, но сохраняет staging area и рабочую директорию. Удобен для объединения или переработки последних коммитов.
- `--mixed` - перемещает `HEAD` и приводит staging area к выбранному коммиту, сохраняя изменения в рабочей директории. Это режим по умолчанию.
- `--hard` - перемещает `HEAD` и приводит staging area и отслеживаемые файлы рабочей директории к выбранному коммиту. Несохранённые изменения могут быть безвозвратно потеряны.

Например, `git reset --soft HEAD~1` отменяет последний коммит, оставляя его изменения подготовленными для нового коммита.

# Что делает `git cherry-pick`?

`git cherry-pick` переносит изменения конкретного коммита из одной ветки в текущую, не объединяя всю историю веток.

Git применяет изменения выбранного коммита и обычно создаёт новый коммит с другим хешем.

Используется, например, когда нужно перенести исправление ошибки из `main` в отдельную release-ветку, не включая остальные изменения.

При переносе могут возникнуть конфликты. Кроме того, повторное применение тех же изменений может привести к дублированию или пустому коммиту.

# Когда использовать `git stash`?

`git stash` временно сохраняет незакоммиченные изменения, позволяя вернуть рабочую директорию к чистому состоянию.

Полезен, когда нужно переключиться на другую задачу, но текущие изменения ещё не готовы для коммита.

Основные команды:

- `git stash` - сохранить изменения отслеживаемых файлов, включая staged и unstaged
- `git stash -u` - дополнительно сохранить неотслеживаемые файлы
- `git stash list` - показать сохранённые состояния
- `git stash apply` - применить изменения, не удаляя stash
- `git stash pop` - применить изменения и удалить stash при успешном применении

`stash` предназначен для временного хранения, а не для долговременного управления версиями.

# Что такое `git reflog` и когда он помогает восстановить историю?

`git reflog` - локальный журнал перемещений ссылок Git, например `HEAD` и указателей веток.

Он позволяет найти предыдущие состояния репозитория даже после `reset`, `rebase` или удаления ветки.

Например:

```
git reflog
git switch -c recovery <commit-hash>
```

Так можно создать ветку на ранее существовавшем коммите и восстановить потерянную историю.

Важно: `reflog` хранится локально, не передаётся при `push` и имеет ограниченный срок хранения. После удаления записей и сборки мусора восстановление может стать невозможным.

# Как найти коммит, внёсший ошибку, через `git bisect`?

`git bisect` использует бинарный поиск по истории коммитов для обнаружения коммита, после которого появилась ошибка.

Процесс:

```
git bisect start
git bisect bad
git bisect good <known-good-commit>
```

Git переключается на промежуточный коммит. Разработчик проверяет наличие ошибки и отмечает результат:

- `git bisect good` - ошибка отсутствует
- `git bisect bad` - ошибка присутствует

Git последовательно сужает диапазон поиска, пока не определит первый проблемный коммит.

После завершения выполняют `git bisect reset`.

При условии, что ошибку можно надёжно воспроизвести, поиск занимает примерно O(log n) проверок вместо последовательного перебора всех коммитов.

# Что делают `git fetch`, `git pull` и `git push`?

`git fetch` скачивает объекты и обновляет информацию об удалённых ветках, но не объединяет их изменения с текущей локальной веткой.

`git pull` выполняет `fetch`, после чего интегрирует полученные изменения в текущую ветку через `merge` или `rebase`, в зависимости от настроек и параметров.

`git push` отправляет необходимые объекты и обновляет ссылки на ветки или теги в удалённом репозитории, если сервер разрешает обновление.

Для контроля над историей часто используют `fetch` перед явным `merge` или `rebase`.

# Чем локальная ветка отличается от remote-tracking branch?

Локальная ветка - ссылка на коммит, которой разработчик управляет непосредственно. Например, `main` или `feature/login`.

Remote-tracking branch - локальная ссылка, отражающая известное Git состояние ветки удалённого репозитория. Например, `origin/main`.

Она обычно обновляется при `git fetch` и не изменяется обычными локальными коммитами.

Локальная ветка может иметь настроенную upstream-ветку, например `origin/main`. Это позволяет Git определять, откуда получать изменения и куда отправлять их по умолчанию, а также сравнивать количество опережающих и отстающих коммитов.

# Как работает `git push --force-with-lease`?

`git push --force-with-lease` позволяет принудительно обновить удалённую ветку, но проверяет, что её состояние соответствует ожидаемому.

В отличие от `--force`, команда не должна перезаписывать новые изменения других разработчиков, если удалённая ветка изменилась с момента последнего известного состояния.

Чаще всего используется после `rebase` уже опубликованной личной ветки.

Важный нюанс: фоновый `git fetch` может обновить remote-tracking branch и ослабить стандартную проверку. Для более строгого контроля можно явно указать ожидаемый хеш:

```
git push --force-with-lease=refs/heads/feature:<expected-sha> origin feature
```

Даже с `--force-with-lease` не следует переписывать историю общей ветки без согласования с командой.

# Для чего используют interactive rebase и squash?

Interactive rebase позволяет редактировать последовательность коммитов перед публикацией или объединением ветки.

Команда `git rebase -i HEAD~N` открывает список последних `N` коммитов, где можно:

- `pick` - оставить коммит
- `reword` - изменить сообщение
- `edit` - остановиться для редактирования коммита
- `squash` - объединить коммит с предыдущим и отредактировать сообщение
- `fixup` - объединить с предыдущим, обычно отбросив сообщение текущего
- `drop` - удалить коммит из последовательности

Squash часто используют, чтобы превратить несколько промежуточных коммитов одной задачи в один логически завершённый.

Interactive rebase переписывает коммиты и меняет их хеши, поэтому безопаснее применять его к личной, ещё не используемой другими истории.

# Как сравнивать версии файлов через `git diff`?

`git diff` показывает различия между состояниями файлов, содержимым staging area и коммитами.

Основные варианты:

```
git diff
git diff --staged
git diff HEAD
git diff HEAD~1 HEAD
git diff main feature
git diff <commit1> <commit2> -- path/to/file
```

- `git diff` - изменения рабочей директории относительно staging area
- `git diff --staged` - подготовленные изменения относительно `HEAD`
- `git diff HEAD` - различия рабочей директории и `HEAD` для отслеживаемых файлов
- `git diff HEAD~1 HEAD` - изменения между двумя коммитами
- `git diff main feature` - различия между состояниями двух веток

По умолчанию неотслеживаемые файлы не отображаются в `git diff`.

# Что делает `git blame` и в чём его ограничения?

`git blame` показывает, какой коммит последним изменил каждую строку файла, а также автора и дату изменения.

Пример:

```
git blame src/app.js
```

Используется для изучения происхождения кода и поиска контекста изменений.

Ограничения:

- Показывает последнее изменение строки, а не обязательно автора исходной логики
- Массовое форматирование может скрывать значимые предыдущие изменения
- Перемещение или копирование кода между файлами может затруднять отслеживание истории

Параметры `-w`, `-M` и `-C` помогают игнорировать изменения пробелов и обнаруживать перемещённый или скопированный код.

# Как работают `.gitignore` и `git rm --cached`?

`.gitignore` содержит правила исключения неотслеживаемых файлов и директорий из обычного добавления в Git.

Чаще всего исключают `node_modules/`, временные файлы, артефакты сборки и локальные конфигурации.

Однако `.gitignore` не перестаёт отслеживать файлы, которые уже добавлены в репозиторий.

Чтобы прекратить отслеживание файла, сохранив его локально:

```
git rm --cached .env
```

Для директории:

```
git rm -r --cached directory/
```

После этого необходимо добавить соответствующее правило в `.gitignore` и создать коммит.

Важно: удаление файла из индекса не удаляет его из предыдущих коммитов.

# Как безопасно удалить секрет, случайно попавший в историю Git?

Если пароль, API-ключ или токен попал в Git, его необходимо считать скомпрометированным.

Порядок действий:

1. Немедленно отозвать или заменить секрет. Удаление из Git не делает его снова безопасным.
2. Удалить секрет из текущего состояния проекта.
3. При необходимости очистить всю историю репозитория с помощью `git filter-repo`, удалив секрет из соответствующих коммитов.
4. Согласовать переписывание истории с командой и принудительно обновить затронутые ветки и теги.
5. Проверить копии репозитория, форки, CI/CD-логи, артефакты и кеши хостинга. При необходимости запросить очистку у администратора платформы.
6. Убедиться, что секрет больше не используется, и настроить проверку секретов в репозитории.

Переписывание истории меняет хеши коммитов и может потребовать повторного клонирования репозитория участниками команды.

Главное: даже после полной очистки Git нельзя гарантировать, что секрет исчез из всех ранее созданных копий. Поэтому отзыв или ротация обязательны.

# Что такое GitFlow, trunk-based development и GitHub Flow?

Это стратегии организации веток и совместной разработки.

GitFlow - модель с несколькими долгоживущими ветками, обычно `main` и `develop`, а также отдельными `feature`, `release` и `hotfix` ветками. Подходит для проектов с формализованными релизными циклами, но усложняет интеграцию и поддержку истории.

Trunk-based development - разработка вокруг одной основной ветки (`main` или `trunk`). Изменения интегрируются часто, обычно через небольшие короткоживущие ветки. Незавершённые функции могут скрываться за feature flags.

GitHub Flow - упрощённая стратегия: создаётся feature-ветка от `main`, в неё вносятся изменения, открывается pull request, проводится проверка кода, после чего изменения объединяются с `main`. Основная ветка должна оставаться пригодной для развёртывания.

Главное различие - количество долгоживущих веток, частота интеграции и сложность релизного процесса.

# Как выбирать стратегию ветвления для команды с частыми релизами?

Для частых релизов обычно лучше подходят trunk-based development или GitHub Flow.

Основные принципы:

- Одна стабильная основная ветка
- Короткоживущие feature-ветки
- Небольшие pull/merge requests
- Автоматические тесты и CI/CD
- Feature flags для изоляции незавершённых функций
- Частая интеграция изменений для уменьшения конфликтов

Trunk-based development особенно удобен при непрерывном развёртывании и высокой автоматизации проверок.

GitHub Flow подходит, когда перед объединением изменений требуется обязательный code review.

Долгоживущие release-ветки стоит использовать, если необходимо одновременно поддерживать несколько версий продукта.

# Что такое protected branches и обязательные проверки merge request?

Protected branches - правила защиты важных веток, например `main`, от нежелательных изменений.

В зависимости от платформы и настроек они позволяют:

- Запретить прямой `push`
- Ограничить или запретить `force push` и удаление веток
- Требовать одобрение pull/merge request
- Требовать успешное прохождение CI/CD-проверок
- Ограничивать круг пользователей, имеющих право объединять изменения

Обязательные проверки merge request - условия, которые должны выполняться до объединения изменений: успешные тесты, линтеры, сборка, security checks и code review.

Они уменьшают вероятность попадания ошибок в основную ветку и обеспечивают единый процесс контроля качества.

# Для чего используют теги Git и semantic versioning?

Git tags - именованные ссылки на определённые коммиты. Обычно используются для фиксации версий и релизов.

Основные виды:

- Lightweight tag - простая ссылка на коммит
- Annotated tag - отдельный объект Git с метаданными, сообщением и возможностью криптографической подписи

Semantic Versioning (SemVer) - соглашение о нумерации версий в формате `MAJOR.MINOR.PATCH`:

- `MAJOR` - обратно несовместимые изменения публичного API
- `MINOR` - новая функциональность с сохранением обратной совместимости
- `PATCH` - обратно совместимые исправления ошибок

Например, `v2.3.1` обозначает основной релиз 2, дополнительную версию 3 и исправление 1.

Git-тег позволяет точно определить коммит релиза, а SemVer - обозначить характер изменений и ожидаемую совместимость версий.
