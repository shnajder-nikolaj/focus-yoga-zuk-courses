# Что такое конечный автомат состояний и когда использовать XState?

Конечный автомат (Finite State Machine, FSM) - модель системы, которая в каждый момент находится в одном из конечного набора состояний и переходит между ними при наступлении событий.

Основные элементы:

- States - возможные состояния системы
- Events - события, инициирующие переходы
- Transitions - правила переходов между состояниями
- Guards - условия, разрешающие переход
- Actions - действия, выполняемые при переходе или входе/выходе из состояния

Например, отправку формы можно описать переходами:

`idle → submitting → success | error`

При этом событие `SUBMIT` допустимо только в определённых состояниях, а неудачная отправка позволяет вернуться к редактированию.

XState - библиотека для управления состояниями и координации процессов на основе FSM, statecharts и модели акторов.

Statecharts расширяют классические автоматы вложенными и параллельными состояниями. В XState v5 акторы позволяют управлять асинхронными операциями и взаимодействиями между процессами.

XState полезен для сложных форм, оформления заказов, авторизации, многошаговых сценариев и процессов с отменой, тайм-аутами и повторными попытками.

Для простого локального состояния обычно достаточно `useState` или `useReducer`. XState оправдан, когда важны явные допустимые переходы и предсказуемое поведение системы.

# Что такое архитектура приложения и какие решения она фиксирует?

Архитектура приложения - совокупность структурных решений о том, как организована система, как взаимодействуют её части и какие правила ограничивают их зависимости.

Архитектура фиксирует:

- Границы модулей - разделение приложения на функциональные области
- Ответственность - какие задачи решает каждый модуль
- Зависимости - какие модули могут использовать другие
- Потоки данных - как передаются данные, события и изменения состояния
- Работу с инфраструктурой - взаимодействие с API, хранилищами и внешними сервисами
- Общие принципы - обработку ошибок, безопасность, тестируемость и расширяемость

Например, архитектурное решение может запрещать UI-компонентам обращаться к API напрямую, требуя использовать слой прикладной логики.

Главная задача архитектуры - управлять сложностью приложения и делать изменения предсказуемыми.

При этом архитектура определяет не только структуру директорий, но и правила взаимодействия компонентов системы.

# Какие признаки у хорошо разделённого на модули frontend-приложения?

Хорошая модульная архитектура характеризуется высокой связностью внутри модулей (high cohesion) и низкой связанностью между ними (low coupling).

Основные признаки:

- Единая ответственность - каждый модуль реализует определённую функциональность
- Явный публичный API - другие модули используют только предусмотренные точки входа
- Инкапсуляция - внутренние детали реализации не доступны напрямую другим модулям
- Контролируемые зависимости - отсутствуют циклические импорты и неявные связи
- Локальность изменений - изменение функциональности затрагивает минимальное количество модулей
- Независимая тестируемость - модуль можно проверять без запуска всего приложения

Например, изменение логики корзины не должно требовать изменений в компонентах авторизации или каталога, если их контракты остались прежними.

Главный практический критерий - можно ли изменить, протестировать или заменить модуль, не разбираясь во внутреннем устройстве остальных частей приложения.

# Чем feature-based структура отличается от структуры по типам файлов?

Структура по типам файлов (type-based) группирует код по техническому назначению:

```
src/
  components/
  hooks/
  services/
  types/
  utils/
```

Код одной функциональности распределяется между разными директориями.

Feature-based структура группирует код по бизнес-возможностям:

```
src/
  features/
    auth/
      components/
      hooks/
      api/
    cart/
      components/
      hooks/
      api/
```

Компоненты, логика, типы и API конкретной функциональности находятся рядом.

Преимущества feature-based подхода:

- Проще находить связанный код
- Изменения чаще локализованы внутри одной функции
- Удобнее распределять ответственность между командами
- Проще контролировать зависимости между функциональными областями

Недостаток - возможное дублирование общих решений и необходимость определять границы между features.

На практике часто используют гибридную структуру: функциональные модули содержат собственный код, а действительно общие компоненты и инфраструктура выносятся отдельно.

# Что такое separation of concerns?

Separation of Concerns (SoC) - принцип разделения системы на части, каждая из которых отвечает за отдельную область задач.

На фронтенде обычно выделяют:

- Presentation - отображение интерфейса
- Business logic - бизнес-правила и вычисления
- Data access - получение и сохранение данных
- State management - хранение и обновление состояния

Например, компонент оформления заказа отвечает за отображение формы, отдельная функция рассчитывает стоимость, а сервис взаимодействует с API.

Это позволяет изменять реализацию одного аспекта без необходимости переписывать остальные.

SoC не требует обязательного создания отдельного слоя или файла для каждой операции. Разделять следует ответственность, а не код ради самого разделения.

# Что означает dependency inversion на фронтенде?

Dependency Inversion Principle (DIP) - принцип, согласно которому высокоуровневая бизнес-логика не должна напрямую зависеть от низкоуровневых деталей реализации. Обе стороны должны зависеть от абстракций.

Например, бизнес-логика авторизации не должна быть жёстко связана с `fetch`, `axios` или конкретным HTTP API.

Вместо этого она использует интерфейс:

```
interface AuthGateway {
  login(email: string, password: string): Promise<User>
}
```

Реализация может работать с REST API, mock-сервисом или другим источником данных.

```
class AuthService {
  constructor(private gateway: AuthGateway) {}

  login(email: string, password: string) {
    return this.gateway.login(email, password)
  }
}
```

Благодаря этому бизнес-логика не меняется при замене инфраструктуры и легко тестируется через подставную реализацию.

Важно: TypeScript-интерфейсы не существуют во время выполнения. Конкретная реализация должна передаваться через конструктор, параметры функции, контекст или другой механизм связывания зависимостей.

# Чем dependency injection отличается от service locator?

Dependency Injection (DI) - зависимости передаются объекту извне, обычно через конструктор, параметры функции или props.

```
const service = new UserService(userRepository)
```

Зависимости явно видны в интерфейсе объекта.

Service Locator - объект самостоятельно запрашивает необходимые зависимости из общего реестра.

```
const service = new UserService()

// Внутри UserService:
const repository = container.get("userRepository")
```

Основные различия:

- DI - зависимости объявлены явно, поэтому проще анализировать, тестировать и заменять реализации
- Service Locator - зависимости скрыты внутри реализации и обнаруживаются только при анализе кода или выполнении

Оба подхода могут использовать контейнер зависимостей, но отличаются тем, кто отвечает за их получение.

DI обычно предпочтительнее, поскольку делает зависимости явными и снижает связанность модулей.

# Что такое MVC, MVP и MVVM и где они применимы на фронтенде?

MVC, MVP и MVVM - архитектурные паттерны разделения представления, состояния и логики взаимодействия с пользователем.

MVC (Model-View-Controller):

- `Model` - данные и бизнес-логика
- `View` - отображение
- `Controller` - обработка пользовательского ввода и координация действий

Используется в классических UI-фреймворках и серверных веб-приложениях. Конкретные реализации MVC могут различаться по тому, как View получает данные от Model.

MVP (Model-View-Presenter):

- `Model` - данные и бизнес-логика
- `View` - интерфейс, преимущественно отвечающий за отображение
- `Presenter` - обрабатывает события и управляет обновлением View через её интерфейс

Подходит для интерфейсов, где нужно отделить логику представления от конкретной UI-технологии и независимо её тестировать.

MVVM (Model-View-ViewModel):

- `Model` - данные и бизнес-логика
- `View` - отображение
- `ViewModel` - состояние и операции, необходимые представлению

View наблюдает за ViewModel, а изменения состояния отражаются в интерфейсе через реактивные механизмы или привязку данных.

MVVM особенно естественен для реактивных UI. В React близкую роль ViewModel могут выполнять custom hooks и специализированные модели состояния, хотя сам React не навязывает MVVM.

Ключевое различие - способ организации взаимодействия между UI и логикой представления.

# Как Flux организует поток данных?

Flux - архитектурный подход, основанный на однонаправленном потоке данных (unidirectional data flow).

В классическом Flux взаимодействие выглядит так:

`Action → Dispatcher → Store → View → Action`

1. Пользовательское действие создаёт `Action`.
2. `Dispatcher` передаёт событие зарегистрированным хранилищам.
3. `Store` обновляет состояние.
4. `View` получает изменения и перерисовывается.
5. Новые действия пользователя запускают следующий цикл.

Главная идея - View не изменяет состояние хранилища напрямую, а инициирует изменения через действия.

Redux развивает идею однонаправленного потока, но использует другой механизм:

`dispatch(action) → reducer → new state → UI`

В Redux нет отдельного Dispatcher в классическом понимании Flux.

Такой подход делает изменения состояния отслеживаемыми, упрощает отладку и предотвращает хаотичные двусторонние зависимости.

# Что такое hexagonal architecture и порты/адаптеры?

Hexagonal Architecture (Ports and Adapters) - архитектура, в которой бизнес-логика изолирована от внешних технологий через абстрактные интерфейсы.

Основные элементы:

- Core - доменная и прикладная логика
- Ports - контракты взаимодействия с внешним миром
- Adapters - конкретные реализации этих контрактов

Например, приложение определяет порт:

```
interface ProductRepository {
  getById(id: string): Promise<Product>
}
```

REST-адаптер реализует этот интерфейс через HTTP-запросы, а тестовый адаптер возвращает данные из памяти.

UI также может выступать входным адаптером: он вызывает прикладные операции, не определяя их внутреннюю реализацию.

Ключевой принцип - бизнес-логика не зависит от React, HTTP, браузерного хранилища или конкретного backend API.

Это позволяет менять инфраструктуру без переписывания предметной логики.

# Какие принципы DDD полезны для сложного frontend-домена?

Domain-Driven Design (DDD) - подход к проектированию ПО, при котором структура и логика системы строятся вокруг предметной области бизнеса.

Для сложного frontend-домена особенно полезны:

- Ubiquitous Language - единый язык разработчиков и экспертов предметной области
- Bounded Context - явные границы моделей и правил разных бизнес-областей
- Entities - сущности с устойчивой идентичностью, например заказ
- Value Objects - значения, определяемые своими свойствами, например денежная сумма с валютой
- Aggregates - группы связанных объектов, изменения которых контролируются общими инвариантами
- Domain Services - бизнес-операции, не принадлежащие естественным образом отдельной сущности

Например, корзина может содержать правила допустимого количества товаров, применения скидок и расчёта итоговой стоимости. Эти правила не должны быть разбросаны по React-компонентам.

DDD особенно полезен для финансовых систем, CRM, ERP и других приложений со сложными бизнес-правилами.

Для простых CRUD-интерфейсов полноценная DDD-модель часто избыточна.

# Как отделить доменные модели от API DTO?

DTO (Data Transfer Object) - структура данных, используемая для передачи информации между системами.

Доменная модель - внутреннее представление бизнес-сущности, отражающее правила и понятия предметной области.

Например, API возвращает:

```
type OrderDto = {
  order_id: string
  total_cents: number
  status: "P" | "C"
}
```

Приложение использует:

```
type Order = {
  id: string
  total: Money
  status: "pending" | "completed"
}
```

Преобразование выполняется на границе инфраструктуры:

```
function mapOrder(dto: OrderDto): Order {
  return {
    id: dto.order_id,
    total: Money.fromCents(dto.total_cents),
    status: dto.status === "P" ? "pending" : "completed",
  }
}
```

На этой границе также следует валидировать внешние данные и обрабатывать неизвестные значения.

Такое разделение позволяет:

- Не зависеть от формата конкретного API
- Использовать бизнес-термины вместо технических полей
- Централизовать преобразования и проверки
- Изменять транспортный контракт без распространения изменений по всему приложению

DTO отражает контракт передачи данных, а доменная модель - внутренний смысл данных и бизнес-правила.

# Как избегать циклических зависимостей между модулями?

Циклическая зависимость возникает, когда модули прямо или косвенно зависят друг от друга.

Например:

`auth → user → permissions → auth`

Такие зависимости затрудняют тестирование, повторное использование и изменение модулей. В JavaScript они также могут приводить к проблемам с порядком инициализации.

Основные способы предотвращения:

- Однонаправленная иерархия - зависимости направлены от верхних уровней к нижним
- Выделение общих абстракций - общие контракты и независимые функции перемещаются в отдельные модули
- Dependency inversion - модуль зависит от интерфейса, а не от конкретной реализации другого модуля
- Явные публичные API - импорты внутренних частей соседних модулей ограничиваются
- Статический анализ - ESLint, dependency-cruiser или Madge выявляют циклы

Важно не переносить весь конфликтующий код в `shared`. Общий модуль должен иметь самостоятельную ответственность.

Хорошая архитектура зависимостей образует направленный ациклический граф (DAG).

# В каких случаях паттерн repository полезен на фронтенде?

Repository - паттерн, предоставляющий интерфейс доступа к данным в терминах предметной области и скрывающий детали их хранения и получения.

Например:

```
interface UserRepository {
  findById(id: string): Promise<User | null>
  save(user: User): Promise<void>
}
```

Бизнес-логика работает с `UserRepository`, не зная, используются ли REST API, IndexedDB или локальный mock.

Repository полезен, когда:

- Существуют разные источники данных
- Требуется offline-first поведение
- Нужно изолировать бизнес-логику от API
- Необходимо преобразовывать DTO в доменные модели
- Требуются подменяемые реализации для тестирования

При этом Repository не обязательно должен управлять кэшированием. Оно может находиться в отдельном инфраструктурном механизме, например TanStack Query.

Если приложение выполняет несколько простых CRUD-запросов, дополнительный слой Repository часто не приносит пользы. Достаточно API-клиента или специализированных функций получения данных.

# Что такое anti-corruption layer при интеграции с внешним API?

Anti-Corruption Layer (ACL) - архитектурный слой, защищающий внутреннюю доменную модель от особенностей и ограничений внешней системы.

Он преобразует внешние данные и операции во внутренние понятия приложения.

Например, внешняя CRM возвращает:

```
{
  client_type: 2,
  active_flag: "Y"
}
```

ACL преобразует их в доменную модель:

```
{
  type: "company",
  isActive: true
}
```

Кроме преобразования полей ACL может:

- Согласовывать различия в бизнес-терминах
- Преобразовывать единицы измерения и статусы
- Обрабатывать несовместимые модели ошибок
- Адаптировать внешние операции к внутренним сценариям
- Скрывать особенности версионирования внешнего API

Отличие от обычного DTO-маппера - ACL защищает не только структуру данных, но и семантику бизнес-модели.

Особенно полезен при интеграции с legacy-системами, сторонними сервисами и API с моделью данных, существенно отличающейся от внутренней.

# Как принимать архитектурные решения при несовместимых требованиях?

Архитектурные решения часто требуют компромиссов между производительностью, простотой, стоимостью разработки, безопасностью и масштабируемостью.

Процесс принятия решения:

1. Определить ограничения - какие требования обязательны, а какие допускают компромиссы
2. Установить приоритеты - какие характеристики важнее для продукта
3. Сравнить альтернативы - оценить преимущества, недостатки и последствия
4. Проверить риски - использовать прототипы, измерения и технические эксперименты
5. Выбрать решение - принять компромисс с учётом текущих условий
6. Зафиксировать причины - документировать предположения и ограничения

Например, сложная система кэширования может повысить производительность, но одновременно увеличить риск несогласованности данных.

Если приложение работает с финансовыми операциями, корректность данных может быть важнее минимальной задержки интерфейса.

Хорошее архитектурное решение не обязано быть оптимальным по всем параметрам. Оно должно удовлетворять ключевым требованиям при приемлемой стоимости и рисках.

# Что такое ADR и когда стоит фиксировать решения письменно?

ADR (Architecture Decision Record) - документ, фиксирующий значимое архитектурное решение и причины его принятия.

Обычно содержит:

- Context - проблема, требования и ограничения
- Decision - выбранное решение
- Alternatives - рассмотренные варианты
- Consequences - преимущества, недостатки и риски
- Status - состояние решения: proposed, accepted, deprecated или superseded

Например, ADR может объяснять, почему команда выбрала TanStack Query вместо собственного механизма серверного кэширования.

ADR полезен, когда решение:

- Влияет на несколько модулей или команд
- Сложно изменить после внедрения
- Предполагает существенные компромиссы
- Может вызвать вопросы у будущих разработчиков

ADR не должен превращаться в подробную документацию всей системы.

Его задача - сохранить контекст принятия решения, чтобы в будущем было понятно не только что сделали, но и почему.

# Как оценить стоимость усложнения архитектуры?

Стоимость архитектуры определяется не только объёмом кода, но и затратами на понимание, развитие и сопровождение системы.

Следует учитывать:

- Cognitive complexity - насколько сложно разработчикам понимать взаимодействие частей системы
- Development cost - сколько дополнительного кода и времени требует архитектура
- Maintenance cost - сколько стоит изменение существующей функциональности
- Testing cost - сколько инфраструктуры и проверок необходимо
- Integration cost - насколько сложно подключать новые модули
- Operational cost - какие дополнительные расходы возникают при эксплуатации

Например, внедрение отдельного слоя use cases, repositories и adapters для простого CRUD-приложения может увеличить количество файлов и абстракций без заметной пользы.

При этом для сложной бизнес-системы те же слои могут снизить стоимость будущих изменений.

Оценивать следует совокупную стоимость владения (TCO):

`TCO = разработка + сопровождение + эксплуатация + стоимость изменений`

Это концептуальная модель, а не точная формула расчёта.

Основной критерий - оправдывает ли снижение будущих рисков и затрат дополнительную сложность сегодня.

# Чем композиция отличается от наследования?

Наследование (Inheritance) - механизм, при котором новый класс расширяет или переопределяет поведение существующего класса.

Композиция (Composition) - построение сложного объекта или поведения из независимых частей.

Наследование:

```
class AdminButton extends Button {
  // Дополнительное поведение
}
```

Композиция в React:

```
function AdminButton() {
  return (
    <Button>
      Admin
    </Button>
  )
}
```

При наследовании дочерний класс зависит от реализации и контракта родительского класса.

При композиции поведение формируется через компоненты, props, hooks или переданные зависимости.

Преимущества композиции:

- Меньшая связанность реализаций
- Возможность комбинировать поведение
- Локальное изменение отдельных частей
- Отсутствие сложных иерархий наследования

В React композиция обычно предпочтительнее наследования для повторного использования UI и поведения.

Наследование остаётся полезным там, где действительно существует устойчивая иерархия типов с корректным отношением «является разновидностью».

# Что такое паттерны Factory, Strategy, Adapter и Observer?

Factory - инкапсулирует создание объектов, скрывая выбор конкретной реализации и детали инициализации.

```
function createLogger(env: string) {
  return env === "production"
    ? new RemoteLogger()
    : new ConsoleLogger()
}
```

Полезен, когда создание объектов зависит от конфигурации или требует сложной настройки.

Strategy - определяет семейство взаимозаменяемых алгоритмов с общим интерфейсом.

Например, разные стратегии расчёта стоимости доставки.

Позволяет изменять алгоритм без изменения кода, который его использует.

Adapter - преобразует интерфейс одного объекта в интерфейс, ожидаемый другим кодом.

Например, адаптер стороннего API приводит данные и операции к внутреннему контракту приложения.

Observer - организует зависимость «источник - подписчики», при которой подписчики получают уведомления об изменениях источника.

Применяется в системах событий, реактивных хранилищах и механизмах подписки.

Различие по назначению: Factory создаёт объекты, Strategy выбирает поведение, Adapter согласует интерфейсы, Observer распространяет уведомления.

# Где паттерн Observer встречается в браузере и React?

Observer позволяет объектам подписываться на изменения источника и получать уведомления при наступлении событий.

В браузере он встречается в:

- `addEventListener()` - подписка на DOM-события
- `MutationObserver` - наблюдение за изменениями DOM
- `ResizeObserver` - отслеживание изменения размеров элементов
- `IntersectionObserver` - отслеживание пересечения элемента с областью наблюдения

В React похожие механизмы используются при работе с внешними хранилищами состояния.

Например:

```
const state = useSyncExternalStore(
  store.subscribe,
  store.getSnapshot
)
```

`store.subscribe` регистрирует подписчика, а `getSnapshot` позволяет React получить актуальное состояние.

React самостоятельно организует обновление компонентов при изменении их state, props или context. Это реактивный механизм, но его не следует считать буквальной реализацией классического Observer на уровне каждого компонента.

При использовании подписок важно освобождать ресурсы: удалять обработчики событий, отключать наблюдателей и отписываться от хранилищ.

# Как применять Strategy при различиях в бизнес-правилах?

Strategy полезен, когда одна бизнес-операция имеет несколько вариантов реализации.

Например, расчёт скидки зависит от типа клиента:

```
interface DiscountStrategy {
  calculate(total: number): number
}

class RegularDiscount implements DiscountStrategy {
  calculate(total: number) {
    return total
  }
}

class VipDiscount implements DiscountStrategy {
  calculate(total: number) {
    return total * 0.9
  }
}
```

Использующий код работает с общим интерфейсом:

```
function calculatePrice(
  total: number,
  strategy: DiscountStrategy
) {
  return strategy.calculate(total)
}
```

Конкретная стратегия выбирается при сборке или выполнении сценария.

Преимущества:

- Разные бизнес-правила изолированы друг от друга
- Новые алгоритмы добавляются без изменения основного расчёта
- Каждую стратегию можно тестировать отдельно
- Уменьшается количество условных ветвлений внутри алгоритмов

Strategy оправдан, когда различия устойчивы и имеют самостоятельную логику.

Для двух простых условий обычный `if` часто понятнее, чем дополнительная система интерфейсов и классов.

# Что такое Command и где он полезен в UI?

Command - поведенческий паттерн, представляющий операцию как отдельный объект с данными и логикой выполнения.

Например:

```
interface Command {
  execute(): void
  undo(): void
}
```

Команда изменения текста может сохранять предыдущее и новое значения, чтобы поддерживать выполнение и отмену операции.

Command полезен в UI для:

- Undo/Redo - отмены и повторного выполнения действий
- Истории операций - записи последовательности изменений
- Очередей команд - отложенного выполнения действий
- Горячих клавиш - связывания разных способов ввода с одной операцией
- Макросов - объединения нескольких команд в последовательность

Например, графический редактор может представлять перемещение объекта, изменение размера и удаление как отдельные команды.

Важно различать `undo` и повторную отправку команды: отмена требует обратной операции или восстановления состояния, а повторное выполнение может создавать дополнительные побочные эффекты.

Главное преимущество - операция отделяется от UI-элемента, который её инициировал.

# Как работает state machine для сложного пользовательского сценария?

State machine моделирует пользовательский сценарий через набор состояний, событий и допустимых переходов между ними.

Например, процесс оформления заказа:

```
cart
  ↓ CHECKOUT
checkout
  ↓ SUBMIT
processing
  ├── SUCCESS → completed
  └── FAILURE → failed
                   ↓ RETRY
                 processing
```

В состоянии `processing` повторная отправка заказа может быть запрещена, а переход к `completed` разрешён только после подтверждения результата операции.

Для сложных сценариев используются дополнительные механизмы:

- Guards - проверяют условия переходов
- Actions - выполняют действия при переходах
- Context - хранит дополнительные данные сценария
- Nested states - группируют вложенные состояния
- Parallel states - моделируют независимые процессы
- Invoked actors - управляют асинхронными операциями и их жизненным циклом

Например, при выходе из состояния `processing` можно остановить связанную асинхронную операцию, если она поддерживает отмену.

В XState v5 машина описывается через `createMachine` или `setup(...).createMachine`, а выполняется актором, созданным через `createActor`.

Основное преимущество - допустимые действия определяются текущим состоянием, а невозможные переходы не нужно предотвращать множеством разрозненных проверок.

Это особенно важно, когда комбинации независимых boolean-флагов начинают создавать противоречивые состояния интерфейса.

# Что такое инверсия управления?

Inversion of Control (IoC) - принцип, при котором управление созданием объектов или выполнением определённых частей программы передаётся внешнему механизму.

При обычном подходе приложение самостоятельно управляет вызовами и зависимостями.

При IoC часть управления получает фреймворк, контейнер или другой внешний компонент.

Например, в React:

```
function App() {
  const [count, setCount] = useState(0)

  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  )
}
```

Разработчик описывает компонент, но React управляет его вызовами, обновлениями и жизненным циклом.

Другие примеры IoC:

- Dependency Injection - создание и предоставление зависимостей контролируется внешним кодом
- Event handlers - браузер вызывает обработчики при наступлении событий
- Lifecycle hooks - фреймворк определяет, когда выполняется пользовательский код

Dependency Injection - один из способов реализации IoC, но не его синоним.

Основная идея IoC - отделить пользовательскую логику от механизма управления её выполнением.

# Как применять KISS, DRY и YAGNI?

KISS (Keep It Simple, Stupid) - выбирать наиболее простое решение, которое корректно удовлетворяет требованиям.

Например, не внедрять сложную state machine для обычного переключателя, если достаточно `useState`.

DRY (Don't Repeat Yourself) - избегать дублирования знаний и правил внутри системы.

Если одно бизнес-правило расчёта комиссии реализовано в нескольких местах, его изменение потребует синхронного обновления всех реализаций.

Правило следует централизовать.

YAGNI (You Aren't Gonna Need It) - не реализовывать функциональность и абстракции, необходимость которых пока не подтверждена.

Например, не создавать универсальную систему плагинов ради одной существующей интеграции.

Различия:

- KISS минимизирует ненужную сложность
- DRY предотвращает дублирование знаний
- YAGNI предотвращает преждевременную реализацию возможностей

Эти принципы необходимо применять совместно. Излишняя абстракция ради DRY может нарушать KISS и YAGNI.

# Почему чрезмерный DRY может ухудшить архитектуру?

DRY направлен на устранение дублирования знаний, а не любого визуально похожего кода.

Два фрагмента могут выглядеть одинаково, но принадлежать разным бизнес-контекстам и изменяться независимо.

Например, формы регистрации и оформления заказа могут использовать одинаковые поля и проверки. Однако в будущем их бизнес-правила могут разойтись.

Если преждевременно объединить их в универсальный компонент, появятся:

- Большое количество условных props
- Сложные конфигурации
- Зависимости между независимыми функциональностями
- Риск сломать один сценарий при изменении другого

Это называют неудачной абстракцией (wrong abstraction).

Иногда небольшое дублирование проще поддерживать, чем универсальный механизм с множеством исключений.

Практическое правило: объединять стоит код, который выражает одно и то же знание и должен изменяться по одной причине.

Если фрагменты похожи только технически, их независимость может быть архитектурно правильной.

# Что такое чистая архитектура и как понять её границы на фронтенде?

Clean Architecture - архитектурный подход, при котором бизнес-правила отделены от деталей UI, баз данных, API и фреймворков.

Ключевой принцип - Dependency Rule: зависимости исходного кода направлены внутрь, к более устойчивым бизнес-правилам.

На фронтенде можно выделить:

- Domain - сущности, бизнес-правила и инварианты
- Application - прикладные сценарии (use cases), координирующие бизнес-операции
- Interface Adapters - преобразование данных и согласование контрактов
- Frameworks & Infrastructure - React, HTTP-клиенты, браузерные API и другие технические реализации

Например:

`React Component → Checkout Use Case → Payment Port`

Конкретный адаптер `PaymentApiAdapter` реализует порт и обращается к серверу.

Важно, что прикладная логика знает контракт `Payment Port`, но не зависит от реализации `PaymentApiAdapter`.

Границы проходят там, где различаются ответственность и причины изменения кода.

Например, изменение дизайна формы не должно затрагивать расчёт стоимости заказа, а замена API-клиента не должна требовать изменения бизнес-правил.

Для простого приложения необязательно создавать все слои физически. Clean Architecture задаёт направление зависимостей, а не обязательное количество директорий и интерфейсов.

# Чем императивный UI отличается от декларативного?

Императивный подход описывает последовательность действий, необходимых для изменения интерфейса.

```
const button = document.querySelector("button")!

button.textContent = "Loading..."
button.setAttribute("disabled", "true")
```

Разработчик самостоятельно управляет состоянием DOM.

Декларативный подход описывает, каким должен быть интерфейс при определённом состоянии.

```
function SubmitButton({ loading }: { loading: boolean }) {
  return (
    <button disabled={loading}>
      {loading ? "Loading..." : "Submit"}
    </button>
  )
}
```

React вычисляет необходимое обновление интерфейса при изменении состояния.

Преимущества декларативного подхода:

- UI предсказуемо зависит от состояния
- Меньше ручных операций с DOM
- Проще описывать сложные комбинации состояний
- Легче тестировать отображение

При этом декларативный UI не исключает императивный код.

Например, управление фокусом, прокруткой, Canvas или сторонними DOM-библиотеками часто требует использования `refs` и эффектов.

Основное различие: императивный подход описывает как изменить UI, декларативный - каким UI должен быть.

# Когда использовать event-driven подход внутри приложения?

Event-driven architecture - подход, при котором компоненты системы взаимодействуют через события, сигнализирующие о произошедших изменениях или действиях.

Например, после успешного оформления заказа публикуется событие:

```
eventBus.emit("order:completed", {
  orderId: "123"
})
```

На него могут независимо реагировать аналитика, уведомления и другие части приложения.

Event-driven подход полезен, когда:

- На одно событие должны реагировать несколько независимых модулей
- Отправитель не должен знать конкретных получателей
- Нужна асинхронная или отложенная обработка
- Существуют сложные интеграционные взаимодействия

Однако события создают неявные зависимости: по коду отправителя не всегда понятно, какие обработчики выполнятся.

Также появляются вопросы порядка обработки, повторных событий, ошибок и очистки подписок.

Для простого взаимодействия между двумя компонентами прямой вызов функции или передача callback обычно понятнее.

Event-driven подход оправдан, когда независимость участников важнее простоты прямого взаимодействия.

# Как организовать отмену и повторяемость пользовательских операций?

Для управления операциями необходимо разделять отмену выполнения, отмену результата (undo) и повторный запуск (retry).

1\. Отмена асинхронной операции

Для HTTP-запросов через `fetch` используется `AbortController`:

```
const controller = new AbortController()

fetch("/api/orders", {
  signal: controller.signal
})

// Отмена запроса
controller.abort()
```

Это прерывает клиентскую операцию, но не гарантирует, что сервер прекратил обработку запроса.

2\. Повторный запуск

Для retry необходимо учитывать:

- Idempotency - повторная операция не должна создавать нежелательные дополнительные эффекты
- Retry limits - ограничение количества попыток
- Exponential backoff - увеличение задержки между попытками
- Error classification - повторять только ошибки, для которых это имеет смысл

Для создания заказов и платежей особенно важны idempotency keys, поддерживаемые сервером.

3\. Отмена результата (Undo)

Для локальных операций можно использовать Command с обратным действием или хранить предыдущие состояния.

Для уже выполненной серверной операции может потребоваться отдельное компенсирующее действие, например отмена созданного заказа.

4\. Управление состояниями

Операцию удобно моделировать состояниями:

`idle → running → success | error | cancelled`

Это предотвращает повторные нажатия, некорректные переходы и конфликтующие обновления интерфейса.

# Как моделировать неизменяемое доменное состояние?

Immutable state - состояние, которое не изменяется напрямую. Вместо мутации существующего значения создаётся новое состояние.

Например:

```
type Cart = {
  readonly items: readonly CartItem[]
  readonly total: number
}

function addItem(cart: Cart, item: CartItem): Cart {
  return {
    ...cart,
    items: [...cart.items, item],
    total: cart.total + item.price,
  }
}
```

Исходный объект `cart` остаётся неизменным, а функция возвращает новую версию состояния.

Преимущества:

- Предсказуемые изменения
- Упрощение тестирования
- Удобная история состояний и Undo/Redo
- Возможность сравнивать состояния по ссылкам
- Снижение риска непредвиденных побочных эффектов

Для сложных вложенных структур можно использовать Immer, который позволяет писать код в стиле мутаций, но формирует новое состояние с сохранением неизменённых частей.

Важно учитывать, что `readonly` в TypeScript обеспечивает только статическую проверку типов и не делает объект неизменяемым во время выполнения.

Также следует защищать доменные инварианты. Например, состояние корзины должно обновляться через операции, которые гарантируют корректность количества товаров и итоговой стоимости.

Неизменяемость гарантирует отсутствие прямых изменений существующего состояния, но сама по себе не гарантирует корректность бизнес-правил.

# Что такое технический долг и как его измерять?

Технический долг (Technical Debt) - дополнительные будущие затраты и риски, возникающие из-за технических решений, которые затрудняют развитие и сопровождение системы.

Примеры:

- Сильная связанность модулей
- Дублирование бизнес-логики
- Отсутствие необходимых тестов
- Устаревшие зависимости
- Сложные компоненты с большим количеством обязанностей
- Недостаточная автоматизация разработки и поставки

Технический долг может быть осознанным компромиссом ради быстрого выпуска продукта или следствием некачественных решений.

Измерять его можно через косвенные показатели:

- Lead time for changes - время прохождения изменения от начала работы до выпуска
- Change failure rate - доля изменений, приводящих к сбоям
- Defect rate - частота обнаружения дефектов
- Code churn - частота повторных изменений одних и тех же участков кода
- Dependency risks - количество и критичность проблемных зависимостей
- Maintenance effort - время, затрачиваемое на исправления и сопровождение

Эти показатели не измеряют технический долг напрямую: на них влияют сложность задач, организация команды и другие факторы.

Поэтому полезно фиксировать конкретные проблемы, оценивать их влияние на разработку и наблюдать, как меняются затраты на работу с соответствующими частями системы.

Главный признак технического долга - существующие технические решения систематически увеличивают стоимость или риск будущих изменений.
