# Какие этапы проходит HTTP-запрос от приёма соединения до завершения ответа backend?

Сервер принимает соединение или запрос в уже существующем соединении, разбирает HTTP headers и поток тела, выбирает route и выполняет обработчики. Затем приложение вызывает зависимости, формирует status/headers и передаёт body с учётом backpressure.

После завершения очищают request-specific ресурсы и фиксируют telemetry. Соединение может остаться открытым для следующих запросов; при HTTP/2 несколько streams используют одно соединение. Жизненный цикл HTTP-запроса не равен жизненному циклу socket, а разбор большого body может идти одновременно с получением данных.

# Как keep-alive, connection reuse и ограничения соединений влияют на HTTP-сервер?

Keep-alive позволяет повторно использовать соединение и экономит установление TCP/TLS. При этом idle sockets расходуют ресурсы, а слишком короткое удержание увеличивает число соединений и риск ошибок при несовпадении ожиданий клиента и proxy.

Ограничивают число соединений, idle timeout, число запросов и доступную конкурентность. Для HTTP/2 отдельно учитывают multiplexed streams. Больше соединений не всегда означает больше throughput: bottleneck может находиться в БД, CPU или очереди приложения. Измеряют отказы, занятость и задержку ожидания соединения.

# Почему порядок parsing, authentication, authorization и middleware меняет поведение API?

Каждый middleware работает с тем состоянием запроса, которое подготовлено раньше. Authentication может читать headers до body parsing, но проверка подписи webhook может требовать именно raw body, которое parser уже изменил. Authorization должна предшествовать защищённому действию.

Сначала полезно применять дешёвые ограничения размера и нагрузки, затем только необходимые преобразования. Error handler должен покрывать ошибки предыдущих этапов. Единого обязательного порядка для всех API нет: его определяют данные проверки, побочные эффекты и контракт framework.

# Как ограничивать размер, длительность и сложность обработки входящего HTTP-запроса?

Ограничивают размер headers и body, время их получения, количество multipart parts, распакованный размер, сложность JSON и число активных запросов. Для медленных клиентов нужны временные ограничения чтения, для дорогих операций — общий execution budget.

Лимит в reverse proxy дополняют ограничениями приложения, поскольку до сервиса могут существовать другие пути. `Content-Length` нельзя считать единственным контролем: есть streaming и другие формы передачи. После отказа корректно завершают или освобождают поток, чтобы не оставить незавершённый запрос и ресурсы.

# Почему нужно проверять Content-Type и различать malformed body и бизнес-ошибку?

`Content-Type` определяет ожидаемый parser и семантику тела. Неподдерживаемый формат можно отклонить как `415`, синтаксически неверный JSON — как `400`; структурно корректные данные, нарушающие правила операции, получают согласованный ответ согласно контракту API.

Не следует угадывать формат по содержимому и обрабатывать любой текст как JSON. Отдельно проверяют charset, compressed input и ограничения parser. Бизнес-отказ не должен маскироваться под внутренний `500`, а client error не доказывает отсутствие всех ранее совершённых действий.

# Как централизованно преобразовывать исключения в HTTP-ответы с устойчивым контрактом?

Ожидаемые ошибки классифицируют доменными или application-кодами, а транспортная граница переводит их в согласованные HTTP-статусы и тела. Непредвиденную ошибку логируют с correlation identifier и возвращают безопасный внутренний отказ без stack trace.

Можно использовать **Problem Details** с машинно различимым типом ошибки и контролируемыми расширениями. Клиент не должен разбирать произвольное сообщение. Централизация не означает один статус на все случаи: она обеспечивает единые правила и исключает двойную отправку ответа. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html).

# Что делать, если ошибка возникла после отправки HTTP headers или части тела?

После отправки headers нельзя надёжно заменить status и начать обычный JSON-ответ с ошибкой. Для streaming-протокола можно передать предусмотренное событие ошибки или финальный status, если формат и транспорт это допускают; иначе поток завершают с признаком обрыва.

Ошибку логируют вместе с тем, сколько ответа уже отправлено. Клиент должен отличать завершённый результат от частичного. Повторная попытка записать headers создаёт вторую ошибку и скрывает первоначальную причину. В Express такой путь учитывает `res.headersSent` и поведение error handler.

# Как отменять работу backend после disconnect клиента и освобождать ресурсы запроса?

Сигнализируют отмену request context и передают её в поддерживающие API БД, HTTP-клиенты и внутренние задачи. В `finally` освобождают permits, timers, streams и соединения. События завершения нужно трактовать по API: нормальное закрытие потока не всегда означает disconnect.

Например, преждевременное завершение response можно отличать от штатного через состояние записи framework/runtime. Отмена ожидания не откатывает уже выполненную транзакцию. Если работу нужно довести до конца независимо от клиента, её оформляют как надёжную фоновую операцию.

# Как graceful shutdown прекращает приём запросов и завершает активную работу?

Сначала экземпляр снимают с готовности и прекращают приём новой работы, затем дожидаются активных запросов и остановки workers в пределах общего срока. После этого закрывают clients и pools, сбрасывают telemetry и завершают процесс; по истечении срока применяют оговорённое принудительное завершение.

Сочетают draining балансировщика и поведение runtime. В Node.js `server.close()` прекращает новые соединения и в современных версиях закрывает idle HTTP-соединения, но WebSocket и другие долгоживущие протоколы требуют отдельного учёта. [HTTP server shutdown Node.js](https://nodejs.org/api/http.html#serverclosecallback).

# Как согласовать timeout reverse proxy, HTTP-сервера и downstream-зависимостей?

Внутренние бюджеты выстраивают так, чтобы downstream успел завершиться или отмениться до окончания обработки приложения, а приложение — сформировать ответ до внешнего deadline клиента или proxy. Учитывают время очередей, retries, сериализации и передачи.

Значения нельзя сравнивать без семантики: proxy idle timeout и общий execution deadline ограничивают разное. Streaming endpoint может требовать отдельной политики. Если proxy закрыл соединение раньше, backend должен заметить отмену, иначе продолжит занимать ресурсы для уже бесполезного ответа.

# Как настройки trusted proxy влияют на client IP, scheme, cookies и rate limiting?

За reverse proxy backend может видеть адрес и HTTP scheme самого proxy. Поддерживаемые forwarding headers помогают восстановить client IP и внешний HTTPS, но доверять им можно только от проверенной proxy-цепочки, которая удаляет или перезаписывает клиентские значения.

Слишком широкое доверие позволяет подменить IP для rate limiting, исказить absolute URLs и поведение secure cookies. Фиксированное число hops тоже опасно при маршрутах разной длины. Настройку проверяют на реальной топологии и прямом доступе к сервису. [Express behind proxies](https://expressjs.com/en/guide/behind-proxies/).

# Какие данные запроса логировать для диагностики и как избежать утечки чувствительных значений?

Обычно полезны request/trace identifier, метод, route template, status, длительность, размер ответа, версия приложения и классификация ошибки. Route template предпочтительнее сырого URL для метрик: уникальные идентификаторы повышают cardinality.

Authorization, cookies, токены, пароли и персональные поля удаляют или маскируют. Query string и body не логируют целиком без обоснованной политики. Не доверяют произвольному внешнему correlation header и ограничивают длину значений. Доступ, retention и sampling логов выбирают по диагностической задаче и чувствительности данных.
