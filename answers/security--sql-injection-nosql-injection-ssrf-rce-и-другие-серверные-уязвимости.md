# Почему parameterized queries защищают от SQL Injection и где всё ещё нужны allowlists?

Parameterized query отделяет SQL-структуру от значений: `WHERE user_id = $1` передаёт значение через bind API, и оно не становится SQL-синтаксисом. Конкатенация до подготовки запроса лишает этот механизм смысла. ORM и stored procedure также уязвимы, если внутри строят SQL из недоверенных строк.

Параметр обычно не заменяет имя таблицы, column или направление сортировки. Такие варианты сопоставляют с фиксированными разрешёнными конструкциями на сервере. Least privilege ограничивает последствия, а object authorization отдельно определяет право прочитать найденную строку. [OWASP: SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).

# Как предотвратить NoSQL Injection при построении фильтров из входного JSON?

В document query значение может само быть объектом с операторами. Поэтому передача клиентского JSON прямо в фильтр опасна даже без конкатенации строк. Для ожидаемого имени проверяют, что получен scalar string, а не произвольная структура.

Сервер явно строит фильтр из разрешённых полей и операций, проверяет типы, глубину и размеры. Не принимает raw expressions или произвольные update operators без отдельного контракта. ODM не заменяет эту проверку; дополнительные ограничения execution features и прав БД уменьшают последствия. [OWASP: NoSQL Security](https://cheatsheetseries.owasp.org/cheatsheets/NoSQL_Security_Cheat_Sheet.html).

# Как защищать серверные HTTP-запросы от SSRF с учётом DNS, redirects и egress?

**SSRF** возникает, когда клиент управляет обращением, которое сервер выполняет со своей сетевой доступностью. Если destinations известны, используют точный allowlist hosts, schemes и ports. URL разбирают одним согласованным parser, а фактическое соединение ограничивают разрешённым назначением.

Для произвольных внешних URL исключают private, loopback, link-local и другие запрещённые адреса IPv4/IPv6. Учитывают все DNS-ответы и смену разрешения между проверкой и соединением; redirects отключают либо проверяют каждый переход. Egress proxy и network policy дополнительно блокируют внутренние services и metadata endpoints. Ограничивают размер ответа и timeout. [OWASP: SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

# Почему передача пользовательских данных в shell создаёт Command Injection и риск RCE?

Shell интерпретирует управляющие символы и подстановки, поэтому строка с пользовательским значением может изменить смысл запуска. Предпочтительнее библиотечный API, например файловая операция вместо вызова системной утилиты.

Если процесс необходим, исполняемый файл выбирает сервер, а arguments передают отдельно без shell. Аргументы всё равно валидируют: отдельная строка может оказаться опасной опцией самой программы. Ограничивают поддерживаемые операции, environment, privileges, доступ к files и сети, время и объём вывода. Самодельное quoting не даёт универсальной защиты для разных shells. [OWASP: OS Command Injection Defense](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html).

# Как отличить безопасный template rendering от Server-Side Template Injection?

При безопасном rendering template является доверенным кодом, а пользовательские значения передаются как данные. **SSTI** появляется, когда эти значения включаются в template source, повторно интерпретируются как выражение либо выбирают произвольный template или include path.

Шаблоны хранят и проверяют как код, выбор template ограничивают server-side mapping, render context делают минимальным. HTML escaping защищает вывод от части XSS, но не предотвращает выполнение template language. Если пользователь должен создавать шаблоны, необходимы ограниченный язык и изоляция; наличие sandbox не является универсальной гарантией. [OWASP: SSTI Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Template_Injection_Prevention_Cheat_Sheet.html).

# Как небезопасная десериализация создаёт выполнение кода и как уменьшить этот риск?

Некоторые deserializers восстанавливают классы, вызывают hooks или исполняют выражения. При недоверенном input это может запустить нежелательную цепочку действий с полномочиями сервиса. Подпись payload полезна только при корректной модели доверия к его создателю и сохранности ключей.

Для обмена предпочитают данные ограниченной схемы, не автоматическое восстановление произвольных объектов. Ограничивают типы, глубину, размер и пользовательские constructors. Например, Python pickle не используют для недоверенных данных. Безопасный JSON parser тоже не заменяет последующую schema validation и защиту от чрезмерной нагрузки. [OWASP: Deserialization](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html).

# Как предотвращать path traversal при работе с файлами и распаковке архивов?

Сервер связывает публичный file ID с собственным именем и разрешённым storage root. Если input всё же содержит путь, проверяют компоненты и итоговое разрешение относительно root, учитывая абсолютные paths, платформенные особенности и symlinks. Простое сравнение строкового prefix недостаточно.

При распаковке проверяют каждую entry до записи: destination должен оставаться внутри каталога, а links не должны создавать обход. Отдельно ограничивают число files и распакованный объём. Между проверкой и открытием возможна гонка; применяют безопасные операции с directory handles и запрет следования links там, где доступны. [MITRE CWE-22](https://cwe.mitre.org/data/definitions/22.html).

# Как проверять uploads и обработчики медиа, чтобы не допустить серверной компрометации?

Allowlist форматов и проверка содержимого дополняют проверку extension: клиентский `Content-Type` нельзя считать доказательством типа. Сервер назначает storage name, ограничивает размер и не сохраняет файл как исполняемый контент в доступном webroot.

Media processing выполняют обновлёнными parsers в ограниченном окружении без ненужных credentials и сети. Лимитируют dimensions, decompressed size, CPU и memory. Антивирус или повторное кодирование уменьшают отдельные риски, но не доказывают безопасность любого файла. Проверяют также authorization загрузки, скачивания и дальнейшей обработки. [OWASP: File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

# Как prototype pollution влияет на Node.js backend и как защищать операции merge?

Prototype pollution изменяет свойства, которые другие объекты могут унаследовать. На backend это способно повлиять на authorization defaults, options библиотек или обработку запроса; конкретный ущерб зависит от доступного опасного использования этих свойств.

Не выполняют произвольный deep merge недоверенной структуры в application objects. Используют schema с разрешёнными fields, безопасные обновлённые merge implementations, `Map` или objects без prototype для словарей и проверки собственных properties. Запрет `__proto__` сам по себе не покрывает все пути, включая `constructor.prototype`. Проверяют источник изменения и места, где загрязнённые данные используются. [OWASP: Prototype Pollution Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Prototype_Pollution_Prevention_Cheat_Sheet.html).

# Как подтвердить исправление серверной уязвимости и исключить похожие обходные пути?

В контролируемом окружении фиксируют минимальный сценарий, демонстрирующий нарушенную границу: данные интерпретируются как код, запрос достигает запрещённого адреса или файл выходит за storage root. После исправления сценарий должен завершаться безопасно, а разрешённая функция — продолжать работать.

Проверяют альтернативные endpoints, background jobs, вторичное использование сохранённых данных и parser differences. Нужен regression test на класс ошибки и review похожих мест. WAF rule или изоляция процесса могут временно уменьшить риск, но не подтверждают устранение причины. В отчёт включают проверенную версию и остаточные ограничения.
