# Чем синхронное выполнение отличается от асинхронного?

Синхронное выполнение - инструкции выполняются последовательно, и следующая операция начинается только после завершения предыдущей. Длительная операция блокирует дальнейшее выполнение кода в текущем потоке.

Асинхронное выполнение - позволяет инициировать операцию и продолжить выполнение другого кода, не дожидаясь её результата. Когда результат становится доступен, обработка продолжается через callback, Promise или `async/await`.

В JavaScript асинхронность обеспечивается взаимодействием движка с окружением (браузером или Node.js), которое обрабатывает таймеры, сетевые запросы и другие операции.

Важно: асинхронность сама по себе не означает выполнение JavaScript-кода в нескольких потоках.

# Как связаны call stack, task queue и event loop?

Эти механизмы координируют выполнение синхронного и асинхронного JavaScript-кода.

- Call stack - стек вызовов, в котором находятся выполняющиеся функции.
- Task queue - очередь задач, готовых к выполнению, например callbacks таймеров или событий.
- Event loop - механизм, который организует выполнение задач, микрозадач и, в браузере, обновление интерфейса.

Упрощённый цикл работы браузера:

1. Выполняется текущий JavaScript-код в call stack.
2. После завершения текущей задачи обрабатываются все доступные microtasks.
3. Браузер может выполнить обновление интерфейса.
4. Event loop выбирает следующую задачу и повторяет процесс.

Ключевой принцип: пока выполняется синхронный код, callbacks из очередей не могут прервать его выполнение.

В Node.js event loop имеет несколько фаз, поэтому детали обработки очередей отличаются от браузера.

# Чем microtask queue отличается от task queue?

Task queue содержит обычные задачи (tasks), например callbacks `setTimeout`, `setInterval` и пользовательских событий.

Microtask queue содержит микрозадачи, включая обработчики `Promise.then`, `Promise.catch`, `Promise.finally` и callbacks `queueMicrotask`.

Главное отличие - приоритет выполнения:

- После завершения текущего кода выполняются все доступные микрозадачи.
- Только после опустошения microtask queue event loop может перейти к следующей обычной задаче.
- Микрозадачи, созданные во время выполнения других микрозадач, также выполняются до перехода к следующей задаче.

В браузере микрозадачи обычно обрабатываются до следующей возможности отрисовки интерфейса.

Поэтому бесконечное добавление микрозадач способно заблокировать обработку событий и рендеринг.

# В каком порядке выполняются `Promise.then`, `queueMicrotask` и `setTimeout(0)`?

`Promise.then` и `queueMicrotask` добавляют callbacks в microtask queue, а `setTimeout(0)` планирует обычную задачу.

```
console.log("1");

Promise.resolve().then(() => console.log("2"));

queueMicrotask(() => console.log("3"));

setTimeout(() => console.log("4"), 0);

console.log("5");
```

Результат:

```
1
5
2
3
4
```

Причины:

1. Сначала выполняется синхронный код.
2. Затем микрозадачи в порядке постановки в очередь.
3. После них выполняется callback таймера.

Важно: `Promise.then` и `queueMicrotask` имеют одинаковый приоритет. Порядок зависит от момента добавления в очередь, а не от используемого API.

Для `Promise.then` это справедливо, если промис уже завершён. Если он ожидает результата, callback будет поставлен в очередь позже.

# Какие гарантии и ограничения есть у таймера `setTimeout(0)`?

`setTimeout(0)` планирует выполнение callback с минимальной задержкой, но не гарантирует немедленный запуск.

Особенности:

- Callback выполняется асинхронно, после текущего синхронного кода.
- Перед ним выполняются микрозадачи, ожидающие обработки.
- Реальное время запуска зависит от занятости основного потока и планировщика окружения.
- Браузеры могут увеличивать минимальную задержку таймеров. Например, для глубоко вложенных таймеров применяется ограничение не менее 4 мс, а в фоновых вкладках задержки могут быть значительно больше.
- Точное время выполнения и порядок относительно других независимых задач не гарантируются.

`setTimeout(0)` полезен, когда нужно отложить выполнение и дать event loop возможность обработать другие задачи.

Однако он не гарантирует, что браузер обязательно выполнит отрисовку перед callback.

# Как работают `setInterval` и рекурсивный `setTimeout`?

`setInterval` периодически планирует выполнение callback с указанным интервалом.

```
const id = setInterval(update, 1000);
clearInterval(id);
```

Если callback выполняется дольше заданного интервала, фактическое расписание нарушается. В одном JavaScript-потоке callbacks не выполняются одновременно, но могут запускаться с задержкой.

Рекурсивный `setTimeout` планирует следующее выполнение только после завершения предыдущего:

```
function update() {
  doWork();
  setTimeout(update, 1000);
}

setTimeout(update, 1000);
```

Разница:

- `setInterval` ориентируется на периодическое расписание, не ожидая завершения предыдущей асинхронной операции.
- Рекурсивный `setTimeout` позволяет контролировать паузу между выполнениями.

Для асинхронных запросов часто предпочтительнее рекурсивный `setTimeout`:

```
async function poll() {
  try {
    await fetchData();
  } finally {
    setTimeout(poll, 1000);
  }
}
```

Так следующий запрос начинается не раньше чем через секунду после завершения предыдущего, что предотвращает их наложение.

# Что такое callback hell и как от него уходить?

Callback hell - ситуация, когда множество зависимых асинхронных операций организовано через вложенные callbacks, усложняющие чтение кода, обработку ошибок и управление потоком выполнения.

```
getUser(id, (user) => {
  getOrders(user, (orders) => {
    getDetails(orders, (details) => {
      save(details, () => {
        // ...
      });
    });
  });
});
```

Основные способы решения:

- Promise - позволяют строить последовательные цепочки через `.then()`.
- `async/await` - представляют асинхронную последовательность в линейном виде.
- Декомпозиция - выделяет отдельные операции в самостоятельные функции.

```
async function processUser(id) {
  const user = await getUser(id);
  const orders = await getOrders(user);
  const details = await getDetails(orders);

  await save(details);
}
```

Дополнительное преимущество Promise и `async/await` - централизованная обработка ошибок через `.catch()` или `try/catch`.

# Какие состояния бывают у Promise?

Promise имеет три состояния:

- `pending` - операция ещё не завершилась.
- `fulfilled` - операция успешно завершилась, результат доступен.
- `rejected` - операция завершилась ошибкой, доступна причина отклонения.

Переходы происходят только из `pending` в `fulfilled` или `rejected`. После этого состояние и результат больше не изменяются.

Завершённый Promise называется settled.

Важно различать resolved и fulfilled: Promise может быть resolved другим промисом, но оставаться `pending`, пока тот не завершится.

Обработчики `.then()` и `.catch()` выполняются асинхронно через очередь микрозадач, даже если Promise уже завершён.

# Как работает цепочка `.then().catch().finally()`?

Каждый вызов `.then()`, `.catch()` или `.finally()` возвращает новый Promise, поэтому операции можно объединять в цепочку.

- `.then(onFulfilled, onRejected)` - обрабатывает результат или ошибку. Возвращённое значение становится результатом нового Promise.
- `.catch(onRejected)` - обрабатывает отклонение и эквивалентен `.then(undefined, onRejected)`.
- `.finally(callback)` - выполняется при любом исходе, обычно для очистки ресурсов.

```
fetchData()
  .then((data) => transform(data))
  .then((result) => save(result))
  .catch((error) => {
    console.error(error);
  })
  .finally(() => {
    hideLoader();
  });
```

Если обработчик `.then()` возвращает Promise, цепочка ожидает его завершения. Если выбрасывает исключение, следующий Promise становится отклонённым.

Если `.catch()` возвращает обычное значение, ошибка считается обработанной и цепочка продолжается успешно. Для передачи ошибки дальше необходимо использовать `throw`.

`.finally()` обычно сохраняет исходный результат или ошибку. Исключение - если его callback сам выбросит ошибку или вернёт отклонённый Promise.

# Чем `Promise.all`, `allSettled`, `race` и `any` отличаются?

Все четыре метода принимают итерируемую коллекцию промисов или значений, но по-разному определяют результат.

| Метод                | Когда завершается успешно               | Когда отклоняется                              |
|----------------------|-----------------------------------------|------------------------------------------------|
| `Promise.all`        | Все операции успешны                    | При первом отклонении                          |
| `Promise.allSettled` | После завершения всех операций          | Не отклоняется из-за ошибок отдельных операций |
| `Promise.race`       | Если первым завершился успешный Promise | Если первым завершился отклонённый Promise     |
| `Promise.any`        | При первом успешном результате          | Если все операции отклонены                    |

Особенности:

- `Promise.all` возвращает массив результатов в исходном порядке.
- `Promise.allSettled` возвращает объекты с `status: "fulfilled"` или `"rejected"` и соответствующими `value` или `reason`.
- `Promise.race` учитывает первое завершение независимо от его исхода.
- `Promise.any` игнорирует отдельные ошибки, но при отклонении всех промисов выдаёт `AggregateError`.

Для пустой коллекции `Promise.all` и `Promise.allSettled` успешно завершаются с `[]`, `Promise.any` отклоняется с `AggregateError`, а `Promise.race` навсегда остаётся `pending`.

Эти методы сами по себе не запускают параллельные потоки и не управляют количеством одновременно выполняемых операций.

# Что произойдёт в `Promise.all`, если одна операция завершится ошибкой?

`Promise.all` использует принцип fail-fast: при первом отклонении входного Promise результирующий Promise отклоняется с той же причиной.

```
try {
  const results = await Promise.all([
    fetchUser(),
    fetchOrders(),
    fetchSettings()
  ]);
} catch (error) {
  console.error(error);
}
```

При этом остальные операции не отменяются автоматически и продолжают выполняться.

Последствия:

- Успешные результаты других операций не возвращаются через `Promise.all`.
- Побочные эффекты оставшихся операций могут произойти даже после отклонения общего Promise.
- Для отмены нужно реализовать отдельный механизм, например `AbortController`.

Если требуется дождаться завершения всех операций независимо от ошибок, используют `Promise.allSettled`.

# В чём разница между конкурентностью и параллелизмом?

Конкурентность (concurrency) - способность системы обрабатывать несколько задач за один период времени, переключаясь между ними или ожидая завершения внешних операций.

Параллелизм (parallelism) - физическое выполнение нескольких задач одновременно, например на разных ядрах процессора.

В JavaScript:

- `Promise.all` позволяет конкурентно ожидать несколько асинхронных операций.
- `Web Workers` и `worker_threads` в Node.js позволяют выполнять JavaScript-код параллельно в отдельных потоках.

Например, несколько HTTP-запросов могут обрабатываться конкурентно, даже если JavaScript выполняется в одном потоке.

Главное: конкурентность не требует параллелизма, но параллельное выполнение является одной из форм конкурентности.

# Как выполнять асинхронные операции последовательно?

Для последовательного выполнения используют `async/await` внутри `for...of`.

```
for (const item of items) {
  await processItem(item);
}
```

Каждая следующая операция начинается только после успешного завершения предыдущей.

Также можно использовать цепочку Promise через `.reduce()`, но `for...of` обычно проще читать и отлаживать.

Важно различать:

```
// Последовательно
for (const item of items) {
  await processItem(item);
}

// Конкурентно
await Promise.all(items.map(processItem));
```

Последовательное выполнение необходимо, когда операции зависят друг от друга, важен порядок побочных эффектов или нельзя создавать слишком большую нагрузку на внешний сервис.

Если зависимости отсутствуют, конкурентное выполнение часто быстрее.

# Как ограничить количество одновременно исполняемых задач?

Используют пул задач (worker pool) или семафор, ограничивающий количество одновременно активных асинхронных операций.

Пример реализации с ограничением конкурентности:

```
async function mapLimit(items, limit, fn) {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError("Invalid limit");
  }

  const results = new Array(items.length);
  let next = 0;

  async function worker() {
    while (next < items.length) {
      const index = next++;
      results[index] = await fn(items[index], index);
    }
  }

  const workers = Array.from(
    { length: Math.min(limit, items.length) },
    () => worker()
  );

  await Promise.all(workers);
  return results;
}
```

Использование:

```
const results = await mapLimit(urls, 3, fetchData);
```

Одновременно будут выполняться не более трёх вызовов `fetchData`, а результаты сохранят исходный порядок.

Если одна операция завершится ошибкой, `Promise.all` отклонится, но уже запущенные операции автоматически не отменятся.

Ограничение конкурентности полезно при работе с API, базами данных и другими ресурсами с ограниченной пропускной способностью.

# Как реализовать retry с exponential backoff?

Retry с exponential backoff - механизм повторных попыток, при котором задержка между попытками экспоненциально увеличивается.

Формула:

\\[ delay = \min(maxDelay,\ baseDelay \times 2^{attempt}) \\]

Пример:

```
async function retry(fn, attempts = 4) {
  for (let i = 0; i < attempts; i++) {
    try {
      return await fn();
    } catch (error) {
      if (i === attempts - 1) {
        throw error;
      }

      const delay = Math.min(5000, 200 * 2 ** i);
      const jitter = Math.random() * delay;

      await new Promise(resolve =>
        setTimeout(resolve, jitter)
      );
    }
  }
}
```

Здесь используется full jitter - случайная задержка от `0` до рассчитанного максимума. Это помогает избежать одновременных повторных запросов от множества клиентов.

В production важно учитывать:

- Повторять преимущественно временные ошибки: сбои сети, HTTP `429`, `503` и некоторые `5xx`.
- Не повторять автоматически операции с неидемпотентными побочными эффектами, если нет защиты от дублирования.
- Ограничивать число попыток и максимальную задержку.
- Учитывать серверный заголовок `Retry-After`, если он присутствует.
- Поддерживать отмену запросов и ожидания между попытками.

Для `fetch` HTTP-ошибки нужно проверять отдельно через `response.ok`, иначе retry не сработает на HTTP `500`.

# Как отменять `fetch` через `AbortController`?

`AbortController` позволяет отправить сигнал отмены асинхронной операции через объект `AbortSignal`.

```
const controller = new AbortController();

const request = fetch("/api/data", {
  signal: controller.signal
});

// Отмена запроса
controller.abort();

try {
  await request;
} catch (error) {
  if (error.name !== "AbortError") {
    throw error;
  }
}
```

Механизм:

1. Создаётся `AbortController`.
2. Его `signal` передаётся в `fetch`.
3. Вызов `abort()` переводит сигнал в отменённое состояние.
4. Незавершённый `fetch` отклоняется, обычно с `AbortError`.

Сигнал также может прервать чтение тела ответа, например через `response.json()`.

Ограничение: отмена на стороне клиента не гарантирует прекращение обработки запроса сервером. Сервер мог уже получить запрос и выполнить операцию.

Один `AbortSignal` можно передавать нескольким операциям для их совместной отмены.

# Почему `fetch` не считает HTTP 404/500 отклонённым промисом?

`fetch` различает ошибку выполнения HTTP-запроса и HTTP-ответ со статусом ошибки.

Статусы `404` и `500` означают, что сервер вернул корректный HTTP-ответ. Поэтому Promise успешно завершается объектом `Response`.

`fetch` обычно отклоняется при сетевых ошибках, нарушениях CORS, отмене запроса и других ситуациях, когда операция не может нормально завершиться.

Для проверки HTTP-статуса используется `response.ok`:

```
const response = await fetch("/api/user");

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}

const data = await response.json();
```

`response.ok` равен `true` для статусов `200-299`.

Такое разделение позволяет самостоятельно определять, какие HTTP-статусы считать ошибками и как их обрабатывать.

# Чем `async/await` удобнее цепочек `then`?

`async/await` - синтаксический механизм работы с Promise, позволяющий писать асинхронный код в стиле последовательных инструкций.

Преимущества:

- Линейный поток выполнения вместо длинных цепочек `.then()`.
- Обработка ошибок через привычные `try/catch/finally`.
- Удобная работа с условиями, циклами и промежуточными результатами.
- Более понятные зависимости между операциями.

```
async function loadData() {
  try {
    const user = await getUser();
    const orders = await getOrders(user.id);

    return orders;
  } catch (error) {
    console.error(error);
    throw error;
  }
}
```

`await` приостанавливает выполнение текущей асинхронной функции до завершения Promise, не блокируя JavaScript-поток.

При этом `async/await` не делает операции автоматически параллельными. Последовательные `await` могут замедлять независимые задачи, поэтому для конкурентного выполнения используют `Promise.all`.

# Как обработать ошибку внутри асинхронного цикла?

Для обработки ошибок отдельных итераций размещают `try/catch` внутри цикла.

```
for (const item of items) {
  try {
    await processItem(item);
  } catch (error) {
    console.error(`Ошибка: ${item}`, error);
  }
}
```

Так ошибка одной операции не прерывает обработку остальных элементов.

Если `try/catch` находится снаружи цикла, первая необработанная ошибка прекращает дальнейшие итерации:

```
try {
  for (const item of items) {
    await processItem(item);
  }
} catch (error) {
  console.error(error);
}
```

Выбор зависит от требований:

- Продолжить обработку - ловить ошибки внутри каждой итерации.
- Остановиться при первой ошибке - использовать внешний `try/catch` или повторно выбрасывать ошибку через `throw`.
- Выполнить независимые задачи и собрать все результаты - использовать `Promise.allSettled`.

# Чем `for...of` отличается от `forEach(async () => ...)`?

`for...of` позволяет использовать `await` для последовательного выполнения асинхронных операций.

```
for (const item of items) {
  await processItem(item);
}
```

`forEach` не ожидает завершения Promise, возвращаемых асинхронными callbacks.

```
items.forEach(async (item) => {
  await processItem(item);
});

console.log("Done");
```

Здесь `Done` может появиться раньше завершения всех операций.

Причина: `forEach` синхронно вызывает callbacks и игнорирует возвращаемые ими Promise. Сам метод возвращает `undefined`, поэтому `await items.forEach(...)` не решает проблему.

Для правильного управления выполнением используют:

- `for...of` с `await` - последовательно.
- `Promise.all(items.map(async ...))` - конкурентно, с ожиданием всех успешных результатов.
- `Promise.allSettled(...)` - конкурентно, с ожиданием всех результатов независимо от ошибок.

Дополнительно `forEach(async ...)` усложняет обработку отклонений Promise и может приводить к `unhandled rejection`.

# Что такое async iterator и `for await...of`?

Async iterator - асинхронный итератор, у которого метод `next()` возвращает Promise, разрешающийся объектом `{ value, done }`.

Он позволяет получать элементы по мере их асинхронной доступности, не загружая всю последовательность сразу.

Async iterable реализует метод `[Symbol.asyncIterator]()`, возвращающий такой итератор.

Для перебора используется `for await...of`:

```
async function* generateData() {
  yield await fetchPage(1);
  yield await fetchPage(2);
  yield await fetchPage(3);
}

for await (const page of generateData()) {
  processPage(page);
}
```

Здесь `async function*` создаёт асинхронный генератор.

`for await...of` автоматически ожидает результат каждого `next()`, а затем выполняет тело цикла. Если внутри тела есть собственные асинхронные операции, их нужно явно ожидать через `await`.

Применяется для потоков данных, постраничных запросов, асинхронных генераторов и обработки событий.

Дополнительно `for await...of` способен работать с обычными синхронными итерируемыми объектами.

# Как избежать race condition в асинхронном коде?

Race condition - ситуация, когда итоговое состояние зависит от непредсказуемого порядка завершения конкурирующих операций.

Например, пользователь отправляет два поисковых запроса. Второй завершается раньше первого, после чего устаревший первый ответ перезаписывает актуальные результаты.

Один из способов защиты - проверка идентификатора операции:

```
let currentRequestId = 0;

async function search(query) {
  const requestId = ++currentRequestId;
  const results = await fetchResults(query);

  if (requestId === currentRequestId) {
    render(results);
  }
}
```

Теперь только результат последнего запущенного запроса может изменить интерфейс.

Другие способы:

- `AbortController` - отмена устаревших запросов.
- Последовательное выполнение - исключение нежелательного пересечения операций.
- Mutex или semaphore - контролируемый доступ к общему состоянию.
- Версионирование данных - проверка актуальности состояния перед записью.
- Атомарные операции - синхронизация общей памяти между потоками.

Race condition возможен даже в однопоточном JavaScript: асинхронные операции могут завершаться в произвольном порядке.

# Что такое unhandled promise rejection?

Unhandled promise rejection - отклонение Promise, для которого не был своевременно зарегистрирован обработчик ошибки.

```
async function load() {
  throw new Error("Failed");
}

load(); // Promise отклонён, ошибка не обработана
```

Причина: вызов `async`-функции возвращает Promise. Выброшенная внутри неё ошибка превращается в отклонение этого Promise, а не в синхронное исключение вызывающего кода.

Правильная обработка:

```
load().catch(console.error);
```

Последствия зависят от окружения:

- В браузере может возникнуть событие `unhandledrejection`.
- В Node.js возникает событие `unhandledRejection`; при стандартных настройках современных версий необработанное отклонение может привести к завершению процесса.

Если обработчик добавлен позже, окружение может сообщить о том, что ранее необработанное отклонение теперь обработано.

Поэтому Promise необходимо либо ожидать через `await` с обработкой ошибок, либо явно обрабатывать через `.catch()` или передавать вызывающему коду, который отвечает за обработку.

# Как отменить устаревший запрос при поиске по мере ввода?

Используют `AbortController`, чтобы при появлении нового поискового запроса отменить предыдущий.

```
let controller;
let requestId = 0;

async function search(query) {
  controller?.abort();

  controller = new AbortController();
  const currentId = ++requestId;

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(query)}`,
      { signal: controller.signal }
    );

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const results = await response.json();

    if (currentId === requestId) {
      render(results);
    }
  } catch (error) {
    if (
      error.name !== "AbortError" &&
      currentId === requestId
    ) {
      showError(error);
    }
  }
}
```

Здесь используются два механизма:

- `AbortController` - отменяет предыдущий запрос, сокращая ненужную работу.
- `requestId` - предотвращает отображение устаревшего результата, даже если операция уже завершилась или не поддерживает отмену.

Дополнительно обычно применяют debounce - задержку перед отправкой запроса, которая сбрасывается при каждом новом вводе.

Debounce уменьшает количество запросов, но сам по себе не защищает от race condition.

# Как реализовать собственную упрощённую версию `Promise.all`?

`Promise.all` принимает набор значений и Promise, ожидает их успешного завершения и возвращает результаты в исходном порядке. При первом отклонении общий Promise отклоняется.

Упрощённая реализация для массива:

```
function promiseAll(values) {
  return new Promise((resolve, reject) => {
    const results = new Array(values.length);
    let remaining = values.length;

    if (remaining === 0) {
      resolve([]);
      return;
    }

    for (let i = 0; i < values.length; i++) {
      Promise.resolve(values[i]).then(
        (result) => {
          results[i] = result;
          remaining--;

          if (remaining === 0) {
            resolve(results);
          }
        },
        reject
      );
    }
  });
}
```

Ключевые механизмы:

1. `Promise.resolve()` позволяет одинаково обрабатывать обычные значения, Promise и thenable-объекты.
2. Индекс `i` сохраняет исходный порядок результатов независимо от порядка завершения.
3. `remaining` отслеживает количество незавершённых операций.
4. Когда `remaining === 0`, общий Promise завершается успешно.
5. При первом отклонении вызывается `reject`. Последующие вызовы `resolve` или `reject` уже не изменят состояние общего Promise.

Эта версия поддерживает массивы, включая пустые, но не произвольные итерируемые объекты, которые принимает нативный `Promise.all`.

Важно: `Promise.all` не запускает операции самостоятельно и не отменяет остальные операции после первой ошибки.

# Что такое starvation microtasks и как оно влияет на интерфейс?

Microtask starvation - ситуация, когда непрерывное создание микрозадач не позволяет event loop перейти к обычным задачам и обновлению интерфейса.

Например:

```
function loop() {
  queueMicrotask(loop);
}

loop();
```

Каждая микрозадача добавляет следующую. Поскольку очередь микрозадач должна опустошиться до перехода к следующей задаче, цикл может продолжаться бесконечно.

Последствия:

- Браузер перестаёт обновлять интерфейс.
- Обработчики пользовательских событий не выполняются.
- Таймеры задерживаются.
- Страница может перестать отвечать.

Аналогичная проблема возможна при бесконечных цепочках `Promise.then()` или повторяющемся `await Promise.resolve()`.

Решение - периодически уступать управление event loop, например разбивать большую работу на части и планировать следующую часть через `setTimeout`.

Это даёт браузеру возможность обработать события и выполнить отрисовку между частями работы.

# Как движок JavaScript создаёт execution context?

Execution context - контекст выполнения JavaScript-кода, содержащий информацию, необходимую для разрешения идентификаторов и выполнения инструкций.

Контекст создаётся при запуске скрипта или модуля, а также при каждом вызове функции.

В нём определяются:

- Lexical Environment - окружение лексических привязок и ссылка на внешнее окружение, необходимые для работы областей видимости и замыканий.
- Variable Environment - окружение, используемое, в частности, для обработки объявлений `var`.
- `this` binding - значение `this`, определяемое правилами вызова. Стрелочные функции используют `this` из внешнего окружения.
- Function arguments - параметры функции и связанные с вызовом данные.

Концептуально обработку контекста можно разделить на два этапа.

1\. Создание и инициализация

Движок подготавливает окружение и объявления:

- `function`-декларации обычно доступны до их расположения в коде.
- `var` инициализируется значением `undefined`.
- `let` и `const` существуют в области видимости, но до инициализации находятся в Temporal Dead Zone (TDZ).

2\. Выполнение

Движок исполняет инструкции, вычисляет выражения, присваивает значения и вызывает функции.

При вызове функции её execution context становится активным. После завершения управление возвращается в предыдущий контекст.

Эта модель объясняет hoisting, lexical scope, замыкания и поведение `this`.

# Что хранится в call stack?

Call stack - стек вызовов, который отслеживает активные выполнения функций.

Каждый вызов создаёт stack frame, содержащий необходимые данные для выполнения и возврата из функции. В зависимости от реализации это могут быть:

- Аргументы и локальные значения.
- Ссылки на окружения выполнения.
- Информация о текущей инструкции.
- Адрес возврата в вызывающий код.

Стек работает по принципу LIFO (Last In, First Out): последняя вызванная функция завершается первой.

```
function a() {
  b();
}

function b() {
  c();
}

function c() {
  console.log("Done");
}

a();
```

Во время выполнения `c()` стек концептуально содержит:

```
c()
b()
a()
global
```

После завершения `c()` управление возвращается в `b()`, затем в `a()`.

При глубокой рекурсии стек может переполниться, вызывая `RangeError: Maximum call stack size exceeded` в большинстве JavaScript-движков.

При `await` асинхронная функция приостанавливается, а её выполнение позднее возобновляется через механизм микрозадач. Ожидание Promise не требует постоянно удерживать обычный стек вызовов.

# Как работает сборщик мусора?

Garbage Collector (GC) - механизм автоматического освобождения памяти, занятой объектами, которые больше недоступны программе.

Современные JavaScript-движки используют алгоритмы, основанные на достижимости объектов (reachability).

Основной принцип:

1. Определяются корневые ссылки (GC roots), например глобальные объекты и активные ссылки в выполняющемся коде.
2. От корней обходится граф объектов.
3. Достижимые объекты считаются используемыми.
4. Недостижимые объекты могут быть удалены, а память освобождена.

Распространённая основа такого подхода - mark-and-sweep:

- Mark - пометить достижимые объекты.
- Sweep - освободить память недостижимых объектов.

Современные движки также применяют поколенческую сборку, инкрементальные и параллельные алгоритмы для уменьшения пауз.

Важные особенности:

- Циклические ссылки сами по себе не вызывают утечку памяти: если вся группа объектов недостижима, она может быть собрана.
- GC не гарантирует немедленное освобождение памяти.
- Утечки возникают, когда ненужные объекты остаются достижимыми, например через глобальные коллекции, обработчики событий, таймеры или замыкания.

GC управляет памятью автоматически, но разработчик по-прежнему отвечает за корректное управление ссылками и жизненным циклом ресурсов.

# Для чего могут использоваться `WeakRef` и `FinalizationRegistry`?

`WeakRef` позволяет хранить слабую ссылку на объект, которая не препятствует его сборке мусора.

```
const ref = new WeakRef(object);

const value = ref.deref();

if (value) {
  use(value);
}
```

Метод `deref()` возвращает объект, если он ещё доступен, или `undefined`, если объект уже был собран.

Основное применение - специальные кеши, в которых наличие записи не должно принудительно удерживать объект в памяти.

`FinalizationRegistry` позволяет зарегистрировать callback, который может быть вызван после сборки зарегистрированного объекта.

```
const registry = new FinalizationRegistry((value) => {
  console.log("Collected:", value);
});

registry.register(object, "object-1");
```

Основные ограничения:

- Нельзя предсказать, когда объект будет собран.
- Callback `FinalizationRegistry` не гарантирован и может вообще не выполниться.
- Порядок финализации не гарантируется.
- Нельзя использовать эти API как основной механизм освобождения ресурсов.

Поэтому для файлов, соединений и других ресурсов, требующих надёжного закрытия, необходимы явные механизмы очистки, например `finally` или `dispose`.

# Что такое JIT-компиляция JavaScript?

JIT (Just-In-Time compilation) - компиляция JavaScript в машинный код во время выполнения программы.

В отличие от предварительной компиляции, JIT может учитывать информацию, собранную непосредственно во время работы кода.

Типичный процесс в современных движках:

1. JavaScript-код разбирается парсером.
2. Движок создаёт промежуточное представление, часто байткод.
3. Интерпретатор или базовый компилятор начинает выполнение.
4. Движок собирает информацию о типах значений и часто выполняемых участках кода.
5. Оптимизирующий компилятор создаёт более эффективный машинный код для перспективных участков.
6. Если предположения оптимизации перестают выполняться, возможна деоптимизация (deoptimization) с возвратом к менее оптимизированному выполнению.

Например, если функция многократно получает числа, движок может оптимизировать её для числовых операций. При передаче значения другого типа оптимизация может перестать подходить.

JIT помогает повысить производительность, но конкретные уровни компиляции и алгоритмы зависят от движка JavaScript. Не каждый движок или режим выполнения обязательно использует JIT.

# Как hidden classes и inline caches влияют на производительность?

Hidden classes и inline caches - внутренние механизмы оптимизации доступа к свойствам объектов в некоторых JavaScript-движках, например V8.

Hidden classes (скрытые классы)

Движок отслеживает структуру объекта: набор свойств и особенности их размещения.

```
const a = { x: 1, y: 2 };
const b = { x: 3, y: 4 };
```

Объекты с одинаковой структурой и порядком создания свойств часто могут использовать одну скрытую форму.

Это позволяет движку обращаться к свойствам по заранее известному расположению вместо полноценного динамического поиска.

Если свойства добавляются в разном порядке, удаляются или структура часто меняется, количество форм может увеличиваться и оптимизация усложняется.

Inline caches (встроенные кеши доступа)

Inline cache запоминает информацию о ранее встречавшихся структурах объектов в конкретной точке обращения к свойству.

```
function getX(obj) {
  return obj.x;
}
```

Если `getX` многократно получает объекты одной структуры, движок может использовать быстрый доступ к `x`.

В зависимости от разнообразия встречающихся структур inline cache бывает:

- Monomorphic - одна структура, наиболее простой случай оптимизации.
- Polymorphic - несколько структур.
- Megamorphic - множество разных структур, оптимизация обычно сложнее и менее эффективна.

Практический вывод: стабильная структура объектов часто помогает движку оптимизировать горячие участки кода.

Однако эти механизмы являются деталями реализации движков, поэтому не следует считать конкретный порядок свойств универсальной гарантией производительности.

# Что такое `SharedArrayBuffer` и Atomics?

`SharedArrayBuffer` - объект, представляющий участок памяти, который может совместно использоваться несколькими JavaScript-потоками, например основным потоком и Web Workers.

В отличие от обычного `ArrayBuffer`, его содержимое может быть доступно нескольким потокам одновременно без копирования данных.

```
const buffer = new SharedArrayBuffer(4);
const array = new Int32Array(buffer);

Atomics.add(array, 0, 1);

console.log(Atomics.load(array, 0)); // 1
```

`Atomics` - встроенный объект с методами для атомарных операций над целочисленными типизированными массивами в разделяемой памяти.

Основные методы:

- `Atomics.load()` - атомарное чтение.
- `Atomics.store()` - атомарная запись.
- `Atomics.add()` - атомарное сложение.
- `Atomics.compareExchange()` - условная атомарная замена значения.
- `Atomics.wait()` и `Atomics.notify()` - ожидание и уведомление между потоками.

Зачем нужны атомарные операции?

Если два потока одновременно изменяют одну переменную обычными операциями, возможна потеря обновлений из-за race condition.

Например, операция `counter++` состоит из чтения, вычисления и записи. Между этими действиями другой поток может изменить значение.

`Atomics.add()` выполняет обновление как единую атомарную операцию, предотвращая такую гонку.

Ограничения:

- В браузерах использование `SharedArrayBuffer` между потоками обычно требует cross-origin isolation с соответствующими заголовками COOP и COEP.
- `Atomics.wait()` блокирует вызывающий поток, поэтому в основном потоке браузера запрещён.
- Атомарность отдельных операций не гарантирует корректность сложного многопоточного алгоритма без дополнительной синхронизации.

`SharedArrayBuffer` и `Atomics` применяются для высокопроизводительных вычислений, совместных структур данных и синхронизации между Workers.
