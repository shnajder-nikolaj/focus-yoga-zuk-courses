# Что такое Backend for Frontend и когда он нужен?

**Backend for Frontend (BFF)** - архитектурный паттерн, при котором для конкретного клиентского приложения создаётся отдельный backend, адаптирующий API под его потребности.

BFF располагается между frontend и внутренними сервисами. Он может агрегировать данные, преобразовывать ответы, управлять серверной сессией, кешировать результаты и скрывать внутреннюю архитектуру backend.

**Когда нужен:**
* Web, mobile и другие клиенты требуют разных форматов данных.
* Frontend обращается к множеству микросервисов.
* Необходимо сократить количество сетевых запросов.
* Требуется хранить токены авторизации на сервере.
* Логика подготовки данных для интерфейса становится сложной.

Например, вместо пяти запросов к разным сервисам React выполняет один запрос к BFF, который возвращает готовые данные страницы.

**Недостатки:** дополнительный сервис, инфраструктурные расходы, сложность поддержки и потенциальная дополнительная задержка.

Для небольшого приложения с простым API отдельный BFF часто избыточен.

# Чем BFF отличается от API Gateway и reverse proxy?

Все три компонента могут находиться между клиентом и backend, но решают разные задачи.

* **Reverse proxy** - принимает HTTP-запросы и перенаправляет их на внутренние серверы. Может обеспечивать TLS termination, балансировку нагрузки, кеширование и маршрутизацию.
* **API Gateway** - единая точка входа к API. Обычно реализует маршрутизацию, аутентификацию, rate limiting, логирование и другие общие политики.
* **BFF** - предоставляет API, адаптированный под конкретный frontend. Агрегирует данные, преобразует ответы и реализует специфическую для интерфейса серверную логику.

Например:
* Reverse proxy направляет `/api/*` на API Gateway.
* API Gateway проверяет ограничения и маршрутизирует запросы.
* BFF собирает данные пользователя, заказов и рекомендаций в один ответ для страницы.

**Ключевое различие:** API Gateway обычно решает общие инфраструктурные задачи, а BFF оптимизирует взаимодействие конкретного клиента с backend.

Границы не абсолютны: один сервер может совмещать несколько ролей.

# Как BFF агрегирует несколько сервисов и обрабатывает частичные отказы?

BFF получает запрос от frontend и обращается к нескольким внутренним сервисам, часто параллельно.

Например, для страницы профиля ему нужны:
* User Service - информация о пользователе.
* Order Service - история заказов.
* Recommendation Service - рекомендации.

Независимые запросы можно выполнить через `Promise.allSettled()`, чтобы отказ одного сервиса не отменял обработку остальных результатов.

**Стратегии обработки отказов:**
* **Timeout** - ограничение времени ожидания каждого сервиса.
* **Retry** - повтор временно неудачных запросов с ограничениями и backoff.
* **Circuit Breaker** - временное прекращение обращений к нестабильному сервису.
* **Fallback** - возврат кешированных данных или значения по умолчанию.
* **Graceful Degradation** - отображение доступной функциональности без необязательных данных.
* **Bulkhead** - изоляция ресурсов, чтобы отказ одного сервиса не перегрузил остальные.

Важно разделять критические и необязательные зависимости.

Если User Service недоступен и без него страницу невозможно сформировать, BFF возвращает ошибку. Если недоступны рекомендации, он может вернуть профиль без них.

Формат ответа должен явно обозначать частично недоступные данные, чтобы frontend отличал отсутствие информации от ошибки её получения.

# Как организовать авторизацию в архитектуре React + BFF + auth service?

Рекомендуемая схема для OAuth 2.0/OIDC - **Authorization Code Flow с PKCE**, при котором BFF выступает серверным OAuth-клиентом.

**Последовательность:**

1. React инициирует вход через BFF.
2. BFF перенаправляет пользователя на Auth Service.
3. Пользователь проходит аутентификацию.
4. Auth Service возвращает authorization code на callback BFF.
5. BFF проверяет параметры авторизации и обменивает code на токены.
6. BFF сохраняет токены на сервере и создаёт сессию.
7. Браузер получает сессионную cookie.
8. При запросах React отправляет cookie, а BFF использует access token для обращения к backend.

**Требования безопасности:**
* `HttpOnly` - запрещает JavaScript читать cookie.
* `Secure` - передача cookie только через HTTPS.
* `SameSite` - ограничивает отправку cookie в cross-site запросах.
* CSRF-защита - необходима для изменяющих состояние запросов.
* Проверка прав на backend - выполняется независимо от frontend.
* Обновление и отзыв токенов - управляются сервером.

React не должен получать access token или refresh token, если используется полноценный BFF с серверным хранением токенов.

**Преимущество:** компрометация JavaScript-кода не позволяет напрямую прочитать токены из браузерного хранилища. Однако XSS по-прежнему может выполнять действия от имени пользователя через активную сессию.

# Чем BFF полезен для агрегации нескольких API?

BFF позволяет объединить несколько внутренних API в **единый контракт, удобный для конкретного интерфейса**.

Основные преимущества:

* **Меньше сетевых запросов** - frontend получает необходимые данные за одно обращение.
* **Параллельная загрузка** - BFF одновременно обращается к независимым сервисам.
* **Упрощение frontend** - логика объединения и преобразования данных переносится на сервер.
* **Скрытие инфраструктуры** - клиент не зависит напрямую от адресов и структуры микросервисов.
* **Централизованная обработка ошибок** - BFF определяет fallback и формат частичных результатов.
* **Серверное кеширование** - повторяющиеся запросы могут обслуживаться быстрее.

Например, endpoint `/api/dashboard` возвращает профиль, статистику и уведомления, собранные из нескольких сервисов.

**Ограничение:** агрегация не гарантирует ускорения. Если BFF последовательно вызывает сервисы или создаёт перегрузку, задержка может увеличиться. Поэтому важны параллелизм, таймауты и контроль зависимостей.

# Как спроектировать поиск с подсказками и кешированием?

Поиск с подсказками состоит из поля ввода, механизма управления запросами, API поиска и кеша.

**Архитектура:**

1. Пользователь вводит текст.
2. Frontend применяет `debounce`, например 200-300 мс.
3. После паузы отправляется запрос `/api/search/suggest?q=react`.
4. Backend выполняет поиск по индексу и ранжирует результаты.
5. Frontend отображает подсказки.

**Оптимизации:**
* `AbortController` отменяет устаревшие запросы.
* Проверка идентификатора запроса предотвращает отображение устаревшего ответа.
* Минимальная длина запроса уменьшает нагрузку.
* Кеш по ключу из текста запроса, языка и контекста пользователя исключает повторные обращения.
* TTL ограничивает срок актуальности результатов.
* `stale-while-revalidate` позволяет сразу показать кеш, одновременно обновляя его.

Для серверного поиска используют подходящие индексы: prefix search, full-text search или специализированный поисковый движок.

Важно предусмотреть rate limiting, пустые результаты и доступное управление подсказками с клавиатуры по паттерну `combobox`.

# Как спроектировать таблицу на сотни тысяч строк?

Главная проблема - количество DOM-элементов, объём данных и стоимость операций сортировки и фильтрации.

**Основное решение - виртуализация и серверная обработка данных.**

**Виртуализация:**

В DOM создаются только видимые строки и небольшой запас вокруг области просмотра. Например, при 300 000 записях одновременно могут отображаться лишь 30-50 строк.

Используются `TanStack Virtual`, `react-window` или аналогичные решения.

**Работа с данными:**
* Серверная пагинация - загрузка данных частями.
* Cursor-based pagination - эффективная последовательная навигация по большим наборам.
* Серверная сортировка и фильтрация - операции выполняет база данных.
* Индексы БД - ускоряют выборку.
* Кеширование страниц - уменьшает повторные запросы.
* `AbortController` - отменяет запросы при изменении фильтров.

При произвольном переходе к номеру страницы может потребоваться offset pagination или отдельный механизм позиционирования, поскольку курсоры не обеспечивают прямой доступ к произвольной странице.

**Дополнительно:** нужно учитывать динамическую высоту строк, фиксированные колонки, клавиатурную навигацию и доступность.

Виртуализация оптимизирует рендеринг, но не заменяет серверную оптимизацию запросов.

# Как спроектировать чат с индикаторами доставки и прочтения?

Для чата требуется серверное хранение сообщений, доставка событий в реальном времени и синхронизация состояния.

**Архитектура:**
* REST API - получение истории сообщений.
* WebSocket - обмен сообщениями и событиями.
* База данных - постоянное хранение переписки.
* Очередь сообщений или брокер событий - масштабирование доставки при необходимости.

**Жизненный цикл сообщения:**

1. Пользователь отправляет сообщение.
2. Frontend сразу отображает его со статусом `sending`.
3. Сервер сохраняет сообщение и подтверждает приём - `sent`.
4. Клиент получателя подтверждает доставку - `delivered`.
5. Получатель открывает или просматривает сообщение - `read`, согласно правилам приложения.

**Важные механизмы:**
* `clientMessageId` - уникальный идентификатор для защиты от дублирования при повторах.
* Server-generated ID - постоянный идентификатор сохранённого сообщения.
* Sequence number - восстановление порядка и обнаружение пропущенных событий.
* Reconnection - переподключение WebSocket с загрузкой пропущенных сообщений.
* Optimistic UI - мгновенное отображение отправляемого сообщения.
* Cursor pagination - загрузка истории частями.

Статусы должны иметь точную семантику: успешная отправка на сервер не означает доставку получателю, а доставка не означает прочтение.

Для нескольких устройств также нужно определить, считается ли сообщение прочитанным на любом устройстве или отслеживается отдельно.

# Как спроектировать ленту обновлений с бесконечной прокруткой?

Бесконечная прокрутка строится на **cursor-based pagination**, дозагрузке данных и сохранении позиции пользователя.

**Механизм:**

1. Frontend запрашивает первую порцию записей.
2. Backend возвращает элементы и `nextCursor`.
3. `IntersectionObserver` отслеживает приближение к концу списка.
4. Когда пользователь приближается к нижней границе, загружается следующая порция.
5. Новые элементы добавляются к существующим.

**Ключевые решения:**
* Cursor-based pagination уменьшает проблемы смещения записей при обновлении ленты.
* Стабильная сортировка по времени и уникальному ID обеспечивает предсказуемый порядок.
* Дедупликация по ID предотвращает повторное появление элементов.
* Виртуализация ограничивает количество DOM-узлов.
* Кеширование страниц сохраняет данные при возвращении к ленте.
* Отмена и дедупликация запросов предотвращают лишнюю загрузку.

Новые публикации, появившиеся выше текущей позиции, лучше показывать через индикатор «Новые записи», а не вставлять с автоматическим смещением прокрутки.

Также важно восстанавливать позицию после перехода на страницу публикации и обратно.

# Как спроектировать редактор с autosave и конфликтами изменений?

Редактор должен сохранять изменения автоматически, не терять введённые данные и защищать от перезаписи чужих изменений.

**Autosave:**

1. Пользователь изменяет документ.
2. Редактор помечает состояние как `dirty`.
3. После небольшой паузы запускается сохранение с `debounce`.
4. Сервер сохраняет данные и возвращает новую версию документа.
5. Интерфейс отображает статус `saved`.

Дополнительно используют сохранение по потере фокуса, периодические контрольные сохранения и локальные черновики в `IndexedDB`.

**Обработка конфликтов:**

Каждый документ имеет версию или `ETag`.

При сохранении клиент передаёт ожидаемую версию, например через `If-Match`.

Если документ уже изменён другим пользователем, сервер отклоняет сохранение с `412 Precondition Failed`.

Возможные решения:
* Показать различия между версиями.
* Объединить независимые изменения.
* Предложить пользователю выбрать нужную версию.
* Использовать CRDT или OT для совместного редактирования в реальном времени.

Важно не считать данные сохранёнными до подтверждения сервера и не допускать перезаписи более новых локальных изменений ответом на старый запрос.

# Как спроектировать дашборд с множеством параллельных API-запросов?

Дашборд обычно состоит из независимых виджетов, каждый из которых получает собственные данные.

**Основной принцип - независимая загрузка и изоляция ошибок.**

**Архитектурные решения:**
* `TanStack Query` или аналогичный инструмент - управление запросами, кешем и обновлениями.
* `Promise.allSettled()` - когда необходимо дождаться набора независимых запросов без общего отказа.
* BFF - агрегация данных, если это уменьшает сетевые накладные расходы.
* Ограничение параллелизма - защита браузера и backend от избыточной нагрузки.
* Lazy loading - загрузка тяжёлых виджетов по необходимости.
* WebSocket или SSE - получение оперативных обновлений.

Каждый виджет должен иметь независимые состояния `loading`, `success`, `error` и `empty`.

**Кеширование:** для каждого типа данных выбирается собственный `staleTime`. Например, справочная информация может обновляться редко, а оперативная статистика - значительно чаще.

При большом количестве запросов полезно приоритизировать данные первого экрана и избегать ситуаций, когда отказ одного API блокирует весь дашборд.

# Как спроектировать offline-first PWA?

**Offline-first PWA** - приложение, спроектированное так, чтобы основные функции оставались доступными без подключения к интернету.

Основные компоненты:

* **Service Worker** - перехватывает поддерживаемые сетевые запросы и управляет кешированием.
* **Cache Storage** - хранит статические ресурсы и подходящие HTTP-ответы.
* **IndexedDB** - хранит структурированные данные, локальные изменения и очередь операций.
* **Web App Manifest** - описывает устанавливаемое веб-приложение.

**Стратегии кеширования:**
* `Cache First` - для версионированных статических ресурсов.
* `Network First` - для данных, которым важна актуальность.
* `Stale While Revalidate` - быстрый ответ из кеша с последующим обновлением.

**Работа с изменениями offline:**

1. Пользователь изменяет данные.
2. Изменение сохраняется локально.
3. Операция добавляется в очередь синхронизации.
4. После восстановления соединения операции отправляются на сервер.
5. Сервер подтверждает изменения или сообщает о конфликте.

Для повторов нужны идемпотентные операции и уникальные идентификаторы запросов.

**Ограничения:** браузер может удалить локальные данные, а Background Sync поддерживается не во всех окружениях и не гарантирует немедленного выполнения.

Поэтому синхронизация должна запускаться также при открытии приложения и восстановлении соединения.

# Как спроектировать систему уведомлений в браузере?

Система обычно включает **in-app notifications** и **Web Push Notifications**.

**In-app уведомления** отображаются внутри открытого приложения. Для доставки используются WebSocket, SSE или периодические запросы.

**Web Push** позволяет доставлять уведомления через браузерный push-сервис, даже когда страница приложения не открыта.

**Архитектура Web Push:**

1. Пользователь разрешает уведомления.
2. Frontend регистрирует `Service Worker`.
3. Через `Push API` создаётся подписка.
4. Данные подписки сохраняются на backend.
5. Backend отправляет push-сообщение через push-сервис.
6. Service Worker получает событие `push` и показывает уведомление через `showNotification()`.

**Важные аспекты:**
* HTTPS и поддержка необходимых браузерных API.
* Управление подписками и отзывом разрешений.
* Настройки категорий уведомлений.
* Дедупликация событий.
* Хранение истории уведомлений на сервере.
* Отслеживание статуса прочтения.
* Контроль частоты отправки.

Push-доставка не гарантирована: подписка может истечь, устройство может быть недоступно, а пользователь может запретить уведомления.

Поэтому важные события необходимо хранить на сервере независимо от успешности push-доставки.

# Как спроектировать файловый загрузчик с возобновлением загрузки?

Для больших файлов используется **resumable upload** - загрузка, которую можно продолжить после обрыва соединения.

**Механизм:**

1. Клиент создаёт upload session на сервере.
2. Файл разбивается на части - `chunks`.
3. Части отправляются отдельно.
4. Сервер сохраняет информацию о полученных частях.
5. При обрыве клиент узнаёт текущее состояние загрузки.
6. Недостающие части отправляются повторно.
7. После завершения сервер собирает файл и проверяет целостность.

Возможные технологии:
* `tus` - протокол возобновляемой загрузки.
* S3 Multipart Upload - загрузка частей в объектное хранилище.
* Presigned URLs - прямая загрузка в хранилище без передачи содержимого через backend приложения.

**Обязательные механизмы:**
* Уникальный `uploadId`.
* Контроль размера и типа файла.
* Проверка контрольных сумм.
* Повтор запросов с backoff.
* Отмена загрузки и удаление незавершённых частей.
* Проверка прав доступа.
* Ограничения размера и антивирусная проверка при необходимости.

Для продолжения после перезагрузки страницы можно сохранить `uploadId` и метаданные в `IndexedDB`.

Однако сам объект `File` обычно потребуется выбрать повторно, если приложение не использует поддерживаемый механизм постоянного доступа к файлу.

# Как спроектировать drag-and-drop канбан-доску?

Канбан-доска состоит из колонок и карточек, которые пользователь может перемещать внутри колонки или между колонками.

**Frontend:**
* React хранит отображаемое состояние колонок и карточек.
* `dnd-kit` или аналогичная библиотека управляет drag-and-drop.
* При перемещении применяется `optimistic update`.
* После завершения операции отправляется запрос на backend.
* При ошибке состояние откатывается или синхронизируется с сервером.

**Хранение порядка:**

Каждой карточке можно присвоить поле `position`.

При перемещении между двумя карточками выбирается позиция между соседними значениями.

Для уменьшения количества массовых обновлений применяют дробные позиции или лексикографические ключи сортировки.

Со временем может потребоваться перенумерация позиций.

**Многопользовательская работа:**

Backend должен проверять версии данных и разрешать конкурирующие перемещения. Изменения других пользователей можно доставлять через WebSocket.

Также важны:
* Автопрокрутка при перетаскивании.
* Поддержка touch-устройств.
* Управление с клавиатуры.
* Виртуализация больших колонок.
* Проверка разрешённых переходов между статусами.

# Как спроектировать систему ролей и прав доступа для корпоративного приложения?

Основой может быть **RBAC (Role-Based Access Control)** - модель, в которой пользователи получают права через роли.

Например:
* `admin` - управление пользователями и настройками.
* `editor` - создание и изменение документов.
* `viewer` - только чтение.

Однако в корпоративных приложениях RBAC часто комбинируют с **ABAC (Attribute-Based Access Control)**.

ABAC учитывает дополнительные атрибуты: отдел, организацию, владельца ресурса, статус документа и другие условия.

**Архитектура:**

1. Auth Service устанавливает личность пользователя.
2. Backend получает необходимые данные о ролях и разрешениях.
3. При каждом запросе проверяется право на конкретное действие с конкретным ресурсом.
4. Frontend использует разрешения для отображения доступных элементов интерфейса.

Например, роль `editor` может разрешать редактирование документов, но только внутри собственной организации.

**Принципы безопасности:**
* `Deny by default` - отсутствие разрешения означает отказ.
* `Least privilege` - минимально необходимые права.
* Проверка прав на каждом защищённом backend-запросе.
* Изоляция данных разных организаций.
* Аудит критичных действий.
* Инвалидация кеша разрешений после изменения ролей.

**Важно:** скрытие кнопки в React не является защитой. Сервер должен самостоятельно проверять доступ к данным и операциям.

# Как спроектировать локализацию интерфейса для десятков языков?

Для масштабируемой локализации нужно отделить текстовые ресурсы от компонентов и использовать стандартизированные механизмы форматирования.

**Основные компоненты:**
* `i18next`, `react-intl` или аналогичная библиотека.
* Словари переводов для каждой локали.
* `Intl` API для дат, чисел, валют и единиц измерения.
* ICU MessageFormat для сложных сообщений и множественного числа.
* Lazy loading для загрузки только нужных переводов.

**Важные архитектурные решения:**
* Использовать стабильные ключи переводов вместо текста как идентификатора.
* Поддерживать fallback, если перевод отсутствует.
* Учитывать грамматические формы через локализационные правила, а не ручные условия.
* Поддерживать RTL-языки через `dir="rtl"` и логические CSS-свойства.
* Хранить даты в однозначном формате, а форматировать для пользователя.
* Учитывать региональные различия одной языковой группы.

Например, форматирование даты для `en-US` и `en-GB` может отличаться, хотя язык интерфейса английский.

Для публичных многоязычных страниц также используют отдельные локализованные URL и `hreflang`.

**Главная сложность:** масштабирование переводов, поддержка контекста, согласованность терминологии и тестирование интерфейса с длинными строками и RTL.

# Как организовать наблюдаемость и обработку ошибок в большом SPA?

**Observability** позволяет понимать состояние приложения на основе логов, метрик и трассировок.

Для большого SPA важны три направления.

**1. Error Monitoring**

Собирать:
* Необработанные JavaScript-исключения.
* `unhandledrejection`.
* Ошибки сетевых запросов.
* Ошибки рендеринга React.
* Контекст маршрута, версии приложения и браузера.

В React используют `Error Boundary` для перехвата ошибок рендеринга в соответствующей части дерева компонентов.

Однако Error Boundary не перехватывает автоматически все ошибки в обработчиках событий и асинхронном коде.

**2. Performance Monitoring**

Измерять:
* LCP, INP, CLS.
* Время загрузки маршрутов.
* Продолжительность API-запросов.
* Long Tasks и блокировку main thread.
* Ошибки и задержки критических пользовательских действий.

**3. Distributed Tracing**

Связывать frontend-запросы с backend-трассировками через trace context и request ID.

Инструменты: Sentry, OpenTelemetry, Grafana и другие системы мониторинга.

**Важно:** удалять персональные данные, токены и чувствительные поля из телеметрии.

Дополнительно определяют SLI/SLO, настраивают алерты и разделяют ожидаемые бизнес-ошибки и технические сбои.

# Как выбрать схему маршрутизации для приложения с вложенными разделами?

Маршрутизация должна отражать структуру продукта и позволять независимо управлять вложенными разделами.

Для React часто используют **React Router** или маршрутизатор выбранного фреймворка.

**Основные принципы:**
* Nested routes - вложенные маршруты.
* Layout routes - общие оболочки для разделов.
* Dynamic segments - параметры вроде `/users/:userId`.
* Query parameters - фильтры, сортировка, поиск и другие состояния страницы.
* Lazy loading - загрузка кода разделов по необходимости.
* Route-level loading и error handling - независимая обработка данных и ошибок.

Например:

/dashboard
/dashboard/analytics
/dashboard/settings
/projects/:projectId
/projects/:projectId/tasks

Родительский маршрут `/projects/:projectId` может загружать данные проекта и предоставлять общий layout для вложенных страниц.

**Дополнительные решения:**
* Авторизационные проверки до предоставления защищённых данных.
* Восстановление состояния при переходах.
* Обработка неизвестных маршрутов.
* Сохранение фильтров в URL.
* Поддержка прямого открытия вложенной страницы.

Для SPA с History API сервер должен корректно обрабатывать глубокие ссылки и возвращать HTML приложения для клиентских маршрутов, не подменяя реальные API-ошибки.

# Как обеспечить работу приложения при медленном и нестабильном соединении?

Нужно проектировать приложение с учётом высокой задержки, потери соединения и ограниченной пропускной способности.

**Основные подходы:**

* **Progressive Loading** - сначала отображать критически важные данные.
* **Code Splitting** - загружать JavaScript по мере необходимости.
* **Lazy Loading** - откладывать загрузку тяжёлых компонентов и медиа.
* **Кеширование** - повторно использовать ранее загруженные данные.
* **Optimistic UI** - показывать результат действия до подтверждения сервера.
* **Retry with exponential backoff** - повторять временно неудачные операции с увеличивающейся задержкой.
* **Request cancellation** - отменять устаревшие запросы.
* **Offline queue** - сохранять изменения до восстановления соединения.

**Критически важно:** автоматически повторять изменяющие состояние запросы безопасно только при наличии идемпотентности или другого механизма защиты от дублирования.

Например, повтор запроса на создание платежа без idempotency key может привести к повторной операции.

Также необходимо:
* Показывать пользователю состояние соединения и синхронизации.
* Сохранять незавершённые действия.
* Не блокировать весь интерфейс из-за одного медленного запроса.
* Использовать таймауты с учётом типа операции.

`navigator.onLine` можно применять как вспомогательный сигнал, но он не гарантирует доступность конкретного сервера.

# Как организовать обновление клиентского приложения без потери данных формы?

Основная проблема - пользователь может редактировать форму в момент публикации новой версии приложения.

**Стратегия обновления:**

1. Статические ресурсы публикуются с уникальными хешами в именах.
2. Новая версия приложения становится доступной на сервере.
3. Клиент обнаруживает обновление.
4. Если есть несохранённые изменения, обновление откладывается.
5. Данные формы сохраняются локально или на сервере.
6. После безопасного завершения работы пользователь переходит на новую версию.

**Механизмы:**
* `IndexedDB` - сохранение черновиков.
* Autosave - периодическая отправка изменений на сервер.
* Dirty state - отслеживание несохранённых изменений.
* Версионирование структуры черновиков.
* Миграции локальных данных между версиями.

В PWA новый Service Worker может ожидать завершения работы текущих клиентов.

Принудительное применение обновления через `skipWaiting()` требует осторожности: разные версии ресурсов и приложения могут оказаться активны одновременно.

**Важно:** frontend и backend должны поддерживать совместимость во время rollout. Новая версия API не должна мгновенно ломать уже открытые вкладки со старым JavaScript.

Для критических обновлений можно блокировать несовместимые операции, предварительно сохранив пользовательские данные.

# Как синхронизировать состояние между вкладками и устройствами?

Нужно разделять локальную синхронизацию вкладок и синхронизацию через сервер.

**Между вкладками одного браузера:**

Используют:
* `BroadcastChannel` - обмен событиями между вкладками в рамках поддерживаемого контекста хранения.
* `storage` event - уведомление других вкладок об изменении `localStorage`.
* `SharedWorker` - общий процесс для нескольких вкладок там, где он поддерживается.

Например, после выхода из аккаунта одна вкладка отправляет событие `logout`, остальные очищают пользовательское состояние.

**Между устройствами:**

Источником истины обычно является backend.

1. Устройство изменяет данные.
2. Сервер сохраняет новую версию.
3. Изменение распространяется через WebSocket, SSE или другой механизм.
4. Остальные устройства обновляют локальное состояние.

**Важные механизмы:**
* Версионирование состояния.
* Идентификаторы событий.
* Защита от повторной обработки.
* Восстановление пропущенных изменений.
* Инвалидация локального кеша.
* Обработка конфликтов.

`BroadcastChannel` не синхронизирует разные устройства и не заменяет серверное хранение данных.

Для надёжности после переподключения клиент должен получать актуальный snapshot или пропущенные события, а не полагаться только на realtime-уведомления.

# Как решать конфликт изменений нескольких пользователей?

Конфликт возникает, когда несколько пользователей изменяют одну сущность на основе разных версий её состояния.

**Основные стратегии:**

**1. Pessimistic Locking**

Ресурс блокируется на время редактирования.

Другие пользователи не могут изменять его до снятия блокировки.

Подходит для критичных операций, но ограничивает параллельную работу и требует обработки истёкших блокировок.

**2. Optimistic Locking**

Пользователи работают независимо, а конфликт проверяется при сохранении.

Каждая сущность имеет версию.

Если сохранение выполняется на основе устаревшей версии, сервер отклоняет изменение.

Реализуется через поле `version` или HTTP-заголовки `ETag` и `If-Match`.

**3. Last Write Wins**

Последнее принятое изменение заменяет предыдущее.

Простая стратегия, но может приводить к потере данных.

Подходит только там, где такая потеря допустима.

**4. OT и CRDT**

* **Operational Transformation (OT)** - преобразует конкурентные операции так, чтобы они могли применяться согласованно.
* **Conflict-free Replicated Data Types (CRDT)** - структуры данных, предназначенные для сходимости реплик при корректном объединении изменений.

Применяются в совместных редакторах и других realtime-системах.

**Выбор зависит от данных:** для обычных CRUD-форм часто достаточно optimistic locking, а для одновременного редактирования текста нужны специализированные алгоритмы.

# Как определить границы кэша и стратегии инвалидации?

Сначала определяют, **какие данные кешируются, кто ими владеет, насколько они изменчивы и какую устарелость можно допустить**.

**Основные уровни кеширования:**

* Browser HTTP Cache - HTTP-ответы и статические ресурсы.
* CDN Cache - публичные ресурсы и ответы, пригодные для общего кеша.
* Service Worker Cache - данные, необходимые для offline-работы.
* Client Query Cache - результаты API-запросов в памяти приложения.
* Backend Cache - результаты вычислений и обращений к другим сервисам.

**Стратегии:**

**TTL (Time To Live)** - данные считаются актуальными ограниченное время.

**Cache Invalidation** - данные помечаются устаревшими после конкретного изменения.

**Stale While Revalidate** - сначала возвращаются кешированные данные, затем выполняется фоновое обновление.

**Version-based caching** - новая версия ресурса получает новый ключ кеша.

**Ключ кеша** должен включать все параметры, влияющие на результат: идентификатор ресурса, фильтры, язык, организацию и пользователя, если данные персонализированы.

Например, после изменения профиля можно вызвать `queryClient.invalidateQueries()` для связанных запросов.

**Основные риски:**
* Использование устаревших данных.
* Несогласованность нескольких кешей.
* Утечка персональных данных через общий кеш.
* Неправильная инвалидация зависимых ресурсов.

Для чувствительных ответов используют соответствующую HTTP-политику, например `Cache-Control: private` или `no-store`.

# Как рассчитать и контролировать performance budget?

**Performance Budget** - набор измеримых ограничений производительности, превышение которых считается регрессией.

Бюджет задаётся для конкретных пользовательских сценариев и целевых устройств.

**Основные категории:**

**1. Пользовательские метрики**

Core Web Vitals:
* LCP <= 2,5 секунды - скорость появления основного контента.
* INP <= 200 мс - отзывчивость взаимодействий.
* CLS <= 0,1 - визуальная стабильность.

Эти пороги оцениваются по 75-му перцентилю реальных посещений.

**2. Ресурсные ограничения**

Например:
* Максимальный размер начального JavaScript.
* Максимальное количество критических запросов.
* Максимальный объём загружаемых изображений.
* Допустимое время выполнения JavaScript на слабом устройстве.

**3. Бюджеты пользовательских операций**

Например:
* Открытие модального окна.
* Переключение раздела.
* Отображение результатов поиска.
* Сохранение формы.

**Контроль:**

1. Измерить текущую производительность.
2. Определить целевые устройства и сетевые условия.
3. Установить измеримые ограничения.
4. Проверять их в CI с помощью Lighthouse CI и других инструментов.
5. Собирать реальные метрики через RUM.
6. Анализировать регрессии по маршрутам и версиям приложения.

**Важно:** лабораторные тесты показывают воспроизводимые проблемы, а RUM отражает фактический опыт пользователей.

Performance budget должен контролироваться автоматически, иначе постепенно перестаёт соблюдаться.

# Как организовать постепенный rollout новой функциональности?

**Gradual Rollout** - постепенное включение новой функциональности ограниченной части пользователей.

Основной механизм - **Feature Flags**.

**Типичный процесс:**

1. Новая функциональность развёртывается в production, но остаётся выключенной.
2. Флаг включается для внутренних пользователей.
3. Доступ расширяется на небольшую группу.
4. Собираются метрики ошибок, производительности и бизнес-результатов.
5. Доля пользователей постепенно увеличивается.
6. При проблемах флаг отключается.

**Способы управления:**
* По идентификатору пользователя.
* По организации или группе.
* По региону.
* По проценту аудитории.
* По версии приложения.

Для процентного rollout используют стабильное хеширование идентификатора пользователя и ключа флага. Это позволяет сохранять принадлежность пользователя к одной группе между сессиями.

**Важные требования:**
* Kill switch для быстрого отключения функции.
* Совместимость старого и нового поведения с API.
* Мониторинг по группам rollout.
* Разделение feature rollout и экспериментов A/B.
* Удаление временных флагов после завершения rollout.

**Безопасность:** frontend-флаг не является механизмом авторизации. Пользователь может изменить клиентский код, поэтому доступ к защищённым операциям должен контролироваться сервером.

# Какие trade-offs выбрать между SSR и CSR для конкретного продукта?

**SSR (Server-Side Rendering)** - HTML формируется на сервере и отправляется браузеру.

**CSR (Client-Side Rendering)** - основная разметка формируется в браузере с помощью JavaScript.

**SSR:**

Преимущества:
* Быстрая доступность HTML и потенциально более раннее отображение контента.
* Удобство индексации публичных страниц.
* Возможность получать данные до отправки страницы.

Недостатки:
* Дополнительная нагрузка на сервер.
* Более сложная инфраструктура.
* Необходимость гидратации интерактивных компонентов.
* Риск hydration mismatch.
* Более сложное персонализированное кеширование.

**CSR:**

Преимущества:
* Простая модель интерактивного приложения.
* Независимость UI-переходов от серверного HTML.
* Удобство разработки насыщенных интерактивных интерфейсов.
* Возможность раздавать статические ресурсы через CDN.

Недостатки:
* Зависимость первоначального отображения от загрузки и выполнения JavaScript.
* Потенциально худшие показатели первой загрузки.
* Дополнительные сложности SEO для публичного контента.
* Большая нагрузка на браузер пользователя.

**Выбор по типу продукта:**

* Публичный интернет-магазин - SSR или гибридный рендеринг для каталога и карточек товаров.
* Новостной сайт - SSR или SSG для контентных страниц.
* Корпоративная CRM - часто CSR, поскольку важнее интерактивность, а SEO обычно не требуется.
* Аналитический дашборд - CSR или гибридный подход.
* SaaS-приложение с публичным сайтом - SSR/SSG для маркетинговых страниц и CSR для рабочего интерфейса.

**Гибридный подход** позволяет использовать SSR, SSG и CSR для разных маршрутов и компонентов.

При выборе важно учитывать SEO, LCP, TTFB, стоимость серверного рендеринга, гидратацию, персонализацию и характер взаимодействия с интерфейсом.

SSR сам по себе не гарантирует лучшую производительность: тяжёлая гидратация или медленный сервер могут свести преимущества на нет.
