# Как реализовать поисковую строку с debounce и отменой устаревших запросов?

Debounce откладывает выполнение поиска до момента, когда пользователь перестанет вводить текст на заданное время, например 300 мс. Это уменьшает количество запросов к серверу.

`AbortController` отменяет предыдущий запрос при изменении поисковой строки, предотвращая обработку устаревших результатов.

Пример на React:

```
const [query, setQuery] = useState("");
const [results, setResults] = useState([]);

useEffect(() => {
  if (!query.trim()) {
    setResults([]);
    return;
  }

  const controller = new AbortController();

  const timer = setTimeout(async () => {
    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(query)}`,
        { signal: controller.signal }
      );

      if (!response.ok) throw new Error("Search failed");

      const data = await response.json();

      if (!controller.signal.aborted) {
        setResults(data);
      }
    } catch (error) {
      if (!controller.signal.aborted) {
        console.error(error);
      }
    }
  }, 300);

  return () => {
    clearTimeout(timer);
    controller.abort();
  };
}, [query]);
```

При каждом изменении `query` React выполняет cleanup предыдущего эффекта:

- `clearTimeout()` отменяет поиск, если таймер ещё не сработал
- `controller.abort()` отменяет выполняющийся запрос
- Проверка `signal.aborted` предотвращает обновление состояния устаревшими результатами

Важно: отмена `fetch` не гарантирует прекращения обработки на сервере. Если источник запросов не поддерживает отмену, дополнительно используют идентификатор запроса и принимают результат только последнего.

# Как реализовать autocomplete с клавиатурной навигацией?

Autocomplete состоит из поля ввода, списка подсказок и состояния активного элемента.

Основные состояния:

- `query` - введённый текст
- `options` - найденные варианты
- `activeIndex` - индекс подсвеченного варианта
- `isOpen` - состояние списка

Обработка клавиатуры:

- `ArrowDown` - переход к следующему варианту
- `ArrowUp` - переход к предыдущему
- `Enter` - выбор активного варианта
- `Escape` - закрытие списка
- `Home` / `End` - переход к первому или последнему варианту, если предусмотрено

Для доступности используется паттерн ARIA Combobox:

```
<input
  role="combobox"
  aria-autocomplete="list"
  aria-expanded={isOpen}
  aria-controls="suggestions"
  aria-activedescendant={
    activeIndex >= 0
      ? `option-${activeIndex}`
      : undefined
  }
/>

<ul id="suggestions" role="listbox">
  {options.map((option, index) => (
    <li
      key={option.id}
      id={`option-${index}`}
      role="option"
      aria-selected={activeIndex === index}
    >
      {option.label}
    </li>
  ))}
</ul>
```

Фокус остаётся на `input`, а активный вариант обозначается через `aria-activedescendant`.

При изменении результатов необходимо корректировать `activeIndex`, чтобы он не ссылался на несуществующий элемент.

При выборе варианта мышью важно учитывать, что `blur` поля может произойти раньше `click` по подсказке. Это решают обработкой `pointerdown` или корректным управлением фокусом.

Для асинхронных подсказок дополнительно применяются debounce и отмена устаревших запросов.

# Как реализовать вкладки с доступной ARIA-разметкой?

Вкладки реализуются с помощью трёх ARIA-ролей:

- `tablist` - контейнер вкладок
- `tab` - отдельная вкладка
- `tabpanel` - связанная с вкладкой панель содержимого

Пример:

```
<div role="tablist" aria-label="Настройки">
  <button
    id="tab-profile"
    role="tab"
    aria-selected={activeTab === "profile"}
    aria-controls="panel-profile"
    tabIndex={activeTab === "profile" ? 0 : -1}
    onClick={() => setActiveTab("profile")}
  >
    Профиль
  </button>
</div>

<div
  id="panel-profile"
  role="tabpanel"
  aria-labelledby="tab-profile"
  hidden={activeTab !== "profile"}
>
  Содержимое профиля
</div>
```

Клавиатурная навигация:

- `ArrowLeft` / `ArrowRight` - переход между горизонтальными вкладками
- `Home` / `End` - переход к первой или последней
- `Enter` / `Space` - активация вкладки при ручном режиме переключения
- `Tab` - переход из списка вкладок к следующему элементу в порядке фокуса

Внутри `tablist` только одна вкладка должна иметь `tabIndex={0}`. Остальные получают `-1`, чтобы стрелки управляли перемещением между ними.

Существуют два режима активации:

Automatic activation - вкладка активируется сразу при перемещении фокуса стрелками.

Manual activation - стрелки перемещают фокус, а `Enter` или `Space` активирует выбранную вкладку.

Автоматический режим подходит, когда содержимое переключается без заметной задержки.

# Как реализовать dropdown с обработкой клика вне компонента?

Dropdown управляется состоянием `isOpen`. Для определения клика вне компонента используется `ref` и глобальный обработчик `pointerdown`.

```
const [isOpen, setIsOpen] = useState(false);
const dropdownRef = useRef<HTMLDivElement>(null);

useEffect(() => {
  if (!isOpen) return;

  const handlePointerDown = (event: PointerEvent) => {
    if (
      dropdownRef.current &&
      !dropdownRef.current.contains(event.target as Node)
    ) {
      setIsOpen(false);
    }
  };

  document.addEventListener("pointerdown", handlePointerDown);

  return () => {
    document.removeEventListener(
      "pointerdown",
      handlePointerDown
    );
  };
}, [isOpen]);
```

`dropdownRef` должен охватывать кнопку открытия и содержимое dropdown.

Важные особенности:

- При закрытии по `Escape` нужно возвращать фокус на кнопку открытия
- При размонтировании обработчик обязательно удаляется
- Если содержимое отображается через портал, одного `contains()` может быть недостаточно - необходимо учитывать DOM-узлы портала
- Для обычного выпадающего блока не требуется автоматически назначать `role="menu"`: семантика зависит от назначения компонента

Для простого меню действий используют соответствующий ARIA Menu Pattern, а для выбора значения - Listbox или Combobox.

# Как реализовать список с бесконечной прокруткой?

Infinite scroll автоматически загружает следующую порцию данных при приближении пользователя к концу списка.

Для реализации удобно использовать `IntersectionObserver`, который отслеживает появление специального элемента - sentinel - в области видимости.

Основные состояния:

- `items` - загруженные элементы
- `cursor` или `page` - позиция следующей порции данных
- `isLoading` - выполняется ли запрос
- `hasMore` - существуют ли дополнительные данные

Пример наблюдателя:

```
useEffect(() => {
  const observer = new IntersectionObserver(
    ([entry]) => {
      if (entry.isIntersecting && hasMore && !isLoading) {
        loadMore();
      }
    },
    { rootMargin: "200px" }
  );

  const element = sentinelRef.current;

  if (element) observer.observe(element);

  return () => observer.disconnect();
}, [hasMore, isLoading, loadMore]);
```

`rootMargin: "200px"` позволяет начинать загрузку заранее, не дожидаясь достижения конца страницы.

Ключевые моменты:

- Не допускать параллельной загрузки одной и той же страницы. Для защиты от гонок одного `isLoading` иногда недостаточно - используют синхронную блокировку через `ref` или управление запросами
- Добавлять новые элементы к существующим, исключая дубликаты по идентификатору
- Корректно определять окончание списка через `hasMore` или `nextCursor`
- Обрабатывать ошибки и предоставлять возможность повторить запрос
- Отменять неактуальные запросы при смене фильтров или размонтировании

Cursor-based pagination обычно надёжнее пагинации через `offset`, если данные часто добавляются или удаляются: смещение может приводить к пропускам и дублированию элементов.

Для больших списков infinite scroll часто комбинируют с виртуализацией.

# Как реализовать виртуализированный список?

Виртуализация позволяет отображать только элементы, находящиеся в видимой области прокрутки, вместо создания DOM-узлов для всего списка.

Например, при наличии 100 000 элементов в DOM могут находиться только 20-40.

Для списка с фиксированной высотой элементов:

1. Определяем высоту контейнера `containerHeight` и элемента `itemHeight`.
2. Отслеживаем текущую позицию прокрутки `scrollTop`.
3. Вычисляем диапазон видимых элементов.
4. Рендерим только этот диапазон.
5. Сохраняем общую высоту списка, чтобы скроллбар отражал реальное количество элементов.

Основные вычисления:

```
const startIndex = Math.max(
  0,
  Math.floor(scrollTop / itemHeight) - overscan
);

const visibleCount =
  Math.ceil(containerHeight / itemHeight);

const endIndex = Math.min(
  items.length,
  startIndex + visibleCount + 2 * overscan
);

const visibleItems = items.slice(startIndex, endIndex);
```

`overscan` - дополнительные элементы за пределами видимой области, уменьшающие вероятность появления пустых участков при быстрой прокрутке.

Общая высота:

```
const totalHeight = items.length * itemHeight;
```

Элементы размещаются с соответствующим смещением, например через `position: absolute` и `transform: translateY(...)`.

Главная сложность - переменная высота элементов. В этом случае размеры измеряются динамически, например через `ResizeObserver`, а позиции рассчитываются по накопленным высотам.

Также необходимо учитывать сохранение фокуса, доступность клавиатурной навигации и изменение размеров контейнера.

Готовые решения: `@tanstack/react-virtual`, `react-window`.

# Как реализовать таблицу с сортировкой, фильтрацией и пагинацией?

Реализация строится вокруг исходного массива данных и состояния параметров отображения.

Основные состояния:

- `sorting` - поле сортировки и направление `asc` / `desc`
- `filters` - активные фильтры
- `page` - текущая страница
- `pageSize` - количество записей на странице

Порядок преобразования данных:

1. Фильтрация исходных записей.
2. Сортировка отфильтрованных записей.
3. Пагинация полученного результата.

Пример:

```
const visibleRows = useMemo(() => {
  const filtered = rows.filter(row =>
    row.name.toLowerCase().includes(search.toLowerCase())
  );

  const sorted = [...filtered].sort((a, b) =>
    a.name.localeCompare(b.name) * sortDirection
  );

  const start = (page - 1) * pageSize;

  return sorted.slice(start, start + pageSize);
}, [rows, search, sortDirection, page, pageSize]);
```

Здесь `sortDirection` равен `1` для сортировки по возрастанию и `-1` для убывания.

Важные особенности:

- Не изменять исходный массив через `sort()` - сначала создавать копию
- При изменении фильтров обычно сбрасывать страницу на первую
- Корректно обрабатывать разные типы данных: числа, строки, даты, `null`
- Для доступности указывать `aria-sort` на заголовке текущего столбца сортировки
- Обеспечивать стабильный порядок записей при равных значениях

Для больших наборов данных используют server-side sorting, filtering и pagination: клиент передаёт параметры серверу, а сервер возвращает только нужную часть данных и общее количество записей.

Важно не смешивать серверную пагинацию с локальной сортировкой ограниченной выборки, иначе пользователь получит некорректный глобальный порядок данных.

# Как реализовать чекбоксы с выбором всех и промежуточным состоянием?

Для группы чекбоксов используется коллекция выбранных идентификаторов, например `Set`.

```
const [selectedIds, setSelectedIds] = useState(
  new Set<string>()
);
```

Состояние общего чекбокса определяется количеством выбранных элементов:

- Unchecked - не выбран ни один элемент
- Checked - выбраны все элементы
- Indeterminate - выбрана только часть элементов

```
const allSelected =
  items.length > 0 &&
  items.every(item => selectedIds.has(item.id));

const someSelected =
  items.some(item => selectedIds.has(item.id));

const isIndeterminate = someSelected && !allSelected;
```

У нативного HTML-чекбокса `indeterminate` - DOM-свойство, а не HTML-атрибут. Поэтому его необходимо установить через `ref`:

```
const checkboxRef = useRef<HTMLInputElement>(null);

useEffect(() => {
  if (checkboxRef.current) {
    checkboxRef.current.indeterminate = isIndeterminate;
  }
}, [isIndeterminate]);
```

При нажатии общего чекбокса:

- Если выбраны все - снимаем выделение
- Иначе - выбираем все элементы группы

Обновление `Set` выполняется через создание новой коллекции, чтобы React обнаружил изменение состояния.

Важный нюанс: в таблицах с фильтрацией и пагинацией необходимо определить область действия «Выбрать все»: текущая страница, все отфильтрованные записи или вся выборка на сервере. Это разные сценарии, требующие разной логики.

# Как реализовать форму с динамическим добавлением полей?

Динамическая форма хранит список полей в массиве объектов. Каждое поле должно иметь стабильный уникальный идентификатор.

```
const [fields, setFields] = useState([
  { id: crypto.randomUUID(), value: "" }
]);

const addField = () => {
  setFields(prev => [
    ...prev,
    { id: crypto.randomUUID(), value: "" }
  ]);
};

const removeField = (id: string) => {
  setFields(prev => prev.filter(field => field.id !== id));
};

const updateField = (id: string, value: string) => {
  setFields(prev =>
    prev.map(field =>
      field.id === id ? { ...field, value } : field
    )
  );
};
```

При рендеринге необходимо использовать `key={field.id}`, а не индекс массива.

Почему индекс использовать опасно: после удаления или перестановки полей React может повторно использовать компонент для другого элемента. Это способно приводить к неправильному сопоставлению состояния, ошибок валидации и DOM-элементов.

Для каждого поля можно независимо хранить:

- Значение
- Ошибки валидации
- Состояние `touched`
- Признак обязательности

Если поля образуют сложные вложенные структуры, удобнее использовать React Hook Form с `useFieldArray` или аналогичный механизм управления массивами полей.

# Как реализовать мультишаговую форму с сохранением промежуточных данных?

Мультишаговая форма разделяет заполнение данных на несколько последовательных этапов, сохраняя общее состояние между ними.

Основные состояния:

- `currentStep` - текущий шаг
- `formData` - все введённые данные
- `errors` - ошибки валидации

Все шаги должны использовать единый источник данных, например состояние родительского компонента, `Context` или form-библиотеку.

Алгоритм работы:

1. Пользователь заполняет текущий шаг.
2. При нажатии «Далее» выполняется валидация полей текущего шага.
3. Если данные корректны, обновляется `currentStep`.
4. При переходе назад значения восстанавливаются из общего состояния.
5. На последнем шаге выполняется итоговая валидация и отправка данных.

Для сохранения между перезагрузками можно использовать `sessionStorage`, `localStorage` или серверный черновик.

```
useEffect(() => {
  localStorage.setItem(
    "formDraft",
    JSON.stringify(formData)
  );
}, [formData]);
```

При инициализации формы данные читаются из хранилища и проверяются на соответствие ожидаемой структуре.

Важные нюансы:

- Валидация по шагам не заменяет итоговую проверку перед отправкой
- При изменении данных предыдущих шагов необходимо перепроверять зависимые поля
- Не следует сохранять пароли и другую чувствительную информацию в `localStorage`
- Для сложных форм полезно версионировать структуру черновика
- Серверное сохранение предпочтительно, если требуется продолжение заполнения на другом устройстве

# Как реализовать drag-and-drop список с переупорядочиванием?

Drag-and-drop позволяет перетаскивать элементы, изменяя их порядок в массиве.

Каждый элемент должен иметь стабильный `id`. При завершении перетаскивания определяются идентификаторы перемещаемого элемента и цели, после чего вычисляется новый порядок.

Пример функции перестановки:

```
function reorder<T>(
  items: T[],
  from: number,
  to: number
): T[] {
  const result = [...items];

  const [movedItem] = result.splice(from, 1);

  result.splice(to, 0, movedItem);

  return result;
}
```

Основной процесс:

1. Пользователь начинает перетаскивание.
2. Сохраняется идентификатор активного элемента.
3. При перемещении определяется текущая цель.
4. Отображается визуальная обратная связь.
5. При отпускании вычисляется новый порядок.
6. Состояние обновляется без мутации исходного массива.

Для реализации можно использовать нативный HTML Drag and Drop API или специализированные библиотеки, например `dnd-kit`.

Ограничения нативного API: его сложнее использовать для сенсорного управления, анимаций и доступного переупорядочивания с клавиатуры.

Для полноценной доступности необходимо обеспечить возможность захватить элемент, перемещать его и завершать операцию с клавиатуры, а также озвучивать изменения позиции через доступные уведомления.

Если порядок сохраняется на сервере, обновление можно выполнять оптимистично с откатом при ошибке.

# Как реализовать таймер с паузой, сбросом и корректной очисткой?

Таймер должен поддерживать три основные операции:

- `start` - запуск или продолжение отсчёта
- `pause` - остановка с сохранением прошедшего времени
- `reset` - возврат к начальному состоянию

Главный принцип: не считать время количеством срабатываний `setInterval`, поскольку браузер не гарантирует точного выполнения таймеров, особенно в фоновых вкладках.

Вместо этого рассчитывают время относительно `performance.now()`.

Для реализации используются:

- `elapsedRef` - накопленное время до последней паузы
- `startedAtRef` - момент последнего запуска
- `isRunning` - состояние таймера
- `remaining` - отображаемое оставшееся время

При запуске сохраняется:

```
startedAtRef.current = performance.now();
```

При обновлении:

```
const elapsed =
  elapsedRef.current +
  (performance.now() - startedAtRef.current);

const remaining = Math.max(0, duration - elapsed);
```

При паузе разница между текущим временем и `startedAtRef` добавляется к `elapsedRef`, а интервал останавливается.

При продолжении сохраняется новое время запуска без сброса накопленного значения.

При `reset` накопленное время обнуляется, интервал очищается, а `remaining` возвращается к исходному значению.

В React интервал создают внутри `useEffect`, а `clearInterval` вызывают в cleanup.

Важно: `setInterval` нужен только для обновления интерфейса. Источником истины остаётся прошедшее время, рассчитанное по часам.

Если таймер должен сохраняться после перезагрузки страницы, можно хранить абсолютный момент завершения на основе `Date.now()`, учитывая, что системное время может изменяться.

# Как реализовать toast notification manager?

Toast manager - централизованный механизм управления всплывающими уведомлениями.

Обычно реализуется через `ToastProvider` и React Context, чтобы любой компонент мог вызвать уведомление без передачи callback через множество уровней.

Каждый toast содержит:

```
type Toast = {
  id: string;
  message: string;
  type: "success" | "error" | "info" | "warning";
  duration?: number;
};
```

Менеджер предоставляет основные операции:

- `addToast()` - добавление уведомления
- `removeToast()` - удаление по идентификатору
- `clearToasts()` - удаление всех уведомлений

Добавление:

```
const addToast = (message: string) => {
  const id = crypto.randomUUID();

  setToasts(prev => [
    ...prev,
    { id, message, type: "info" }
  ]);
};
```

Автоматическое удаление реализуется через `setTimeout`. Для каждого уведомления создаётся отдельный таймер, который необходимо очищать при ручном закрытии и размонтировании.

В полноценной реализации также учитываются:

- Ограничение количества одновременно видимых уведомлений
- Очередь ожидающих уведомлений
- Пауза автозакрытия при наведении или взаимодействии
- Предотвращение дублирования одинаковых уведомлений
- Сохранение стабильных идентификаторов

Для доступности используют `role="status"` или `aria-live="polite"` для обычных уведомлений и `role="alert"` для действительно срочных ошибок.

Критически важная информация не должна исчезать исключительно по таймеру.

# Как реализовать кнопку с optimistic update и rollback?

Optimistic update - обновление интерфейса до получения подтверждения от сервера.

Например, при нажатии кнопки «Нравится» счётчик или состояние кнопки меняется сразу, без ожидания ответа API.

Основной алгоритм:

1. Сохраняем предыдущее состояние.
2. Оптимистично обновляем интерфейс.
3. Отправляем запрос на сервер.
4. При успехе оставляем новое состояние.
5. При ошибке выполняем rollback - откат к предыдущему состоянию.

Пример:

```
const [liked, setLiked] = useState(false);
const [pending, setPending] = useState(false);

const toggleLike = async () => {
  if (pending) return;

  const previous = liked;
  const next = !previous;

  setLiked(next);
  setPending(true);

  try {
    await api.updateLike(next);
  } catch {
    setLiked(previous);
  } finally {
    setPending(false);
  }
};
```

Основная проблема - конкурентные изменения.

Если пользователь несколько раз изменит одно значение до завершения предыдущих запросов, простой откат может перезаписать более актуальное состояние.

Для предотвращения используют блокировку повторных операций, идентификаторы запросов или механизм управления мутациями.

В React Query / TanStack Query optimistic update обычно реализуется через `onMutate`, `onError` и последующую инвалидацию запроса.

Для критичных операций необходимо учитывать серверные конфликты, а после мутации при необходимости синхронизировать состояние с сервером.

# Как реализовать переключение темы с сохранением выбора?

Переключение темы обычно реализуется через CSS-переменные и атрибут `data-theme` на корневом элементе документа.

```
:root {
  --background: #ffffff;
  --text: #111111;
}

[data-theme="dark"] {
  --background: #111111;
  --text: #ffffff;
}

body {
  background: var(--background);
  color: var(--text);
}
```

При переключении обновляется атрибут:

```
document.documentElement.dataset.theme = "dark";
```

Выбор сохраняется в `localStorage`:

```
localStorage.setItem("theme", "dark");
```

При инициализации тема определяется по приоритету:

1. Явно сохранённый выбор пользователя.
2. Системная настройка `prefers-color-scheme`.
3. Тема по умолчанию.

Системную тему определяют через:

```
window.matchMedia("(prefers-color-scheme: dark)").matches
```

Если предусмотрен режим `system`, необходимо подписаться на событие `change` у `MediaQueryList`, чтобы тема автоматически обновлялась при изменении настроек ОС.

Важные нюансы:

- Чтобы избежать мигания неправильной темы при загрузке, атрибут желательно устанавливать до первого отображения страницы
- В SSR-приложениях нельзя обращаться к `window` и `localStorage` во время серверного рендеринга
- CSS-свойство `color-scheme` помогает браузеру правильно оформлять встроенные элементы управления
- Доступ к `localStorage` может завершиться ошибкой, поэтому желательно предусмотреть fallback

# Как реализовать загрузчик файлов с progress bar?

Загрузчик состоит из `input[type="file"]`, механизма отправки файла и состояния прогресса.

Для отображения реального прогресса отправки удобно использовать `XMLHttpRequest`, поскольку он поддерживает событие `upload.onprogress`.

```
const uploadFile = (file: File) => {
  const xhr = new XMLHttpRequest();

  const formData = new FormData();
  formData.append("file", file);

  xhr.open("POST", "/api/upload");

  xhr.upload.onprogress = event => {
    if (event.lengthComputable) {
      const percent = Math.round(
        (event.loaded / event.total) * 100
      );

      setProgress(percent);
    }
  };

  xhr.onload = () => {
    if (xhr.status >= 200 && xhr.status < 300) {
      setStatus("success");
    } else {
      setStatus("error");
    }
  };

  xhr.onerror = () => setStatus("error");

  xhr.send(formData);

  return () => xhr.abort();
};
```

`event.loaded` - количество отправленных байтов, `event.total` - общий размер передаваемых данных, когда он известен.

Важные особенности:

- `fetch` не предоставляет универсального стандартного события прогресса загрузки, аналогичного `XMLHttpRequest.upload.onprogress`
- 100% отправленных байтов не означает, что сервер завершил обработку файла
- Не нужно вручную задавать `Content-Type: multipart/form-data` при отправке `FormData` - браузер сам установит корректный `boundary`
- Для отмены загрузки используется `xhr.abort()`
- Для нескольких файлов прогресс можно отслеживать отдельно либо рассчитывать общий по переданным байтам

Проверку расширения, MIME-типа и размера файла необходимо проводить не только на клиенте, но и на сервере. Клиентская валидация не является защитой.

# Как реализовать адаптивное боковое меню с доступной клавиатурной навигацией?

Адаптивное боковое меню меняет способ отображения в зависимости от ширины экрана.

Обычно:

- На десктопе меню постоянно видно или оно сворачивается до компактного состояния
- На мобильных устройствах меню открывается кнопкой и отображается поверх содержимого

Для адаптивности используются CSS Media Queries, а состояние мобильного меню управляется через `isOpen`.

Кнопка открытия:

```
<button
  type="button"
  aria-expanded={isOpen}
  aria-controls="sidebar"
  aria-label="Открыть навигацию"
  onClick={() => setIsOpen(prev => !prev)}
>
  <MenuIcon />
</button>
```

Сам блок навигации:

```
<nav id="sidebar" aria-label="Основная навигация">
  <a href="/dashboard">Главная</a>
  <a href="/settings">Настройки</a>
</nav>
```

Требования к доступности:

1. Все интерактивные элементы должны быть доступны через `Tab` и `Shift+Tab`.
2. Текущую страницу желательно обозначать через `aria-current="page"`.
3. При открытии мобильного модального меню фокус должен перемещаться внутрь.
4. `Escape` должен закрывать меню.
5. При закрытии фокус должен возвращаться на кнопку открытия.
6. Если меню модальное, фокус удерживается внутри, а фоновый контент становится недоступен для взаимодействия.

Для мобильного модального меню можно использовать нативный `<dialog>` с `showModal()`, внутри которого располагается `<nav>`.

Важно: обычная навигация с ссылками не требует `role="menu"` и управления стрелками. Нативная клавиатурная навигация через `Tab` предпочтительнее.

Также необходимо учитывать переключение между мобильной и десктопной версиями при изменении ширины окна, чтобы не оставлять некорректное состояние фокуса.

# Как реализовать чат с автоматической прокруткой и сохранением позиции чтения?

Основная задача - автоматически прокручивать чат вниз при появлении новых сообщений, но не мешать пользователю читать предыдущие.

Для этого необходимо отслеживать, находился ли пользователь возле конца списка до добавления новых сообщений.

Проверка:

```
const isNearBottom = (element: HTMLElement) => {
  const threshold = 80;

  return (
    element.scrollHeight -
    element.scrollTop -
    element.clientHeight < threshold
  );
};
```

Если пользователь находится внизу, после добавления нового сообщения выполняется:

```
container.scrollTop = container.scrollHeight;
```

Если пользователь прокрутил историю вверх, автоматическая прокрутка не выполняется. Вместо неё можно показывать кнопку «Новые сообщения».

Для сохранения позиции при загрузке старых сообщений сверху используется компенсация изменения высоты контейнера.

Перед добавлением:

```
const oldHeight = container.scrollHeight;
const oldScrollTop = container.scrollTop;
```

После обновления DOM:

```
container.scrollTop =
  oldScrollTop +
  (container.scrollHeight - oldHeight);
```

Это сохраняет положение ранее видимых сообщений, несмотря на появление новых элементов сверху.

В React такие измерения и изменения позиции обычно выполняются с использованием `useLayoutEffect`, когда необходимо избежать визуального скачка.

Дополнительные нюансы:

- Изображения могут изменять высоту сообщений после загрузки. Для компенсации можно использовать `ResizeObserver`
- Для больших историй сообщений необходима виртуализация
- Для плавной прокрутки вниз можно использовать `scrollTo({ behavior: "smooth" })`, но при частом поступлении сообщений она может мешать
- Новые сообщения нужно добавлять с устойчивыми уникальными идентификаторами
- Для обновления истории в реальном времени можно использовать WebSocket или SSE

Главный принцип - автоматически прокручивать чат только тогда, когда пользователь уже находился возле конца истории.

# Как реализовать редактируемую таблицу с валидацией и сохранением изменений?

Редактируемая таблица позволяет изменять значения непосредственно в ячейках или строках без перехода на отдельную страницу.

Основные состояния:

- `rows` - исходные данные таблицы
- `editingCell` - редактируемая ячейка
- `draftValues` - временные изменения
- `errors` - ошибки валидации
- `saving` - состояние сохранения

Алгоритм реализации:

1. При клике по ячейке включается режим редактирования.
2. Значение копируется в локальное состояние черновика.
3. Пользователь изменяет значение через `input`, `select` или другой контрол.
4. Перед сохранением выполняется валидация.
5. При успешной валидации отправляется запрос на сервер.
6. После подтверждения обновляются основные данные таблицы.
7. При ошибке пользователь получает сообщение, а несохранённые изменения остаются доступны для исправления.

Пример простой валидации:

```
function validateAge(value: number): string | null {
  if (!Number.isInteger(value)) {
    return "Возраст должен быть целым числом";
  }

  if (value < 0 || value > 120) {
    return "Недопустимый возраст";
  }

  return null;
}
```

Варианты сохранения:

- `onBlur` - при потере фокуса
- `Enter` - при подтверждении редактирования
- Кнопка «Сохранить» - для отдельной строки или всей таблицы
- Автосохранение с debounce - при изменении значений

Для клавиатурной навигации обычно реализуют `Enter` для подтверждения и `Escape` для отмены редактирования.

Важные особенности:

- Не изменять исходные строки до подтверждения сохранения, если не используется optimistic update
- Хранить черновики по идентификаторам строк и полей, а не по индексам
- Отображать ошибки рядом с соответствующими полями
- Предотвращать конфликтующие параллельные запросы
- Учитывать ситуацию, когда одну запись одновременно редактируют несколько пользователей

Для защиты от перезаписи чужих изменений можно применять optimistic concurrency control с версией записи или HTTP-заголовками `ETag` и `If-Match`.

Для частичного обновления данных обычно используют `PATCH`, передавая только изменённые поля.

При больших таблицах редактирование комбинируют с виртуализацией, учитывая необходимость сохранять черновики при размонтировании ячеек за пределами видимой области.
