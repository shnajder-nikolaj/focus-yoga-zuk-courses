# Какие инварианты и state machines нужно определить для заказа, оплаты и резерва?

Заказ, payment attempt и reservation имеют разные state machines и собственные IDs. Например, заказ ожидает оплату, платёж требует действия пользователя или находится в обработке, а запас уже временно зарезервирован. Один общий флаг `paid` не описывает этот процесс.

Фиксируют инварианты: сумма и currency оплаты соответствуют согласованному заказу; одна payment operation не создаёт повторное списание; остаток не уходит ниже допустимой границы. Определяют допустимые переходы, владельца решения и обработку неизвестного исхода. Cancellation, capture и refund не считают взаимозаменяемыми состояниями.

# Как проектировать создание заказа и платёжную попытку при повторе клиентского запроса?

Client request связывают с idempotency key, subject и fingerprint существенных параметров. В локальной transaction создают либо находят тот же заказ и payment operation, сохраняя устойчивый результат. Иной payload с тем же key не должен молча создавать другое действие.

Провайдеру передают стабильный key этой payment operation, а не новый key на каждую сетевую попытку. Проверяют scope, retention и семантику idempotency конкретной API version. После истечения её окна слепой повтор может быть небезопасен: сначала восстанавливают известный результат. [Stripe: Idempotent requests](https://docs.stripe.com/api/idempotent_requests).

# Как согласовать локальную запись заказа и вызов платёжного провайдера без общей транзакции?

Сначала устойчиво записывают намерение и связь с заказом, например вместе с outbox record. Worker вызывает провайдера и сохраняет external ID и результат. Сбой после внешнего успеха до локальной записи оставляет неизвестный исход, поэтому retry использует прежнюю operation identity и предусмотренную provider idempotency.

Outbox устраняет потерю локального намерения, но не создаёт общую transaction с провайдером. Неизвестный исход переводят в проверяемое промежуточное состояние с reconciliation. Возврат ответа UI и возврат пользователя с внешней страницы не являются доказательством окончательной оплаты.

# Как payment webhooks, polling и reconciliation восстанавливают фактический исход оплаты?

Webhook проверяют по подписи и правилам replay, затем надёжно сохраняют событие или задание до успешного acknowledgement. Обработка проверяет event ID и допустимый переход, поскольку deliveries могут повторяться и приходить в ином порядке.

Polling восстанавливает актуальное состояние по external ID, когда событие задержалось или исход запроса неизвестен. Reconciliation систематически сравнивает локальные operations и данные провайдера, выделяя расхождения для исправления. Event timestamp не заменяет корректный state transition и дедупликацию. [Stripe: Webhooks](https://docs.stripe.com/webhooks#event-ordering).

# Как reservation и conditional updates предотвращают overselling общего остатка?

Для SKU задают authoritative состояние доступного, reserved и проданного количества. Создание reservation и уменьшение доступного остатка выполняют атомарно, например условным update с проверкой достаточности и записью уникального reservation ID в той же transaction.

При конфликте одна попытка получает business rejection или повторяет transaction по установленным правилам. Cache каталога может показывать приблизительную доступность, но не подтверждает резерв. Для нескольких SKU определяют atomicity и порядок locks либо saga с явной компенсацией. Eventual counters без дополнительного протокола не гарантируют отсутствие overselling.

# Как TTL резерва и поздний ответ оплаты согласуются при конкурентном истечении брони?

Истечение — это условный переход состояния reservation, а не факт, что cleanup job успел удалить строку. Конкурирующие процессы оплаты и освобождения должны сериализовать или атомарно проверять актуальные state, version и deadline.

Если место уже освобождено и передано другому заказу, поздняя успешная оплата не может автоматически подтвердить старую бронь. Нужна согласованная бизнес-политика: повторное резервирование при наличии, предложение альтернативы либо отдельный refund process. Компенсация тоже может задержаться, поэтому промежуточный статус остаётся наблюдаемым до завершения.

# Как атомарно бронировать уникальное место или несколько пересекающихся временных интервалов?

Для конкретного места фиксируют уникальность активного закрепления или атомарно меняют состояние его authoritative record. При бронировании диапазона времени проверка «сначала SELECT, потом INSERT» без координации допускает конфликтующие записи.

В PostgreSQL подходящий range type и exclusion constraint могут запретить пересечение для одного resource; для равенства resource ID может потребоваться соответствующий operator class. Границы интервала, например `[start, end)`, определяют явно. Несколько мест бронируют в одной transaction, если требуется all-or-nothing, с постоянным порядком locks. [PostgreSQL: Exclusion Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-EXCLUSION).

# Как saga управляет отменой заказа, освобождением резерва и возвратом платежа?

Saga хранит состояние процесса и результат каждого шага: reservation, payment, confirmation и необходимых compensations. Команды имеют устойчивые operation IDs, а переходы переживают повтор и рестарт coordinator. Таймаут означает необходимость выяснить результат, а не автоматически окончательный отказ.

Освобождение резерва и refund — новые действия с собственными ошибками; они не являются мгновенным rollback уже выполненной операции. Процесс может временно находиться в `compensation_pending`. Определяют границы автоматического retry, ручной разбор и запрет позднего события повторно запустить завершённый шаг.

# Как ledger и audit trail помогают находить расхождения в платёжном процессе?

**Ledger** хранит устойчивые записи о денежных движениях и их связи с бизнес-операциями. Суммы представлены точными значениями в заданной currency, а не двоичным floating point. В модели двойной записи проверяют баланс записей в выбранной учётной единице.

Audit trail объясняет, кто и почему инициировал переход, какие IDs и версии участвовали. Исправление проводят отдельной корректирующей записью, сохраняя историю. Сверяют payment, refund, provider fees и settlement по определённым правилам: сумма успешно оплаченных заказов не обязательно равна сумме одного банковского поступления.

# Как проверять платёжно-складской процесс при гонках, повторных событиях и неизвестном исходе?

Проверяют два параллельных заказа на последний остаток, один key с разными payloads, повтор webhook и сбой между внешним успехом и локальным commit. Отдельно моделируют истечение reservation одновременно с оплатой и restart во время компенсации.

Критерии — сохранение инвариантов, отсутствие повторного side effect, достижимость конечного либо явно разбираемого состояния. Время и ответы dependencies контролируют в тестовом окружении. Проверка только HTTP status не обнаружит повторное списание или потерю резерва: анализируют историю operations, записи БД и итог reconciliation.
