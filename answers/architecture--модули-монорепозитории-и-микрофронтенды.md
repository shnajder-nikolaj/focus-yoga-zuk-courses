# Что считать модулем в frontend-приложении?

Модуль - логически самостоятельная часть приложения, которая решает определённую задачу, имеет чёткие границы, публичный API и скрытую реализацию.

Например, модуль `auth` может содержать компоненты авторизации, бизнес-логику, API-запросы и состояние.

Хороший модуль обладает высокой связностью внутри (cohesion) и низкой зависимостью от других модулей (coupling). Его внутреннюю реализацию можно менять без необходимости изменять потребителей, если публичный контракт остаётся прежним.

# Чем модульность на уровне JavaScript отличается от модульности архитектуры?

Модульность JavaScript - технический механизм организации кода через `import` и `export`. Он позволяет разделять файлы, управлять зависимостями и областью видимости.

Архитектурная модульность - разделение системы по ответственности, бизнес-возможностям и контрактам взаимодействия.

Можно иметь сотни JavaScript-модулей, но плохую архитектуру, если они произвольно зависят друг от друга.

Главное различие: JavaScript-модули определяют, как код связан технически, а архитектурные модули - как распределена ответственность в системе.

# Что такое cohesion и coupling и как они влияют на поддержку проекта?

Cohesion (связность) - степень, в которой элементы одного модуля относятся к общей задаче. Высокая связность означает, что модуль содержит функциональность с единой ответственностью.

Coupling (зацепление) - степень зависимости модулей друг от друга. Чем сильнее модули зависят от внутренних деталей соседей, тем сложнее изменять их независимо.

Желательная архитектура - high cohesion, low coupling.

Это уменьшает область влияния изменений, упрощает тестирование и позволяет развивать модули независимо. При этом важно учитывать не только количество зависимостей, но и их характер: зависимость от стабильного интерфейса обычно безопаснее зависимости от изменяемой реализации.

# Как проектировать публичный API внутреннего пакета?

Публичный API определяет, какие возможности пакета доступны внешним потребителям и какие гарантии он предоставляет.

Основные принципы:

- Минимальный API - экспортировать только необходимые компоненты, функции и типы.
- Стабильные контракты - избегать изменений, ломающих существующих потребителей.
- Инкапсуляция - скрывать внутренние файлы, состояние и детали реализации.
- Явные зависимости - не заставлять потребителя знать внутреннюю структуру пакета.
- Предсказуемое поведение - документировать входные данные, результаты и ошибки.

Обычно публичные экспорты собирают в `index.ts`, а доступные пути дополнительно ограничивают через `package.json` и поле `exports`.

Например, потребитель должен импортировать `@app/auth`, а не `@app/auth/src/internal/session-manager`.

# Как разграничить domain modules и инфраструктурные модули?

Domain modules реализуют предметную область приложения: бизнес-правила, сущности и пользовательские сценарии. Например, `orders`, `payments`, `catalog`.

Инфраструктурные модули предоставляют технические механизмы: HTTP-клиенты, логирование, хранение данных, аналитику и интеграции.

Основной принцип - бизнес-логика не должна зависеть от конкретной инфраструктурной реализации.

Например, доменный модуль может определять интерфейс `PaymentGateway`, а инфраструктурный модуль реализовывать его через конкретный платёжный API.

Это позволяет заменять технические реализации, не переписывая бизнес-правила. Связь обычно организуют через интерфейсы, dependency injection или композицию на уровне приложения.

# Когда выбирать монорепозиторий, а когда несколько репозиториев?

Монорепозиторий (monorepo) - один репозиторий для нескольких приложений и пакетов.

Подходит, когда проекты активно используют общий код, часто меняются совместно и нуждаются в единых инструментах, зависимостях и проверках. Позволяет выполнять атомарные изменения сразу в нескольких пакетах.

Несколько репозиториев (polyrepo) подходят, когда проекты имеют независимые команды, жизненные циклы, политики доступа или практически не разделяют код.

Главный компромисс:

- Monorepo упрощает совместную разработку, но требует управления графом зависимостей и эффективного CI.
- Polyrepo обеспечивает более явную организационную изоляцию, но усложняет синхронные изменения между проектами.

Выбор репозитория не определяет способ деплоя: в монорепозитории приложения также могут выпускаться независимо.

# Чем npm/pnpm/Yarn workspaces отличаются от Nx и Turborepo?

npm, pnpm и Yarn workspaces - механизмы пакетных менеджеров, позволяющие управлять несколькими пакетами внутри одного репозитория.

Они отвечают за установку, разрешение и связывание зависимостей между workspace-пакетами.

Nx и Turborepo - инструменты оркестрации задач в монорепозитории.

Они предоставляют:

- Построение графа задач и зависимостей.
- Выполнение задач в правильном порядке.
- Локальное и удалённое кэширование результатов.
- Параллельное выполнение независимых задач.
- Оптимизацию проверок и сборок.

Nx дополнительно предоставляет развитые инструменты анализа проектов, генераторы и средства контроля архитектуры.

Эти решения не исключают друг друга: например, `pnpm workspaces` управляет пакетами, а `Turborepo` организует их сборку и тестирование.

# Как организовать общие библиотеки в монорепозитории?

Общие библиотеки размещают в отдельных workspace-пакетах, обычно внутри `packages/` или `libs/`.

Разделять их следует по ответственности, например:

- `packages/ui` - переиспользуемые UI-компоненты.
- `packages/utils` - независимые утилиты.
- `packages/api-client` - клиентские API-адаптеры.
- `packages/types` - действительно общие типовые контракты.
- `packages/config` - конфигурации инструментов.

У каждого пакета должны быть собственный `package.json`, публичный API, явно объявленные зависимости и необходимые проверки.

Не стоит превращать общую библиотеку в универсальный `shared`, куда помещается несвязанная функциональность. Это увеличивает coupling и приводит к ненужным зависимостям.

# Что такое task graph и affected builds?

Task graph - направленный граф задач, определяющий порядок их выполнения с учётом зависимостей.

Например, если `app:build` требует `ui:build`, сборка UI должна завершиться раньше сборки приложения. Независимые задачи могут выполняться параллельно.

Affected builds - механизм определения задач, результаты которых потенциально затронуты изменениями.

Он использует изменения файлов, зависимости проектов и конфигурацию входных данных задач.

Например, изменение пакета `ui` может потребовать пересборки приложений, которые его используют, но не затронуть независимые сервисы.

Важно: в Nx зависимость в графе выполнения сама по себе не гарантирует попадание задачи в `affected`. Влияние изменений определяется настроенными `inputs` и зависимостями между ними.

# Как настроить кэширование сборки по зависимостям?

Кэширование основано на вычислении хеша входных данных задачи.

В хеш должны попадать все данные, влияющие на результат:

- Исходные файлы и необходимые зависимости.
- Конфигурация сборки и версии инструментов.
- Lockfile и версии пакетов.
- Значимые переменные окружения.
- Аргументы команды.

Если хеш совпадает с предыдущим запуском, инструмент восстанавливает сохранённые артефакты вместо повторного выполнения задачи.

Необходимо правильно указать `inputs`, `outputs` и зависимости задач в Nx или Turborepo.

Основной риск - некорректный кэш при неучтённых входных данных или недетерминированной сборке. Например, если результат зависит от переменной окружения, отсутствующей в хеше, можно получить устаревший артефакт.

Локальный кэш ускоряет повторные сборки разработчика, удалённый позволяет переиспользовать результаты между разработчиками и CI.

# Как версионировать общие пакеты и выпускать изменения?

Обычно используют Semantic Versioning (SemVer):

- `MAJOR` - несовместимые изменения публичного API.
- `MINOR` - обратно совместимая функциональность.
- `PATCH` - обратно совместимые исправления.

В монорепозитории возможны две стратегии:

Fixed versioning - пакеты выпускаются с общей версией. Удобно для тесно связанных библиотек.

Independent versioning - каждый пакет версионируется отдельно. Подходит для независимо развиваемых библиотек.

Для автоматизации используют `Changesets`, release-пайплайны и CI.

Типичный процесс: изменение пакета, проверка совместимости, обновление версий и зависимостей, формирование changelog, публикация в npm registry.

Важно учитывать, что SemVer описывает совместимость контрактов, а не просто масштаб изменений в коде.

# Какие риски у слепого переиспользования общих компонентов?

Главный риск - создание чрезмерной абстракции, которая пытается удовлетворить потребности разных сценариев.

Последствия:

- Увеличение количества пропсов и условной логики.
- Сильная зависимость независимых частей приложения.
- Сложность изменений без регрессий.
- Нарушение инкапсуляции.
- Усложнение тестирования и версионирования.

Например, универсальный `UserCard` для профиля, админки и списка сотрудников постепенно может превратиться в компонент с десятками флагов.

Переиспользовать стоит стабильные общие принципы и поведение, а не любой визуально похожий код.

Иногда небольшое дублирование лучше преждевременной общей абстракции.

# Как предотвратить циклические импорты между пакетами?

Циклическая зависимость возникает, когда пакет A зависит от B, а B прямо или через другие пакеты зависит от A.

Она усложняет сборку, тестирование, инициализацию модулей и изменение архитектуры.

Основные способы предотвращения:

- Построить направленную структуру зависимостей без циклов.
- Запретить импорты из более высоких архитектурных слоёв в нижние.
- Выносить действительно общие контракты в независимые пакеты.
- Использовать dependency inversion, когда реализация зависит от интерфейса.
- Автоматически проверять граф через Nx, dependency-cruiser или ESLint.

Важно не создавать отдельный пакет для каждого цикла. Иногда цикл показывает, что два модуля фактически представляют одну ответственность и их нужно объединить.

# Как организовать независимое тестирование модулей?

Каждый модуль должен тестироваться через собственный публичный API, без необходимости запускать всё приложение.

Основные подходы:

- Unit tests - проверяют бизнес-логику и отдельные функции.
- Component tests - проверяют поведение UI-компонентов.
- Integration tests - проверяют взаимодействие частей модуля.
- Contract tests - проверяют совместимость интерфейсов между модулями.

Внешние зависимости заменяют тестовыми реализациями или моками, но внутреннюю реализацию самого тестируемого модуля без необходимости не подменяют.

Для этого зависимости следует передавать явно, например через dependency injection.

Важно сохранять и интеграционные проверки: независимые тесты модулей не гарантируют корректность их совместной работы.

# Что такое package exports и как ограничивать несанкционированный deep import?

`package.json#exports` определяет публичные точки входа пакета и ограничивает доступ к внутренним файлам через имя пакета.

Например:

```
{
  "name": "@app/ui",
  "exports": {
    ".": "./dist/index.js",
    "./button": "./dist/button.js"
  }
}
```

Разрешены импорты `@app/ui` и `@app/ui/button`.

Импорт `@app/ui/src/internal.js` через механизм разрешения пакетов будет запрещён, если путь не объявлен в `exports`.

Это защищает внутреннюю структуру пакета от случайного использования и позволяет менять реализацию без нарушения публичных контрактов.

Ограничение: `exports` не является механизмом безопасности. Оно не блокирует прямой доступ к файлам по абсолютным путям или обход через специально настроенные алиасы.

Для контроля архитектуры его дополняют правилами ESLint и проверками зависимостей.

# Как настроить TypeScript project references в монорепозитории?

TypeScript Project References позволяют разбить TypeScript-проект на несколько связанных проектов и выполнять их инкрементальную компиляцию.

Каждый пакет получает собственный `tsconfig.json`.

Например, для `packages/core`:

```
{
  "compilerOptions": {
    "composite": true,
    "declaration": true,
    "outDir": "./dist"
  },
  "include": ["src"]
}
```

Пакет, использующий `core`, объявляет зависимость:

```
{
  "references": [
    { "path": "../core" }
  ]
}
```

Команда `tsc -b` анализирует ссылки, определяет порядок сборки и перекомпилирует устаревшие проекты.

Ключевые особенности:

- `composite: true` обязателен для проектов, на которые ссылаются другие.
- Зависимые проекты используют сгенерированные декларации `.d.ts`.
- `declarationMap` улучшает навигацию по исходникам.
- Project references не заменяют зависимости в `package.json` и настройку разрешения модулей.

Это особенно полезно в больших монорепозиториях, где полная проверка TypeScript занимает значительное время.

# Чем внутренний модуль приложения отличается от публикуемой npm-библиотеки?

Внутренний модуль существует в контексте конкретного приложения. Он может использовать соглашения проекта, общие настройки и внутренние зависимости.

Публикуемая npm-библиотека рассчитана на независимых потребителей и должна предоставлять устойчивый контракт.

Для библиотеки особенно важны:

- SemVer и обратная совместимость.
- Корректные `exports` и декларации TypeScript.
- Явные `dependencies` и `peerDependencies`.
- Совместимость с целевыми окружениями и системами модулей.
- Отсутствие неявных зависимостей от приложения.

Внутренний workspace-пакет может иметь многие из этих свойств, но не обязан поддерживать совместимость с внешними пользователями.

Главное различие - масштаб обязательств по совместимости и независимости от окружения.

# Какие критерии стоит использовать для объединения двух модулей?

Объединение оправдано, если модули:

- Реализуют одну бизнес-ответственность.
- Почти всегда изменяются одновременно.
- Имеют большое количество взаимных зависимостей.
- Не обладают самостоятельной ценностью или жизненным циклом.
- Требуют постоянного доступа к внутренним деталям друг друга.

Например, если `cart-items` и `cart-pricing` тесно связаны инвариантами корзины и не используются отдельно, их объединение может упростить архитектуру.

Основной критерий - общая ответственность и характер изменений, а не количество файлов.

Объединять модули только ради устранения импортов неправильно: это может создать чрезмерно большой модуль с несколькими несвязанными обязанностями.

# В каких случаях микрофронтенды оправданы?

Микрофронтенды (microfrontends) - архитектурный подход, при котором frontend разделён на относительно независимые приложения, объединяемые в единый пользовательский интерфейс.

Они оправданы, когда:

- Над продуктом работают несколько самостоятельных команд.
- Разные части системы требуют независимых релизов.
- Приложение содержит крупные, слабо связанные бизнес-домены.
- Необходимо постепенно мигрировать с устаревшего frontend-стека.
- Различные части продукта имеют независимые жизненные циклы.

Например, крупная платформа может независимо разрабатывать каталог, оформление заказов и личный кабинет.

Ключевой фактор - организационная и релизная независимость. Если её нет, преимущества микрофронтендов часто не компенсируют архитектурную сложность.

# Какие риски создают микрофронтенды в небольшом продукте?

В небольшом продукте микрофронтенды часто увеличивают сложность без существенной пользы.

Основные риски:

- Дублирование React и других зависимостей.
- Дополнительные сетевые запросы и JavaScript.
- Несогласованность UI и дизайн-системы.
- Усложнение роутинга, авторизации и передачи состояния.
- Дополнительная инфраструктура сборки и деплоя.
- Сложная диагностика ошибок между приложениями.
- Необходимость контролировать совместимость версий.

При этом независимые релизы создают дополнительные сценарии несовместимости.

Если продукт разрабатывает одна небольшая команда, модульный монолит обычно проще в поддержке и позволяет сохранить чёткие архитектурные границы без runtime-композиции.

# Чем build-time композиция отличается от runtime-композиции?

Build-time composition - объединение модулей во время сборки приложения.

Например, приложение импортирует компонент из npm-пакета:

```
import { Header } from "@app/ui";
```

Компонент становится частью собираемого приложения. Изменение библиотеки обычно требует пересборки потребителя.

Runtime composition - загрузка и объединение частей приложения во время выполнения.

Например, shell-приложение загружает удалённый модуль через Module Federation.

Отличия:

- Build-time обеспечивает более предсказуемую интеграцию и совместимость на момент сборки.
- Runtime позволяет независимо развёртывать части приложения, но переносит часть проверок совместимости на время выполнения.

Важно: динамический `import()` сам по себе не означает независимый runtime-релиз. Если модуль собирается вместе с приложением, это всё ещё build-time зависимость с отложенной загрузкой.

# Как работает Module Federation на высоком уровне?

Module Federation позволяет нескольким независимо собранным приложениям предоставлять и использовать JavaScript-модули во время выполнения.

Основные элементы:

- Host - приложение, загружающее удалённые модули.
- Remote - сборка, предоставляющая модули другим приложениям.
- Container - runtime-интерфейс доступа к экспортируемым модулям.
- Shared dependencies - библиотеки, которые могут переиспользоваться между сборками.

Принцип работы:

1. Remote собирается и публикует контейнер, обычно доступный через `remoteEntry.js`.
2. Host загружает контейнер во время выполнения.
3. Инициализируется общий контекст зависимостей (`share scope`).
4. Host запрашивает нужный модуль у контейнера.
5. Модуль загружается, выполняется и используется приложением.

Это позволяет обновить удалённый модуль без обязательной пересборки host, если их контракты совместимы.

# Как управлять общими зависимостями React между микрофронтендами?

При использовании React важно избегать нескольких несовместимых экземпляров библиотеки внутри одного React-дерева.

В Webpack Module Federation обычно настраивают `shared`:

```
shared: {
  react: {
    singleton: true,
    requiredVersion: "^19.0.0"
  },
  "react-dom": {
    singleton: true,
    requiredVersion: "^19.0.0"
  }
}
```

`singleton: true` ограничивает использование библиотеки одной версией в общем share scope.

`requiredVersion` определяет допустимый диапазон версий.

`strictVersion` позволяет требовать строгого соблюдения ограничений совместимости.

Разные экземпляры React при совместном использовании компонентов и хуков могут вызывать ошибки вроде `Invalid hook call`.

Важно согласовывать версии `react` и `react-dom` между приложениями и проверять совместимость в CI.

`singleton` не гарантирует, что выбранная версия удовлетворяет требованиям всех потребителей.

# Какие проблемы возникают при разных версиях дизайн-системы?

Разные версии дизайн-системы могут привести к:

- Визуальным расхождениям между частями интерфейса.
- Несовместимым API компонентов.
- Конфликтам CSS-переменных и глобальных стилей.
- Различному поведению одинаковых компонентов.
- Дублированию кода и увеличению bundle size.

Например, одна версия `Button` использует токен `--color-primary`, а другая ожидает `--button-primary-background`.

Для решения применяют общие design tokens, SemVer, документированные контракты компонентов и проверки совместимости.

При этом независимые микрофронтенды не обязаны одновременно использовать одну версию дизайн-системы. Важно обеспечить совместимость визуальных и технических контрактов на период миграции.

# Как реализовать независимые релизы микрофронтендов?

Каждый микрофронтенд должен иметь собственную сборку, CI/CD-пайплайн и публикуемые артефакты.

Типичная архитектура:

- Каждый remote собирается независимо.
- Артефакты размещаются на CDN или отдельном сервере.
- Host получает адреса remote через конфигурацию или manifest.
- Обновления remote не требуют пересборки host при сохранении контрактов.
- При ошибках возможен откат на предыдущую версию remote.

Критически важно обеспечить совместимость публичных API, общих зависимостей и механизмов взаимодействия.

Для этого используют contract tests, интеграционные тесты поддерживаемых сочетаний версий и постепенное развёртывание.

Также необходимо продумать кэширование: старый `remoteEntry.js` не должен ссылаться на уже удалённые артефакты новой или предыдущей сборки.

# Как устроить роутинг между микрофронтендами?

Обычно выделяют центральный роутер в shell-приложении, который определяет, какой микрофронтенд необходимо загрузить для текущего URL.

Например:

- `/catalog/*` - микрофронтенд каталога.
- `/checkout/*` - оформление заказа.
- `/account/*` - личный кабинет.

Внутри микрофронтенда может использоваться собственный вложенный роутер.

При этом важно согласовать:

- Владение URL-префиксами.
- Использование общего `history`.
- Навигацию между приложениями.
- Обработку неизвестных маршрутов.
- Поддержку прямого открытия URL и обновления страницы.

Основной принцип - должен существовать один согласованный механизм управления браузерным URL.

Иначе разные роутеры могут независимо изменять историю браузера и создавать конфликты навигации.

# Как обмениваться событиями между независимыми приложениями?

Для взаимодействия микрофронтендов используют явные контракты сообщений.

Основные механизмы:

- CustomEvent - события через DOM.
- Event Bus - централизованный механизм публикации и подписки.
- Pub/Sub - обмен сообщениями без прямой зависимости отправителя от получателя.
- `postMessage` - коммуникация между iframe и другими оконными контекстами.
- Backend API - синхронизация данных через сервер.

Например, после добавления товара в корзину каталог публикует событие `cart:item-added`, а другой модуль обновляет отображение корзины.

События должны иметь документированную структуру, версию и семантику.

Важно учитывать, что события обычно не сохраняются: если подписчик отсутствовал в момент отправки, он может пропустить сообщение. Поэтому события не должны быть единственным источником критически важного состояния.

# Почему глобальный Redux store между микрофронтендами может быть проблемой?

Общий Redux store создаёт сильную runtime-зависимость между приложениями.

Микрофронтенды начинают зависеть от:

- Общей структуры состояния.
- Названий actions.
- Поведения reducers.
- Совместимых версий Redux и middleware.
- Порядка инициализации частей приложения.

Изменение состояния одним микрофронтендом может сломать другой, даже если они выпускаются независимо.

Это нарушает принцип автономности.

Обычно каждый микрофронтенд владеет собственным состоянием, а общие данные передаются через контракты, события или API.

Небольшое глобальное состояние допустимо, например для информации о текущем пользователе, но желательно предоставлять доступ к нему через стабильный интерфейс, а не напрямую через структуру Redux store.

# Как обеспечить изоляцию CSS и глобальных обработчиков?

Изоляция должна охватывать как стили, так и побочные эффекты JavaScript.

Для CSS используют:

- CSS Modules.
- Уникальные префиксы классов.
- Shadow DOM.
- CSS-in-JS с изолированными именами классов.
- iframe, когда требуется более строгая изоляция.

Для JavaScript необходимо контролировать глобальные ресурсы:

- Удалять обработчики `window` и `document` при размонтировании.
- Очищать таймеры и подписки.
- Отменять ненужные запросы через `AbortController`.
- Избегать конфликтующих изменений глобальных объектов.

Shadow DOM изолирует стили, но не создаёт отдельное JavaScript-окружение.

iframe обеспечивает более строгую изоляцию DOM и JavaScript, однако усложняет коммуникацию, размеры контейнеров и навигацию.

# Что делать, если один микрофронтенд недоступен?

Необходимо обеспечить graceful degradation - контролируемое ухудшение функциональности без полного отказа приложения.

Основные меры:

- Обрабатывать ошибки загрузки remote.
- Показывать fallback UI вместо недоступного модуля.
- Использовать Error Boundary для ошибок React-рендеринга.
- Предусматривать повторную загрузку с ограничением числа попыток.
- По возможности сохранять работу независимых разделов.
- Логировать ошибки с указанием проблемного микрофронтенда и его версии.

Например, если недоступен блок рекомендаций, страница товара должна продолжать работать.

Важно различать ошибки загрузки и ошибки выполнения: React Error Boundary не перехватывает автоматически все ошибки загрузки удалённых скриптов.

Если недоступен критический модуль, например оформление оплаты, следует явно сообщить о невозможности завершить операцию, а не имитировать её успешное выполнение.

# Как измерять производительность страницы из нескольких микрофронтендов?

Производительность необходимо измерять на уровне всей страницы и каждого микрофронтенда отдельно.

Основные метрики:

- LCP - время отображения крупнейшего содержательного элемента.
- INP - отзывчивость интерфейса на взаимодействия.
- CLS - визуальная стабильность.
- TTFB - время до первого байта ответа.
- JavaScript bundle size - объём загружаемого JavaScript.
- Long Tasks - длительные задачи, блокирующие главный поток.

Для анализа используют Chrome DevTools, Lighthouse, Performance API и Real User Monitoring (RUM).

Дополнительно полезно измерять время загрузки, инициализации и монтирования каждого remote через `performance.mark()` и `performance.measure()`.

Обязательно учитывать совокупную стоимость: несколько микрофронтендов могут независимо показывать хорошие результаты, но вместе перегружать главный поток JavaScript, сеть и память.

# Какие альтернативы Module Federation существуют?

Module Federation - один из способов композиции микрофронтендов, но не единственный.

Основные альтернативы:

- npm/workspace-пакеты - объединение приложений на этапе сборки.
- single-spa - runtime-оркестрация независимых frontend-приложений.
- Native ES Modules + Import Maps - загрузка JavaScript-модулей по URL с управлением разрешением импортов.
- Web Components - интеграция через стандартизированные пользовательские HTML-элементы.
- iframe - изоляция приложений в отдельных браузерных контекстах.
- Server-side composition - объединение фрагментов интерфейса на сервере или edge-уровне.

Выбор зависит от требований к независимому деплою, совместимости технологий, изоляции и производительности.

Например, Web Components определяют контракт UI-компонентов, но сами по себе не решают задачи доставки и управления версиями. Для полноценной архитектуры микрофронтендов часто требуется сочетание нескольких механизмов.

# Чем статическая зависимость отличается от runtime-зависимости?

Статическая зависимость известна на этапе сборки. Сборщик может разрешить её, проанализировать и включить в граф приложения.

Например:

```
import { Button } from "@app/ui";
```

Runtime-зависимость определяется или загружается во время выполнения приложения.

Например, host может получить URL удалённого модуля из конфигурации и загрузить его через Module Federation.

Ключевое отличие заключается в моменте разрешения зависимости и проверки её доступности.

У статических зависимостей большинство проблем обнаруживается во время сборки. У runtime-зависимостей появляются дополнительные риски: недоступность сервера, несовместимость версий и ошибки загрузки.

При этом `import()` не всегда означает runtime-зависимость в архитектурном смысле: обычный bundler часто знает её цель ещё на этапе сборки.

# Что такое dependency graph и как его проверять автоматически?

Dependency graph - направленный граф, показывающий зависимости между модулями, пакетами или проектами.

Узлы графа представляют модули, а рёбра - зависимости.

Он позволяет обнаруживать:

- Циклические зависимости.
- Нарушения архитектурных слоёв.
- Нежелательные зависимости между доменами.
- Избыточную связанность модулей.
- Область влияния изменений.

Для автоматических проверок используют `Nx`, `dependency-cruiser`, `Madge` и правила ESLint.

Например, можно запретить импорт из `features` в `shared` или зависимости одного бизнес-домена от внутренних файлов другого.

Проверки запускают в CI, чтобы архитектурные нарушения блокировали слияние изменений.

Важно различать граф зависимостей исходного кода и task graph: первый описывает связи модулей, второй - порядок выполнения задач.

# Когда приложение следует разделять на отдельные пакеты?

Выделение отдельного пакета оправдано, если часть приложения:

- Имеет самостоятельную ответственность.
- Обладает стабильным публичным API.
- Используется несколькими приложениями или модулями.
- Требует независимого тестирования и сборки.
- Имеет собственный жизненный цикл.
- Должна иметь явно контролируемые зависимости.

Например, библиотеку UI-компонентов, используемую несколькими приложениями, логично выделить в `@app/ui`.

При этом большой размер папки сам по себе не является основанием для создания пакета.

Пакет создаёт дополнительную архитектурную границу и стоимость её поддержки. Если независимость и переиспользование не нужны, обычный внутренний модуль может быть более подходящим решением.

# Как избегать конфликтов глобальных стилей в микрофронтендах?

Основная проблема - CSS является глобальным в пределах обычного DOM-документа, поэтому стили одного микрофронтенда могут влиять на другой.

Например, правило `button { ... }` способно изменить кнопки во всех приложениях.

Способы предотвращения:

- Использовать CSS Modules и локальные имена классов.
- Избегать глобальных селекторов вроде `button`, `h1` и `div`.
- Применять уникальные префиксы классов или namespaces.
- Ограничивать стили корневым контейнером микрофронтенда.
- Использовать Shadow DOM для изоляции дерева стилей.
- Централизовать CSS reset и глобальные design tokens.

CSS-переменные также требуют согласования: изменение глобального `--primary-color` может затронуть все микрофронтенды.

Наиболее надёжный принцип - каждый микрофронтенд управляет собственными стилями, а глобальные правила определяются только на уровне shell-приложения.

# Что такое Module Federation в Webpack?

Module Federation - встроенный в Webpack 5 механизм, позволяющий независимо собранным приложениям предоставлять и загружать модули во время выполнения.

Реализуется через `ModuleFederationPlugin`.

Пример конфигурации remote:

```
const { ModuleFederationPlugin } = require("webpack").container;

new ModuleFederationPlugin({
  name: "catalog",
  filename: "remoteEntry.js",
  exposes: {
    "./ProductCard": "./src/ProductCard"
  },
  shared: {
    react: { singleton: true },
    "react-dom": { singleton: true }
  }
});
```

Основные параметры:

- `name` - имя федеративного контейнера.
- `filename` - имя файла точки входа remote.
- `exposes` - модули, предоставляемые другим приложениям.
- `remotes` - удалённые контейнеры, доступные текущей сборке.
- `shared` - настройки совместного использования зависимостей.

Host может подключить remote:

```
new ModuleFederationPlugin({
  name: "shell",
  remotes: {
    catalog: "catalog@https://example.com/remoteEntry.js"
  },
  shared: {
    react: { singleton: true },
    "react-dom": { singleton: true }
  }
});
```

После этого компонент можно загрузить:

```
const ProductCard = React.lazy(
  () => import("catalog/ProductCard")
);
```

Webpack загружает контейнер, согласовывает общие зависимости и получает экспортируемый модуль.

Главное преимущество - возможность независимо собирать и развёртывать приложения, сохраняя возможность использовать их модули в общем интерфейсе.

Главное ограничение - необходимость обеспечивать runtime-совместимость, доступность удалённых сборок и корректное управление общими зависимостями.
