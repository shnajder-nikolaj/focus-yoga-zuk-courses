# Какую проблему решает FSD?

Feature-Sliced Design (FSD) - архитектурная методология организации frontend-кода, направленная на снижение связанности модулей и упрощение развития приложения.

Основные проблемы, которые решает FSD:

- Неявные зависимости - модули произвольно импортируют друг друга, создавая циклические зависимости и затрудняя рефакторинг.
- Размытые границы ответственности - бизнес-логика, UI и работа с API распределены по разным папкам без понятных правил.
- Сложная навигация - для изменения одной функциональности приходится искать связанные файлы по всему проекту.
- Плохая масштабируемость - с ростом приложения изменения в одном модуле начинают затрагивать множество других.

FSD решает эти проблемы через иерархию слоёв, изоляцию слайсов и публичные интерфейсы модулей.

В результате структура проекта отражает бизнес-домены, а зависимости становятся предсказуемыми. Это упрощает тестирование, рефакторинг и параллельную разработку.

# Какие слои предусматривает FSD и каково их назначение?

FSD предусматривает шесть основных актуальных слоёв, расположенных сверху вниз:

1. `app` - инициализация приложения, провайдеры, роутинг, глобальные настройки.
2. `pages` - страницы приложения, соответствующие маршрутам или крупным частям экранов.
3. `widgets` - самостоятельные крупные блоки интерфейса, объединяющие нижележащую функциональность.
4. `features` - пользовательские действия и сценарии, имеющие бизнес-ценность.
5. `entities` - бизнес-сущности, их модели, состояние и связанные операции.
6. `shared` - переиспользуемая инфраструктура, UI-kit, утилиты и конфигурация.

Ранее существовал слой `processes` для сложных межстраничных процессов, но он устарел (`deprecated`) и в новых проектах не рекомендуется.

Основное правило: вышестоящие слои могут зависеть от нижестоящих, но не наоборот.

Например, `features` может использовать `entities` и `shared`, но не `widgets` или `pages`.&#x20;

# Чем слой отличается от слайса и сегмента?

Это три уровня организации кода в FSD.

- Layer (слой) - определяет архитектурную ответственность модуля и допустимое направление зависимостей. Например, `features`.
- Slice (слайс) - изолированный модуль внутри слоя, объединённый бизнес-смыслом. Например, `features/add-to-cart`.
- Segment (сегмент) - раздел внутри слайса, группирующий код по техническому назначению: `ui`, `model`, `api`, `lib`, `config`.

Пример:

```
src/
└── features/              # Layer
    └── add-to-cart/       # Slice
        ├── ui/            # Segment
        ├── model/         # Segment
        ├── api/           # Segment
        └── index.ts       # Public API
```

Слой отвечает на вопрос «какова роль кода?», слайс - «к какой функциональности он относится?», сегмент - «какую техническую задачу выполняет?»

Особенность: `app` и `shared` не делятся на слайсы, а содержат сегменты непосредственно.

# Что хранить в `app`, `pages`, `widgets`, `features`, `entities` и `shared`?

- `app` - `App`, `RouterProvider`, `Redux Provider`, глобальные стили, инициализация приложения, обработка глобальных ошибок.
- `pages` - компоненты страниц, их локальное состояние, загрузку данных и логику, специфичную для конкретной страницы.
- `widgets` - крупные композиционные блоки: `Header`, `Sidebar`, `ProductCatalog`, `UserDashboard`.
- `features` - пользовательские действия: `sign-in`, `add-to-cart`, `edit-profile`, `submit-review`.
- `entities` - бизнес-сущности `user`, `product`, `order`, включая типы, API, доменную логику, состояние и компоненты их отображения.
- `shared` - `Button`, `Modal`, `Input`, HTTP-клиент, универсальные хуки, утилиты, токены дизайна, конфигурацию.

Ключевой критерий - ответственность и область применения кода, а не его технический тип.

Например, `ProductCard` может находиться в `entities/product/ui`, если отображает товар. А `AddToCartButton` - в `features/add-to-cart/ui`, поскольку реализует пользовательское действие.

При этом FSD не требует создавать все слои. Простая страница может содержать собственный UI и запросы без выделения отдельных `widgets` и `features`.

# Как работают правила допустимых импортов между слоями?

В FSD действует правило однонаправленных зависимостей: модуль может импортировать другие слайсы только из строго нижележащих слоёв.

```
app
 ↓
pages
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared
```

Стрелки показывают допустимое направление зависимостей. При этом можно пропускать промежуточные слои.

Примеры:

```
// Допустимо: feature использует entity
import { ProductCard } from '@/entities/product'

// Допустимо: page использует feature
import { AddToCartButton } from '@/features/add-to-cart'

// Недопустимо: entity использует feature
import { AddToCartButton } from '@/features/add-to-cart'
```

Дополнительные правила:

- Слайсы одного слоя не должны напрямую зависеть друг от друга.
- Внутри одного слайса разрешены импорты между его сегментами.
- `app` и `shared` не имеют слайсов, поэтому их сегменты могут импортировать друг друга.
- Внешние импорты должны использовать публичный API соответствующего слайса.

Эти ограничения предотвращают архитектурные циклы и позволяют изменять высокоуровневые модули без необходимости изменять нижележащие.&#x20;

# Что такое public API слайса и зачем нужен `index.ts`?

Public API - публичный интерфейс слайса, определяющий, какие компоненты, функции и типы доступны другим модулям.

Обычно реализуется через `index.ts`, который реэкспортирует разрешённые сущности:

```
// features/add-to-cart/index.ts
export { AddToCartButton } from './ui/AddToCartButton'
export { useAddToCart } from './model/useAddToCart'
```

Использование:

```
// Правильно
import { AddToCartButton } from '@/features/add-to-cart'

// Неправильно: обращение к внутренней структуре
import { AddToCartButton } from '@/features/add-to-cart/ui/AddToCartButton'
```

Преимущества:

- Инкапсуляция - внутренние детали слайса скрыты.
- Стабильность контрактов - можно менять внутреннюю структуру без изменения внешних импортов.
- Контроль зависимостей - наружу экспортируется только необходимое.
- Упрощение рефакторинга - потребители не зависят от расположения внутренних файлов.

`index.ts` не создаёт настоящую изоляцию на уровне TypeScript: технически глубокий импорт остаётся возможным, если его не запрещают инструменты проекта.

Важно не создавать чрезмерные реэкспорты и циклические зависимости через `index.ts`. Внутри слайса обычно используют относительные импорты напрямую, а не его собственный Public API.

# Когда логика относится к `features`, а когда к `entities`?

`entities` содержит переиспользуемые модели бизнес-сущностей и правила, относящиеся к самим этим сущностям.

Например, для `entities/product`:

- Типы и схемы данных товара.
- Расчёт доступности товара.
- Форматирование характеристик.
- Переиспользуемое состояние товара.

`features` содержит законченные пользовательские действия, которые используют бизнес-сущности.

Например, для `features/add-to-cart`:

- Обработку добавления товара в корзину.
- Проверку условий выполнения действия.
- Состояние выполнения операции.
- UI-кнопку добавления.

Главное различие:

- `entities` - что представляет собой бизнес-объект и какие правила ему принадлежат.
- `features` - что пользователь может сделать с бизнес-объектом.

При этом не каждую бизнес-операцию нужно помещать в `features`. В FSD 2.1 логика, используемая только одной страницей, обычно остаётся внутри её слайса в `pages`.

# По каким признакам выделять самостоятельный feature?

Самостоятельную feature стоит выделять, когда функциональность:

1. Имеет самостоятельную бизнес-ценность - представляет понятное пользовательское действие, например `add-to-favorites`.
2. Имеет чёткие границы ответственности - обладает собственным поведением и публичным контрактом.
3. Переиспользуется - используется несколькими страницами или независимыми сценариями.
4. Может изменяться независимо - её внутреннюю реализацию можно менять без изменения потребителей.

Например, добавление товара в избранное из каталога, карточки товара и результатов поиска - хороший кандидат на `features/add-to-favorites`.

Не стоит выделять feature только потому, что появился обработчик `onClick`, форма или отдельный API-запрос.

В FSD 2.1 предпочтителен подход `pages-first`: сначала размещать код рядом с его использованием и выделять feature, когда появляется реальная потребность в самостоятельной границе.&#x20;

# Когда использовать widgets, а когда достаточно композиции на странице?

Widget - крупный самостоятельный блок интерфейса, который может объединять несколько компонентов, сущностей и пользовательских действий.

Например, `widgets/header` может включать навигацию, поиск, уведомления и меню пользователя.

Widget оправдан, когда блок:

- Переиспользуется на нескольких страницах.
- Имеет самостоятельную ответственность и достаточно сложную внутреннюю структуру.
- Объединяет несколько нижележащих модулей в устойчивую композицию.

Если блок используется только на одной странице, его обычно лучше оставить в `pages/<page>/ui`.

В FSD 2.1 использование `widgets` не рекомендуется по умолчанию, поскольку границы между widget и feature часто пересекаются. Вместо отдельного widget предпочтительно компоновать функциональность в `pages` или `app`. При этом существующий слой `widgets` остаётся допустимым и не является устаревшим.&#x20;

# Можно ли одной feature импортировать другую и какие проблемы это создаёт?

По базовым правилам FSD прямой импорт между разными слайсами слоя `features` запрещён, поскольку они находятся на одном уровне.

Например:

```
// features/checkout/model/checkout.ts

import { applyCoupon } from '@/features/apply-coupon'
```

Проблемы:

- Сильная связанность - изменение одной feature может затрагивать другую.
- Нарушение независимости - функциональность становится сложнее переносить и тестировать изолированно.
- Риск циклических зависимостей - особенно при взаимных импортах.
- Сложность развития - границы между функциональностями постепенно размываются.

Предпочтительные решения:

- Вынести общую доменную логику в `entities`, если ей действительно место там.
- Объединить features, если они представляют одну ответственность.
- Организовать взаимодействие через композицию в `pages` или `app`.

В отдельных случаях осознанный импорт через Public API другой feature допускается как архитектурный компромисс, но это исключение, а не базовое правило FSD.

# Как организовать cross-slice взаимодействие?

Cross-slice взаимодействие - координация независимых слайсов, которым необходимо совместно реализовать пользовательский сценарий.

Основной подход - композиция на вышестоящем слое, где разрешено использовать оба слайса.

Например, страница оформления заказа может импортировать `features/apply-coupon` и `features/checkout` и координировать их через общее состояние, свойства компонентов или callbacks.

Основные способы организации взаимодействия:

- Композиция на верхнем слое - `pages` или `app` связывают несколько независимых слайсов.
- Dependency Injection - зависимости передаются через аргументы функций, props или Context вместо прямого импорта.
- Общая доменная модель - независимые features используют один публичный контракт из `entities`.
- Общий state manager - слайсы взаимодействуют через состояние и действия доменной модели, соблюдая направление зависимостей.

Для взаимосвязанных бизнес-сущностей FSD предусматривает специальный механизм `@x`:

```
import type { User } from '@/entities/user/@x/order'
```

Здесь `user` предоставляет специальный публичный интерфейс для `order`. Это узкое исключение для слоя `entities`, а не универсальный способ разрешить импорты между любыми слайсами.

Использование глобального `EventBus` также возможно, но создаёт неявные зависимости между отправителями и подписчиками. Поэтому его не следует использовать только ради обхода правил FSD.&#x20;

# Как расположить API-запросы, query hooks и DTO в FSD?

Расположение зависит от того, кто использует код и какова его ответственность.

1\. API-клиент и инфраструктура

`shared/api` - базовый HTTP-клиент, общая настройка `fetch` или `axios`, обработка ошибок, авторизация запросов.

2\. API-запросы

- `pages/profile/api` - запросы, специфичные для страницы профиля.
- `features/add-to-cart/api` - запросы, обслуживающие пользовательское действие.
- `entities/product/api` - запросы, принадлежащие переиспользуемой доменной модели товара.
- `shared/api` - общие функции запросов и контракты backend API, используемые разными модулями.

Размещение всех запросов в `shared/api` допустимо, если там остаётся транспортная логика без бизнес-правил.

3\. Query hooks

Хуки `useQuery` и `useMutation` размещают рядом с ответственностью, которой они принадлежат.

Например:

```
entities/
└── product/
    ├── api/
    │   ├── get-product.ts
    │   └── product.queries.ts
    └── index.ts
```

В `product.queries.ts` могут находиться `queryOptions`, `queryKey` и переиспользуемый хук `useProduct`.

Если запрос нужен только одной странице, такую обёртку лучше оставить внутри страницы.

4\. DTO и доменные модели

DTO (Data Transfer Object) описывает формат передачи данных через API. Он может отличаться от внутренней доменной модели.

Например:

```
type ProductDto = {
  product_id: number
  price_cents: number
}

type Product = {
  id: number
  price: number
}
```

DTO следует хранить рядом с API-контрактами, например в `shared/api` или соответствующем `api`-сегменте.

Доменную модель `Product` можно хранить в `entities/product/model`, а преобразование DTO в доменную модель - рядом с API-адаптером, использующим этот контракт.

Важно: не следует привязывать всю frontend-архитектуру к структуре backend API. Структура backend-эндпоинтов и границы frontend-слайсов решают разные задачи.

# Где должен находиться Redux store в FSD?

Корневой Redux store обычно располагается в `app/store`, поскольку отвечает за объединение состояния всего приложения и подключение middleware.

Пример:

```
src/
├── app/
│   ├── store/
│   │   └── store.ts
│   └── providers/
│       └── StoreProvider.tsx
├── entities/
│   └── user/
│       └── model/
│           └── userSlice.ts
└── features/
    └── add-to-cart/
        └── model/
            └── cartActionSlice.ts
```

Разделение ответственности:

- `app/store` - `configureStore`, объединение reducers, middleware, конфигурация хранилища.
- `entities/*/model` - состояние и reducers переиспользуемых бизнес-сущностей.
- `features/*/model` - состояние пользовательских действий.
- `pages/*/model` - состояние, специфичное для страницы.
- `app/providers` - подключение `Redux Provider`.

Например, `app/store` импортирует reducers из нижележащих слоёв. При этом сами reducers не должны импортировать корневой store из `app`.

Важно: Redux slice и FSD slice - разные понятия. Redux slice представляет часть состояния хранилища, а FSD slice - архитектурный модуль, который может включать UI, API и несколько Redux slices.

# Где хранить базовые UI-компоненты и тематические стили?

Базовые UI-компоненты размещаются в `shared/ui`:

```
shared/
├── ui/
│   ├── button/
│   ├── input/
│   ├── modal/
│   └── select/
└── lib/
```

Такие компоненты должны быть независимы от конкретных бизнес-сценариев, но могут содержать собственную UI-логику: управление открытием модального окна, клавиатурную навигацию, фокус и т.д.

Стили распределяются по области ответственности:

- `app/styles` - CSS reset, глобальные стили, подключение шрифтов, базовые переменные темы.
- `shared/ui` - стили компонентов UI-kit.
- `shared` - общие дизайн-токены и конфигурация темы, которые используются разными модулями.
- `entities`, `features`, `pages` - локальные стили соответствующих компонентов.

Например, `Button` и его стили находятся в `shared/ui`, а стили формы авторизации - рядом с формой в `pages/login/ui` или `features/sign-in/ui`.

Основной принцип: стили должны находиться максимально близко к владельцу, а глобальными следует делать только действительно общие настройки.

# Как размещать роутинг и layout приложения?

Роутинг обычно размещается в `app`, поскольку определяет структуру приложения и объединяет страницы.

Например:

```
app/
├── routes/
│   └── router.tsx
├── providers/
└── styles/

pages/
├── home/
└── profile/
```

Конфигурация маршрутов импортирует страницы через их Public API:

```
const router = createBrowserRouter([
  {
    path: '/',
    element: <HomePage />,
  },
  {
    path: '/profile/:id',
    element: <ProfilePage />,
  },
])
```

Layout размещается в зависимости от области применения:

- `app` - общий layout приложения, интеграция с роутером, глобальная структура.
- `pages` - layout, специфичный для страницы или группы маршрутов.
- `shared/ui` - универсальный layout-компонент без бизнес-зависимостей.
- `widgets` - переиспользуемый композиционный layout, если этот слой используется в проекте.

Например, `AppLayout` может содержать `Header`, `Sidebar` и `Outlet` для вложенных маршрутов.

Route Guards и маршрутизация, зависящая от авторизации, обычно организуются на уровне `app`, используя публичное состояние сессии из нижележащих слоёв.

В файловых роутерах, например Next.js App Router, структуру маршрутов определяет фреймворк. В таком случае маршрутные файлы могут выступать тонкими адаптерами к FSD-страницам.

# Как мигрировать существующий React-проект на FSD постепенно?

Миграцию лучше выполнять поэтапно, без полного переписывания приложения.

Основные этапы:

1. Выделить `app`, `pages` и `shared`. Перенести инициализацию приложения, роутинг и провайдеры в `app`, а экраны - в `pages`.
2. Организовать код внутри страниц. Разделить его на `ui`, `model`, `api` по необходимости, не меняя поведение.
3. Устранить зависимости между страницами. Перенести действительно общий код в нижние слои или оставить независимые реализации.
4. Сформировать `shared`. Выделить UI-kit, HTTP-клиент, общие утилиты и конфигурацию.
5. Постепенно выделять `entities` и `features`. Только там, где появились устойчивые переиспользуемые ответственности.
6. Создать Public API. Добавить `index.ts` и заменить глубокие импорты публичными.
7. Включить архитектурные проверки. Контролировать новые нарушения, затем постепенно устранять существующие.

На время миграции допустимо сосуществование старой и новой структуры. Главное - не создавать новые неконтролируемые зависимости.

В FSD 2.1 рекомендуется миграция `pages-first`: сначала организовать страницы и инфраструктуру, затем извлекать самостоятельные модули по мере необходимости.&#x20;

# Как бороться с искусственным дроблением кода на мелкие слайсы?

Избыточная декомпозиция возникает, когда разработчики создают отдельные features и entities для каждой небольшой операции, компонента или типа данных.

Например:

```
features/
├── open-modal/
├── close-modal/
├── validate-input/
├── submit-form/
└── reset-form/
```

Если все операции относятся к одному пользовательскому сценарию, такая структура искусственно усложняет проект.

Способы избежать этого:

- Выделять слайсы по бизнес-смыслу, а не по количеству функций.
- Оставлять локальную логику в `pages`, если она больше нигде не используется.
- Объединять тесно связанные действия, если они имеют общую ответственность и изменяются вместе.
- Не создавать абстракции заранее, ориентируясь на гипотетическое переиспользование.
- Не создавать пустые слои и сегменты ради соблюдения шаблона.

Например, вместо пяти отдельных features для операций с формой можно оставить один модуль `features/edit-profile`, если он представляет самостоятельный переиспользуемый сценарий.

Ключевой критерий - высокая связность внутри слайса и минимальная связанность между слайсами.

# Как контролировать зависимости ESLint-правилами?

Архитектурные ограничения FSD можно автоматически проверять через ESLint.

Основные инструменты:

- `eslint-plugin-boundaries` - позволяет описывать допустимые зависимости между архитектурными модулями.
- `no-restricted-imports` - запрещает конкретные импорты и шаблоны путей.
- `import/no-cycle` из `eslint-plugin-import` - помогает обнаруживать циклические зависимости.

При использовании `eslint-plugin-boundaries` версии 7 основное правило - `boundaries/dependencies`. Оно позволяет задать политику, согласно которой, например, `features` может импортировать только `entities` и `shared`, а соседние feature-слайсы изолированы.

Важно проверять не только уровни слоёв, но и конкретные границы слайсов: простого запрета на импорты из `features` недостаточно, чтобы предотвратить все нарушения.

Также существует Steiger - специализированный архитектурный линтер FSD, работающий отдельно от ESLint.

```
npm install -D steiger

npx steiger src
```

Он проверяет, в частности:

- `fsd/forbidden-imports` - недопустимые зависимости.
- `fsd/no-public-api-sidestep` - обход Public API.
- `fsd/public-api` - наличие публичных интерфейсов.
- `fsd/excessive-slicing` - чрезмерное дробление на слайсы.

Архитектурные проверки рекомендуется запускать в CI, чтобы нарушения не попадали в основную ветку проекта.&#x20;

# Как реализовать общий auth flow без нарушения направленности зависимостей?

Авторизация затрагивает несколько уровней: HTTP-клиент, состояние сессии, пользовательские действия, маршруты и интерфейс.

Чтобы сохранить правила FSD, необходимо разделить инфраструктуру авторизации, состояние сессии и пользовательские сценарии.

Возможная структура:

```
src/
├── app/
│   ├── routes/
│   └── providers/
├── pages/
│   └── login/
├── features/
│   └── sign-in/
├── entities/
│   └── user/
└── shared/
    ├── api/
    └── auth/
```

Распределение ответственности:

- `shared/api` - HTTP-клиент, обработка ответов, повторные запросы, механизм обновления токена.
- `shared/auth` - инфраструктура сессии, хранение и предоставление токенов, если клиент управляет ими самостоятельно.
- `entities/user` - переиспользуемая бизнес-модель пользователя, если она нужна приложению.
- `features/sign-in` - пользовательский сценарий входа, если он выделен как самостоятельная feature.
- `pages/login` - страница авторизации.
- `app/routes` - маршруты, редиректы, защита приватных экранов.

Главная архитектурная проблема: HTTP-клиент находится в `shared`, поэтому он не должен импортировать состояние авторизации из `features` или `entities`.

Решения:

1. Хранить техническое состояние сессии в `shared/auth`, чтобы HTTP-клиент мог получать токен без нарушения зависимостей.
2. Передавать токен или функцию его получения в HTTP-клиент через Dependency Injection.
3. Использовать серверную cookie-based авторизацию, при которой браузер автоматически отправляет соответствующие cookies.

Для браузерных приложений обычно предпочтительны `HttpOnly`, `Secure` cookies с подходящей политикой `SameSite`, если backend поддерживает такую архитектуру. При этом необходимо учитывать CSRF-защиту.

Важно: управление авторизацией на frontend не заменяет проверку прав на backend. Route Guards защищают интерфейс и навигацию, но не сами ресурсы сервера.&#x20;

# Когда FSD не подходит проекту или добавляет лишнюю сложность?

FSD не всегда оправдан, поскольку архитектурные ограничения имеют собственную стоимость.

Примеры ситуаций:

- Небольшое приложение - несколько экранов с простой логикой и небольшим количеством зависимостей.
- Краткосрочный прототип - приоритетом является скорость проверки гипотез, а не долговременная поддержка.
- Библиотека или UI-kit - код организуется вокруг публичных компонентов и пакетов, а не пользовательских бизнес-сценариев.
- Приложение с минимальной бизнес-логикой - дополнительные `features` и `entities` могут оказаться искусственными.
- Команда без согласованных архитектурных правил - формальное наличие FSD-папок не предотвращает хаотичные зависимости.

Основные издержки FSD - необходимость проектировать границы модулей, поддерживать Public API и соблюдать ограничения импортов.

FSD приносит наибольшую пользу, когда проект имеет сложные бизнес-сценарии, множество взаимосвязанных модулей, активно развивается и поддерживается несколькими разработчиками.

При этом FSD не обязательно внедрять полностью. Для небольшого проекта может быть достаточно `app`, `pages` и `shared`, без отдельных `features`, `entities` и `widgets`.
