# Как выбирать синхронный вызов или асинхронное сообщение между сервисами?

Синхронный вызов подходит, когда ответ нужен для текущего действия и зависимость должна быть доступна сейчас. Асинхронное сообщение подходит для отложенной работы, сглаживания пиков и независимой реакции нескольких потребителей.

Асинхронность переносит сложность в состояние процесса, дубли, порядок, мониторинг и срок завершения. Синхронность создаёт временную связь и увеличивает задержку цепочки. Выбор делают по бизнес-требованию к ответу и согласованности, а не только по скорости транспорта. Иногда правильное решение — оставить тесно связанный сценарий внутри одного сервиса.

# Какие компромиссы между REST, gRPC и messaging важны для внутренних API?

REST поверх HTTP удобен для ресурсов, стандартных инструментов и широкого круга клиентов. gRPC даёт типизированные RPC-контракты, генерацию клиентов и streaming, но требует подходящей поддержки протокола, схем и диагностики.

Messaging обеспечивает временное разъединение и накопление работы, но меняет модель взаимодействия: нужно отслеживать результат отдельно и учитывать повторную доставку. Нельзя сравнивать только размер payload: важны частота запросов, совместимость, отказоустойчивость, опыт команды и полная стоимость эксплуатации. Все варианты требуют явного контракта ошибок.

# Как разделить политики API Gateway и бизнес-логику внутренних сервисов?

Gateway удобно поручить маршрутизацию, проверку внешнего токена, квоты, наблюдаемость и общие транспортные политики. Внутренние сервисы сохраняют ответственность за предметные правила и права на конкретный ресурс, поскольку к ним могут обращаться разные каналы.

Если gateway начинает управлять состоянием заказа или правилами списания, он превращается в центральный бизнес-компонент и связывает релизы команд. Небольшая агрегация допустима по явному назначению, но ownership и отказоустойчивость должны оставаться понятными. [API Gateway pattern](https://microservices.io/patterns/apigateway.html).

# Как определить границы нескольких BFF для web, mobile и партнёрского API?

Границу BFF определяют потребности и жизненный цикл клиентов: mobile может требовать компактных ответов и долгой совместимости, web — композиции страниц, партнёры — стабильного внешнего контракта. Отдельный BFF оправдан, если эти различия регулярно мешают независимым изменениям.

Общие доменные правила остаются в сервисах-владельцах; BFF адаптирует представление и координирует клиентский сценарий. Создавать отдельный BFF для каждого экрана обычно избыточно. Если различия невелики, один API с понятными контрактами может быть проще.

# Чем client-side service discovery отличается от server-side discovery?

При **client-side discovery** клиент получает доступные адреса и сам выбирает экземпляр; ему нужны логика балансировки и обновление списка. При **server-side discovery** клиент обращается к стабильному адресу router или load balancer, который выбирает backend.

Второй вариант упрощает клиентов, но добавляет инфраструктурную зависимость и иногда сетевой переход. В обоих случаях важны актуальность регистрации, исключение недоступных экземпляров и поведение при отказе discovery. Конкретная реализация может использовать DNS, реестр или платформенную абстракцию. [Server-side discovery](https://microservices.io/patterns/server-side-discovery.html).

# Как DNS, реестр сервисов и health checks участвуют в поиске экземпляра сервиса?

Реестр хранит адреса и состояние экземпляров; DNS позволяет разрешить логическое имя сервиса. Балансировщик или клиент получает список кандидатов и использует health checks либо платформенные сигналы готовности для исключения неподходящих адресов.

DNS-кэш и TTL означают, что удаление записи не мгновенно меняет поведение всех клиентов. Долгоживущие соединения тоже могут оставаться привязанными к старому экземпляру. Для завершения работы используют снятие готовности и draining, а health checks проектируют так, чтобы краткий сбой зависимости не вызвал массовое отключение всей системы.

# Чем service mesh отличается от API Gateway и когда его сложность оправдана?

API Gateway управляет входом в API и часто обслуживает внешних клиентов. **Service mesh** предоставляет общие возможности связи между workloads: управление трафиком, шифрование, идентификацию и телеметрию, обычно через инфраструктурные прокси или другой слой платформы.

Mesh полезен при большом числе сервисов и потребности в единых политиках, но добавляет компоненты, конфигурацию и сложность диагностики. Он не заменяет предметную авторизацию и корректный контракт приложения. Для небольшой системы библиотек и стандартных возможностей платформы может быть достаточно. [Возможности service mesh на примере Istio](https://istio.io/latest/about/service-mesh/).

# Как передавать identity и проверять права при вызовах между сервисами?

Различают identity вызывающего сервиса и конечного пользователя. Сервис может аутентифицироваться через mTLS или собственный токен, а делегированные пользовательские полномочия передаваться отдельным проверяемым контекстом с подходящими `audience`, сроком жизни и scope.

Получатель самостоятельно проверяет доверенный источник identity и доступ к ресурсу. Нельзя доверять произвольному `X-User-Id` из внешнего запроса или пересылать привилегированный токен всем downstream-сервисам. Пользовательские и сервисные полномочия связывают по явным правилам, чтобы избежать confused deputy.

# Как согласовать deadline, timeout и retry budget по цепочке сервисных вызовов?

**Deadline** задаёт крайний срок всей операции; downstream-вызов получает оставшийся бюджет с запасом на возврат ответа. Timeout конкретной попытки не должен превышать этот остаток. После отмены прекращают ненужную работу и освобождают ресурсы.

Retry budget ограничивает общее число и стоимость повторов. Если три уровня независимо делают по три попытки, нагрузка на нижний уровень может вырасти до 27 вызовов. Повторы размещают на осмысленном уровне и разрешают только при подходящей семантике операции. [Deadline propagation в gRPC](https://grpc.io/docs/guides/deadlines/).

# Как эволюционировать межсервисный контракт без одновременного релиза всех участников?

Изменения вводят через совместимый переход: сначала получатель принимает старый и новый формат, затем отправители переходят на новый, после наблюдения и установленного срока старый контракт удаляют. Новые необязательные поля безопасны лишь при корректной обработке неизвестных полей клиентами.

Проверяют схемы и потребительские контрактные тесты, включая старые версии и семантику ошибок. Для событий учитывают сохранённую историю и replay: прежние записи могут читаться намного позже релиза. Версия URL или схемы сама по себе не обеспечивает совместимость.

# Как передавать trace context и диагностировать частичные отказы между сервисами?

Trace context передают через HTTP/gRPC metadata и заголовки сообщений; каждый значимый вызов создаёт связанный span. Для отложенной обработки выбирают подходящую связь, включая span links, если несколько причин объединяются в одну операцию.

Логи связывают с trace и идентификатором бизнес-операции, а метрики показывают задержки и ошибки по зависимостям. Контекст от внешнего клиента считают недоверенным; в baggage не передают секреты. Tracing помогает локализовать частичный отказ, но не заменяет сохранённое состояние процесса. [Context propagation OpenTelemetry](https://opentelemetry.io/docs/concepts/context-propagation/).

# Как предотвращать chatty communication и каскадные отказы при агрегации данных?

Chatty communication сокращают пакетными запросами, подходящими контрактами, агрегацией или локальной read model из событий. Сначала измеряют число переходов и объём данных: скрыть множество запросов одним внешним endpoint недостаточно, если внутри остаётся тот же дорогой fan-out.

Для каскадных отказов задают deadlines, предел параллельности, ограниченные retries, circuit breaker и изоляцию ресурсов. Некритичные данные могут иметь fallback с явным признаком неполноты. Отсутствие ответа нельзя незаметно превращать в бизнес-значение вроде нулевого остатка.
