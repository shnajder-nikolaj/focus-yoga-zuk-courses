# Как API server, etcd, scheduler и controller manager разделяют обязанности control plane?

**API server** принимает Kubernetes API-запросы, выполняет необходимые проверки и предоставляет доступ к состоянию объектов. **etcd** хранит согласованные данные control plane. **Scheduler** выбирает node для подходящих ещё не размещённых Pods, а **controller manager** запускает циклы управления, например replicas и nodes.

Компоненты взаимодействуют через API и наблюдение состояния, а не выполняют единую последовательность команд для каждого приложения. Отказ одного процесса и потеря quorum etcd имеют разные последствия. Важны HA control plane, ограничение доступа и проверяемые backups etcd. [Архитектура Kubernetes](https://kubernetes.io/docs/concepts/architecture/).

# Как kubelet, container runtime и сетевые компоненты обеспечивают выполнение Pod на node?

**Kubelet** наблюдает назначенные node Pods и организует их выполнение через container runtime по CRI. Runtime создаёт и запускает containers, а kubelet управляет необходимыми probes, volumes и сообщает status.

CNI и связанные сетевые компоненты настраивают Pod network, а Service dataplane обеспечивает соответствующую маршрутизацию. Kubelet не выбирает сам глобально лучший node для обычного Pod: это задача scheduler. Наличие здорового API server не гарантирует, что конкретный worker способен получить image, подключить volume и запустить процесс; эти зависимости проверяют отдельно.

# Как declarative API, spec, status и reconciliation связывают желаемое состояние с фактическим?

В **spec** пользователь или controller описывает желаемую конфигурацию, в **status** компоненты сообщают наблюдаемое состояние. **Reconciliation** повторно сравнивает их и выполняет действия для приближения к цели.

Принятие объекта API означает, что запрос прошёл необходимые проверки и сохранён, но не что инфраструктура уже готова. Controller должен переносить повтор, временные ошибки и рестарт. Поля имеют владельцев, поэтому два механизма, одновременно меняющих один параметр, могут конфликтовать. Для оценки результата смотрят conditions, актуальность status и фактическую работоспособность.

# Почему Pod является единицей размещения и какие ресурсы разделяют его containers?

**Pod** объединяет тесно связанные containers, размещаемые на одном node и имеющие общий lifecycle-контекст. Они разделяют network namespace, Pod IP и port space, поэтому могут обращаться друг к другу через loopback; declared volumes могут подключаться нескольким containers.

При этом writable filesystem каждого container отдельно, а PID namespace не становится общим автоматически. Pod не распределяется частями по нескольким nodes. Объединять независимые сервисы в один Pod только ради удобства сети обычно мешает отдельному масштабированию и обновлению. Сам процесс приложения всё равно должен поддерживать корректное завершение.

# Как init containers и sidecars дополняют жизненный цикл основного container?

Обычные **init containers** выполняют подготовку и должны успешно завершиться до запуска основных containers: например, сформировать configuration или дождаться нужного предусловия. Их повторяемость важна, поскольку попытка может запускаться заново.

**Sidecar** работает рядом с приложением и предоставляет вспомогательную функцию: proxy, log shipping или синхронизацию. В поддерживаемых версиях native sidecars описываются специальной моделью restartable init containers, что влияет на порядок старта и завершения. Обычный второй container не получает все эти свойства автоматически. Учитывают readiness, ресурсы и поведение при завершении Job.

# Как ReplicaSet поддерживает число replicas и зачем над ним нужен Deployment?

**ReplicaSet** стремится поддерживать требуемое число Pods, соответствующих selector и Pod template. Он создаёт недостающие экземпляры и удаляет лишние, но не даёт сам по себе полноценной модели смены версии приложения.

**Deployment** управляет ReplicaSets и rollout: при изменении Pod template создаёт новую revision и регулирует переход между старым и новым набором. Поэтому обычно создают Deployment, а не вручную редактируют принадлежащий ему ReplicaSet. Изменение числа replicas у подчинённого объекта может быть перезаписано вышестоящим controller.

# Как revision, Pod template и rollout strategy задают обновление Deployment?

Изменение **Pod template**, например image или environment, инициирует новую Deployment revision с новым ReplicaSet. Масштабирование replicas само по себе обычно не создаёт новую revision. Strategy задаёт способ перехода, например RollingUpdate или Recreate.

Контроллер регулирует допустимую доступность, но успешный rollout не доказывает корректность бизнес-функции. Проверяют фактическую версию, readiness, метрики и взаимодействие старых и новых экземпляров. Возврат revision меняет workload-конфигурацию, а не отменяет изменения БД и внешние эффекты. Историю сохраняют по выбранной политике, чтобы предыдущая revision была доступна.

# Как StatefulSet сохраняет identity, порядок запуска и связь Pod с persistent storage?

**StatefulSet** предоставляет устойчивую ordinal identity Pods, предсказуемые имена и связь с индивидуальными PVC через `volumeClaimTemplates`. Новый экземпляр может вернуться к storage прежней identity вместо получения случайных данных другой replica.

Правила Pod management и update strategy регулируют порядок действий; это полезно приложениям со своей кластерной логикой. Но StatefulSet не реализует replication протокол БД, выбор её лидера или backup. Стабильный DNS требует соответствующей Service-конфигурации, а сохранность PVC при удалении зависит от выбранных retention policies и storage. [StatefulSets](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/).

# Когда выбирать Deployment, StatefulSet, DaemonSet, Job или CronJob?

**Deployment** подходит для взаимозаменяемых replicas, **StatefulSet** — когда важны identity и привязка к данным. **DaemonSet** запускает подходящий экземпляр на выбранных nodes, например node agent.

**Job** управляет выполнением до завершения по заданным условиям, **CronJob** создаёт Jobs по расписанию. Повторы и пересечения запусков учитывают на уровне workload: scheduled execution не означает ровно один бизнес-эффект. Выбор controller определяется lifecycle и требованиями приложения, а не только наличием volume. Сервис с состоянием не становится отказоустойчивой БД автоматически от смены Deployment на StatefulSet.

# Как ownerReferences, labels и selectors влияют на управление и удаление ресурсов?

**Labels** классифицируют объекты, **selectors** выбирают набор, а **ownerReferences** фиксируют управление и участвуют в garbage collection. Controller может принять подходящий объект без текущего владельца по правилам своего типа; совпадение label не является универсальным доказательством ownership.

Слишком широкий или пересекающийся selector способен затронуть лишние Pods. При удалении владельца поведение зависимых объектов зависит от propagation policy, ownership и finalizers. Финальные данные на volume могут иметь иной lifecycle. Имена, namespace, UID и цепочку владельцев проверяют до массовых операций.

# Как Pod phases, container states и restartPolicy описывают сбой и восстановление?

**Pod phase** — крупная сводка, например Pending, Running, Succeeded или Failed. **Container states** отражают Waiting, Running и Terminated с причинами и exit codes. Running Pod не обязательно готов принимать трафик, а `CrashLoopBackOff` описывает повторные сбои и задержку restart, не отдельную Pod phase.

`restartPolicy` определяет допустимый перезапуск containers kubelet в данном Pod. Замена самого Pod на другом node — работа controller, а не такой локальный restart. Проверяют условия, предыдущие container logs и ownership, чтобы понимать, какой механизм восстанавливает workload.

# Что происходит с workloads при отказе worker node, API server или quorum etcd?

При отказе **worker node** обычные containers перестают быть доступными, а controllers после обнаружения и предусмотренных задержек могут создать replacement Pods на других nodes. Этому нужны capacity, подходящая topology и доступное storage; защита от старого writer остаётся важной для данных.

При недоступном **API server** уже работающие процессы часто продолжают работу, но управление и новые изменения ограничены. Потеря **quorum etcd** препятствует нормальному согласованному обновлению control-plane state. Восстановление этих компонентов не равно восстановлению всех application data: у БД и volumes свои процедуры.
