# Какую проблему решает TanStack Query?

TanStack Query - библиотека для управления асинхронным состоянием, прежде всего данными, получаемыми с сервера.

Она решает типичные проблемы работы с серверными данными:

- Кэширование - повторное использование ранее загруженных данных
- Дедупликация запросов - объединение одновременных запросов с одинаковым `queryKey`
- Синхронизация - обновление устаревших данных в фоне
- Управление состояниями - отслеживание загрузки, ошибок и успешных запросов
- Инвалидация - пометка данных как устаревших после изменений
- Мутации - отправка изменений на сервер, включая optimistic updates
- Пагинация - управление постраничной загрузкой и бесконечными списками

Без TanStack Query эти механизмы приходится реализовывать самостоятельно через `useEffect`, `useState`, Context или другие инструменты.

TanStack Query не заменяет HTTP-клиент: запросы по-прежнему выполняются через `fetch`, `axios` или аналогичные средства.

# Что такое server state и почему его не стоит приравнивать к client state?

Server state - данные, источником истины для которых является сервер: пользователи, товары, заказы и другие ресурсы API.

Client state - состояние, которым управляет само приложение: открытые модальные окна, выбранные вкладки, локальные настройки интерфейса.

Основные отличия server state:

- Данные могут изменяться независимо от клиента
- Локальная копия может устаревать
- Получение и обновление требуют асинхронных операций
- Возможны сетевые ошибки и задержки
- Требуются кэширование, повторные запросы и синхронизация

Например, список заказов может измениться на сервере из-за действий другого пользователя. Локальное состояние React само об этом не узнает.

Поэтому server state требует механизмов синхронизации с источником истины, а не только хранения значений.

TanStack Query управляет серверными данными, тогда как `useState`, `useReducer` и Zustand обычно используют для клиентского состояния. Граница зависит от того, кому принадлежат данные и кто отвечает за их актуальность.

# Что такое `queryKey` и почему он должен учитывать параметры запроса?

`queryKey` - уникальный ключ, по которому TanStack Query идентифицирует запрос и хранит его результат в кэше.

В TanStack Query v5 ключ задаётся массивом:

```
useQuery({
  queryKey: ['users', { page, status }],
  queryFn: () => fetchUsers({ page, status }),
})
```

Все параметры, влияющие на результат запроса, должны входить в `queryKey`.

Если использовать один ключ для разных страниц или фильтров, библиотека будет считать их одним запросом, что может привести к отображению неправильных данных.

При изменении `queryKey` компонент подписывается на другую запись кэша. Если подходящих актуальных данных нет, выполняется загрузка.

Особенности:

- Ключи сравниваются через детерминированное хеширование
- Порядок элементов массива имеет значение
- Порядок свойств внутри объекта значения не имеет
- Разные ключи создают независимые записи кэша

Ключи также используются для инвалидации и обновления данных через `QueryClient`.&#x20;

# Как работают `useQuery` и `useMutation`?

`useQuery` используется для получения и кэширования данных.

```
const { data, isPending, isFetching, error } = useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
})
```

При выполнении `useQuery` библиотека:

1. Находит запись по `queryKey` в кэше
2. Возвращает доступные кэшированные данные
3. При необходимости запускает `queryFn`
4. Сохраняет результат и уведомляет подписанные компоненты

`useMutation` используется для операций изменения данных: создания, обновления и удаления.

```
const mutation = useMutation({
  mutationFn: createUser,
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['users'] })
  },
})

mutation.mutate({ name: 'Alex' })
```

`useMutation` предоставляет `mutate`, `mutateAsync`, состояния `isPending`, `isSuccess`, `isError` и обработчики жизненного цикла.

Главное отличие: `useQuery` управляет получением и синхронизацией кэшируемых данных, а `useMutation` - выполнением операций изменения. Мутации не инвалидируют связанные запросы автоматически.

# Чем `staleTime` отличается от `gcTime`?

`staleTime` определяет, сколько времени данные после успешного обновления считаются актуальными (`fresh`).

Пока данные актуальны, обычные триггеры автоматического обновления, такие как повторное монтирование компонента или возвращение фокуса, не запускают запрос.

По умолчанию `staleTime: 0`, поэтому данные сразу считаются устаревшими.

`gcTime` определяет, через какое время неиспользуемая запись кэша удаляется сборщиком мусора.

Отсчёт начинается, когда запрос становится неактивным, то есть перестаёт иметь активных подписчиков. По умолчанию в браузере `gcTime` равен 5 минутам.

```
useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
  staleTime: 60_000,
  gcTime: 300_000,
})
```

Здесь данные считаются актуальными одну минуту, а после исчезновения подписчиков могут оставаться в кэше ещё пять минут.

Разница: `staleTime` управляет актуальностью данных, `gcTime` - временем хранения неиспользуемого кэша.

В v5 также поддерживаются `staleTime: Infinity` и `staleTime: 'static'`. Первый вариант позволяет вручную инвалидировать данные, второй блокирует обновления на основе инвалидации. В SSR `gcTime` по умолчанию равен `Infinity`.

# Что означают fresh, stale, fetching и inactive для кэша?

Эти понятия описывают разные характеристики запроса и не являются взаимоисключающими состояниями.

- Fresh - данные актуальны согласно `staleTime`. Обычные автоматические триггеры не вызывают их повторную загрузку.
- Stale - данные считаются устаревшими. Они остаются доступными, но могут обновляться при наступлении соответствующего события.
- Fetching - запрос выполняется в данный момент. Может происходить как первоначальная загрузка, так и фоновое обновление существующих данных.
- Inactive - у запроса нет активных подписчиков. Его результат может оставаться в кэше до истечения `gcTime`.

Например, запрос может одновременно находиться в состояниях `stale` и `fetching`: пользователь видит старые данные, пока загружается их новая версия.

В API TanStack Query v5 загрузка дополнительно разделяется на `status` (`pending`, `success`, `error`) и `fetchStatus` (`fetching`, `paused`, `idle`).

Поэтому `isPending` не эквивалентен `isFetching`: запрос может находиться в состоянии `pending`, но ещё не выполняться, например при `enabled: false`.

# Как устроены background refetch и window focus refetch?

Background refetch - повторная загрузка данных в фоне без удаления предыдущего результата из интерфейса.

Когда запрос становится устаревшим, TanStack Query может обновить его при определённых событиях:

- Монтирование нового подписчика (`refetchOnMount`)
- Возвращение пользователя на вкладку (`refetchOnWindowFocus`)
- Восстановление сетевого соединения (`refetchOnReconnect`)
- Срабатывание заданного интервала (`refetchInterval`)

Window focus refetch по умолчанию включён. В TanStack Query v5 для определения возвращения пользователя к странице используется событие `visibilitychange`.

```
useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
  staleTime: 60_000,
  refetchOnWindowFocus: true,
})
```

Если пользователь вернулся на вкладку через 30 секунд после загрузки, запрос не повторится: данные ещё актуальны. Если через 90 секунд - может запуститься фоновое обновление.

При background refetch старые данные остаются доступными, а `isFetching` становится `true`.

Важно: истечение `staleTime` само по себе не запускает запрос. Оно только делает данные устаревшими. Для обновления необходим соответствующий триггер.&#x20;

# Как отменять запросы при смене query key?

TanStack Query передаёт в `queryFn` объект `AbortSignal`, который позволяет отменять асинхронные операции.

```
useQuery({
  queryKey: ['users', userId],
  queryFn: async ({ signal }) => {
    const response = await fetch(`/api/users/${userId}`, {
      signal,
    })

    if (!response.ok) {
      throw new Error('Failed to fetch user')
    }

    return response.json()
  },
})
```

Когда `queryKey` изменяется и предыдущий запрос становится неактуальным или неиспользуемым, TanStack Query может прервать его через `AbortSignal`.

Ключевой момент: реальная отмена сетевого запроса происходит только тогда, когда `queryFn` передаёт `signal` в поддерживающий отмену HTTP-клиент.

Если `signal` не используется, прежний запрос по умолчанию может продолжить выполнение и сохранить результат в собственную запись кэша.

Для ручной отмены:

```
await queryClient.cancelQueries({
  queryKey: ['users'],
})
```

При отмене TanStack Query также восстанавливает предыдущее состояние отменяемого запроса.&#x20;

# Когда нужен `enabled` у запроса?

`enabled` управляет возможностью автоматического выполнения запроса.

Чаще всего используется, когда запрос нельзя выполнить до появления необходимых данных.

```
const { data } = useQuery({
  queryKey: ['user', userId],
  queryFn: () => fetchUser(userId!),
  enabled: userId != null,
})
```

Пока `userId` отсутствует, запрос автоматически не выполняется. Когда условие становится истинным, TanStack Query может начать загрузку.

Другие сценарии: ожидание авторизации, применение фильтров по кнопке, загрузка данных после открытия определённого раздела.

При `enabled: false`:

- Автоматическая загрузка и фоновое обновление отключены
- `invalidateQueries` и `refetchQueries` не запускают повторный запрос
- Ручной `refetch()` остаётся доступным

В TypeScript альтернативой может быть `skipToken`, но при его использовании ручной `refetch()` не работает.&#x20;

# Как использовать `select` для преобразования данных?

`select` позволяет преобразовать результат запроса перед передачей его компоненту, не изменяя исходные данные в кэше.

```
const { data: activeUsers } = useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
  select: (users) => users.filter((user) => user.active),
})
```

В кэше сохраняется полный массив пользователей, но компонент получает только активных.

`select` позволяет:

- Фильтровать и сортировать данные
- Извлекать конкретные поля
- Вычислять производные значения
- Сокращать объём данных, используемых компонентом

Преобразование повторно выполняется при изменении исходных данных или ссылки на функцию `select`. Для дорогостоящих преобразований полезно использовать стабильную функцию, например через `useCallback`.

Разные компоненты могут использовать один `queryKey`, но получать разные представления общих кэшированных данных.

# Как работают `invalidateQueries`, `refetchQueries` и `removeQueries`?

Все три метода работают с записями кэша, но выполняют разные действия.

`invalidateQueries` помечает подходящие запросы как устаревшие, независимо от их `staleTime`.

```
queryClient.invalidateQueries({
  queryKey: ['users'],
})
```

По умолчанию активные запросы после инвалидации обновляются в фоне. Неактивные остаются в кэше и могут обновиться при последующем использовании.

`refetchQueries` непосредственно запускает повторную загрузку подходящих запросов, даже если данные считаются актуальными.

```
queryClient.refetchQueries({
  queryKey: ['users'],
  type: 'active',
})
```

`removeQueries` удаляет подходящие записи из кэша без их повторной загрузки.

```
queryClient.removeQueries({
  queryKey: ['users'],
})
```

По умолчанию ключи сопоставляются по префиксу: `['users']` соответствует также `['users', 5]`. Для точного совпадения используется `exact: true`.

Обычно после мутации применяется `invalidateQueries`, для принудительного обновления - `refetchQueries`, а для очистки ненужного кэша - `removeQueries`.

Отключённые через `enabled: false` запросы не обновляются этими методами автоматически.&#x20;

# Как организовать optimistic updates?

Optimistic update - обновление интерфейса до получения подтверждения от сервера.

Пользователь сразу видит результат действия, пока мутация выполняется в фоне.

Типичная последовательность:

1. Отменить текущие запросы, которые могут перезаписать оптимистичные данные
2. Сохранить предыдущее состояние кэша
3. Обновить кэш через `setQueryData`
4. Выполнить мутацию
5. При ошибке восстановить старые данные
6. После завершения синхронизировать кэш с сервером

Пример:

```
useMutation({
  mutationFn: updateUser,

  onMutate: async (updatedUser) => {
    await queryClient.cancelQueries({
      queryKey: ['user', updatedUser.id],
    })

    const previousUser = queryClient.getQueryData([
      'user',
      updatedUser.id,
    ])

    queryClient.setQueryData(
      ['user', updatedUser.id],
      (old: User | undefined) =>
        old ? { ...old, ...updatedUser } : old,
    )

    return { previousUser }
  },

  onError: (_error, updatedUser, result) => {
    queryClient.setQueryData(
      ['user', updatedUser.id],
      result?.previousUser,
    )
  },

  onSettled: (_data, _error, updatedUser) => {
    return queryClient.invalidateQueries({
      queryKey: ['user', updatedUser.id],
    })
  },
})
```

В TanStack Query v5 `onMutate` может вернуть значение, которое затем передаётся обработчикам `onError` и `onSettled`.

Важно учитывать конкурентные мутации: если несколько изменений одного ресурса выполняются одновременно, простой откат к сохранённому снимку может перезаписать более новое изменение.

# Как откатывать optimistic updates при ошибке мутации?

Для отката используется сохранённое до оптимистичного обновления состояние кэша.

В `onMutate` нужно получить предыдущие данные и вернуть их:

```
onMutate: async (newData) => {
  await queryClient.cancelQueries({
    queryKey: ['items'],
  })

  const previousItems = queryClient.getQueryData(['items'])

  queryClient.setQueryData(['items'], newData)

  return { previousItems }
}
```

Если мутация завершается ошибкой, `onError` восстанавливает прежнее значение:

```
onError: (_error, _variables, result) => {
  queryClient.setQueryData(
    ['items'],
    result?.previousItems,
  )
}
```

Затем можно инвалидировать запрос в `onSettled`, чтобы получить фактическое состояние с сервера.

Важно: откат должен учитывать все изменённые записи кэша. Если оптимистичная мутация изменила и список, и отдельный объект, восстановить нужно оба.

Для простых случаев достаточно повторного запроса, но сохранение предыдущего состояния позволяет выполнить откат даже при недоступности сервера.&#x20;

# Как правильно инвалидировать кэш после мутации?

После успешной мутации необходимо инвалидировать запросы, результаты которых могли измениться на сервере.

Обычно инвалидацию выполняют в `onSuccess`:

```
const mutation = useMutation({
  mutationFn: updateUser,

  onSuccess: (_data, variables) => {
    return Promise.all([
      queryClient.invalidateQueries({
        queryKey: ['users'],
      }),
      queryClient.invalidateQueries({
        queryKey: ['user', variables.id],
      }),
    ])
  },
})
```

Здесь инвалидируются список пользователей и данные конкретного пользователя.

Основные правила:

- Инвалидировать все связанные данные, включая списки, детали и агрегаты
- Использовать точные ключи или префиксы, чтобы не обновлять лишние запросы
- Применять `onSuccess`, если обновление необходимо только после успешной операции
- Применять `onSettled`, если синхронизация нужна независимо от результата
- Возвращать `Promise` из обработчика, если мутация должна оставаться в состоянии `pending` до завершения обновления

Если сервер возвращает обновлённый объект, можно сразу записать его через `setQueryData`, а связанные списки инвалидировать отдельно.

Главный принцип: инвалидировать данные, на которые повлияла мутация, а не весь кэш приложения.&#x20;

# Чем `initialData` отличается от `placeholderData`?

Оба параметра позволяют отображать данные до завершения обычной загрузки, но по-разному влияют на кэш.

`initialData` устанавливает начальное значение непосредственно в кэш запроса.

```
useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
  initialData: initialUsers,
})
```

Эти данные считаются полноценным результатом запроса. Если `staleTime` равен нулю, они сразу будут устаревшими и могут обновиться в фоне.

Для указания фактического времени получения начальных данных существует `initialDataUpdatedAt`.

`placeholderData` предоставляет временные данные только наблюдателю запроса и не сохраняет их в основной кэш.

```
useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
  placeholderData: [],
})
```

Пока отображается временный результат, `isPlaceholderData` равен `true`, а запрос может выполняться в фоне.

Главное отличие: `initialData` подходит для уже известных полноценных данных, `placeholderData` - для временного или неполного представления, которое не должно считаться реальным результатом запроса.&#x20;

# Как работает `useInfiniteQuery`?

`useInfiniteQuery` предназначен для последовательной загрузки страниц, например при бесконечной прокрутке или использовании кнопки «Загрузить ещё».

В отличие от `useQuery`, он хранит несколько страниц внутри одной записи кэша.

```
const {
  data,
  fetchNextPage,
  hasNextPage,
  isFetchingNextPage,
} = useInfiniteQuery({
  queryKey: ['posts'],
  queryFn: ({ pageParam }) => fetchPosts(pageParam),
  initialPageParam: null as string | null,
  getNextPageParam: (lastPage) =>
    lastPage.nextCursor ?? undefined,
})
```

Основные элементы:

- `initialPageParam` - параметр первой страницы
- `queryFn` - функция получения страницы с использованием `pageParam`
- `getNextPageParam` - определяет параметр следующей страницы
- `fetchNextPage()` - загружает следующую страницу
- `hasNextPage` - показывает, доступны ли следующие страницы
- `isFetchingNextPage` - показывает состояние загрузки следующей страницы

Результат хранится в виде:

```
data.pages       // Массив загруженных страниц
data.pageParams  // Параметры этих страниц
```

Для отображения элементы можно объединить:

```
const posts = data?.pages.flatMap((page) => page.items) ?? []
```

При обновлении infinite query загруженные страницы обычно повторно запрашиваются последовательно, чтобы избежать проблем с устаревшими курсорами.

Важно не запускать неконтролируемые параллельные `fetchNextPage`, поскольку страницы одной infinite query используют общий кэш. Для ограничения количества хранимых страниц предусмотрен `maxPages`.&#x20;

# Как реализовать dependent queries?

Dependent queries - запросы, выполнение которых зависит от результата других запросов.

Например, для загрузки заказов сначала необходимо получить пользователя.

```
const { data: user } = useQuery({
  queryKey: ['user'],
  queryFn: fetchUser,
})

const { data: orders } = useQuery({
  queryKey: ['orders', user?.id],
  queryFn: () => fetchOrders(user!.id),
  enabled: user != null,
})
```

Механизм работы:

1. Выполняется запрос пользователя
2. Пока пользователь неизвестен, запрос заказов отключён
3. После получения пользователя `enabled` становится `true`
4. Запускается запрос заказов с соответствующим `queryKey`

Важно включать значение зависимости в `queryKey`. Иначе при смене пользователя запрос может использовать данные предыдущего пользователя.

Недостаток зависимых запросов - request waterfall: второй запрос начинается только после завершения первого, увеличивая общее время загрузки.

Если API позволяет получить необходимые данные одним запросом или выполнить независимые запросы параллельно, последовательная зависимость не требуется.&#x20;

# Как избежать дублирования запросов несколькими компонентами?

TanStack Query автоматически дедуплицирует одновременно выполняющиеся запросы с одинаковым `queryKey` внутри одного `QueryClient`.

```
// ComponentA
useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
})

// ComponentB
useQuery({
  queryKey: ['users'],
  queryFn: fetchUsers,
})
```

Если оба компонента запрашивают данные одновременно, TanStack Query использует один выполняющийся запрос. Оба компонента получают его результат.

Для корректной дедупликации необходимо:

- Использовать общий экземпляр `QueryClient`
- Применять одинаковые ключи для одинаковых ресурсов
- Включать все влияющие на результат параметры в `queryKey`
- Настраивать `staleTime`, чтобы избежать ненужных повторных загрузок при последующих монтированиях

Важно: дедупликация одновременных запросов не означает, что запрос выполнится только один раз за всё время работы приложения.

Если данные стали `stale`, новые события могут инициировать повторную загрузку.

# Как работает prefetching запросов?

Prefetching - предварительная загрузка данных до того, как компонент начнёт их использовать.

Применяется, например, при наведении на ссылку, перед переходом на страницу или в загрузчиках маршрутов.

Традиционный API TanStack Query:

```
await queryClient.prefetchQuery({
  queryKey: ['user', userId],
  queryFn: () => fetchUser(userId),
  staleTime: 60_000,
})
```

Библиотека выполняет запрос и сохраняет результат в кэше. Когда компонент вызывает `useQuery` с тем же ключом, он может сразу получить готовые данные.

Если данные ещё актуальны согласно `staleTime`, дополнительная загрузка не требуется.

Особенности:

- Предварительно загруженные данные хранятся в общем кэше
- Если данные не используются, они удаляются согласно `gcTime`
- `prefetchQuery` не возвращает загруженные данные и не пробрасывает ошибку запроса
- Предварительная загрузка уменьшает задержку при последующей навигации

Особенность актуальных версий v5.105.x: `prefetchQuery` помечен устаревшим API в пользу `queryClient.query()`. Новый метод возвращает данные и пробрасывает ошибки, поэтому при предварительной загрузке без ожидания результата ошибку нужно обработать.

```
void queryClient
  .query({
    queryKey: ['user', userId],
    queryFn: () => fetchUser(userId),
    staleTime: 60_000,
  })
  .catch(() => {})
```

# Как использовать QueryClient вне React-компонентов?

`QueryClient` - центральный объект управления кэшем и запросами TanStack Query.

Его методы не зависят от React-хуков, поэтому доступны в обычных TypeScript-модулях, обработчиках событий, роутерах и сервисах.

Для клиентского приложения можно создать общий экземпляр:

```
// queryClient.ts
import { QueryClient } from '@tanstack/react-query'

export const queryClient = new QueryClient()
```

Передать его React:

```
<QueryClientProvider client={queryClient}>
  <App />
</QueryClientProvider>
```

А затем использовать вне компонентов:

```
import { queryClient } from './queryClient'

await queryClient.invalidateQueries({
  queryKey: ['users'],
})
```

Доступны методы:

- `getQueryData` - синхронное чтение данных из кэша
- `setQueryData` - обновление кэшированных данных
- `invalidateQueries` - инвалидация запросов
- `cancelQueries` - отмена запросов
- `query` - асинхронное получение и кэширование данных в актуальных v5

Важно: в браузерном приложении обычно используется стабильный общий экземпляр, а при SSR `QueryClient` должен изолироваться между серверными запросами, чтобы данные разных пользователей не смешивались.

# Как реализовать SSR dehydrate/hydrate?

Dehydration и hydration позволяют передать предварительно загруженные на сервере данные в клиентский кэш TanStack Query.

Процесс состоит из трёх этапов.

1\. Загрузка данных на сервере

Для каждого серверного запроса создаётся отдельный `QueryClient`, через который загружаются необходимые данные.

```
const queryClient = new QueryClient()

await queryClient.query({
  queryKey: ['users'],
  queryFn: fetchUsers,
  staleTime: 60_000,
})

const dehydratedState = dehydrate(queryClient)
```

`dehydrate()` создаёт состояние кэша для передачи клиенту. Его необходимо безопасно сериализовать средствами используемого SSR-фреймворка.

2\. Передача состояния клиенту

Сервер передаёт `dehydratedState` вместе с результатом рендеринга.

3\. Восстановление кэша на клиенте

```
<QueryClientProvider client={queryClient}>
  <HydrationBoundary state={dehydratedState}>
    <App />
  </HydrationBoundary>
</QueryClientProvider>
```

`HydrationBoundary` восстанавливает переданные запросы в клиентском кэше.

В результате компонент, вызывающий `useQuery` с тем же ключом, получает уже загруженные данные и может сразу их отобразить.

Важные особенности:

- На сервере нельзя использовать общий `QueryClient` для всех HTTP-запросов
- Ключи серверных и клиентских запросов должны совпадать
- По умолчанию `dehydrate()` включает только успешные запросы
- При `staleTime: 0` клиент может сразу повторно запросить гидратированные данные
- Необходимо учитывать сериализацию специальных типов и исключать конфиденциальные данные, которые нельзя передавать клиенту

В Next.js, Remix и других SSR-фреймворках способ передачи и восстановления состояния зависит от их архитектуры.&#x20;

# Какие проблемы возникают при сохранении query cache между сессиями пользователя?

TanStack Query хранит кэш в памяти, но его можно сохранять между перезагрузками приложения через `persistQueryClient` и соответствующие persister-адаптеры.

Основные риски:

1\. Утечка данных между пользователями

После выхода из аккаунта кэш может содержать личные данные предыдущего пользователя.

Если следующий пользователь получит доступ к сохранённому кэшу, он может увидеть чужую информацию.

2\. Устаревшие данные

Сохранённый результат может больше не соответствовать состоянию сервера.

3\. Изменение структуры данных

После обновления приложения формат сохранённых объектов может стать несовместимым с новой версией кода.

4\. Хранение чувствительной информации

Данные в `localStorage` и аналогичных хранилищах потенциально доступны JavaScript-коду страницы. Поэтому в них не следует сохранять токены, секреты и другую чувствительную информацию.

5\. Рост объёма кэша

Большие списки и результаты многочисленных запросов могут занимать значительный объём хранилища.

Для предотвращения проблем используют:

- Очистку памяти и сохранённого кэша при выходе из аккаунта
- Изоляцию кэша по идентификатору пользователя или сессии
- `maxAge` для ограничения срока жизни сохранённых данных
- `buster` для сброса кэша при несовместимых изменениях
- Исключение чувствительных запросов из персистентного хранения

Важно: `queryClient.clear()` очищает кэш текущего экземпляра. При использовании persister необходимо также обеспечить удаление соответствующих данных из постоянного хранилища.&#x20;

# Как синхронизировать серверные события с кэшем TanStack Query?

Для получения событий от сервера обычно используют WebSocket или Server-Sent Events (SSE).

После получения события приложение может синхронизировать кэш двумя способами.

1\. Инвалидация запроса

```
socket.onmessage = (event) => {
  const message = JSON.parse(event.data)

  if (message.type === 'user.updated') {
    queryClient.invalidateQueries({
      queryKey: ['user', message.userId],
    })
  }
}
```

TanStack Query помечает данные устаревшими и при необходимости повторно загружает их с сервера.

Этот подход подходит, когда событие сообщает только факт изменения ресурса.

2\. Непосредственное обновление кэша

Если событие содержит актуальные данные, их можно сразу записать:

```
socket.onmessage = (event) => {
  const message = JSON.parse(event.data)

  if (message.type === 'user.updated') {
    queryClient.setQueryData(
      ['user', message.user.id],
      message.user,
    )
  }
}
```

Это позволяет обновить интерфейс без дополнительного HTTP-запроса.

При реализации необходимо учитывать порядок событий, возможные пропуски при потере соединения и конкуренцию с обычными запросами. Для контроля порядка могут использоваться версии ресурсов или временные метки.

При отключении компонента или завершении сессии подписки на события нужно корректно закрывать.

Выбор подхода: `invalidateQueries` надёжнее, когда событие содержит неполные данные. `setQueryData` эффективнее, когда событие содержит полное актуальное состояние ресурса.

# Как реализовать пагинацию через TanStack Query?

Для классической постраничной навигации используется `useQuery`, а номер страницы включается в `queryKey`.

```
const [page, setPage] = useState(1)

const {
  data,
  isFetching,
  isPlaceholderData,
} = useQuery({
  queryKey: ['users', page],
  queryFn: () => fetchUsers(page),
  placeholderData: (previousData) => previousData,
})
```

При изменении `page` TanStack Query обращается к другой записи кэша.

Если страница уже была загружена и её данные ещё находятся в кэше, библиотека может использовать их повторно.

`placeholderData` позволяет отображать предыдущую страницу, пока загружается следующая, предотвращая резкое исчезновение контента.

В TanStack Query v5 для этого также предусмотрена функция `keepPreviousData`:

```
import { keepPreviousData } from '@tanstack/react-query'

useQuery({
  queryKey: ['users', page],
  queryFn: () => fetchUsers(page),
  placeholderData: keepPreviousData,
})
```

При отображении предыдущей страницы `isPlaceholderData` равен `true`. Это позволяет временно отключить переход вперёд, если сведения о следующей странице ещё не получены.

Дополнительно можно предварительно загружать следующую страницу через `QueryClient`, чтобы уменьшить задержку при переходе.

Важные отличия двух подходов:

- `useQuery` - каждая страница имеет собственный `queryKey` и независимую запись кэша. Подходит для обычной пагинации с переходом между страницами
- `useInfiniteQuery` - все загруженные страницы объединяются в одной записи кэша. Подходит для бесконечной прокрутки и кнопки «Загрузить ещё»

При offset-based пагинации сервер обычно получает `page` и `limit`. При cursor-based пагинации используется курсор, предоставленный сервером. Выбор зависит от API и требований к интерфейсу.&#x20;
