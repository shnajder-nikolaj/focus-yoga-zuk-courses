# Чем контролируемые формы отличаются от форм на ref?

Контролируемая форма (controlled) - значения полей хранятся в состоянии React и передаются через `value` или `checked`. Изменения обрабатываются через `onChange`, который обновляет состояние и вызывает повторный рендер соответствующего компонента.

Неконтролируемая форма (uncontrolled) - значения хранятся непосредственно в DOM. React получает их через `ref`, обычно при отправке формы или другом явном обращении к полю.

Основные различия:

- Контролируемые поля удобны для динамического интерфейса, мгновенной валидации и логики, зависящей от значений. Однако обновление состояния может приводить к дополнительным рендерам.
- Неконтролируемые поля требуют меньше синхронизации с React и обычно эффективнее при большом количестве полей. Однако для реактивного отображения значений необходимы дополнительные механизмы.

`React Hook Form` преимущественно использует неконтролируемые поля, но поддерживает оба подхода.

# Как работает `register()` в React Hook Form?

`register()` регистрирует поле в `React Hook Form`, связывая его с внутренним состоянием формы и механизмом валидации.

Функция возвращает набор свойств:

- `name` - уникальное имя поля, по которому хранится его значение.
- `ref` - ссылка на DOM-элемент.
- `onChange` - обработчик изменений значения.
- `onBlur` - обработчик потери фокуса.

Пример:

```
<input
  {...register("email", {
    required: "Укажите email",
    pattern: {
      value: /^\S+@\S+\.\S+$/,
      message: "Некорректный email",
    },
  })}
/>
```

При регистрации `React Hook Form` отслеживает значение поля, его взаимодействия с пользователем и результаты валидации.

Ключевая особенность: для обычных HTML-полей библиотека использует DOM и внутреннее хранилище значений, не требуя обновления React-состояния при каждом вводе. Компонент перерисовывается только при изменении данных, на которые он подписан.

# В каких случаях нужен `Controller`?

`Controller` используется для интеграции `React Hook Form` с контролируемыми компонентами, которым необходимо явно передавать `value` и `onChange`.

Типичные примеры - `Select`, `DatePicker`, `Autocomplete` и компоненты сторонних UI-библиотек, которые не поддерживают стандартную регистрацию через DOM `ref`.

```
<Controller
  name="country"
  control={control}
  render={({ field }) => (
    <CustomSelect
      value={field.value}
      onChange={field.onChange}
      onBlur={field.onBlur}
    />
  )}
/>
```

`Controller` предоставляет объект `field`, содержащий `value`, `onChange`, `onBlur`, `name` и `ref`. Эти свойства связывают компонент с состоянием формы.

Если компонент использует нестандартный формат событий, значения необходимо преобразовать при передаче в `field.onChange`.

Для обычных HTML-полей предпочтительнее `register()`, поскольку он проще и не требует контролируемого режима.

# Как работает `useFieldArray`?

`useFieldArray` - хук для управления динамическими массивами полей, например списком адресов, контактов или товаров.

Он предоставляет:

- `fields` - массив элементов со служебными уникальными идентификаторами.
- `append()`, `prepend()`, `insert()` - добавление элементов.
- `remove()` - удаление элементов.
- `swap()`, `move()` - изменение порядка.
- `update()`, `replace()` - обновление или замена элементов.

Пример для `React Hook Form v7`:

```
const { control, register } = useForm({
  defaultValues: {
    users: [{ name: "" }],
  },
});

const { fields, append, remove } = useFieldArray({
  control,
  name: "users",
});

return (
  <>
    {fields.map((field, index) => (
      <div key={field.id}>
        <input {...register(`users.${index}.name`)} />

        <button type="button" onClick={() => remove(index)}>
          Удалить
        </button>
      </div>
    ))}

    <button
      type="button"
      onClick={() => append({ name: "" })}
    >
      Добавить
    </button>
  </>
);
```

Важно: в React-ключах необходимо использовать `field.id`, а не индекс массива. Это позволяет сохранять правильное соответствие компонентов при перемещении и удалении элементов.

`fields` описывает структуру массива и начальные значения элементов, но не является реактивным источником текущих значений. Для отслеживания изменений используется `useWatch()`.

Метод `update()` размонтирует и заново монтирует обновляемый элемент. Если нужно изменить отдельное поле без такого поведения, лучше использовать `setValue()`.

В `React Hook Form v8` идентификатор элемента переименован из `id` в `key`.&#x20;

# Как передать значения формы валидационной схеме Zod?

Для интеграции `Zod` с `React Hook Form` используется `zodResolver` из пакета `@hookform/resolvers/zod`.

```
import { z } from "zod";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

const schema = z.object({
  email: z.email(),
  age: z.number().min(18, "Минимальный возраст - 18"),
});

type FormValues = z.infer<typeof schema>;

const {
  register,
  handleSubmit,
  formState: { errors },
} = useForm<FormValues>({
  resolver: zodResolver(schema),
});

const onSubmit = (data: FormValues) => {
  console.log(data);
};
```

При валидации `React Hook Form` автоматически передаёт значения формы в `zodResolver`, который:

1. Проверяет данные по схеме Zod.
2. Преобразует ошибки Zod в формат `formState.errors`.
3. Возвращает валидированные данные для `handleSubmit`, если проверка прошла успешно.

Вручную передавать значения в схему не требуется.

Важные особенности:

- HTML-поля обычно возвращают строки. Для чисел можно использовать `register("age", { valueAsNumber: true })` или преобразование в схеме.
- Для проверки зависимостей между полями применяются `refine()` или `superRefine()`.
- Если схема преобразует значения через `transform()`, типы `z.input<typeof schema>` и `z.output<typeof schema>` могут различаться. В таком случае их можно отдельно указать в `useForm<Input, Context, Output>()`.

# Как различаются синхронная и асинхронная валидации?

Синхронная валидация выполняется непосредственно во время вызова функции и сразу возвращает результат. Используется для проверки формата, обязательности, длины и диапазонов значений.

```
register("username", {
  required: "Обязательное поле",
  minLength: {
    value: 3,
    message: "Минимум 3 символа",
  },
});
```

Асинхронная валидация возвращает `Promise` и применяется, когда проверка требует асинхронной операции, например запроса к серверу для проверки уникальности имени.

```
register("username", {
  validate: async (value) => {
    const available = await checkUsername(value);

    return available || "Имя уже занято";
  },
});
```

`React Hook Form` ожидает завершения асинхронной проверки и обновляет ошибки. Состояние можно отслеживать через `formState.isValidating` и `validatingFields`.

Основные особенности асинхронной валидации:

- Задержки. При проверке на каждом изменении значения запросов может быть слишком много. Используется `debounce` или проверка при `onBlur`.
- Гонки запросов. Более ранний запрос может завершиться позже нового. Необходимо предотвращать применение устаревших результатов.
- Сетевые ошибки. Недоступность сервера следует обрабатывать отдельно от невалидности значения.

В Zod для асинхронных проверок используются асинхронные `refine()` и методы `parseAsync()` или `safeParseAsync()`. `zodResolver` поддерживает асинхронный режим.

Важно: клиентская валидация не заменяет серверную. Даже успешно проверенные браузером данные должны повторно проверяться сервером.

# Как реализовать зависимые поля формы?

Зависимые поля - поля, отображение, доступность или правила валидации которых зависят от значений других полей.

В `React Hook Form` для отслеживания зависимостей используются `watch()` или `useWatch()`.

Пример:

```
const { register, control } = useForm({
  defaultValues: {
    hasCompany: false,
    companyName: "",
  },
});

const hasCompany = useWatch({
  control,
  name: "hasCompany",
});

return (
  <>
    <input type="checkbox" {...register("hasCompany")} />

    {hasCompany && (
      <input {...register("companyName")} />
    )}
  </>
);
```

Когда `hasCompany` меняется, компонент получает новое значение и обновляет отображение зависимого поля.

Для более сложной логики используются:

- `setValue()` - программное изменение зависимого поля.
- `resetField()` - сброс значения и состояния поля.
- `trigger()` - повторная проверка указанного поля.
- `deps` в `register()` - повторная валидация указанных зависимых полей при проверке исходного поля.

Важный нюанс: при `shouldUnregister: false` значения размонтированных полей сохраняются. Если скрытое поле больше не должно участвовать в отправке, его нужно удалить через `unregister()` либо явно обработать при формировании данных.

Если используется Zod, условная обязательность и другие зависимости должны быть отражены и в схеме валидации. Само скрытие поля не отменяет ограничения схемы.

# Как обработать ошибки сервера на уровне отдельных полей?

Для установки серверных ошибок используется метод `setError()`.

Например, сервер возвращает ошибку о занятом email:

```
const onSubmit = async (data: FormValues) => {
  try {
    await createUser(data);
  } catch (error) {
    if (isEmailConflict(error)) {
      setError(
        "email",
        {
          type: "server",
          message: "Email уже используется",
        },
        { shouldFocus: true }
      );
    }
  }
};
```

Ошибка появится в `formState.errors.email` и может отображаться так же, как ошибка клиентской валидации.

Если сервер возвращает ошибки нескольких полей, их можно сопоставить с именами полей формы и последовательно вызвать `setError()`.

Для ошибок, не связанных с конкретным полем, используется `root`:

```
setError("root.server", {
  type: "server",
  message: "Не удалось сохранить данные",
});
```

Важные особенности:

- Серверные ошибки зарегистрированных полей могут исчезать при следующей успешной клиентской валидации.
- `setError()` не добавляет постоянное правило валидации. Если ограничение должно проверяться перед каждой отправкой, его необходимо реализовать отдельно.
- Ошибки сервера должны преобразовываться из формата API в понятные сообщения. Не следует напрямую выводить пользователю внутренние сведения сервера.

# Как организовать многошаговую форму с сохранением состояния?

Многошаговая форма (wizard) разделяет ввод данных на несколько последовательных этапов, сохраняя значения между переходами.

Основные способы организации:

- Один `useForm()`. Создаётся в родительском компоненте, а отдельные шаги отображаются условно. Данные хранятся в одном экземпляре формы.
- `FormProvider` и `useFormContext()`. Позволяют компонентам шагов получать доступ к общему состоянию без передачи методов через множество уровней `props`.
- Внешнее хранилище. Например, Zustand или Context. Используется, если шаги находятся на разных страницах или экземпляр формы может размонтироваться.

Пример:

```
const methods = useForm({
  defaultValues: {
    name: "",
    email: "",
    address: "",
  },
  shouldUnregister: false,
});

const [step, setStep] = useState(0);

return (
  <FormProvider {...methods}>
    {step === 0 && <PersonalStep />}
    {step === 1 && <AddressStep />}

    <button
      type="button"
      onClick={() => setStep((prev) => prev + 1)}
    >
      Далее
    </button>
  </FormProvider>
);
```

При `shouldUnregister: false` значения полей сохраняются после размонтирования соответствующих компонентов. Это поведение установлено по умолчанию в React Hook Form v7.

Если требуется сохранять прогресс после перезагрузки страницы, данные дополнительно записываются в `sessionStorage`, `localStorage` или на сервер.

Важно: данные из браузерного хранилища необходимо проверять при восстановлении. Чувствительные данные, например пароли, не следует сохранять в `localStorage`.

# Как избежать частых рендеров большой формы?

`React Hook Form` оптимизирует производительность за счёт неконтролируемых полей, внутреннего хранилища значений и подписок на отдельные части состояния.

Основные приёмы:

- Использовать `register()` для стандартных HTML-полей вместо перевода каждого поля в контролируемый режим.
- Использовать `useWatch()` внутри небольших компонентов, которым действительно нужно отслеживать изменения конкретных полей.
- Использовать `useFormState()` для локальной подписки на ошибки, `isDirty`, `isSubmitting` и другие свойства состояния.
- Избегать `watch()` без аргументов в корневом компоненте большой формы, поскольку он подписывает компонент на изменения всей формы.
- Применять `getValues()` для разового чтения значений без подписки и рендера.
- Использовать `React.memo()` для тяжёлых дочерних компонентов, если их свойства остаются стабильными.
- Не запускать тяжёлую валидацию на каждом вводе без необходимости. Настраивать `mode`, `reValidateMode` и задержки для дорогих проверок.

Например:

```
function PricePreview({ control }) {
  const price = useWatch({
    control,
    name: "price",
  });

  return <span>{price}</span>;
}
```

При изменении `price` обновляется компонент `PricePreview`, а не обязательно вся форма.

Ключевой принцип: подписывать компонент только на те значения и состояния, которые необходимы ему для отображения.

# Чем `defaultValues` отличаются от программного `reset()`?

`defaultValues` задаёт начальные значения полей при создании формы и служит базой для определения изменений через `isDirty` и `dirtyFields`.

```
const { register, reset } = useForm({
  defaultValues: {
    name: "Alex",
    email: "",
  },
});
```

Значения `defaultValues` кэшируются. Изменение объекта после инициализации не обновляет автоматически уже созданную форму.

`reset()` программно сбрасывает значения полей и состояние формы.

```
reset(); // Вернуть значения defaultValues

reset({
  name: "John",
  email: "john@example.com",
});
```

При вызове `reset()` без аргументов восстанавливаются текущие значения по умолчанию. При передаче новых значений они становятся новой базой сравнения, если не указан `keepDefaultValues: true`.

Дополнительные опции позволяют управлять сбросом:

- `keepErrors` - сохранить ошибки.
- `keepDirtyValues` - сохранить изменённые пользователем значения.
- `keepTouched` - сохранить информацию о посещённых полях.
- `keepDefaultValues` - сохранить прежнюю базу значений по умолчанию.

Если данные загружаются асинхронно, можно использовать асинхронные `defaultValues`, реактивное свойство `values` или вызвать `reset(data)` после получения ответа.

Ключевое различие: `defaultValues` определяет исходное состояние формы, а `reset()` позволяет программно восстановить или переопределить его во время работы приложения.

# Как работать с загрузкой файлов в форме?

Для загрузки файлов используется HTML-элемент `<input type="file">`. Он является неконтролируемым, поскольку браузер не позволяет программно устанавливать выбранный файл через `value`.

В `React Hook Form` файловый ввод можно зарегистрировать через `register()`:

```
const { register, handleSubmit } = useForm();

const onSubmit = async (data) => {
  const file = data.avatar?.[0];

  if (!file) return;

  const formData = new FormData();
  formData.append("avatar", file);

  await fetch("/api/upload", {
    method: "POST",
    body: formData,
  });
};

return (
  <form onSubmit={handleSubmit(onSubmit)}>
    <input
      type="file"
      accept="image/*"
      {...register("avatar")}
    />

    <button type="submit">Загрузить</button>
  </form>
);
```

Значение файлового поля обычно представляет собой `FileList`, содержащий объекты `File`.

Для отправки файлов часто используется `FormData`, позволяющий передавать бинарные данные в формате `multipart/form-data`.

Важные особенности:

- Атрибут `accept` ограничивает предлагаемые типы файлов в интерфейсе выбора, но не гарантирует их безопасность.
- Размер, тип и содержимое файла необходимо проверять на сервере.
- При использовании `fetch()` с `FormData` не нужно вручную устанавливать заголовок `Content-Type`, поскольку браузер самостоятельно добавит границу `multipart`.
- Для предварительного просмотра можно использовать `URL.createObjectURL()`, освобождая созданный URL через `URL.revokeObjectURL()`.
- Файлы не следует сохранять в `localStorage` как обычные значения формы.

`React Hook Form` также не поддерживает полноценное отслеживание `isDirty` для объектов `File` и `FileList`, поэтому состояние выбранных файлов при необходимости управляется отдельно.

# Как реализовать autosave и защититься от гонок запросов?

Autosave - автоматическое сохранение данных формы при изменении значений без явной отправки пользователем.

Типичная реализация:

1. Отслеживать изменения формы через `subscribe()` или `useWatch()`.
2. Использовать `debounce`, чтобы не отправлять запрос при каждом нажатии клавиши.
3. Проверять необходимость сохранения через `isDirty` или сравнение с последними сохранёнными данными.
4. Отправлять снимок значений формы на сервер.
5. После успешного сохранения обновлять состояние сохранённых данных.

Главная проблема - гонки запросов (race conditions).

Например:

- Пользователь вводит значение `A`, отправляется запрос №1.
- Затем вводит `B`, отправляется запрос №2.
- Запрос №2 завершается раньше запроса №1.
- Поздний ответ или обработка запроса №1 может привести к восстановлению устаревшего значения `A`.

Способы защиты:

- `AbortController` - отмена предыдущего запроса при появлении новых изменений.
- Request ID - идентификатор запроса, позволяющий игнорировать устаревшие ответы.
- Последовательное сохранение - следующий запрос отправляется после завершения предыдущего.
- Версионирование данных - сервер проверяет версию документа и отклоняет устаревшие изменения.

Важно понимать, что `AbortController` не гарантирует отмену уже начавшейся обработки на сервере. Поэтому для защиты сохранённых данных нужны последовательная запись или серверный контроль версий.

Дополнительно необходимо учитывать изменения, внесённые во время запроса. Вызов `reset(savedData)` после ответа может затереть новые пользовательские изменения.

В актуальных версиях React Hook Form для такого сценария доступен `resetDefaultValues(savedData)`, который обновляет базу сравнения `isDirty`, не изменяя текущие значения полей (начиная с v7.77).&#x20;

# Как обеспечить доступность формы с динамическими ошибками?

Доступность формы означает, что пользователи клавиатуры и скринридеров могут понимать назначение полей, обнаруживать ошибки и исправлять их.

Основные механизмы:

- `label` - связывает текстовое название с полем через `htmlFor` и `id`.
- `aria-invalid` - сообщает вспомогательным технологиям, что поле содержит ошибку.
- `aria-describedby` - связывает поле с текстом ошибки или дополнительной инструкцией.
- `role="alert"` - позволяет скринридеру объявлять динамически появляющиеся критичные ошибки.
- Управление фокусом - после неудачной отправки фокус переносится на первое некорректное поле.
- `aria-live="polite"` - используется для ненавязчивого объявления общего статуса формы, например результата сохранения.

Пример:

```
<label htmlFor="email">Email</label>

<input
  id="email"
  aria-invalid={!!errors.email}
  aria-describedby={
    errors.email ? "email-error" : undefined
  }
  {...register("email", {
    required: "Укажите email",
  })}
/>

{errors.email && (
  <p id="email-error" role="alert">
    {errors.email.message}
  </p>
)}
```

При ошибке скринридер сможет определить, что поле невалидно, и получить связанную с ним информацию.

Важные особенности:

- Ошибки должны содержать конкретное объяснение, а не просто сообщение «Некорректное значение».
- Нельзя передавать информацию об ошибках только цветом.
- Не следует агрессивно объявлять каждое изменение ошибки во время ввода - это затрудняет работу со скринридером.
- При нескольких ошибках полезно показывать общий список с возможностью перехода к проблемным полям.

В `React Hook Form` для управления фокусом используется `setFocus()`, а при ошибках отправки библиотека также поддерживает автоматическую фокусировку через `shouldFocusError`.

# Как React Hook Form использует особенности управляемых и неуправляемых полей?

`React Hook Form` использует гибридную архитектуру, объединяющую эффективность неконтролируемых полей с возможностями контролируемых компонентов.

Неконтролируемые поля

При использовании `register()` библиотека связывается с HTML-элементом через `ref` и обработчики событий.

Значения хранятся в DOM и внутреннем хранилище React Hook Form. Изменения не требуют синхронизации каждого символа с React `useState`.

Это позволяет уменьшить количество рендеров, особенно в больших формах.

Контролируемые поля

При использовании `Controller` или `useController()` значение поля передаётся компоненту через `value`, а изменения поступают через `onChange`.

React Hook Form синхронизирует это значение со своим внутренним хранилищем и обновляет компонент через подписку.

Такой подход необходим для UI-компонентов, самостоятельно управляющих отображаемым значением.

Общий механизм

Независимо от способа регистрации оба типа полей используют общую систему:

- Хранение и получение значений через `getValues()` и `setValue()`.
- Отслеживание изменений через `dirtyFields` и `isDirty`.
- Валидацию через встроенные правила или `resolver`.
- Обработку ошибок через `formState.errors`.
- Подписки на изменения значений и состояния.

Библиотека не заставляет всю форму перерисовываться при каждом изменении значения. Обновления React определяются подписками компонентов на конкретные данные.

Ключевая идея: `register()` оптимален для нативных полей, а `Controller` позволяет подключать контролируемые компоненты к той же системе управления формой.

# Как организовать обработку ошибок в многошаговой форме?

В многошаговой форме необходимо проверять данные на уровне текущего шага и всей формы, сохраняя ошибки и значения между переходами.

Основные принципы:

1. При переходе вперёд проверять поля текущего шага.
2. Не разрешать переход, если обязательные поля текущего шага заполнены неверно.
3. Сохранять введённые значения при переключении шагов.
4. Перед окончательной отправкой проверять все данные, включая зависимости между шагами.
5. Ошибки сервера сопоставлять с соответствующими полями и шагами.

Для проверки конкретного шага используется `trigger()`:

```
const steps = [
  ["firstName", "lastName"],
  ["email", "phone"],
  ["address"],
] as const;

const nextStep = async () => {
  const isValid = await trigger([...steps[step]], {
    shouldFocus: true,
  });

  if (isValid) {
    setStep((prev) => prev + 1);
  }
};
```

`trigger()` возвращает `Promise<boolean>`, поэтому необходимо использовать `await`.

Важный нюанс: при использовании общей схемы Zod нужно учитывать валидацию полей других шагов. Для сложных форм можно создавать отдельные схемы каждого шага и общую схему для финальной проверки.

Если сервер возвращает ошибку поля из предыдущего шага, необходимо:

1. Определить, к какому шагу относится поле.
2. Установить ошибку через `setError()`.
3. Переключить форму на соответствующий шаг.
4. После монтирования нужного поля установить на него фокус через `setFocus()`.

Ошибки, относящиеся ко всей форме, например невозможность сохранить заявку, отображаются отдельно через `root`.

Ключевой принцип: каждый шаг проверяет свои данные для разрешения перехода, а финальная проверка гарантирует согласованность всей формы.
