# Что такое XSS и какие её основные разновидности?

XSS (Cross-Site Scripting) - уязвимость, позволяющая злоумышленнику внедрить и выполнить JavaScript в контексте доверенного веб-сайта.

Вредоносный код выполняется с правами origin приложения и может читать доступные JavaScript данные, похищать токены, изменять DOM и отправлять запросы от имени пользователя.

Основные разновидности:

- Reflected XSS - вредоносный ввод из запроса попадает в ответ сервера без безопасной обработки.
- Stored XSS - вредоносный ввод сохраняется на сервере и выполняется при последующем отображении.
- DOM-based XSS - уязвимость возникает при небезопасной обработке данных JavaScript-кодом непосредственно в браузере.

Основная защита - контекстно-зависимое экранирование, безопасные DOM API, sanitization для пользовательского HTML и CSP как дополнительный уровень защиты.

# Чем reflected XSS отличается от stored и DOM-based XSS?

Reflected XSS возникает, когда сервер возвращает пользовательский ввод непосредственно в HTML-ответе без безопасного экранирования. Например, параметр поискового запроса отображается на странице как HTML. Обычно атака требует перехода по специально подготовленной ссылке.

Stored XSS возникает, когда вредоносный ввод сохраняется в базе данных, комментариях или профиле пользователя. При отображении этих данных код выполняется у посетителей страницы. Атака может затрагивать множество пользователей без дополнительных действий с их стороны.

DOM-based XSS возникает на стороне браузера, когда JavaScript получает недоверенные данные и передаёт их в опасный API, например `innerHTML` или `eval()`.

Пример:

```
const params = new URLSearchParams(location.search);

document.querySelector('#result').innerHTML =
  params.get('query');
```

Если `query` содержит вредоносную HTML-разметку с обработчиком событий, браузер может выполнить JavaScript.

Принципиальное различие: reflected и stored описывают способ поступления и хранения вредоносных данных, а DOM-based - место возникновения уязвимости. Поэтому DOM-based XSS может одновременно быть reflected или stored.

# Чем экранирование отличается от sanitization?

Экранирование (escaping/output encoding) преобразует специальные символы так, чтобы браузер интерпретировал их как данные, а не как разметку или код.

Например, при выводе в HTML:

```
<script> -> &lt;script&gt;
```

HTML-тег отображается как текст и не выполняется.

Экранирование зависит от контекста: HTML, HTML-атрибуты, JavaScript, CSS и URL требуют разных правил. Универсального экранирования для всех контекстов не существует.

Sanitization очищает недоверенное содержимое, удаляя или ограничивая потенциально опасные элементы, атрибуты и значения, сохраняя разрешённую разметку.

Например, HTML sanitizer может сохранить `<b>`, но удалить `onclick` и ссылки с опасными протоколами.

Разница:

- Экранирование - позволяет безопасно отобразить данные как текст.
- Sanitization - позволяет безопасно отобразить ограниченный набор HTML-разметки.

Если HTML не требуется, предпочтительнее `textContent` или стандартное экранирование фреймворка. Если требуется пользовательская разметка, используют проверенный sanitizer, например `DOMPurify`.

# Какие ограничения есть у HTML sanitizer?

HTML sanitizer снижает риск XSS, но не гарантирует безопасность при любом использовании результата.

Основные ограничения:

- Зависимость от контекста. HTML, безопасный для вставки в DOM, необязательно безопасен внутри JavaScript, CSS или URL.
- Ошибки конфигурации. Разрешённые опасные атрибуты, элементы или URL-схемы могут привести к XSS.
- Обходы через особенности парсинга. Браузеры по-разному обрабатывают сложную HTML, SVG и MathML-разметку; у sanitizer тоже могут быть уязвимости.
- Изменение после очистки. Конкатенация HTML, повторный парсинг или модификация сторонней библиотекой могут нарушить безопасность.
- Другие угрозы. Sanitizer не предотвращает автоматически небезопасные переходы, загрузку внешних ресурсов, утечки данных и все виды UI-атак.

Sanitizer необходимо регулярно обновлять, использовать с минимальным набором разрешённых элементов и не считать заменой контекстному экранированию.

# Что такое Trusted Types?

Trusted Types - браузерный механизм защиты от DOM-based XSS, ограничивающий передачу обычных строк в потенциально опасные DOM API.

Вместо произвольных строк такие API могут требовать специальные типы:

- `TrustedHTML` - для HTML-разметки.
- `TrustedScript` - для JavaScript-кода.
- `TrustedScriptURL` - для URL загружаемых скриптов.

Значения создаются через заранее определённые политики `trustedTypes.createPolicy()`, которые должны выполнять необходимую проверку или очистку.

Пример включения через CSP:

```
Content-Security-Policy: require-trusted-types-for 'script'
```

После включения браузер блокирует передачу обычной строки в защищённые API, например:

```
element.innerHTML = userInput;
```

Если значение не является допустимым Trusted Type, операция обычно завершается `TypeError`.

Директива `trusted-types` дополнительно ограничивает имена политик, которые приложение вправе создавать.

Важно: Trusted Types самостоятельно не очищает данные. Безопасность зависит от реализации политик. По состоянию на 2026 год механизм поддерживается современными браузерами, но для старых версий необходима проверка совместимости.&#x20;

# Как работает Content Security Policy?

Content Security Policy (CSP) - браузерный механизм безопасности, определяющий, какие ресурсы разрешено загружать и выполнять на странице.

Политика обычно передаётся сервером через HTTP-заголовок:

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  object-src 'none';
  base-uri 'self';
```

Основные директивы:

- `default-src` - политика по умолчанию для поддерживающих её типов ресурсов.
- `script-src` - источники и условия выполнения JavaScript.
- `style-src` - источники CSS.
- `img-src` - источники изображений.
- `connect-src` - адреса для `fetch`, XHR, WebSocket и других соединений.
- `frame-ancestors` - кому разрешено встраивать страницу во фрейм.
- `object-src` - разрешённые источники для `<object>` и `<embed>`.

При загрузке ресурса или выполнении кода браузер проверяет соответствующую директиву и блокирует операцию при нарушении политики.

Для защиты от XSS предпочтительна strict CSP с использованием nonce или hash, а не только списков доверенных доменов. Необоснованное использование `'unsafe-inline'` и `'unsafe-eval'` значительно ослабляет защиту.

CSP также поддерживает режим `Content-Security-Policy-Report-Only`, позволяющий обнаруживать нарушения без блокировки.

CSP - дополнительная защита, а не замена безопасной обработке пользовательского ввода.

# Зачем CSP nonce и hash?

Nonce и hash позволяют CSP разрешать выполнение конкретных скриптов без глобального разрешения inline JavaScript через `'unsafe-inline'`.

Nonce - случайное криптографически стойкое значение, которое сервер генерирует для каждого HTML-ответа.

```
Content-Security-Policy: script-src 'nonce-abc123'
```

```
<script nonce="abc123">
  initApp();
</script>
```

Браузер выполняет скрипт, если его nonce совпадает с разрешённым значением. В реальном приложении nonce должен быть непредсказуемым и новым для каждого ответа.

Hash - криптографический хеш содержимого скрипта:

```
Content-Security-Policy:
  script-src 'sha256-BASE64_HASH'
```

Браузер вычисляет хеш скрипта и сравнивает его с указанным в политике. При изменении содержимого хеш перестаёт совпадать.

Различия:

- Nonce удобен для динамически генерируемых HTML-страниц.
- Hash удобен для статических скриптов, содержимое которых известно заранее.

Оба механизма ограничивают выполнение внедрённых скриптов, но не защищают от вредоносного кода внутри уже доверенного скрипта.

# Что такое CSRF и какие условия позволяют атаке сработать?

CSRF (Cross-Site Request Forgery) - атака, при которой злоумышленник заставляет браузер авторизованного пользователя выполнить нежелательное действие на другом сайте.

Например, пользователь авторизован в банковском приложении. Вредоносная страница инициирует запрос на перевод денег, а браузер автоматически добавляет подходящие для этого запроса cookies банковского приложения.

Для классической CSRF-атаки обычно необходимы следующие условия:

1. Пользователь имеет действующую сессию.
2. Браузер автоматически отправляет данные авторизации, например session cookie, в контексте атакующего запроса.
3. Атакующий может инициировать запрос с нужными параметрами.
4. Сервер не проверяет надлежащим образом происхождение или подлинность запроса.

Чтение ответа злоумышленнику необязательно - достаточно выполнения операции сервером. Поэтому Same-Origin Policy и CORS сами по себе не предотвращают CSRF.

Основные средства защиты:

- CSRF-токены, которые сервер проверяет при изменяющих состояние запросах.
- `SameSite=Lax` или `Strict` для cookies.
- Проверка заголовков `Origin`, `Referer` и `Sec-Fetch-Site`.
- Запрет изменения состояния через `GET`.

Важно учитывать, что `SameSite` ограничивает cross-site, а не все cross-origin запросы. Поэтому запросы между поддоменами одного сайта требуют отдельного внимания.

# Почему CORS сам по себе не является механизмом аутентификации?

CORS (Cross-Origin Resource Sharing) управляет тем, разрешено ли JavaScript-коду одного origin читать ответы другого origin через браузер.

Он не устанавливает личность пользователя и не определяет его права доступа.

Например:

```
Access-Control-Allow-Origin: https://app.example.com
```

Этот заголовок сообщает браузеру, что скрипты указанного origin могут получить доступ к ответу при выполнении остальных условий CORS.

Однако:

- HTTP-клиенты вроде `curl` не обязаны соблюдать CORS.
- Некоторые cross-origin запросы отправляются даже без разрешения CORS.
- Разрешённый origin не означает, что пользователь авторизован.
- Наличие или подделка заголовка `Origin` вне браузера не подтверждает подлинность клиента.

Поэтому сервер должен самостоятельно проверять аутентификацию и авторизацию каждого защищённого запроса.

# Что такое preflight request и когда он появляется?

Preflight request - предварительный HTTP-запрос методом `OPTIONS`, с помощью которого браузер проверяет, разрешает ли сервер определённый cross-origin запрос.

Он возникает, когда запрос не удовлетворяет условиям CORS-safelisted request, например:

- Используется `PUT`, `PATCH` или `DELETE`.
- Передаётся заголовок `Authorization` или другой несистемный заголовок, не входящий в safelist.
- Отправляется `POST` с `Content-Type: application/json`.

Пример:

```
OPTIONS /api/users
Origin: https://app.example.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: authorization
```

Ответ сервера:

```
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: DELETE
Access-Control-Allow-Headers: authorization
```

Если проверка успешна, браузер отправляет основной запрос. При отрицательном результате основной запрос не отправляется.

Результаты preflight могут кешироваться браузером на время, ограниченное `Access-Control-Max-Age` и внутренними лимитами браузера.

Важно: preflight - это проверка CORS-разрешений, а не аутентификация. Некоторые обычные cross-origin запросы отправляются без него.

# Почему `Access-Control-Allow-Origin: *` нельзя совмещать с credentials?

Значение `*` разрешает чтение ресурса любому origin в запросах без credentials, но не может использоваться для разрешения credentialed CORS-запросов.

Credentials могут включать cookies, HTTP-аутентификацию и клиентские TLS-сертификаты.

Браузер не предоставит JavaScript доступ к ответу credentialed-запроса, если сервер вернёт:

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

Причина - запрет чрезмерно широкого доступа к потенциально персонализированным данным.

Для credentialed CORS-запросов сервер должен указать конкретный разрешённый origin:

```
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Vary: Origin
```

На клиенте:

```
fetch('https://api.example.com/profile', {
  credentials: 'include',
});
```

`Vary: Origin` важен, когда сервер динамически выбирает разрешённый origin, чтобы кеши корректно разделяли варианты ответа.

При этом CORS не гарантирует, что запрос не был отправлен - он ограничивает доступ браузерного JavaScript к ответу.&#x20;

# Что такое clickjacking и как его предотвратить?

Clickjacking - атака, при которой злоумышленник обманом заставляет пользователя взаимодействовать с элементами другого сайта, обычно скрытыми или визуально замаскированными.

Типичный сценарий:

1. Злоумышленник встраивает доверенный сайт через `<iframe>`.
2. Делает iframe прозрачным или накладывает на поддельный интерфейс.
3. Пользователь нажимает на видимую кнопку, но фактически взаимодействует с элементом встроенного сайта.

Это может привести к подтверждению операций, изменению настроек или выполнению других нежелательных действий.

Основная защита - запрет или ограничение встраивания страницы:

```
Content-Security-Policy: frame-ancestors 'none'
```

Для совместимости со старыми браузерами:

```
X-Frame-Options: DENY
```

Если встраивание необходимо, следует разрешать только доверенные origin.

# Как работают `frame-ancestors` и X-Frame-Options?

Оба механизма определяют, каким страницам разрешено встраивать защищённый документ в iframe и другие поддерживаемые контейнеры.

`frame-ancestors` - директива CSP, позволяющая задать список разрешённых источников:

```
Content-Security-Policy:
  frame-ancestors 'self' https://partner.example.com
```

Она разрешает встраивание с того же origin и указанного внешнего origin.

Дополнительные варианты:

- `'none'` - полностью запретить встраивание.
- `'self'` - разрешить встраивание только с того же origin.

Браузер проверяет всю цепочку родительских документов. Если хотя бы один из них не разрешён, встраивание блокируется.

`X-Frame-Options` - более старый HTTP-заголовок:

```
X-Frame-Options: DENY
X-Frame-Options: SAMEORIGIN
```

Он поддерживает только ограниченные варианты политики. Устаревшее значение `ALLOW-FROM` не поддерживается современными браузерами.

Главные различия:

- `frame-ancestors` поддерживает несколько разрешённых origin.
- `X-Frame-Options` не позволяет сформировать полноценный список разрешённых сайтов.
- `frame-ancestors` должен передаваться через HTTP-заголовок, а не через `<meta>`.
- При наличии действующей политики `frame-ancestors` современные браузеры отдают ей приоритет перед `X-Frame-Options`.

Не следует путать `frame-ancestors` с `frame-src`: первая ограничивает, кто может встроить текущую страницу, вторая - какие фреймы может загружать сама страница.

# Чем Same-Origin Policy отличается от CORS?

Same-Origin Policy (SOP) - базовая политика безопасности браузера, ограничивающая взаимодействие документов и скриптов между разными origin.

Origin определяется сочетанием:

```
scheme + host + port
```

Например:

```
https://example.com
https://example.com:8080
```

Это разные origin из-за отличающихся портов.

SOP ограничивает чтение cross-origin ответов и доступ к DOM чужих документов, но допускает некоторые cross-origin запросы и встраивание ресурсов.

CORS - механизм, позволяющий серверу выборочно ослаблять ограничения SOP для чтения HTTP-ответов браузерным JavaScript.

Пример:

```
Access-Control-Allow-Origin: https://app.example.com
```

Сервер явно разрешает указанному origin читать ответ при соблюдении остальных условий CORS.

Главное различие:

- SOP устанавливает ограничения доступа между origin.
- CORS позволяет серверу управляемо разрешать определённый cross-origin доступ.

CORS не отменяет SOP полностью. Например, разрешение CORS на API не предоставляет доступ к DOM произвольного cross-origin iframe.

# Что такое mixed content и почему браузер может его блокировать?

Mixed content возникает, когда HTTPS-страница загружает ресурсы по незащищённому HTTP.

Например:

```
<script src="http://example.com/app.js"></script>
```

Проблема в том, что HTTP-трафик может быть перехвачен или изменён злоумышленником, несмотря на защищённое соединение основной страницы.

Современные браузеры обрабатывают такие ресурсы по-разному:

- Блокируемый контент - скрипты, стили, `fetch` и другие опасные ресурсы обычно блокируются.
- Автоматически обновляемый контент - изображения, аудио и видео обычно переводятся с HTTP на HTTPS. Если безопасная загрузка невозможна, ресурс не загружается.

Есть дополнительные ограничения, например для ресурсов, загружаемых по IP-адресам.

Для предотвращения mixed content необходимо загружать ресурсы по HTTPS. CSP-директива `upgrade-insecure-requests` может автоматически заменять небезопасные URL на HTTPS, но не гарантирует доступность ресурса по этому протоколу.&#x20;

# Что такое prototype pollution и в каких случаях оно опасно?

Prototype pollution - уязвимость JavaScript, при которой злоумышленник изменяет прототип объектов через неконтролируемые ключи и операции записи.

Частые источники - рекурсивное объединение объектов, обработка JSON и функции установки значений по строковому пути.

Опасные ключи:

```
'__proto__'
'constructor'
'prototype'
```

Например, небезопасная функция глубокого объединения может позволить записать свойство в `Object.prototype`.

После этого другие объекты могут наследовать внедрённое значение:

```
const user = {};

console.log(user.isAdmin); // true
```

Такое поведение возможно, если атакующий ранее загрязнил соответствующий прототип.

Опасность возникает, когда приложение использует унаследованное свойство в чувствительной логике. Последствия могут включать обход проверок доступа, XSS, изменение конфигурации и, в отдельных серверных сценариях, выполнение произвольного кода.

Основные способы защиты:

- Валидировать структуру и допустимые ключи входных объектов.
- Не передавать недоверенные данные в небезопасные deep merge и path setter.
- Использовать `Object.hasOwn()` вместо неявного доверия унаследованным свойствам.
- Использовать `Map` или `Object.create(null)` для словарей с произвольными ключами.
- Обновлять зависимости, содержащие уязвимые операции.

# Как уменьшить риски уязвимых npm-зависимостей?

Риск связан как с известными уязвимостями пакетов, так и с возможностью внедрения вредоносного кода через зависимости.

Основные меры:

- Минимизировать зависимости - не устанавливать ненужные библиотеки и регулярно удалять неиспользуемые.
- Использовать lockfile - фиксировать конкретные версии и целостность прямых и транзитивных зависимостей.
- Использовать `npm ci` в CI/CD - устанавливать зависимости строго по lockfile с проверкой согласованности с `package.json`.
- Проверять уязвимости - применять `npm audit`, Dependabot, Renovate и другие SCA-инструменты.
- Контролировать обновления - анализировать изменения, особенно при смене владельца пакета или появлении неожиданных install-скриптов.
- Ограничивать lifecycle scripts - применять `--ignore-scripts` там, где это совместимо с проектом.
- Защищать CI/CD - выдавать минимальные права, не раскрывать секреты ненадёжным сборочным процессам и защищать публикацию пакетов.

Важно понимать, что `npm audit` выявляет преимущественно известные уязвимости. Он не гарантирует обнаружение нового вредоносного пакета.

Lockfile обеспечивает воспроизводимость установленных версий, но не гарантирует безопасность содержащегося в них кода.

# Что такое supply-chain attack в frontend-проекте?

Supply-chain attack - атака через компоненты, инструменты или инфраструктуру, от которых зависит разработка, сборка и доставка приложения.

В frontend-проектах распространённые сценарии:

- Компрометация npm-пакета и публикация вредоносной версии.
- Typosquatting - публикация пакета с названием, похожим на популярную библиотеку.
- Dependency confusion - подмена внутренней зависимости внешним пакетом с совпадающим именем.
- Вредоносные `preinstall` или `postinstall` скрипты.
- Компрометация CI/CD, сборочных инструментов или CDN.

Атака может происходить на разных этапах.

Во время установки или сборки вредоносная зависимость способна читать переменные окружения, похищать секреты CI/CD и изменять итоговый bundle.

Во время выполнения в браузере внедрённый JavaScript может похищать доступные пользователю данные и выполнять действия в контексте приложения.

Главная особенность - злоумышленник атакует не обязательно исходный код приложения, а доверенную часть цепочки поставки.

# Зачем ограничивать доступ к sourcemaps и клиентским секретам?

Sourcemaps сопоставляют минифицированный JavaScript с исходным кодом и используются для отладки.

Публичные sourcemaps могут раскрывать:

- Структуру исходного проекта.
- Имена внутренних модулей и функций.
- Комментарии разработчиков.
- Недокументированные API и внутреннюю логику.
- Фрагменты исходного кода, отсутствующие в обычном bundle.

В production sourcemaps можно загружать в приватный сервис мониторинга ошибок, не публикуя их для всех пользователей.

Однако сокрытие sourcemaps не является полноценной мерой безопасности, поскольку клиентский JavaScript всё равно доступен для анализа.

Отдельная проблема - клиентские секреты.

Любое значение, встроенное в frontend bundle, потенциально доступно пользователю независимо от минификации, обфускации и наличия sourcemaps.

Поэтому:

- Секретные API-ключи, пароли и приватные токены должны оставаться на сервере.
- Публичные клиентские ключи следует ограничивать по назначению, разрешённым API и доступным квотам.
- Переменные окружения, передаваемые сборщиком в клиентский код, нельзя считать секретными.

Например, `VITE_SECRET_KEY` в Vite не становится секретом только потому, что определён через `.env`.

# Какие риски у хранения токенов в localStorage, memory и cookie?

У каждого способа хранения токенов свои ограничения.

`localStorage`

- Сохраняется после перезагрузки страницы и закрытия браузера.
- Доступен JavaScript-коду соответствующего origin.
- При XSS злоумышленник может прочитать и похитить токен.
- Автоматически не отправляется с HTTP-запросами, поэтому классический CSRF для токена, явно передаваемого через `Authorization`, обычно не применяется.

Memory (память приложения)

- Токен хранится в переменной или состоянии JavaScript.
- Не сохраняется автоматически между полноценными перезагрузками страницы.
- Уменьшает время доступности токена и риск его извлечения из постоянного хранилища.
- Не защищает полностью от XSS: вредоносный код может перехватывать токен или выполнять запросы от имени пользователя.

Cookie

- Может автоматически отправляться браузером в подходящих запросах.
- Атрибут `HttpOnly` запрещает чтение cookie через JavaScript.
- `Secure` ограничивает передачу защищёнными соединениями.
- `SameSite` помогает ограничивать CSRF.

Недостаток cookie-аутентификации - необходимость CSRF-защиты. Кроме того, `HttpOnly` препятствует чтению токена при XSS, но не мешает вредоносному скрипту выполнять авторизованные запросы через браузер.

На практике для веб-приложений часто предпочтительна серверная сессия через `HttpOnly`, `Secure`, `SameSite` cookie либо BFF-архитектура, в которой токены OAuth не передаются браузерному JavaScript.

# Как безопасно обрабатывать OAuth callback URL?

OAuth callback - URL, на который authorization server перенаправляет пользователя после авторизации.

При обработке callback важно предотвратить подмену авторизационного ответа, перехват кода и небезопасные перенаправления.

Основные требования:

1. Использовать Authorization Code Flow с PKCE. Проверка `code_verifier` связывает обмен кода с первоначальным запросом авторизации.
2. Проверять `state` или применять эквивалентную подтверждённую защиту от CSRF. Значение должно быть связано с начатой авторизацией и не допускать повторного использования.
3. Использовать точное сопоставление `redirect_uri` с зарегистрированными значениями на authorization server.
4. Не допускать open redirect. Параметры вроде `returnUrl` должны проверяться по разрешённым адресам или безопасным относительным маршрутам.
5. Проверять issuer при работе с несколькими OAuth-провайдерами, чтобы предотвратить mix-up attack.
6. Удалять временные параметры из адресной строки после обработки callback, например через `history.replaceState()`.
7. Не передавать токены через URL, если протокол позволяет этого избежать. URL может попадать в историю браузера, логи и сторонние системы.

В OpenID Connect дополнительно проверяют `nonce` в ID Token, если он используется в авторизационном запросе.

Важно: OAuth callback не должен доверять значениям из `location.search` без проверки. Авторизационный код необходимо обменивать на токены только в контексте корректно начатой авторизации.

Эти требования согласуются с актуальными рекомендациями OAuth 2.0 Security Best Current Practice - RFC 9700.&#x20;

# Чем SRI (`integrity`) полезен при загрузке внешних скриптов?

SRI (Subresource Integrity) - механизм проверки целостности внешних ресурсов, загружаемых браузером.

Он позволяет убедиться, что содержимое скрипта или stylesheet соответствует заранее известному криптографическому хешу.

Пример:

```
<script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-BASE64_HASH"
  crossorigin="anonymous"
></script>
```

Механизм работы:

1. Браузер загружает ресурс.
2. Вычисляет криптографический хеш полученного содержимого.
3. Сравнивает его со значением в `integrity`.
4. При несовпадении блокирует использование ресурса.

Это снижает риск выполнения изменённого или подменённого скрипта в случае компрометации CDN или другого внешнего источника.

Для cross-origin ресурсов SRI требует корректной настройки CORS, поэтому обычно используется `crossorigin="anonymous"`.

Ограничения: SRI не проверяет безопасность самого кода, не защищает от компрометации основного HTML-документа и требует обновления хеша при изменении файла.&#x20;

# Как защищать данные от утечки через URL, логи и analytics?

Утечки возникают, когда чувствительные данные попадают в системы, где их могут сохранять, передавать или просматривать без достаточного контроля.

URL

Query-параметры могут сохраняться в истории браузера, серверных логах, системах аналитики и передаваться через `Referer`.

Поэтому не следует помещать в URL пароли, access tokens, refresh tokens и другие секреты.

Если временный код авторизации необходимо принять через URL, его следует оперативно обработать и удалить из адресной строки.

Для ограничения передачи адресов внешним ресурсам используется `Referrer-Policy`, например:

```
Referrer-Policy: strict-origin-when-cross-origin
```

Для более строгого ограничения:

```
Referrer-Policy: no-referrer
```

Логи

Необходимо:

- Исключать токены, пароли, cookies и чувствительные персональные данные.
- Маскировать или удалять секретные значения из заголовков, параметров запросов и ошибок.
- Ограничивать доступ к логам.
- Настраивать сроки хранения и автоматическое удаление.

Analytics

Данные аналитики должны передаваться по принципу минимальной необходимости.

Опасно автоматически отправлять полный URL, содержимое форм, пользовательские идентификаторы и произвольные объекты приложения.

Предпочтительнее использовать allowlist разрешённых событий и параметров, исключать секреты и чувствительные данные до отправки.

Ключевой принцип - минимизация данных на источнике. Лучше вообще не передавать чувствительную информацию в URL, логи и аналитику, чем пытаться удалить её после сохранения.
