# Чем unit tests отличаются от integration tests и e2e tests?

Различаются масштабом проверяемой системы, степенью изоляции и стоимостью выполнения.

- Unit tests (модульные) - проверяют отдельную функцию, класс или небольшой модуль. Внешние зависимости при необходимости заменяются тестовыми двойниками. Быстрые, помогают точно локализовать ошибки.
- Integration tests (интеграционные) - проверяют взаимодействие нескольких частей системы. Например, React-компонента, состояния и API-клиента. Позволяют обнаруживать ошибки на границах модулей.
- E2E tests (End-to-End) - проверяют пользовательские сценарии через реальный браузер и развернутое приложение. Например, авторизация, оформление заказа, выход из аккаунта. Дают уверенность в работе системы целиком, но обычно медленнее и сложнее в обслуживании.

Границы условны: интеграционный тест может использовать настоящий API или его имитацию, а E2E - мокировать отдельные внешние сервисы.

# Что такое testing pyramid и testing trophy?

Testing Pyramid (пирамида тестирования) - модель распределения тестов по уровням:

- Основание - много быстрых unit-тестов.
- Середина - меньше integration-тестов.
- Вершина - немного дорогих E2E-тестов.

Идея - получать быструю обратную связь, сохраняя проверку взаимодействия компонентов и критических пользовательских сценариев.

Testing Trophy (трофей тестирования) - альтернативная модель, популярная во frontend-разработке. Она выделяет четыре уровня:

- Static analysis - TypeScript, ESLint и другие статические проверки.
- Unit - тестирование изолированной логики.
- Integration - основной акцент на взаимодействии компонентов.
- E2E - проверка ключевых сценариев приложения.

Главное различие - Testing Trophy делает акцент на интеграционных тестах, поскольку многие frontend-ошибки возникают при взаимодействии компонентов, состояния и API.

Обе модели - ориентиры, а не обязательные пропорции.

# Какие свойства должны быть у хорошего теста?

Хороший тест должен обладать следующими свойствами:

- Детерминированность - одинаковые входные данные и условия приводят к одинаковому результату.
- Изолированность - результат не зависит от порядка выполнения других тестов.
- Быстрота - тест обеспечивает достаточно быструю обратную связь для своего уровня.
- Понятность - по названию, подготовке и проверкам ясно, какое поведение тестируется.
- Устойчивость - не ломается при рефакторинге, который сохраняет внешнее поведение.
- Чувствительность к ошибкам - падает, когда нарушается проверяемое требование.
- Воспроизводимость - проблему можно повторить локально и диагностировать.

Главный критерий - тест должен обнаруживать реальные регрессии, не создавая излишних затрат на поддержку.

# Что такое AAA (Arrange, Act, Assert)?

AAA - шаблон организации теста из трёх этапов:

1. Arrange - подготовка исходных данных, зависимостей и окружения.
2. Act - выполнение тестируемого действия.
3. Assert - проверка ожидаемого результата.

Пример:

```
test('applies discount', () => {
  // Arrange
  const price = 100;
  const discount = 20;

  // Act
  const result = applyDiscount(price, discount);

  // Assert
  expect(result).toBe(80);
});
```

Такое разделение делает тест понятнее и помогает отличать подготовку условий от проверяемого поведения.

# Чем mock отличается от stub, spy и fake?

Все четыре понятия относятся к test doubles - заменителям реальных зависимостей.

- Stub - возвращает заранее определённые значения. Например, API-клиент всегда возвращает тестового пользователя.
- Spy - фиксирует информацию о вызовах функции: аргументы, количество вызовов, порядок. Может сохранять реальную реализацию.
- Mock - заменитель с ожиданиями относительно взаимодействий: какие методы должны вызываться, с какими аргументами и сколько раз.
- Fake - упрощённая, но работающая реализация зависимости. Например, хранилище в памяти вместо реальной базы данных.

В Jest и Vitest термин `mock` часто используется шире. Например, `jest.fn()` или `vi.fn()` могут одновременно выполнять роли stub и spy.

Разница в назначении: stub управляет ответами, spy наблюдает за вызовами, mock проверяет взаимодействия, fake воспроизводит упрощённое поведение.

# Что такое test double?

Test double - объект или функция, заменяющие реальную зависимость при тестировании.

Используется для изоляции тестируемого кода, управления ответами зависимостей и воспроизведения сложных ситуаций без обращения к реальным внешним системам.

Основные разновидности:

- Dummy - объект-заглушка, который передаётся, но фактически не используется.
- Stub - возвращает подготовленные результаты.
- Spy - записывает информацию о вызовах.
- Mock - позволяет задавать и проверять ожидаемые взаимодействия.
- Fake - предоставляет упрощённую рабочую реализацию.

Например, вместо реального платёжного сервиса можно использовать test double, который имитирует успешную или неуспешную оплату.

Недостаток чрезмерного использования test doubles - тест может проходить, хотя взаимодействие с настоящей зависимостью работает неправильно.

# Как отличить тестирование реализации от тестирования поведения?

Тестирование реализации проверяет внутреннее устройство кода: конкретные методы, приватное состояние, структуру компонентов или детали вызовов.

Тестирование поведения проверяет наблюдаемый результат с точки зрения пользователя или внешнего контракта.

Например, для React-компонента со счётчиком:

- Проверка реализации - убедиться, что вызвался `setState` или конкретный обработчик.
- Проверка поведения - нажать кнопку и убедиться, что отображаемое значение увеличилось.

Главный критерий: если внутреннюю реализацию можно изменить без изменения функциональности, тест не должен ломаться.

Исключение - ситуации, когда взаимодействие само является частью контракта, например обязательный вызов API, отправка события или предотвращение повторного запроса.&#x20;

# Какие случаи стоит проверять через property-based testing?

Property-based testing проверяет общие свойства алгоритма на множестве автоматически сгенерированных входных данных вместо нескольких заранее выбранных примеров.

Особенно полезно, когда существуют математические или логические инварианты:

- Сортировка - результат отсортирован и содержит те же элементы.
- Сериализация - `decode(encode(value))` восстанавливает исходное значение для поддерживаемых данных.
- Обратимые операции - применение операции и обратной к ней восстанавливает исходное состояние.
- Валидация - результат удовлетворяет заданным ограничениям.
- Финансовые вычисления - соблюдаются правила округления и сохранения итоговых сумм.

Например, для сортировки можно генерировать массивы разных размеров, с отрицательными числами, дубликатами и экстремальными значениями.

Инструмент `fast-check` позволяет генерировать данные и минимизировать ошибочный пример через shrinking.

Подход особенно эффективен для чистых функций, парсеров, преобразований данных и сложной бизнес-логики.

# Что такое snapshot testing и когда оно создаёт ложную уверенность?

Snapshot testing - сравнение текущего результата работы кода с ранее сохранённым эталоном.

Например, Jest или Vitest может сохранить структуру отрендеренного компонента и сравнивать её при последующих запусках.

Преимущества - быстрое обнаружение непреднамеренных изменений структуры или сериализованного результата.

Ложная уверенность возникает, когда:

- Snapshot проверяет структуру, но не корректность поведения.
- Большие snapshots трудно анализировать.
- Разработчики автоматически обновляют эталоны без проверки изменений.
- Тест проходит, хотя в интерфейсе есть логическая ошибка.
- Snapshot содержит нестабильные данные: даты, случайные идентификаторы, динамические значения.

Snapshot фиксирует изменения, но не определяет, являются ли они ошибками.

Поэтому snapshots полезны для небольших стабильных структур, но не заменяют поведенческие тесты.

# Как проверять пограничные значения и ошибочные сценарии?

Используют Boundary Value Analysis - проверку значений на границах допустимого диапазона и рядом с ними.

Например, если допустимая длина пароля от 8 до 64 символов, стоит проверить:

- 7 символов - ошибка.
- 8 символов - минимально допустимое значение.
- 64 символа - максимально допустимое значение.
- 65 символов - ошибка.

Дополнительно проверяют ошибочные сценарии:

- Пустые и отсутствующие значения.
- Неверные типы и форматы данных.
- Неожиданные ответы API.
- Ошибки авторизации и доступа.
- Сетевые сбои и тайм-ауты.
- Повторные действия пользователя.
- Конфликтующие операции.

Для frontend важно проверять не только обнаружение ошибки, но и корректное поведение интерфейса: сообщение пользователю, сохранение введённых данных, возможность повторить действие.

# В чём различие TDD и BDD?

TDD (Test-Driven Development) - подход, при котором тесты пишутся до реализации функциональности.

Основной цикл:

1. Red - написать тест, который не проходит.
2. Green - реализовать минимальный код, чтобы тест прошёл.
3. Refactor - улучшить реализацию, сохранив прохождение тестов.

BDD (Behavior-Driven Development) - подход, ориентированный на описание ожидаемого поведения системы через понятные бизнес-сценарии.

Часто используется формат Gherkin:

```
Given пользователь авторизован
When пользователь добавляет товар в корзину
Then корзина содержит этот товар
```

TDD концентрируется на процессе разработки через тесты, BDD - на согласовании поведения системы между разработчиками, тестировщиками и бизнесом.

Они совместимы: сценарии BDD могут реализовываться через цикл TDD.

# Как оценивать пользу coverage и почему 100% не гарантирует качество?

Code coverage показывает, какая часть кода была выполнена во время тестов.

Основные метрики:

- Statement coverage - покрытие инструкций.
- Branch coverage - покрытие ветвей условий.
- Function coverage - покрытие функций.
- Line coverage - покрытие строк.

Однако выполнение кода не означает проверку его правильности.

Например:

```
test('sum', () => {
  sum(2, 3);
});
```

Тест выполняет функцию, но не проверяет результат. Даже при 100% statement coverage ошибка в вычислениях может остаться незамеченной.

Coverage полезен для обнаружения непроверенных участков и оценки изменений покрытия.

Но качество тестов определяется способностью находить ошибки, а не процентом покрытия.

Для дополнительной оценки используют mutation testing: инструмент намеренно изменяет код и проверяет, обнаруживают ли тесты эти изменения.

# Как бороться с flaky tests?

Flaky test - тест, который периодически проходит или падает без изменений тестируемого кода.

Основные причины:

- Race conditions и неправильная синхронизация.
- Фиксированные задержки вместо ожидания условий.
- Зависимость от порядка выполнения тестов.
- Общие данные и состояние между тестами.
- Нестабильные внешние сервисы.
- Различия окружений.
- Случайные значения, время и анимации.

Методы устранения:

- Использовать автоматические ожидания и проверки состояния.
- Изолировать тестовые данные и окружение.
- Контролировать время и случайность.
- Заменять неконтролируемые внешние зависимости.
- Запускать проблемные тесты многократно и анализировать артефакты падений.
- Исключать зависимости от скорости машины.

Retries не исправляют flaky tests, а лишь позволяют повторно выполнить тест. Их можно использовать как временную защиту CI, сохраняя информацию о нестабильности.

# Как организовать фикстуры и фабрики тестовых данных?

Fixtures (фикстуры) - заранее подготовленные данные, зависимости или окружение для тестирования.

Factories (фабрики) - функции, создающие тестовые объекты с возможностью переопределять отдельные поля.

Пример фабрики:

```
const createUser = (overrides = {}) => ({
  id: 'user-1',
  name: 'Alex',
  role: 'user',
  ...overrides,
});

const admin = createUser({ role: 'admin' });
```

Рекомендации:

- Использовать factories для объектов с множеством полей.
- Применять fixtures для типовых сценариев и настройки окружения.
- Создавать независимые данные для каждого теста.
- Делать значения по умолчанию валидными и предсказуемыми.
- Выделять специальные фабрики для ошибочных состояний.
- Автоматически очищать созданные ресурсы.

Не стоит создавать одну огромную фикстуру для всех тестов: она усложняет понимание зависимостей и увеличивает вероятность конфликтов.

# Как тестировать асинхронный код с таймерами?

Для тестирования таймеров используют fake timers - управляемую замену системных таймеров.

В Jest и Vitest доступны методы `useFakeTimers()`, `advanceTimersByTime()` и `useRealTimers()`.

Пример на Vitest:

```
test('calls callback after delay', () => {
  vi.useFakeTimers();

  try {
    const callback = vi.fn();

    setTimeout(callback, 1000);

    vi.advanceTimersByTime(999);
    expect(callback).not.toHaveBeenCalled();

    vi.advanceTimersByTime(1);
    expect(callback).toHaveBeenCalledOnce();
  } finally {
    vi.useRealTimers();
  }
});
```

Для асинхронных callback и Promise могут потребоваться `advanceTimersByTimeAsync()` или аналогичные методы, позволяющие выполнить связанные микрозадачи.

Важно учитывать различие между таймерами и очередью микрозадач, восстанавливать реальные таймеры после теста и избегать бесконечных циклов при рекурсивном планировании.

# Как тестировать retry, cancellation и race conditions?

Retry - повторное выполнение операции после ошибки.

Проверяют:

- Количество попыток.
- Задержки между попытками.
- Успешное завершение после временной ошибки.
- Прекращение попыток после достижения лимита.
- Отсутствие повторов для неповторяемых ошибок.

Для контроля задержек используют fake timers.

Cancellation - отмена асинхронной операции.

Например, через `AbortController` проверяют, что после отмены запрос прекращается, отмена корректно обрабатывается, а устаревшие данные не обновляют интерфейс.

Race conditions - ошибки, возникающие из-за непредсказуемого порядка завершения операций.

Например, пользователь отправил запросы A и B, причём B отправлен позже, но завершился раньше.

Тест должен управлять моментами завершения запросов и проверять, что ответ A не перезаписывает более актуальные данные B, если приложение использует стратегию `latest request wins`.

Для детерминированного управления завершением операций применяют отложенные Promise и управляемые HTTP-моки вместо случайных задержек.

# Что такое contract tests?

Contract testing - проверка совместимости взаимодействующих систем по согласованному контракту.

В frontend контракт обычно описывает HTTP API:

- Методы и маршруты.
- Форматы запросов.
- Структуры ответов.
- Обязательные и необязательные поля.
- Статусы ошибок.

Например, frontend ожидает, что `GET /users/1` вернёт объект с полями `id` и `name`. Contract test проверяет, что backend действительно предоставляет такой ответ.

Существует подход consumer-driven contract testing: потребитель формулирует свои ожидания, а поставщик проверяет их на своей стороне. Один из инструментов - Pact.

Contract tests позволяют обнаруживать несовместимые изменения API до запуска полноценного E2E.

При этом они не заменяют тестирование бизнес-логики и пользовательских сценариев.

# Как распределить тесты по стадиям CI pipeline?

Тесты распределяют по скорости, стоимости выполнения и важности обратной связи.

Типичный порядок:

1. Static checks - линтеры, проверка типов, форматирование.
2. Unit tests - быстрые проверки отдельных модулей.
3. Integration tests - взаимодействие компонентов и сервисов.
4. Build - проверка успешной сборки приложения.
5. E2E smoke tests - несколько критических сценариев на тестовом окружении.
6. Full E2E / visual regression - расширенная проверка браузерного поведения и интерфейса.

Независимые стадии можно выполнять параллельно.

При каждом pull request желательно запускать быстрые проверки и критические E2E. Более дорогие наборы можно выполнять перед релизом или по расписанию, в зависимости от рисков проекта.

Главный принцип - ошибки должны обнаруживаться как можно раньше, а дорогостоящие тесты не должны излишне замедлять разработку.

# Чем Jest отличается от Vitest?

Jest и Vitest - фреймворки для тестирования JavaScript и TypeScript, предоставляющие test runner, assertions, mocking, coverage и snapshot testing.

Jest:

- Зрелая экосистема и широкая поддержка существующих проектов.
- Использует собственную систему выполнения и преобразования модулей.
- Для TypeScript, JSX и ESM в некоторых конфигурациях требуются дополнительные настройки.
- Хорошо подходит для проектов, уже использующих Jest, включая приложения на Node.js.

Vitest:

- Построен на инфраструктуре Vite и использует его конфигурацию и преобразование модулей.
- Ориентирован на современные ESM-проекты.
- Поддерживает TypeScript и JSX с минимальной конфигурацией.
- Имеет Jest-совместимый API, хотя полной совместимости нет.
- Поддерживает запуск тестов в реальном браузере через Browser Mode.

Основное различие - архитектура выполнения и интеграция с системой сборки.

Для проектов на Vite обычно удобнее Vitest. Для существующих проектов с Jest переход не всегда оправдан.&#x20;

# Как тестировать асинхронную загрузку и ошибки API?

Нужно проверять все основные состояния асинхронной операции:

- Loading - отображается индикатор загрузки.
- Success - данные успешно загружены и отображаются.
- Empty - сервер вернул пустой результат.
- Error - отображается ошибка и предусмотренное поведение восстановления.
- Retry - повторный запрос корректно обрабатывается.

Для React обычно используют React Testing Library вместе с MSW.

render(<UserProfile />);

expect(await screen.findByText('Alex'))
  .toBeVisible();

`findByText()` асинхронно ожидает появления элемента.

Для ошибок API настраивают ответ `500`, `401` или сетевой сбой и проверяют реакцию интерфейса.

Важно не только проверить итоговое состояние, но и убедиться, что переходы между состояниями происходят правильно.

# Как MSW перехватывает HTTP-запросы?

MSW (Mock Service Worker) - библиотека для перехвата HTTP-запросов и возврата подготовленных ответов.

В браузере используется Service Worker, который перехватывает подходящие запросы, выполняемые страницами в области его действия.

Механизм:

1. Приложение отправляет обычный HTTP-запрос через `fetch`, Axios или другой клиент.
2. Service Worker перехватывает запрос.
3. MSW ищет подходящий обработчик.
4. Обработчик формирует тестовый HTTP-ответ.
5. Приложение получает его так, будто ответ пришёл от сервера.

Пример MSW v2:

```
const handlers = [
  http.get('/api/user', () => {
    return HttpResponse.json({
      id: 1,
      name: 'Alex',
    });
  }),
];
```

В Node.js Service Workers недоступны, поэтому MSW применяет другой механизм перехвата запросов через `setupServer()`.

Главное преимущество - приложение продолжает использовать настоящий HTTP-клиент, а тест управляет ответами на сетевом уровне.&#x20;

# Чем MSW удобнее мокирования `fetch` в тестах компонентов?

При прямом мокировании `fetch` заменяется конкретная функция:

```
vi.stubGlobal('fetch', vi.fn());
```

Такой тест зависит от того, каким HTTP-клиентом пользуется приложение.

MSW перехватывает запросы независимо от конкретного API-клиента, если используемый транспорт поддерживается библиотекой.

Преимущества MSW:

- Одинаковые обработчики можно использовать в тестах, Storybook и локальной разработке.
- Можно моделировать статусы HTTP, заголовки, задержки и сетевые ошибки.
- Тесты меньше зависят от внутренних деталей API-клиента.
- Не требуется подменять глобальный `fetch`.
- Удобно тестировать взаимодействие нескольких компонентов с API.

Например, замена `fetch` на Axios не потребует переписывания обработчиков MSW.

При этом MSW не гарантирует совместимость с настоящим backend - для этого нужны интеграционные или контрактные проверки.&#x20;

# Для чего применяют interaction testing в Storybook?

Interaction testing проверяет поведение компонентов при пользовательских действиях непосредственно внутри Storybook.

Используется для тестирования:

- Нажатий кнопок.
- Ввода данных в формы.
- Валидации.
- Открытия и закрытия модальных окон.
- Изменения состояния компонентов.
- Реакции на события и ответы API.

В Storybook взаимодействия описываются через функцию `play`, которая запускается после рендеринга истории.

Пример:

```
export const FilledForm = {
  play: async ({ canvas, userEvent }) => {
    await userEvent.type(
      canvas.getByRole('textbox'),
      'Alex'
    );

    await userEvent.click(
      canvas.getByRole('button', {
        name: 'Save',
      })
    );

    await expect(
      canvas.getByText('Saved')
    ).toBeVisible();
  },
};
```

Преимущество - один и тот же сценарий можно интерактивно изучать в Storybook и автоматически проверять в CI.

Это особенно полезно для компонентов UI Kit и сложных интерактивных состояний.&#x20;

# Как организовать visual regression testing?

Visual regression testing - автоматическое обнаружение визуальных изменений интерфейса путём сравнения изображений с эталоном.

Типичный процесс:

1. Зафиксировать размеры viewport, браузер и окружение.
2. Открыть компонент или страницу в известном состоянии.
3. Дождаться завершения загрузки и стабилизации интерфейса.
4. Сделать скриншот.
5. Сравнить его с эталонным изображением.
6. Проанализировать различия и подтвердить допустимые изменения.

Инструменты: Playwright, Chromatic, Percy.

Важно контролировать:

- Версии браузеров и ОС.
- Шрифты и их загрузку.
- Анимации и переходы.
- Динамические данные.
- Дату и время.
- Размеры viewport.
- Внешние изображения и ресурсы.

Для нестабильных областей можно использовать маскирование или специальные настройки сравнения.

Visual regression обнаруживает визуальные изменения, но не определяет самостоятельно, являются ли они ошибками.

# Чем Playwright отличается от Cypress?

Playwright и Cypress - инструменты автоматизации браузера для E2E и других видов тестирования.

Playwright:

- Управляет браузером через API автоматизации.
- Поддерживает Chromium, Firefox и WebKit.
- Позволяет работать с несколькими вкладками, окнами и browser contexts.
- Предоставляет встроенные механизмы изоляции тестов.
- Поддерживает JavaScript, TypeScript, Python, Java и .NET.
- Имеет встроенные инструменты трассировки и диагностики.

Cypress:

- Использует архитектуру с выполнением тестового кода в браузере и управляемой очередью команд.
- Предоставляет интерактивный test runner с удобной отладкой.
- Поддерживает E2E и component testing.
- Работает с браузерами семейств Chromium, Firefox и WebKit.
- Не имеет встроенного управления несколькими вкладками на уровне Playwright, но поддерживает соответствующие сценарии через дополнительные инструменты.
- Основной язык тестирования - JavaScript/TypeScript.

Главное различие - архитектура автоматизации и возможности управления браузерными контекстами.

Playwright обычно удобнее для сложных multi-tab и multi-user сценариев. Cypress привлекателен интерактивной отладкой и тесной интеграцией тестов с браузерным окружением.&#x20;

# Как выбрать ключевые пользовательские сценарии для E2E?

E2E стоит использовать для сценариев, нарушение которых создаёт значительный риск для продукта.

Основные критерии:

- Бизнес-критичность - авторизация, оплата, оформление заказа.
- Частота использования - основные пользовательские операции.
- Сложность интеграций - взаимодействие frontend, backend и внешних сервисов.
- Вероятность регрессии - функциональность, которая часто изменяется или ломается.
- Стоимость ошибки - потеря данных, денег или доступа.

Обычно начинают с happy path - основного успешного сценария, затем добавляют наиболее важные негативные сценарии.

Например, для интернет-магазина:

1. Пользователь открывает каталог.
2. Добавляет товар в корзину.
3. Переходит к оформлению заказа.
4. Заполняет данные.
5. Подтверждает заказ.
6. Получает подтверждение.

Не нужно переносить все возможные проверки в E2E. Детальную валидацию отдельных полей эффективнее проверять на уровне unit и integration tests.

# Как устроены browser contexts и изоляция тестов?

Browser Context - изолированная браузерная сессия внутри одного экземпляра браузера.

Каждый контекст имеет собственные:

- Cookies.
- `localStorage` и `sessionStorage`.
- IndexedDB.
- Настройки разрешений.
- Браузерное состояние сессии.

В Playwright Test по умолчанию для каждого теста создаётся отдельный context.

```
test('example', async ({ page, context }) => {
  await page.goto('/dashboard');
});
```

Это позволяет избежать зависимости одного теста от состояния другого.

В одном браузере можно создать несколько контекстов, например для администратора и обычного пользователя.

При этом browser contexts изолируют браузерное состояние, но не backend и базу данных. Если тесты изменяют общие серверные данные, нужна дополнительная изоляция.&#x20;

# Как тестировать аутентифицированного пользователя без ручного логина в каждом тесте?

В Playwright для этого используют повторное использование состояния аутентификации через `storageState`.

Процесс:

1. Отдельный setup-тест выполняет авторизацию через UI или API.
2. Состояние браузера сохраняется в файл.
3. Остальные тесты создают контексты с этим состоянием.
4. Пользователь уже авторизован при открытии приложения.

Пример сохранения:

```
await page.context().storageState({
  path: 'playwright/.auth/user.json',
});
```

Использование:

```
test.use({
  storageState: 'playwright/.auth/user.json',
});
```

`storageState` позволяет восстанавливать cookies, `localStorage` и поддерживаемое сохраняемое состояние IndexedDB. `sessionStorage` автоматически не сохраняется.

Важно учитывать истечение токенов и не добавлять файлы аутентификации в Git, поскольку они могут содержать действующие учётные данные.

Если параллельные тесты изменяют данные пользователя, лучше использовать разные тестовые аккаунты.&#x20;

# Почему в E2E предпочтительны устойчивые locators?

Locator - способ нахождения элемента интерфейса, с которым взаимодействует тест.

Неустойчивые селекторы зависят от структуры или оформления:

```
page.locator('.container > div:nth-child(2)');
```

Такие тесты ломаются при изменении DOM, даже если функциональность сохранилась.

Предпочтительнее использовать семантические locators:

```
page.getByRole('button', {
  name: 'Submit',
});

page.getByLabel('Email');

page.getByTestId('submit-button');
```

Приоритет обычно следующий:

1. Семантические селекторы (`getByRole`, `getByLabel`).
2. Видимый пользователю текст.
3. Специальные тестовые атрибуты (`data-testid`).
4. CSS-селекторы, когда они действительно необходимы.

Семантические locators лучше отражают пользовательское взаимодействие.

Playwright также автоматически ожидает выполнения необходимых условий перед действиями, что уменьшает количество проблем с синхронизацией.

# Как тестировать сетевые ошибки и медленные ответы сервера?

Для таких тестов используют контролируемый перехват HTTP-запросов через MSW, Playwright `page.route()` или Cypress `cy.intercept()`.

Основные сценарии:

- HTTP `500` - внутренняя ошибка сервера.
- HTTP `401` - необходимость повторной авторизации.
- HTTP `403` - отсутствие доступа.
- HTTP `429` - ограничение количества запросов.
- Network failure - отсутствие сетевого ответа.
- Slow response - длительное ожидание ответа.
- Timeout - превышение допустимого времени ожидания.

Пример Playwright:

```
await page.route('**/api/users', route => {
  return route.abort('failed');
});

await page.goto('/users');

await expect(
  page.getByRole('alert')
).toBeVisible();
```

Для медленных ответов используют управляемую задержку или отложенное завершение запроса.

Проверяют, что интерфейс отображает загрузку, корректно обрабатывает ошибку, не теряет пользовательские данные и позволяет повторить операцию, если это предусмотрено.

Важно различать HTTP-ошибку и сетевой сбой: например, `fetch` не отклоняет Promise только из-за статуса `500`.

# Как проверять состояние загрузки и optimistic updates?

Loading state - состояние интерфейса во время выполнения асинхронной операции.

Тест должен проверять последовательность:

1. Операция начинается.
2. Появляется индикатор загрузки или блокируется соответствующее действие.
3. Сервер возвращает ответ.
4. Индикатор исчезает и отображается результат.

Чтобы проверить промежуточное состояние, запрос нужно контролируемо задержать.

Optimistic update - обновление интерфейса до подтверждения успешного выполнения операции сервером.

Например, после нажатия Like счётчик сразу увеличивается, а запрос выполняется в фоне.

Нужно проверить:

- Изменение интерфейса происходит до ответа сервера.
- При успешном ответе новое состояние сохраняется.
- При ошибке происходит rollback или другая предусмотренная обработка.
- Повторные действия не приводят к неконсистентному состоянию.

Особенно важно тестировать конкурентные обновления, когда несколько optimistic operations выполняются одновременно.

# Как работать с несколькими вкладками и окнами?

В Playwright каждая вкладка представлена объектом `Page`, а несколько вкладок могут принадлежать одному `BrowserContext`.

Для обработки новой вкладки используют событие `page` или `popup`.

Пример:

```
const popupPromise = page.waitForEvent('popup');

await page.getByRole('link', {
  name: 'Open details',
}).click();

const popup = await popupPromise;

await expect(
  popup.getByRole('heading', {
    name: 'Details',
  })
).toBeVisible();
```

Важно начинать ожидание события до действия, которое открывает вкладку, иначе можно пропустить событие.

Для тестирования нескольких пользователей лучше создавать отдельные browser contexts, чтобы разделить их авторизацию и браузерное состояние.

В Cypress работа с несколькими вкладками менее универсальна и может требовать дополнительных инструментов.&#x20;

# Как тестировать загрузку и скачивание файлов?

Загрузка файлов (upload) проверяется через передачу тестового файла в `<input type="file">`.

В Playwright:

```
await page
  .getByLabel('Upload file')
  .setInputFiles('fixtures/document.pdf');
```

Затем проверяют:

- Отображение имени файла.
- Успешную отправку.
- Ограничения размера и формата.
- Ошибки загрузки.
- Корректность сохранённых данных, если это входит в сценарий.

Скачивание файлов (download) проверяется через событие `download`.

```
const downloadPromise = page.waitForEvent('download');

await page.getByText('Download').click();

const download = await downloadPromise;

expect(download.suggestedFilename())
  .toBe('report.pdf');
```

При необходимости файл сохраняют через `download.saveAs()` и проверяют его содержимое.

Важно тестировать не только факт скачивания, но и корректность файла, если это критично для функциональности.&#x20;

# Что делать с flaky тестом, который падает только в CI?

Сначала нужно определить различия между локальной средой и CI.

Основные причины:

- Меньше доступных CPU и памяти.
- Разные версии браузера или Node.js.
- Отличия ОС, шрифтов и системных настроек.
- Более медленные сетевые операции.
- Параллельное выполнение тестов.
- Конфликты общих данных.
- Различия временных зон и переменных окружения.

Порядок диагностики:

1. Сохранить логи, screenshots, videos и traces падения.
2. Повторить тест в CI-окружении, желательно в аналогичном контейнере.
3. Запустить тест многократно и проверить зависимость от параллельности.
4. Найти конкретное действие или ожидание, вызывающее сбой.
5. Устранить причину: неправильную синхронизацию, общие данные или различия окружения.

Не стоит сразу увеличивать все timeout. Это может скрыть проблему и замедлить CI.

Retries допустимы как временная мера, но нестабильный тест необходимо исправлять.

# Как использовать trace viewer и видеозаписи для диагностики?

Trace Viewer в Playwright позволяет исследовать выполнение теста пошагово.

Trace может содержать:

- Последовательность действий.
- DOM snapshots.
- Скриншоты.
- Сетевые запросы и ответы.
- Ошибки и логи.
- Время выполнения операций.

Пример настройки:

```
export default defineConfig({
  use: {
    trace: 'retain-on-failure',
    video: 'retain-on-failure',
    screenshot: 'only-on-failure',
  },
});
```

После падения можно открыть trace:

```
npx playwright show-trace trace.zip
```

Видео показывает визуальную последовательность действий и помогает выявлять перекрытия элементов, анимации и неожиданные переходы.

Trace Viewer полезнее для детального анализа, поскольку позволяет изучать состояние DOM, сетевые запросы и конкретные шаги теста.

При использовании `trace: 'on-first-retry'` трассировка записывается на первой повторной попытке. Если нужно исследовать первоначальное падение, подходит `retain-on-failure`.&#x20;

# Как проверять accessibility в E2E?

Accessibility testing (a11y) проверяет доступность интерфейса для пользователей с различными ограничениями.

Основные направления:

- Семантическая HTML-разметка.
- Доступные имена элементов.
- Корректное использование ARIA.
- Клавиатурная навигация.
- Управление фокусом.
- Контрастность текста.
- Доступность сообщений об ошибках.

Для автоматизации часто используют `axe-core` и `@axe-core/playwright`.

Пример:

```
const results = await new AxeBuilder({ page })
  .analyze();

expect(results.violations).toEqual([]);
```

Однако автоматические проверки обнаруживают только часть проблем.

Дополнительно необходимо проверять поведение вручную или через E2E:

- Навигацию с помощью `Tab`, `Enter`, `Space`, `Escape`.
- Попадание фокуса в модальное окно и его возвращение после закрытия.
- Доступность основных действий без мыши.
- Корректность взаимодействия со скринридерами.

Автоматические a11y-тесты не гарантируют полное соответствие WCAG. Они дополняют ручное тестирование.&#x20;

# Как параллелить тесты без конфликтов данных?

Параллельное выполнение ускоряет тестирование, но создаёт риск конфликтов при работе с общим состоянием.

Основные методы изоляции:

- Отдельные browser contexts - исключают конфликты cookies и локального состояния.
- Уникальные тестовые данные - разные пользователи, заказы и другие сущности.
- Отдельные аккаунты для workers - предотвращают одновременное изменение данных одного пользователя.
- Изоляция базы данных - отдельные схемы, базы или пространства имён, если это необходимо.
- Fixtures - создают и очищают ресурсы теста.
- Мокирование внешних зависимостей - исключает конфликты с неконтролируемыми сервисами.

В Playwright можно использовать `testInfo.parallelIndex` для привязки тестовых данных к конкретному worker.

При этом важно различать изоляцию browser context и серверного состояния: отдельные вкладки или contexts могут обращаться к одной базе данных.

Надёжный параллельный тест должен проходить независимо от порядка и одновременного выполнения других тестов.

# Что такое visual regression и как управлять эталонными скриншотами?

Visual regression - изменение внешнего вида интерфейса относительно ранее утверждённой версии.

Для обнаружения таких изменений используются baseline screenshots (эталонные скриншоты).

В Playwright:

```
await expect(page).toHaveScreenshot(
  'dashboard.png'
);
```

При последующих запусках Playwright сравнивает текущий скриншот с сохранённым эталоном.

Правила управления baseline:

- Хранить эталоны в системе контроля версий или специализированном сервисе.
- Генерировать их в стабильном окружении.
- Использовать фиксированные версии браузеров, viewport и шрифтов.
- Контролировать динамический контент.
- Просматривать визуальные различия при code review.
- Обновлять эталоны только после проверки изменений.
- При необходимости хранить отдельные эталоны для разных браузеров и размеров экрана.

Нельзя автоматически принимать все изменения скриншотов: это превращает visual regression testing в формальную проверку без реальной пользы.

Главная задача baseline - фиксировать утверждённое визуальное состояние, а не просто последнее полученное изображение.&#x20;
