# Чем ИИ-агент отличается от обычного LLM-чата и автодополнения кода?

ИИ-агент (AI Agent) - система на основе языковой модели, способная самостоятельно выполнять последовательность действий для достижения поставленной цели с помощью доступных инструментов.

Основные различия:

- Автодополнение кода - предлагает продолжение кода на основе текущего контекста. Разработчик самостоятельно принимает и интегрирует предложения.
- LLM-чат - отвечает на вопросы, объясняет код и предлагает решения. Сам по себе не выполняет действия в проекте, если не подключены соответствующие инструменты.
- ИИ-агент - анализирует задачу, исследует проект, изменяет файлы, запускает команды и тесты, проверяет результаты и при необходимости исправляет ошибки.

Главное отличие - способность выполнять многошаговые задачи с использованием инструментов и обратной связи.

При этом автономность агента ограничивается доступными инструментами, разрешениями и настройками среды. Агент не гарантирует корректность результата и требует контроля разработчика.

# Какие ИИ-инструменты для разработки вы использовали (Cursor, Codex, Claude Code, GitHub Copilot)?

Основные инструменты для AI-assisted разработки:

- Cursor - редактор кода с интегрированным ИИ. Поддерживает контекстный поиск по проекту, генерацию и редактирование кода, многофайловые изменения, выполнение терминальных команд через Agent Mode.
- OpenAI Codex - coding agent для работы с репозиторием. Может исследовать код, реализовывать функциональность, исправлять ошибки, запускать тесты и подготавливать изменения.
- Claude Code - агент для работы с кодовой базой через терминал, IDE и другие поддерживаемые интерфейсы. Используется для анализа архитектуры, рефакторинга, отладки, редактирования файлов и запуска команд.
- GitHub Copilot - ИИ-ассистент, интегрированный с IDE и GitHub. Поддерживает автодополнение, чат, code review и агентные режимы, включая выполнение задач с подготовкой pull request.

Ключевое различие между инструментами определяется не только используемой LLM, но и способом интеграции с проектом, доступными инструментами, уровнем автономности и контролем изменений.

На собеседовании важно указывать реальный опыт: какие инструменты использовались, какие задачи решались и как проверялся результат. Знакомство с возможностями инструмента не равнозначно практическому опыту.

# Для каких задач вы используете ИИ в повседневной разработке?

ИИ полезен для ускорения задач, где результат можно проверить:

- Написание кода - генерация типовых компонентов, функций, обработчиков API и вспомогательных утилит.
- Рефакторинг - упрощение сложной логики, устранение дублирования, изменение структуры кода.
- Отладка - анализ ошибок, логов, stack trace и поиск возможных причин неисправностей.
- Тестирование - генерация unit- и integration-тестов, поиск пограничных случаев.
- Изучение проекта - поиск зависимостей, анализ существующей архитектуры и незнакомого кода.
- Документирование - подготовка README, JSDoc, описаний API и технических комментариев.
- Работа с инструментами - составление регулярных выражений, SQL-запросов, shell-команд и конфигураций.

Основной принцип - использовать ИИ для ускорения реализации, но проверять результат самостоятельно.

Сгенерированный код необходимо проверять на соответствие требованиям, корректность, безопасность и совместимость с существующей архитектурой.

# Какие задачи лучше делегировать ИИ-агенту, а какие выполнять самостоятельно?

ИИ-агенту целесообразно делегировать задачи, которые имеют понятные требования, ограниченный контекст и проверяемый результат:

- Генерацию boilerplate-кода
- Написание и дополнение тестов
- Локальный рефакторинг
- Исправление воспроизводимых ошибок
- Обновление документации
- Типовые изменения в нескольких файлах
- Поиск и анализ существующей реализации

Разработчику следует оставлять ключевые решения, требующие понимания бизнес-контекста и оценки последствий:

- Выбор архитектуры и технологических компромиссов
- Определение бизнес-правил и критериев корректности
- Проектирование критичных механизмов безопасности
- Решения, затрагивающие чувствительные данные
- Проверку изменений перед интеграцией
- Контроль критичных операций в production

Это не означает, что ИИ нельзя использовать для архитектуры или безопасности. Он может предлагать варианты и анализировать риски, но окончательное решение должен принимать разработчик.

Критерий делегирования - насколько точно сформулирована задача, насколько легко проверить результат и какова стоимость потенциальной ошибки.

# Какие ограничения есть у современных coding agents?

Основные ограничения:

- Галлюцинации - агент может придумывать несуществующие API, методы, зависимости или неверно интерпретировать требования.
- Ограниченный контекст - модель не всегда получает достаточно информации о большом проекте. При сжатии контекста могут теряться важные детали.
- Неполное понимание бизнес-логики - агент может предложить технически корректное решение, не соответствующее продуктовым требованиям.
- Недетерминированность - одинаковые запросы могут приводить к разным решениям и последовательностям действий.
- Ошибки при многошаговой работе - неверное предположение на раннем этапе может повлиять на все последующие изменения.
- Ограничения окружения - отсутствие необходимых зависимостей, разрешений, сетевого доступа или корректной тестовой среды.
- Риски безопасности - возможны небезопасные команды, утечки данных, prompt injection через содержимое файлов и результаты внешних инструментов.
- Стоимость и задержки - сложные задачи требуют множества запросов к модели и вызовов инструментов.

Важно понимать, что успешное прохождение тестов не гарантирует правильность решения. Тесты могут не покрывать нужные сценарии, а агент способен адаптировать реализацию под ошибочные проверки.

Поэтому результаты работы агента необходимо проверять через `git diff`, тесты, статический анализ и code review.

# Что такое agentic coding и чем он отличается от обычной генерации кода?

Agentic coding - подход к разработке, при котором ИИ-агент самостоятельно выполняет последовательность действий для реализации задачи, используя инструменты и проверяя промежуточные результаты.

При обычной генерации кода модель получает запрос и возвращает готовый фрагмент. Разработчик самостоятельно интегрирует его в проект, запускает тесты и исправляет ошибки.

При agentic coding процесс выглядит иначе:

1. Агент получает задачу и критерии успешного выполнения.
2. Исследует кодовую базу и определяет необходимые изменения.
3. Формирует план реализации.
4. Изменяет файлы и зависимости при необходимости.
5. Запускает тесты, линтеры и другие проверки.
6. Анализирует ошибки и корректирует реализацию.
7. Предоставляет результат для проверки разработчиком.

Например, задача «Добавить авторизацию через JWT» может включать создание middleware, изменение маршрутов, добавление зависимостей и написание тестов.

Основное отличие - агент работает с задачей целиком, а не ограничивается генерацией отдельного фрагмента кода.

При этом качество результата зависит от постановки задачи, доступного контекста, инструментов и критериев проверки.

# Как устроен цикл работы ИИ-агента с инструментами?

Работа ИИ-агента обычно строится по принципу Agent Loop - повторяющегося цикла принятия решений, выполнения действий и анализа результатов.

Основные этапы:

1. Получение задачи - агент получает цель, инструкции, ограничения и доступный контекст.
2. Анализ и планирование - модель определяет необходимые действия. План может пересматриваться по ходу выполнения.
3. Выбор инструмента - модель формирует запрос к подходящему инструменту, например `read_file`, `edit_file` или `run_command`.
4. Выполнение действия - среда исполнения проверяет разрешения, вызывает инструмент и получает результат.
5. Анализ результата - модель обрабатывает полученные данные, ошибки или результаты тестов.
6. Следующий шаг - агент выбирает новое действие, корректирует предыдущие изменения либо завершает работу.

Пример цикла исправления ошибки:

`Чтение кода → Поиск причины → Изменение файла → Запуск тестов → Анализ ошибки → Исправление → Повторная проверка`

Результаты вызовов инструментов возвращаются модели и становятся частью доступного ей контекста.

Цикл продолжается до достижения цели, исчерпания лимитов, возникновения блокирующей ошибки или необходимости подтверждения пользователя.

Важная особенность: модель предлагает действия, но фактическое выполнение и контроль разрешений обеспечиваются средой агента. Это позволяет ограничивать потенциально опасные операции.

# Что такое tool calling и как агент взаимодействует с файловой системой, терминалом и браузером?

Tool Calling (Function Calling) - механизм, позволяющий языковой модели вызывать внешние инструменты для получения информации и выполнения действий.

Модель не получает прямой доступ к операционной системе автоматически. Вместо этого ей предоставляется описание доступных инструментов, включая их названия, назначение и параметры.

Типичный процесс:

1. Приложение передаёт модели список доступных инструментов.
2. Модель выбирает инструмент и формирует структурированный запрос с аргументами.
3. Среда исполнения проверяет запрос и выполняет соответствующее действие.
4. Результат возвращается модели.
5. Модель использует его для следующего действия или формирования ответа.

Основные категории инструментов:

- Файловая система - чтение, поиск, создание и редактирование файлов проекта.
- Терминал - запуск команд, тестов, сборки, линтеров и Git-операций.
- Браузер - поиск документации, получение веб-страниц, взаимодействие с интерфейсами при наличии соответствующих инструментов.
- Внешние API - работа с GitHub, Jira, базами данных и другими интеграциями.

Например, для проверки проекта агент может вызвать `run_command` с аргументом `{"command":"npm test"}`. Исполнитель запускает команду и возвращает её вывод и код завершения.

Принципиальный момент: `tool calling` определяет способ запроса действия, но не гарантирует его безопасность. Разрешения, изоляция окружения, валидация аргументов и подтверждение опасных операций должны контролироваться отдельно.

# Что такое MCP (Model Context Protocol) и какие задачи он решает?

MCP (Model Context Protocol) - открытый протокол для стандартизированного подключения ИИ-приложений к внешним инструментам и источникам данных.

Он позволяет интегрировать файловые системы, базы данных, GitHub, документацию и другие сервисы без разработки отдельного механизма подключения для каждого сочетания ИИ-клиента и инструмента.

MCP использует архитектуру Host - Client - Server:

- MCP Host - приложение, в котором работает ИИ, например IDE или агент.
- MCP Client - компонент приложения, устанавливающий соединение с конкретным MCP-сервером.
- MCP Server - предоставляет доступ к определённым данным или операциям.

Основные возможности MCP-сервера:

- Tools - функции, которые агент может вызывать, например выполнение SQL-запроса или получение информации из GitHub.
- Resources - данные, доступные для чтения и использования в контексте модели.
- Prompts - переиспользуемые шаблоны взаимодействия с моделью.

Для обмена сообщениями применяется `JSON-RPC`. Подключение может осуществляться локально через `stdio` или по сети через поддерживаемые HTTP-транспорты.

Пример: агент подключается к MCP-серверу PostgreSQL, получает описание доступных инструментов и использует разрешённый инструмент для изучения структуры базы данных.

MCP решает три основные задачи: унификация интеграций, повторное использование инструментов и отделение ИИ-приложения от реализации внешних сервисов.

При этом MCP сам по себе не гарантирует безопасность. Необходимо отдельно контролировать аутентификацию, права доступа, доверие к серверам и выполняемые операции.

# Как оценить эффективность использования ИИ-агентов в разработке?

Эффективность ИИ-агентов следует оценивать по реальному сокращению затрат на выполнение задач при сохранении качества, а не по количеству сгенерированного кода.

Основные метрики:

- Время выполнения задачи - сколько занимает реализация с агентом и без него.
- Доля успешно завершённых задач - сколько задач выполнено с соблюдением требований и критериев приёмки.
- Время проверки и исправлений - сколько разработчик тратит на code review, корректировки и повторные запросы.
- Качество результата - количество дефектов, регрессий, проблем безопасности и повторных исправлений.
- Стоимость использования - расходы на модель, токены, инфраструктуру и инструменты.
- Влияние на процесс разработки - изменение времени прохождения задач, PR cycle time и пропускной способности команды.

Для оценки экономии времени можно использовать формулу:

\\[ \text{Экономия времени} = \frac{T\_{\text{без ИИ}} - T\_{\text{с ИИ}}}{T\_{\text{без ИИ}}} \times 100\\% \\]

Время с ИИ должно включать постановку задачи, работу агента, проверку и исправление результата.

Например, если задача без ИИ занимает 120 минут, а с ИИ вместе с проверкой - 75 минут, экономия составляет 37,5%.

Для объективной оценки следует сравнивать сопоставимые задачи одинаковой сложности, учитывать опыт разработчиков и проводить измерения на достаточной выборке.

Главный критерий: агент полезен, если ускоряет получение корректного, проверенного и поддерживаемого результата, а не просто увеличивает скорость генерации кода.
