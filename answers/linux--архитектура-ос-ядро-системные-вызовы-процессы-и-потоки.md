# Как kernel space и user space разделяют выполнение и доступ к ресурсам Linux?

**User space** выполняет приложения с ограниченным доступом к аппаратуре и памяти других процессов. **Kernel space** содержит ядро и механизмы управления памятью, процессами, devices и сетевым стеком.

Приложение запрашивает привилегированную операцию через контролируемый интерфейс, обычно системный вызов. Переход в ядро не означает, что приложению переданы root-права. Ошибка обычного процесса обычно ограничена его контекстом, тогда как kernel bug способен повлиять на всю систему. Общая граница дополняется permissions, namespaces и другими механизмами.

# Чем системный вызов отличается от библиотечной функции и как работают errno и EINTR?

**Системный вызов** — интерфейс к функции ядра, а **библиотечная функция** — userspace API: она может вызвать один syscall, несколько или обойтись без перехода в kernel. Например, buffering меняет связь между `printf` и реальной записью, а некоторые операции времени доступны через vDSO.

Обычные libc wrappers часто сообщают ошибку через `-1` и `errno`; правила конкретного API проверяют отдельно. `EINTR` означает прерывание ожидающей операции сигналом, но повтор не всегда равен безопасному перезапуску с начала. Учитывают частично выполненную работу и особенности `SA_RESTART`.

# Как process, thread, PID и TID связаны с ресурсами и адресным пространством?

**Process** объединяет адресное пространство и набор ресурсов, а **threads** одного процесса обычно разделяют память и file descriptors, сохраняя собственные stacks, регистры и scheduling state. В Linux каждый thread представлен отдельной task.

**PID**, возвращаемый обычным process API, связан с thread group, а **TID** различает отдельный поток; их видимость также зависит от PID namespace. Изоляция памяти между процессами сильнее, чем между threads: ошибка указателя одного thread может повредить весь процесс. Shared memory между процессами создаёт отдельное осознанное исключение.

# Как fork и exec создают и заменяют процессы без полного копирования всей памяти?

`fork` создаёт дочерний process с первоначально сходным адресным пространством и унаследованными ресурсами. Linux обычно использует **copy-on-write**: физические pages не копируются немедленно целиком, а расход появляется при записи и необходимых изменениях mappings.

`exec` заменяет программу текущего process новым executable, сохраняя process identity и предусмотренные inherited resources, например descriptors без close-on-exec. В многопоточном process после fork в ребёнке остаётся вызывавший thread, поэтому до exec особенно важны ограничения безопасных функций и состояние locks. [fork](https://man7.org/linux/man-pages/man2/fork.2.html).

# Как wait, exit status, zombie и orphan описывают завершение дочернего процесса?

После завершения child ядро сохраняет минимальную информацию для parent: **exit status** и accounting. Пока parent не выполнит подходящий `wait`, такой child может оставаться **zombie**: он не исполняет код, но занимает запись учёта.

**Orphan** — процесс, потерявший parent; он может продолжать работу и быть переподчинён init или subreaper. Zombie и orphan не синонимы. Системе нужен процесс, который собирает статусы детей. Убийство уже завершившегося zombie не решает проблему: исправляют reaping у его живого parent.

# Как file descriptor, open file description и dup задают совместный доступ к файлу?

**File descriptor** — небольшой индекс в таблице descriptors процесса. Он ссылается на **open file description**, где хранится состояние открытого доступа, например offset и часть flags. Сам inode описывает файл, но не индивидуальную позицию чтения.

После `dup` или подходящего наследования через fork несколько descriptors могут ссылаться на одно open file description и разделять offset. Два независимых `open` одного файла обычно создают разные descriptions. Descriptor-specific flags, например close-on-exec, имеют отдельную семантику. Это важно при перенаправлении, конкурентном чтении и передаче descriptors.

# Как pipe, Unix domain socket, shared memory и message passing различаются как IPC?

**Pipe** даёт последовательный поток байтов и простую связь процессов, но не универсальные message boundaries. **Unix domain socket** поддерживает подходящие stream или datagram-модели и дополнительные локальные механизмы, например передачу descriptors.

**Shared memory** уменьшает копирование и позволяет обращаться к общим данным, но требует явной синхронизации, протокола владения и обработки смерти участника. Message passing переносит координацию в обмен и buffering. Выбор зависит от объёма, границ сообщений, изоляции и failure model; «общая память быстрее» без оценки contention и согласования недостаточно.

# Как сигналы доставляются процессам и потокам и почему обработчик ограничен в действиях?

Signal может быть направлен процессу или определённому thread; mask задаётся с соответствующей per-thread семантикой, а dispositions в процессе обычно общие. Для process-directed signal ядро выбирает подходящий thread по правилам доставки.

Асинхронный handler способен прервать код в неудобной точке, поэтому разрешены только **async-signal-safe** действия. Обычные locks, allocation и многие logging functions могут вызвать deadlock или повреждение состояния. Часто handler лишь устанавливает безопасный флаг или уведомляет event loop, а основная работа выполняется позже. `SIGKILL` и `SIGSTOP` нельзя перехватить обычным handler. [Signal safety](https://man7.org/linux/man-pages/man7/signal-safety.7.html).

# Как blocking, nonblocking и asynchronous I/O различаются по поведению вызывающего кода?

**Blocking I/O** может удерживать вызывающий thread в ожидании результата. **Nonblocking I/O** возвращает доступный результат либо `EAGAIN`/`EWOULDBLOCK`, если сейчас пришлось бы ждать, позволяя event loop обслужить другую работу.

**Asynchronous I/O** отделяет отправку операции от уведомления о её завершении. Readiness и completion — разные модели: готовый socket не означает, что весь application message уже получен, а вызов может обработать только часть bytes. Неблокирующий networking не делает автоматически неблокирующим чтение произвольного обычного файла через тот же API.

# Как select, poll и epoll помогают обслуживать много соединений?

`select`, `poll` и **epoll** позволяют ждать readiness нескольких descriptors вместо отдельного blocking thread на каждое соединение. Они различаются интерфейсом, ограничениями и затратами на ведение interest set; epoll удобен для больших наборов с небольшим числом активных событий.

При **edge-triggered** работе обычно используют nonblocking descriptors и читают или пишут до `EAGAIN`, иначе можно не получить нового edge для оставшихся данных. Учитывают закрытие, half-close и частичные операции. Сам epoll не создаёт протокол сообщений и не гарантирует отсутствие application races. [epoll](https://man7.org/linux/man-pages/man7/epoll.7.html).

# Как context switch отличается от перехода в kernel mode и влияет на производительность?

**Context switch** передаёт CPU другой task с сохранением и восстановлением execution state. Переход user/kernel mode при syscall может завершиться возвращением в ту же task и не обязательно включает переключение на другую.

Стоимость зависит от scheduler, адресного пространства, caches, TLB и workload, поэтому фиксированная универсальная цена неверна. Частые switches могут быть нормальными для I/O, а могут отражать contention или чрезмерное число threads. Смотрят voluntary и involuntary switches вместе с latency и профилем ожидания, а не объявляют любое большое число причиной проблемы.

# Как procfs, sysfs и файловые интерфейсы отражают состояние процессов и устройств?

**procfs** предоставляет динамические интерфейсы процессов и части kernel state, например `/proc/<pid>/status`, mappings и descriptors. **sysfs** отражает devices и kernel objects с attributes для наблюдения и предусмотренной настройки.

Это не обычные неизменяемые дисковые файлы: содержимое генерируется, процесс может исчезнуть между чтениями, а доступ зависит от permissions и namespace. Запись в некоторые interfaces меняет систему. Для автоматизации выбирают документированные поля, учитывают races и не печатают без необходимости command lines или environment, которые могут содержать secrets.
