# Какие гарантии ACID даёт транзакция и какие бизнес-правила она не проверяет автоматически?

**Atomicity** обеспечивает общий commit или rollback изменений в заданной транзакционной области. **Consistency** требует сохранения реализованных ограничений. **Isolation** задаёт допустимые взаимодействия concurrent-транзакций, **Durability** — сохранение подтверждённого результата в рамках гарантий движка и настроек.

БД не знает всех бизнес-правил автоматически: корректно оформленная транзакция может записать неверный тариф или нарушить непредставленный инвариант. Нужно определить constraints, алгоритм и подходящий isolation level. Внешний HTTP-вызов обычно находится за пределами локального rollback.

# Как autocommit, BEGIN, COMMIT, ROLLBACK и savepoints задают границы транзакции?

В autocommit отдельные statements обычно выполняются как самостоятельные транзакции. `BEGIN` открывает явную группу, `COMMIT` подтверждает её, `ROLLBACK` отменяет неподтверждённые изменения. Поведение клиентских wrappers нужно учитывать отдельно.

Savepoint задаёт точку частичного отката внутри той же транзакции, но не подтверждает промежуточный результат независимо. Ошибка может перевести transaction context в состояние, требующее rollback или rollback to savepoint. Границу выбирают по атомарному действию, избегая долгого ожидания пользователя или сети внутри неё.

# Как MVCC использует версии строк и snapshots для конкурентного чтения?

**MVCC** сохраняет версии данных и определяет их видимость через snapshot и правила isolation level. Читатель может видеть подтверждённое прошлое состояние, пока другая транзакция создаёт новую версию строки.

Это уменьшает часть конфликтов чтения с записью, но не устраняет locks и все ожидания. Старые версии можно очистить только когда они больше не нужны поддерживаемым readers. Долгий snapshot способен задержать cleanup и увеличить storage. Детали видимости и хранения различаются между движками. [MVCC PostgreSQL](https://www.postgresql.org/docs/current/mvcc-intro.html).

# Чем dirty read, non-repeatable read, phantom read, lost update и write skew отличаются?

**Dirty read** видит неподтверждённую запись, **non-repeatable read** — изменение уже прочитанной строки, **phantom read** — изменение набора строк повторного predicate-запроса. **Lost update** возникает, когда изменение на основе старого значения затирает чужое.

**Write skew** допускает два решения по одному старому snapshot с записью разных строк, вместе нарушающих инвариант. Например, два дежурных независимо снимают себя со смены, каждый видя другого. Названия изоляции следует проверять по реальному движку и виду чтения.

# Как Read Committed, Repeatable Read и Serializable различаются на примере PostgreSQL?

В PostgreSQL `Read Committed` обычно берёт snapshot для каждого statement, поэтому следующий запрос способен увидеть чужой commit. `Repeatable Read` использует стабильный snapshot транзакции, не допускает обычных phantom reads, но может допускать serialization anomalies.

`Serializable` проверяет результат на совместимость с последовательным исполнением и при конфликте может завершить попытку ошибкой. Приложение должно поддерживать правильный retry. Поведение этих названий в другом движке может отличаться. [Isolation PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html).

# Почему snapshot isolation не эквивалентна serializable isolation?

Snapshot isolation даёт согласованное чтение и обнаруживает предусмотренные конфликты записи, но разные транзакции могут изменять разные строки, приняв несовместимые решения по общему snapshot. Именно так возникает write skew без прямой перезаписи одной строки.

Serializable требует, чтобы общий эффект был эквивалентен некоторому последовательному исполнению. Его достигают дополнительной координацией, блокировками или обнаружением конфликтов с abort. Стабильность повторного SELECT сама по себе эту гарантию не доказывает.

# Как SELECT FOR UPDATE и условный UPDATE защищают конкурентное изменение строки?

`SELECT ... FOR UPDATE` блокирует выбранные существующие строки от несовместимых изменений на срок транзакции. Он не обязательно защищает отсутствие строки или весь predicate-набор: это зависит от движка и режима.

Условный `UPDATE`, например `SET stock = stock - :n WHERE stock >= :n`, позволяет связать проверку с изменением и проверить число затронутых строк. Для read-modify-write также используют version predicate. Выбор механизма определяется инвариантом; отдельный SELECT и безусловная запись оставляют гонку. [Locks PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html).

# Как unique, foreign key и check constraints участвуют в обеспечении инвариантов?

Unique constraint защищает выбранную уникальность при concurrent inserts, foreign key — предусмотренную связь, check — допустимое условие строки в рамках возможностей движка. Это надёжнее отдельной предварительной проверки приложением без защиты записи.

Например, два запроса могут одновременно увидеть свободное имя, но unique constraint позволит подтвердить только допустимый результат. Семантика null, deferred checks и область tenant должны быть заданы явно. Cross-row бизнес-правило не следует автоматически считать реализованным обычным CHECK.

# Почему возникает deadlock и как порядок захвата ресурсов уменьшает риск?

Deadlock образует цикл ожиданий: транзакция A держит ресурс X и ждёт Y, а B держит Y и ждёт X. СУБД обычно обнаруживает цикл и отменяет одну попытку, но приложение должно обработать такой исход.

Единый порядок изменения сущностей, короткие транзакции и подходящие индексы уменьшают риск. Lock timeout ограничивает ожидание, но не является полной заменой deadlock handling. После отказа нужен корректный rollback и при допустимости повтор всего сценария, а не продолжение повреждённого transaction context.

# Как безопасно повторить транзакцию после serialization failure или deadlock?

Завершают неуспешную попытку, создают новую транзакцию, заново читают состояние и вычисляют решение. Классифицируют ошибку по надёжному коду движка, ограничивают число попыток и общий срок, при необходимости добавляют backoff.

Повторяемый блок не должен без защиты отправлять письма или выполнять внешний платёж: первая попытка могла успеть совершить этот эффект. Для публикации используют согласованное намерение/outbox. Новое состояние может привести к корректному бизнес-отказу, поэтому повтор не обязан закончиться прежним результатом.

# Как долгие транзакции влияют на locks, MVCC cleanup и размер базы?

Долгая транзакция удерживает locks и snapshot, занимает соединение и может мешать cleanup старых версий. В PostgreSQL это способствует накоплению мёртвых tuples и повышает работу vacuum; большой transaction age также требует внимания к обслуживанию.

Даже `idle in transaction` опасен, если приложение ждёт вне БД, сохраняя контекст. Разделяют длинный процесс на короткие атомарные этапы с долговечным прогрессом. Timeouts и monitoring помогают выявить проблему, но их выбор должен учитывать корректность восстановления.

# Почему commit timeout создаёт неизвестный исход и как его согласовать с идемпотентностью?

Если соединение оборвалось во время `COMMIT`, клиент может не знать, успел ли сервер подтвердить запись. Ошибка ожидания не равна доказанному rollback, поэтому слепой повтор способен удвоить бизнес-операцию.

Стабильный operation/idempotency ID и результат сохраняют атомарно с изменением. После неизвестного исхода проверяют их через подходящий источник чтения или запускают контролируемую сверку. Отсутствие результата на отстающей replica тоже не доказывает отсутствие commit. Ответ и recovery должны различать отказ и неопределённость.
