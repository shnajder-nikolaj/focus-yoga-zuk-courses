# Чем CSR отличается от SSR, SSG и ISR?

Это стратегии формирования HTML и доставки контента пользователю.

- CSR (Client-Side Rendering) - браузер получает минимальный HTML и JavaScript, который формирует интерфейс. Первоначальное отображение зависит от загрузки и выполнения JavaScript. Последующие переходы обычно выполняются без полной перезагрузки страницы.
- SSR (Server-Side Rendering) - сервер формирует HTML при запросе страницы. Браузер может показать содержимое до загрузки JavaScript, а затем выполняется гидратация для подключения интерактивности.
- SSG (Static Site Generation) - HTML генерируется заранее, обычно во время сборки. Готовые страницы можно отдавать через CDN без серверного рендеринга при каждом запросе.
- ISR (Incremental Static Regeneration) - механизм Next.js, позволяющий обновлять предварительно сгенерированные страницы без полной пересборки приложения. Регенерация может запускаться по истечении заданного интервала или по запросу.

Основные различия:

| Стратегия | Когда формируется HTML           | Актуальность данных             |
|-----------|----------------------------------|---------------------------------|
| CSR       | В браузере                       | Зависит от клиентских запросов  |
| SSR       | При запросе к серверу            | Обычно на момент запроса        |
| SSG       | Во время сборки                  | На момент генерации             |
| ISR       | Предварительно и при регенерации | Зависит от политики ревалидации |

SSR, SSG и ISR могут использовать гидратацию для интерактивности. Эти стратегии также можно комбинировать в одном приложении.

# Какие задачи решает серверный рендеринг?

SSR (Server-Side Rendering) позволяет отправлять браузеру готовый HTML вместо ожидания формирования интерфейса клиентским JavaScript.

Основные задачи:

- Первоначальное отображение - пользователь может увидеть содержимое до загрузки и выполнения клиентского JavaScript.
- SEO - поисковые роботы получают HTML с содержимым страницы, не полагаясь исключительно на выполнение JavaScript.
- Социальные превью - метаданные страницы могут присутствовать непосредственно в серверном HTML.
- Работа с серверными данными - данные можно получить до формирования HTML, используя серверные API и доступ к базе данных.
- Снижение нагрузки на клиент - часть работы по формированию интерфейса переносится на сервер.

Ограничения: SSR увеличивает нагрузку на сервер, может повышать TTFB (Time to First Byte) и не устраняет необходимость загружать JavaScript для интерактивных компонентов.

Готовый HTML также не означает, что страница уже интерактивна: обработчики событий становятся доступны после соответствующей гидратации.

# Как работает hydration?

Hydration (гидратация) - процесс подключения React к HTML, который ранее был сформирован на сервере.

Последовательность работы:

1. Сервер рендерит React-компоненты в HTML и отправляет его браузеру.
2. Браузер отображает полученную разметку.
3. Загружается клиентский JavaScript.
4. React вызывает `hydrateRoot()` и выполняет первоначальный клиентский рендер, сопоставляя результат с существующим DOM.
5. React подключает обработку событий и восстанавливает интерактивность компонентов.

В отличие от `createRoot().render()`, гидратация предполагает повторное использование существующей HTML-разметки, а не создание всего DOM с нуля.

Главное требование: первоначальный результат клиентского рендера должен совпадать с серверной разметкой.

После гидратации дальнейшие обновления выполняются обычным механизмом React.

# Что вызывает hydration mismatch?

Hydration mismatch возникает, когда HTML, сформированный сервером, отличается от результата первоначального клиентского рендера React.

Типичные причины:

- Недетерминированные значения - `Date.now()`, `Math.random()` и другие значения, меняющиеся между рендерами.
- Разные окружения - использование `window`, `localStorage` или `navigator` непосредственно при рендеринге.
- Локализация - различия часовых поясов, языка или форматирования дат.
- Разные данные - состояние или ответы API изменились между серверным и клиентским рендерингом.
- Некорректный HTML - например, вложенный `<div>` внутри `<p>`, который браузер автоматически исправляет.
- Сторонние модификации DOM - браузерные расширения, сторонние скрипты или преобразования HTML.

Последствия зависят от типа несоответствия. React может восстановить часть дерева клиентским рендерингом, но автоматическое исправление всех различий не гарантируется.

Для предотвращения mismatch нужно обеспечить одинаковый первоначальный вывод. Браузерные данные можно читать в `useEffect`, а серверные данные - передавать клиенту вместе с HTML.

# Что такое selective hydration?

Selective Hydration - механизм React, позволяющий гидратировать отдельные части интерфейса независимо, с учётом их готовности и приоритета.

Он работает совместно с `Suspense` и конкурентным планировщиком React.

Основные особенности:

- Разные `Suspense`-границы могут гидратироваться независимо по мере готовности необходимых ресурсов.
- React может приоритизировать гидратацию области, с которой пользователь пытается взаимодействовать.
- Гидратация менее приоритетных областей может уступать место более важной работе.
- Некоторые события пользовательского ввода React способен поставить в очередь и воспроизвести после гидратации соответствующей области.

Например, если пользователь нажимает кнопку в ещё не гидратированном блоке, React может приоритетно выполнить гидратацию этого блока вместо ожидания завершения всей страницы.

Преимущество: пользователь получает интерактивность важных частей интерфейса раньше, чем завершится гидратация всего приложения.

# Чем React Server Components отличаются от обычного SSR?

SSR и React Server Components (RSC) решают разные задачи.

SSR формирует HTML на сервере для первоначального отображения страницы. Компоненты, требующие интерактивности, затем гидратируются в браузере, поэтому их клиентский код должен быть загружен.

RSC - архитектура, в которой часть React-компонентов выполняется исключительно на сервере и не входит в клиентский JavaScript-бандл.

Ключевые различия:

| Характеристика                    | SSR                                         | RSC                                                    |
|-----------------------------------|---------------------------------------------|--------------------------------------------------------|
| Основной результат                | HTML                                        | RSC Payload                                            |
| Код компонентов                   | Может требоваться в браузере для гидратации | Код Server Components не отправляется клиенту          |
| Доступ к серверным ресурсам       | Да                                          | Да                                                     |
| Локальное интерактивное состояние | Возможно после гидратации                   | Недоступно в Server Components                         |
| Обновление                        | Новый HTML или клиентский рендер            | Новое серверное дерево, передаваемое через RSC Payload |

RSC Payload - сериализованное представление результата серверного React-рендеринга, содержащее данные, необходимые для восстановления дерева, и ссылки на Client Components.

RSC и SSR могут работать совместно. Например, Next.js использует RSC для серверного формирования дерева компонентов, а SSR - для получения первоначального HTML.

Главное отличие: SSR оптимизирует первоначальную доставку HTML, а RSC позволяет исключать серверную логику и код Server Components из клиентского бандла.

# Какие ограничения накладывает граница Server/Client Components?

Граница Server/Client Components разделяет код, выполняемый на сервере, и код, который может выполняться в браузере.

Server Components:

- Не могут использовать интерактивное состояние через `useState`, обработчики DOM-событий или `useEffect`.
- Не имеют доступа к браузерным API.
- Могут непосредственно обращаться к серверным ресурсам, включая базы данных и внутренние API.
- Могут быть асинхронными и использовать `async/await` при рендеринге.

Client Components:

- Объявляются директивой `'use client'` в поддерживающих RSC фреймворках.
- Могут использовать состояние, эффекты и браузерные API.
- Могут предварительно рендериться на сервере, поэтому обращение к `window` во время первоначального рендера требует осторожности.
- Не должны импортировать серверные модули с секретами или кодом, рассчитанным исключительно на сервер.

Передача данных через границу:

Props, передаваемые из Server Component в Client Component, должны поддерживаться механизмом сериализации React. Допускаются не только JSON-значения, но и некоторые специальные типы, например `Date`, `Map`, `Set`, `Promise`, React-элементы и Server Functions.

При этом Client Component не может напрямую импортировать Server Component как серверный код. Однако Server Component можно передать через `children` или другой prop в виде уже созданного React-элемента.

Важно: `'use client'` определяет границу клиентского графа модулей. Зависимости, импортированные таким модулем, включаются в клиентский граф.

# Можно ли передавать функции через границу Server/Client Components?

Обычные функции, определённые на сервере, нельзя передавать как props в Client Components, поскольку они не сериализуются для выполнения в браузере.

Исключение - Server Functions, объявленные с помощью `'use server'`.

В этом случае клиент получает специальную ссылку на серверную функцию, а не её реализацию. При вызове React отправляет запрос на сервер, где функция выполняется.

Пример:

```
// actions.ts
'use server';

export async function saveData(formData: FormData) {
  const value = formData.get('value');
  await saveToDatabase(value);
}
```

```
// Form.tsx
'use client';

import { saveData } from './actions';

export function Form() {
  return (
    <form action={saveData}>
      <input name="value" />
      <button type="submit">Save</button>
    </form>
  );
}
```

Обычные клиентские функции также можно передавать между Client Components без специальных ограничений RSC.

Важно: Server Functions являются доступными для вызова серверными операциями. Каждая такая функция должна самостоятельно проверять авторизацию и входные данные.

# Чем серверное получение данных отличается от `useEffect` с `fetch`?

Серверное получение данных выполняется до или во время формирования серверного результата. Компонент получает данные непосредственно в серверном окружении.

Пример Server Component:

```
async function Products() {
  const products = await getProducts();

  return <ProductList products={products} />;
}
```

Клиентское получение через `useEffect` запускается после того, как компонент был отображён и React выполнил соответствующий эффект.

```
useEffect(() => {
  fetch('/api/products')
    .then(res => res.json())
    .then(setProducts);
}, []);
```

Основные различия:

- Первоначальный HTML - серверные данные могут присутствовать сразу, а данные из `useEffect` обычно появляются после клиентского запроса.
- Производительность - серверное получение позволяет избежать последовательности «загрузка JavaScript - выполнение эффекта - запрос данных». Однако серверные запросы тоже могут создавать задержки.
- Доступ к ресурсам - сервер может работать с базой данных и приватными API, не раскрывая секреты браузеру.
- SEO - данные, полученные на сервере, могут быть включены в первоначальный HTML.
- Кэширование - серверные стратегии управляются фреймворком, а клиентские могут использовать TanStack Query, SWR и другие решения.

Серверная загрузка предпочтительна для данных, необходимых при первоначальном рендеринге. Клиентская подходит для обновлений после взаимодействия, браузерных данных и частого фонового обновления интерфейса.

# Как организовать Suspense boundaries для потоковой выдачи HTML?

Streaming SSR позволяет отправлять HTML частями, не дожидаясь завершения рендеринга всей страницы.

Для этого медленные или независимые области интерфейса оборачиваются в `Suspense`.

```
function Page() {
  return (
    <Layout>
      <Header />

      <Suspense fallback={<ProductsSkeleton />}>
        <Products />
      </Suspense>

      <Suspense fallback={<ReviewsSkeleton />}>
        <Reviews />
      </Suspense>
    </Layout>
  );
}
```

Принцип работы:

1. Сервер формирует доступную часть страницы, включая `Header` и `fallback` для ожидающих областей.
2. Начальная HTML-разметка отправляется браузеру.
3. По мере готовности `Products` и `Reviews` сервер отправляет дополнительные HTML-фрагменты.
4. React заменяет соответствующие заглушки готовым содержимым.

Правила организации границ:

- Разделять независимые блоки, которые могут загружаться параллельно.
- Оставлять основной каркас страницы доступным без ожидания медленных данных.
- Использовать осмысленные skeleton-компоненты вместо блокировки всей страницы одним индикатором.
- Не создавать чрезмерно много мелких границ, чтобы не усложнять последовательность отображения.

Для Node.js потоковый SSR реализуется через `renderToPipeableStream()`, а в окружениях с Web Streams - через `renderToReadableStream()`.

`Suspense` реагирует на операции, которые приостанавливают рендеринг, например чтение Promise через `use()`. Обычный `fetch` внутри `useEffect` не активирует серверную `Suspense`-границу.

# Что такое server actions/functions и как обеспечивать их безопасность?

Server Functions - асинхронные функции, выполняемые на сервере, которые могут вызываться из клиентского React-приложения.

Server Actions - Server Functions, используемые в контексте действий, например отправки формы или изменения данных.

Функции обозначаются директивой `'use server'`. Фреймворк создаёт механизм удалённого вызова: клиент отправляет запрос, сервер выполняет функцию и возвращает результат.

Основные требования безопасности:

- Аутентификация - проверять пользователя непосредственно внутри серверной операции.
- Авторизация - проверять право пользователя изменять конкретный ресурс.
- Валидация - считать все аргументы недоверенными и проверять их на сервере, например через Zod.
- Защита от CSRF - использовать предоставляемые фреймворком механизмы и правильно настраивать разрешённые источники запросов.
- Защита от злоупотреблений - применять rate limiting и другие ограничения для чувствительных операций.
- Контроль данных - не возвращать клиенту секреты и лишнюю внутреннюю информацию.

В Next.js Server Actions вызываются через HTTP `POST`. Фреймворк предоставляет встроенные проверки, включая проверку `Origin` относительно `Host` или `X-Forwarded-Host`, но они не заменяют авторизацию.

Критически важно: Server Action следует рассматривать как публично вызываемый серверный endpoint. Скрытие кнопки или отсутствие ссылки на функцию не защищает её от прямого вызова.

# Как избежать дублирующей загрузки данных на клиенте после SSR?

При SSR данные загружаются на сервере. Если клиент после гидратации повторно вызывает `fetch` для тех же данных, возникает лишний сетевой запрос.

Основные способы предотвращения:

- Передача начальных данных - сериализовать серверный результат и использовать его для начального состояния клиента.
- Гидратация кэша - заполнить клиентский кэш TanStack Query через `dehydrate()` и восстановить через `HydrationBoundary`.
- Настройка актуальности - задать подходящий `staleTime`, чтобы данные не считались устаревшими сразу после гидратации.
- Использование RSC - передавать серверные данные Client Components через props вместо повторного обращения к API.
- Интеграция с роутером - использовать данные `loader`, которые роутер передаёт компонентам при SSR и гидратации.

Пример с TanStack Query:

```
useQuery({
  queryKey: ['products'],
  queryFn: fetchProducts,
  staleTime: 60_000,
});
```

При условии, что серверный кэш уже гидратирован, запрос не будет автоматически повторяться только из-за монтирования компонента в течение указанного периода актуальности.

Важно различать:

- Request deduplication - объединяет одинаковые запросы во время одного рендера или загрузки.
- Cache hydration - переносит уже полученные данные с сервера в клиентский кэш.

Первое не заменяет второе.

# Как устроены вложенные маршруты?

Nested Routes - маршруты, организованные в иерархию, где дочерние страницы отображаются внутри родительских компонентов.

В React Router дочерний маршрут рендерится через `<Outlet />`.

Пример:

```
const routes = [
  {
    path: '/dashboard',
    Component: DashboardLayout,
    children: [
      { index: true, Component: Overview },
      { path: 'settings', Component: Settings },
    ],
  },
];
```

```
function DashboardLayout() {
  return (
    <>
      <Sidebar />
      <Outlet />
    </>
  );
}
```

Для `/dashboard/settings` React Router отобразит `Settings` внутри `DashboardLayout`.

Особенности:

- Дочерние пути обычно определяются относительно родительского маршрута.
- Родительские компоненты сохраняются при переходах между дочерними страницами, пока остаются частью совпавшей ветки маршрутов.
- Каждый уровень может иметь собственные данные, обработку ошибок и состояние загрузки.
- `index` обозначает дочернюю страницу по умолчанию для URL родителя.

Вложенные маршруты позволяют синхронизировать структуру URL со структурой интерфейса.

# Как организовать layouts для групп страниц?

Layout - общий компонент, который оборачивает несколько страниц и содержит повторяющиеся элементы интерфейса: навигацию, боковую панель, шапку или подвал.

В React Router layouts обычно реализуются через родительские маршруты и `<Outlet />`.

Для страниц с одинаковой оболочкой можно использовать pathless layout route - родительский маршрут без собственного URL-сегмента.

```
{
  Component: AuthLayout,
  children: [
    { path: '/login', Component: Login },
    { path: '/register', Component: Register },
  ],
}
```

`AuthLayout` должен содержать `<Outlet />`, через который отображается выбранная дочерняя страница.

Это позволяет использовать одну оболочку для `/login` и `/register`, не добавляя дополнительный сегмент в URL.

В Next.js App Router layouts определяются файлами `layout.tsx`, а группировка маршрутов выполняется через папки вида `(auth)`.

Главный принцип: общие элементы размещаются в layout, а уникальный контент - в соответствующих страницах.

# Как передавать path params и query params?

Path params - параметры, входящие непосредственно в путь URL.

Например, маршрут `/users/:id` соответствует `/users/42`, где `id = "42"`.

В React Router параметры доступны через `useParams()`:

```
const { id } = useParams();
```

В `loader` и `action` они передаются через аргумент `params`.

Query params - параметры строки запроса после `?`.

Например:

```
/products?page=2&sort=price
```

В React Router используются `useSearchParams()`:

```
const [searchParams, setSearchParams] = useSearchParams();

const page = searchParams.get('page');

setSearchParams({ page: '3' });
```

Основные различия:

- Path params обычно идентифицируют ресурс или часть маршрута.
- Query params обычно задают фильтрацию, сортировку, поиск или пагинацию.
- Оба вида параметров поступают из URL как строки и требуют проверки и преобразования типов.
- Изменение query params не обязательно означает переход на другой маршрут, но может запускать повторную загрузку его данных.

Важно: параметры URL полностью контролируются пользователем, поэтому нельзя считать их доверенными.

# Как работают loaders и actions в data routers?

В React Router Data Router связывает маршруты с получением данных и обработкой изменений.

Loader - функция для загрузки данных маршрута.

Она выполняется при соответствующей навигации до отображения данных маршрута и получает объект с параметрами, включая `request` и `params`.

```
async function loader({ params }) {
  const user = await getUser(params.id);

  if (!user) {
    throw new Response('Not Found', { status: 404 });
  }

  return user;
}
```

Компонент получает результат через `useLoaderData()`.

Action - функция обработки изменений данных, например отправки формы.

```
async function action({ request }) {
  const formData = await request.formData();

  await createUser(formData);

  return redirect('/users');
}
```

`action` вызывается через `<Form>`, `useSubmit()` или `fetcher`.

Жизненный цикл:

1. Пользователь открывает маршрут - вызываются необходимые loaders.
2. Роутер предоставляет результаты компонентам.
3. Пользователь отправляет форму - выполняется соответствующий action.
4. После успешного изменения React Router автоматически ревалидирует необходимые данные маршрутов.

Важное различие окружений: в React Router Data Mode функции `loader` и `action` могут выполняться в браузере. В Framework Mode серверные `loader` и `action` выполняются на сервере и исключаются из клиентского бандла.

# Как обрабатывать ошибки загрузки маршрута?

В React Router ошибки маршрутов обрабатываются через Error Boundaries.

Они могут перехватывать ошибки, возникшие при:

- Выполнении `loader`.
- Выполнении `action`.
- Рендеринге компонента маршрута.

В Data Mode можно задать `errorElement` или `ErrorBoundary` в конфигурации маршрута.

```
{
  path: '/users/:id',
  loader: userLoader,
  Component: UserPage,
  ErrorBoundary: UserError,
}
```

Внутри `UserError` можно использовать `useRouteError()`, чтобы получить ошибку. В Framework Mode ошибка также доступна через props соответствующей границы.

Механизм: если маршрут не имеет собственного Error Boundary, ошибка передаётся ближайшей родительской границе.

Рекомендуется различать:

- 404 - запрошенный ресурс отсутствует.
- 401/403 - проблемы аутентификации или доступа.
- 5xx и неожиданные ошибки - внутренние сбои приложения.

Ожидаемые ошибки валидации формы обычно лучше возвращать как результат `action`, а не выбрасывать в Error Boundary.

Ошибки следует логировать, но не раскрывать пользователю серверные stack traces и внутренние сведения.

# Как организовать редирект после авторизации?

Редирект после авторизации обычно выполняется после успешной проверки учётных данных и создания пользовательской сессии.

В React Router с Data Router предпочтительно выполнять перенаправление из `action`:

```
async function action({ request }) {
  const formData = await request.formData();

  await authenticate(formData);

  return redirect('/dashboard');
}
```

`redirect()` создаёт HTTP-ответ с перенаправлением, который обрабатывается роутером.

Если пользователь пытался открыть защищённую страницу, можно сохранить исходный путь в `returnTo` или аналогичном параметре, а затем вернуть его туда после авторизации.

При этом нужно:

- Проверять, что `returnTo` ведёт на разрешённый внутренний маршрут, чтобы исключить open redirect.
- Не размещать секреты и токены доступа в URL.
- Проверять авторизацию на сервере при обращении к защищённым данным.
- Не полагаться только на клиентские проверки маршрутов.

В обычном клиентском компоненте можно использовать `useNavigate()`, но для серверной авторизации предпочтительнее редирект на уровне `loader` или `action`.

# Чем навигация через `<Link>` отличается от обычной ссылки?

В React Router `<Link>` обеспечивает клиентскую навигацию без полной перезагрузки документа.

```
<Link to="/profile">Profile</Link>
```

В результате React Router:

- Перехватывает обычное внутреннее навигационное нажатие.
- Изменяет URL через History API.
- Загружает необходимые модули и данные маршрута.
- Обновляет соответствующие компоненты без полной перезагрузки страницы.

Обычная ссылка:

```
<a href="/profile">Profile</a>
```

По умолчанию инициирует браузерную навигацию с загрузкой нового документа.

При этом `<Link>` остаётся настоящей HTML-ссылкой. Он поддерживает открытие в новой вкладке, контекстное меню и стандартное поведение браузера. При необходимости роутер допускает обычную документную навигацию.

`<Link>` используют для внутренних маршрутов SPA. Обычный `<a>` подходит для внешних ресурсов, файлов и переходов, требующих полной перезагрузки.

# Как настроить lazy loading по маршрутам?

Route-based Lazy Loading - загрузка JavaScript только для маршрутов, которые действительно понадобились пользователю.

В React Router Data Mode можно использовать свойство `lazy` маршрута:

```
const router = createBrowserRouter([
  {
    path: '/dashboard',
    lazy: () => import('./routes/dashboard'),
  },
]);
```

Модуль `dashboard` экспортирует необходимые части маршрута, например `Component`, `loader` и `ErrorBoundary`.

Роутер загружает модуль при переходе на соответствующий маршрут.

Другой вариант - использовать `React.lazy()` совместно с `Suspense`.

```
const Dashboard = lazy(() => import('./Dashboard'));
```

Различие: `React.lazy()` откладывает загрузку React-компонента, а маршрутный `lazy` позволяет интегрировать отложенную загрузку с механизмами роутера.

В React Router Framework Mode разбиение кода по маршрутам обеспечивается сборочной системой автоматически.

Основные преимущества:

- Уменьшение первоначального JavaScript-бандла.
- Сокращение объёма кода, который браузер должен загрузить и обработать.
- Независимая загрузка редко посещаемых разделов.

Ограничение - первый переход на ещё не загруженный маршрут может потребовать дополнительного сетевого запроса. Для важных переходов можно применять prefetch.

# Как управлять scroll restoration при переходах?

Scroll Restoration - восстановление или изменение позиции прокрутки при навигации.

При обычной загрузке документа браузер управляет прокруткой самостоятельно. В SPA переходы выполняются без перезагрузки страницы, поэтому управление прокруткой должно учитывать роутер.

В React Router используется компонент:

```
<ScrollRestoration />
```

Он позволяет:

- Восстанавливать предыдущую позицию при переходах назад и вперёд.
- Прокручивать новые страницы к началу.
- Настраивать ключ сохранения позиции через `getKey`.
- Сохранять позиции прокрутки в `sessionStorage`.

Для отдельных переходов можно использовать:

```
<Link to="/products" preventScrollReset>
  Products
</Link>
```

Это предотвращает автоматический сброс позиции при переходе, но не отключает восстановление при навигации назад и вперёд.

В Next.js App Router управление прокруткой встроено в механизм навигации. Для `Link` и `router.push()` можно использовать опцию `scroll: false`.

Важно: собственная логика с `window.scrollTo()` не всегда корректно работает с асинхронным рендерингом, вложенными контейнерами и восстановлением истории.

# Как реализовать подтверждение при уходе с формы с несохранёнными данными?

Для защиты несохранённых изменений нужно отслеживать состояние формы и блокировать потенциально опасные переходы.

В React Router используется `useBlocker()`:

```
const blocker = useBlocker(isDirty);
```

Где `isDirty` указывает, что значения формы отличаются от последнего сохранённого состояния.

Если пользователь пытается перейти на другой маршрут, блокировка переходит в состояние `blocked`.

Далее можно показать собственное модальное окно с вариантами:

- Остаться - вызвать `blocker.reset()`.
- Уйти без сохранения - вызвать `blocker.proceed()`.

Для закрытия вкладки, перезагрузки страницы и других переходов вне SPA используется браузерное событие `beforeunload`.

```
useEffect(() => {
  if (!isDirty) return;

  const handler = (event: BeforeUnloadEvent) => {
    event.preventDefault();
    event.returnValue = true;
  };

  window.addEventListener('beforeunload', handler);

  return () => {
    window.removeEventListener('beforeunload', handler);
  };
}, [isDirty]);
```

Ограничения: браузер самостоятельно определяет текст системного предупреждения, а `beforeunload` не гарантирует срабатывание во всех ситуациях, особенно на мобильных устройствах.

После успешного сохранения формы необходимо сбрасывать `isDirty`, чтобы не блокировать ожидаемую навигацию.

# Как работают маршруты с параметрами и приоритетом сопоставления?

В React Router маршруты сопоставляются с URL по структуре пути и вычисляемому приоритету.

Существуют несколько типов сегментов:

- Статические - `/users/new`.
- Динамические - `/users/:id`.
- Опциональные - `/users/:id?`.
- Splat - `/files/*`, соответствующий оставшейся части пути.

Приоритет определяется специфичностью маршрута. Статические сегменты имеют более высокий приоритет, чем динамические, а splat-сегменты - самый низкий.

Например:

```
/users/new
/users/:id
/users/*
```

Для URL `/users/new` будет выбран статический маршрут, даже если динамический маршрут определён раньше.

React Router ранжирует совпадающие ветки маршрутов, учитывая структуру полного пути. Поэтому простая перестановка объявлений обычно не требуется для разрешения конфликтов между статическими и динамическими сегментами.

Важно: параметры маршрута остаются строками. Их необходимо валидировать, а отсутствие ресурса по корректному параметру обрабатывать отдельно, например как 404.

# Чем Next.js отличается от чистого React-приложения?

React - библиотека для построения пользовательских интерфейсов. Она предоставляет компоненты, состояние, хуки и механизмы рендеринга, но сама по себе не определяет полноценную архитектуру веб-приложения.

Next.js - фреймворк на основе React, предоставляющий готовую инфраструктуру для разработки приложений.

Основные возможности Next.js:

- Рендеринг - SSR, SSG, ISR, streaming и React Server Components.
- Роутинг - файловая маршрутизация, вложенные layouts и динамические маршруты.
- Работа с данными - серверная загрузка, кэширование, ревалидация и Server Functions.
- Backend - Route Handlers для HTTP API и серверная логика.
- Оптимизация - автоматическое разделение кода, оптимизация изображений, шрифтов и загрузки ресурсов.
- SEO - управление метаданными, sitemap и robots.txt.

В обычном React-приложении эти возможности необходимо организовывать самостоятельно или подключать через другие библиотеки и инструменты.

Главное отличие: Next.js задаёт архитектуру полноценного приложения, включая серверную часть, тогда как React отвечает прежде всего за построение и обновление интерфейса.

# Чем App Router отличается от Pages Router?

В Next.js существуют две системы маршрутизации: Pages Router и App Router.

| Характеристика          | Pages Router                            | App Router                                            |
|-------------------------|-----------------------------------------|-------------------------------------------------------|
| Директория              | `pages/`                                | `app/`                                                |
| Компоненты по умолчанию | Обычные React-компоненты                | Server Components                                     |
| Получение данных        | `getServerSideProps`, `getStaticProps`  | `async` Server Components, `fetch`, серверные функции |
| Layouts                 | Через пользовательские паттерны         | Встроенные `layout.tsx`                               |
| Streaming               | Ограниченная интеграция                 | Нативная интеграция с `Suspense`                      |
| Изменение данных        | API Routes и другие серверные механизмы | Server Actions и Route Handlers                       |

Pages Router использует модель, в которой получение серверных данных обычно описывается отдельными функциями страницы.

App Router использует архитектуру React Server Components, вложенные маршруты и серверное получение данных непосредственно в компонентах.

Например, в App Router страница может быть асинхронной:

```
export default async function Page() {
  const products = await getProducts();

  return <ProductList products={products} />;
}
```

App Router является основным направлением развития Next.js. Pages Router продолжает поддерживаться, но не предоставляет все возможности новой архитектуры.

# Как работают layouts, templates и nested routes в Next.js?

В Next.js App Router маршруты формируются из структуры директорий внутри `app/`.

Основные файлы:

- `page.tsx` - компонент страницы, доступной по соответствующему URL.
- `layout.tsx` - общая оболочка для вложенных страниц.
- `template.tsx` - оболочка, которая может перемонтироваться при изменении соответствующего сегмента маршрута.

Например:

```
app/
  layout.tsx
  dashboard/
    layout.tsx
    page.tsx
    settings/
      page.tsx
```

При открытии `/dashboard/settings` формируется следующая иерархия:

```
RootLayout
  DashboardLayout
    SettingsPage
```

Layout сохраняет своё состояние и не перемонтируется при переходах между дочерними страницами, если остаётся частью активной иерархии.

Template использует механизм ключей для перемонтирования при изменении соответствующего сегмента. Это позволяет сбрасывать локальное состояние и повторно запускать эффекты. Изменения более глубоких сегментов не обязательно перемонтируют родительский template.

Для логической группировки маршрутов используются Route Groups:

```
app/
  (marketing)/
    layout.tsx
    about/
      page.tsx
  (dashboard)/
    layout.tsx
    settings/
      page.tsx
```

Названия в круглых скобках не входят в URL.

Такая структура позволяет создавать разные layouts для групп страниц. Переход между разными корневыми layouts вызывает полную загрузку документа.

# Когда использовать Server Component и когда Client Component?

Server Component следует использовать, когда компоненту не требуется интерактивность в браузере.

Подходящие задачи:

- Получение данных из базы данных или внутренних API.
- Формирование статического и серверного контента.
- Работа с ресурсами, требующими серверных полномочий.
- Уменьшение клиентского JavaScript-бандла.

Client Component необходим, когда компонент использует:

- `useState`, `useReducer` и интерактивное состояние.
- `useEffect` и другие клиентские эффекты.
- Обработчики событий, например `onClick`.
- Браузерные API.
- Клиентские библиотеки, требующие DOM или React Context.

В App Router компоненты по умолчанию являются Server Components. Для Client Components используется директива `'use client'`.

Пример архитектуры:

```
// Server Component
export default async function ProductPage() {
  const product = await getProduct();

  return (
    <>
      <ProductInfo product={product} />
      <AddToCartButton productId={product.id} />
    </>
  );
}
```

`ProductInfo` может оставаться серверным, а `AddToCartButton` - клиентским.

Основной принцип: оставлять компоненты серверными по умолчанию и переносить клиентскую границу как можно ближе к интерактивным элементам.

При этом Client Components тоже могут предварительно рендериться на сервере. `'use client'` не означает автоматическое отключение SSR.

# Как устроены механизмы кэширования и ревалидации в Next.js?

Next.js использует несколько механизмов кэширования на разных уровнях.

Основные механизмы:

- Request Memoization - устранение повторных одинаковых `fetch`-запросов в пределах одного серверного React-рендера.
- Data Cache / Cache Components - повторное использование результатов загрузки данных между запросами в соответствии с выбранной политикой.
- Full Route Cache - хранение предварительно сформированных HTML и RSC-результатов статических маршрутов.
- Client Router Cache - хранение RSC Payload в памяти браузера для ускорения клиентских переходов.

Не все механизмы активны одновременно. Их поведение зависит от версии Next.js и выбранной модели кэширования.

В Next.js 15+ `fetch` не кэшируется между запросами по умолчанию. В прежней модели можно использовать:

```
fetch(url, { cache: 'force-cache' });
```

или:

```
fetch(url, {
  next: { revalidate: 3600 },
});
```

В Next.js 16 появилась модель Cache Components, включаемая через `cacheComponents: true`.

В ней кэширование описывается явно:

```
import { cacheLife, cacheTag } from 'next/cache';

async function getProducts() {
  'use cache';

  cacheLife('hours');
  cacheTag('products');

  return db.product.findMany();
}
```

Ревалидация обновляет или инвалидирует кэшированные данные.

Основные API:

- `cacheLife()` - управление временем жизни кэшированных результатов.
- `revalidateTag()` - пометка записей с определённым тегом как устаревших.
- `updateTag()` - немедленная инвалидация тега из Server Action.
- `revalidatePath()` - инвалидация данных, связанных с маршрутом.

В модели Cache Components директива `'use cache'` явно обозначает кэшируемую область, а `cacheLife()` определяет политику её обновления.

Важно: кэширование данных, серверного результата маршрута и клиентской навигации - разные механизмы. Инвалидация одного уровня не всегда автоматически означает очистку всех остальных.&#x20;

# Как работают динамические маршруты и параметры?

В Next.js App Router динамические маршруты создаются с помощью квадратных скобок в названиях директорий.

Основные варианты:

- `[id]` - один динамический сегмент.
- `[...slug]` - один или несколько сегментов.
- `[[...slug]]` - ноль или несколько сегментов.

Например:

```
app/products/[id]/page.tsx
```

Соответствует `/products/42`.

В Next.js 16 `params` является Promise:

```
export default async function Page({
  params,
}: {
  params: Promise<{ id: string }>;
}) {
  const { id } = await params;

  return <div>Product: {id}</div>;
}
```

Для query params используется `searchParams`:

```
export default async function Page({
  searchParams,
}: {
  searchParams: Promise<{ page?: string }>;
}) {
  const { page } = await searchParams;

  return <div>Page: {page ?? '1'}</div>;
}
```

В Client Components можно применять `useParams()` и `useSearchParams()` из `next/navigation`.

Для предварительной генерации известных динамических маршрутов используется `generateStaticParams()`.

Важно: начиная с Next.js 16 синхронный доступ к серверным `params` и `searchParams` больше не поддерживается.&#x20;

# Как выбрать между SSR, SSG и ISR?

Выбор зависит от того, насколько часто изменяются данные и требуется ли персонализация.

SSG подходит, если содержимое редко меняется и может быть сформировано заранее.

Примеры:

- Документация.
- Статические информационные страницы.
- Страницы с редко обновляемым содержимым.

ISR подходит, когда содержимое можно кэшировать, но периодически необходимо обновлять.

Примеры:

- Каталоги товаров.
- Статьи и новостные страницы.
- Публичные страницы с регулярно обновляемыми данными.

SSR подходит, когда содержимое зависит от конкретного запроса или пользователя.

Примеры:

- Личный кабинет.
- Персонализированные страницы.
- Контент, требующий актуальных данных непосредственно при запросе.

Критерий выбора:

- Данные известны заранее и почти не меняются - SSG.
- Данные общие для пользователей, но периодически обновляются - ISR.
- Данные персонализированы или должны вычисляться для каждого запроса - SSR.

При этом современные механизмы Next.js позволяют комбинировать стратегии внутри одной страницы.

Например, статический каталог может использовать кэшированные данные, а персональный блок пользователя - серверный рендеринг при каждом запросе.

# Как работают streaming и Suspense в Next.js?

Streaming в Next.js App Router позволяет отправлять HTML частями по мере готовности компонентов.

Основные механизмы:

1\. `loading.tsx`

Файл автоматически создаёт загрузочное состояние для соответствующего сегмента маршрута.

```
app/
  products/
    loading.tsx
    page.tsx
```

Пока `page.tsx` ожидает данные, пользователь может видеть интерфейс из `loading.tsx`, а уже готовый родительский layout остаётся доступным.

2\. `<Suspense>`

Позволяет управлять загрузкой отдельных компонентов:

```
<Suspense fallback={<ProductsSkeleton />}>
  <Products />
</Suspense>
```

Последовательность:

1. Next.js начинает серверный рендеринг.
2. Готовая часть HTML и загрузочные состояния отправляются браузеру.
3. Сервер продолжает выполнять асинхронные операции.
4. Готовые фрагменты интерфейса поступают в HTML-потоке.
5. React постепенно отображает содержимое и гидратирует необходимые Client Components.

В Next.js 16 с включёнными Cache Components поддерживается Partial Prerendering (PPR) - предварительное формирование статической оболочки с последующей потоковой выдачей динамических областей.

Для корректного streaming важно располагать `Suspense` рядом с асинхронными областями. Если медленный запрос выполняется выше границы, он может заблокировать отправку соответствующей части страницы.

# Как реализовать Server Action и защитить её от неавторизованных вызовов?

Server Action создаётся как асинхронная функция с директивой `'use server'`.

Пример:

```
// app/actions.ts
'use server';

import { auth } from '@/lib/auth';
import { db } from '@/lib/db';
import { revalidatePath } from 'next/cache';

export async function updatePost(
  postId: string,
  formData: FormData
) {
  const session = await auth();

  if (!session?.user) {
    throw new Error('Unauthorized');
  }

  const post = await db.post.findUnique({
    where: { id: postId },
  });

  if (!post) {
    throw new Error('Not found');
  }

  if (post.authorId !== session.user.id) {
    throw new Error('Forbidden');
  }

  const title = formData.get('title');

  if (typeof title !== 'string' || !title.trim()) {
    throw new Error('Invalid title');
  }

  await db.post.update({
    where: { id: postId },
    data: { title: title.trim() },
  });

  revalidatePath(`/posts/${postId}`);
}
```

В примере проверяются:

1. Аутентификация - пользователь имеет действующую сессию.
2. Авторизация - пользователь является владельцем конкретной записи.
3. Валидация - входное значение имеет ожидаемый тип и допустимое содержимое.
4. Инвалидация - кэш маршрута обновляется после изменения данных.

Для реального приложения также могут потребоваться ограничения длины данных, rate limiting и защита от конфликтующих изменений.

Главное правило: проверку доступа необходимо выполнять внутри каждой чувствительной серверной операции, даже если страница уже защищена через layout или Proxy.

# Как загрузить данные с правильной стратегией кэширования?

Стратегия кэширования определяется требованиями к актуальности и конфиденциальности данных.

1\. Данные всегда должны быть свежими

В модели без Cache Components:

```
const response = await fetch(url, {
  cache: 'no-store',
});
```

Такой запрос не использует постоянный Data Cache Next.js.

2\. Данные практически не изменяются

```
const response = await fetch(url, {
  cache: 'force-cache',
});
```

Результат может повторно использоваться между запросами.

3\. Данные должны обновляться периодически

```
const response = await fetch(url, {
  next: { revalidate: 300 },
});
```

Кэш ревалидируется с интервалом 300 секунд согласно политике Next.js.

4\. Данные должны обновляться после конкретного события

Можно использовать теги:

```
const response = await fetch(url, {
  next: { tags: ['products'] },
});
```

После изменения данных:

```
revalidateTag('products', 'max');
```

В Next.js 16 с включёнными Cache Components предпочтительна модель `'use cache'` с `cacheLife()` и `cacheTag()`.

При выборе стратегии важно учитывать:

- Публичные данные можно кэшировать между пользователями.
- Персонализированные данные нельзя случайно помещать в общий кэш без корректного разделения по пользователям и правам доступа.
- Часто изменяемые данные требуют ограниченного времени жизни или явной инвалидации.
- Критически актуальные данные не должны полагаться на кэш, допускающий устаревшие значения.

Также необходимо учитывать кэширование на CDN и в браузере: `cache: 'no-store'` в серверном `fetch` само по себе не управляет всеми возможными уровнями кэша.

# Как избежать утечки секретов через переменные окружения?

Next.js поддерживает переменные окружения через `process.env` и файлы `.env`.

Главное правило: переменные с префиксом `NEXT_PUBLIC_` предназначены для клиентского кода и могут включаться непосредственно в JavaScript-бандл.

Например:

```
DATABASE_URL=postgresql://...
NEXT_PUBLIC_API_URL=https://api.example.com
```

`DATABASE_URL` должен использоваться только на сервере. `NEXT_PUBLIC_API_URL` может быть доступен в браузере.

Для защиты секретов необходимо:

- Не добавлять `NEXT_PUBLIC_` к токенам, паролям и приватным ключам.
- Хранить секреты в серверных переменных окружения или специализированных secret managers.
- Не импортировать серверные модули с секретами в Client Components.
- Использовать `server-only` для модулей, которые не должны попадать в клиентский граф зависимостей.
- Не возвращать секреты через props, RSC Payload, API-ответы или HTML.
- Исключать `.env` с секретами из Git и не выводить значения в публичные логи.

Важно: даже Server Component может раскрыть секрет, если явно передаст его в Client Component или включит в HTML.

Префикс `NEXT_PUBLIC_` также означает, что переменная обычно подставляется в клиентский бандл во время сборки. Изменение её значения после сборки не обновляет уже сформированный JavaScript.

# Что такое edge runtime и чем он отличается от Node.js runtime?

Edge Runtime - серверная среда выполнения JavaScript, ориентированная на развёртывание обработчиков ближе к пользователям через распределённую инфраструктуру.

Node.js Runtime - полноценная серверная среда Node.js с поддержкой Node API и совместимых npm-пакетов.

Основные различия:

| Характеристика   | Edge Runtime                                             | Node.js Runtime                                           |
|------------------|----------------------------------------------------------|-----------------------------------------------------------|
| Расположение     | Часто ближе к пользователю                               | Зависит от размещения сервера                             |
| API              | Web API и ограниченный набор возможностей                | Web API и Node.js API                                     |
| Файловая система | Нет обычного Node.js `fs`                                | Доступна                                                  |
| npm-пакеты       | Только совместимые с Edge                                | Широкая совместимость                                     |
| Сценарии         | Лёгкие обработчики, географически распределённые запросы | Базы данных, сложная серверная логика, Node.js-библиотеки |

Потенциальное преимущество Edge Runtime - уменьшение сетевой задержки между пользователем и обработчиком.

Однако если Edge-функция обращается к базе данных в удалённом регионе, общая задержка может увеличиться.

В Next.js runtime для поддерживаемых маршрутов можно выбирать через:

```
export const runtime = 'edge';
```

Особенность Next.js 16: `proxy.ts` выполняется в Node.js Runtime и не поддерживает настройку `runtime = 'edge'`. Модель Cache Components также требует Node.js Runtime.&#x20;

# Как организовать обработку ошибок и not-found страницы?

В Next.js App Router используются специальные файловые соглашения.

`error.tsx` - обработка неожиданных ошибок в соответствующем сегменте маршрута и его дочерних сегментах.

```
'use client';

export default function Error({
  reset,
}: {
  error: Error;
  reset: () => void;
}) {
  return (
    <div>
      <p>Something went wrong</p>
      <button onClick={reset}>Retry</button>
    </div>
  );
}
```

В реальном компоненте `error` также доступен для логирования. Функция `reset()` повторно пытается отобразить содержимое границы.

`not-found.tsx` - интерфейс для отсутствующих ресурсов и маршрутов.

Для вызова используется:

```
import { notFound } from 'next/navigation';

export default async function Page() {
  const post = await getPost();

  if (!post) {
    notFound();
  }

  return <PostView post={post} />;
}
```

`notFound()` прерывает рендеринг текущего сегмента и активирует соответствующий not-found UI.

`global-error.tsx` - обработка ошибок, которые не могут быть перехвачены обычными границами, в том числе ошибок корневого layout. Такой компонент должен самостоятельно формировать необходимые корневые HTML-элементы.

Основные правила:

- Ожидаемые ошибки, например ошибки валидации, обрабатывать явно.
- Неожиданные ошибки передавать Error Boundary.
- Использовать `notFound()` для отсутствующих ресурсов.
- Логировать внутренние ошибки, не раскрывая пользователю чувствительную информацию.

Нюанс streaming: если ответ уже начал передаваться, изменить HTTP-статус невозможно. Поэтому not-found UI в потоковом ответе не всегда сопровождается HTTP 404.

# Как работает middleware или proxy на уровне приложения?

Proxy - механизм Next.js для выполнения логики до завершения обработки входящего HTTP-запроса.

Начиная с Next.js 16 файловое соглашение `middleware.ts` переименовано в `proxy.ts`.

Proxy может:

- Выполнять перенаправления через `NextResponse.redirect()`.
- Переписывать маршруты через `NextResponse.rewrite()`.
- Изменять заголовки запроса и ответа.
- Работать с cookies.
- Выполнять предварительные проверки доступа.
- Реализовывать правила маршрутизации или A/B-тестирование.

Пример:

```
// proxy.ts
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  const token = request.cookies.get('session');

  if (!token) {
    return NextResponse.redirect(
      new URL('/login', request.url)
    );
  }

  return NextResponse.next();
}

export const config = {
  matcher: ['/dashboard/:path*'],
};
```

`matcher` ограничивает маршруты, для которых выполняется Proxy.

`redirect` и `rewrite` отличаются:

- `redirect` - отправляет браузеру перенаправление на другой URL.
- `rewrite` - внутренне обрабатывает запрос другим маршрутом, сохраняя исходный URL в браузере.

Ограничение безопасности: Proxy подходит для предварительных проверок, но не должен быть единственным уровнем авторизации.

Доступ к данным необходимо проверять непосредственно в Server Functions, Route Handlers и серверных операциях.

Также не рекомендуется выполнять в Proxy тяжёлые запросы к базе данных или сложную бизнес-логику.

# Как сравнить data loading в Remix, React Router framework mode и Next.js?

В этих технологиях используются разные модели получения и передачи серверных данных.

Remix 2 и React Router Framework Mode

React Router унаследовал модель загрузки данных Remix 2. В современных версиях React Router, включая v8, основными механизмами остаются:

- `loader` - серверное получение данных для маршрута.
- `clientLoader` - получение данных на клиенте.
- `action` - серверная обработка изменений.
- `clientAction` - клиентская обработка действий.
- `Form` и `fetcher` - отправка данных.
- Автоматическая ревалидация loaders после изменений.

Данные привязаны к маршрутам. При клиентской навигации роутер получает необходимые результаты серверных loaders через HTTP-запросы.

Next.js App Router

Основная модель основана на React Server Components:

```
export default async function Page() {
  const products = await getProducts();

  return <ProductList products={products} />;
}
```

Данные загружаются непосредственно в серверном компоненте.

Next.js использует RSC Payload для передачи серверного результата клиенту, а для изменений предоставляет Server Functions и Route Handlers.

Remix 3

С октября 2026 года Remix 3 является отдельным стабильным фреймворком с новой архитектурой, не основанной на React.

Он использует Web API `Request` и `Response`, типизированные маршруты, controllers и middleware. Обработчики получают данные и возвращают HTTP-ответы, включая HTML, JSON, редиректы и потоки.

Поэтому переносить модель `loader`/`action` из Remix 2 на Remix 3 напрямую некорректно.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://remix.run\&sz=32)

Remix+1



Итоговое сравнение:

| Технология                  | Основной подход                                                          |
|-----------------------------|--------------------------------------------------------------------------|
| Remix 2                     | Загрузка и изменение данных через `loader`/`action` маршрута             |
| React Router Framework Mode | Серверные и клиентские loaders/actions, интегрированные с маршрутизацией |
| Next.js App Router          | Загрузка данных в Server Components и изменения через Server Functions   |
| Remix 3                     | Обработка `Request` через controllers с формированием `Response`         |

Ключевое архитектурное различие: React Router связывает загрузку данных с маршрутом, Next.js позволяет размещать её непосредственно в серверном дереве компонентов, а Remix 3 строит обработку вокруг HTTP-запросов и контроллеров.

# Как правильно организовать SEO metadata и sitemap?

В Next.js App Router SEO-метаданные задаются через Metadata API.

Для статических страниц используется экспорт `metadata`:

```
import type { Metadata } from 'next';

export const metadata: Metadata = {
  title: 'Products',
  description: 'Product catalog',
  alternates: {
    canonical: '/products',
  },
};
```

Для динамических страниц используется `generateMetadata()`:

```
export async function generateMetadata({ params }) {
  const { slug } = await params;
  const post = await getPost(slug);

  return {
    title: post.title,
    description: post.description,
  };
}
```

Основные элементы SEO:

- `title` - заголовок страницы.
- `description` - краткое описание содержимого.
- Canonical URL - указание предпочтительного URL при наличии дублирующихся страниц.
- Open Graph / Twitter metadata - управление отображением ссылок в социальных сетях.
- `robots` - правила индексации отдельных страниц.
- Sitemap - перечень URL, доступных для обнаружения поисковыми системами.

Для генерации sitemap используется `app/sitemap.ts`:

```
import type { MetadataRoute } from 'next';

export default function sitemap(): MetadataRoute.Sitemap {
  return [
    {
      url: 'https://example.com/',
      lastModified: new Date(),
    },
    {
      url: 'https://example.com/products',
      lastModified: new Date(),
    },
  ];
}
```

Next.js автоматически формирует соответствующий `/sitemap.xml`.

Для правил обхода используется `app/robots.ts` или статический `robots.txt`.

Важно:

- Динамические страницы должны иметь уникальные и корректные метаданные.
- Sitemap должен содержать канонические URL страниц, которые предполагается индексировать.
- `lastModified` должен отражать реальное изменение содержимого, а не просто момент выполнения функции.
- Sitemap помогает обнаруживать страницы, но не гарантирует их индексацию.
- Для закрытого контента применяют корректные правила авторизации и, при необходимости, `noindex`.

SSR и SSG облегчают получение контента поисковыми системами, но сами по себе не гарантируют высоких позиций в поиске.

# Как устроить инвалидацию данных после изменения на сервере?

Инвалидация - пометка кэшированных данных как устаревших или удаление их из кэша, чтобы последующие обращения использовали актуальное состояние.

В Next.js для этого применяются несколько API.

`revalidatePath()` - инвалидирует кэш, связанный с конкретным маршрутом.

```
revalidatePath('/products');
```

`revalidateTag()` - инвалидирует данные по логическому тегу.

```
revalidateTag('products', 'max');
```

В современной модели Next.js это использует стратегию stale-while-revalidate: устаревшие данные могут быть временно возвращены, пока кэш обновляется.

`updateTag()` - немедленно помечает кэшированные данные как недействительные, чтобы следующий запрос дождался свежих данных.

```
updateTag('products');
```

`updateTag()` доступен только внутри Server Actions.

Пример изменения данных:

```
'use server';

import { updateTag } from 'next/cache';
import { db } from '@/lib/db';

export async function createProduct(formData: FormData) {
  const name = formData.get('name');

  if (typeof name !== 'string' || !name.trim()) {
    throw new Error('Invalid name');
  }

  await db.product.create({
    data: { name: name.trim() },
  });

  updateTag('products');
}
```

Предполагается, что данные каталога ранее были кэшированы с тегом `products`, а право на создание товара проверено на сервере.

Последовательность правильной инвалидации:

1. Проверить пользователя и входные данные.
2. Выполнить изменение в базе данных.
3. Дождаться успешного завершения операции.
4. Инвалидировать соответствующий кэш.
5. Вернуть обновлённый интерфейс или выполнить перенаправление.

Если изменение происходит через Route Handler или внешний webhook, можно использовать `revalidateTag()` или `revalidatePath()`.

Главное различие: `revalidateTag('products', 'max')` допускает временно устаревшие данные, а `updateTag('products')` предназначен для сценариев, когда пользователь должен сразу увидеть собственные изменения.

# Какие риски есть у hydration mismatch и как его диагностировать?

Hydration mismatch - несоответствие между серверной HTML-разметкой и первоначальным результатом клиентского рендера React.

Основные риски:

- Некорректный интерфейс - пользователь может видеть содержимое, отличающееся от ожидаемого.
- Сбои интерактивности - при некоторых несоответствиях элементы могут неправильно реагировать на действия.
- Дополнительный клиентский рендеринг - React может отказаться от гидратации проблемной области и заново сформировать её на клиенте.
- Проблемы производительности - повторный рендеринг увеличивает объём работы браузера.
- Визуальные скачки - замена серверного содержимого может вызывать изменения layout.

Диагностика:

1. Проверить сообщения React в консоли и диагностическую информацию Next.js.
2. Определить компонент, в котором возникает несоответствие.
3. Сравнить серверный HTML с ожидаемым первоначальным клиентским результатом.
4. Проверить использование `Date.now()`, `Math.random()`, локализации и браузерных API.
5. Проверить корректность вложенности HTML-элементов.
6. Убедиться, что сервер и клиент используют одинаковые первоначальные данные.

Для программного отслеживания ошибок гидратации можно использовать `onRecoverableError` в `hydrateRoot()`:

```
hydrateRoot(container, <App />, {
  onRecoverableError(error, errorInfo) {
    reportError({
      message: error.message,
      componentStack: errorInfo.componentStack,
    });
  },
});
```

В Next.js вызов `hydrateRoot()` обычно выполняется самим фреймворком, поэтому диагностика строится через его инструменты и системы мониторинга.

Для предотвращения mismatch необходимо обеспечить детерминированный первоначальный рендер.

Если значение доступно только в браузере, его можно получить после гидратации через `useEffect`.

Для редких неизбежных текстовых различий существует `suppressHydrationWarning`, но он подавляет предупреждение только на одном уровне вложенности и не исправляет само несоответствие.

Важно: `suppressHydrationWarning` не следует применять как универсальное решение. Правильный подход - найти причину различий и устранить её.
