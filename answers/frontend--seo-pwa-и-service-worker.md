# Как frontend-архитектура влияет на индексацию страниц?

Frontend-архитектура определяет, насколько легко поисковый робот может получить содержимое страницы, обнаружить ссылки и обработать метаданные.

Основные подходы:

- CSR (Client-Side Rendering) - HTML формируется в браузере через JavaScript. Поисковому роботу может потребоваться дополнительный этап рендеринга.
- SSR (Server-Side Rendering) - сервер возвращает HTML с содержимым страницы. Робот может анализировать его без выполнения JavaScript.
- SSG (Static Site Generation) - HTML создаётся во время сборки. Подходит для страниц, содержимое которых не требует генерации при каждом запросе.
- ISR (Incremental Static Regeneration) - позволяет обновлять предварительно сгенерированные страницы без полной пересборки сайта. Реализация зависит от фреймворка.

Для SEO важны доступность содержимого в HTML, корректные HTTP-статусы, уникальные URL, метаданные, семантическая разметка и доступные для обхода ссылки.

SSR и SSG обычно упрощают индексацию, но сами по себе не гарантируют высоких позиций в поиске.&#x20;

# Что должно содержаться в `title`, `meta description` и canonical URL?

`<title>` - уникальный и информативный заголовок страницы, отражающий её основное содержимое. Используется поисковыми системами при формировании заголовка результата поиска, хотя они могут его изменить.

`<meta name="description">` - краткое описание содержимого страницы. Может использоваться поисковыми системами для формирования сниппета, но не гарантирует его точный текст и не является прямым фактором ранжирования Google.

Canonical URL - предпочтительный адрес страницы среди нескольких URL с одинаковым или очень похожим содержимым.

Пример:

```
<title>Купить ноутбук Lenovo - Магазин</title>

<meta
  name="description"
  content="Ноутбуки Lenovo: характеристики, цены и доставка."
/>

<link
  rel="canonical"
  href="https://example.com/laptops/lenovo"
/>
```

Canonical рекомендуется указывать абсолютным URL, включая протокол и домен.

Важно: `rel="canonical"` - рекомендация поисковику, а не обязательная команда. Google может выбрать другой канонический адрес.&#x20;

# Что такое `robots.txt` и `sitemap.xml`?

`robots.txt` - текстовый файл в корне сайта, содержащий правила обхода URL поисковыми роботами.

Пример:

```
User-agent: *
Disallow: /admin/
Allow: /

Sitemap: https://example.com/sitemap.xml
```

Он регулирует сканирование страниц, но не гарантирует исключение URL из поискового индекса. Для запрета индексации используют `noindex` в HTML или HTTP-заголовке `X-Robots-Tag`, причём робот должен иметь возможность получить эту директиву.

`sitemap.xml` - XML-файл со списком URL, которые сайт рекомендует поисковым системам для обхода.

Может содержать:

- `<loc>` - адрес страницы
- `<lastmod>` - дата последнего существенного изменения
- `<sitemapindex>` - ссылки на другие sitemap-файлы, если используется индекс sitemap

Sitemap помогает обнаруживать страницы и обновления, но не гарантирует сканирование или индексацию.

# Чем client-side rendering может усложнять работу поисковых роботов?

При CSR сервер обычно возвращает минимальный HTML, а основное содержимое формируется JavaScript после загрузки страницы.

Это создаёт несколько проблем:

- Не все поисковые роботы выполняют JavaScript.
- Рендеринг может происходить отдельно от первоначального сканирования, задерживая индексацию.
- Ошибки JavaScript и недоступные API могут препятствовать получению контента.
- Ссылки, создаваемые только после взаимодействия пользователя, могут остаться незамеченными.
- Метаданные, устанавливаемые слишком поздно, могут обрабатываться некорректно.

Googlebot умеет выполнять JavaScript, но это не устраняет все ограничения.

Решение: использовать SSR или SSG для SEO-значимого контента, предоставлять обычные HTML-ссылки через `<a href>` и обеспечивать корректные метаданные непосредственно в HTML-ответе.&#x20;

# Как устроены structured data и JSON-LD?

Structured Data - структурированные метаданные, описывающие содержимое страницы в формате, понятном поисковым системам.

Чаще всего используется словарь Schema.org, содержащий типы сущностей: `Product`, `Article`, `Organization`, `BreadcrumbList` и другие.

JSON-LD (JSON for Linked Data) - рекомендуемый Google формат передачи структурированных данных внутри HTML.

Пример:

```
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "MacBook Air",
  "description": "Ноутбук Apple MacBook Air"
}
</script>
```

Здесь:

- `@context` - определяет используемый словарь
- `@type` - указывает тип описываемой сущности
- `name`, `description` - свойства сущности

Поисковые системы используют эти данные для понимания содержимого и потенциального формирования расширенных результатов поиска (Rich Results).

Разметка должна соответствовать реальному содержимому страницы. Наличие JSON-LD не гарантирует отображение расширенного результата.&#x20;

# Как избежать дублирования страниц при параметрах URL?

Параметры URL могут создавать несколько адресов с одинаковым содержимым:

```
/products?sort=price
/products?sort=popular
/products?utm_source=email
```

Основные способы устранения дублирования:

- Canonical - указывать предпочтительный URL для страниц с одинаковым или очень похожим содержимым.
- 301/308 redirect - перенаправлять на основной адрес, если альтернативный URL не нужен.
- Нормализация URL - удалять ненужные параметры, например `utm_*`, при формировании внутренних ссылок.
- Sitemap - включать только канонические адреса.
- `noindex` - использовать для страниц, которые не должны индексироваться, но не в качестве основного механизма каноникализации.

Например, страницы с разной сортировкой могут ссылаться через `rel="canonical"` на `/products`, если содержат фактически один набор товаров.

Важно: параметры фильтрации, создающие существенно отличающееся и полезное содержимое, не всегда следует объединять под один canonical.&#x20;

# Что такое Open Graph metadata?

Open Graph (OG) - протокол метаданных, определяющий, как страница представляется при публикации ссылки в социальных сетях и мессенджерах.

Основные свойства:

- `og:title` - заголовок
- `og:description` - описание
- `og:image` - изображение предпросмотра
- `og:url` - канонический адрес объекта
- `og:type` - тип содержимого, например `website` или `article`

Пример:

```
<meta property="og:title" content="Название статьи" />
<meta property="og:description" content="Описание статьи" />
<meta property="og:image" content="https://example.com/cover.jpg" />
<meta property="og:url" content="https://example.com/article" />
<meta property="og:type" content="article" />
```

Open Graph влияет на внешний вид предпросмотра ссылки, но не является прямым механизмом улучшения поискового ранжирования.

# Какие требования нужно выполнить для установки PWA?

PWA (Progressive Web App) - веб-приложение, которое может устанавливаться на устройство и использовать возможности браузера, похожие на возможности нативных приложений.

Основные требования для установки в Chromium-браузерах:

- HTTPS - приложение должно работать в безопасном контексте. Для разработки допускается `localhost`.
- Web App Manifest - должен содержать название, стартовый URL, режим отображения и необходимые иконки.
- Иконки - обычно требуются размеры `192x192` и `512x512`.
- Корректный режим отображения - например, `standalone`, позволяющий запускать приложение без обычного интерфейса браузера.

Service Worker не является универсальным обязательным требованием для установки PWA, но используется для offline-режима, кэширования и фоновых возможностей.

Требования зависят от браузера. Например, Safari позволяет добавлять веб-приложения на домашний экран, даже если они не соответствуют всем критериям установки Chromium.&#x20;

# Что содержит Web App Manifest?

Web App Manifest - JSON-файл с метаданными, определяющими внешний вид и поведение установленного веб-приложения.

Основные поля:

- `name` - полное название приложения
- `short_name` - сокращённое название
- `id` - идентификатор приложения
- `start_url` - стартовый адрес
- `scope` - область URL, принадлежащих приложению
- `display` - режим отображения: `standalone`, `fullscreen`, `minimal-ui`, `browser`
- `icons` - иконки разных размеров
- `theme_color` - цвет оформления интерфейса
- `background_color` - цвет фона при запуске
- `orientation` - предпочтительная ориентация экрана
- `screenshots` - изображения для предпросмотра приложения

Пример:

```
{
  "name": "My Application",
  "short_name": "MyApp",
  "id": "/",
  "start_url": "/",
  "scope": "/",
  "display": "standalone",
  "theme_color": "#ffffff",
  "background_color": "#ffffff",
  "icons": [
    {
      "src": "/icon-192.png",
      "sizes": "192x192",
      "type": "image/png"
    },
    {
      "src": "/icon-512.png",
      "sizes": "512x512",
      "type": "image/png"
    }
  ]
}
```

Подключается через HTML:

```
<link rel="manifest" href="/manifest.webmanifest" />
```

Manifest описывает приложение, но самостоятельно не обеспечивает offline-работу и кэширование.

# Как работает жизненный цикл Service Worker?

Service Worker - JavaScript-воркер, работающий отдельно от страницы и способный перехватывать сетевые запросы, управлять кэшем и обрабатывать фоновые события.

Основные этапы жизненного цикла:

1. Registration - браузер регистрирует Service Worker через `navigator.serviceWorker.register()`.
2. Installing - вызывается событие `install`, обычно выполняется предварительное кэширование ресурсов.
3. Installed / Waiting - воркер установлен и ожидает активации, если предыдущая версия ещё контролирует открытые страницы.
4. Activating - вызывается `activate`, часто используется для удаления устаревших кэшей.
5. Activated - воркер начинает обрабатывать события `fetch`, `push`, `sync` и другие.
6. Redundant - воркер становится неактуальным или не проходит установку.

Особенности:

- Service Worker работает отдельно от основного потока и не имеет доступа к DOM.
- Браузер может остановить его при отсутствии работы и запустить повторно при событии.
- `event.waitUntil()` позволяет продлить обработку события до завершения переданного Promise.
- `skipWaiting()` позволяет новой версии активироваться, не дожидаясь закрытия старых вкладок.
- `clients.claim()` позволяет активному воркеру начать контролировать уже открытые страницы в пределах его `scope`.

Важно: Service Worker не является постоянно работающим фоновым процессом.&#x20;

# Какие стратегии кэширования доступны Service Worker?

Service Worker может перехватывать запросы через событие `fetch` и самостоятельно выбирать источник ответа с использованием Cache Storage API.

Основные стратегии:

- Cache First - сначала кэш, затем сеть. Подходит для статических ресурсов.
- Network First - сначала сеть, при ошибке кэш. Подходит для актуальных данных.
- Stale While Revalidate - немедленно отдаёт кэшированную версию и параллельно обновляет кэш через сеть.
- Cache Only - использует только кэш. Подходит для заранее сохранённых ресурсов.
- Network Only - использует только сеть. Подходит для запросов, требующих актуального ответа.

Стратегии можно комбинировать для разных ресурсов.

Например, изображения можно загружать через `Cache First`, а данные пользовательского профиля - через `Network First`.

Для реализации часто используют Workbox, который предоставляет готовые стратегии, управление сроком жизни кэша и обработку ошибок.&#x20;

# Чем cache-first отличается от network-first и stale-while-revalidate?

Cache First

Сначала проверяется кэш. Если ресурс найден, он сразу возвращается. Если отсутствует, выполняется сетевой запрос.

- Преимущество - высокая скорость и работа без сети.
- Недостаток - данные могут долго оставаться устаревшими.

Network First

Сначала выполняется сетевой запрос. При сетевой ошибке используется кэшированная версия.

- Преимущество - при доступной сети можно получать актуальные данные.
- Недостаток - медленная или нестабильная сеть увеличивает время ожидания.

Stale While Revalidate

Сразу возвращается кэшированная версия, если она есть, одновременно отправляется сетевой запрос для обновления кэша.

- Преимущество - быстрый ответ и обновление данных в фоне.
- Недостаток - пользователь сначала получает потенциально устаревшую информацию.

Ключевое различие - баланс между скоростью ответа и актуальностью данных.

# Как обновлять Service Worker без потери несохранённых данных?

При обнаружении новой версии Service Worker браузер обычно устанавливает её в фоне и оставляет в состоянии `waiting`, пока старая версия контролирует открытые страницы.

Для безопасного обновления:

1. Обнаружить новую версию через `registration.waiting` или событие `updatefound`.
2. Проверить, есть ли несохранённые пользовательские данные.
3. При необходимости сохранить изменения в `IndexedDB`.
4. Предложить пользователю обновить приложение.
5. После подтверждения отправить новому Service Worker сообщение через `postMessage()`.
6. Вызвать `self.skipWaiting()` для активации новой версии.
7. Обработать `controllerchange` и при необходимости перезагрузить страницу.

Главная опасность - автоматическая перезагрузка вкладки или переключение на несовместимую версию ресурсов при наличии несохранённых изменений.

Само обновление Service Worker обычно не уничтожает состояние формы, но перезагрузка страницы может привести к его потере.

Поэтому `skipWaiting()` не следует автоматически вызывать при каждом обновлении без учёта состояния приложения. Также важно сохранять совместимость старых открытых вкладок с новой версией ресурсов.&#x20;

# Что такое Background Sync и в каких браузерах его поддержка ограничена?

Background Sync API - механизм, позволяющий отложить сетевую операцию и выполнить её через Service Worker, когда браузер определит, что соединение восстановлено.

Например, пользователь отправляет сообщение без интернета. Приложение сохраняет его локально и регистрирует задачу синхронизации:

```
const registration = await navigator.serviceWorker.ready;

await registration.sync.register("sync-messages");
```

Service Worker обрабатывает событие:

```
self.addEventListener("sync", (event) => {
  if (event.tag === "sync-messages") {
    event.waitUntil(sendPendingMessages());
  }
});
```

Поддержка браузеров:

- Chrome, Edge и другие Chromium-браузеры - поддерживают обычный Background Sync.
- Firefox - не поддерживает.
- Safari, включая iOS Safari - не поддерживает.

API не гарантирует немедленное выполнение задачи. Браузер самостоятельно определяет подходящее время и может ограничивать фоновые операции.

Для кроссбраузерной реализации используют резервный механизм: сохраняют операции в `IndexedDB` и повторяют их при восстановлении соединения или следующем открытии приложения.&#x20;

# Как реализовать offline fallback страницу?

Offline fallback - резервная HTML-страница, отображаемая, когда пользователь пытается открыть страницу без подключения к интернету и её содержимое недоступно в кэше.

Реализация:

1. Создать `/offline.html`.
2. Сохранить её в Cache Storage во время установки Service Worker.
3. Перехватывать навигационные запросы.
4. При сетевой ошибке возвращать offline-страницу.

Пример:

```
const CACHE_NAME = "offline-v1";

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => {
      return cache.add("/offline.html");
    })
  );
});

self.addEventListener("fetch", (event) => {
  if (event.request.mode === "navigate") {
    event.respondWith(
      fetch(event.request).catch(() => {
        return caches.match("/offline.html");
      })
    );
  }
});
```

Если навигационный запрос завершится сетевой ошибкой, пользователь увидит сохранённую страницу.

Важно: offline-страница должна быть закэширована заранее. Её ресурсы также должны быть доступны офлайн.

Для SPA можно дополнительно кэшировать основной HTML и JavaScript, чтобы приложение продолжало работать без сети.

# Как доставлять push-уведомления в браузере?

Web Push позволяет серверу отправлять уведомления пользователю даже тогда, когда страница приложения не открыта.

Механизм работы:

1. Приложение регистрирует Service Worker.
2. Пользователь разрешает уведомления через `Notification.requestPermission()`.
3. Через `PushManager.subscribe()` создаётся подписка, содержащая endpoint и ключи шифрования.
4. Подписка передаётся на backend.
5. Backend отправляет зашифрованное сообщение в push-сервис браузера, обычно используя Web Push Protocol и VAPID.
6. Push-сервис доставляет сообщение браузеру.
7. Service Worker получает событие `push` и показывает уведомление через `showNotification()`.

Пример обработчика:

```
self.addEventListener("push", (event) => {
  const data = event.data?.json() ?? {};

  event.waitUntil(
    self.registration.showNotification(
      data.title ?? "Уведомление",
      {
        body: data.body,
        icon: "/icon.png"
      }
    )
  );
});
```

Важные ограничения:

- Требуется HTTPS и разрешение пользователя.
- Разрешение следует запрашивать после действия пользователя.
- Доставка зависит от браузера, ОС и настроек уведомлений.
- На iOS Web Push поддерживается начиная с iOS 16.4 для веб-приложений, добавленных на домашний экран.

Web Push не гарантирует моментальную доставку каждого сообщения.&#x20;

# Какие риски у чрезмерно агрессивного кэширования PWA?

Основные риски:

- Устаревшие данные - пользователь видит информацию, которая уже изменилась на сервере.
- Несовместимость версий - старый HTML может ссылаться на удалённые JavaScript-файлы или работать с изменённым API.
- Неправильная инвалидация - обновления приложения не отображаются из-за сохранённого кэша.
- Переполнение хранилища - большое количество ресурсов расходует дисковое пространство.
- Удаление браузером - браузер может автоматически очищать кэш при нехватке места.
- Утечка данных - приватная информация может остаться доступной в общем кэше после выхода пользователя из аккаунта.
- Некорректная работа с ошибками - закэшированные ответы с ошибками могут продолжать возвращаться вместо актуальных данных.

Основные меры защиты: версионирование кэша, ограничение срока хранения и объёма, удаление старых ресурсов, правильный выбор стратегий для разных запросов.

Особенно важно не кэшировать приватные и персонализированные ответы без контроля доступа и жизненного цикла таких данных.&#x20;

# Как влияет SSR на SEO и время до интерактивности?

SSR (Server-Side Rendering) формирует HTML на сервере и отправляет браузеру уже готовую разметку.

Влияние на SEO:

- Поисковые роботы получают основное содержимое без обязательного выполнения JavaScript.
- Метаданные доступны непосредственно в HTML.
- Упрощается обнаружение ссылок и индексация страниц.

Влияние на производительность:

SSR часто улучшает скорость первоначального отображения содержимого, поскольку браузеру не требуется сначала выполнить JavaScript для создания основной разметки.

Однако SSR не гарантирует быстрое наступление интерактивности.

Например, React-приложению после загрузки HTML может потребоваться hydration - процесс подключения обработчиков событий и восстановления интерактивного состояния компонентов.

Пока необходимый JavaScript не загружен и не выполнен, некоторые элементы страницы могут оставаться неинтерактивными.

Дополнительные особенности:

- SSR может увеличить `TTFB`, поскольку сервер выполняет рендеринг.
- Большой JavaScript-бандл способен задерживать интерактивность.
- Streaming SSR позволяет отправлять HTML частями, не дожидаясь завершения всей страницы.
- Selective Hydration позволяет отдавать приоритет гидратации отдельных частей интерфейса.

Итог: SSR обычно улучшает доступность контента для поисковых роботов и может ускорять первоначальное отображение, но скорость интерактивности зависит от объёма JavaScript, гидратации и архитектуры приложения.&#x20;

# Как реализовать offline-first сохранение пользовательских изменений?

Offline-first - архитектурный подход, при котором приложение сохраняет работоспособность без сети, а синхронизация с сервером выполняется при появлении соединения.

Основной механизм:

1. Локальное сохранение. Изменения пользователя сразу записываются в `IndexedDB`, не дожидаясь ответа сервера.
2. Очередь операций. Каждое изменение добавляется в локальную очередь с идентификатором, типом операции и данными.
3. Мгновенное обновление UI. Пользователь сразу видит результат изменения, даже без интернета.
4. Синхронизация. При доступности сети операции отправляются на сервер через `Background Sync` или обычные запросы.
5. Подтверждение. После успешного ответа сервера операция удаляется из очереди.
6. Обработка конфликтов. Если данные изменились на другом устройстве, приложение применяет выбранную стратегию разрешения конфликтов.

Пример работы:

```
Пользователь изменил заметку
        |
        v
Сохранение в IndexedDB
        |
        v
Обновление интерфейса
        |
        v
Добавление операции в очередь
        |
        v
Появление подключения
        |
        v
Отправка изменений на сервер
        |
        v
Подтверждение и очистка очереди
```

Ключевые технические особенности:

- IndexedDB предпочтительнее `localStorage` для хранения структурированных данных и очереди операций благодаря асинхронности и транзакциям.
- Idempotency Key позволяет избежать дублирования операций при повторной отправке.
- Retry с exponential backoff позволяет повторять временно неудачные запросы без перегрузки сервера.
- Версионирование данных через `ETag`, версии записей или другие механизмы помогает обнаруживать конфликты.
- Conflict Resolution определяет, какие изменения должны сохраниться при одновременном редактировании.

Нельзя полагаться исключительно на `navigator.onLine`: он не гарантирует доступность сервера. Также Background Sync поддерживается не всеми браузерами, поэтому очередь нужно обрабатывать и при обычной работе приложения.

Главный принцип: сначала надёжно сохранить изменения локально, затем синхронизировать их с сервером, не теряя данные при сбоях сети, повторных запросах и конфликтах.
