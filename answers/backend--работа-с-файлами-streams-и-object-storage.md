# Как streaming и buffering отличаются по памяти, задержке и обработке ошибок при работе с файлами?

**Buffering** собирает весь файл или крупный результат в памяти до дальнейшей работы; это проще для небольших данных, но память растёт с размером и числом одновременных операций. **Streaming** передаёт части постепенно и уменьшает необходимость полного буфера.

Поток тоже использует память: важны внутренние очереди и потребители. После отправки части файла уже нельзя заменить результат обычным сообщением об ошибке. Выбор учитывает максимальный размер, преобразования, возможность повтора и допустимость частичного ответа.

# Как передавать файл через stream pipeline с backpressure и общей отменой?

Этапы соединяют через механизм, который передаёт ошибки, соблюдает backpressure и закрывает участников при отказе. Например, Promise API Node.js позволяет вызвать `await pipeline(source, transform, destination, { signal })` из `node:stream/promises`.

Медленный destination должен замедлять source, а общая отмена — прерывать чтение и преобразования, если они её поддерживают. Память ограничивают на каждом этапе; `highWaterMark` не является жёстким лимитом всей операции. Ошибка pipeline с HTTP-response может уже закрыть соединение. [Streams API Node.js](https://nodejs.org/api/stream.html).

# Как ограничивать multipart upload и проверять имя, тип и содержимое файла?

Ограничивают общий размер, число parts, размеры отдельных полей и файлов, время получения и допустимую конкурентность. Клиентское имя не используют как доверенный путь: генерируют собственный key и исключают path traversal и перезапись чужих объектов.

Extension и `Content-Type` проверяют, но не считают доказательством формата; исследуют содержимое и при необходимости сканируют или декодируют его в ограниченной среде. Файл держат недоступным до завершения проверки. Распаковка требует контроля итогового объёма и путей. [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

# Как организовать прямую загрузку в Object Storage через ограниченное разрешение backend?

Backend проверяет пользователя, tenant, квоту и намерение, создаёт upload ID и выдаёт короткое разрешение на нужный object key и операцию. Клиент передаёт байты напрямую хранилищу, снижая нагрузку на сервер приложения.

После загрузки backend самостоятельно проверяет наличие, размер, checksum и статус проверки содержимого. Клиентское «успешно загружено» не является доказательством. Разрешение может допускать повторную запись до истечения срока, поэтому публикацию связывают с проверенной версией или отдельным окончательным объектом, а не с изменяемым quarantine key.

# Как multipart upload и resumable upload восстанавливают передачу большого файла?

Файл разбивают на части и сохраняют идентификатор загрузки, номера и подтверждения частей. После обрыва выясняют уже принятые части и повторяют недостающие, затем отдельно подтверждают сборку итогового объекта.

Разные протоколы определяют resume по part number или offset, поэтому клиент и backend должны использовать один контракт. Части проверяют по целостности, ограничивают параллелизм и очищают незавершённые загрузки. В S3 создание multipart upload, передача частей и complete являются отдельными этапами. [Multipart upload S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html).

# Как согласовать запись metadata в БД и загрузку объекта без общей транзакции?

Используют состояния, например `Pending → Uploaded → Verified → Available`, и стабильный upload ID. Объект сначала попадает в staging/quarantine, затем после проверки metadata атомарно переводятся в доступное состояние в БД.

Если один шаг упал, повтор или reconciliation сопоставляет запись и объект по идентификатору. Осиротевший объект очищают по политике, а запись без объекта не выдают как готовый файл. Удаление тоже требует восстановления: локальный commit и Object Storage API не становятся одной транзакцией автоматически.

# Как Object Storage keys, versioning и checksums помогают обеспечить целостность файла?

Object key выбирают стабильным и изолированным по назначению и владельцу, не полагаясь на пользовательское имя. Versioning позволяет различать перезаписи и ссылаться на конкретную проверенную версию. Checksum проверяет целостность переданных байтов при подходящем алгоритме и способе вычисления.

`ETag` не следует автоматически считать MD5 всего файла: multipart upload, шифрование и реализация хранилища меняют его смысл. Совпадение checksum не подтверждает безопасность содержимого или права пользователя. Для важных операций сохраняют размер, алгоритм, checksum и version ID.

# Как выдавать приватный файл через proxy, signed URL или CDN с учётом прав?

Proxy позволяет проверять доступ при каждом запросе, но пропускает трафик через приложение. Signed URL передаёт скачивание хранилищу на ограниченное время; CDN добавляет кэширование и собственные механизмы подписи и invalidation.

Доступ к выдаче разрешения проверяют на backend. Уже выданная ссылка может оставаться рабочей до истечения срока, даже если пользователь вышел из системы. Cache key и policies не должны смешивать приватные варианты. Учитывают tenant, срок, версию объекта и требования к немедленному отзыву.

# Как Range requests и Content-Disposition влияют на скачивание и возобновление?

`Range` позволяет запросить часть представления; поддерживающий сервер обычно возвращает `206` с `Content-Range`, а недопустимый диапазон — `416`. Для безопасного продолжения нужно убедиться, что файл не изменился, например через подходящий validator и `If-Range`.

`Content-Disposition` задаёт inline/attachment и имя скачивания. Имя кодируют корректно и не допускают header injection. Поддержку диапазонов проверяют по всему пути через proxy/CDN, а большое число мелких диапазонов ограничивают, чтобы не создать лишнюю нагрузку.

# Как генерировать большой CSV или архив потоком и обрабатывать частичный результат?

Данные читают ограниченными порциями или cursor, преобразуют и отправляют с backpressure. Не следует сначала загружать весь набор из БД в массив: это уничтожает преимущество потоковой выдачи. Для согласованного экспорта задают snapshot или явно допускают изменения данных.

В CSV корректно экранируют разделители и учитывают формулы при открытии в spreadsheet. Архив при обрыве может оказаться непригодным целиком. Для долгой генерации часто удобнее фоновая задача, завершённый объект в storage и выдача ссылки после проверки успеха.

# Как проектировать TTL, lifecycle и очистку временных или осиротевших объектов?

Разделяют временные загрузки, опубликованные файлы, старые версии и незавершённые multipart sessions. TTL и lifecycle задают по назначению; удаление должно учитывать активные операции, references и согласованность с metadata.

Cleanup запускают идемпотентно с достаточным grace period, чтобы не удалить объект между загрузкой и финализацией. Orphan detection проверяет обе стороны, а не только возраст key. Versioning и retention могут сохранять старые данные и расходы после обычного delete; их правила учитывают отдельно.

# Как наблюдать и тестировать файловые операции при медленном клиенте, обрыве и повреждении данных?

Измеряют размер, длительность, throughput, память, число активных потоков, отмены, ошибки checksums и возраст незавершённых загрузок. Логи связывают с upload ID, не раскрывая signed URLs и секреты.

Проверки включают медленный consumer, разрыв посередине, неверную часть, недостаток места, отказ storage и повтор финализации. Проверяют не только статус, но и cleanup ресурсов, целостность итоговых байтов и отсутствие публикации непроверенного файла. Для streaming-ошибки клиент должен отличать неполный результат от успешного.
