# Как сравнить `map`, `forEach`, `filter`, `reduce` и `flatMap`?

Все методы перебирают массив, но отличаются назначением и возвращаемым результатом.

- `map()` - преобразует каждый элемент и возвращает новый массив той же длины.
- `forEach()` - выполняет функцию для каждого элемента, возвращает `undefined`. Обычно используется для побочных эффектов.
- `filter()` - возвращает новый массив только с элементами, удовлетворяющими условию.
- `reduce()` - последовательно накапливает результат в аккумуляторе. Позволяет получить число, объект, массив или другое значение.
- `flatMap()` - выполняет преобразование, затем разворачивает результат на один уровень вложенности. Удобен, когда один элемент может порождать несколько элементов или ни одного.

```
const numbers = [1, 2, 3];

numbers.map(x => x * 2);         // [2, 4, 6]
numbers.forEach(x => console.log(x)); // undefined
numbers.filter(x => x > 1);      // [2, 3]
numbers.reduce((sum, x) => sum + x, 0); // 6
numbers.flatMap(x => [x, x * 2]); // [1, 2, 2, 4, 3, 6]
```

Все пять методов не изменяют структуру исходного массива напрямую, но callback может изменять его элементы или вложенные объекты.

Особенности: методы пропускают пустые слоты разреженных массивов. `map()` сохраняет их, а `filter()` и `flatMap()` формируют плотный результат. `reduce()` без начального значения выбрасывает `TypeError`, если массив не содержит элементов.

# Чем `find()` отличается от `filter()`?

`find()` возвращает первый элемент, удовлетворяющий условию, и прекращает поиск. Если совпадений нет, возвращает `undefined`.

`filter()` проверяет все элементы и возвращает новый массив со всеми совпадениями. Если совпадений нет, возвращает `[]`.

```
const users = [
  { id: 1, active: true },
  { id: 2, active: false },
  { id: 3, active: true }
];

users.find(user => user.active);
// { id: 1, active: true }

users.filter(user => user.active);
// [{ id: 1, active: true }, { id: 3, active: true }]
```

`find()` предпочтительнее, когда нужен один элемент: он может завершиться раньше и не создаёт массив результатов.

Оба метода имеют временную сложность O(n) в худшем случае. `filter()` дополнительно выделяет память под результирующий массив.

# Чем `some()` отличается от `every()`?

Оба метода проверяют элементы массива и возвращают `boolean`.

- `some()` возвращает `true`, если хотя бы один элемент удовлетворяет условию.
- `every()` возвращает `true`, только если все элементы удовлетворяют условию.

```
const numbers = [2, 4, 7];

numbers.some(x => x % 2 !== 0);  // true
numbers.every(x => x % 2 === 0); // false
```

Оба используют короткое замыкание (short-circuit evaluation):

- `some()` останавливается на первом `true`.
- `every()` останавливается на первом `false`.

Для пустого массива `some()` возвращает `false`, а `every()` - `true`, поскольку нет ни одного элемента, нарушающего условие.

Методы не мутируют массив самостоятельно и имеют сложность O(n) в худшем случае.

# Как работают `slice()`, `splice()` и `toSpliced()`?

`slice(start, end)` возвращает часть массива от `start` включительно до `end` исключительно, не изменяя оригинал.

`splice(start, deleteCount, ...items)` изменяет исходный массив: удаляет, заменяет или вставляет элементы. Возвращает массив удалённых элементов.

`toSpliced(start, deleteCount, ...items)` выполняет аналогичное `splice()` преобразование, но возвращает новый массив и не мутирует исходный.

```
const arr = [1, 2, 3, 4];

arr.slice(1, 3);       // [2, 3]
arr;                   // [1, 2, 3, 4]

arr.splice(1, 2, 9);   // [2, 3]
arr;                   // [1, 9, 4]

arr.toSpliced(1, 1, 8); // [1, 8, 4]
arr;                    // [1, 9, 4]
```

У всех трёх методов отрицательный `start` отсчитывается от конца массива.

Важные особенности:

- `slice()` создаёт поверхностную копию: вложенные объекты остаются общими.
- `splice()` возвращает удалённые элементы, а не изменённый массив.
- `toSpliced()` доступен начиная с ECMAScript 2023 и создаёт новый массив с поверхностным копированием элементов.

# Какие методы массива мутируют исходный массив?

Мутирующие методы изменяют содержимое или порядок элементов исходного массива.

Основные:

- `push()` - добавляет элементы в конец.
- `pop()` - удаляет последний элемент.
- `unshift()` - добавляет элементы в начало.
- `shift()` - удаляет первый элемент.
- `splice()` - удаляет, вставляет или заменяет элементы.
- `sort()` - сортирует массив на месте.
- `reverse()` - меняет порядок элементов на обратный.
- `fill()` - заполняет диапазон указанным значением.
- `copyWithin()` - копирует часть массива в другую позицию внутри него.

Немутирующие альтернативы:

| Мутирующий метод     | Немутирующая альтернатива |
|----------------------|---------------------------|
| `sort()`             | `toSorted()`              |
| `reverse()`          | `toReversed()`            |
| `splice()`           | `toSpliced()`             |
| `arr[index] = value` | `with(index, value)`      |

Немутирующие методы создают новые массивы, но обычно выполняют поверхностное копирование, сохраняя ссылки на вложенные объекты.

Методы `map()`, `filter()` и `slice()` также не мутируют исходный массив самостоятельно.

# Чем `sort()` отличается от `toSorted()`?

Оба метода сортируют элементы, используя одинаковые правила сравнения.

`sort()` изменяет исходный массив и возвращает ссылку на него.

`toSorted()` создаёт новый отсортированный массив, оставляя исходный без изменений.

```
const numbers = [3, 1, 2];

const sorted = numbers.toSorted((a, b) => a - b);

console.log(sorted);  // [1, 2, 3]
console.log(numbers); // [3, 1, 2]

numbers.sort((a, b) => a - b);

console.log(numbers); // [1, 2, 3]
```

Особенности:

- Без компаратора оба метода сортируют элементы по строковому представлению.
- Современный стандарт ECMAScript гарантирует стабильную сортировку: элементы, которые компаратор считает равными, сохраняют взаимный порядок.
- `toSorted()` выполняет поверхностное копирование и доступен начиная с ECMAScript 2023.
- `sort()` сохраняет пустые слоты разреженных массивов и перемещает их в конец, а `toSorted()` преобразует такие слоты в `undefined`.

# Почему числовая сортировка через `sort()` требует компаратор?

По умолчанию `sort()` преобразует элементы в строки и сравнивает их лексикографически по последовательностям UTF-16 code units.

```
[10, 2, 100, 5].sort();
// [10, 100, 2, 5]
```

Для числовой сортировки передают компаратор:

```
const numbers = [10, 2, 100, 5];

numbers.sort((a, b) => a - b);
// [2, 5, 10, 100]

numbers.sort((a, b) => b - a);
// [100, 10, 5, 2]
```

Компаратор должен возвращать:

- Отрицательное число - `a` располагается перед `b`.
- Положительное число - `b` располагается перед `a`.
- `0` или `NaN` - элементы считаются равными по порядку сортировки.

Корректный компаратор должен быть детерминированным, согласованным и не нарушать транзитивность сравнения. Иначе результат сортировки может зависеть от реализации движка.

# Чем `includes()` отличается от `indexOf()`?

`includes()` проверяет наличие значения и возвращает `boolean`.

`indexOf()` ищет первое вхождение и возвращает его индекс либо `-1`, если элемент отсутствует.

Главное техническое отличие - алгоритм сравнения:

- `includes()` использует SameValueZero, поэтому распознаёт `NaN`.
- `indexOf()` использует строгое равенство (`===`), при котором `NaN` не равен самому себе.

```
const arr = [10, NaN, 30];

arr.includes(NaN); // true
arr.indexOf(NaN);  // -1

arr.includes(30);  // true
arr.indexOf(30);   // 2
```

Дополнительное отличие: `includes()` воспринимает пустые слоты разреженного массива как `undefined`, а `indexOf()` их пропускает.

Оба метода выполняют линейный поиск O(n) и сравнивают объекты по ссылке, а не по содержимому.

# Как эффективно удалить дубликаты из массива?

Для массива примитивов обычно используют `Set`, поскольку он хранит только уникальные значения.

```
const numbers = [1, 2, 2, 3, 1];

const unique = [...new Set(numbers)];
// [1, 2, 3]
```

`Set` использует сравнение SameValueZero: считает `NaN` равным `NaN`, а `+0` и `-0` одинаковыми. Порядок первого появления элементов сохраняется.

Средняя временная сложность - O(n), дополнительная память - O(n).

Для объектов есть ограничение: сравнение выполняется по ссылке, поэтому объекты с одинаковыми полями остаются разными элементами.

Если требуется уникальность по `id`, можно использовать `Map`:

```
const users = [
  { id: 1, name: "Alex" },
  { id: 1, name: "John" },
  { id: 2, name: "Kate" }
];

const unique = [
  ...new Map(users.map(user => [user.id, user])).values()
];
```

В этом примере при повторяющихся `id` сохраняется последний объект с данным идентификатором, а порядок ключей определяется их первым появлением.

# Как построить словарь элементов по идентификатору?

Словарь позволяет получать элемент по идентификатору без перебора всего массива.

Основные варианты - `Map` и обычный объект.

Через `Map`:

```
const users = [
  { id: 1, name: "Alex" },
  { id: 2, name: "Kate" }
];

const usersById = new Map(
  users.map(user => [user.id, user])
);

usersById.get(2);
// { id: 2, name: "Kate" }
```

Через `Object.fromEntries()`:

```
const usersById = Object.fromEntries(
  users.map(user => [user.id, user])
);

usersById[2];
// { id: 2, name: "Kate" }
```

Различия:

- `Map` поддерживает ключи любого типа, включая объекты.
- `Object` использует только строковые и символьные ключи, поэтому числовые идентификаторы преобразуются в строки.
- `Map` предоставляет удобные методы `get()`, `set()`, `has()` и свойство `size`.
- Обычный объект удобен для JSON-подобных структур и доступа через `obj[id]`.

Построение словаря занимает в среднем O(n), последующий поиск - в среднем O(1).

При повторяющихся идентификаторах более поздний элемент перезаписывает значение предыдущего.

# Как сгруппировать массив объектов по ключу?

Группировка преобразует массив в структуру, где каждому значению ключа соответствует массив подходящих элементов.

В современном JavaScript для этого предназначен `Object.groupBy()`:

```
const users = [
  { name: "Alex", role: "admin" },
  { name: "Kate", role: "user" },
  { name: "John", role: "admin" }
];

const grouped = Object.groupBy(
  users,
  user => user.role
);

// {
//   admin: [
//     { name: "Alex", role: "admin" },
//     { name: "John", role: "admin" }
//   ],
//   user: [
//     { name: "Kate", role: "user" }
//   ]
// }
```

Существует также `Map.groupBy()`, который возвращает `Map` и позволяет группировать по ключам любого типа, включая объекты.

Оба метода стандартизированы в ECMAScript 2024. `Object.groupBy()` создаёт объект с `null`-прототипом, а ключи приводит к строкам или символам.

До появления этих методов группировку часто реализовывали через `reduce()`.

Средняя временная сложность группировки - O(n). Сами объекты элементов не копируются: массивы групп содержат ссылки на исходные объекты.

# Чем `Array.from()` отличается от spread для преобразования коллекции?

Оба способа могут преобразовывать итерируемые объекты в массивы, но имеют разные возможности.

Spread (`...`) разворачивает элементы итерируемого объекта:

```
const set = new Set([1, 2, 3]);

const arr = [...set];
// [1, 2, 3]
```

`Array.from()` поддерживает как итерируемые, так и массивоподобные объекты с `length` и индексами:

```
const arrayLike = {
  0: "a",
  1: "b",
  length: 2
};

Array.from(arrayLike);
// ["a", "b"]
```

Кроме того, `Array.from()` поддерживает преобразование элементов через второй аргумент:

```
Array.from([1, 2, 3], x => x * 2);
// [2, 4, 6]
```

Это позволяет выполнить преобразование без промежуточного массива, который возник бы при `[...source].map(...)`.

Главное различие: spread требует итерируемый объект, а `Array.from()` дополнительно работает с массивоподобными структурами и поддерживает встроенную функцию преобразования.

# Как работают Unicode code points и surrogate pairs в строках?

JavaScript хранит строки в виде последовательности UTF-16 code units - 16-битных кодовых единиц.

Unicode code point - числовой идентификатор символа Unicode. Для его представления в UTF-16 используется:

- Одна кодовая единица для значений от `U+0000` до `U+FFFF`, кроме диапазона суррогатов.
- Две кодовые единицы (surrogate pair) для значений от `U+10000` до `U+10FFFF`.

Из-за этого `string.length` возвращает количество кодовых единиц, а не Unicode code points или визуальных символов.

```
const str = "😀";

str.length;        // 2
str[0];            // первая половина surrogate pair

str.charCodeAt(0); // 55357
str.codePointAt(0); // 128512
```

`for...of` и строковый итератор учитывают surrogate pairs:

```
[..."😀"].length; // 1
```

Но даже один code point не всегда соответствует одному визуальному символу. Например, `e` с комбинируемым акцентом может состоять из двух code points, а emoji с модификаторами - из нескольких.

Для разделения строки на графемные кластеры (визуально воспринимаемые символы) применяется `Intl.Segmenter` с `granularity: "grapheme"`.

# Чем `slice()` отличается от `substring()` для строк?

Оба метода извлекают подстроку, не изменяя исходную строку.

`slice(start, end)` поддерживает отрицательные индексы, отсчитывая позиции от конца.

`substring(start, end)` преобразует отрицательные индексы в `0` и меняет аргументы местами, если `start > end`.

```
const str = "JavaScript";

str.slice(0, 4);      // "Java"
str.substring(0, 4);  // "Java"

str.slice(-6);        // "Script"
str.substring(-6);    // "JavaScript"

str.slice(5, 2);      // ""
str.substring(5, 2);  // "vaS"
```

Оба метода исключают символ с индексом `end` и используют индексы UTF-16 code units, поэтому могут разрезать surrogate pair посередине.

На практике `slice()` обычно предпочтительнее, поскольку поддерживает отрицательные индексы и не переставляет границы автоматически.

# Как работают регулярные выражения и флаги `g`, `i`, `m`, `u`?

RegExp - механизм сопоставления строк с шаблоном. Регулярные выражения используются для поиска, проверки формата, извлечения и замены фрагментов текста.

```
const regex = /\bcat\b/gi;

"Cat and cat".match(regex);
// ["Cat", "cat"]
```

Основные флаги:

- `g` (global) - позволяет находить все совпадения, а не только первое. При использовании `exec()` или `test()` влияет на состояние поиска через `lastIndex`.
- `i` (ignoreCase) - включает регистронезависимое сравнение.
- `m` (multiline) - изменяет работу `^` и `$`, позволяя им соответствовать началу и концу отдельных строк внутри текста.
- `u` (unicode) - включает Unicode-aware режим: корректную обработку code points за пределами BMP, запись `\u{...}` и более строгий разбор шаблона.

Пример `m`:

```
const text = "hello\nworld";

text.match(/^world/);  // null
text.match(/^world/m); // ["world"]
```

Важный нюанс: флаг `g` делает регулярное выражение состояниезависимым при использовании `test()` и `exec()`:

```
const regex = /a/g;

regex.test("a"); // true
regex.test("a"); // false
regex.test("a"); // true
```

Это происходит из-за изменения `lastIndex`.

Флаг `m` не заставляет точку `.` соответствовать символу перевода строки. Для этого существует отдельный флаг `s` (dotAll).

# Что такое жадные и ленивые квантификаторы в RegExp?

Квантификаторы определяют, сколько раз может повторяться часть регулярного выражения:

- `*` - от нуля до бесконечности.
- `+` - от одного до бесконечности.
- `?` - ноль или один раз.
- `{n,m}` - от `n` до `m` повторений.

По умолчанию квантификаторы жадные (greedy) - пытаются захватить максимально возможное количество символов, при котором весь шаблон может совпасть.

Добавление `?` делает квантификатор ленивым (lazy) - он сначала пытается захватить минимум символов.

```
const str = "<b>Hello</b>";

str.match(/<.*>/);
// ["<b>Hello</b>"]

str.match(/<.*?>/);
// ["<b>"]
```

Жадные квантификаторы сначала пытаются захватить больше текста, ленивые - меньше, но оба могут расширять или сокращать совпадение через backtracking, чтобы удовлетворить остальную часть шаблона.

Ленивый квантификатор не гарантирует отсутствие backtracking и не обязательно работает быстрее.

# Как устроены объекты `Date` и часовые пояса?

`Date` хранит момент времени как количество миллисекунд, прошедших с 1 января 1970 года, 00:00:00 UTC (Unix epoch). Внутреннее значение не содержит часовой пояс.

```
const date = new Date("2025-01-01T12:00:00Z");

date.getTime(); 
// 1735732800000
```

`Date` предоставляет два набора методов:

- `getFullYear()`, `getHours()` и аналогичные - возвращают компоненты даты в локальном часовом поясе окружения.
- `getUTCFullYear()`, `getUTCHours()` и аналогичные - возвращают компоненты в UTC.

```
const date = new Date("2025-01-01T12:00:00Z");

date.getUTCHours(); // 12
date.getHours();    // зависит от часового пояса окружения
```

Ключевые особенности:

- `Date` представляет конкретный момент времени, а не календарную дату или часовой пояс.
- `toISOString()` возвращает строку в UTC.
- `getTimezoneOffset()` вычисляет разницу между UTC и локальным временем для конкретной даты.
- Локальное смещение может изменяться из-за перехода на летнее или зимнее время (DST).
- Для отображения времени в конкретном часовом поясе можно использовать `Intl.DateTimeFormat` с параметром `timeZone`.

# Почему хранение времени в локальном часовом поясе может быть проблемой?

Локальное время само по себе не всегда однозначно определяет момент времени.

Например, `2025-10-26 02:30` в часовом поясе `Europe/Berlin` встречается дважды из-за перехода с летнего времени на зимнее.

Основные проблемы:

- DST-переходы: некоторые локальные часы повторяются или вообще не существуют.
- Разные часовые пояса: одинаковые локальные значения соответствуют разным моментам времени.
- Изменение правил: государства могут менять смещения и даты переходов.
- Потеря контекста: сохранённое значение `2025-01-01 12:00` не указывает, в каком часовом поясе оно было задано.

Для событий, произошедших в конкретный момент, обычно сохраняют UTC timestamp или ISO 8601 со смещением.

```
"2025-01-01T12:00:00Z"
```

Но для будущих событий, привязанных к местному времени, например «каждый день в 09:00 по Берлину», одного UTC timestamp недостаточно.

В таком случае необходимо сохранять локальное время и идентификатор IANA time zone, например `Europe/Berlin`, чтобы корректно учитывать будущие изменения смещения.

# Как использовать `Intl.DateTimeFormat`, `Intl.NumberFormat` и `Intl.Collator`?

`Intl` предоставляет API интернационализации для форматирования и сравнения данных с учётом локали.

### `Intl.DateTimeFormat`

Форматирует даты с учётом локали, часового пояса и настроек отображения.

```
const formatter = new Intl.DateTimeFormat("ru-RU", {
  dateStyle: "long",
  timeZone: "Europe/Moscow"
});

formatter.format(new Date("2025-01-01T12:00:00Z"));
// "1 января 2025 г."
```

### `Intl.NumberFormat`

Форматирует числа, валюты, проценты и другие числовые значения.

```
const formatter = new Intl.NumberFormat("ru-RU", {
  style: "currency",
  currency: "RUB"
});

formatter.format(1500);
// "1 500,00 ₽"
```

Точные пробелы и формат отображения могут зависеть от версии локализационных данных окружения.

### `Intl.Collator`

Сравнивает строки с учётом языковых правил сортировки.

```
const collator = new Intl.Collator("ru-RU");

const words = ["Яблоко", "Арбуз", "Банан"];

words.sort(collator.compare);
// ["Арбуз", "Банан", "Яблоко"]
```

В отличие от стандартного строкового сравнения, `Intl.Collator` учитывает правила конкретного языка.

Практический нюанс: при форматировании большого количества значений эффективнее создать экземпляр форматтера один раз и повторно использовать его, чем создавать новый для каждого элемента.

# Какие ошибки возникают при использовании локального часового пояса?

Основные ошибки связаны с тем, что разработчики смешивают момент времени (instant), календарную дату и локальное представление.

1\. Неоднозначный парсинг даты.

```
new Date("2025-01-01");
// Интерпретируется как 00:00 UTC

new Date("2025-01-01T00:00:00");
// Интерпретируется как локальное время
```

Из-за этого одинаковая календарная дата может соответствовать разным моментам времени.

2\. Смещение календарной даты при отображении.

```
const date = new Date("2025-01-01");

date.getDate();
// Может вернуть 31 в часовом поясе западнее UTC
```

Причина - строка без времени интерпретируется как полночь UTC, а `getDate()` использует локальный часовой пояс.

3\. Ошибки при переходе на летнее и зимнее время.

Локальное время может быть несуществующим или неоднозначным. Например, при переводе часов вперёд время `02:30` может не существовать.

4\. Прибавление фиксированных 24 часов вместо календарного дня.

```
const nextDay = new Date(
  date.getTime() + 24 * 60 * 60 * 1000
);
```

Такой код прибавляет ровно 24 часа, но при DST-переходе следующий календарный день в локальном времени может начинаться через 23 или 25 часов.

5\. Использование смещения вместо полноценного часового пояса.

`UTC+1` не эквивалентен `Europe/Berlin`, поскольку у Берлина смещение меняется в течение года.

6\. Неправильная интерпретация `toISOString()`.

Метод всегда возвращает время в UTC, поэтому календарная дата может отличаться от локальной.

Для предотвращения ошибок необходимо различать три сущности: конкретный момент времени, календарную дату и локальное время с часовым поясом. Для сложных сценариев полезна модель типов `Temporal`, в частности `Instant`, `PlainDate` и `ZonedDateTime`, с учётом поддержки API в целевых окружениях.
