# Как обеспечить доступность сложного UI Kit?

Доступность UI Kit нужно закладывать на уровне компонентов, а не исправлять отдельно в каждом приложении.

Основные требования:

- Семантика - использовать нативные HTML-элементы, корректные ARIA-роли, состояния и доступные названия.
- Клавиатура - поддерживать навигацию, управление и видимый индикатор фокуса.
- Управление фокусом - правильно перемещать и восстанавливать фокус в модальных окнах, меню и других интерактивных компонентах.
- Визуальная доступность - обеспечивать контрастность, масштабирование текста, различимость состояний и поддержку `prefers-reduced-motion`.
- Тестирование - проверять компоненты через `axe-core`, клавиатуру и скринридеры.

Для сложных компонентов используют паттерны WAI-ARIA Authoring Practices. Доступное поведение должно входить в API компонентов по умолчанию.

Обычно ориентируются на WCAG 2.2 AA, но соответствие всего приложения зависит также от правильного использования компонентов и контента.

# Что такое WCAG и какие у неё основные принципы?

WCAG (Web Content Accessibility Guidelines) - международные рекомендации W3C по обеспечению доступности веб-контента.

Основываются на четырёх принципах POUR:

1. Perceivable (Воспринимаемость) - информация должна быть доступна разными способами: текстовые альтернативы, субтитры, достаточная контрастность.
2. Operable (Управляемость) - интерфейс должен работать с клавиатурой, предоставлять достаточно времени и не создавать препятствий для навигации.
3. Understandable (Понятность) - содержимое и поведение интерфейса должны быть предсказуемыми, а ошибки - понятными.
4. Robust (Надёжность) - контент должен корректно интерпретироваться браузерами и вспомогательными технологиями.

WCAG определяет три уровня соответствия: A (базовый), AA (повышенный) и AAA (наиболее строгий).

На практике часто ориентируются на WCAG 2.2 AA, который включает требования уровней A и AA.&#x20;

# Почему семантическая HTML-разметка помогает доступности?

Семантические HTML-элементы передают браузеру и вспомогательным технологиям информацию о назначении и структуре контента.

Например:

- `<nav>` - навигационная область.
- `<main>` - основное содержимое страницы.
- `<button>` - интерактивная кнопка.
- `<label>` - название элемента формы.
- `<h1>`-`<h6>` - иерархия заголовков.

Браузер преобразует семантику в Accessibility Tree, через которое скринридеры получают роли, названия, состояния и другую информацию об элементах.

Нативные элементы также предоставляют встроенное поведение. Например, `<button>` поддерживает управление клавиатурой без дополнительного JavaScript.

# Чем нативный `button` лучше кликабельного `div`?

`<button>` изначально является интерактивным элементом и предоставляет:

- Семантику - скринридер распознаёт его как кнопку.
- Клавиатурное управление - активация через `Enter` и `Space`.
- Фокусировку - автоматически участвует в последовательности `Tab`.
- Состояния - поддерживает `disabled` и другие стандартные атрибуты.
- Интеграцию с формами - поддерживает `type="submit"`, `type="reset"` и `type="button"`.

Для кликабельного `<div>` пришлось бы вручную реализовать `role="button"`, `tabindex="0"`, обработчики клавиатуры и соответствующие состояния.

Правило: если существует подходящий нативный HTML-элемент, предпочтительно использовать его.

# Как обеспечить управление интерфейсом только клавиатурой?

Все интерактивные действия должны быть доступны без мыши.

Основные механизмы:

- `Tab` и `Shift + Tab` - перемещение между фокусируемыми элементами.
- `Enter` и `Space` - активация кнопок и других элементов согласно их поведению.
- `Arrow Keys` - навигация внутри сложных компонентов, например вкладок или меню.
- `Escape` - закрытие модальных окон и всплывающих компонентов.
- `Home` и `End` - переход к началу или концу набора элементов там, где это предусмотрено паттерном.

Необходимо сохранять логичный порядок фокуса, показывать его через `:focus-visible` и предотвращать ситуации, когда пользователь не может покинуть компонент с клавиатуры (keyboard trap).

Для повторяющейся навигации полезны ссылки пропуска, например «Перейти к основному содержимому».

# Что такое focus order и tabindex?

Focus order - последовательность перемещения клавиатурного фокуса между элементами интерфейса.

По умолчанию браузер определяет её на основе DOM и правил фокусируемости элементов.

Атрибут `tabindex` позволяет управлять участием элемента в этой последовательности:

- `tabindex="0"` - добавляет элемент в обычную последовательность `Tab`.
- `tabindex="-1"` - исключает из последовательности `Tab`, но позволяет установить фокус программно через `.focus()`.
- `tabindex="1"` и больше - задаёт приоритетный порядок фокуса, что обычно приводит к непредсказуемой навигации и не рекомендуется.

В сложных компонентах применяют roving tabindex: один элемент получает `tabindex="0"`, остальные `-1`, а перемещение между ними осуществляется стрелками.

Важно: визуальный порядок элементов должен соответствовать логическому порядку фокуса. Перестановка элементов через CSS не обязательно изменяет порядок клавиатурной навигации.

# Когда используют `aria-label`, `aria-labelledby` и `aria-describedby`?

Эти атрибуты позволяют предоставлять элементам доступные названия и описания.

- `aria-label` - задаёт доступное название непосредственно строкой. Например, `aria-label="Закрыть"` для кнопки с одной иконкой.
- `aria-labelledby` - формирует доступное название из текста других элементов по их `id`. Подходит, когда название уже присутствует на странице.
- `aria-describedby` - связывает элемент с дополнительным описанием, например подсказкой или сообщением об ошибке.

Ключевое отличие: `aria-label` и `aria-labelledby` определяют, что это за элемент, а `aria-describedby` объясняет дополнительную информацию о нём.

Для обычных полей формы предпочтительно использовать нативный `<label>`. Если видимое название уже существует, обычно лучше ссылаться на него через `aria-labelledby`, чем дублировать текст в `aria-label`.

# Чем `role` отличается от HTML-семантики?

HTML-семантика определяет назначение элемента и зачастую предоставляет встроенное поведение браузера.

`role` - ARIA-атрибут, который сообщает вспомогательным технологиям семантическую роль элемента.

Например, `role="button"` позволяет представить `<div>` как кнопку в Accessibility Tree, но не добавляет поддержку `Enter`, `Space`, фокусировку или поведение настоящей кнопки.

Таким образом:

- HTML предоставляет семантику и нативное поведение.
- ARIA позволяет уточнять или задавать семантику, состояния и связи.
- ARIA не заменяет реализацию интерактивного поведения.

Предпочтение всегда следует отдавать нативной HTML-семантике, используя ARIA там, где её недостаточно.

# Как правильно реализовать диалог с фокус-ловушкой?

Focus trap - механизм, удерживающий клавиатурный фокус внутри модального окна, пока оно открыто.

Правильный модальный диалог должен:

1. Иметь `role="dialog"`, `aria-modal="true"` и доступное название через `aria-labelledby` или `aria-label`.
2. Перемещать фокус внутрь после открытия.
3. Удерживать `Tab` и `Shift + Tab` внутри диалога.
4. Поддерживать закрытие через `Escape` и предоставлять видимую кнопку закрытия.
5. Делать фоновые элементы недоступными для взаимодействия.
6. Восстанавливать фокус после закрытия.

Предпочтительный вариант - нативный `<dialog>` с `showModal()`. Браузер самостоятельно обеспечивает модальность, блокировку фонового содержимого и управление последовательностью фокуса. При этом нужно правильно выбрать начальный фокус и проверить поведение закрытия.

Для самописных диалогов необходимо самостоятельно обеспечить все перечисленные механизмы.&#x20;

# Как обеспечить возврат фокуса после закрытия модального окна?

Перед открытием модального окна необходимо сохранить элемент, который его вызвал, обычно через `document.activeElement`.

После закрытия следует вызвать у сохранённого элемента `.focus()`.

В React для хранения ссылки можно использовать `useRef`.

Важные нюансы:

- Возвращать фокус нужно после того, как фоновый интерфейс снова станет доступным.
- Если исходный элемент удалён из DOM, фокус следует переместить на логически подходящий элемент.
- Если действие внутри диалога изменило интерфейс, новым фокусом может стать результат этого действия.

Например, после создания записи логично сфокусировать созданную запись, а не обязательно кнопку «Создать».

# Что такое live region и `aria-live`?

Live region - область страницы, изменения содержимого которой могут автоматически озвучиваться скринридером без перемещения фокуса.

Атрибут `aria-live` управляет приоритетом объявлений:

- `aria-live="polite"` - изменения озвучиваются при удобной возможности, не прерывая текущую речь.
- `aria-live="assertive"` - важные изменения могут прерывать текущее объявление.
- `aria-live="off"` - изменения не объявляются автоматически только благодаря этому атрибуту.

Пример:

```
<div aria-live="polite">
  Данные успешно сохранены
</div>
```

Для сообщений о статусе также используют `role="status"`, для срочных ошибок - `role="alert"`.

Важный нюанс: live region желательно создавать заранее, а затем обновлять её содержимое. Это повышает надёжность озвучивания изменений.

# Как озвучивать ошибки формы экранному диктору?

Ошибки должны быть видимыми, понятными и программно связанными с соответствующими полями.

Основные механизмы:

- `aria-invalid="true"` - указывает, что значение поля невалидно.
- `aria-describedby` - связывает поле с текстом ошибки.
- `aria-errormessage` - позволяет явно связать невалидное поле с сообщением об ошибке.
- `role="alert"` или `aria-live` - позволяет объявлять динамически появляющиеся ошибки.

Пример:

```
<label for="email">Email</label>

<input
  id="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
/>

<span id="email-error">
  Введите корректный email
</span>
```

При отправке формы с несколькими ошибками полезно показать общий список ошибок со ссылками на поля и переместить фокус на этот список либо на первое невалидное поле.

Не следует полагаться только на `role="alert"`: пользователь должен иметь возможность повторно найти и прочитать ошибку.&#x20;

# Как проектировать доступные вкладки и dropdown?

Вкладки (Tabs) реализуются по паттерну WAI-ARIA Tabs:

- Контейнер - `role="tablist"`.
- Переключатели - `role="tab"` с `aria-selected`.
- Панели - `role="tabpanel"`.
- Связь между вкладкой и панелью - через `aria-controls` и `aria-labelledby`.

Навигация между вкладками осуществляется стрелками, `Tab` перемещает фокус за пределы группы вкладок. Активация может происходить при фокусировке или через `Enter`/`Space`.

Dropdown требует выбора подходящего паттерна в зависимости от назначения:

- Выбор значения - нативный `<select>` или ARIA `combobox`/`listbox`.
- Меню команд - `role="menu"` и `role="menuitem"` с навигацией стрелками и закрытием через `Escape`.
- Раскрывающийся блок или навигационный список - кнопка с `aria-expanded`, при необходимости `aria-controls`, и обычные ссылки или элементы внутри.

Нельзя автоматически использовать `role="menu"` для любого выпадающего списка: этот паттерн требует специального клавиатурного поведения.&#x20;

# Почему цвет не должен быть единственным способом передачи информации?

Пользователи с нарушениями цветовосприятия, слабым зрением или при использовании режимов высокой контрастности могут не различать некоторые цвета.

Поэтому информацию необходимо дублировать другими визуальными признаками:

- Ошибка - красный цвет + текст ошибки или иконка.
- Успех - зелёный цвет + текстовое подтверждение.
- Обязательное поле - символ `*` с пояснением или текст «Обязательное».
- Активное состояние - цвет + подчёркивание, рамка или другой визуальный признак.

Это соответствует критерию WCAG 1.4.1 Use of Color (A).

Главный принцип: смысл информации должен сохраняться даже без различения цветов.

# Какие требования есть к контрастности текста?

WCAG определяет минимальные коэффициенты контрастности между текстом и фоном.

| Элемент                                            | WCAG AA | WCAG AAA                        |
|----------------------------------------------------|---------|---------------------------------|
| Обычный текст                                      | 4.5:1   | 7:1                             |
| Крупный текст                                      | 3:1     | 4.5:1                           |
| Значимые элементы интерфейса и графические объекты | 3:1     | Зависит от применимого критерия |

Крупный текст - от 24 CSS-пикселей при обычном начертании или примерно от 18.66 CSS-пикселей при жирном.

Требование 3:1 для элементов интерфейса относится к визуальной информации, необходимой для их распознавания и определения состояния, а не ко всем декоративным деталям.

Контрастность рассчитывается через относительную яркость цветов и не зависит напрямую от разницы их RGB-значений.

Для некоторых элементов, например логотипов, неактивных компонентов и декоративного содержимого, предусмотрены исключения.&#x20;

# Как учитывать настройку `prefers-reduced-motion`?

`prefers-reduced-motion` - CSS media feature, позволяющая определить, запросил ли пользователь уменьшение анимации в настройках системы.

Пример:

```
.element {
  transition: transform 300ms ease;
}

@media (prefers-reduced-motion: reduce) {
  .element {
    transition: none;
  }
}
```

При значении `reduce` следует отключать или упрощать необязательные анимации, особенно масштабирование, параллакс и интенсивное перемещение элементов.

Необязательно отключать вообще все переходы. Например, плавное изменение прозрачности может оставаться приемлемым.

Главное: сокращение анимаций не должно нарушать функциональность интерфейса или скрывать важную информацию.&#x20;

# Как тестировать интерфейс с VoiceOver или NVDA?

VoiceOver - встроенный скринридер Apple, NVDA - скринридер для Windows.

Проверять интерфейс желательно в распространённых сочетаниях: VoiceOver + Safari и NVDA + Firefox/Chrome.

Основные проверки:

1. Навигация - можно ли последовательно перемещаться по заголовкам, ссылкам, кнопкам и областям страницы.
2. Названия и роли - правильно ли озвучиваются элементы и их назначение.
3. Состояния - сообщаются ли `expanded`, `selected`, `checked`, `disabled` и другие состояния.
4. Формы - корректно ли читаются названия полей, инструкции и ошибки.
5. Динамический контент - озвучиваются ли уведомления и изменения состояния.
6. Сложные компоненты - правильно ли работают диалоги, вкладки, меню и управление фокусом.

Важно проверять не только последовательность `Tab`, но и специальные команды скринридера для навигации по структуре документа.

Цель тестирования - убедиться, что пользователь может понять интерфейс и выполнить основные сценарии без визуального восприятия страницы.

# Чем `aria-hidden` отличается от `inert`?

Оба механизма влияют на доступность содержимого, но решают разные задачи.

`aria-hidden="true"`:

- Исключает элемент и его потомков из Accessibility Tree.
- Не скрывает содержимое визуально.
- Не запрещает клики и клавиатурную фокусировку.
- Не должен применяться к фокусируемым элементам или их предкам.

`inert`:

- Исключает элемент и его потомков из Accessibility Tree.
- Блокирует пользовательское взаимодействие с содержимым.
- Исключает элементы из клавиатурной навигации.
- Запрещает фокусировку, выделение текста и обычное взаимодействие с элементами.

Пример применения `aria-hidden` - скрытие декоративной иконки от скринридера.

Пример применения `inert` - отключение фонового интерфейса при открытом модальном окне.

Ключевое отличие: `aria-hidden` управляет доступностью информации для вспомогательных технологий, а `inert` дополнительно блокирует взаимодействие.&#x20;

# Как проверять accessibility автоматически через axe-core?

`axe-core` - библиотека для автоматического выявления распространённых нарушений доступности на основе правил WCAG и других проверок.

Её можно использовать через расширение браузера, `jest-axe` или `@axe-core/playwright`.

Пример с Playwright:

```
import AxeBuilder from "@axe-core/playwright";
import { test, expect } from "@playwright/test";

test("accessibility", async ({ page }) => {
  await page.goto("/");

  const results = await new AxeBuilder({ page }).analyze();

  expect(results.violations).toEqual([]);
});
```

`axe-core` помогает выявлять проблемы:

- Отсутствующие доступные названия элементов.
- Некорректное использование ARIA.
- Недостаточную контрастность в поддерживаемых сценариях.
- Нарушения структуры и связей элементов.
- Некоторые проблемы с формами и интерактивными компонентами.

Проверки можно запускать в CI/CD и выполнять для разных состояний интерфейса: открытого диалога, раскрытого меню, формы с ошибками.

Ограничение: отсутствие нарушений в `axe-core` не гарантирует соответствие WCAG. Автоматические тесты не способны полноценно оценить логичность навигации, корректность управления фокусом и понятность интерфейса.

Поэтому автоматические проверки необходимо сочетать с ручным тестированием клавиатуры и скринридеров.&#x20;
