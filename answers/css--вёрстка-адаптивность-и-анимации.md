# Как работает главная и поперечная ось Flexbox?

Flexbox использует две оси для расположения элементов:

- Главная ось (main axis) - направление размещения элементов. Определяется свойством `flex-direction`: `row`, `row-reverse`, `column`, `column-reverse`.
- Поперечная ось (cross axis) - перпендикулярна главной и используется для выравнивания элементов.

При `flex-direction: row` главная ось обычно горизонтальная, а при `column` - вертикальная. Однако физическое направление осей зависит также от `direction` и `writing-mode`.

Выравнивание вдоль главной оси управляется `justify-content`, вдоль поперечной - `align-items` и `align-self`.

# Как соотносятся `flex-grow`, `flex-shrink` и `flex-basis`?

Эти свойства определяют, как flex-элемент распределяет доступное пространство вдоль главной оси.

- `flex-basis` - задаёт исходный базовый размер элемента до распределения свободного пространства.
- `flex-grow` - определяет, какую долю положительного свободного пространства получит элемент.
- `flex-shrink` - определяет, как элемент участвует в сокращении размеров при недостатке пространства.

Если свободное пространство положительное, используется `flex-grow`. Если отрицательное - `flex-shrink`.

При сжатии учитывается не только `flex-shrink`, но и базовый размер элемента: коэффициент сжатия умножается на `flex-basis`. Это позволяет пропорционально сокращать элементы разных размеров.

Сокращённая запись:

```
.item {
  flex: 1 1 200px;
}
```

Эквивалентна:

```
.item {
  flex-grow: 1;
  flex-shrink: 1;
  flex-basis: 200px;
}
```

Важно: `flex-grow` и `flex-shrink` не гарантируют итоговый размер. На него также влияют `min-width`, `max-width`, размеры содержимого и другие ограничения.

# Чем `justify-content` отличается от `align-items` и `align-content`?

Все три свойства управляют выравниванием, но применяются к разным осям и объектам.

- `justify-content` - распределяет свободное пространство между элементами вдоль главной оси.
- `align-items` - задаёт выравнивание элементов внутри flex-линии по поперечной оси.
- `align-content` - распределяет flex-линии вдоль поперечной оси, когда включён `flex-wrap` и есть свободное пространство.

Например, `justify-content: space-between` распределяет элементы от начала до конца главной оси, а `align-items: center` центрирует их относительно поперечной оси.

`align-content` не предназначен для выравнивания отдельных элементов. В однострочном flex-контейнере он не влияет на расположение.

# Когда `flex-wrap` меняет поведение выравнивания?

При `flex-wrap: nowrap` все элементы располагаются в одной flex-линии. При `wrap` или `wrap-reverse` они могут переноситься на несколько линий, если не помещаются вдоль главной оси.

Это влияет на выравнивание:

- `justify-content` распределяет элементы отдельно внутри каждой линии.
- `align-items` выравнивает элементы по поперечной оси внутри их линии.
- `align-content` начинает управлять распределением нескольких линий по поперечной оси.

При `wrap-reverse` дополнительно меняется направление поперечной оси.

Важно: `flex-wrap` не создаёт строгую сетку. Элементы разных линий не выравниваются по общим колонкам, поскольку каждая линия рассчитывается независимо.

# Почему flex-элемент может не сжиматься из-за `min-width: auto`?

По умолчанию flex-элементы имеют `min-width: auto`, которое в определённых условиях устанавливает автоматический минимальный размер на основе содержимого.

Для flex-элемента с горизонтальной главной осью это часто означает, что он не может стать уже своего минимального размера по содержимому (min-content).

Например, длинное неразрывное слово может заставить элемент выйти за пределы контейнера, несмотря на `flex-shrink: 1`.

Решение:

```
.item {
  min-width: 0;
}
```

Это разрешает элементу сжиматься ниже минимальной ширины содержимого. При необходимости дополнительно используют `overflow-wrap` или управление переполнением.

Для вертикальной главной оси аналогичная проблема возникает с `min-height: auto`, поэтому часто требуется `min-height: 0`.

# Какие проблемы создаёт `order` для клавиатурной навигации?

Свойство `order` меняет визуальный порядок flex- и grid-элементов, но не изменяет их последовательность в DOM.

Из-за этого возникают проблемы:

- Клавиатурная навигация через `Tab` обычно следует DOM-порядку, а не визуальному расположению.
- Скринридеры преимущественно используют логический порядок документа.
- Пользователь может видеть элементы в одной последовательности, а перемещаться между ними в другой.

Это нарушает предсказуемость интерфейса и может создавать проблемы доступности.

Правило: логический порядок элементов должен определяться HTML-разметкой. `order` следует использовать для визуальных изменений, которые не нарушают смысловую последовательность и навигацию.

# В каких случаях CSS Grid лучше Flexbox?

CSS Grid лучше подходит для двумерных макетов, где необходимо одновременно управлять строками и колонками.

Основные случаи использования:

- Сетки карточек с выравниванием по колонкам и строкам.
- Макеты страниц с боковыми панелями, шапкой и основным содержимым.
- Интерфейсы, требующие точного позиционирования элементов в областях сетки.
- Компоненты, в которых несколько элементов должны разделять общие линии сетки.

Flexbox лучше подходит для одномерного расположения элементов - в строку или колонку, например для навигационных меню, панелей инструментов и групп кнопок.

При переносе строк Flexbox рассчитывает каждую линию независимо. Grid создаёт общую систему строк и колонок, благодаря чему обеспечивает более предсказуемое двумерное выравнивание.

Оба механизма часто используются совместно: Grid для общей структуры, Flexbox для содержимого отдельных компонентов.

# Как работают `grid-template-columns`, `grid-template-areas` и `grid-auto-flow`?

Эти свойства управляют разными аспектами CSS Grid.

- `grid-template-columns` - определяет размеры и количество колонок явной сетки.
- `grid-template-areas` - задаёт именованные области сетки, к которым элементы привязываются через `grid-area`.
- `grid-auto-flow` - определяет алгоритм автоматического размещения элементов, которым не задали точное положение.

Пример:

```
.layout {
  display: grid;
  grid-template-columns: 200px 1fr;

  grid-template-areas:
    "header header"
    "sidebar main";

  grid-auto-flow: row;
}

.header  { grid-area: header; }
.sidebar { grid-area: sidebar; }
.main    { grid-area: main; }
```

Здесь создаются две колонки: первая шириной `200px`, вторая занимает оставшееся пространство. `header` занимает обе колонки.

`grid-auto-flow` поддерживает значения:

- `row` - автоматическое размещение преимущественно по строкам.
- `column` - преимущественно по колонкам.
- `dense` - дополнительный алгоритм заполнения свободных ячеек, который может визуально переставлять элементы относительно их DOM-порядка.

# Чем `auto-fill` отличается от `auto-fit`?

Оба значения используются с `repeat()` для автоматического создания максимально возможного количества треков, помещающихся в контейнер.

Разница проявляется, когда элементов меньше, чем потенциальных колонок.

- `auto-fill` - сохраняет пустые колонки, резервируя под них пространство.
- `auto-fit` - схлопывает пустые колонки, позволяя занятым колонкам использовать освободившееся пространство.

```
.grid {
  display: grid;
  grid-template-columns:
    repeat(auto-fit, minmax(200px, 1fr));
}
```

В этом примере при широком контейнере и малом количестве карточек `auto-fit` позволяет карточкам растягиваться.

Если заменить его на `auto-fill`, пустые колонки продолжат занимать пространство.

Важно: разница относится к пустым повторяемым трекам. Когда все созданные колонки заняты, результат обычно одинаковый.

# Как устроены единицы `fr` и функция `minmax()`?

`fr` - единица CSS Grid, обозначающая долю доступного пространства в контейнере сетки после учёта других размеров и отступов.

```
.grid {
  display: grid;
  grid-template-columns: 1fr 2fr;
}
```

При достаточном пространстве вторая колонка получит вдвое больше распределяемого пространства, чем первая.

Однако `fr` учитывает ограничения минимальных размеров треков и содержимого. Поэтому `1fr` не всегда означает беспрепятственное сжатие.

`minmax(min, max)` - задаёт диапазон размеров трека: минимальную и максимальную границы.

```
.grid {
  grid-template-columns:
    repeat(3, minmax(0, 1fr));
}
```

`minmax(0, 1fr)` позволяет колонкам сжиматься ниже автоматического минимального размера содержимого, что полезно для предотвращения неожиданного расширения сетки.

Часто используется также `minmax(200px, 1fr)`: колонка не должна быть уже `200px`, но при наличии свободного пространства может расширяться.

# Что такое implicit grid и как возникают неявные треки?

Implicit grid (неявная сетка) - строки и колонки, которые браузер создаёт автоматически за пределами явно заданной сетки.

Неявные треки возникают, когда:

- Элементов больше, чем помещается в явной сетке.
- Элемент явно размещён за пределами существующих линий сетки.
- Алгоритму автоматического размещения требуются дополнительные строки или колонки.

```
.grid {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
  grid-auto-rows: 100px;
}
```

Здесь явно определены три колонки, но количество строк не ограничено. При добавлении элементов браузер автоматически создаёт строки высотой `100px`.

Размеры неявных треков задаются через `grid-auto-rows` и `grid-auto-columns`. По умолчанию используется `auto`.

Важно различать:

- Explicit grid - треки, заданные через `grid-template-*`.
- Implicit grid - треки, созданные алгоритмом Grid автоматически.

# Для чего нужен `subgrid`?

`subgrid` позволяет вложенной CSS Grid-сетке использовать размеры и линии треков родительской сетки вместо создания полностью независимой сетки.

Это решает проблему выравнивания вложенных элементов относительно общей структуры.

```
.parent {
  display: grid;
  grid-template-columns: repeat(3, 1fr);
}

.child {
  display: grid;
  grid-column: span 3;
  grid-template-columns: subgrid;
}
```

Здесь `.child` использует три колонки родительской сетки, которые охватывает сам элемент.

`subgrid` можно задавать независимо для строк и колонок:

- `grid-template-columns: subgrid` - наследует структуру колонок.
- `grid-template-rows: subgrid` - наследует структуру строк.

Особенно полезен для карточек с заголовками, описаниями и кнопками, которые должны выравниваться по общим линиям, несмотря на различия в содержимом.

Ограничение: `subgrid` работает только внутри родительской Grid-сетки и использует треки, которые охватывает вложенный grid-элемент.&#x20;

# Как реализовать адаптивную сетку без media queries?

Для этого используют CSS Grid с `repeat()`, `auto-fit` или `auto-fill`, `minmax()` и относительными единицами измерения.

```
.grid {
  display: grid;
  grid-template-columns:
    repeat(auto-fit, minmax(min(100%, 250px), 1fr));
  gap: 16px;
}
```

Механизм работы:

- `auto-fit` создаёт столько колонок, сколько помещается в контейнер.
- `minmax()` позволяет колонкам расширяться и сжиматься в заданных пределах.
- `min(100%, 250px)` не позволяет минимальной ширине колонки превышать ширину контейнера.
- `1fr` распределяет свободное пространство между колонками.

При изменении ширины контейнера количество колонок автоматически меняется.

Преимущество: адаптивность зависит от доступного пространства, а не от заранее заданных брейкпоинтов.

Ограничение: такой подход удобен для гибких сеток, но не заменяет media queries, если на разных размерах экрана требуется принципиально менять структуру интерфейса.

# Чем mobile-first отличается от desktop-first?

Это два подхода к организации адаптивных стилей.

Mobile-first - сначала описываются стили для небольших экранов, затем добавляются изменения через `min-width`.

```
.card {
  width: 100%;
}

@media (min-width: 768px) {
  .card {
    width: 50%;
  }
}
```

Desktop-first - сначала описываются стили для больших экранов, затем используются ограничения `max-width` для адаптации к меньшим.

Основные различия:

- Mobile-first постепенно расширяет интерфейс по мере увеличения доступного пространства.
- Desktop-first постепенно упрощает интерфейс для меньших экранов.
- Mobile-first часто помогает изначально сосредоточиться на ключевом содержимом и ограниченном пространстве.

Важно: mobile-first сам по себе не улучшает производительность. Браузер всё равно загружает подходящие CSS-ресурсы, а производительность зависит от конкретной реализации.

# Как работают `@media` и `@container`?

Оба правила позволяют применять CSS условно, но проверяют разные характеристики.

`@media` проверяет характеристики среды отображения: размер viewport, ориентацию, пользовательские настройки, тип устройства и другие медиаусловия.

```
@media (width >= 768px) {
  .card {
    display: flex;
  }
}
```

`@container` позволяет проверять характеристики контейнера, например его ширину, и применять стили к вложенным элементам.

```
.wrapper {
  container-type: inline-size;
}

@container (width >= 500px) {
  .card {
    display: flex;
  }
}
```

Главное различие:

- `@media` - адаптация относительно среды отображения, часто viewport.
- `@container` - адаптация относительно конкретного контейнера.

Например, при широком экране карточка может находиться в узком сайдбаре. `@media` будет учитывать ширину viewport, а `@container` позволит адаптировать карточку именно под ширину сайдбара.

# Как устроены container queries и когда они удобнее media queries?

Container queries - механизм условного применения CSS на основе характеристик контейнера, внутри которого находится элемент.

Для запросов к размерам сначала объявляется контейнер:

```
.card-wrapper {
  container: card / inline-size;
}
```

Затем определяется правило:

```
@container card (width >= 400px) {
  .card {
    flex-direction: row;
  }
}
```

Браузер находит подходящий контейнер-предок, проверяет условие и применяет стили к вложенным элементам.

Основные особенности:

- `container-type: inline-size` позволяет выполнять запросы к размеру контейнера по строчной оси.
- `container-type: size` поддерживает запросы по обеим осям, но накладывает более строгие ограничения на определение размера контейнера.
- `container-name` позволяет обращаться к определённым контейнерам.
- Контейнерные единицы `cqw`, `cqh`, `cqi`, `cqb` позволяют задавать размеры относительно query-контейнера.
- Помимо размерных запросов существуют style queries, а также другие разновидности container queries с отдельными условиями поддержки браузерами.

Когда удобнее: при разработке переиспользуемых компонентов, которые могут находиться в разных частях интерфейса - карточках, боковых панелях, модальных окнах.

Ограничение: запрос к размеру не может непосредственно менять стили самого контейнера, от размера которого зависит условие. Обычно изменяются его потомки. Это предотвращает циклические зависимости между размерами и стилями.&#x20;

# Как поддерживать RTL и вертикальные режимы письма в CSS?

Для поддержки разных направлений текста следует использовать логические CSS-свойства вместо физических.

Например:

```
.element {
  margin-inline-start: 16px;
  padding-block-end: 8px;
  border-inline-start: 1px solid;
}
```

В отличие от `margin-left` и `padding-bottom`, логические свойства ориентируются на направление текста и режим письма.

Ключевые механизмы:

- `direction: rtl` - задаёт направление письма справа налево.
- HTML-атрибут `dir="rtl"` - задаёт базовое направление текста семантически.
- `writing-mode: vertical-rl` - включает вертикальное расположение строк.
- `inline-size` и `block-size` - логические аналоги размеров вдоль строчной и блочной осей.
- `inset-inline-start`, `margin-inline-end` и другие логические свойства заменяют привязку к физическим сторонам.

Для текстового содержимого предпочтительно использовать HTML-атрибут `dir`, поскольку он влияет не только на оформление, но и на семантику направления текста.

Для динамических фрагментов с неизвестным направлением полезны `dir="auto"` и элемент `<bdi>`.

Важно: поддержка RTL требует проверки иконок, навигации, порядка элементов и поведения интерфейса. Не все визуальные элементы нужно зеркально отражать.

# Как адаптировать дизайн под изменение системного размера шрифта?

Основной принцип - интерфейс должен сохранять работоспособность при увеличении текста без обрезания содержимого и потери функциональности.

Для этого используют:

- `rem` для размеров текста и отступов, которые должны масштабироваться относительно корневого шрифта.
- `em` для размеров, зависящих от текущего элемента.
- `line-height` без единиц измерения для пропорциональной высоты строк.
- `min-height` вместо фиксированной `height`, если содержимое может увеличиваться.
- Гибкие размеры контейнеров и перенос текста.

Пример:

```
.card {
  padding: 1rem;
  min-height: 4rem;
}

.card__title {
  font-size: 1.25rem;
  line-height: 1.4;
  overflow-wrap: anywhere;
}
```

Не следует без необходимости задавать жёсткие размеры контейнеров и использовать `overflow: hidden`, если это может обрезать важный текст.

Важный нюанс: `rem` зависит от вычисленного размера шрифта корневого элемента. Если жёстко задать `html { font-size: 16px; }`, пользовательские настройки базового размера шрифта могут не учитываться ожидаемым образом.

Адаптивность нужно проверять при увеличении текста, масштабировании страницы и изменении доступной ширины экрана.

# Чем `transition` отличается от `animation`?

Оба механизма позволяют изменять CSS-свойства во времени, но отличаются способом управления.

`transition` - создаёт плавный переход между двумя вычисленными состояниями свойства.

```
.button {
  background-color: blue;
  transition: background-color 200ms ease;
}

.button:hover {
  background-color: red;
}
```

Переход запускается, когда меняется значение свойства, например при `hover`, `focus` или изменении класса.

`animation` - использует `@keyframes` для описания последовательности состояний.

```
@keyframes pulse {
  0% { opacity: 1; }
  50% { opacity: 0.5; }
  100% { opacity: 1; }
}

.button {
  animation: pulse 1s infinite;
}
```

Главные отличия:

- `transition` обычно требует изменения состояния свойства для запуска.
- `animation` может запускаться автоматически при применении стиля.
- `transition` описывает переход между исходным и конечным значениями.
- `animation` поддерживает промежуточные ключевые кадры, повторения, направление воспроизведения и управление состоянием анимации.

`transition` удобнее для простых интерактивных эффектов. `animation` - для сложных, многоэтапных и повторяющихся движений.

# Как работают `transform`, `translate`, `scale` и `rotate`?

`transform` позволяет визуально изменять положение, масштаб, угол поворота и форму элемента с помощью геометрических преобразований.

Основные функции:

- `translate()` - перемещение относительно исходного положения.
- `scale()` - масштабирование.
- `rotate()` - вращение.
- `skew()` - наклон.

Пример:

```
.element {
  transform: translateX(50px) rotate(30deg);
}
```

Порядок функций имеет значение, поскольку преобразования комбинируются математически и могут влиять друг на друга.

В современном CSS также существуют независимые свойства:

```
.element {
  translate: 50px 0;
  rotate: 30deg;
  scale: 1.2;
}
```

Они позволяют изменять отдельные преобразования, не перезаписывая всё значение `transform`.

При совместном использовании отдельных свойств и `transform` порядок применения фиксирован: `translate`, `rotate`, `scale`, затем `transform`.

Особенности:

- Преобразования обычно не меняют размеры элемента в потоке документа, поэтому могут приводить к визуальному перекрытию.
- `transform-origin` задаёт точку, относительно которой выполняются преобразования.
- Значение `transform`, отличное от `none`, создаёт новый stacking context и containing block для определённых позиционированных потомков.

# Почему анимации `transform` и `opacity` часто производительнее анимаций размеров?

Браузер обычно выполняет несколько этапов визуализации:

1. Style - вычисление CSS-стилей.
2. Layout - расчёт размеров и расположения элементов.
3. Paint - отрисовка визуального содержимого.
4. Composite - объединение графических слоёв.

Анимация `width`, `height`, `margin` и подобных свойств может требовать повторного расчёта геометрии, а иногда и перерисовки элементов.

Анимации `transform` и `opacity` часто могут выполняться на этапе compositing, без повторного Layout и Paint на каждом кадре.

```
.element {
  transition: transform 200ms ease;
}

.element:hover {
  transform: translateY(-10px);
}
```

Если элемент вынесен в отдельный композитный слой, браузер может выполнять такое преобразование особенно эффективно.

Однако это не гарантировано: создание слоёв, использование памяти GPU, сложные эффекты и особенности браузера также влияют на производительность.

`will-change: transform` может подсказать браузеру подготовить оптимизацию, но постоянное применение к большому количеству элементов увеличивает расход ресурсов.

# Как учитывать `prefers-reduced-motion`?

`prefers-reduced-motion` - CSS media feature, позволяющая определить, предпочитает ли пользователь уменьшенное количество анимаций и движений.

```
.element {
  transition: transform 300ms ease;
}

@media (prefers-reduced-motion: reduce) {
  .element {
    transition: none;
  }
}
```

Это особенно важно для пользователей с вестибулярными нарушениями, которым масштабирование, резкое перемещение и другие движения могут причинять дискомфорт.

При этом не обязательно полностью отключать все анимации. Можно:

- Убирать декоративные и бесконечные анимации.
- Заменять перемещение или масштабирование менее интенсивными эффектами.
- Сокращать длительность переходов.
- Сохранять необходимые состояния и обратную связь интерфейса.

Если анимация управляется JavaScript, предпочтение можно проверить через `matchMedia('(prefers-reduced-motion: reduce)')`.

Важно: `prefers-reduced-motion` сообщает о предпочтении пользователя, но не запрещает анимации технически. Реализация адаптации остаётся ответственностью разработчика.&#x20;

# Как использовать `@supports` для progressive enhancement?

`@supports` позволяет применять CSS-правила только при наличии поддержки определённых CSS-возможностей браузером.

Это используется для progressive enhancement - постепенного улучшения интерфейса без нарушения его базовой работоспособности в окружениях с ограниченной поддержкой.

```
.layout {
  display: flex;
}

@supports (display: grid) {
  .layout {
    display: grid;
    grid-template-columns: repeat(3, 1fr);
  }
}
```

Сначала определяется базовая реализация через Flexbox. Если браузер поддерживает Grid, применяется улучшенная версия.

Дополнительно поддерживаются:

- `not` - отрицание условия.
- `and` - необходимость поддержки нескольких возможностей.
- `or` - достаточно поддержки одной возможности.
- `selector()` - проверка поддержки синтаксиса CSS-селектора.

Например:

```
@supports (grid-template-rows: subgrid) {
  .nested {
    grid-template-rows: subgrid;
  }
}
```

Ограничение: `@supports` проверяет распознавание синтаксиса и заявленную поддержку возможности, но не гарантирует отсутствие ошибок в её реализации.&#x20;

# Как организовать CSS-слои в крупном приложении?

CSS Cascade Layers (`@layer`) позволяют управлять приоритетами групп стилей независимо от специфичности отдельных селекторов.

Например:

```
@layer reset, base, components, utilities;
```

Затем стили распределяются по слоям:

```
@layer base {
  body {
    font-family: sans-serif;
  }
}

@layer components {
  .button {
    padding: 12px;
  }
}

@layer utilities {
  .p-0 {
    padding: 0;
  }
}
```

Для обычных деклараций более поздний слой имеет больший приоритет, чем предыдущий.

Это позволяет разделять стили по ответственности:

- `reset` - нормализация браузерных стилей.
- `base` - глобальные стили и типографика.
- `components` - стили компонентов.
- `utilities` - вспомогательные классы.

Важные особенности каскада:

- Приоритет слоя определяется порядком его объявления, а не порядком селекторов внутри других слоёв.
- Специфичность сравнивается уже внутри соответствующего уровня каскада.
- Обычные стили вне слоёв имеют приоритет выше обычных стилей внутри слоёв.
- Для деклараций с `!important` порядок слоёв обратный: более ранние слои имеют больший приоритет.

Поэтому важно заранее объявлять порядок слоёв и контролировать размещение сторонних стилей, например подключать их через `@import ... layer(...)`.&#x20;

# Какие преимущества и недостатки у БЭМ, CSS Modules и CSS-in-JS?

Эти подходы решают проблему организации и изоляции стилей, но делают это разными способами.

1\. БЭМ (Block Element Modifier)

Методология именования CSS-классов через блок, элемент и модификатор.

```
.card {}
.card__title {}
.card--active {}
```

Преимущества:

- Понятная структура и ответственность классов.
- Не требует специальной сборки.
- Предсказуемые селекторы с невысокой специфичностью.

Недостатки:

- Длинные названия классов.
- Нет технической изоляции: конфликты имён всё ещё возможны.
- Требует соблюдения соглашений всей командой.

2\. CSS Modules

Механизм сборки, при котором локальные CSS-классы преобразуются в уникальные идентификаторы.

```
import styles from './Button.module.css';

<button className={styles.button}>Click</button>
```

Преимущества:

- Автоматическая локальная область видимости классов.
- Хорошая совместимость с компонентной архитектурой.
- Обычный CSS без необходимости генерировать стили во время выполнения.

Недостатки:

- Требуется поддержка сборщика.
- Глобальные стили и наследование по-прежнему могут влиять на компоненты.
- Сложные динамические стили требуют дополнительных решений: классов, CSS-переменных или inline-стилей.

3\. CSS-in-JS

Подход, при котором стили описываются через JavaScript или TypeScript.

Примерный вариант API:

```
const Button = styled.button`
  color: red;
  padding: 12px;
`;
```

Преимущества:

- Удобная интеграция стилей с состоянием и пропсами компонентов.
- Возможность использовать типизацию и общие JavaScript-абстракции.
- Инкапсуляция стилей в библиотеках, поддерживающих автоматическое формирование классов.

Недостатки:

- Runtime-реализации могут увеличивать JavaScript-бандл и стоимость выполнения.
- Возможны дополнительные сложности с SSR, гидратацией и порядком внедрения стилей.
- Поведение и производительность сильно зависят от конкретной библиотеки.

Важно: CSS-in-JS бывает runtime и build-time. Недостатки runtime-генерации не обязательно относятся к решениям, извлекающим CSS на этапе сборки.

# Чем SCSS mixin отличается от функции и placeholder selector?

Все три механизма позволяют переиспользовать код в Sass, но решают разные задачи.

1\. Mixin (`@mixin`) - переиспользование наборов CSS-деклараций и правил.

```
@mixin flex-center {
  display: flex;
  justify-content: center;
  align-items: center;
}

.container {
  @include flex-center;
}
```

При компиляции содержимое миксина подставляется в место вызова.

Миксины поддерживают аргументы, условия и передачу блоков через `@content`.

Недостаток: многократное использование может приводить к дублированию CSS-деклараций в итоговом файле.

2\. Function (`@function`) - вычисление и возврат значения.

```
@function double($value) {
  @return $value * 2;
}

.box {
  padding: double(8px);
}
```

Функция возвращает результат, который можно использовать в CSS-свойствах и выражениях Sass.

Главное отличие от миксина: функция предназначена для вычисления значений, а не генерации CSS-правил.

3\. Placeholder selector (`%`) - шаблон селектора, который можно расширять через `@extend`.

```
%flex-center {
  display: flex;
  justify-content: center;
}

.container {
  @extend %flex-center;
}

.modal {
  @extend %flex-center;
}
```

Результат компиляции:

```
.container, .modal {
  display: flex;
  justify-content: center;
}
```

Сам placeholder не попадает в итоговый CSS, если не используется через `@extend`.

Основное различие:

- Mixin - копирует CSS-декларации и правила в места вызова.
- Function - вычисляет и возвращает значение.
- Placeholder - переиспользует набор правил через объединение селекторов.

`@extend` может уменьшить дублирование деклараций, но при сложном наследовании приводит к разрастанию и усложнению селекторов.

Поэтому mixin удобнее для параметризуемых стилей, function - для вычислений, placeholder - для общих неизменяемых наборов деклараций.&#x20;
