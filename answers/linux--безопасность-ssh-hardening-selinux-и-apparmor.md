# Как threat model и принцип least privilege определяют практический план hardening Linux?

Начинают с **threat model**: какие данные и операции защищают, кто имеет доступ, откуда возможна атака и каковы последствия. Затем минимизируют доступные services, identities, сетевые пути и права, сохраняя необходимые функции и восстановление.

**Least privilege** означает достаточные полномочия для конкретной роли, а не одинаковый жёсткий шаблон на все hosts. Изменения проверяют на функциональности, наблюдаемости и возможности администрирования. Hardening не заменяет patching и управление credentials; документируют обоснованные исключения и владельца каждого из них.

# Как SSH использует host keys и user keys для разных проверок доверия?

**Host key** подтверждает identity SSH-сервера клиенту, а **user key** позволяет серверу проверить пользователя. Это разные направления доверия и разные private keys. Клиент проверяет host identity по trusted known_hosts или другой согласованной схеме, например host certificates.

Изменение host key сначала сопоставляют с ожидаемым переустановлением или ротацией, а не автоматически отключают проверку. Private user key защищают на клиенте и отзывают при компрометации. Надёжный login пользователя не исправляет подключение к поддельному серверу при неверной host verification. [OpenSSH](https://man.openbsd.org/ssh).

# Как безопасно управлять SSH-доступом, sudo и аварийным административным доступом?

Используют персональные identities, управляемые keys или certificates и ограниченный административный доступ через проверенную sudo policy. Доступы имеют владельца, срок пересмотра и процедуру отзыва при уходе сотрудника.

Ограничение password или direct root login вводят вместе с проверенным альтернативным доступом и recovery-процедурой. Конфигурацию валидируют до применения и проверяют новую независимую сессию, сохраняя возможность исправить ошибку. Для MFA учитывают конкретную authentication chain и настройки PAM/OpenSSH: один flag не доказывает прохождение всех требуемых факторов. [sshd_config](https://man.openbsd.org/sshd_config).

# Как agent forwarding, port forwarding и bastion меняют границы SSH-доверия?

**Agent forwarding** не обязан копировать private key на удалённый host, но процесс с доступом к forwarded agent может использовать его для authentication в пределах доступных возможностей. Поэтому доверие к промежуточному host остаётся существенным.

**Port forwarding** открывает новый путь между сетевыми областями и может обходить ожидаемые application boundaries. **Bastion** централизует вход, но требует собственной защиты и контроля разрешённых направлений. ProxyJump позволяет строить подключение без автоматического включения agent forwarding на каждом узле. Политики keys, forwarding и host verification рассматривают совместно. [SSH forwarding](https://man.openbsd.org/ssh).

# Как DAC, capabilities и mandatory access control дополняют друг друга?

**DAC** использует owner, group, mode bits и ACL для обычной проверки доступа. **Capabilities** делят привилегированные Linux-операции на отдельные полномочия, позволяя не выдавать процессу все возможности root.

**Mandatory access control**, например SELinux или AppArmor, добавляет централизованную policy, которую обычный владелец файла не может произвольно обойти. Эти уровни дополняют друг друга: разрешение DAC не гарантирует разрешение MAC. Capabilities тоже не являются безобидными flags — отдельное широкое полномочие способно существенно расширить доступ. [Capabilities](https://man7.org/linux/man-pages/man7/capabilities.7.html).

# Как SELinux contexts, domains и types участвуют в решении о доступе?

**SELinux context** содержит компоненты identity и policy, в частности type; для процессов говорят о domain. Type enforcement проверяет, какие действия domain может выполнять над объектами соответствующих types, с учётом остальных правил policy.

Поэтому файл с подходящими Unix permissions может оставаться недоступным из-за неверной label. После переноса данных проверяют ожидаемый context и постоянное правило labeling, а не только временно меняют метку. SELinux user и Linux UID — разные понятия. Доступные domains, booleans и tools зависят от distribution и установленной policy. [SELinux в RHEL](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/using_selinux/getting-started-with-selinux_using-selinux).

# Как AppArmor profiles и режимы enforce и complain ограничивают приложение?

**AppArmor profile** описывает допустимые действия программы, включая доступ к путям и другие поддерживаемые категории. Это path-oriented модель с деталями, зависящими от версии kernel, parser и distribution.

В **enforce** нарушения policy блокируются и журналируются по правилам профиля. **Complain** помогает исследовать поведение и обычно журналирует то, что было бы запрещено; явные deny-правила имеют особенности и могут продолжать действовать. Complain не считают рабочим эквивалентом полного enforcement. Профиль проверяют на update, reload и редких, но обязательных операциях приложения. [AppArmor Ubuntu](https://ubuntu.com/server/docs/how-to/security/apparmor/).

# Как расследовать SELinux или AppArmor denial без отключения защиты целиком?

Сначала читают denial record и сопоставляют процесс, операция, object path или context и время события. Затем проверяют обычные permissions, корректность labels, ожидаемый service path и выбранный profile/domain.

Если доступ нужен по архитектуре, исправляют configuration, labeling или минимальное правило policy и проверяют результат. Автоматическое разрешение всего, что появилось в audit log, может закрепить ошибку или лишний доступ. Глобальное отключение защиты скрывает причину и расширяет последствия. После изменения воспроизводят необходимый сценарий и проверяют, что посторонний доступ остался запрещён.

# Как updates, минимальный набор пакетов и контроль services уменьшают поверхность атаки?

Оставляют только необходимые packages и services, контролируют enabled units, автозапуск и реально открытые listeners. Неиспользуемый компонент создаёт дополнительный путь атаки и требует обновления даже без явного использования приложением.

Security updates проводят по управляемой процедуре с проверкой зависимостей, restart или reboot, когда они нужны, и возможностью восстановления. Обновлённый файл библиотеки не означает, что все старые процессы уже используют новую версию. Сравнивают ожидаемый inventory с фактическим состоянием и отдельно учитывают software, установленное вне package manager.

# Как host firewall, listening sockets и network exposure участвуют в hardening?

Проверяют, какой процесс слушает какой address и port, затем сопоставляют host firewall, cloud rules и фактические пути доступа. Listener на `0.0.0.0` или IPv6 wildcard может быть доступен шире, чем ожидалось по одному application config.

Разрешают необходимые направления и источники, учитывая management, DNS и зависимости. Container networking и NAT могут менять прохождение packet через host rules, поэтому проверяют реальный dataplane. Firewall не заменяет authentication сервиса и не делает безопасным избыточный привилегированный listener. Изменения подтверждают доступом из предусмотренных сетевых контекстов.

# Как защищать сервис через systemd sandboxing и изоляцию файловой системы?

Systemd позволяет задать service user, убрать лишние capabilities и ограничить доступ к filesystem, devices и другим ресурсам. Например, `ProtectSystem`, `ReadWritePaths`, `PrivateTmp` и `NoNewPrivileges` решают разные части задачи.

Нужные механизмы зависят от версии systemd, kernel и режима запуска. Политика должна учитывать запись state, reload, logs и доступ к credentials. Read-only root не запрещает запись через явно разрешённые paths, а private temporary directory не является полной виртуальной машиной. Проверяют фактически применённые ограничения и поведение приложения. [systemd.exec](https://man7.org/linux/man-pages/man5/systemd.exec.5.html).

# Как audit logs, контроль изменений и управление credentials помогают обнаружить компрометацию?

Собирают authentication, sudo, service и необходимые audit events, связывают их с identity и изменениями configuration. Отслеживают неожиданные users, keys, привилегии, listeners и запуск новых процессов по выбранной модели наблюдения.

Logs сохраняют с ограниченным доступом и подходящей внешней доставкой: атакующий с достаточными локальными правами может изменить свидетельства на host. Учитывают потери и переполнение audit pipeline. При компрометации отзывают доступные credentials и проверяют производные identities, а не только удаляют найденный файл. Detection подтверждают проверяемыми сценариями, избегая секретов в telemetry.
