# Как Terraform, OpenTofu и Pulumi описывают desired state и взаимодействуют с provider API?

Все три инструмента сопоставляют описание ресурсов с известным состоянием и через **providers** вызывают API облака или другой платформы. Terraform и OpenTofu используют конфигурационный язык семейства HCL, а Pulumi позволяет описывать ресурсы в поддерживаемых языках программирования и YAML.

Provider переводит модель ресурса в операции API и определяет часть поведения updates и replacement. Код на общем языке не делает инфраструктуру автоматически императивной последовательностью: Pulumi также строит граф ресурсов. Версии CLI, providers и поддерживаемые возможности фиксируют; общая история Terraform и OpenTofu не гарантирует бессрочную идентичность функций.

# Зачем IaC-инструменту state и почему конфигурация не заменяет его полностью?

**State** связывает адрес ресурса в коде с реальным ID, хранит известные attributes и другую metadata для планирования дальнейших действий. Без этой связи инструмент не всегда может отличить существующий управляемый объект от ресурса, который нужно создать.

Конфигурация описывает намерение, а state — учтённую историю управления и идентичность. При этом state не является безусловной истиной о текущем облаке: внешние изменения требуют refresh или другого согласования. State защищают, версионируют и восстанавливают по проверенной процедуре; его случайное удаление способно привести к дублированию инфраструктуры.

# Как plan или preview отличается от apply и почему одобренный план может устареть?

**Plan** или **preview** показывает предполагаемые действия на основании конфигурации, state, прочитанных API-данных и известных inputs. **Apply** выполняет изменения, часть результата может стать известна только при создании ресурсов.

Между проверкой и apply могут измениться инфраструктура, права, quota или внешние данные. Сохранённый plan Terraform может быть отклонён как устаревший при изменении state; он не замораживает весь внешний мир. Для review привязывают план к конкретным исходникам и версиям. Preview Pulumi исполняет программу, поэтому её пользовательский код тоже должен избегать необдуманных внешних эффектов.

# Как dependency graph и явные зависимости задают порядок создания ресурсов?

Ссылки на attributes и outputs создают **dependency graph**: ресурс создаётся после получения необходимых результатов зависимостей, а независимые части могут выполняться параллельно. Это отличается от простого исполнения файлов сверху вниз.

Явный `depends_on` или соответствующий механизм нужен, когда зависимость существует, но не выражена передачей значения, например готовность политики доступа. Слишком широкие зависимости увеличивают неизвестные values и длительность операций. Цикл означает, что модель требует переработки. Наличие ресурса в API ещё не всегда означает готовность внешнего сервиса, поэтому provider должен корректно ожидать нужное состояние.

# Как remote backend, locking и versioning защищают совместную работу со state?

**Remote backend** хранит state в общем защищённом месте. **Locking** сериализует операции, меняющие один state, если выбранный backend поддерживает такой механизм; удалённое хранение само по себе не доказывает наличие lock.

**Versioning** и backups помогают восстановиться после порчи или ошибочного обновления. Доступ разделяют по окружениям и identities, а concurrency pipeline дополняет backend protection. `force-unlock` нельзя использовать, пока не выяснено, что прежний владелец действительно прекратил работу. Pulumi имеет собственные backend-механизмы, которые проверяют отдельно. [Terraform locking](https://developer.hashicorp.com/terraform/language/state/locking), [Pulumi backends](https://www.pulumi.com/docs/iac/concepts/state-and-backends/).

# Почему sensitive marking не гарантирует отсутствие секрета в state или plan?

В Terraform `sensitive` прежде всего ограничивает обычное отображение значения: оно всё ещё может сохраняться в state и plan. Поэтому файлы, outputs, debug logs и доступ к backend защищают отдельно. Ephemeral и write-only возможности уменьшают сохранение некоторых значений только в поддерживаемых версиях и providers.

OpenTofu предоставляет настраиваемое шифрование state и plan, а Pulumi шифрует значения, корректно помеченные secrets, выбранным secrets provider. Эти механизмы не защищают произвольный plaintext, который программа вывела наружу. [Terraform sensitive data](https://developer.hashicorp.com/terraform/language/manage-sensitive-data), [OpenTofu encryption](https://opentofu.org/docs/language/state/encryption/), [Pulumi secrets](https://www.pulumi.com/docs/iac/concepts/secrets/).

# Как modules и component resources формируют переиспользуемые инфраструктурные интерфейсы?

**Module** Terraform/OpenTofu или **component resource** Pulumi объединяет связанные ресурсы за небольшим интерфейсом inputs и outputs. Например, компонент сервиса может задавать сеть, compute и наблюдаемость с общими правилами.

Интерфейс отражает устойчивую предметную задачу, а не каждый случайный параметр provider. Определяют ownership, версии, defaults и совместимость обновлений. Слишком большой универсальный module становится трудным для изменения, слишком мелкие обёртки лишь скрывают provider API. Проверяют, какие изменения inputs приведут к replacement и как потребитель увидит это в plan.

# Как разделять окружения по state, credentials и blast radius?

Для production и тестов выбирают отдельные state boundaries и credentials, при необходимости accounts или projects. Размер state определяет, какие изменения планируются вместе и каков возможный **blast radius** ошибки или компрометации.

Workspace или stack помогает разделить значения и state, но сам по себе не является полной security boundary: нужны IAM, backend policies и независимые deployment identities. Общие ресурсы имеют явного владельца и публикуют стабильные outputs. Не объединяют всё в один огромный state только ради удобного доступа к значениям.

# Как import, moved blocks и state operations позволяют принять и переорганизовать существующие ресурсы?

**Import** связывает уже существующий объект с управляемым адресом; после него приводят конфигурацию к желаемому виду и внимательно проверяют следующий plan. Сам импорт не гарантирует, что ресурс не будет заменён из-за отличающихся settings.

В Terraform/OpenTofu `moved` blocks фиксируют перенос адреса без создания нового объекта. В Pulumi похожие задачи идентичности решают через import и aliases по его правилам. Низкоуровневые state operations применяют при остановленных конкурирующих изменениях и с backup. Смена адреса в коде без учёта state часто выглядит как удаление старого и создание нового ресурса.

# Как drift, refresh и изменения через cloud console влияют на следующий plan?

**Drift** — расхождение управляемого состояния и фактического ресурса, например ручная смена instance size через console. Refresh получает доступные актуальные attributes, после чего plan показывает, как соотносятся live state и конфигурация.

Инструмент может предложить вернуть параметр, заменить объект или сохранить внешнее значение по специальным правилам. Не каждое поле provider читает и моделирует одинаково. Для ручного аварийного изменения решают, становится ли оно новым desired state, затем обновляют код. Игнорирование drift без владельца создаёт скрытую зависимость от действий, отсутствующих в репозитории.

# Как lifecycle rules и зависимые ресурсы влияют на замену и удаление инфраструктуры?

**Lifecycle rules** меняют порядок и условия операций, но не создают неограниченных возможностей у внешнего API. `create_before_destroy` требует запаса quota и возможности временно иметь два ресурса; уникальное имя может этому мешать.

`prevent_destroy` защищает предусмотренные операции Terraform/OpenTofu, но не является универсальным запретом удаления вне инструмента. `ignore_changes` передаёт часть управления другому владельцу и может скрывать важный drift. Зависимые ресурсы способны тоже потребовать replacement. Для данных дополнительно нужны backups, protection на стороне платформы и review plan на последствия удаления.

# Как тестировать IaC и продолжать работу после частично выполненного apply?

Проверяют синтаксис, формат, inputs, policy и планируемые критичные действия. Логику reusable modules и components тестируют отдельно, а существенные provider-сценарии — в ограниченном тестовом окружении с проверкой cleanup. Mocks не подтверждают реальную семантику cloud API.

**Apply не является общей транзакцией**: часть ресурсов может успешно измениться до ошибки. Сохраняют logs и state, проверяют реальное состояние, устраняют причину и строят новый plan. Не удаляют state ради «чистого старта». Если API выполнил действие, но инструмент не сохранил результат, может потребоваться согласованный import или восстановление связи.
