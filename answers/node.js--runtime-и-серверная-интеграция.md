# Чем Node.js отличается от браузерной среды выполнения JavaScript?

Node.js - среда выполнения JavaScript вне браузера, построенная на движке V8. Она предоставляет API для работы с файловой системой, сетью, процессами и операционной системой.

Основные различия:

- Браузер - предоставляет DOM, `window`, `document`, `localStorage` и другие Web API. JavaScript выполняется в изолированной среде с ограниченным доступом к ОС.
- Node.js - предоставляет `process`, `Buffer`, `fs`, `http`, `net`, `worker_threads` и другие серверные API. Может работать с файлами, создавать HTTP-серверы и запускать процессы.
- Общие API - обе среды поддерживают стандартный JavaScript и многие Web API, включая `fetch`, `URL`, `Promise`, `AbortController` и Web Streams.

Node.js использует Event Loop и `libuv` для асинхронного ввода-вывода. Браузер также имеет Event Loop, но его работа дополнительно связана с DOM, событиями интерфейса и рендерингом.

Главное отличие - не язык JavaScript, а доступные API, модель безопасности и окружение выполнения.

# Как работает Event Loop в Node.js?

Event Loop - механизм, позволяющий Node.js обрабатывать множество асинхронных операций без создания отдельного JavaScript-потока для каждого запроса.

JavaScript-код по умолчанию выполняется в одном основном потоке. Асинхронные операции передаются операционной системе или пулу потоков `libuv`. Когда операция завершается, соответствующий callback становится доступным для выполнения через Event Loop.

Основные фазы Event Loop:

1. Timers - выполнение готовых callbacks `setTimeout()` и `setInterval()`.
2. Pending callbacks - выполнение некоторых отложенных системных callbacks.
3. Poll - получение и обработка событий ввода-вывода.
4. Check - выполнение callbacks `setImmediate()`.
5. Close callbacks - обработка событий закрытия соединений.

Между выполнением callbacks Node.js обрабатывает очередь `process.nextTick()` и микрозадачи, включая обработчики `Promise`. Обычно `process.nextTick()` имеет приоритет над микрозадачами Promise, хотя в некоторых контекстах, например при выполнении ESM, порядок может отличаться.

Важные особенности:

- `setTimeout(fn, 0)` не гарантирует немедленного выполнения.
- `setImmediate()` выполняется в фазе `check`.
- Длительный синхронный код блокирует Event Loop.
- Асинхронность сама по себе не означает параллельное выполнение JavaScript.

Начиная с Node.js 20, из-за изменений в `libuv` обработка таймеров происходит после фазы `poll`, что может влиять на порядок выполнения `setTimeout()` и `setImmediate()`.&#x20;

# Что такое libuv и thread pool?

libuv - кроссплатформенная библиотека на C, обеспечивающая Node.js механизм Event Loop и асинхронные операции ввода-вывода.

Она использует системные механизмы, например `epoll` в Linux, `kqueue` в macOS и `IOCP` в Windows.

Thread pool - пул рабочих потоков `libuv`, предназначенный для операций, которые невозможно или нецелесообразно выполнять через неблокирующий системный ввод-вывод.

Через него выполняются, в частности:

- Некоторые операции с файловой системой (`fs`).
- `dns.lookup()`.
- Операции `crypto.pbkdf2()`, `crypto.scrypt()`.
- Асинхронное сжатие через `zlib`.

По умолчанию пул содержит 4 потока. Размер настраивается через `UV_THREADPOOL_SIZE`.

Важно различать:

- Event Loop - выполняет JavaScript callbacks.
- Thread pool - выполняет определённые нативные операции в фоновых потоках.
- `worker_threads` - позволяет параллельно выполнять JavaScript в отдельных потоках.

Большинство сетевых операций Node.js использует неблокирующий ввод-вывод ОС и не занимает отдельный поток из thread pool на каждое соединение.

Перегрузка пула длительными задачами увеличивает задержки других операций, использующих тот же пул.&#x20;

# Чем CommonJS отличается от ESM в Node.js?

CommonJS (CJS) и ECMAScript Modules (ESM) - две системы модулей, поддерживаемые Node.js.

| Особенность       | CommonJS           | ESM                                              |
|-------------------|--------------------|--------------------------------------------------|
| Импорт            | `require()`        | `import`                                         |
| Экспорт           | `module.exports`   | `export`                                         |
| Загрузка          | Обычно синхронная  | Поддерживает асинхронное связывание и выполнение |
| Top-level `await` | Нет                | Да                                               |
| Расширение        | `.cjs`             | `.mjs`                                           |
| Стандарт          | Node.js-экосистема | ECMAScript                                       |

Для `.js` файлов система модулей определяется настройкой `"type"` в `package.json` либо, при отсутствии явного указания, правилами определения формата Node.js.

CommonJS:

```
const fs = require('node:fs');

module.exports = { fs };
```

ESM:

```
import fs from 'node:fs';

export { fs };
```

ESM использует статически анализируемые импорты и live bindings - импортированные привязки отражают изменения экспортируемых значений.

Системы модулей совместимы не полностью:

- ESM может импортировать CommonJS.
- CommonJS может загружать ESM через `import()`.
- Современные версии Node.js также позволяют `require()` загружать синхронные ESM без top-level `await`.
- В ESM отсутствуют CommonJS-переменные `__dirname` и `__filename`; вместо них доступны `import.meta` и связанные API.

Для новых проектов обычно выбирают ESM, поскольку это стандартная система модулей JavaScript.&#x20;

# Как работают streams и backpressure?

Streams - интерфейс для последовательной обработки данных небольшими частями без необходимости загружать весь объём в память.

Основные типы Node.js Streams:

- `Readable` - источник данных.
- `Writable` - получатель данных.
- `Duplex` - одновременно чтение и запись.
- `Transform` - преобразование данных при передаче.

Например, `fs.createReadStream()` читает файл частями, а `fs.createWriteStream()` записывает их.

Backpressure - механизм регулирования скорости передачи данных, когда получатель обрабатывает их медленнее источника.

При вызове `writable.write(chunk)`:

- `true` означает, что внутренний буфер пока находится ниже порога.
- `false` сигнализирует, что дальнейшую запись следует приостановить.
- Событие `drain` сообщает, что запись можно продолжить.

За управление буферизацией отвечает параметр `highWaterMark`. Это порог, а не строгий предел использования памяти.

Для соединения потоков обычно применяют `pipe()` или `pipeline()`:

```
import { pipeline } from 'node:stream/promises';
import { createReadStream, createWriteStream } from 'node:fs';

await pipeline(
  createReadStream('input.txt'),
  createWriteStream('output.txt')
);
```

`pipeline()` автоматически управляет backpressure, передаёт ошибки и завершает связанные потоки при сбоях.

Главное преимущество - предсказуемое использование памяти при обработке больших файлов и сетевых данных.&#x20;

# Как обработать потоковый HTTP-ответ?

Потоковый HTTP-ответ позволяет обрабатывать данные по мере получения, не ожидая загрузки всего тела ответа.

В современном Node.js глобальный `fetch()` возвращает объект `Response`, у которого `body` представляет собой Web `ReadableStream`.

Пример:

```
const response = await fetch(url);

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}

if (!response.body) {
  throw new Error('Response body is empty');
}

const decoder = new TextDecoder();

for await (const chunk of response.body) {
  const text = decoder.decode(chunk, {
    stream: true
  });

  process.stdout.write(text);
}

process.stdout.write(decoder.decode());
```

Здесь:

1. `fetch()` получает HTTP-ответ.
2. `response.body` предоставляет поток данных.
3. `for await...of` последовательно читает части ответа.
4. `TextDecoder` преобразует байты в текст, корректно обрабатывая символы, разделённые между несколькими частями.

Важные особенности:

- HTTP-чанки не обязательно совпадают с границами строк или JSON-объектов.
- Для NDJSON или SSE необходимо отдельно разбирать границы сообщений.
- `response.text()` и `response.json()` полностью считывают тело, поэтому не подходят для постепенной обработки.
- Нужно учитывать ошибки потока, таймауты и отмену через `AbortController`.

При использовании `node:http` тело ответа представлено Node.js `Readable`, который также можно читать через `for await...of` или передавать через `pipeline()`.

# Что такое EventEmitter?

EventEmitter - класс из модуля `node:events`, реализующий механизм публикации событий и подписки на них.

Он позволяет компонентам взаимодействовать через именованные события без прямого вызова друг друга.

Основные методы:

- `on(event, listener)` - подписка.
- `once(event, listener)` - однократная подписка.
- `emit(event, ...args)` - генерация события.
- `off(event, listener)` - удаление обработчика.

Пример:

```
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();

emitter.on('message', (data) => {
  console.log(data);
});

emitter.emit('message', 'Hello');
```

Ключевая особенность: `emit()` вызывает обработчики синхронно, в порядке их регистрации. EventEmitter сам по себе не делает выполнение асинхронным и не ожидает завершения Promise, возвращённых обработчиками.

Событие `error` имеет специальное поведение: если оно вызвано без обработчика, ошибка по умолчанию приводит к завершению процесса.

EventEmitter используется в потоках, сетевых соединениях и других событийно-ориентированных API Node.js.&#x20;

# Как работают `process.env` и почему их нельзя считать валидацией конфигурации?

`process.env` - объект, предоставляющий доступ к переменным окружения процесса Node.js.

Они используются для передачи конфигурации: адресов сервисов, портов, режимов работы и секретов.

```
const port = process.env.PORT;
const apiUrl = process.env.API_URL;
```

Значения обычно представлены строками, даже если логически обозначают число или boolean.

Например:

```
process.env.DEBUG = 'false';

console.log(Boolean(process.env.DEBUG));
// true
```

Почему `process.env` не является валидацией:

- Переменная может отсутствовать.
- Значение может иметь неправильный формат.
- Строка может не соответствовать ожидаемому типу.
- Значение может выходить за допустимые пределы.
- Несколько переменных могут быть логически несовместимы.

Поэтому конфигурацию необходимо проверять при запуске приложения.

Например:

```
const port = Number(process.env.PORT);

if (!Number.isInteger(port) || port < 1 || port > 65535) {
  throw new Error('Invalid PORT');
}
```

В крупных проектах для этого используют схемы валидации, например `Zod`.

Важно: переменные окружения не становятся автоматически безопасными. Их нельзя без необходимости логировать или передавать в клиентский JavaScript, особенно если они содержат секреты.

# Как организовать proxy между frontend и API в dev-среде?

Dev proxy - прокси-сервер, который перенаправляет запросы frontend-приложения к backend API во время локальной разработки.

Основная задача - обращаться к API через тот же origin, что и frontend, избегая проблем с CORS.

Например:

- Frontend: `http://localhost:5173`.
- Backend: `http://localhost:3000`.
- Запрос frontend: `/api/users`.

В Vite настройка выглядит так:

```
// vite.config.js

export default {
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true
      }
    }
  }
};
```

Теперь вызов:

```
fetch('/api/users');
```

отправляется на Vite dev-сервер, который перенаправляет его на `http://localhost:3000/api/users`.

Особенности:

- `changeOrigin` изменяет заголовок `Host` для целевого сервера.
- `rewrite` позволяет менять путь запроса.
- Для WebSocket-проксирования используется `ws: true`.
- При работе с cookie необходимо учитывать `Domain`, `Path`, `SameSite` и особенности перенаправления.

Важно: dev proxy действует только во время разработки. В production аналогичная маршрутизация должна быть настроена отдельно, например через Nginx или сервер приложения.&#x20;

# Чем middleware в Express отличается от middleware Redux?

В обоих случаях middleware - промежуточная функция, которая перехватывает обработку и может передать управление следующему обработчику.

Различие заключается в том, что именно обрабатывается.

Express middleware работает с HTTP-запросами и ответами:

```
app.use((req, res, next) => {
  console.log(req.method);
  next();
});
```

Middleware может изменять `req` и `res`, проверять авторизацию, логировать запросы, завершать HTTP-ответ или передавать управление через `next()`.

Redux middleware работает с действиями, передаваемыми через `dispatch()`:

```
const logger = store => next => action => {
  console.log(action.type);
  return next(action);
};
```

Оно может перехватывать, изменять и перенаправлять actions, запускать асинхронные операции или использовать текущее состояние через `getState()`.

Основные отличия:

- Express: `req`, `res`, `next` - управление жизненным циклом HTTP-запроса.
- Redux: `store`, `next`, `action` - управление прохождением action к reducer.
- Express: middleware может завершить HTTP-ответ.
- Redux: middleware может остановить передачу action, не вызвав `next(action)`.

В Express 5 отклонённые Promise, возвращённые middleware, автоматически передают ошибку в механизм обработки ошибок.

В Redux `next(action)` передаёт action дальше по цепочке, а `store.dispatch(action)` запускает прохождение через всю цепочку middleware.&#x20;

# Что такое rate limiting и как он помогает backend API?

Rate limiting - ограничение количества запросов, которые клиент может выполнить за определённый период времени.

Он защищает API от чрезмерной нагрузки, случайных всплесков активности и некоторых видов злоупотреблений.

Например, API может разрешать не более 100 запросов в минуту на пользователя. При превышении лимита сервер обычно возвращает `429 Too Many Requests`.

Основные алгоритмы:

- Fixed Window - фиксированное количество запросов за интервал.
- Sliding Window - подсчёт запросов в скользящем временном окне.
- Token Bucket - запросы расходуют токены, которые постепенно восстанавливаются. Позволяет кратковременные всплески нагрузки.
- Leaky Bucket - сглаживает скорость обработки запросов.

Ограничения можно применять по IP-адресу, пользователю, API-ключу или конкретному endpoint.

В распределённой системе счётчики обычно хранят в общем хранилище, например Redis, чтобы несколько экземпляров API использовали единые лимиты.

При превышении лимита полезно возвращать `Retry-After`.

Важно: rate limiting снижает вероятность перегрузки и злоупотреблений, но не заменяет аутентификацию, авторизацию и полноценную защиту от DDoS.

# Как устроить BFF для cookie-based сессий?

BFF (Backend for Frontend) - серверный слой между frontend-приложением и внутренними API, адаптированный под потребности конкретного клиента.

Для cookie-based аутентификации BFF выступает посредником, который управляет пользовательской сессией.

Типичный сценарий:

1. Пользователь отправляет логин и пароль на BFF.
2. BFF проверяет учётные данные через сервис аутентификации.
3. BFF создаёт серверную сессию или получает токены доступа.
4. Браузер получает сессионную cookie с `HttpOnly`, `Secure` и подходящим `SameSite`.
5. При последующих запросах браузер автоматически отправляет cookie на BFF.
6. BFF проверяет сессию, выполняет запросы к внутренним API и возвращает результат клиенту.

Например:

```
Browser
   |
   | Cookie: session=...
   v
  BFF
   |
   | Authorization: Bearer ...
   v
Internal API
```

Преимущества:

- Токены внутренних API можно хранить исключительно на сервере.
- `HttpOnly` не позволяет JavaScript напрямую читать сессионную cookie.
- BFF централизованно управляет сессиями, обновлением токенов и авторизацией.
- Frontend работает с единым API, обычно через тот же origin.

Требования безопасности:

- Проверять сессию на каждом защищённом запросе.
- Использовать HTTPS и безопасные настройки cookie.
- Обеспечить CSRF-защиту для изменяющих состояние операций.
- Проверять права доступа пользователя к каждому ресурсу.
- Хранить состояние сессий в общем хранилище, если BFF масштабируется горизонтально.

`SameSite` снижает риск CSRF, но не во всех сценариях заменяет CSRF-токены или проверку `Origin`.

`HttpOnly` защищает cookie от прямого чтения JavaScript, но не устраняет другие последствия XSS.&#x20;

# Почему нельзя доверять данным, пришедшим от клиента?

Потому что клиентская среда находится вне доверенной границы сервера.

Пользователь может изменять запросы через DevTools, Postman, собственные скрипты или напрямую через HTTP.

Поэтому нельзя считать достоверными:

- Значения из форм и JSON.
- Query-параметры и URL.
- HTTP-заголовки.
- Идентификаторы пользователей и ресурсов.
- Цены, скидки, роли и разрешения.
- Результаты клиентской валидации.

Например, пользователь может изменить:

```
{
  "productId": 123,
  "price": 1
}
```

Если сервер доверяет переданной цене, пользователь сможет попытаться приобрести товар по произвольной стоимости.

Поэтому сервер должен самостоятельно:

1. Проверять формат, типы и ограничения входных данных.
2. Аутентифицировать пользователя.
3. Проверять его права на конкретное действие и ресурс.
4. Проверять бизнес-правила, например актуальную стоимость товара.
5. Безопасно использовать данные в SQL, HTML, файловых путях и других контекстах.

TypeScript не обеспечивает runtime-валидацию, поскольку его типы отсутствуют во время выполнения.

Клиентская валидация нужна для UX, а серверная - для обеспечения корректности данных и безопасности.

# Как обрабатывать таймауты и отмену исходящих HTTP-запросов на сервере?

Исходящие HTTP-запросы могут зависнуть из-за сетевых проблем, перегрузки внешнего сервиса или медленной передачи данных.

Поэтому сервер должен ограничивать продолжительность запросов и уметь отменять операции, которые больше не нужны.

В современном Node.js для `fetch()` используют `AbortController` и `AbortSignal`.

Пример таймаута:

```
const response = await fetch(apiUrl, {
  signal: AbortSignal.timeout(5000)
});
```

Через 5 секунд сигнал будет отменён, и незавершённая операция прервётся.

Если необходимо учитывать и отключение клиента, и серверный дедлайн, можно объединить сигналы:

```
const signal = AbortSignal.any([
  clientSignal,
  AbortSignal.timeout(5000)
]);

const response = await fetch(apiUrl, { signal });
```

`clientSignal` здесь - сигнал, который серверный обработчик отменяет при прекращении клиентского запроса.

Важные особенности:

- Таймаут должен приводить к реальной отмене операции, а не только к прекращению ожидания Promise.
- Нужно обрабатывать ошибки сети, таймауты и обычные HTTP-ответы с ошибочными статусами.
- `fetch()` не отклоняет Promise автоматически при HTTP-статусах `4xx` или `5xx`.
- При отмене необходимо освобождать связанные ресурсы и прекращать чтение потоков.
- Повторные запросы допустимы только с учётом идемпотентности операции.

Для `node:http` вызов `request.setTimeout()` сам по себе не отменяет запрос. При наступлении таймаута необходимо явно вызвать `request.destroy()` или использовать механизм отмены.

Практически важно различать таймаут соединения, таймаут ожидания ответа и общий дедлайн операции. Их поддержка зависит от используемого HTTP-клиента.&#x20;

# Чем serverless function отличается от долгоживущего Node.js сервера?

Долгоживущий Node.js сервер - постоянно работающий процесс, который самостоятельно принимает и обрабатывает запросы.

Например:

```
import http from 'node:http';

http.createServer((req, res) => {
  res.end('Hello');
}).listen(3000);
```

Serverless function - функция, которую платформа запускает в ответ на событие, например HTTP-запрос, сообщение из очереди или запланированное задание.

Примеры платформ: AWS Lambda, Azure Functions, Google Cloud Functions.

Основные различия:

| Критерий            | Node.js сервер                                  | Serverless function                                   |
|---------------------|-------------------------------------------------|-------------------------------------------------------|
| Жизненный цикл      | Постоянно работающий процесс                    | Экземпляры запускаются и переиспользуются платформой  |
| Масштабирование     | Настраивается разработчиком или инфраструктурой | Обычно управляется платформой                         |
| Состояние в памяти  | Сохраняется на протяжении жизни процесса        | Может сохраниться между вызовами, но не гарантируется |
| Запуск              | Обычно процесс уже работает                     | Возможен cold start                                   |
| Ограничения времени | Определяются инфраструктурой                    | Часто есть лимит выполнения                           |
| Оплата              | Обычно за выделенные ресурсы                    | Часто за вызовы и потреблённые ресурсы                |

Cold start - дополнительная задержка, возникающая при создании нового окружения выполнения функции.

При повторных вызовах платформа может использовать уже существующий экземпляр, сохраняя инициализированные подключения и объекты.

Однако полагаться на сохранность памяти между вызовами нельзя.

Особенности serverless:

- Для постоянного состояния используют внешние хранилища.
- Длительные задачи могут упираться в ограничения платформы.
- Поддержка WebSocket и streaming зависит от провайдера.
- Масштабирование может создавать большое количество одновременных подключений к базе данных.
- Холодные запуски могут увеличивать задержки ответов.

Serverless удобен для независимых обработчиков событий и нагрузки с переменной интенсивностью.

Долгоживущий Node.js сервер предоставляет больше контроля над соединениями, ресурсами и жизненным циклом приложения.&#x20;
