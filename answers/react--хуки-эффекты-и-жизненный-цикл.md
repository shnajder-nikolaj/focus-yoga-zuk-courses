# Какие правила вызова React Hooks существуют и почему?

React Hooks должны вызываться по следующим правилам:

1. Только на верхнем уровне React-компонента или пользовательского хука. Нельзя вызывать хуки внутри условий, циклов, обработчиков событий, вложенных функций или после условного `return`.
2. Только из React-компонентов и других хуков. Нельзя вызывать их из обычных JavaScript-функций.
3. В одинаковом порядке при каждом рендере. Нельзя изменять последовательность вызовов хуков между рендерами.

React связывает состояние хуков с их позицией в последовательности вызовов. Если порядок изменится, React может сопоставить состояние не с тем хуком.

Исключение в React 19: API `use()` допускает вызовы внутри условий и циклов, но по-прежнему должен использоваться во время рендеринга компонента или хука.

Соблюдение правил проверяет `eslint-plugin-react-hooks`.

# Как работает `useState` и батчинг обновлений?

`useState` позволяет компоненту хранить состояние между рендерами.

```
const [count, setCount] = useState(0);
```

- `count` - значение состояния для текущего рендера
- `setCount` - функция, которая ставит обновление состояния в очередь
- `useState(0)` - начальное значение, используемое при инициализации состояния

Вызов `setCount` не изменяет переменную `count` в текущем рендере. Он запрашивает новый рендер, в котором React вычислит следующее состояние.

Батчинг (batching) - объединение нескольких обновлений состояния, позволяющее избежать лишних рендеров.

```
function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}
```

Если `count === 0`, результат будет `1`, поскольку все три вызова используют значение из одного рендера.

```
function handleClick() {
  setCount(prev => prev + 1);
  setCount(prev => prev + 1);
  setCount(prev => prev + 1);
}
```

Теперь результат будет `3`, поскольку каждое обновление использует результат предыдущего.

Начиная с React 18, при использовании `createRoot` автоматический батчинг работает не только в обработчиках React, но и в `Promise`, `setTimeout` и других асинхронных обработчиках.

React не объединяет произвольные независимые пользовательские события в один батч. Для принудительного синхронного применения обновления существует `flushSync`, но использовать его следует редко.

# Когда передавать функцию в `setState`?

Функциональное обновление нужно, когда новое состояние зависит от предыдущего.

```
setCount(prev => prev + 1);
```

Это особенно важно:

- При нескольких последовательных обновлениях состояния
- В асинхронных обработчиках с потенциально устаревшими значениями
- В таймерах и подписках, изменяющих состояние относительно предыдущего

React помещает функции обновления в очередь и последовательно применяет их к актуальному состоянию.

Если новое значение не зависит от предыдущего, достаточно прямого обновления:

```
setIsOpen(true);
```

Функция обновления должна быть чистой: не изменять существующие объекты и не выполнять побочные эффекты. В `StrictMode` React может вызывать её дважды в режиме разработки.

# Что такое stale closure в React-компоненте?

Stale closure - ситуация, когда функция продолжает использовать устаревшие значения `state` или `props`, захваченные замыканием во время предыдущего рендера.

Пример:

```
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => {
    console.log(count);
  }, 1000);

  return () => clearInterval(id);
}, []);
```

Эффект создаётся с первоначальным значением `count`. Поскольку массив зависимостей пуст, интервал не пересоздаётся и продолжает выводить старое значение.

Способы решения:

- Указывать необходимые зависимости эффекта
- Использовать функциональные обновления, если требуется изменить состояние относительно предыдущего
- Использовать `useRef`, когда нужен доступ к изменяемому значению без нового рендера
- Использовать `useEffectEvent` (React 19.2+) для логики внутри эффектов, которая должна читать актуальные значения без повторной синхронизации эффекта

Основная причина проблемы - каждый рендер создаёт собственные замыкания, сохраняющие значения этого рендера.

# Чем `useReducer` отличается от `useState`?

Оба хука управляют состоянием компонента, но отличаются способом вычисления нового состояния.

`useState` обновляет состояние напрямую:

```
const [count, setCount] = useState(0);

setCount(prev => prev + 1);
```

`useReducer` передаёт действие (`action`) функции-редьюсеру (`reducer`), которая вычисляет следующее состояние:

```
function reducer(state, action) {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };

    case "reset":
      return { count: 0 };

    default:
      return state;
  }
}

const [state, dispatch] = useReducer(reducer, { count: 0 });

dispatch({ type: "increment" });
```

`useReducer` полезен, когда:

- Состояние имеет сложную структуру
- Несколько полей должны изменяться согласованно
- Существует много типов обновлений
- Требуется вынести бизнес-логику изменения состояния из обработчиков

Редьюсер должен быть чистой функцией и возвращать новое состояние без мутации предыдущего.

Важно: `useReducer` сам по себе не предотвращает лишние рендеры и не делает обновления асинхронными.

# Какие случаи подходят для `useContext`?

`useContext` позволяет читать данные из ближайшего соответствующего Context Provider без передачи их через каждый промежуточный компонент.

Подходящие случаи:

- Текущая тема оформления
- Локализация и языковые настройки
- Информация о текущем пользователе
- Настройки приложения
- Общие зависимости и сервисы

Пример:

```
const ThemeContext = createContext("light");

function Button() {
  const theme = useContext(ThemeContext);

  return <button className={theme}>Click</button>;
}
```

Context Provider:

```
<ThemeContext value="dark">
  <Button />
</ThemeContext>
```

В React 18 используется синтаксис `<ThemeContext.Provider>`. Начиная с React 19 можно использовать сам `<ThemeContext>` как Provider.

Ограничение: Context не является полноценным хранилищем состояния. Он передаёт значение по дереву компонентов, а управление состоянием остаётся задачей `useState`, `useReducer` или внешнего хранилища.

Для часто изменяемого состояния большого приложения Context может быть неэффективен, поскольку изменение его значения уведомляет всех потребителей.

# Когда изменение Context приводит к повторным рендерам?

React повторно рендерит компоненты, использующие `useContext`, когда значение ближайшего Provider изменяется по сравнению с предыдущим значением.

Для сравнения используется `Object.is`.

```
const value = { theme: "dark" };

<ThemeContext value={value}>
  <Child />
</ThemeContext>
```

Если объект `value` создаётся заново при каждом рендере Provider, его ссылка изменяется, даже если содержимое осталось прежним. Это приводит к обновлению потребителей Context.

Для стабилизации значения можно использовать `useMemo`:

```
const value = useMemo(
  () => ({ theme, setTheme }),
  [theme]
);
```

Особенности:

- Изменение Context обновляет подписанные на него компоненты
- `React.memo` не блокирует обновления, вызванные изменением используемого Context
- При неизменном значении Context его потребители всё равно могут рендериться по другим причинам, например из-за обновления родителя
- Изменение одного поля общего объекта Context может привести к повторному рендеру всех потребителей этого объекта

Для разделения независимых обновлений можно использовать несколько Context или внешнее хранилище с селекторами.

# Для чего нужен `useEffect`?

`useEffect` предназначен для синхронизации React-компонента с внешними системами после применения изменений React.

Типичные задачи:

- Подписка на браузерные события
- Управление таймерами
- Подключение к WebSocket
- Синхронизация со сторонними библиотеками
- Выполнение сетевых запросов, когда загрузкой не управляет фреймворк или специализированный механизм данных

Пример:

```
useEffect(() => {
  const handleResize = () => {
    console.log(window.innerWidth);
  };

  window.addEventListener("resize", handleResize);

  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
```

Эффект состоит из двух частей:

- Setup - устанавливает синхронизацию
- Cleanup - отменяет установленную синхронизацию

`useEffect` выполняется только на клиенте после commit-фазы. Обычно React позволяет браузеру отрисовать изменения перед его выполнением, но при обновлениях, вызванных взаимодействием пользователя, эффект может выполниться до отрисовки.

# Какую логику не стоит помещать в `useEffect`?

В `useEffect` не следует помещать логику, для которой не требуется синхронизация с внешней системой.

1\. Вычисление производных данных

Неправильно:

```
const [fullName, setFullName] = useState("");

useEffect(() => {
  setFullName(firstName + " " + lastName);
}, [firstName, lastName]);
```

Правильно:

```
const fullName = `${firstName} ${lastName}`;
```

2\. Обработка пользовательских действий

Отправку формы, обработку кликов и другие действия, вызванные конкретным событием, обычно следует выполнять непосредственно в обработчиках событий.

3\. Синхронизация одного состояния с другим без необходимости

Избыточное состояние создаёт дополнительные обновления и риск рассинхронизации.

4\. Дорогие чистые вычисления

Их следует выполнять во время рендера, при необходимости используя `useMemo`.

5\. Управление обычным потоком данных

Не следует использовать эффекты для передачи данных между компонентами, когда достаточно `props`, Context или подъёма состояния.

Основной принцип: если компоненту не требуется взаимодействовать с внешней системой, эффект, скорее всего, не нужен.

# Как работают зависимости в `useEffect`?

Массив зависимостей определяет, когда React должен повторно синхронизировать эффект.

```
useEffect(() => {
  // Логика эффекта
}, [dependency]);
```

Три варианта:

- Без массива зависимостей - после каждого commit соответствующего рендера
- \- после монтирования, с cleanup при размонтировании
- `[a, b]` - после монтирования и при изменении хотя бы одной зависимости

React сравнивает зависимости предыдущего и текущего рендера через `Object.is`.

Зависимостями являются реактивные значения, используемые внутри эффекта: `props`, `state`, а также переменные и функции, объявленные непосредственно в компоненте.

```
useEffect(() => {
  document.title = `Count: ${count}`;
}, [count]);
```

Важные особенности:

- Объекты и функции сравниваются по ссылке
- Созданные при каждом рендере объекты могут вызывать лишние запуски
- Нельзя произвольно исключать используемые реактивные значения из зависимостей
- Пустой массив не означает гарантированный однократный запуск, особенно в `StrictMode`

Актуальность зависимостей проверяет правило `exhaustive-deps`.

# Когда вызывается cleanup-функция эффекта?

Cleanup - функция очистки, возвращаемая из `useEffect`.

Она вызывается:

1. При размонтировании компонента
2. Перед повторным выполнением эффекта, если изменились его зависимости
3. Во время дополнительного цикла проверки эффектов в `StrictMode` в режиме разработки

```
useEffect(() => {
  const id = setInterval(() => {
    console.log("Tick");
  }, 1000);

  return () => clearInterval(id);
}, []);
```

При изменении зависимостей порядок следующий:

Cleanup предыдущего эффекта -> Setup нового эффекта.

Cleanup необходим для освобождения ресурсов: удаления обработчиков, отмены таймеров, закрытия соединений и прекращения подписок.

Он также помогает предотвращать устаревшие асинхронные обновления.

Cleanup не предназначен для выполнения произвольной бизнес-логики при закрытии компонента. Его задача - корректно отменить то, что было настроено эффектом.

# Почему эффект может выполняться повторно в `StrictMode`?

`StrictMode` в режиме разработки выполняет дополнительные проверки, помогающие обнаруживать побочные эффекты и ошибки очистки ресурсов.

При первоначальном монтировании, если `StrictMode` включён на уровне корня приложения, React запускает дополнительный цикл:

```
Setup -> Cleanup -> Setup
```

Это позволяет обнаружить:

- Отсутствующую очистку подписок и таймеров
- Повторное создание соединений без закрытия предыдущих
- Побочные эффекты, зависящие от количества запусков
- Некорректную инициализацию внешних ресурсов

Дополнительно React повторно вызывает функции рендера для обнаружения нечистых вычислений.

Важно: дополнительные проверки работают только в development. В production они не выполняются.

Если `StrictMode` включён не на уровне корня, React не выполняет дополнительный запуск эффектов при первоначальном монтировании.

Правильное решение - обеспечить симметричность setup и cleanup, а не подавлять повторный запуск через `useRef`.

# Чем `useEffect` отличается от `useLayoutEffect`?

Оба хука предназначены для побочных эффектов, но отличаются моментом выполнения относительно отрисовки браузера.

`useEffect`:

- Обычно выполняется после отрисовки браузером
- Не предназначен для блокирования отображения интерфейса
- Подходит для подписок, сетевых запросов и большинства внешних синхронизаций

`useLayoutEffect`:

- Выполняется после изменения DOM, но до следующей отрисовки браузера
- Блокирует отрисовку до завершения эффекта и синхронных обновлений, вызванных из него
- Используется для измерения DOM, расчёта размеров и позиционирования элементов без визуального мерцания

Пример:

```
useLayoutEffect(() => {
  const rect = elementRef.current.getBoundingClientRect();

  setHeight(rect.height);
}, []);
```

`useLayoutEffect` полезен, когда пользователь не должен видеть промежуточное положение элемента.

Ограничения: тяжёлые вычисления внутри `useLayoutEffect` задерживают отображение страницы. Оба хука работают только на клиенте; при серверном рендеринге эффекты не выполняются.

# Для чего нужен `useInsertionEffect`?

`useInsertionEffect` предназначен преимущественно для библиотек CSS-in-JS, которые динамически добавляют CSS-правила в документ.

Он позволяет вставить стили до выполнения layout-эффектов, чтобы измерения элементов учитывали актуальные CSS-правила.

```
useInsertionEffect(() => {
  // Добавление CSS-правил
}, [styles]);
```

Особенности:

- Выполняется до `useLayoutEffect`
- Не предназначен для обычной логики компонентов
- Не позволяет обновлять React state внутри эффекта
- Не гарантирует, что DOM уже обновлён
- Не гарантирует доступность прикреплённых `ref`

Использовать `useInsertionEffect` в прикладных компонентах практически никогда не требуется.

# Как корректно синхронизировать React-компонент с внешней системой?

Синхронизацию следует организовывать через эффект, который создаёт подключение, поддерживает его актуальность и корректно освобождает ресурсы.

Пример подключения к внешнему сервису:

```
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);

  connection.connect();

  return () => {
    connection.disconnect();
  };
}, [serverUrl, roomId]);
```

Принцип работы:

1. React применяет изменения компонента
2. Эффект устанавливает соединение
3. При изменении `serverUrl` или `roomId` React закрывает старое соединение
4. Создаётся новое соединение с актуальными параметрами
5. При размонтировании соединение закрывается

Ключевые требования:

- Указывать все реактивные зависимости
- Обеспечивать симметричность подключения и отключения
- Не создавать внешние ресурсы непосредственно во время рендера
- Не использовать эффект для синхронизации данных, которые можно вычислить из `props` и `state`

Для внешних хранилищ состояния, предоставляющих подписку и снимок данных, предпочтителен `useSyncExternalStore`.

# Как избежать бесконечного цикла рендеров из-за эффекта?

Бесконечный цикл возникает, когда эффект изменяет состояние, новое состояние вызывает рендер, а после рендера эффект снова запускается.

Пример:

```
useEffect(() => {
  setCount(count + 1);
}, [count]);
```

После каждого изменения `count` эффект запускается заново.

Другой распространённый случай - нестабильная ссылочная зависимость:

```
const options = { enabled: true };

useEffect(() => {
  setData(options);
}, [options]);
```

При каждом рендере создаётся новый объект `options`. Эффект видит новую ссылку, обновляет состояние и запускает следующий рендер.

Способы предотвращения:

- Не обновлять состояние внутри эффекта без необходимости
- Вычислять производные данные во время рендера
- Переносить создание объектов и функций внутрь эффекта, если это возможно
- Использовать `useMemo` и `useCallback`, когда действительно нужна стабильность ссылок
- Применять функциональные обновления, если они позволяют убрать ненужную зависимость от предыдущего состояния

Не следует исправлять бесконечный цикл простым удалением зависимостей: это может привести к stale closure.

# Как отменять сетевой запрос при размонтировании или смене параметров?

Для отмены `fetch` используется `AbortController`.

```
useEffect(() => {
  const controller = new AbortController();

  async function load() {
    try {
      const response = await fetch(`/api/users/${userId}`, {
        signal: controller.signal
      });

      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`);
      }

      const data = await response.json();
      setUser(data);
    } catch (error) {
      if (!controller.signal.aborted) {
        setError(error);
      }
    }
  }

  load();

  return () => controller.abort();
}, [userId]);
```

При изменении `userId` React вызывает cleanup предыдущего эффекта, отменяет старый запрос и запускает новый.

При размонтировании запрос также отменяется.

Важные нюансы:

- Отмена запроса не гарантирует прекращение обработки на сервере
- `fetch` при отмене обычно отклоняется с ошибкой `AbortError`
- `AbortController` предотвращает дальнейшее ожидание и обработку отменённого запроса на клиенте
- Для защиты от race conditions дополнительно можно использовать флаг актуальности запроса, особенно когда асинхронная операция не поддерживает отмену

# Чем `useMemo` отличается от `useCallback`?

Оба хука используются для мемоизации, но сохраняют разные результаты.

`useMemo` сохраняет результат вычисления:

```
const filteredItems = useMemo(() => {
  return items.filter(item => item.active);
}, [items]);
```

Вычисление повторяется при изменении зависимостей.

`useCallback` сохраняет ссылку на функцию:

```
const handleClick = useCallback(() => {
  setCount(prev => prev + 1);
}, []);
```

Функция сохраняет идентичность между рендерами, пока зависимости не изменились.

Концептуально:

```
useCallback(fn, deps) === useMemo(() => fn, deps)
```

Основные сценарии:

- `useMemo` - дорогостоящие вычисления, стабильные объекты и значения
- `useCallback` - стабильные обработчики для мемоизированных компонентов и зависимостей других хуков

Важно: ни один из хуков не предотвращает рендер сам по себе. `useCallback` не отменяет создание переданного ему функционального выражения, а сохраняет возвращаемую React ссылку.

Начиная с React Compiler ручная мемоизация во многих случаях может быть автоматизирована.

# В каких случаях мемоизация ухудшает производительность?

Мемоизация имеет собственную стоимость:

- React хранит мемоизированные значения и зависимости
- При рендерах требуется сравнивать зависимости
- Мемоизированные объекты могут дольше удерживаться в памяти
- Лишняя мемоизация усложняет код и поддержку

Пример:

```
const doubled = useMemo(() => count * 2, [count]);
```

Обычное вычисление `count * 2` настолько дешёвое, что мемоизация здесь не даёт практической пользы.

Также мемоизация малоэффективна, если зависимости изменяются на каждом рендере:

```
const options = { limit: 10 };

const result = useMemo(
  () => calculate(options),
  [options]
);
```

Объект `options` каждый раз новый, поэтому кеш постоянно инвалидируется.

Правильный критерий: мемоизация должна сокращать реальные затраты на вычисления или предотвращать значимые лишние рендеры.

Решение желательно принимать по результатам профилирования, а не применять `useMemo` и `useCallback` ко всем значениям.

# Для чего нужен `useRef` помимо доступа к DOM?

`useRef` предоставляет изменяемый объект с полем `current`, который сохраняется между рендерами.

```
const ref = useRef(initialValue);
```

Изменение `ref.current` не вызывает повторный рендер.

Помимо доступа к DOM, `useRef` используют для:

- Хранения идентификаторов таймеров
- Сохранения экземпляров внешних объектов
- Хранения предыдущих значений
- Сохранения данных, необходимых обработчикам, но не влияющих непосредственно на отображение
- Хранения ссылок на `AbortController`, WebSocket и другие ресурсы

Пример:

```
const timerRef = useRef(null);

function startTimer() {
  clearTimeout(timerRef.current);

  timerRef.current = setTimeout(() => {
    console.log("Done");
  }, 1000);
}
```

Отличие от `useState`:

- `useState` хранит данные, изменения которых должны отражаться в UI
- `useRef` хранит изменяемые значения, которые сами по себе не должны вызывать рендер

Ограничение: чтение и изменение `ref.current` во время рендера обычно нарушает принцип чистоты компонентов. Исключение - предсказуемая однократная инициализация.

`useRef` не является механизмом реактивности.

# Как организовать `useImperativeHandle` и в каких случаях он оправдан?

`useImperativeHandle` позволяет компоненту управлять тем, какие методы и значения доступны родителю через `ref`.

Пример для React 19:

```
function CustomInput({ ref }) {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus() {
      inputRef.current?.focus();
    },

    clear() {
      if (inputRef.current) {
        inputRef.current.value = "";
      }
    }
  }), []);

  return <input ref={inputRef} />;
}
```

Родительский компонент:

```
const inputRef = useRef(null);

<CustomInput ref={inputRef} />;

inputRef.current?.focus();
```

В React 18 и более ранних версиях для передачи `ref` в функциональный компонент требуется `forwardRef`.

Когда оправдано:

- Программное управление фокусом
- Прокрутка к определённому элементу
- Запуск анимации
- Интеграция с DOM API или сторонними императивными библиотеками

Использовать `useImperativeHandle` для обычной передачи данных между компонентами не следует. Для этого предпочтительны `props` и `state`.

Публичный интерфейс должен быть минимальным: предоставлять конкретные операции, а не полный доступ к внутреннему состоянию или DOM.

# Как спроектировать собственный custom hook?

Custom hook - JavaScript-функция, которая начинается с `use` и инкапсулирует переиспользуемую логику React Hooks.

Пример:

```
function useWindowWidth() {
  const [width, setWidth] = useState(
    () => typeof window !== "undefined"
      ? window.innerWidth
      : 0
  );

  useEffect(() => {
    const update = () => {
      setWidth(window.innerWidth);
    };

    update();

    window.addEventListener("resize", update);

    return () => {
      window.removeEventListener("resize", update);
    };
  }, []);

  return width;
}
```

Использование:

```
function Component() {
  const width = useWindowWidth();

  return <div>{width}px</div>;
}
```

Принципы проектирования:

1. Одна ответственность. Хук должен решать конкретную задачу.
2. Понятный API. Принимать необходимые параметры и возвращать удобные значения или методы.
3. Соблюдение правил Hooks. Хуки вызываются только на верхнем уровне.
4. Управление ресурсами. Подписки, таймеры и соединения должны корректно очищаться.
5. Управление зависимостями. Не допускать stale closure и ненужных повторных запусков.
6. Обработка ошибок и граничных случаев. Учитывать SSR, размонтирование и асинхронность там, где это применимо.

Важно: каждый вызов custom hook создаёт собственное состояние. Использование одного и того же хука в разных компонентах не означает автоматического совместного использования данных.

# Что такое `useSyncExternalStore` и зачем он библиотекам состояния?

`useSyncExternalStore` предназначен для подписки React-компонента на внешнее хранилище данных.

```
const state = useSyncExternalStore(
  subscribe,
  getSnapshot,
  getServerSnapshot
);
```

Аргументы:

- `subscribe` - подписывает компонент на изменения хранилища и возвращает функцию отписки
- `getSnapshot` - возвращает актуальный снимок данных
- `getServerSnapshot` - необязательная функция, предоставляющая снимок для SSR и гидратации

Пример:

```
const isOnline = useSyncExternalStore(
  subscribeToOnlineStatus,
  () => navigator.onLine,
  () => true
);
```

React отслеживает изменения внешнего хранилища и обновляет компонент, если результат `getSnapshot` изменился по сравнению с предыдущим по `Object.is`.

Зачем это библиотекам состояния:

- Обеспечивает согласованность данных при конкурентном рендеринге
- Предотвращает tearing - ситуацию, когда компоненты одного интерфейса отображают разные версии общего состояния
- Позволяет интегрировать React с хранилищами, существующими вне его системы состояния
- Поддерживает серверный рендеринг через `getServerSnapshot`

Важно: `getSnapshot` должен возвращать стабильное значение, пока данные не изменились. Для изменяемых объектов необходимо возвращать кешированный неизменяемый снимок, иначе возможен бесконечный цикл рендеров.

# Для чего нужен `useId` и почему это не замена ключам списка?

`useId` генерирует уникальный идентификатор, подходящий для связывания HTML-элементов и атрибутов доступности.

```
function Input() {
  const id = useId();

  return (
    <>
      <label htmlFor={id}>Email</label>
      <input id={id} type="email" />
    </>
  );
}
```

Основное применение:

- Связь `label` и `input`
- Атрибуты `aria-labelledby` и `aria-describedby`
- Идентификаторы элементов, которым необходима уникальность в документе

`useId` поддерживает согласованную генерацию идентификаторов при SSR и гидратации, если структура дерева React согласована.

Почему нельзя использовать вместо `key`:

`key` позволяет React определять идентичность элементов списка между рендерами.

```
items.map(item => (
  <Item key={item.id} />
));
```

`useId` связан с позицией вызова в дереве компонентов, а не с идентичностью данных.

Кроме того, вызывать `useId` внутри цикла нельзя по правилам Hooks.

Для ключей следует использовать стабильные идентификаторы самих данных, например `item.id`.

# Чем `useTransition` отличается от `useDeferredValue`?

Оба хука помогают сохранять отзывчивость интерфейса при дорогостоящих обновлениях, но работают по-разному.

`useTransition` позволяет пометить конкретные обновления состояния как менее приоритетные.

```
const [isPending, startTransition] = useTransition();

function handleChange(value) {
  startTransition(() => {
    setFilter(value);
  });
}
```

React может прервать рендеринг такого обновления ради более приоритетного действия пользователя.

`isPending` показывает, продолжается ли Transition.

`useDeferredValue` позволяет использовать отложенную версию уже существующего значения.

```
const [query, setQuery] = useState("");

const deferredQuery = useDeferredValue(query);
```

`query` обновляется сразу, а `deferredQuery` может временно сохранять предыдущее значение, пока React выполняет фоновый рендеринг.

Основное различие:

- `useTransition` - когда разработчик контролирует вызов обновления состояния
- `useDeferredValue` - когда значение уже поступает извне или требуется отложить обновление зависимой части интерфейса

Важные ограничения:

- Transition нельзя использовать для управления значением текстового `input`
- `useDeferredValue` не является debounce и не задаёт фиксированную задержку
- Оба механизма управляют приоритетом рендеринга, а не ускоряют сами вычисления
- После `await` внутри `startTransition` обновления состояния пока требуется дополнительно оборачивать в `startTransition`

# Как `useOptimistic` помогает отображать оптимистические изменения?

`useOptimistic` позволяет временно отобразить ожидаемый результат операции до подтверждения сервером.

Например, пользователь нажимает «Нравится», и интерфейс немедленно показывает новое состояние, не ожидая завершения запроса.

```
const [liked, setLiked] = useState(false);

const [optimisticLiked, setOptimisticLiked] =
  useOptimistic(liked);
```

Обновление:

```
function handleLike() {
  startTransition(async () => {
    setOptimisticLiked(true);

    try {
      await saveLike();

      startTransition(() => {
        setLiked(true);
      });
    } catch (error) {
      // Отобразить ошибку
    }
  });
}
```

Принцип:

1. `setOptimisticLiked(true)` немедленно обновляет отображаемое состояние
2. Запускается асинхронная операция
3. При успехе обновляется основное состояние `liked`
4. При завершении Action оптимистическое состояние возвращается к актуальному основному состоянию

Если запрос завершился ошибкой и основное состояние не изменилось, интерфейс автоматически возвращается к предыдущему значению.

`useOptimistic` также поддерживает reducer для сложных изменений:

```
const [optimisticItems, addOptimisticItem] = useOptimistic(
  items,
  (current, newItem) => [
    ...current,
    { ...newItem, pending: true }
  ]
);
```

Важно: оптимистические обновления должны выполняться внутри Action или Transition. Для корректной обработки ошибок необходимо отдельно реализовать отображение ошибки и, при необходимости, повторную отправку.

# Как использовать `useActionState`?

`useActionState` - хук React 19+, предназначенный для управления состоянием асинхронных и синхронных Actions, в том числе отправки форм.

```
const [state, formAction, isPending] = useActionState(
  action,
  initialState
);
```

- `state` - результат последнего завершённого Action
- `formAction` - функция запуска Action
- `isPending` - признак выполняющегося действия

Пример:

```
async function saveUser(previousState, formData) {
  const name = formData.get("name");

  try {
    const response = await fetch("/api/user", {
      method: "POST",
      headers: {
        "Content-Type": "application/json"
      },
      body: JSON.stringify({ name })
    });

    if (!response.ok) {
      throw new Error("Save failed");
    }

    return { success: true, error: null };
  } catch {
    return { success: false, error: "Save failed" };
  }
}

function UserForm() {
  const [state, formAction, isPending] = useActionState(
    saveUser,
    { success: false, error: null }
  );

  return (
    <form action={formAction}>
      <input name="name" />

      <button disabled={isPending}>
        {isPending ? "Saving..." : "Save"}
      </button>

      {state.error && <p>{state.error}</p>}
      {state.success && <p>Saved</p>}
    </form>
  );
}
```

Особенности:

- Первый аргумент Action получает предыдущее состояние
- Второй аргумент получает данные действия, например `FormData`
- Action может выполнять асинхронные операции и побочные эффекты
- React последовательно обрабатывает несколько Actions одного хука
- При использовании с `<form action={formAction}>` React управляет отправкой формы как Action
- Для программного вызова `formAction` вне Action prop используется `startTransition`

При использовании Server Functions поддерживается интеграция с серверными действиями и progressive enhancement.

# Что делает `use` в React и какие условия применения у него есть?

`use` - API React 19+, позволяющий читать ресурсы во время рендеринга, прежде всего `Promise` и Context.

Работа с Promise:

```
function UserProfile({ userPromise }) {
  const user = use(userPromise);

  return <h1>{user.name}</h1>;
}
```

Если Promise ещё не завершился, React приостанавливает рендеринг компонента через Suspense.

```
<Suspense fallback={<p>Loading...</p>}>
  <UserProfile userPromise={userPromise} />
</Suspense>
```

После выполнения Promise React продолжает рендеринг с полученными данными.

Если Promise отклоняется, ошибка передаётся ближайшему Error Boundary.

Работа с Context:

```
const theme = use(ThemeContext);
```

Это аналогично `useContext`, но допускает условные вызовы.

Ключевые особенности и ограничения:

- `use` можно вызывать внутри условий и циклов
- Вызывать `use` необходимо во время рендеринга React-компонента или хука
- `use(promise)` нельзя оборачивать в `try/catch`; для ошибок используется Error Boundary
- Promise должен иметь стабильную идентичность между рендерами, обычно обеспечиваемую кешированием
- Нельзя создавать новый `fetch()` непосредственно внутри каждого рендера и передавать полученный Promise в `use`
- Promise, передаваемый из Server Component в Client Component, должен возвращать сериализуемые данные
- Чтение Context через `use` не поддерживается в Server Components

Для `use(promise)` обычно необходим Suspense boundary, а само создание и кеширование Promise лучше поручать фреймворку или специализированному источнику данных.

# Как избежать утечек ресурсов при закрытии React-компонента с соединением?

Необходимо освобождать все внешние ресурсы в cleanup-функции `useEffect`.

Пример с WebSocket:

```
useEffect(() => {
  const socket = new WebSocket(url);

  function handleMessage(event) {
    console.log(event.data);
  }

  socket.addEventListener("message", handleMessage);

  return () => {
    socket.removeEventListener("message", handleMessage);
    socket.close();
  };
}, [url]);
```

При размонтировании или изменении `url` React удаляет обработчик и закрывает соединение.

Что необходимо учитывать:

- Закрывать WebSocket, EventSource и другие соединения
- Отменять таймеры и интервалы
- Удалять обработчики событий
- Отписываться от внешних хранилищ и потоков данных
- Отменять активные запросы через `AbortController`
- Останавливать механизмы автоматического переподключения

Особенно важно: если соединение реализует автоматическое переподключение, одного `socket.close()` может быть недостаточно. Необходимо также отменить запланированные попытки переподключения.

Эффект должен корректно работать при последовательности `setup -> cleanup -> setup`, которую React проверяет в `StrictMode`.

# Что проверяют правила React Hooks?

Правила React Hooks проверяются через `eslint-plugin-react-hooks`.

Два основных правила:

1\. `rules-of-hooks`

Проверяет корректность вызова хуков:

- Вызов только из React-компонентов и custom hooks
- Отсутствие вызовов внутри условий и циклов
- Отсутствие вызовов после условного `return`
- Отсутствие вызовов внутри обработчиков и обычных вложенных функций
- Сохранение корректного порядка хуков

Для API `use` предусмотрены исключения из ограничений на условия и циклы.

2\. `exhaustive-deps`

Проверяет корректность массивов зависимостей в `useEffect`, `useMemo`, `useCallback` и других поддерживаемых хуках.

```
useEffect(() => {
  console.log(userId);
}, []);
```

Линтер обнаружит, что `userId` отсутствует в зависимостях.

Современный `eslint-plugin-react-hooks` также включает дополнительные проверки, связанные с React Compiler и корректностью React-кода: `purity`, `immutability`, `refs`, `set-state-in-render`, `set-state-in-effect` и другие.

Цель правил - предотвращать нарушения порядка хуков, stale closure, побочные эффекты во время рендера и другие ошибки, несовместимые с моделью работы React.

# Как реализовать `useDebounce`, `usePrevious` и `useOutsideClick`?

1\. `useDebounce`

Возвращает значение с задержкой после последнего изменения.

```
function useDebounce(value, delay = 300) {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);

    return () => clearTimeout(timer);
  }, [value, delay]);

  return debouncedValue;
}
```

Принцип работы:

- При изменении `value` запускается таймер
- Если значение изменилось повторно, предыдущий таймер отменяется
- После периода без изменений обновляется `debouncedValue`

Используется для поиска, фильтрации и сокращения количества запросов.

2\. `usePrevious`

Сохраняет значение предыдущего завершённого рендера.

```
function usePrevious(value) {
  const ref = useRef(undefined);

  useEffect(() => {
    ref.current = value;
  }, [value]);

  return ref.current;
}
```

Поскольку эффект выполняется после рендера, возвращается значение, сохранённое предыдущим выполнением эффекта.

При первоначальном рендере возвращается `undefined`.

Хук полезен для сравнения предыдущего и текущего значения.

3\. `useOutsideClick`

Вызывает обработчик при нажатии вне указанного DOM-элемента.

```
function useOutsideClick(ref, onOutside) {
  useEffect(() => {
    function handlePointerDown(event) {
      const element = ref.current;

      if (element && !element.contains(event.target)) {
        onOutside(event);
      }
    }

    document.addEventListener(
      "pointerdown",
      handlePointerDown
    );

    return () => {
      document.removeEventListener(
        "pointerdown",
        handlePointerDown
      );
    };
  }, [ref, onOutside]);
}
```

Использование:

```
const menuRef = useRef(null);

useOutsideClick(menuRef, () => {
  setIsOpen(false);
});

return <div ref={menuRef}>Menu</div>;
```

Особенности:

- `useDebounce` обязательно очищает предыдущий таймер
- `usePrevious` использует `ref`, чтобы хранить значение без дополнительного рендера
- `useOutsideClick` проверяет принадлежность элемента через `contains()`
- Для `useOutsideClick` желательно передавать стабильный обработчик, если требуется избегать повторных подписок

# Как реализовать `useLocalStorage` с обработкой ошибок сериализации?

`useLocalStorage` синхронизирует React state с браузерным `localStorage`.

При реализации необходимо учитывать:

- Ошибки `JSON.parse()` при чтении повреждённых данных
- Ошибки `JSON.stringify()` при сериализации циклических объектов и неподдерживаемых типов
- Исключения браузера при обращении к хранилищу
- Отсутствие `localStorage` при SSR
- Ограничения объёма хранилища

Пример:

```
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    if (typeof window === "undefined") {
      return initialValue;
    }

    try {
      const stored = window.localStorage.getItem(key);

      return stored !== null
        ? JSON.parse(stored)
        : initialValue;
    } catch (error) {
      console.error("LocalStorage read error:", error);
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      const serialized = JSON.stringify(value);

      if (serialized === undefined) {
        throw new Error("Value is not JSON-serializable");
      }

      window.localStorage.setItem(key, serialized);
    } catch (error) {
      console.error("LocalStorage write error:", error);
    }
  }, [key, value]);

  return [value, setValue];
}
```

Принцип работы:

1. При инициализации хук пытается прочитать значение из `localStorage`
2. Если значение отсутствует или чтение завершилось ошибкой, используется `initialValue`
3. При изменении React state эффект сериализует значение
4. Сериализованные данные сохраняются в `localStorage`
5. При ошибке сохранения приложение продолжает работать, но данные могут не сохраниться

Важные ограничения:

- `localStorage` хранит только строки, поэтому необходима сериализация
- `BigInt` и циклические объекты вызывают ошибки стандартного `JSON.stringify`
- Обновление `localStorage` не вызывает автоматического рендера React
- Событие `storage` позволяет синхронизировать изменения между вкладками, но его обработка в примере не реализована
- Пример предполагает стабильный `key` на протяжении жизни компонента

Особенность SSR: чтение `localStorage` при первоначальном клиентском рендере может привести к несовпадению HTML при гидратации. В SSR-приложениях нужно обеспечить одинаковое первоначальное значение на сервере и клиенте, а затем загрузить сохранённое значение после монтирования либо использовать соответствующий механизм клиентской синхронизации.

# Как реализовать `useFetch` с отменой и защитой от race conditions?

`useFetch` инкапсулирует выполнение запроса и управление состояниями загрузки, успеха и ошибки.

Основные требования:

- Запускать запрос при изменении параметров
- Управлять `loading`, `data` и `error`
- Отменять предыдущий запрос через `AbortController`
- Игнорировать устаревшие результаты
- Не обновлять состояние после размонтирования
- Проверять HTTP-статус ответа

Пример:

```
function useFetch(url) {
  const [state, setState] = useState({
    data: null,
    error: null,
    loading: Boolean(url)
  });

  useEffect(() => {
    if (!url) {
      setState({
        data: null,
        error: null,
        loading: false
      });
      return;
    }

    const controller = new AbortController();
    let active = true;

    async function load() {
      setState({
        data: null,
        error: null,
        loading: true
      });

      try {
        const response = await fetch(url, {
          signal: controller.signal
        });

        if (!response.ok) {
          throw new Error(`HTTP ${response.status}`);
        }

        const data = await response.json();

        if (!active) return;

        setState({
          data,
          error: null,
          loading: false
        });
      } catch (error) {
        if (!active || controller.signal.aborted) {
          return;
        }

        setState({
          data: null,
          error,
          loading: false
        });
      }
    }

    load();

    return () => {
      active = false;
      controller.abort();
    };
  }, [url]);

  return state;
}
```

Использование:

```
function User({ userId }) {
  const { data, error, loading } = useFetch(
    `/api/users/${userId}`
  );

  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error: {error.message}</p>;
  if (!data) return null;

  return <h1>{data.name}</h1>;
}
```

Как защищаться от race conditions?

Предположим:

1. Пользователь запрашивает данные пользователя `A`
2. Сразу после этого переключается на пользователя `B`
3. Запрос `B` завершается быстрее
4. Позже завершается запрос `A`

Без дополнительной защиты устаревший ответ `A` может перезаписать актуальные данные `B`.

В реализации используются два механизма.

`AbortController` отменяет предыдущий запрос при изменении `url` или размонтировании.

Флаг `active` запрещает обработку результата после завершения жизненного цикла соответствующего эффекта:

```
if (!active) return;
```

Даже если асинхронная операция не поддерживает отмену или успела завершиться, устаревший результат не будет применён к состоянию.

Дополнительно `response.ok` проверяется вручную, поскольку `fetch` не отклоняет Promise автоматически при HTTP-ошибках вроде `404` или `500`.

Ограничения реализации:

- Отсутствует кеширование ответов
- Не реализованы повторные запросы и retry
- Нет дедупликации одинаковых запросов
- Не поддерживается автоматическая повторная загрузка при возвращении фокуса
- Возможны последовательные сетевые запросы при загрузке данных через вложенные компоненты
- Серверный рендеринг сам по себе не выполняет запросы, находящиеся в `useEffect`

Для сложного управления серверным состоянием обычно используются возможности фреймворка или специализированные библиотеки.
