# Чем Zustand отличается от Redux Toolkit?

Zustand - минималистичная библиотека управления состоянием. Redux Toolkit (RTK) - официальный набор инструментов для работы с Redux, основанный на архитектуре `actions → reducers → store`.

Основные различия:

- Обновление состояния: в Zustand состояние изменяется через `set`, обычно из методов самого store. В Redux изменения происходят через `dispatch(action)` и reducers.
- Структура: Zustand не требует actions и reducers. Redux Toolkit использует `createSlice`, `configureStore` и другие инструменты для организации логики.
- Иммутабельность: обе библиотеки требуют корректного обновления ссылок на изменяемые данные. RTK использует Immer, позволяющий писать мутации внутри reducers.
- Подписки: Zustand использует селекторы для подписки на части состояния. Redux применяет аналогичный механизм через `useSelector`.
- Отладка: Redux Toolkit имеет встроенную интеграцию с Redux DevTools. Zustand поддерживает DevTools через middleware.
- Асинхронность: Zustand позволяет выполнять асинхронную логику непосредственно в методах store. RTK предоставляет `createAsyncThunk`, listener middleware и RTK Query.

Zustand удобен для небольшого и среднего объёма клиентского состояния с минимальными ограничениями на архитектуру. Redux Toolkit полезен для сложных приложений, где важны стандартизированные обновления, отслеживание событий и развитые инструменты отладки.&#x20;

# Как устроена подписка компонента на часть Zustand store?

Zustand использует селекторы - функции, извлекающие необходимые данные из состояния.

```
const count = useStore((state) => state.count);
```

Механизм работы:

1. Компонент подписывается на внешний store через механизм React `useSyncExternalStore`.
2. При изменении store Zustand получает новое значение селектора.
3. Результат сравнивается с предыдущим через `Object.is` по умолчанию.
4. Если результат изменился, React инициирует обновление компонента.

При изменении другого поля store компонент не обязан перерисовываться, если выбранное значение осталось прежним.

Важно: селекторы не отслеживают обращения к полям автоматически, как MobX. Они выполняются над состоянием, а результат определяет необходимость обновления компонента.

# Как избежать ненужных рендеров при выборе нескольких полей Zustand?

Если селектор возвращает новый объект, `Object.is` считает его изменившимся даже при одинаковых значениях полей.

```
// Новый объект при каждом вызове селектора
const { count, name } = useStore((s) => ({
  count: s.count,
  name: s.name,
}));
```

В Zustand v5 для таких случаев используется `useShallow`:

```
import { useShallow } from "zustand/react/shallow";

const { count, name } = useStore(
  useShallow((s) => ({
    count: s.count,
    name: s.name,
  }))
);
```

`useShallow` выполняет поверхностное сравнение результатов селектора и сохраняет предыдущую ссылку, если выбранные значения не изменились.

Другой вариант - отдельные подписки:

```
const count = useStore((s) => s.count);
const name = useStore((s) => s.name);
```

Важно: `shallow` не выполняет глубокое сравнение вложенных объектов. Для вложенных данных необходимо сохранять стабильность ссылок или применять подходящий механизм сравнения.

В Zustand v5 также доступен `createWithEqualityFn` из `zustand/traditional`, позволяющий задать пользовательскую функцию сравнения.&#x20;

# Что такое middleware persist и как безопасно сохранять состояние?

`persist` - middleware Zustand для сохранения состояния между перезагрузками приложения.

Поддерживает `localStorage`, `sessionStorage` и пользовательские хранилища. При запуске восстанавливает сохранённые данные через механизм rehydration.

```
import { create } from "zustand";
import { persist } from "zustand/middleware";

const useStore = create(
  persist(
    (set) => ({
      theme: "light",
      token: null,
      setTheme: (theme) => set({ theme }),
    }),
    {
      name: "app-settings",
      partialize: (state) => ({
        theme: state.theme,
      }),
      version: 1,
    }
  )
);
```

Важные механизмы:

- `partialize` - выбирает поля для сохранения, исключая лишние и чувствительные данные.
- `version` и `migrate` - обеспечивают совместимость сохранённого состояния при изменении структуры.
- `onRehydrateStorage` - позволяет отслеживать восстановление состояния.
- `skipHydration` - позволяет управлять моментом восстановления, что полезно при SSR.

Безопасность: данные в `localStorage` доступны JavaScript и могут быть похищены при XSS. Не следует хранить там пароли, секреты и чувствительные токены. Данные после восстановления необходимо валидировать, поскольку пользователь может изменить содержимое хранилища.

`persist` не шифрует данные и не гарантирует их целостность.&#x20;

# Как организовать несколько независимых экземпляров Zustand store?

Использовать фабрику store на основе `createStore`, создавая отдельный экземпляр для каждой независимой области состояния.

```
import { createStore, useStore } from "zustand";

const createCounterStore = () =>
  createStore((set) => ({
    count: 0,
    increment: () =>
      set((s) => ({ count: s.count + 1 })),
  }));

const storeA = createCounterStore();
const storeB = createCounterStore();
```

`storeA` и `storeB` имеют независимые состояния и подписки.

Для React обычно используют `Context`:

1. Создают экземпляр через фабрику.
2. Передают его через `Context.Provider`.
3. Получают нужный экземпляр через `useContext`.
4. Подписываются на состояние через `useStore(store, selector)`.

Это полезно для независимых форм, вкладок, виджетов и изолированных частей приложения.

Важно: при SSR нельзя использовать общий изменяемый singleton store для пользовательского состояния, иначе возможна утечка данных между запросами. Экземпляры должны создаваться с учётом границ запроса или дерева компонентов.&#x20;

# Как работает реактивность в MobX?

MobX использует автоматическое отслеживание зависимостей между наблюдаемыми данными (`observable`) и реактивными вычислениями.

Механизм работы:

1. Поля объекта становятся наблюдаемыми через `observable`, `makeObservable` или `makeAutoObservable`.
2. При выполнении `observer`, `computed` или `autorun` MobX регистрирует прочитанные observable-поля.
3. Формируется граф зависимостей между состоянием и вычислениями.
4. При изменении наблюдаемого поля MobX инвалидирует зависимые вычисления и запускает необходимые реакции.
5. React-компоненты, обёрнутые в `observer`, обновляются при изменении используемых ими данных.

Главное отличие от Zustand и Redux: MobX автоматически определяет зависимости по факту чтения свойств. Явные селекторы обычно не требуются.

Важно: MobX отслеживает обращения к observable-полям только внутри отслеживаемого выполнения. Например, чтение поля внутри `setTimeout` не станет зависимостью внешнего `autorun`.&#x20;

# Чем observable, action и computed отличаются?

Это три основных механизма MobX:

- `observable` - реактивное состояние. MobX отслеживает чтение и изменение его полей.
- `action` - операция изменения состояния. Группирует изменения в транзакцию, чтобы реакции не наблюдали промежуточные состояния.
- `computed` - производное значение, вычисляемое на основе observable-данных. Кешируется при активном наблюдении и пересчитывается при изменении зависимостей.

```
import { makeAutoObservable } from "mobx";

class Counter {
  count = 0;

  constructor() {
    makeAutoObservable(this);
  }

  increment() {
    this.count++;
  }

  get doubled() {
    return this.count * 2;
  }
}
```

Здесь `count` становится `observable`, `increment` - `action`, а `doubled` - `computed`.

`computed` должен оставаться чистым вычислением без побочных эффектов. Если значение никто не наблюдает, MobX может приостановить его кеширование.&#x20;

# Когда использовать MobX вместо Redux?

MobX подходит для приложений со сложной моделью предметной области, большим количеством связанных объектов и производных значений.

Его преимущества:

- Автоматическое отслеживание зависимостей без ручных селекторов.
- Удобная работа с классами, объектами и вложенными структурами.
- Возможность изменять observable-данные напрямую внутри actions.
- Автоматическое кеширование производных значений через `computed`.

Redux Toolkit предпочтительнее, когда важны строгий поток изменений через actions, воспроизводимая история событий и предсказуемая архитектура.

Главный компромисс MobX - зависимости формируются динамически, поэтому причины обновлений иногда сложнее отследить, чем явные Redux actions.

# Что такое atom в Jotai?

Atom - минимальная единица состояния в Jotai, на которую компоненты могут подписываться независимо.

```
import { atom, useAtom } from "jotai";

const countAtom = atom(0);

function Counter() {
  const [count, setCount] = useAtom(countAtom);

  return (
    <button onClick={() => setCount((c) => c + 1)}>
      {count}
    </button>
  );
}
```

Атом описывает состояние, но само значение хранится в Jotai store, поэтому один и тот же atom может иметь разные значения в разных store.

Атомы бывают:

- Primitive - хранят собственное значение.
- Derived - вычисляются на основе других атомов.
- Read-only - предоставляют вычисляемое значение без возможности прямой записи.
- Writable - определяют собственную логику обновления через функцию записи.

```
const doubledAtom = atom(
  (get) => get(countAtom) * 2
);
```

Jotai автоматически отслеживает зависимости между атомами и обновляет подписчиков при изменении соответствующих значений.&#x20;

# Какие плюсы и минусы атомарного хранения состояния?

Атомарное хранение предполагает разделение состояния на небольшие независимые единицы.

Преимущества:

- Точечные подписки - компоненты обновляются при изменении используемых атомов.
- Композиция - производные атомы могут зависеть от других атомов.
- Модульность - состояние удобно распределять по функциональным областям.
- Изоляция - можно создавать независимые store через `Provider`.

Недостатки:

- Большое количество атомов усложняет навигацию по состоянию.
- Зависимости между атомами могут образовывать сложный граф.
- Согласованное обновление нескольких атомов требует продуманной организации логики.
- Динамически создаваемые атомы требуют контроля идентичности ссылок и жизненного цикла.

Ключевой принцип: атомизация полезна, когда разные части состояния имеют независимых потребителей. Чрезмерное дробление может усложнить архитектуру без заметного выигрыша.

# Как сравнить Zustand, Jotai, MobX и Redux с точки зрения отладки?

- Redux Toolkit: наиболее структурированная отладка. Redux DevTools показывает actions, изменения состояния и историю событий, поддерживает time-travel debugging.
- Zustand: middleware `devtools` позволяет использовать Redux DevTools, просматривать изменения и историю. Для понятной истории желательно явно именовать обновления.
- MobX: предоставляет `spy`, `trace`, `getDependencyTree` и `getObserverTree`. Они помогают анализировать реакции и зависимости, но единой истории actions по умолчанию нет.
- Jotai: поддерживает `jotai-devtools`, `debugLabel`, снимки атомов и интеграцию с Redux DevTools. Основной акцент - отслеживание значений и зависимостей отдельных атомов.

Итог: Redux Toolkit удобнее для анализа последовательности событий, MobX - для исследования реактивных зависимостей, Zustand и Jotai - для относительно простой отладки состояния при использовании соответствующих инструментов.&#x20;

# Как избежать смешивания локального, глобального и серверного состояния?

Разделять состояние по источнику данных, области использования и жизненному циклу.

- Локальное состояние: `useState`, `useReducer` - данные, принадлежащие конкретному компоненту: открытие модального окна, состояние ввода.
- Глобальное клиентское состояние: Zustand, Redux, Jotai, MobX - данные, которые должны совместно использовать разные компоненты: тема, настройки интерфейса, состояние многошагового процесса.
- Серверное состояние: TanStack Query, RTK Query - данные, полученные с сервера: пользователи, заказы, результаты запросов.

Серверное состояние отличается тем, что оно может устаревать, требует кеширования, повторных запросов и синхронизации с источником данных.

Не следует без необходимости копировать данные из Query-кеша в глобальный store: появляются два источника истины, которые приходится синхронизировать.

Практическое правило: хранить данные там, где находится их основной источник истины, и не дублировать производные значения, если их можно вычислить.

# Чем Observable отличается от Promise?

`Promise` представляет результат одной асинхронной операции, а `Observable` описывает поток из нуля, одного или множества значений, которые могут поступать во времени.

Основные различия:

- Количество значений: Promise завершается одним результатом или ошибкой. Observable может выдавать множество значений через `next`.
- Выполнение: Promise обычно начинает выполнение сразу при создании. Observable обычно ленивый - выполнение начинается при `subscribe`.
- Отмена: Promise не имеет встроенного механизма отмены. Observable позволяет прекратить подписку через `unsubscribe`.
- Обработка: Promise использует `then`, `catch`, `finally`. Observable поддерживает операторы `map`, `filter`, `switchMap`, `debounceTime` и другие.
- Завершение: Promise переходит в `fulfilled` или `rejected`. Observable может завершиться через `complete`, ошибку через `error` или продолжать работать неограниченно долго.

Важно: `unsubscribe` прекращает подписку, но фактическая отмена асинхронной операции зависит от реализации источника.

Promise удобен для разовых операций, Observable - для событий, WebSocket-соединений и сложных асинхронных потоков.&#x20;

# Что такое push-based поток данных?

Push-based - модель, в которой источник самостоятельно отправляет данные потребителю по мере их появления.

В отличие от pull-based, где потребитель запрашивает следующее значение, в push-based источник определяет момент отправки.

```
const stream$ = new Observable((subscriber) => {
  subscriber.next(1);
  subscriber.next(2);
  subscriber.complete();
});

stream$.subscribe(console.log);
```

Здесь источник самостоятельно передаёт значения подписчику через `next`.

RxJS Observable использует push-based модель, позволяющую обрабатывать события и асинхронные данные без постоянного опроса источника.

Важно: Observable может отправлять значения как асинхронно, так и синхронно.

# Как работают `subscribe` и `unsubscribe`?

`subscribe` подключает наблюдателя к Observable и возвращает объект `Subscription`, управляющий подпиской.

```
const subscription = interval(1000).subscribe({
  next: (value) => console.log(value),
  error: (error) => console.error(error),
  complete: () => console.log("Completed"),
});

subscription.unsubscribe();
```

Основные механизмы:

- `next` - получает очередное значение.
- `error` - получает ошибку, после которой поток завершается.
- `complete` - сообщает об успешном завершении.
- `unsubscribe` - закрывает подписку и запускает освобождение связанных ресурсов.

Для cold Observable каждый `subscribe` обычно запускает независимое выполнение источника.

Для hot Observable подписчики могут получать значения от общего источника.

Важно: `unsubscribe` не вызывает пользовательский обработчик `complete`. При этом прекращаются связанные с подпиской таймеры, обработчики событий и внутренние подписки, если источник реализует корректный teardown.

# Чем cold observable отличается от hot observable?

Cold Observable создаёт независимое выполнение источника для каждой подписки.

```
const cold$ = interval(1000);

cold$.subscribe(console.log);
cold$.subscribe(console.log);
```

Каждый подписчик получает собственную последовательность, начинающуюся с нуля.

Hot Observable использует общий источник данных, существующий независимо от конкретного подписчика.

```
const subject = new Subject<number>();

subject.subscribe(console.log);
subject.next(1);
```

Подписчики получают значения, отправленные после их подключения. Пропущенные события обычный `Subject` не воспроизводит.

Основные различия:

- Cold: отдельное выполнение для каждого подписчика. Пример - HTTP-запрос, создаваемый при каждой подписке.
- Hot: общий источник для нескольких подписчиков. Пример - события пользовательского интерфейса или `Subject`.

Операторы `share` и `shareReplay` позволяют совместно использовать выполнение источника между подписчиками.

Ключевой нюанс: hot/cold характеризует способ организации источника, а не то, синхронно или асинхронно он работает.

# В каких случаях применять `switchMap`, `mergeMap`, `concatMap` и `exhaustMap`?

Все четыре оператора преобразуют значения исходного Observable во внутренние Observable, но по-разному управляют их подписками.

- `switchMap` - при новом значении отменяет предыдущую внутреннюю подписку и переключается на новую. Подходит для поиска с автодополнением, когда важен только последний запрос.
- `mergeMap` - выполняет внутренние Observable параллельно, объединяя результаты по мере поступления. Подходит для независимых запросов, которые должны выполняться одновременно. Поддерживает ограничение конкурентности.
- `concatMap` - выполняет внутренние Observable последовательно, дожидаясь завершения предыдущего. Подходит для операций, где важен порядок выполнения.
- `exhaustMap` - игнорирует новые значения, пока текущий внутренний Observable не завершится. Подходит для защиты от повторной отправки формы.

Пример:

```
searchInput$.pipe(
  debounceTime(300),
  switchMap((query) => searchApi(query))
);
```

При изменении поисковой строки предыдущая внутренняя подписка отменяется, и результаты устаревших запросов не попадают в поток.

Важно: отмена подписки через `switchMap` не всегда означает физическую отмену HTTP-запроса - это зависит от используемого API.

Также следует учитывать, что `concatMap` может накапливать очередь, а `exhaustMap` - пропускать события.

Правило выбора:

- Нужен только последний результат - `switchMap`.
- Нужно параллельное выполнение - `mergeMap`.
- Нужна строгая последовательность - `concatMap`.
- Нужно игнорировать повторные запуски - `exhaustMap`.&#x20;

# Как различаются `Subject`, `BehaviorSubject` и `ReplaySubject`?

Все три являются разновидностями `Subject`, который одновременно выступает Observable и Observer: позволяет отправлять значения через `next` и подписываться на них через `subscribe`.

- `Subject` - передаёт новые значения текущим подписчикам. Не хранит предыдущие значения.
- `BehaviorSubject` - требует начального значения и хранит последнее. Новый подписчик сразу получает текущее значение, пока Subject активен.
- `ReplaySubject` - сохраняет историю значений и воспроизводит её новым подписчикам. Размер истории можно ограничивать количеством значений и временем хранения.

```
const subject = new Subject<number>();

const behavior = new BehaviorSubject<number>(0);

const replay = new ReplaySubject<number>(3);
```

Применение:

- `Subject` - события, уведомления.
- `BehaviorSubject` - текущее состояние, которое должно быть доступно новым подписчикам.
- `ReplaySubject` - потоки, где новым подписчикам необходимы предыдущие события.

Важно: `ReplaySubject` без ограничений буфера потенциально может удерживать неограниченное количество значений в памяти.&#x20;

# Как работают `debounceTime` и `distinctUntilChanged`?

`debounceTime(ms)` пропускает последнее значение только после периода, в течение которого источник не отправлял новых значений.

`distinctUntilChanged()` пропускает значение, только если оно отличается от последнего переданного значения.

```
searchInput$.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap((query) => searchApi(query))
);
```

Последовательность:

1. Пользователь вводит текст.
2. `debounceTime(300)` ожидает 300 мс без новых событий.
3. `distinctUntilChanged()` проверяет, изменилось ли значение по сравнению с предыдущим пропущенным значением.
4. Если изменилось, `switchMap` запускает запрос.

По умолчанию `distinctUntilChanged` сравнивает значения через `===`, поэтому два разных объекта с одинаковым содержимым считаются различными. Для объектов можно передать собственную функцию сравнения.

Важно: `debounceTime` не гарантирует периодическое выполнение при непрерывном потоке событий - каждое новое значение сбрасывает ожидание.&#x20;

# Как обработать ошибку внутри RxJS pipeline?

Для обработки ошибок используется `catchError`, который перехватывает ошибку и заменяет завершившийся с ошибкой поток другим Observable.

```
source$.pipe(
  map((value) => processValue(value)),
  catchError((error) => {
    console.error(error);
    return of(null);
  })
);
```

Основные подходы:

- `catchError` - перехват ошибки и возврат резервного Observable.
- `retry` - повторная подписка на источник после ошибки.
- `throwError` - передача ошибки дальше по цепочке.
- `finalize` - выполнение очистки при завершении, ошибке или отписке.

Особенно важно расположение `catchError`.

```
events$.pipe(
  switchMap((id) =>
    fetchData(id).pipe(
      catchError(() => of(null))
    )
  )
);
```

Здесь ошибка обрабатывается внутри `switchMap`, поэтому внешний поток `events$` продолжит принимать новые события.

Если разместить `catchError` после `switchMap` и вернуть `of(null)`, он заменит весь завершившийся с ошибкой поток, который после этого завершится.

Это принципиально для интерфейсов с постоянно поступающими событиями.&#x20;

# Как избежать утечек подписок?

Утечки возникают, когда подписки продолжают работать после того, как их результаты больше не нужны. Особенно это касается бесконечных потоков: `interval`, `fromEvent`, WebSocket и `Subject`.

Основные способы предотвращения:

- `unsubscribe()` - явное освобождение подписки.
- `take(1)` - автоматическое завершение после первого значения.
- `takeUntil(notifier$)` - завершение при получении сигнала от другого Observable.
- `firstValueFrom()` - получение первого значения через Promise с автоматической отпиской после его получения.
- `finalize()` - освобождение дополнительных ресурсов при завершении подписки.

В React подписку обычно создают внутри `useEffect` и удаляют при размонтировании или изменении зависимостей:

```
useEffect(() => {
  const subscription = stream$.subscribe((value) => {
    console.log(value);
  });

  return () => subscription.unsubscribe();
}, [stream$]);
```

В Angular для этого часто применяют `AsyncPipe` или `takeUntilDestroyed`.

Важно: не каждую подписку нужно отменять вручную. Потоки, которые самостоятельно завершаются, освобождают свои ресурсы после завершения.

Однако для долгоживущих потоков необходимо явно контролировать жизненный цикл. Также следует учитывать, что `shareReplay` без корректной настройки управления подписками может удерживать источник активным после отключения потребителей.&#x20;
