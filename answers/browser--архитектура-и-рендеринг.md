# Что происходит после ввода URL в адресную строку браузера?

Браузер выполняет последовательность действий, чтобы получить страницу и отобразить её пользователю.

1. Обработка URL - определяет протокол, домен, порт, путь и параметры запроса. Проверяет возможность использования кеша или Service Worker.
2. DNS Lookup - определяет IP-адрес сервера по доменному имени, если подходящий адрес не найден в кеше.
3. Установка соединения - использует TCP + TLS для HTTPS через HTTP/1.1 или HTTP/2 либо QUIC для HTTP/3. Существующее соединение может переиспользоваться.
4. HTTP-запрос - отправляет запрос серверу с необходимыми заголовками, cookies и другими данными.
5. HTTP-ответ - получает статус, заголовки и содержимое. При перенаправлении выполняет переход по новому адресу.
6. Парсинг HTML - постепенно формирует DOM и обнаруживает дополнительные ресурсы: CSS, JavaScript, изображения.
7. Обработка CSS и JavaScript - строит CSSOM, выполняет скрипты с учётом их типа и атрибутов. Скрипты могут изменять DOM и стили.
8. Рендеринг - вычисляет стили, размеры и позиции элементов, подготавливает команды рисования и формирует итоговые кадры.
9. Отображение - выводит содержимое на экран и продолжает загружать оставшиеся ресурсы, обрабатывать события и обновлять страницу.

Важно: эти операции не всегда выполняются строго последовательно. Загрузка ресурсов, парсинг и некоторые этапы рендеринга могут пересекаться. Браузер способен показать часть страницы до завершения загрузки всего документа.

# Какие процессы и потоки обычно участвуют в работе современного браузера?

Современные браузеры, например Chrome, используют многопроцессную архитектуру для изоляции сайтов, повышения безопасности и устойчивости.

Основные процессы:

- Browser Process - управляет интерфейсом браузера, вкладками, навигацией и координирует системные операции.
- Renderer Process - обрабатывает веб-страницы: HTML, CSS, JavaScript, DOM и рендеринг.
- GPU Process - обслуживает графические операции и взаимодействие с GPU.
- Utility Processes - выполняют отдельные служебные задачи, например сетевые операции или обработку данных.
- Extension Processes - обеспечивают выполнение компонентов расширений.

Внутри Renderer Process обычно работают:

- Main Thread - выполняет JavaScript, обрабатывает DOM, вычисляет стили, выполняет layout и часть paint pipeline.
- Compositor Thread - управляет композитными слоями и может обновлять некоторые кадры независимо от Main Thread.
- Raster Threads - преобразуют команды рисования в пиксельные изображения.
- Worker Threads - выполняют JavaScript в Web Workers без непосредственного доступа к DOM.

Процессы имеют изолированную память и обмениваются сообщениями через IPC (Inter-Process Communication). Потоки одного процесса используют общее адресное пространство.

Важно: одна вкладка не обязательно соответствует одному процессу. Благодаря Site Isolation разные сайты и вложенные `iframe` могут выполняться в отдельных Renderer Process.&#x20;

# Чем движок рендеринга отличается от JavaScript-движка?

Движок рендеринга (Rendering Engine) отвечает за обработку HTML и CSS, построение DOM, вычисление стилей, расположение элементов и подготовку страницы к отображению.

Примеры: `Blink` (Chrome, Edge), `WebKit` (Safari), `Gecko` (Firefox).

JavaScript-движок (JavaScript Engine) отвечает за парсинг, компиляцию и выполнение JavaScript, управление объектами и сборку мусора.

Примеры: `V8` (Chrome, Edge), `JavaScriptCore` (Safari), `SpiderMonkey` (Firefox).

Они взаимодействуют через браузерные механизмы и API:

1. JavaScript-движок выполняет код, вызывающий `document.createElement()`.
2. Движок рендеринга через реализацию DOM API создаёт элемент.
3. При необходимости пересчитываются стили, layout и выполняется отрисовка.

Ключевое отличие: JavaScript-движок исполняет код, а движок рендеринга отвечает за представление и отображение документа. Сам JavaScript-движок не реализует DOM.

# Что такое DOM и CSSOM?

DOM (Document Object Model) - объектная модель HTML/XML-документа, представленная деревом узлов.

DOM содержит элементы, текстовые узлы, комментарии и связи между ними. Через DOM API JavaScript может читать и изменять структуру документа, атрибуты и содержимое.

CSSOM (CSS Object Model) - объектная модель CSS, представляющая таблицы стилей, правила, селекторы и объявления CSS в доступном для браузера виде.

CSSOM используется при сопоставлении CSS-правил элементам и вычислении их стилей с учётом каскада, наследования и специфичности.

Главное отличие:

- DOM описывает структуру и содержимое документа.
- CSSOM описывает правила его оформления.

Обе модели используются браузером при формировании визуального представления страницы.

# Как браузер строит render tree?

Render Tree - внутреннее представление элементов документа, участвующих в визуальном форматировании и отрисовке.

Упрощённый процесс построения:

1. Браузер создаёт DOM из HTML.
2. Парсит CSS и формирует CSSOM.
3. Сопоставляет CSS-правила DOM-элементам и вычисляет итоговые стили.
4. Создаёт дерево визуальных объектов с учётом структуры документа и вычисленных стилей.
5. Использует его для расчёта геометрии и последующей отрисовки.

Особенности:

- `display: none` исключает элемент и его потомков из обычного дерева рендеринга.
- `visibility: hidden` сохраняет участие элемента в layout, хотя он не рисуется.
- Псевдоэлементы `::before` и `::after` могут создавать дополнительные визуальные объекты.
- Один DOM-элемент не обязательно соответствует одному объекту рендеринга.

Важно: Render Tree - упрощённое понятие. Современные движки используют более сложные структуры, включая layout tree, fragment tree и paint-related структуры.

# Какие стадии входят в critical rendering path?

Critical Rendering Path (CRP) - последовательность операций, необходимых браузеру для первоначального отображения страницы.

Основные стадии:

1. HTML Parsing - преобразование HTML в DOM.
2. CSS Parsing - построение CSSOM.
3. Style Calculation - вычисление итоговых стилей элементов.
4. Render Tree Construction - формирование визуальной структуры страницы.
5. Layout (Reflow) - вычисление размеров и расположения элементов.
6. Paint - формирование команд рисования текста, цветов, границ и других визуальных элементов.
7. Rasterization - преобразование команд рисования в пиксели.
8. Compositing - объединение графических слоёв в итоговый кадр.

JavaScript может участвовать в этом процессе, изменяя DOM и CSSOM или задерживая выполнение отдельных стадий.

Главная особенность: CRP зависит от критических ресурсов, без которых браузер не может корректно сформировать первоначальное изображение страницы.

Чем меньше блокирующих ресурсов и вычислений находится на критическом пути, тем раньше браузер сможет отобразить содержимое.&#x20;

# Чем layout/reflow отличается от paint/repaint?

Layout (Reflow) - вычисление геометрии элементов: размеров, координат и взаимного расположения.

Возникает при изменениях, влияющих на геометрию документа, например:

- Изменение `width`, `height`, `margin`, `padding`.
- Добавление или удаление элементов.
- Изменение содержимого, влияющего на размеры.
- Изменение размеров окна браузера.

Paint (Repaint) - формирование или обновление визуального содержимого элементов без обязательного пересчёта их геометрии.

Например, изменение `background-color`, `color` или `box-shadow` обычно требует Paint, но не Layout.

Ключевое различие:

- Layout отвечает на вопрос «где находится элемент и сколько места занимает?».
- Paint отвечает на вопрос «как элемент выглядит?».

Layout часто приводит к последующему Paint, но Paint не обязательно требует Layout.

Изменения `transform` и `opacity` в подходящих условиях могут обрабатываться на этапе Compositing без повторных Layout и Paint.

# Что такое compositing и зачем нужны графические слои?

Compositing - этап формирования итогового кадра из отдельных графических слоёв (Compositing Layers).

Браузер может выделять элементы в самостоятельные слои, например при использовании анимаций `transform`, `opacity`, видео и некоторых эффектов.

Принцип работы:

1. Браузер определяет, какие части страницы должны находиться в отдельных слоях.
2. Слои подготавливаются и растеризуются.
3. Compositor объединяет их с учётом порядка, прозрачности, трансформаций и обрезки.
4. Полученный кадр передаётся на отображение.

Главное преимущество - возможность обновлять положение или прозрачность уже растеризованных слоёв без повторного Layout и Paint.

Например, анимация `transform: translateX(...)` может выполняться средствами композитора независимо от основного потока.

Однако дополнительные слои расходуют память GPU и требуют ресурсов для управления ими. Поэтому чрезмерное применение `will-change` может ухудшить производительность.

Важно: создание отдельного compositing layer определяется браузером. Не каждый элемент со `z-index`, `transform` или собственным stacking context обязательно становится отдельным графическим слоем.&#x20;

# Какой код блокирует основной поток браузера?

Main Thread выполняет JavaScript, обрабатывает пользовательские события, DOM-операции и значительную часть рендеринга.

Основной поток блокируют длительные синхронные операции:

- Тяжёлые вычисления и большие циклы JavaScript.
- Сложная синхронная обработка данных, например `JSON.parse()` больших объектов.
- Массовые изменения DOM.
- Дорогие вычисления стилей и Layout.
- Синхронные запросы `XMLHttpRequest` (устаревшая практика).
- Длительные обработчики событий.
- Бесконечные цепочки микрозадач (`Promise`, `queueMicrotask`), не позволяющие браузеру перейти к рендерингу.

JavaScript использует модель run-to-completion: текущая задача выполняется до завершения и не прерывается обычными пользовательскими событиями.

Пока Main Thread занят, браузер не может своевременно выполнять другие задачи этого потока. В результате задерживается обработка кликов, ввод текста и обновление интерфейса.

Асинхронный `fetch()` не блокирует поток во время ожидания сети, но обработка его результата в JavaScript может блокировать.

Web Workers позволяют выполнять тяжёлые вычисления вне Main Thread, однако не предоставляют прямого доступа к DOM.

# Как HTML-парсер обрабатывает теги `script`, `style` и `link`?

Поведение HTML-парсера зависит от типа элемента, его атрибутов и назначения ресурса.

`<script>`

Обычный классический скрипт без `async` и `defer` останавливает HTML-парсер до завершения загрузки и выполнения скрипта.

Атрибуты изменяют поведение:

- `async` - загружает скрипт параллельно, выполняет сразу после готовности, без гарантии порядка относительно других async-скриптов.
- `defer` - загружает параллельно, выполняет после завершения HTML-парсинга, сохраняя порядок отложенных классических скриптов, до `DOMContentLoaded`.
- `type="module"` - по умолчанию ведёт себя подобно `defer`, но использует семантику ES-модулей. `async` изменяет момент выполнения.

`<style>`

Браузер парсит встроенные CSS-правила и добавляет их в CSSOM.

HTML-парсинг обычно продолжается, но стили могут задерживать рендеринг, поскольку браузеру необходимо учитывать их при вычислении оформления.

`<link>`

Поведение зависит от `rel`:

- `rel="stylesheet"` - загружает CSS и обычно блокирует первоначальный рендеринг, если стили применимы к текущему устройству.
- `rel="preload"` - заранее загружает ресурс, но само по себе не блокирует рендеринг.
- `rel="prefetch"` - подсказывает браузеру возможность заранее загрузить ресурс для будущего использования.

Важно: уже загруженный CSS может влиять на выполнение классических скриптов. Если скрипт зависит от ещё не загруженных предшествующих таблиц стилей, браузер может задержать его выполнение.

# Что такое render-blocking ресурсы?

Render-blocking ресурсы - ресурсы, которые задерживают первоначальную отрисовку страницы, поскольку браузер должен обработать их перед отображением соответствующего содержимого.

Основные примеры:

- CSS-файлы через `<link rel="stylesheet">`, если их `media` соответствует текущим условиям.
- Встроенные критические CSS-правила, которые необходимо обработать перед отрисовкой.
- Синхронные JavaScript-скрипты, способные задерживать HTML-парсинг и первоначальный рендеринг.

CSS блокирует рендеринг потому, что браузеру необходимо вычислить оформление элементов до их отображения.

JavaScript может блокировать парсер, изменять DOM/CSSOM и занимать Main Thread, поэтому способен задерживать появление содержимого.

Не все загружаемые ресурсы блокируют рендеринг. Обычные изображения, `async`-скрипты и ресурсы с `preload` сами по себе не обязаны задерживать первоначальную отрисовку.

При этом они могут влиять на другие показатели производительности, включая LCP.

# Когда браузер использует GPU и compositor thread?

Браузер использует GPU для ускорения графических операций, включая растеризацию, композицию слоёв, преобразования и обработку некоторых визуальных эффектов.

Compositor Thread координирует формирование кадров из подготовленных графических слоёв.

Типичные сценарии:

- Анимации `transform` и `opacity` на композитных слоях.
- Прокрутка страницы, которую можно обработать без обращения к Main Thread.
- Объединение слоёв с прозрачностью и трансформациями.
- Отображение графики через WebGL и WebGPU.

Главное преимущество - некоторые визуальные обновления могут происходить независимо от выполнения JavaScript на Main Thread.

Например, при зависшем JavaScript прокрутка иногда продолжает работать, если браузер способен обрабатывать её на Compositor Thread.

Ограничение: GPU не заменяет CPU и не вычисляет DOM или CSS Layout. Изменения геометрии страницы по-прежнему требуют соответствующей работы движка рендеринга.

Кроме того, некоторые обработчики прокрутки и пользовательского ввода могут вынуждать композитор ожидать Main Thread.

# Как `requestAnimationFrame` связан с обновлением кадра?

`requestAnimationFrame(callback)` - API для планирования JavaScript-кода перед следующим обновлением изображения страницы.

Браузер вызывает callback перед очередной отрисовкой, синхронизируя его с циклом обновления дисплея.

Пример:

```
function animate(timestamp) {
  element.style.transform = `translateX(${timestamp * 0.05}px)`;
  requestAnimationFrame(animate);
}

requestAnimationFrame(animate);
```

Особенности:

- Callback обычно вызывается с частотой обновления дисплея: 60, 120, 144 Гц и т.д.
- Получает временную метку для вычисления прогресса анимации.
- Выполняется на Main Thread и может сам блокировать рендеринг.
- Для непрерывной анимации необходимо повторно вызывать `requestAnimationFrame`.
- В фоновых вкладках вызовы обычно приостанавливаются.

При 60 Гц интервал между кадрами составляет примерно 16,7 мс. За это время браузеру нужно выполнить все необходимые операции, а не только callback.

Важно: `requestAnimationFrame` не гарантирует 60 FPS и не устраняет тяжёлые вычисления. Он помогает синхронизировать изменения с обновлением экрана.&#x20;

# Что такое forced synchronous layout и layout thrashing?

Forced Synchronous Layout - ситуация, когда JavaScript заставляет браузер немедленно пересчитать геометрию страницы, вместо того чтобы выполнить Layout позже в обычном цикле рендеринга.

Это происходит, если код изменяет DOM или стили, а затем запрашивает актуальные геометрические данные.

Пример:

```
element.style.width = "200px";
const width = element.offsetWidth;
```

После изменения `width` геометрия может считаться устаревшей. Чтение `offsetWidth` вынуждает браузер синхронно вычислить актуальные размеры.

Layout Thrashing - многократное чередование изменений и чтений геометрии, вызывающее повторные принудительные Layout.

Пример:

```
elements.forEach((element) => {
  element.style.width = "200px";
  console.log(element.offsetWidth);
});
```

Вместо одного общего пересчёта браузер потенциально выполняет Layout на каждой итерации.

Основные способы предотвращения:

- Группировать чтения геометрии перед изменениями DOM.
- Не чередовать операции чтения и записи в циклах.
- Использовать `transform` для анимаций, не требующих изменения геометрии.

Важно: чтение `offsetWidth` или `getBoundingClientRect()` не всегда вызывает принудительный Layout. Он требуется, когда геометрические данные устарели и должны быть пересчитаны.

# Как работает `requestIdleCallback`?

`requestIdleCallback(callback)` - API для выполнения низкоприоритетных задач в периоды, когда браузер считает основной поток свободным.

Браузер определяет доступное время до следующей важной работы, например обработки пользовательского ввода или обновления кадра.

Callback получает объект `IdleDeadline`:

- `timeRemaining()` - приблизительное количество миллисекунд, доступных для работы.
- `didTimeout` - показывает, что callback был запущен из-за истечения заданного `timeout`.

Пример:

```
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0 && tasks.length > 0) {
    processTask(tasks.shift());
  }
});
```

Подходит для некритичных задач: фоновой обработки данных, предварительной подготовки ресурсов, отложенной аналитики.

Ограничения:

- Браузер не гарантирует быстрый вызов callback.
- При постоянной нагрузке свободного времени может долго не быть.
- `timeout` позволяет запустить задачу вне периода простоя, поэтому она всё равно может блокировать Main Thread.
- Поддержка API различается между браузерами.

`requestIdleCallback` не создаёт отдельный поток и не подходит для длительных непрерывных вычислений.&#x20;

# Когда полезны `scheduler.postTask` и уступка управления основному потоку?

`scheduler.postTask()` позволяет планировать задачи с приоритетами, а `scheduler.yield()` - добровольно прерывать длительную асинхронную работу, предоставляя браузеру возможность выполнить другие задачи.

`scheduler.postTask()` поддерживает три основных приоритета:

- `user-blocking` - критичные для взаимодействия с пользователем задачи.
- `user-visible` - задачи, влияющие на видимый результат, но не блокирующие непосредственное взаимодействие.
- `background` - некритичные фоновые задачи.

Пример:

```
scheduler.postTask(updateUI, {
  priority: "user-blocking",
});

scheduler.postTask(sendAnalytics, {
  priority: "background",
});
```

`scheduler.yield()` полезен для разделения длительной работы на части:

```
async function processItems(items) {
  for (let i = 0; i < items.length; i++) {
    processItem(items[i]);

    if (i % 100 === 0) {
      await scheduler.yield();
    }
  }
}
```

При `await scheduler.yield()` текущий JavaScript уступает управление, а продолжение планируется как новая задача. Это позволяет браузеру обработать ожидающие события и при подходящих условиях обновить интерфейс.

Когда использовать: для больших вычислительных циклов, обработки крупных коллекций и других задач, которые можно безопасно разделить на части.

Важно: `scheduler.yield()` не переносит вычисления в отдельный поток. Обе API выполняют задачи в рамках соответствующего потока, а не параллельно ему.

По состоянию на 2026 год эти API поддерживаются не всеми браузерами, поэтому необходимо учитывать совместимость.&#x20;

# Как браузер принимает решение об уничтожении DOM-узлов и объектов JS?

Браузер использует Garbage Collector (GC) для автоматического освобождения памяти, занятой объектами, которые больше недостижимы из используемых программой корней.

Основной принцип - reachability (достижимость).

Сборщик мусора начинает обход графа объектов от корней, например глобальных объектов, активных стеков вызовов и других ссылок, удерживаемых средой выполнения.

Объекты, недостижимые из корней, могут быть освобождены.

Для DOM действуют дополнительные связи с внутренними структурами браузера.

Например:

```
const element = document.createElement("div");
document.body.append(element);

element.remove();
```

После `remove()` элемент исключается из DOM-дерева, но переменная `element` продолжает удерживать ссылку на него.

Следовательно, объект нельзя освободить, пока ссылка остаётся достижимой.

Другие причины удержания DOM-узлов:

- Ссылки внутри массивов, объектов, `Map`.
- Замыкания, удерживаемые действующими обработчиками событий.
- Таймеры и асинхронные операции, сохраняющие ссылки.
- Внутренние ссылки браузера на используемые объекты.

Такие элементы часто называют Detached DOM Nodes.

Современные GC умеют собирать циклические структуры, если они полностью недостижимы.

Важно: удаление элемента из DOM или присваивание переменной `null` не гарантирует немедленного освобождения памяти. Время запуска GC определяется движком.&#x20;

# Почему вкладка браузера может замедлять таймеры в фоне?

Браузеры ограничивают выполнение задач в неактивных вкладках, чтобы уменьшить потребление CPU, памяти и энергии.

Этот механизм называется Timer Throttling.

Он затрагивает прежде всего `setTimeout()` и `setInterval()`.

Например, Chrome может:

- Объединять проверки таймеров скрытой вкладки с интервалом около одной секунды.
- При длительном нахождении вкладки в фоне и соблюдении дополнительных условий проверять таймеры примерно раз в минуту.
- Приостанавливать `requestAnimationFrame`, пока страница скрыта.

Точные ограничения зависят от браузера, времени неактивности, воспроизведения звука и других факторов.

Также браузер может полностью заморозить фоновую страницу или выгрузить её при нехватке ресурсов.

Практическое следствие: `setTimeout(fn, 1000)` не гарантирует выполнение через одну секунду. Он задаёт минимальную задержку до возможности запуска callback.

Для отслеживания реального времени следует использовать временные метки, например `Date.now()` или `performance.now()`, а не считать количество срабатываний таймера.

Состояние видимости страницы можно определять через `document.visibilityState` и событие `visibilitychange`.&#x20;

# Как работает back-forward cache и что мешает его использованию?

Back-Forward Cache (bfcache) - механизм сохранения состояния страницы в памяти браузера для быстрого восстановления при навигации назад и вперёд.

В отличие от обычного HTTP-кеша, bfcache сохраняет не только сетевые ресурсы, но и состояние документа:

- DOM и связанные структуры.
- JavaScript heap.
- Состояние пользовательского интерфейса.
- Позицию прокрутки и другие данные страницы.

Принцип работы:

1. Пользователь переходит со страницы A на страницу B.
2. Браузер при возможности сохраняет страницу A в bfcache.
3. Выполнение JavaScript на сохранённой странице приостанавливается.
4. При возвращении браузер восстанавливает страницу без повторного построения DOM и обычной загрузки документа.

Определить восстановление можно через `pageshow`:

```
window.addEventListener("pageshow", (event) => {
  if (event.persisted) {
    console.log("Restored from bfcache");
  }
});
```

Что может мешать использованию bfcache:

- Обработчики `unload`.
- Некоторые активные WebSocket, WebRTC и IndexedDB-соединения.
- Незавершённые сетевые операции.
- Некоторые варианты применения `Cache-Control: no-store`.
- Ограничения безопасности и особенности браузера.
- Нехватка памяти, из-за которой сохранённая страница удаляется из кеша.

Конкретные ограничения зависят от браузера и его версии. Например, `Cache-Control: no-store` и открытые соединения не во всех браузерах являются безусловными блокирующими факторами.

Для управления жизненным циклом страницы предпочтительнее использовать `pagehide` и `pageshow`, а не `unload`.

Важно: восстановленная страница может содержать устаревшие данные. При необходимости их обновляют после события `pageshow`.&#x20;

# Как диагностировать зависания интерфейса в Chrome Performance?

Chrome DevTools Performance позволяет анализировать выполнение JavaScript, обработку событий, рендеринг и формирование кадров.

Основной процесс диагностики:

1. Открыть DevTools → Performance и начать запись.
2. Воспроизвести зависание - выполнить действие, вызывающее задержку интерфейса.
3. Остановить запись и найти проблемный временной интервал.
4. Изучить Main Thread - определить длительные задачи и используемое процессорное время.
5. Проанализировать Flame Chart - выяснить, какие функции и вложенные вызовы занимают больше всего времени.
6. Проверить Rendering - найти дорогие `Recalculate Style`, `Layout`, `Paint` и другие операции.
7. Изучить Interactions и Frames - определить задержки взаимодействия и пропущенные кадры.

Особое внимание следует обращать на:

- Long Tasks - задачи продолжительностью более 50 мс, которые Chrome отмечает на временной шкале.
- Forced Reflow - принудительные синхронные перерасчёты Layout.
- Long JavaScript Execution - тяжёлые обработчики событий, циклы и вычисления.
- Garbage Collection - паузы и накладные расходы сборки мусора.
- INP (Interaction to Next Paint) - задержку от пользовательского взаимодействия до следующего визуального обновления.

Для поиска конкретных функций используются представления Bottom-Up и Call Tree.

Bottom-Up помогает увидеть операции, суммарно потребляющие больше всего времени, а Call Tree показывает иерархию вызовов.

Дополнительно можно использовать CPU Throttling для воспроизведения проблемы на слабых устройствах.

Главный принцип диагностики: сначала определить, где именно теряется время - JavaScript, вычисление стилей, Layout, Paint или ожидание Main Thread. Только после этого искать конкретную причину в коде.&#x20;
