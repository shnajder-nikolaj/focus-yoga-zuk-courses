# Какие события могут вызвать рендер React-компонента?

React запускает рендер компонента в следующих случаях:

- Первоначальный рендер - компонент впервые появляется в дереве.
- Изменение состояния - обновление через `useState`, `useReducer` или другие механизмы состояния.
- Рендер родителя - по умолчанию React повторно рендерит дочерние компоненты, даже если их `props` не изменились.
- Изменение контекста - изменение значения `Context.Provider` вызывает обновление компонентов, использующих этот контекст через `useContext`.
- Обновление внешнего хранилища - например, через подписку `useSyncExternalStore`.

Дополнительно рендер может повторяться при возобновлении работы после `Suspense` или прерывании конкурентного рендеринга.

Важно: вызов функции обновления состояния не гарантирует повторного рендера. Если новое значение совпадает с предыдущим по `Object.is`, React может пропустить обновление.

В режиме разработки `StrictMode` намеренно вызывает функции компонентов повторно для обнаружения побочных эффектов.&#x20;

# Чем рендер отличается от commit и монтирования?

Это разные этапы жизненного цикла React-компонента.

- Render - React вызывает функции компонентов, получает React-элементы и вычисляет необходимые изменения интерфейса. DOM на этом этапе не изменяется.
- Commit - React применяет вычисленные изменения к DOM, обновляет ссылки `ref` и выполняет соответствующие этапу эффекты.
- Mounting (монтирование) - первоначальное добавление компонента в дерево React с созданием его состояния и, при необходимости, DOM-узлов.

Монтирование происходит один раз в рамках конкретного существования компонента в дереве. Render и commit могут происходить многократно.

При этом не каждый рендер приводит к изменениям DOM. Если результат остался прежним, React может ничего не менять.

# Что такое reconciliation?

Reconciliation - процесс согласования предыдущего и нового деревьев React-элементов для определения необходимых изменений интерфейса.

После обновления состояния или свойств React строит новое представление UI и сопоставляет его с предыдущим.

На основании сравнения React решает:

- Какие компоненты и DOM-узлы можно сохранить.
- Какие свойства и содержимое нужно обновить.
- Какие элементы необходимо создать или удалить.
- Какое локальное состояние компонентов сохранить или сбросить.

Reconciliation позволяет обновлять интерфейс без полного пересоздания DOM и сохранять состояние компонентов при неизменной идентичности.

# Как React сравнивает деревья элементов?

React использует эвристический алгоритм сравнения, основанный на типах элементов, их положении в дереве и ключах `key`.

Основные правила:

- Разные типы элементов - React заменяет старое поддерево новым, сбрасывая локальное состояние компонентов внутри.
- Одинаковые типы - React может сохранить существующий компонент или DOM-узел, обновить свойства и продолжить сравнение потомков.
- Дочерние элементы - сопоставляются внутри общего родителя по позиции либо по `key`.
- Одинаковые `key` и типы - позволяют сохранить идентичность элемента при изменении порядка среди соседних элементов.

Вместо поиска минимального количества изменений для произвольных деревьев React использует алгоритм с типичной сложностью O(n) относительно количества рассматриваемых элементов.

Алгоритм не выполняет полноценный поиск перемещённых поддеревьев между разными родителями.

# Как `key` влияет на сохранение состояния при перестановке элементов?

`key` определяет идентичность элемента среди дочерних элементов одного родителя.

Если у элементов стабильные уникальные ключи, React может сопоставить их между рендерами и сохранить локальное состояние при перестановке.

```
items.map(item => (
  <Item key={item.id} item={item} />
))
```

При изменении порядка элементов состояние каждого `Item` останется связанным с его `id`.

Если использовать индекс массива:

```
items.map((item, index) => (
  <Item key={index} item={item} />
))
```

после сортировки состояние может остаться привязанным к позиции, а не к исходному элементу. Например, текст в поле ввода окажется связан с другим объектом.

Важно:

- `key` должен быть уникальным среди соседних элементов, а не глобально.
- Изменение `key` принудительно сбрасывает состояние компонента и его потомков.
- Для динамических списков предпочтительны стабильные идентификаторы данных.&#x20;

# Что такое React Fiber и какую задачу он решает?

React Fiber - внутренняя архитектура React, предназначенная для организации рендеринга, согласования деревьев и управления приоритетами обновлений.

Каждый Fiber представляет единицу работы, связанную с компонентом или другим элементом дерева. Он хранит информацию о типе элемента, свойствах, состоянии, связях с другими Fiber и необходимых изменениях.

До Fiber согласование дерева в React выполнялось преимущественно синхронно, без возможности приостановить начатый обход.

Fiber позволяет:

- Разбивать вычисление интерфейса на отдельные единицы работы.
- Приостанавливать и возобновлять работу.
- Прерывать менее приоритетные вычисления ради срочных обновлений.
- Повторно выполнять или отменять незавершённый рендер.
- Подготавливать новое дерево отдельно от текущего.

React использует текущее дерево Fiber и рабочее дерево (work-in-progress), которое постепенно формируется при обновлении.

Главная задача Fiber - сделать вычисление интерфейса управляемым, чтобы сложные обновления не блокировали срочные взаимодействия дольше необходимого.

При этом возможность прерывания относится прежде всего к render phase. Commit выполняется без такого прерывания.

# Как работает планирование обновлений в React?

React использует механизм Scheduler совместно с системой приоритетов lanes, чтобы определять порядок выполнения обновлений.

Общий процесс:

1. Обновление состояния создаёт задачу для соответствующего дерева Fiber.
2. React назначает обновлению приоритет через механизм lanes.
3. Планировщик выбирает работу с учётом приоритетов и текущих условий.
4. React выполняет рендер синхронно или с возможностью уступать управление браузеру.
5. Если появляется более приоритетное обновление, конкурентный рендер может быть прерван и впоследствии повторён.
6. После завершения вычислений React выполняет commit.

Например, если пользователь печатает в поле ввода во время вычисления большого списка, React может обработать срочное обновление поля раньше завершения менее приоритетного обновления списка.

Для пометки обновлений как несрочных используются `startTransition` и `useTransition`.

Важно: планировщик работает в основном кооперативно. React не прерывает произвольный выполняющийся JavaScript-код посреди функции, а уступает управление в предусмотренных точках.

# Почему рендер-функция компонента должна быть чистой?

Чистая функция при одинаковых входных данных возвращает одинаковый результат и не создаёт побочных эффектов.

В React это означает, что компонент во время рендера должен только вычислять JSX на основании `props`, `state` и `context`.

Нельзя выполнять во время рендера:

- Изменение DOM.
- Сетевые запросы с побочными эффектами.
- Изменение внешних переменных или объектов.
- Подписки на события.
- Обновление состояния других компонентов.

Причина в том, что React может вызвать компонент несколько раз, прервать рендер или отказаться от его результата.

Если рендер содержит побочные эффекты, они могут выполниться даже тогда, когда соответствующие изменения интерфейса не будут применены.

Правильное разделение ответственности:

- Render - чистое вычисление интерфейса.
- Обработчики событий - действия пользователя.
- `useEffect` - синхронизация с внешними системами после commit.
- `useLayoutEffect` - синхронная работа с DOM после его изменений, до отрисовки браузером.

# Что такое render phase и commit phase?

React разделяет обновление интерфейса на две основные фазы.

Render phase - этап вычисления нового состояния интерфейса.

На этом этапе React:

- Вызывает функции компонентов.
- Обрабатывает обновления состояния.
- Выполняет reconciliation.
- Определяет необходимые изменения.

В конкурентном режиме эта фаза может приостанавливаться, повторяться или отменяться.

Commit phase - этап применения подготовленных изменений.

На этом этапе React:

- Изменяет DOM.
- Обновляет `ref`.
- Выполняет очистку и запуск соответствующих layout-эффектов.
- После commit запускает пассивные эффекты `useEffect` согласно правилам их выполнения.

Ключевое различие: render phase вычисляет изменения и может быть прервана, а commit phase применяет результат синхронно и не прерывается для обработки другого React-обновления.

# Что такое concurrent rendering и какие ограничения имеет эта модель?

Concurrent rendering - модель рендеринга, появившаяся в React 18, при которой React может выполнять вычисления интерфейса с возможностью приостановки и переключения между задачами.

Это позволяет обрабатывать срочные обновления, не дожидаясь завершения менее приоритетных вычислений.

Например, при фильтрации большого списка React может обновлять значение текстового поля сразу, а вычисление результатов выполнять как Transition.

Основные ограничения:

- Не является многопоточностью. JavaScript компонентов по-прежнему обычно выполняется в основном потоке браузера.
- Не прерывает произвольный синхронный код. Долгая функция компонента может блокировать поток до завершения своего вызова.
- Не делает все обновления конкурентными. Возможность прерывания зависит от типа обновления и используемых API.
- Не гарантирует ускорения вычислений. Позволяет распределять работу по приоритетам, но не уменьшает её стоимость автоматически.
- Не допускает побочных эффектов во время рендера. Незавершённые вычисления могут быть отброшены.

Для использования конкурентных возможностей применяются `startTransition`, `useTransition`, `useDeferredValue` и интеграции с `Suspense`.

React гарантирует согласованность применяемого интерфейса, даже если его подготовка прерывалась.&#x20;

# Как React группирует обновления состояния?

Batching - механизм объединения нескольких обновлений состояния в один цикл рендеринга для уменьшения количества повторных вычислений.

Например:

```
function handleClick() {
  setCount(c => c + 1);
  setVisible(v => !v);
}
```

React обычно обработает оба обновления в рамках одного рендера.

Начиная с React 18 при использовании `createRoot` работает automatic batching - автоматическая группировка обновлений не только в обработчиках событий React, но и внутри:

- `setTimeout`.
- Обработчиков Promise.
- Нативных обработчиков событий.
- Других асинхронных callback-функций.

Однако группировка не означает, что все обновления всегда объединяются. Например, обновления до и после `await` могут обрабатываться отдельно.

Особенность: несколько вызовов `setState` с использованием одного устаревшего значения не накапливают изменения автоматически.

```
setCount(count + 1);
setCount(count + 1);
```

Оба вызова вычисляют одинаковое новое значение.

Для последовательных изменений следует использовать функциональную форму:

```
setCount(c => c + 1);
setCount(c => c + 1);
```

В этом случае состояние увеличится на `2`.&#x20;

# Какие обновления React считает срочными и несрочными?

React различает обновления по приоритетам, учитывая их влияние на пользовательское взаимодействие.

Срочные обновления (urgent updates) должны обрабатываться с минимальной задержкой.

Примеры:

- Ввод текста.
- Обновление состояния после непосредственного пользовательского действия.
- Изменение состояния управляемого поля ввода.

Несрочные обновления (non-urgent updates) могут быть отложены или прерваны более приоритетной работой.

Примеры:

- Переключение между тяжёлыми страницами.
- Обновление большого списка результатов.
- Пересчёт сложного графика.

React позволяет явно помечать обновления как Transition:

```
setInputValue(value);

startTransition(() => {
  setSearchQuery(value);
});
```

Здесь `setInputValue` обновляет поле ввода, а `setSearchQuery` запускает менее приоритетное обновление результатов.

Важно: `startTransition` не подходит для управления значением текстового поля. При этом не каждое обычное обновление автоматически имеет максимальный приоритет - React использует более детальную внутреннюю систему приоритетов.

# Когда `flushSync` может быть необходим?

`flushSync` из `react-dom` заставляет React синхронно применить необходимые обновления, чтобы DOM был актуален к моменту возврата из вызова.

Он используется при интеграции с внешними API, которым нужно немедленно получить обновлённый DOM.

Например:

```
import { flushSync } from 'react-dom';

flushSync(() => {
  setOpen(true);
});

elementRef.current?.focus();
```

После `flushSync` элемент уже должен присутствовать в DOM, если он создаётся при `open === true`.

Типичные сценарии:

- Работа со сторонними библиотеками, напрямую использующими DOM.
- Интеграция с браузерными API вроде `beforeprint`.
- Ситуации, когда внешняя система требует синхронного обновления интерфейса.

Ограничения:

- Частое использование снижает производительность.
- Может принудительно обработать другие ожидающие обновления.
- Может привести к повторному отображению `Suspense fallback`.

В обычных React-компонентах `flushSync` практически не нужен.&#x20;

# Чем `React.memo` отличается от `useMemo`?

Оба механизма реализуют мемоизацию, но оптимизируют разные операции.

`React.memo` - мемоизирует компонент, позволяя пропустить его повторный рендер, если входные `props` не изменились.

```
const UserCard = memo(function UserCard({ user }) {
  return <div>{user.name}</div>;
});
```

По умолчанию React сравнивает отдельные свойства через `Object.is`.

`useMemo` - кеширует результат вычисления между рендерами, пока зависимости не изменятся.

```
const filteredUsers = useMemo(
  () => users.filter(user => user.active),
  [users]
);
```

Основное различие:

- `React.memo` - помогает избежать повторного рендера компонента из-за рендера родителя.
- `useMemo` - помогает избежать повторного вычисления значения.

`React.memo` не предотвращает обновления собственного состояния компонента или используемого им контекста.

`useMemo` не предотвращает рендер компонента, внутри которого вызывается.

Оба механизма являются оптимизациями производительности, а не инструментами обеспечения корректности.

# Что может вызвать лишний рендер при использовании React Context?

При изменении `value` у `Context.Provider` React обновляет компоненты, читающие этот контекст через `useContext`.

Сравнение старого и нового значения выполняется через `Object.is`.

Распространённая проблема - создание нового объекта при каждом рендере провайдера:

```
<AuthContext.Provider value={{ user, logout }}>
  {children}
</AuthContext.Provider>
```

Даже если `user` не изменился, объект `value` имеет новую ссылку. Это вызывает обновления потребителей контекста.

Для стабилизации значения можно использовать:

```
const value = useMemo(
  () => ({ user, logout }),
  [user, logout]
);
```

При этом `logout` тоже должен иметь стабильную ссылку, иначе мемоизация не поможет.

Другие причины лишних рендеров:

- Один большой Context хранит множество независимых состояний.
- Компонент использует только часть контекста, но обновляется при изменении всего значения.
- Провайдер часто рендерится и создаёт новые функции или объекты.

Важно: `React.memo` не предотвращает рендер при изменении контекста, который компонент непосредственно читает.

Для уменьшения обновлений контекст разделяют по независимым областям данных либо используют хранилища с подпиской на конкретные значения.&#x20;

# Как выявлять дорогие рендеры через React DevTools Profiler?

React DevTools Profiler позволяет анализировать время рендеринга компонентов и выявлять дорогостоящие обновления.

Основной процесс:

1. Открыть вкладку `Profiler` в React DevTools.
2. Начать запись.
3. Выполнить проблемное пользовательское действие.
4. Остановить запись.
5. Изучить отдельные commits и компоненты, участвовавшие в них.

Основные представления:

- Flamegraph - отображает иерархию компонентов и стоимость их рендеринга.
- Ranked - помогает найти компоненты с наибольшими затратами на рендер.

Особое внимание следует обращать на:

- Компоненты с большим временем рендеринга.
- Частые повторные commits.
- Компоненты, обновляющиеся без изменения значимых данных.
- Каскады обновлений после выполнения эффектов.

В зависимости от версии DevTools можно использовать информацию о причинах рендера и изменившихся `props`.

Важно: измерения в development-режиме могут отличаться от production, особенно при включённом `StrictMode`. Результаты следует проверять в условиях, близких к реальным.

# Что такое referential equality и почему она важна для оптимизации?

Referential equality - равенство значений по ссылке, когда две переменные указывают на один и тот же объект или функцию.

В JavaScript объекты сравниваются по идентичности:

```
const a = { id: 1 };
const b = { id: 1 };

console.log(a === b); // false
```

Несмотря на одинаковое содержимое, объекты имеют разные ссылки.

В React это важно, потому что `React.memo`, зависимости хуков и Context используют сравнение значений, основанное на `Object.is`.

Например:

```
<Child options={{ theme: 'dark' }} />
```

При каждом рендере родителя создаётся новый объект `options`. Даже если `Child` обёрнут в `React.memo`, изменение ссылки может привести к его повторному рендеру.

Для сохранения ссылки можно использовать:

```
const options = useMemo(
  () => ({ theme: 'dark' }),
  []
);
```

Для функций аналогичную задачу решает `useCallback`.

Важно: стабильность ссылок полезна там, где она влияет на сравнение зависимостей или возможность пропуска рендера. Мемоизировать каждый объект и каждую функцию не требуется.

# Как работает `Suspense` и что выступает его fallback?

`Suspense` позволяет показывать временный интерфейс, пока вложенные компоненты ожидают ресурсов, поддерживающих механизм Suspense.

Например:

```
<Suspense fallback={<Spinner />}>
  <UserProfile />
</Suspense>
```

Если `UserProfile` при рендере приостанавливается, React отображает `Spinner`.

Fallback - React-элемент, который временно заменяет содержимое границы `Suspense`.

В качестве fallback можно использовать:

- Индикатор загрузки.
- Skeleton-компонент.
- Текст.
- `null`, если ничего показывать не нужно.

Suspense активируется, например, при:

- Загрузке кода через `React.lazy`.
- Чтении Promise через `use()`.
- Загрузке данных через совместимый с Suspense фреймворк.

Важные особенности:

- Обычный `fetch` внутри `useEffect` сам по себе не активирует Suspense.
- Если компонент приостановился до первого монтирования, React повторит его первоначальный рендер после готовности данных.
- Если уже отображаемое содержимое снова приостанавливается, React может показать fallback повторно.
- `startTransition` и `useDeferredValue` позволяют избежать нежелательного скрытия уже отображённого содержимого.

`Suspense` обрабатывает ожидание ресурсов, но не заменяет Error Boundary для обработки ошибок.&#x20;

# Что такое streaming rendering?

Streaming rendering - механизм серверного рендеринга, при котором HTML отправляется клиенту постепенно, по мере готовности отдельных частей интерфейса.

В отличие от традиционного SSR, серверу не обязательно ждать формирования всей страницы.

Общий процесс:

1. Сервер начинает рендерить React-дерево.
2. Готовая часть HTML отправляется браузеру.
3. Для ещё не готовых частей отображаются `Suspense fallback`.
4. По мере готовности сервер отправляет дополнительные HTML-фрагменты.
5. Браузер постепенно заменяет заглушки готовым содержимым.
6. React гидратирует серверный HTML, подключая клиентскую интерактивность.

Основные API:

- `renderToPipeableStream` - для Node.js Streams.
- `renderToReadableStream` - для окружений с Web Streams.

Преимущества:

- Пользователь раньше видит первоначальное содержимое.
- Медленные компоненты не блокируют отправку всей страницы.
- Поддерживается выборочная гидратация (selective hydration).

Ограничение: streaming улучшает доставку и отображение HTML, но не гарантирует, что весь интерфейс сразу станет интерактивным. Для этого необходима соответствующая клиентская гидратация.&#x20;

# Почему `lazy()` должен объявляться вне компонента?

`React.lazy()` создаёт объект, представляющий лениво загружаемый тип React-компонента.

Если вызывать `lazy()` внутри компонента, при каждом рендере будет создаваться новый тип компонента:

```
function App() {
  const Page = lazy(() => import('./Page'));

  return <Page />;
}
```

React воспринимает новый тип как другой компонент, поэтому может размонтировать старый экземпляр и создать новый.

Это приводит к:

- Сбросу локального состояния.
- Повторному монтированию.
- Лишним вычислениям и выполнению эффектов.

Правильный вариант:

```
const Page = lazy(() => import('./Page'));

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Page />
    </Suspense>
  );
}
```

При таком объявлении идентичность ленивого компонента остаётся стабильной.

`lazy()` кеширует результат загрузки для созданного им типа компонента, поэтому повторный вызов загрузчика для этого типа не требуется.&#x20;

# Как использовать lazy loading для маршрутов?

Route-based lazy loading - разделение приложения на JavaScript-модули, загружаемые при переходе на соответствующие маршруты.

Это уменьшает объём JavaScript, необходимого при первоначальной загрузке приложения.

Например, в React Router 7 с Data Router можно использовать `lazy` в конфигурации маршрута:

```
import { createBrowserRouter } from 'react-router';

const router = createBrowserRouter([
  {
    path: '/',
    Component: Home
  },
  {
    path: '/settings',
    lazy: () => import('./routes/settings')
  }
]);
```

Модуль `./routes/settings` может экспортировать компонент маршрута:

```
export function Component() {
  return <Settings />;
}
```

React Router загрузит модуль при необходимости. Его механизм `route.lazy` также позволяет динамически загружать другие свойства маршрута.

Другой вариант - использовать `React.lazy` вместе с `Suspense` при декларативной маршрутизации.

Основные особенности:

- Каждый маршрут может быть отдельным JavaScript-чанком.
- Загрузка кода происходит по требованию.
- Пользователь должен видеть предусмотренное состояние загрузки.
- Ошибки загрузки модулей необходимо обрабатывать.
- При необходимости можно предварительно загружать код предполагаемого следующего маршрута.

Lazy loading сокращает первоначальную загрузку, но может добавить задержку при первом посещении маршрута.&#x20;

# Как проектировать границы ошибок и загрузки?

В React для обработки ошибок и ожидания ресурсов используются разные механизмы.

Error Boundary перехватывает ошибки, возникающие при рендеринге вложенного дерева, и отображает резервный интерфейс.

Suspense Boundary отображает fallback, когда вложенное дерево ожидает поддерживаемые ресурсы.

Пример композиции:

```
<ErrorBoundary fallback={<ErrorMessage />}>
  <Suspense fallback={<Loading />}>
    <UserProfile />
  </Suspense>
</ErrorBoundary>
```

Здесь:

- `Suspense` обрабатывает ожидание данных или кода.
- `ErrorBoundary` обрабатывает ошибки рендеринга, включая неудачную загрузку через `lazy`.

Основные принципы проектирования:

- Границы должны соответствовать логическим частям интерфейса. Ошибка одного виджета не должна обязательно ломать всю страницу.
- Общие элементы интерфейса желательно сохранять видимыми. Например, шапка приложения не должна исчезать при загрузке содержимого страницы.
- Fallback должен соответствовать ожидаемому содержимому. Для крупных блоков часто подходит skeleton.
- Ошибки должны иметь понятный сценарий восстановления. Например, повторную попытку загрузки или переход на другую страницу.
- Слишком крупные границы уменьшают независимость частей интерфейса, а чрезмерное дробление усложняет управление состояниями загрузки.

Важно учитывать, что Error Boundary не перехватывает обычные ошибки обработчиков событий, произвольных асинхронных callback-функций и серверного рендеринга.

В React стандартная реализация Error Boundary основана на классовом компоненте или готовой библиотеке.

# Что меняется при использовании React Compiler и как он связан с ручной мемоизацией?

React Compiler - компилятор, выполняющий автоматическую оптимизацию React-компонентов и хуков во время сборки приложения.

Стабильная версия React Compiler 1.0 вышла в октябре 2025 года.

Компилятор анализирует код и автоматически применяет мемоизацию, которая раньше часто требовала ручного использования:

- `React.memo`.
- `useMemo`.
- `useCallback`.

Например, React Compiler может определить, что результат вычисления или JSX-элемент не зависит от изменившихся данных, и повторно использовать предыдущее значение.

Что меняется на практике:

- Уменьшается необходимость вручную контролировать идентичность объектов и функций.
- Многие повторные рендеры пропускаются автоматически.
- Разработчик может больше концентрироваться на корректности логики.
- Оптимизации выполняются только для кода, который компилятор способен безопасно проанализировать.

При этом React Compiler требует соблюдения правил React, включая чистоту рендера и корректное использование хуков.

Связь с ручной мемоизацией:

- В новом коде обычно можно полагаться на компилятор.
- Существующие `useMemo`, `useCallback` и `React.memo` необязательно удалять.
- Ручная мемоизация остаётся полезной, когда необходимо явно контролировать стабильность значения.
- Удаление существующей мемоизации требует проверки, поскольку может изменить результат компиляции.

React Compiler не устраняет все причины обновлений, не исправляет некорректную архитектуру состояния и не гарантирует отсутствие дорогостоящих рендеров.&#x20;

# Как использовать React Profiler и Chrome Performance вместе?

Эти инструменты анализируют производительность на разных уровнях.

React DevTools Profiler показывает:

- Какие компоненты рендерились.
- Сколько времени занял их рендер.
- Какие обновления входили в отдельные commits.
- Где находятся дорогие поддеревья.

Chrome DevTools Performance показывает:

- Выполнение JavaScript.
- Долгие задачи основного потока.
- Обработку событий.
- Перерасчёт стилей и layout.
- Отрисовку и композитинг.
- Сетевую активность и взаимодействие с браузером.

Практический процесс:

1. В React Profiler найти медленное пользовательское действие и участвующие компоненты.
2. Определить наиболее дорогие renders и commits.
3. Записать то же действие через Chrome Performance.
4. Найти соответствующие длительные задачи на временной шкале.
5. Определить источник задержки: React-вычисления, пользовательский JavaScript, layout, paint или другие операции.
6. После изменений повторить измерение.

Начиная с React 19.2 доступны React Performance Tracks для Chrome Performance:

- `Scheduler` - показывает выполнение React-задач и их приоритеты.
- `Components` - показывает работу компонентов и эффектов.

Они позволяют анализировать React вместе с браузерными операциями на общей временной шкале.

Важно: медленный React-рендер и медленная отрисовка браузера - разные проблемы. Первый инструмент помогает найти затратные компоненты, второй - установить фактическую причину задержки интерфейса.&#x20;

# Как снизить количество ненужных React-рендеров?

Основная задача - уменьшить количество компонентов, затрагиваемых обновлениями, и исключить обновления без реальной необходимости.

1\. Хранить состояние ближе к месту использования.

Не следует поднимать локальное состояние выше, чем требуется.

Например, состояние открытого меню лучше хранить в компоненте меню, а не в корневом компоненте приложения.

2\. Использовать `React.memo` для компонентов с неизменными props.

Это позволяет пропускать рендеры, вызванные обновлением родителя.

3\. Стабилизировать ссылки там, где это важно.

Применять `useMemo` и `useCallback`, если новые объекты или функции мешают мемоизации либо вызывают ненужные эффекты.

4\. Разделять Context по областям ответственности.

Не хранить множество часто изменяющихся независимых состояний в одном контексте.

5\. Исключать лишние обновления из `useEffect`.

Не хранить в состоянии значения, которые можно непосредственно вычислить из существующих `props` и `state`.

6\. Использовать подписки на отдельные значения.

При работе с большими внешними хранилищами выбирать механизмы, позволяющие обновлять компоненты только при изменении используемых ими данных.

7\. Избегать нестабильной идентичности компонентов.

Не создавать определения компонентов внутри других компонентов и не использовать случайные `key`.

8\. Использовать React Compiler, если он включён в проект.

Он автоматически выполняет значительную часть оптимизаций мемоизации.

Важно: уменьшение числа рендеров не всегда означает повышение производительности. Иногда один дорогой рендер хуже нескольких дешёвых, поэтому изменения необходимо оценивать измерениями.

# Как проверить, что интерфейс не перерисовывается слишком часто?

Основной инструмент - React DevTools Profiler, позволяющий измерять количество и стоимость рендеров при реальных взаимодействиях.

Последовательность проверки:

1. Записать конкретное действие пользователя, например ввод символа или переключение вкладки.
2. Посмотреть количество commits и компоненты, участвовавшие в обновлениях.
3. Проверить, какие компоненты рендерятся при изменении конкретного состояния.
4. Убедиться, что независимые части интерфейса не обновляются без необходимости.
5. Проанализировать время выполнения рендеров, а не только их количество.
6. Повторить измерения после изменений.

Для локальной диагностики можно временно использовать счётчик вызовов функции компонента:

```
function UserCard({ user }) {
  console.count('UserCard render');

  return <div>{user.name}</div>;
}
```

Однако такой счётчик показывает вызовы функции компонента, а не количество commits. React может выполнить рендер и отказаться от его результата.

Также необходимо учитывать:

- `StrictMode` может намеренно вызывать компоненты повторно в development-режиме.
- Конкурентный рендеринг может повторять незавершённые вычисления.
- Повторный рендер не обязательно означает изменение DOM.
- Значение имеет не только частота обновлений, но и их продолжительность.

Критерий нормальной работы - обновления выполняются только там, где это необходимо, и не создают заметных задержек пользовательского взаимодействия. Универсального допустимого количества рендеров не существует.
