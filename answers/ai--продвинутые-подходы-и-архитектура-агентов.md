# Что такое single-agent и multi-agent подходы?

Single-agent - архитектура, в которой один ИИ-агент управляет выполнением задачи: анализирует запрос, планирует действия, вызывает инструменты, обрабатывает результаты и принимает решения о следующих шагах.

Один агент может выполнять несколько ролей, переключаться между инструментами и самостоятельно проверять результаты.

Multi-agent - архитектура, в которой несколько специализированных агентов совместно решают задачу. Каждый может иметь собственную модель, инструкции, инструменты, контекст и область ответственности.

Например, при разработке функциональности:

- `Planner` анализирует требования и составляет план
- `Developer` реализует изменения
- `Reviewer` проверяет код
- `Tester` запускает тесты и анализирует ошибки

Взаимодействие может быть организовано через центрального координатора (orchestrator) или непосредственную передачу управления между агентами (handoff).

Главное различие: в single-agent подходе управление сосредоточено в одном агенте, а в multi-agent распределено между несколькими.

При этом multi-agent не обязательно использует разные LLM. Несколько агентов могут работать на одной модели, но иметь разные роли и контексты.

# В каких случаях использование нескольких агентов оправдано?

Multi-agent оправдан, когда разделение задачи на независимые или специализированные части даёт измеримую пользу по сравнению с одним агентом.

Основные случаи:

- Сложные задачи. Разработка большой функциональности, требующей анализа архитектуры, реализации, тестирования и проверки безопасности
- Разные специализации. Агент для SQL-запросов, агент для frontend и агент для инфраструктуры используют разные инструкции и инструменты
- Параллельная обработка. Несколько независимых задач выполняются одновременно, сокращая общее время
- Изоляция контекста. Каждый агент получает только необходимые данные, уменьшая размер и загрязнение контекстного окна
- Независимая проверка. Один агент выполняет задачу, другой оценивает результат по заданным критериям
- Разграничение доступа. Агенты получают минимальные разрешения, необходимые для своих операций

Когда multi-agent не оправдан: небольшие линейные задачи, где дополнительная координация увеличивает стоимость, задержки и вероятность ошибок.

Несколько агентов не гарантируют более качественный результат. Они создают дополнительные точки отказа: неправильную делегацию, потерю контекста, противоречивые решения и конфликты изменений.

Поэтому базовым вариантом обычно остаётся single-agent, а multi-agent вводится при наличии конкретного ограничения, которое он способен устранить.

# Что такое subagents и как распределять задачи между ними?

Subagents (субагенты) - подчинённые агенты, которым основной агент делегирует отдельные задачи.

Основной агент обычно выступает координатором: определяет подзадачи, выбирает исполнителей, передаёт входные данные и объединяет результаты.

Субагент может иметь собственные инструкции, инструменты и независимый контекст выполнения.

Пример распределения при разработке API:

- `Main Agent` - анализирует задачу и координирует выполнение
- `Database Agent` - проектирует изменения схемы БД
- `Backend Agent` - реализует API
- `Test Agent` - проверяет корректность реализации

Для корректной делегации каждому субагенту необходимо определить:

1. Цель - какой результат требуется получить
2. Контекст - необходимые требования, файлы и ограничения
3. Инструменты - какие операции разрешено выполнять
4. Область ответственности - какие ресурсы он может изменять
5. Формат результата - что передать основному агенту и по каким критериям оценивать готовность

Например, субагенту тестирования можно передать задачу: проверить endpoint, выполнить интеграционные тесты и вернуть список ошибок с указанием файлов и причин.

Важный принцип: задачи должны иметь чёткие границы. Если несколько субагентов одновременно изменяют одни и те же файлы, возникают конфликты и риск потери изменений.

# Чем последовательная работа агентов отличается от параллельной?

Последовательная работа (sequential execution) - агенты выполняют задачи по очереди, причём следующий этап может использовать результат предыдущего.

Пример:

`Planner → Developer → Reviewer → Tester`

Подход подходит для задач с зависимостями: невозможно полноценно проверить реализацию до её появления.

Преимущества - предсказуемый порядок выполнения, простая передача результатов и контроль зависимостей.

Недостаток - общее время складывается из времени последовательных этапов.

Параллельная работа (parallel execution) - несколько агентов одновременно выполняют независимые задачи.

Пример: один агент анализирует frontend, второй - backend, третий - инфраструктуру. После завершения координатор объединяет результаты.

Преимущества - сокращение времени выполнения и возможность независимого анализа.

Недостатки - повышенная нагрузка на API, необходимость синхронизации и риск конфликтов при работе с общими ресурсами.

При идеальной параллельности общее время определяется наиболее длительной задачей, но на практике добавляются затраты на координацию и объединение результатов.

На практике часто используют гибридный подход: независимые этапы выполняются параллельно, а зависимые - последовательно.

# Как организовать передачу контекста между независимыми агентами?

Передача контекста (context handoff) - механизм обмена необходимой информацией между агентами, которые могут не иметь общей истории сообщений.

Контекст передаётся явно через сообщения, структурированные объекты или общее хранилище.

Основные способы:

- Structured output. Передача результата в согласованном формате, например JSON с полями `task`, `status`, `result`, `errors`
- Shared state. Общее состояние задачи в базе данных или специализированном хранилище
- Artifacts. Передача ссылок на файлы, изменения кода, отчёты и результаты тестирования
- Summarization. Сжатие длинной истории в краткое описание принятых решений, ограничений и текущего состояния
- RAG. Получение необходимого проектного контекста из общей базы знаний

Например, разработчик завершает задачу и передаёт тестировщику список изменённых файлов, описание поведения API и команды запуска тестов.

Важное ограничение: не следует без необходимости передавать полную историю работы одного агента другому. Это увеличивает расход токенов, добавляет нерелевантную информацию и может ухудшать качество решений.

Надёжная передача контекста требует сохранения критичных фактов, явного разделения фактов и предположений, версионирования артефактов и проверки полученных данных.

Также необходимо учитывать безопасность: агент должен получать только разрешённые данные, а содержимое файлов и результаты инструментов нельзя считать доверенными инструкциями.

# Что такое human-in-the-loop и когда требуется участие разработчика?

Human-in-the-loop (HITL) - подход, при котором человек участвует в принятии решений, проверке результатов или подтверждении действий ИИ-агента.

Агент выполняет автоматизированную работу, но на определённых этапах приостанавливается и ожидает решения человека.

Основные сценарии:

- Необратимые действия. Удаление данных, изменение production-инфраструктуры, выполнение критичных миграций
- Изменения архитектуры. Выбор между решениями с существенными техническими последствиями
- Недостаток информации. Неоднозначные требования или отсутствующие бизнес-правила
- Безопасность. Запрос расширенных разрешений, доступ к секретам или выполнение потенциально опасных команд
- Контроль качества. Проверка сложных изменений перед объединением кода или развёртыванием

Пример: агент подготовил миграцию базы данных и оценил возможные последствия. Перед выполнением в production он запрашивает подтверждение разработчика.

Технически HITL часто реализуется через interrupt/resume:

1. Агент достигает контрольной точки
2. Состояние выполнения сохраняется
3. Человеку отправляется запрос на подтверждение или уточнение
4. После ответа выполнение возобновляется с учётом принятого решения

В HITL важно проверять не только факт подтверждения, но и его полномочия и применимость к конкретному действию.

HITL особенно необходим там, где стоимость ошибочного действия превышает выгоду от полной автоматизации.

# Как организовать checkpoints и восстановление состояния после ошибок агента?

Checkpoint - сохранённое состояние выполнения агента, позволяющее продолжить работу после сбоя, перезапуска или прерывания.

Checkpoint может содержать текущий этап, историю необходимых сообщений, результаты инструментов, промежуточные артефакты и информацию о незавершённых операциях.

Типичная организация:

1. State management. Состояние задачи представляется структурированным объектом
2. Persistence. После значимых этапов состояние сохраняется в устойчивом хранилище, например PostgreSQL
3. Execution tracking. Каждый запуск и этап получают идентификаторы и статусы
4. Failure detection. При ошибке фиксируются причина и последний успешно завершённый этап
5. Recovery. Система загружает checkpoint и возобновляет выполнение согласно механизму выбранного runtime

Например, агент выполнил анализ проекта, изменил код и начал тестирование. Если тестовый этап завершился ошибкой, система может восстановить состояние после изменения кода без повторного анализа проекта.

При этом восстановление состояния не эквивалентно откату внешних действий. Запись в базу данных или вызов API могут уже иметь последствия.

Поэтому важны:

- Idempotency - безопасное повторное выполнение операций без нежелательных дублирующих эффектов
- Retry policy - ограниченное количество повторных попыток с задержками
- Compensating actions - отдельные операции для компенсации уже выполненных действий
- External state tracking - учёт результатов внешних операций, которые не сохраняются автоматически в checkpoint

Например, в `LangGraph` используются checkpointer и идентификатор `thread_id`. При возобновлении прерванного узла его код может выполняться заново с начала, поэтому побочные эффекты требуют особого контроля.&#x20;

# Что такое RAG и как он может использоваться для предоставления агенту знаний о проекте?

RAG (Retrieval-Augmented Generation) - подход, при котором языковая модель получает дополнительную информацию из внешних источников непосредственно перед генерацией ответа или выполнением задачи.

В отличие от обучения или fine-tuning модели, RAG позволяет использовать актуальные проектные знания без изменения её весов.

Типичный процесс:

1. Indexing. Документация, исходный код и архитектурные описания разбиваются на фрагменты (`chunks`) и индексируются
2. Retrieval. По запросу агента находятся релевантные фрагменты с использованием keyword, vector или hybrid search
3. Augmentation. Найденные данные добавляются в контекст модели
4. Generation. Агент использует полученные сведения для формирования ответа или принятия решения

Для векторного поиска часто используются embeddings - числовые представления текста, позволяющие оценивать его семантическую близость к запросу.

Пример: агент получает задачу реализовать авторизацию. RAG позволяет найти существующие middleware, правила безопасности, архитектурные соглашения и документацию API.

Это помогает учитывать особенности проекта без загрузки всего репозитория в контекстное окно.

Ограничения RAG:

- Качество результата зависит от полноты и актуальности индекса
- Неправильное разбиение документов может нарушать смысловые связи
- Поиск способен пропустить критичную информацию
- Найденные документы могут содержать устаревшие сведения или prompt injection
- Модель всё равно может ошибаться при интерпретации найденного контекста

Поэтому для работы с кодом RAG часто комбинируют с точным поиском символов, анализом AST, LSP и чтением исходных файлов.

# Как оценивать стоимость использования ИИ-агента с учётом токенов и времени?

Стоимость ИИ-агента включает расходы на модель, инструменты, инфраструктуру и время выполнения задачи.

Основная составляющая при использовании облачных LLM API - стоимость токенов.

Провайдеры обычно устанавливают отдельные тарифы для:

- `Input tokens` - токенов входного контекста
- `Output tokens` - токенов сгенерированного ответа
- `Cached input tokens` - повторно используемых токенов контекста, если поддерживается кэширование

Базовая формула:

\\[ C\_{\text{LLM}} = \frac{T\_{\text{in}}P\_{\text{in}}+ T\_{\text{out}}P\_{\text{out}}}{10^6} \\]

Где:

- \\(T\\) - количество токенов соответствующего типа
- \\(P\\) - цена за миллион токенов

При наличии кэширования его стоимость учитывается отдельно. Для агента с несколькими обращениями к моделям расходы суммируются по всем вызовам.

Дополнительно учитываются:

- Вызовы платных инструментов и внешних API
- Выполнение кода, контейнеры, поиск и хранение данных
- Повторные запросы из-за ошибок (`retries`)
- Работа субагентов и повторные проверки
- Вычислительные ресурсы и эксплуатационные расходы

Время выполнения (`latency`) следует измерять отдельно от стоимости API. Оно влияет на производительность системы, пользовательский опыт и стоимость инфраструктуры.

Основные метрики:

- Cost per task - полная стоимость одной задачи
- Latency per task - время от запуска до результата
- Success rate - доля успешно выполненных задач
- Cost per successful task - общие расходы, разделённые на количество успешных задач

Последняя метрика особенно важна: дешёвый агент с большим количеством ошибок может оказаться дороже более качественной модели.

# Как сравнивать качество разных моделей и агентов при решении одной технической задачи?

Для объективного сравнения используют evaluations (evals) - воспроизводимые проверки моделей и агентных систем на наборе задач с заранее определёнными критериями.

Важно разделять качество самой модели и качество агента: конечный результат зависит также от инструкций, инструментов, контекста и механизма управления выполнением.

Процесс сравнения:

1. Подготовить benchmark. Собрать репрезентативный набор реальных технических задач различной сложности
2. Определить критерии. Например, корректность реализации, прохождение тестов, безопасность, соблюдение требований
3. Обеспечить сопоставимые условия. Использовать одинаковые исходные данные, окружение, доступные инструменты и ограничения, если оценивается именно модель
4. Выполнить несколько запусков. Повторные испытания позволяют оценить нестабильность результатов
5. Проверить результаты. Использовать автоматические тесты, статический анализ и независимую экспертную оценку
6. Сравнить метрики. Учитывать не только качество, но и стоимость, задержки и надёжность

Для задач программирования полезны следующие метрики:

- Task success rate - доля задач, удовлетворяющих критериям приёмки
- Test pass rate - доля успешно пройденных тестов
- Pass\@k - вероятность получить хотя бы одно успешное решение среди `k` независимых попыток
- Latency - время выполнения
- Cost per successful task - стоимость успешного решения
- Regression rate - частота появления новых ошибок после изменений

Для агентов дополнительно анализируют execution traces - последовательности вызовов моделей, инструментов и передач управления. Это позволяет выявлять неправильное планирование, неудачную делегацию и лишние действия.&#x20;
