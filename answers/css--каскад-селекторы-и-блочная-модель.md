````
# Как подключить CSS к странице и какие способы имеют разные последствия?

Существует четыре основных способа подключения CSS:

1. **Внешний файл** - `<link rel="stylesheet" href="styles.css">`. Основной способ. Стили переиспользуются, кешируются браузером и отделены от HTML. Обычная таблица стилей в `<head>` блокирует рендеринг до загрузки и обработки CSS.
2. **Встроенные стили** - `<style>...</style>`. CSS размещается непосредственно в HTML. Не требует отдельного запроса, но увеличивает размер документа и усложняет кеширование.
3. **Инлайновые стили** - `<div style="color: red">`. Применяются к конкретному элементу и имеют высокий приоритет среди обычных авторских деклараций. Не поддерживают обычный синтаксис селекторов и медиазапросов внутри атрибута.
4. **Импорт** - `@import url("styles.css")`. Подключает другую таблицу стилей из CSS. Может создавать последовательные сетевые запросы и задерживать рендеринг, поэтому для основных стилей предпочтительнее `<link>`.

Дополнительно CSS может загружаться динамически через JavaScript, но это создаёт риск появления страницы без необходимых стилей до выполнения скрипта.

При одинаковом уровне каскада и специфичности побеждает последнее объявление независимо от того, находится оно в `<style>` или во внешнем файле. Инлайновые стили имеют отдельный, более высокий приоритет среди обычных авторских деклараций.

# Как браузер рассчитывает приоритет CSS-правил?

Браузер использует **каскад (CSS Cascade)** - алгоритм выбора итогового значения свойства, когда на элемент действует несколько деклараций.

Порядок определения приоритета:

1. **Применимость** - учитываются только подходящие правила, включая условия `@media`, `@supports` и совпадение селекторов.
2. **Происхождение и важность** - браузерные, пользовательские и авторские стили, `!important`, каскадные слои, анимации и переходы.
3. **Специфичность** - сравнивается вес селекторов.
4. **Близость области видимости (`@scope`)** - при равной специфичности предпочтение получает правило с ближайшим корнем области.
5. **Порядок объявления** - при остальных равных условиях побеждает последнее правило.

Упрощённая иерархия от меньшего приоритета к большему, без детализации слоёв:

1. Обычные стили браузера.
2. Обычные пользовательские стили.
3. Обычные авторские стили.
4. CSS-анимации (`@keyframes`).
5. Авторские стили с `!important`.
6. Пользовательские стили с `!important`.
7. Браузерные стили с `!important`.
8. Активные CSS-переходы (`transition`).

**Важно:** специфичность сравнивается только после определения приоритетного происхождения, важности и слоя. Поэтому селектор с `#id` не обязательно победит менее специфичный селектор из более приоритетного слоя.

# Что такое специфичность и как её вычислять?

**Специфичность (specificity)** - вес CSS-селектора, который используется для разрешения конфликтов между правилами одного уровня каскада.

Обычно представляется тройкой `(A, B, C)`:

- **A** - количество ID-селекторов (`#header`).
- **B** - количество классов (`.active`), атрибутов (`[disabled]`) и псевдоклассов (`:hover`).
- **C** - количество селекторов типов (`div`) и псевдоэлементов (`::before`).

Примеры:

- `div` - `(0, 0, 1)`
- `.card` - `(0, 1, 0)`
- `div.card:hover` - `(0, 2, 1)`
- `#app .card` - `(1, 1, 0)`
- `#app .card p` - `(1, 1, 1)`

Сравнение происходит **слева направо**, по каждому разряду. Поэтому один ID-селектор сильнее любого количества классов.

Особенности:

- `*` и комбинаторы (`>`, `+`, `~`, пробел) не увеличивают специфичность.
- `:where()` всегда имеет нулевую специфичность.
- `:is()`, `:not()` и `:has()` получают специфичность наиболее специфичного селектора в своих аргументах.
- Инлайновый `style` имеет отдельный приоритет выше обычных авторских правил.
- `!important` не увеличивает специфичность, а изменяет приоритет декларации на уровне каскада.

Высокая специфичность не означает безусловную победу: сначала учитываются происхождение, важность и каскадный слой.

# Как работают `!important`, `@layer` и порядок объявления стилей?

**`!important`** повышает приоритет конкретной CSS-декларации в каскаде.

```css
.button {
  color: red !important;
}

#submit {
  color: blue;
}
````

Кнопка будет красной, несмотря на более специфичный селектор `#submit`.

Однако `!important` не имеет абсолютного приоритета: пользовательские и браузерные `!important`-стили могут переопределять авторские, а активные CSS-переходы имеют ещё более высокий приоритет.

`@layer` позволяет создавать каскадные слои и управлять приоритетами независимо от специфичности селекторов.

```
@layer reset, components, overrides;

@layer components {
  .button {
    color: blue;
  }
}

@layer overrides {
  button {
    color: red;
  }
}
```

Кнопка станет красной: слой `overrides` объявлен после `components`, поэтому имеет больший приоритет для обычных деклараций, даже при меньшей специфичности.

Основные правила:

- Для обычных деклараций более поздний слой приоритетнее раннего.
- Обычные стили вне слоёв приоритетнее обычных стилей внутри слоёв.
- Для `!important` порядок слоёв обращается: более ранние слои становятся приоритетнее поздних, а декларации внутри слоёв приоритетнее деклараций вне слоёв.
- Порядок слоёв фиксируется при их первом объявлении.

Порядок объявления учитывается только после происхождения, важности, слоя, специфичности и близости `@scope`. Если эти условия равны, побеждает последняя декларация.

# Чем наследование CSS отличается от каскадирования?

Каскадирование определяет, какое значение CSS-свойства выбрать из нескольких конкурирующих деклараций для одного элемента.

Наследование позволяет элементу получать значение свойства от родителя, когда для него не задано собственное значение и свойство наследуется по умолчанию.

Например:

```
.parent {
  color: red;
  border: 1px solid black;
}
```

Дочерний элемент унаследует `color: red`, но не унаследует `border`.

Обычно наследуются свойства текста: `color`, `font-family`, `font-size`, `line-height` и другие.

Не наследуются по умолчанию свойства геометрии и оформления: `margin`, `padding`, `border`, `width`, `height`, `background-color`.

Ключевое различие: каскад выбирает значение среди подходящих деклараций, а наследование используется при определении значения свойства, если собственное значение не задано и свойство допускает наследование.

Любая применимая декларация на самом элементе, даже с низкой специфичностью, имеет преимущество перед значением, которое элемент мог бы получить по наследству.

# Как работают ключевые слова `inherit`, `initial`, `unset`, `revert` и `revert-layer`?

Это универсальные CSS-значения для управления значением свойства.

- `inherit` - принудительно наследует вычисленное значение свойства от родителя, даже если свойство обычно не наследуется.
- `initial` - устанавливает начальное значение свойства, определённое спецификацией CSS.
- `unset` - действует как `inherit` для наследуемых свойств и как `initial` для ненаследуемых.
- `revert` - откатывает значение к результату каскада без деклараций текущего происхождения. Для авторских стилей это обычно означает возврат к пользовательским или браузерным стилям.
- `revert-layer` - откатывает значение так, будто декларации текущего каскадного слоя для свойства отсутствуют, позволяя использовать результат предыдущих слоёв. При отсутствии подходящих значений откат может дойти до другого происхождения.

Пример:

```
button {
  color: inherit;
  background: revert;
}
```

Кнопка наследует цвет текста родителя, а фон определяется без авторских деклараций для этого свойства.

Важно различать `initial` и `revert`: например, `display: initial` устанавливает `inline`, поскольку это начальное значение `display`. А `display: revert` для `<div>` обычно возвращает браузерное `block`.

# Какие есть виды CSS-селекторов?

CSS-селекторы позволяют выбирать элементы по типу, атрибутам, состоянию и положению в DOM.

Основные виды:

- Типа: `div`, `button` - выбирают элементы по имени тега.
- Класса: `.card` - выбирает элементы с указанным классом.
- ID: `#header` - выбирает элементы по идентификатору.
- Универсальный: `*` - соответствует любому элементу.
- Атрибута: `[disabled]`, `[type="text"]`, `[class^="btn"]`.
- Псевдоклассы: `:hover`, `:focus-visible`, `:checked`, `:nth-child(2)`.
- Псевдоэлементы: `::before`, `::after`, `::first-line`.

Комбинаторы определяют отношения между элементами:

- `A B` - потомок `A` любой глубины.
- `A > B` - непосредственный ребёнок.
- `A + B` - следующий соседний элемент.
- `A ~ B` - любой следующий сосед с общим родителем.
- `A || B` - связь с колонкой в табличной или колоночной структуре.

Селекторы можно комбинировать:

```
.card > button:hover {
  background: blue;
}
```

Правило выбирает кнопку, которая является непосредственным ребёнком `.card` и находится в состоянии наведения.

Запятая используется для группировки независимых селекторов: `h1, h2, h3`.

# Чем псевдокласс отличается от псевдоэлемента?

Псевдокласс выбирает существующий элемент на основании его состояния, положения или других условий.

Примеры:

- `:hover` - на элемент наведён указатель.
- `:focus-visible` - элемент находится в состоянии фокуса, для которого требуется видимый индикатор.
- `:first-child` - элемент является первым ребёнком родителя.
- `:checked` - checkbox или radio выбран.

Псевдоэлемент выбирает определённую часть элемента или создаваемый CSS объект, который можно стилизовать.

Примеры:

- `::before` и `::after` - генерируют содержимое.
- `::first-letter` - выбирает первую букву.
- `::selection` - стилизует выделенный текст.
- `::marker` - стилизует маркер списка.

Пример:

```
button:hover {
  color: red;
}

button::before {
  content: "→ ";
}
```

Псевдокласс изменяет стиль кнопки при наведении, а псевдоэлемент добавляет перед её содержимым стрелку.

Обычно псевдоклассы записываются через `:`, а псевдоэлементы через `::`. Для некоторых исторических псевдоэлементов поддерживается и одинарное двоеточие.

# Для чего нужны `:is()`, `:where()` и `:has()`?

Эти функциональные псевдоклассы упрощают селекторы и позволяют описывать более сложные условия.

`:is()` группирует альтернативные селекторы без дублирования CSS.

```
:is(h1, h2, h3) {
  color: blue;
}
```

Специфичность `:is()` определяется самым специфичным селектором из переданного списка.

`:where()` работает аналогично `:is()`, но всегда имеет нулевую специфичность.

```
:where(.card, .panel) button {
  border: none;
}
```

Полезен для базовых стилей, которые должны легко переопределяться.

`:has()` выбирает элемент на основании наличия связанных с ним элементов, их состояния или структуры.

```
.card:has(> img) {
  padding: 0;
}

.form:has(input:invalid) {
  border-color: red;
}
```

Первый селектор выбирает `.card` с непосредственным дочерним изображением, второй - форму с невалидным полем ввода.

`:has()` позволяет решать многие задачи без JavaScript и дополнительных CSS-классов. При этом слишком широкие условия могут увеличивать стоимость пересчёта стилей.

# Как устроена блочная модель CSS?

CSS Box Model описывает прямоугольную область, занимаемую элементом.

Она состоит из четырёх областей, от внутренней к внешней:

1. Content - содержимое элемента, например текст или изображение.
2. Padding - внутренний отступ между содержимым и границей.
3. Border - граница элемента.
4. Margin - внешний отступ, отделяющий элемент от окружающих элементов.

По умолчанию используется `box-sizing: content-box`, поэтому `width` и `height` задают размер области содержимого.

Например:

```
.box {
  width: 200px;
  padding: 20px;
  border: 2px solid;
  margin: 10px;
}
```

Фактическая ширина border-box:

`200 + 20 × 2 + 2 × 2 = 244px`.

С учётом внешних отступов область по горизонтали составляет `264px`.

Важно: `margin` не является частью border-box, не окрашивается фоном элемента и может схлопываться по вертикали в определённых условиях.

# Что меняет `box-sizing: border-box`?

`box-sizing` определяет, какие области блочной модели включаются в заданные `width` и `height`.

`content-box` - значение по умолчанию. Размеры относятся только к содержимому, а `padding` и `border` увеличивают фактический размер элемента.

`border-box` - заданные размеры включают `content`, `padding` и `border`.

```
.box {
  box-sizing: border-box;
  width: 200px;
  padding: 20px;
  border: 2px solid;
}
```

Общая ширина элемента по границе будет `200px`, а ширина области содержимого - `156px`.

`margin` в расчёт не входит.

Это упрощает создание сеток и адаптивных интерфейсов, поскольку внутренние отступы не увеличивают установленную ширину.

Часто применяется глобально:

```
*,
*::before,
*::after {
  box-sizing: border-box;
}
```

При этом `border-box` не запрещает содержимому переполнять элемент и не отменяет ограничения `min-width` или `max-width`.

# Почему вертикальные margin могут схлопываться?

Margin collapsing - механизм, при котором вертикальные внешние отступы некоторых блочных элементов в обычном потоке объединяются вместо суммирования.

Например:

```
.first {
  margin-bottom: 30px;
}

.second {
  margin-top: 20px;
}
```

Расстояние между блоками обычно составит `30px`, а не `50px`.

Схлопывание возникает между:

- Соседними блоками в обычном потоке.
- Родителем и первым либо последним дочерним блоком при отсутствии разделяющих границ, отступов и некоторых других условий.
- Верхним и нижним margin одного пустого блока.

Для положительных отступов выбирается максимальный. При отрицательных учитывается сумма максимального положительного и наиболее отрицательного значений.

Margin не схлопываются:

- Между flex- и grid-элементами.
- У абсолютно позиционированных и плавающих элементов.
- Между BFC-контейнером и его дочерними элементами.

Чтобы предотвратить схлопывание margin родителя с дочерним элементом, можно создать новый BFC:

```
.container {
  display: flow-root;
}
```

Схлопывание - стандартное поведение блочной модели, а не ошибка браузера.

# Чем `display: none`, `visibility: hidden`, `opacity: 0` и `content-visibility` отличаются?

Эти свойства по-разному управляют отображением, компоновкой и доступностью элементов.

`display: none`

- Убирает элемент и его потомков из раскладки.
- Не оставляет места в документе.
- Элемент не отрисовывается и обычно отсутствует в дереве доступности.
- Не доступен для пользовательского взаимодействия.

`visibility: hidden`

- Сохраняет место элемента в раскладке.
- Скрывает его визуально и исключает из обычного взаимодействия и дерева доступности.
- Потомок может стать видимым, если ему явно установить `visibility: visible`.

`opacity: 0`

- Делает элемент полностью прозрачным.
- Сохраняет его размеры и участие в раскладке.
- Элемент может получать клики, фокус и оставаться доступным для скринридеров.
- Поддерживает плавную анимацию прозрачности.

`content-visibility` управляет обработкой содержимого:

- `visible` - обычная отрисовка.
- `hidden` - содержимое не обрабатывается для раскладки и отрисовки, но собственный блок элемента сохраняется. Скрытое содержимое недоступно для фокуса и поиска по странице.
- `auto` - браузер может пропускать раскладку и отрисовку содержимого вне видимой области, сохраняя его доступность для поиска и вспомогательных технологий.

`content-visibility: auto` применяется для оптимизации длинных страниц. Часто сочетается с `contain-intrinsic-size`, чтобы зарезервировать приблизительное место и уменьшить смещения раскладки.

# В чём различие `block`, `inline`, `inline-block`, `flex` и `grid`?

`display` определяет внешний тип отображения элемента и способ раскладки его содержимого.

`block`

- Обычно начинается с новой строки.
- При автоматической ширине занимает доступную ширину контейнера.
- Поддерживает размеры и внешние отступы.
- Дочерние элементы располагаются по правилам обычного потока.

`inline`

- Участвует в строке вместе с текстом.
- Ширина зависит от содержимого.
- Для обычных нереплейснутых inline-элементов `width` и `height` не применяются.
- Вертикальные margin не изменяют расстояние между строками.

`inline-block`

- Располагается в строке, подобно `inline`.
- Поддерживает `width`, `height`, `padding` и `margin`.
- Внутри ведёт себя как блочный контейнер.

`flex`

- Создаёт flex-контейнер.
- Организует дочерние элементы преимущественно по одной оси.
- Позволяет управлять распределением пространства, выравниванием и изменением размеров элементов.

`grid`

- Создаёт grid-контейнер.
- Позволяет управлять строками и колонками одновременно.
- Подходит для двумерных сеток и сложных макетов.

`display: flex` и `display: grid` по умолчанию создают блоковые контейнеры. Для строчных вариантов существуют `inline-flex` и `inline-grid`.

# Как работает `overflow` и какие проблемы создаёт обрезка содержимого?

`overflow` определяет, что происходит, если содержимое выходит за границы области элемента.

Основные значения:

- `visible` - содержимое может отображаться за пределами элемента. Значение по умолчанию.
- `hidden` - переполнение обрезается, полосы прокрутки скрыты, но программная прокрутка и прокрутка к фокусируемым элементам возможны.
- `clip` - обрезает содержимое и не создаёт прокручиваемый контейнер.
- `scroll` - создаёт прокручиваемый контейнер с полосами прокрутки независимо от наличия переполнения.
- `auto` - создаёт прокрутку, когда она необходима.

Для независимого управления осями существуют `overflow-x` и `overflow-y`.

Основные проблемы обрезки:

1. Выпадающие меню, tooltip и popover могут оказаться обрезанными.
2. `box-shadow`, `outline` и другие визуальные эффекты могут исчезать за границами контейнера.
3. Фокусируемые элементы могут стать визуально недоступными.
4. `overflow: hidden` и `auto` создают прокручиваемые контейнеры, что может влиять на `position: sticky`.
5. Некоторые значения `overflow` создают BFC и изменяют поведение раскладки.

Важно: `overflow: hidden` не эквивалентен `overflow: clip`. Первый допускает программную прокрутку и создаёт BFC, второй сам по себе этого не делает.

# Что такое normal flow и как вывести элемент из потока?

Normal flow - стандартный механизм размещения элементов, при котором их позиции и размеры определяются структурой документа, типами отображения и правилами форматирования.

В обычном блочном потоке блоки располагаются последовательно по вертикали, а строчные элементы участвуют в формировании строк.

Flexbox и Grid используют собственные модели раскладки, но их элементы продолжают участвовать в компоновке своих контейнеров.

Вывести элемент из обычного потока можно несколькими способами:

`position: absolute` или `fixed`

Элемент перестаёт занимать место в обычной раскладке, поэтому соседние элементы располагаются так, будто его там нет.

`float: left` или `right`

Элемент выводится из обычного потока блоков и смещается к краю контейнера. При этом текст и другие строчные элементы могут обтекать его.

Важно различать:

- `position: relative` - элемент визуально смещается, но сохраняет первоначально занимаемое место.
- `position: sticky` - сохраняет участие в потоке, хотя визуально может смещаться при прокрутке.
- `transform: translate(...)` - изменяет визуальное положение, не перестраивая окружающую раскладку.

Поэтому визуальное перемещение элемента не всегда означает выход из потока.

# Как работают `position: static`, `relative`, `absolute`, `fixed`, `sticky`?

Свойство `position` определяет модель позиционирования элемента.

`static`

Значение по умолчанию. Элемент размещается обычным способом. Свойства смещения `top`, `right`, `bottom`, `left` не влияют на его положение.

`relative`

Элемент сохраняет место в потоке, но может визуально смещаться относительно исходной позиции.

```
.element {
  position: relative;
  top: 10px;
}
```

Соседние элементы не перестраиваются из-за такого смещения.

`absolute`

Элемент удаляется из обычного потока и позиционируется относительно содержащего блока, обычно ближайшего подходящего предка с `position`, отличным от `static`.

`fixed`

Элемент удаляется из потока и обычно позиционируется относительно viewport, поэтому не перемещается при прокрутке документа. Некоторые свойства предков, например `transform`, могут изменить его содержащий блок.

`sticky`

Элемент участвует в потоке, но при прокрутке может фиксироваться относительно границ ближайшего прокручиваемого контейнера, оставаясь ограниченным своей содержащей областью.

Для работы по соответствующей оси обычно требуется указать смещение, например `top: 0`.

Важно: `sticky` может работать неожиданно, если предок имеет `overflow: hidden`, `auto` или `scroll`, поскольку это влияет на выбор прокручиваемого контейнера.

# Что является containing block для абсолютно позиционированного элемента?

Containing block - область, относительно которой рассчитываются положение и некоторые размеры элемента.

Для `position: absolute` содержащим блоком обычно становится padding-box ближайшего предка, у которого `position` отличается от `static`.

```
.parent {
  position: relative;
}

.child {
  position: absolute;
  top: 0;
  right: 0;
}
```

Здесь `.child` позиционируется относительно `.parent`.

Но содержащий блок могут создавать и другие свойства предков, например:

- `transform` со значением, отличным от `none`.
- `filter` или `perspective`.
- `contain: layout` или `contain: paint`.
- `content-visibility: auto`.
- `will-change` для определённых свойств, способных создавать containing block.

Если подходящего предка нет, используется initial containing block, размеры которого в обычной веб-странице связаны с viewport.

Отдельная особенность есть у позиционированных строчных предков: содержащий блок определяется по их фрагментам, а не по обычной прямоугольной модели блочного контейнера.

# Как создаётся stacking context и почему `z-index` иногда не действует?

Stacking context - независимый контекст наложения, внутри которого определяется порядок отображения элементов по оси Z.

Его создают, например:

- Корневой элемент `<html>`.
- `position: relative` или `absolute` с `z-index`, отличным от `auto`.
- `position: fixed` или `sticky`.
- Flex- и grid-элементы с `z-index`, отличным от `auto`.
- `opacity` меньше `1`.
- `transform`, `filter`, `perspective` и некоторые другие визуальные свойства.
- `isolation: isolate`.
- `contain: layout` или `paint`.
- `container-type: inline-size` или `size`.

Главная особенность: вложенный stacking context рассматривается как единое целое внутри родительского контекста.

Например, если один родительский контекст имеет `z-index: 1`, а другой `z-index: 2`, дочерний элемент первого контекста с `z-index: 9999` не сможет оказаться поверх второго родительского контекста только благодаря своему `z-index`.

Причины, по которым `z-index` может не давать ожидаемого результата:

1. Элемент не позиционирован и не является flex/grid-элементом, для которого применим `z-index`.
2. Элемент находится внутри stacking context с меньшим приоритетом.
3. Наложение ограничено другим контекстом или содержимое обрезается через `overflow`.
4. Другой элемент находится в браузерном top layer, например модальное `<dialog>` или открытый popover. Обычный `z-index` не позволяет перекрыть этот слой.

Для диагностики важно изучать всю иерархию stacking context, а не только значения `z-index` отдельных элементов.

# Чем `outline` отличается от `border`?

Оба свойства создают визуальную обводку, но работают по-разному.

`border`:

- Является частью блочной модели.
- Влияет на размеры элемента в зависимости от `box-sizing`.
- Может изменять расположение соседних элементов.
- Поддерживает разные стили для каждой стороны.

`outline`:

- Рисуется вокруг элемента, обычно снаружи границы.
- Не занимает места в раскладке и не изменяет размеры элемента.
- Может накладываться на соседние элементы.
- Поддерживает `outline-offset` для изменения расстояния от обводки до элемента.

Главная область применения `outline` - индикация фокуса.

```
button:focus-visible {
  outline: 2px solid blue;
  outline-offset: 3px;
}
```

Важно не удалять `outline` у интерактивных элементов без равноценной замены: это ухудшает доступность интерфейса при управлении с клавиатуры.

# Как работают `min-width`, `max-width`, `min-height` и `max-height`?

Эти свойства ограничивают допустимые размеры элемента.

- `min-width` - минимальная ширина.
- `max-width` - максимальная ширина.
- `min-height` - минимальная высота.
- `max-height` - максимальная высота.

Например:

```
.container {
  width: 100%;
  max-width: 1200px;
  min-height: 300px;
}
```

Контейнер занимает доступную ширину, но не превышает `1200px`, а его высота не становится меньше `300px`.

При конфликте ограничений `min-width` имеет приоритет над `max-width`, аналогично для высоты.

Важная особенность Flexbox и Grid: у flex- и grid-элементов автоматический минимальный размер часто зависит от содержимого. Из-за этого элемент может не сжиматься и создавать переполнение.

Типичное решение:

```
.flex-child {
  min-width: 0;
}
```

Это позволяет элементу сжиматься меньше минимальной ширины его содержимого.

Также важно учитывать, что процентная высота может не рассчитываться ожидаемым образом, если размер содержащего блока по соответствующей оси не определён.

# Что делают `calc()`, `min()`, `max()` и `clamp()`?

Эти CSS-функции позволяют вычислять значения свойств и создавать адаптивные размеры.

`calc()` выполняет математические операции.

```
width: calc(100% - 32px);
```

Позволяет комбинировать совместимые величины, включая проценты и абсолютные единицы.

`min()` выбирает минимальное из переданных значений.

```
width: min(100%, 800px);
```

Ширина не превысит `800px` и не станет больше доступных `100%`.

`max()` выбирает максимальное значение.

```
padding: max(16px, 2vw);
```

Отступ не будет меньше `16px`.

`clamp()` ограничивает значение заданным диапазоном.

```
font-size: clamp(16px, 2vw, 24px);
```

Значение будет масштабироваться относительно `2vw`, но не станет меньше `16px` или больше `24px`.

Концептуально:

`clamp(MIN, VALUE, MAX)` ≈ `max(MIN, min(VALUE, MAX))`.

Эти функции полезны для адаптивной типографики и размеров без большого количества медиазапросов.

# Когда использовать `em`, `rem`, `%`, `vw`, `vh`, `dvh`, `svh` и `lvh`?

Выбор единицы зависит от того, относительно чего должен масштабироваться размер.

`em` - относительно размера шрифта элемента. Для самого `font-size` значение рассчитывается относительно размера шрифта родителя.

Подходит для внутренних отступов и размеров, которые должны масштабироваться вместе с текстом.

`rem` - относительно размера шрифта корневого элемента `<html>`.

Подходит для глобальной системы размеров, отступов и типографики.

`%` - относительно определённой характеристики содержащего блока или другого базового значения, в зависимости от свойства.

Например, `width: 50%` обычно означает половину ширины содержащего блока.

`vw` - 1% ширины viewport.

Подходит для размеров, зависящих от ширины окна браузера.

`vh` - 1% высоты viewport. В современных браузерах обычно соответствует большой высоте viewport (`lvh`), поэтому на мобильных устройствах элементы высотой `100vh` могут выходить за видимую область при открытых панелях браузера.

`svh` - 1% малого viewport, то есть высоты при максимально раскрытых динамических панелях браузера.

Полезен, когда содержимое должно помещаться на экран даже при видимых панелях браузера.

`lvh` - 1% большого viewport, то есть высоты при максимально скрытых панелях браузера.

`dvh` - 1% динамической высоты viewport, которая изменяется при появлении и скрытии браузерных панелей.

Подходит для мобильных полноэкранных интерфейсов, но изменение высоты может вызывать пересчёт раскладки.

Практически:

- `rem` - глобальная шкала размеров.
- `em` - размеры относительно текста компонента.
- `%` - зависимость от контейнера.
- `vw` - зависимость от ширины экрана.
- `svh` - гарантированное размещение внутри минимальной видимой высоты.
- `dvh` - адаптация к текущей видимой высоте.

# Как работают CSS custom properties и чем они отличаются от переменных SCSS?

CSS custom properties - пользовательские CSS-свойства, которые участвуют в каскаде и могут использоваться через `var()`.

```
:root {
  --primary-color: blue;
}

.button {
  color: var(--primary-color);
}
```

По умолчанию custom properties наследуются, поэтому их удобно переопределять на уровне компонента или темы:

```
.dark-theme {
  --primary-color: white;
}
```

Основные особенности:

- Значения определяются браузером с учётом каскада.
- Их можно изменять во время выполнения через CSS или JavaScript.
- Они поддерживают наследование.
- Можно указать запасное значение: `var(--color, black)`.
- С помощью `@property` можно зарегистрировать тип, начальное значение и поведение наследования.

SCSS-переменные (`$color`) существуют только во время компиляции.

```
$primary-color: blue;

.button {
  color: $primary-color;
}
```

После компиляции переменная заменяется конкретным значением и не существует как переменная в браузере.

Ключевое различие: SCSS-переменные обрабатываются на этапе сборки, а CSS custom properties - в браузере и могут динамически изменяться.

Важно: если подстановка `var()` даёт некорректное значение свойства, браузер может применить начальное или наследуемое значение вместо предыдущей декларации. Резервное значение `var()` не исправляет любую ошибку типа данных.

# Что такое логические CSS-свойства (`margin-inline`, `padding-block`)?

Логические CSS-свойства задают отступы, границы и размеры относительно направления письма, а не фиксированных физических сторон элемента.

Вместо `left`, `right`, `top` и `bottom` используются две логические оси:

- Inline - направление движения текста внутри строки.
- Block - направление расположения строк и блоков.

Например:

```
.card {
  margin-inline: 20px;
  padding-block: 16px;
}
```

Для горизонтального текста это соответствует горизонтальным margin и вертикальным padding.

Свойства `margin-inline-start` и `margin-inline-end` автоматически учитывают направление текста.

При `direction: ltr`:

- `inline-start` - слева.
- `inline-end` - справа.

При `direction: rtl` значения меняются местами.

Однако соответствие логических и физических сторон также зависит от `writing-mode`.

Основное преимущество - возможность создавать интерфейсы, адаптирующиеся к языкам с разными направлениями письма без дублирования CSS.

# Чем `object-fit` отличается от `background-size`?

Оба свойства управляют масштабированием визуального содержимого, но применяются к разным объектам.

`object-fit` определяет, как содержимое заменяемого элемента, например `<img>` или `<video>`, вписывается в его собственный прямоугольник.

```
img {
  width: 300px;
  height: 200px;
  object-fit: cover;
}
```

Основные значения:

- `fill` - растягивает содержимое до размеров блока, возможно с искажением пропорций.
- `contain` - полностью помещает содержимое с сохранением пропорций.
- `cover` - заполняет область с сохранением пропорций, обрезая лишнее.
- `none` - не масштабирует содержимое.
- `scale-down` - выбирает меньший результат между `none` и `contain`.

Для управления положением используется `object-position`.

`background-size` управляет размером фонового изображения, установленного через `background-image`.

```
.card {
  background-image: url("image.jpg");
  background-size: cover;
  background-position: center;
}
```

Ключевые различия:

- `object-fit` применяется к содержимому заменяемого HTML-элемента.
- `background-size` применяется к CSS-фону.
- `<img>` участвует в семантике документа, может иметь `alt` и использоваться для содержательных изображений.
- CSS-фон обычно подходит для декоративных изображений.

`object-fit` не изменяет размеры самого элемента, а определяет, как изображение располагается внутри его области.

# Что такое BFC и какие задачи решает новый контекст форматирования?

BFC (Block Formatting Context) - независимый контекст блочного форматирования, который определяет размещение блоков и взаимодействие с плавающими элементами.

BFC позволяет изолировать некоторые аспекты раскладки от окружающего содержимого.

Он создаётся, например, при:

- `display: flow-root`.
- `overflow: hidden`, `auto` или `scroll`.
- `float`, отличном от `none`.
- `position: absolute` или `fixed`.
- Использовании `inline-block`.

Flex- и grid-контейнеры также создают независимые контексты форматирования для содержимого, но используют собственные модели раскладки, а не обычный BFC для своих элементов.

Основные задачи BFC:

1. Предотвращение схлопывания margin между контейнером и его дочерними блоками.
2. Учет внутренних float-элементов при определении высоты контейнера.
3. Предотвращение перекрытия внешними float-элементами области блока, формирующего BFC.

Пример:

```
.container {
  display: flow-root;
}
```

Это позволяет контейнеру корректно охватывать плавающие дочерние элементы без дополнительных очищающих элементов.

`display: flow-root` предпочтительнее `overflow: hidden`, если задача состоит именно в создании BFC, поскольку он не обрезает выступающее содержимое.

# Для чего нужны `contain`, `content-visibility` и `will-change`?

Все три свойства могут использоваться для оптимизации браузерного рендеринга, но решают разные задачи.

`contain` ограничивает влияние элемента и его содержимого на окружающую страницу.

Основные варианты:

- `contain: size` - позволяет рассчитывать размеры контейнера без учёта размеров потомков.
- `contain: layout` - изолирует некоторые зависимости раскладки.
- `contain: paint` - ограничивает отрисовку содержимого границами контейнера.
- `contain: style` - ограничивает отдельные стилистические эффекты, например распространение некоторых счётчиков.

Существуют комбинированные значения `content` и `strict`.

Ограничения могут менять поведение размеров, позиционирования и обрезки, поэтому применять их без необходимости не следует.

`content-visibility` позволяет браузеру пропускать работу по раскладке и отрисовке содержимого.

```
.section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px;
}
```

Для длинных страниц это может значительно уменьшить стоимость первоначального рендеринга. `contain-intrinsic-size` помогает зарезервировать место под содержимое, которое пока не было обработано.

`will-change` сообщает браузеру, что определённое свойство скоро изменится.

```
.element {
  will-change: transform;
}
```

Браузер может заранее подготовить оптимизации, например отдельный композиционный слой.

Однако это не гарантирует ускорения: постоянное использование `will-change` может увеличивать расход памяти и количество слоёв.

Различие: `contain` ограничивает зависимости раскладки и отрисовки, `content-visibility` позволяет пропускать обработку содержимого, а `will-change` предупреждает о предстоящих изменениях.

# Что такое FOUC и как снизить риск его появления?

FOUC (Flash of Unstyled Content) - кратковременное отображение HTML без необходимых CSS-стилей или с неполным оформлением.

Обычно возникает, когда браузер успевает показать содержимое до применения стилей.

Причины:

- Поздняя или асинхронная загрузка CSS.
- Динамическое добавление стилей через JavaScript.
- Использование `@import` с дополнительными сетевыми запросами.
- Ошибки при SSR, когда сервер отправляет HTML без соответствующего CSS.
- Поздняя инициализация темы или CSS-in-JS.

Способы предотвращения:

1. Подключать критически важные таблицы стилей через `<link rel="stylesheet">` в `<head>`.
2. Встраивать небольшой critical CSS непосредственно в HTML, когда это оправданно.
3. Обеспечивать доставку необходимых стилей вместе с HTML при SSR.
4. Использовать предварительную загрузку необходимых ресурсов, когда это действительно уменьшает задержку.
5. Согласовывать серверное и клиентское определение темы, чтобы избежать визуального переключения после гидратации.
6. Избегать ситуации, когда основное оформление зависит от выполнения JavaScript.

Стандартные CSS-файлы, подключённые в `<head>`, обычно блокируют первоначальный рендеринг именно для предотвращения отображения страницы до применения необходимых стилей.

# Какие особенности есть у CSS-in-JS при SSR?

При SSR (Server-Side Rendering) сервер формирует HTML до выполнения клиентского JavaScript.

Если используются CSS-in-JS-библиотеки, генерирующие стили во время выполнения, необходимо обеспечить наличие нужного CSS уже в серверном ответе.

Основные особенности:

1\. Сбор и отправка CSS

Стили компонентов должны быть собраны при серверном рендеринге и переданы вместе с HTML, например через `<style>` или отдельные таблицы стилей.

Иначе пользователь может увидеть FOUC.

2\. Согласованность серверного и клиентского рендеринга

Сервер и клиент должны формировать совместимые классы и стили, чтобы при гидратации React не возникало расхождений.

Проблемы возможны при зависимости стилей от случайных значений, времени, браузерного окружения или различающихся начальных состояний.

3\. Изоляция запросов

Состояние сборщика стилей и кешей, содержащих данные конкретного рендера, необходимо правильно изолировать между запросами, чтобы избежать утечек стилей между пользователями.

4\. Streaming SSR

При потоковом рендеринге стили могут потребоваться до того, как сервер сформирует весь HTML.

Поддержка зависит от библиотеки, её версии и интеграции с фреймворком. Например, Emotion и styled-components используют разные механизмы серверной вставки и сбора CSS.

5\. React Server Components

Возможность использования CSS-in-JS внутри Server Components зависит от библиотеки и версии. Некоторые подходы требуют клиентских компонентов или специальных интеграций, а другие поддерживают серверную генерацию стилей.

6\. Производительность

Runtime CSS-in-JS может увеличивать стоимость выполнения JavaScript и вставки стилей. Статическая генерация CSS на этапе сборки обычно уменьшает эти расходы.

Поэтому при SSR важно учитывать не только синтаксис библиотеки, но и её механизм генерации CSS, поддержку потокового рендеринга, кеширование и гидратацию.

# Когда Tailwind упрощает поддержку, а когда усложняет её?

Tailwind CSS - utility-first CSS-фреймворк, в котором оформление строится из небольших классов, отвечающих за отдельные свойства.

Например:

```
<button class="rounded-lg bg-blue-600 px-4 py-2 text-white">
  Submit
</button>
```

Tailwind упрощает поддержку, когда:

- В проекте используется единая дизайн-система.
- Команда придерживается согласованных utility-классов и токенов.
- Необходимо быстро создавать и изменять адаптивные интерфейсы.
- Важно избегать конфликтов между глобальными CSS-селекторами.
- Оформление должно находиться рядом с разметкой компонента.

Tailwind генерирует CSS на этапе сборки, поэтому использование utility-классов обычно не требует runtime CSS-in-JS.

Tailwind усложняет поддержку, когда:

- JSX перегружен длинными наборами классов.
- Одинаковые наборы классов дублируются в разных компонентах.
- Сложные состояния и условия приводят к громоздкой логике `className`.
- Требуется много нестандартных значений и сложных селекторов.
- Стилизация чужой разметки или больших объёмов HTML без контроля над классами становится неудобной.

Отдельная особенность: Tailwind определяет используемые классы по исходному коду во время сборки. Динамически составленные имена вроде `bg-${color}-500` могут не распознаваться.

Поэтому динамические варианты обычно задают через явные наборы полных классов либо CSS-переменные.

Ключевой критерий: Tailwind удобен, когда интерфейс хорошо выражается через повторно используемые utility-классы и дизайн-токены. При сложных динамических стилях и сильно разрастающейся разметке его преимущества могут уменьшаться.

# Как сравнить CSS Modules, styled-components, Emotion и vanilla-extract?

Все четыре подхода решают задачи организации CSS, изоляции стилей компонентов и повторного использования оформления, но различаются способом генерации CSS и стоимостью выполнения.

CSS Modules

Обычные CSS-файлы с локальной областью видимости классов.

```
/* Button.module.css */
.button {
  color: blue;
}
```

```
import styles from "./Button.module.css";

<button className={styles.button}>Click</button>
```

Преимущества:

- Стандартный CSS без дополнительной runtime-генерации стилей.
- Изоляция классов.
- Небольшие накладные расходы.
- Хорошая совместимость с SSR.

Недостатки:

- Динамические значения обычно требуют классов, inline styles или CSS-переменных.
- Нет полноценной типизации CSS по умолчанию.

styled-components

CSS-in-JS-библиотека, позволяющая создавать стилизованные React-компоненты.

```
const Button = styled.button`
  color: ${({ $active }) => ($active ? "blue" : "gray")};
`;
```

Преимущества:

- Тесная интеграция с React.
- Динамические стили через props.
- Темизация и композиция компонентов.
- Автоматическая генерация классов.

Недостатки:

- Дополнительная runtime-работа.
- Необходимость учитывать серверную генерацию и гидратацию стилей.
- Дополнительные зависимости и ограничения интеграции.

Emotion

CSS-in-JS-библиотека, предоставляющая несколько способов описания стилей, включая `css` и `styled`.

```
const buttonStyle = css`
  color: blue;
`;
```

По возможностям близка к styled-components, но предоставляет более гибкий API для композиции и применения стилей.

Преимущества:

- Динамическая стилизация.
- Возможность использовать объектный и шаблонный синтаксис.
- Темизация и композиция стилей.

Недостатки:

- Runtime-накладные расходы.
- Особенности SSR и кеширования.
- Некоторые серверные способы вставки CSS могут влиять на структурные селекторы вроде `:nth-child()`.

vanilla-extract

Подход CSS-in-TypeScript, при котором стили описываются на TypeScript и преобразуются в статический CSS во время сборки.

```
export const button = style({
  color: "blue",
  padding: "12px",
});
```

Преимущества:

- Статическая генерация CSS без обязательной runtime-вставки стилей.
- Типизация свойств.
- Локальные классы.
- Поддержка тем и дизайн-токенов через CSS-переменные.
- Хорошая совместимость с SSR.

Недостатки:

- Требует интеграции со сборщиком.
- Произвольная генерация новых CSS-правил из runtime-значений ограничена.
- Для динамических значений обычно используются заранее подготовленные варианты или CSS-переменные.

Итоговое сравнение:

| Критерий                  | CSS Modules                   | styled-components           | Emotion                     | vanilla-extract                 |
|---------------------------|-------------------------------|-----------------------------|-----------------------------|---------------------------------|
| Синтаксис                 | CSS                           | JS/TS + CSS                 | JS/TS + CSS                 | JS/TS                           |
| Изоляция классов          | Да                            | Да                          | Да                          | Да                              |
| Статическая генерация CSS | Да                            | Обычно нет                  | Обычно нет                  | Да                              |
| Runtime-генерация стилей  | Нет                           | Да                          | Да                          | Нет для статических стилей      |
| Динамические стили        | Через классы и CSS-переменные | Через props                 | Через props и JS            | Через варианты и CSS-переменные |
| Типизация стилей          | Дополнительно                 | Частичная, через TypeScript | Частичная, через TypeScript | Да                              |
| SSR                       | Простой                       | Требует учёта интеграции    | Зависит от способа SSR      | Простой                         |

Практический выбор:

- CSS Modules - когда нужны простота, изоляция и обычный CSS.
- styled-components - когда важна компонентная модель стилизации и динамические стили через React props.
- Emotion - когда нужен гибкий CSS-in-JS API с возможностью комбинировать разные способы описания стилей.
- vanilla-extract - когда нужны типизированные стили и дизайн-токены без обязательных runtime-расходов на генерацию CSS.

Для большинства обычных интерфейсов CSS Modules и vanilla-extract обеспечивают более предсказуемую стоимость выполнения, поскольку основной CSS создаётся во время сборки. Runtime CSS-in-JS оправдан, когда его динамические возможности действительно необходимы.
