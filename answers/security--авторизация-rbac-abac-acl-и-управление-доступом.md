# Как PEP, PDP и источники атрибутов разделяют исполнение authorization policy?

**PEP** перехватывает действие и исполняет решение: разрешает, ограничивает или отклоняет его. **PDP** вычисляет решение по policy и контексту. Источники атрибутов предоставляют проверенные сведения о subject, resource, tenant и окружении; policy administration управляет самими правилами.

Центральный PDP не защищает endpoint, который обошёл PEP. Проверки нужны и в асинхронных путях. Неопределённый результат или ошибка вычисления не должны автоматически давать доступ; допустимое использование кэша задаётся отдельной политикой свежести. Логи связывают решение с policy version, не раскрывая secrets.

# Как проектировать RBAC permissions, role hierarchy и separation of duties без role explosion?

Сначала определяют permissions как действия над видами ресурсов, затем объединяют их в роли по рабочим обязанностям. Пользователь получает role assignment в определённом scope, например tenant. Иерархия наследования должна быть явной и не создавать неожиданных административных полномочий.

**Separation of duties** запрещает опасные сочетания, например самостоятельное создание и окончательное подтверждение одной выплаты. Если каждый проект и статус требуют новой роли, модель перегружена: часть условий удобнее выразить через attributes или relationships. Регулярно проверяют неиспользуемые permissions и реальные границы каждой роли.

# Как ABAC использует атрибуты субъекта, ресурса, действия и окружения из доверенных источников?

В **ABAC** решение вычисляется из атрибутов subject, resource, action и при необходимости environment. Например, сотрудник может читать документ своего отдела при достаточном уровне допуска и разрешённом состоянии документа.

Источник каждого атрибута должен быть доверенным и достаточно свежим. `department` или `tenant_id`, присланные клиентом, не становятся достоверными от наличия authentication. Задают поведение для отсутствующих атрибутов, конфликтующих правил и изменения policy. Тесты проверяют не только успешные комбинации, но и неполный, устаревший или подменённый контекст. [NIST SP 800-162](https://csrc.nist.gov/pubs/sp/800/162/upd2/final).

# Когда ACL и relationship-based access control удобнее назначения глобальных ролей?

**ACL** привязывает разрешения к конкретному ресурсу: например, документ доступен определённым пользователям и группам. Relationship-based access control выводит право из отношений: участник команды, владеющей папкой, получает доступ к её документам по заданным правилам.

Это удобно для совместной работы и делегирования, где глобальная роль «редактор» слишком широка. Нужно определить наследование, исключения, циклы и скорость применения отзыва. Большой граф отношений требует проверки consistency и стоимости поиска. Такие модели можно сочетать с RBAC и contextual conditions. [Google: Zanzibar](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/).

# Как tenant scoping и object-level checks защищают списки, batch operations и экспорты?

Tenant context устанавливают из проверенной identity и подтверждённого membership. Client-supplied tenant ID может выбирать контекст, но не доказывает право работать в нём. Scope включают в query и проверку объекта до чтения или изменения данных.

List, search, counts, batch и export должны использовать тот же принцип. Фильтрация после unrestricted query может утечь через pagination, totals или побочные эффекты. Worker получает проверенный контекст, а cache keys и storage paths учитывают tenant. Row-level security может усилить защиту, если connection context задаётся и очищается корректно. [OWASP: Multi-Tenant Security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html).

# Как field-level authorization ограничивает чтение и изменение свойств ресурса?

Право изменять объект не означает право менять любое его поле. Сервер строит allowlist входных полей по действию и policy, а sensitive transitions, например изменение owner или approval status, выделяет в проверяемые сценарии.

На чтении response projection также зависит от прав: удаление поля только из UI не защищает API. Защита должна охватывать вложенные объекты, exports и альтернативные serializers. Если поле отсутствует во входе, это отличается от явного `null`; PATCH не должен обходить правила через неожиданный merge. Проверки выполняются до применения изменения.

# Как передавать delegated identity между сервисами без confused deputy?

Downstream service должен понимать, кто вызывает его технически и от чьего имени совершается действие. Service identity и delegated user identity выполняют разные роли. Их передают через проверяемые credentials или защищённый контекст с ограниченными audience, scope и сроком.

**Confused deputy** возникает, когда привилегированный сервис использует свои права для недопустимой цели вызывающего. Поэтому он проверяет связь user, action и resource, а не только факт доверия к upstream service. Обычный пользовательский header с subject не является удостоверением. В фоновых задачах отдельно определяют необходимость повторной проверки текущих прав.

# Как кэшировать authorization decisions с учётом изменения прав и отзыва доступа?

Ключ кэша учитывает subject, action, resource, tenant и значимые версии policy или membership. Иначе решение, принятое в одном контексте, может быть использовано в другом. TTL выбирают по допустимой задержке применения изменения прав, а не только по производительности.

Для срочного отзыва используют invalidation, versioning или проверку актуального состояния на критичной операции. Отрицательные решения тоже устаревают после выдачи права. При отказе PDP кэш используют только в рамках заранее заданной модели риска и свежести. Кэшированный allow без границы срока создаёт длительное окно доступа.

# Как TOCTOU между проверкой доступа и изменением данных влияет на авторизацию?

При **TOCTOU** состояние меняется между проверкой и действием: после подтверждения доступа меняется owner, membership или статус ресурса. Две корректные по отдельности операции могут вместе нарушить policy.

По возможности проверку ресурса и mutation объединяют условным запросом, version check либо подходящими locks и isolation. Если authorization state хранится отдельно, простая DB transaction не делает его автоматически согласованным с данными. Определяют точку применения отзыва и допустимое окно для уже начатой работы. Критичные переходы проверяют конкурентными сценариями. [MITRE CWE-367](https://cwe.mitre.org/data/definitions/367.html).

# Как построить матрицу authorization tests для ролей, tenants и способов доступа?

Строят cases по subject, role, tenant, ownership, resource state и action. Для каждой разрешённой комбинации проверяют соседние запреты: чужой объект, другую организацию, sensitive field и administrative function. Ожидаемые решения выводят из policy, а не копируют из реализации.

Те же правила проверяют через REST, GraphQL, batch, export и background paths, если они доступны. Добавляют tests после отзыва membership, при отсутствии контекста и ошибке PDP. Проверяют отсутствие побочного изменения при отказе, а не только HTTP status. [OWASP: Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html).
