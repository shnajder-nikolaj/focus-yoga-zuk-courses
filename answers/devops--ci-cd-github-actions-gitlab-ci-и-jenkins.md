# Как спроектировать pipeline сервиса от проверки commit до продвижения релизного артефакта?

Pipeline начинают с быстрых проверок входного commit: формат, статический анализ, типы и unit tests. Затем выполняют сборку, integration и contract tests, проверки безопасности, публикацию версионированного артефакта и деплой с проверкой здоровья.

Дешёвые независимые проверки запускают параллельно, а дорогие этапы зависят от их результата. Production получает конкретный артефакт, связанный с commit, а не новую случайную пересборку. У каждого этапа определяют входы, выходы, timeout и критерий успеха. Секреты и права деплоя доступны только задачам, которым они нужны.

# Как workflows, jobs, steps, stages и agents соотносятся в GitHub Actions, GitLab CI и Jenkins?

В **GitHub Actions** workflow описывает событие запуска и jobs; job выполняется на runner и состоит из steps. В **GitLab CI** pipeline содержит jobs на runners, `stages` задают обычный порядок групп, а `needs` позволяет описать более точные зависимости.

В **Jenkins** Pipeline задаётся, например, в `Jenkinsfile`; stages организуют работу, steps выполняют действия, а agents выделяют среду исполнения. Эти понятия не совпадают один-к-одному: stage Jenkins не эквивалентен GitLab stage по всем правилам планирования. При переносе проверяют условия запуска, передачу файлов, секреты и семантику отказа. [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/).

# Как DAG зависимостей и параллельные jobs сокращают критический путь pipeline?

**DAG** описывает реальные зависимости задач вместо общего барьера между крупными этапами. Если deployment сервиса A зависит только от его тестов, сборка несвязанного сервиса B не обязана его задерживать.

Общую длительность определяет критический путь вместе с ожиданием свободных runners. Matrix jobs ускоряют проверки по версиям и платформам, но увеличивают стоимость и нагрузку на общие базы и registry. Зависимости передачи artifacts указывают явно. Параллелизм безопасен только при разделении временных ресурсов, иначе сокращение времени оборачивается гонками и flaky failures.

# Как разделить cache, job artifacts и release registry в CI/CD?

**Cache** ускоряет повторное получение зависимостей; pipeline должен корректно работать и без него. **Job artifacts** передают результаты конкретной job другим jobs и сохраняют отчёты с заданным сроком хранения. **Release registry** хранит опубликованные версии пакетов или образов для дальнейшего использования и продвижения.

Ключ кеша учитывает lockfile, ОС и toolchain. Кеш из недоверенного запуска не должен незаметно попадать в доверенную сборку. Для релиза используют конкретную версию или digest с контролем доступа; наличие файла в кеше не подтверждает его происхождение. [GitLab: cache и artifacts](https://docs.gitlab.com/ci/caching/), [назначение artifacts](https://docs.gitlab.com/ci/jobs/job_artifacts/).

# Как обеспечить воспроизводимую сборку и продвижение одного digest между окружениями?

Фиксируют исходный commit, зависимости и toolchain, контролируют внешние входы сборки. **Reproducible build** означает возможность независимо получить одинаковый результат при определённых входах; само наличие lockfile этого не доказывает.

Для продвижения релиза собирают артефакт один раз и разворачивают его digest в test, staging и production. Конфигурацию окружений передают отдельно. Подвижный tag вроде `latest` не является устойчивой идентичностью. Для multi-platform image различают digest manifest index и конкретного платформенного образа, чтобы было понятно, что именно проверили и запустили.

# Как изолировать runners и agents для доверенного кода, внешних pull requests и production deploy?

Runner, исполняющий pull request, фактически запускает чужой код, включая build scripts зависимостей. Его изолируют от production-сети, секретов и привилегированных credentials; предпочтительны временные среды без сохранённого состояния между заданиями разных уровней доверия.

Отдельно защищают cache, artifacts и доступ к Docker socket: контейнер сам по себе не создаёт достаточную границу. В GitHub Actions особенно внимательно проверяют `pull_request_target` и `workflow_run`: привилегированный workflow не должен checkout и исполнять непроверенный код из PR. Логи с замаскированными значениями не предотвращают кражу секрета самим процессом. [Безопасное использование Actions](https://docs.github.com/en/actions/reference/security/secure-use).

# Как OIDC и короткоживущие credentials ограничивают доступ CI/CD к облаку?

CI job получает подписанный **OIDC token** с идентичностью запуска и обменивает его у облачного провайдера на короткоживущие права. В CI больше не нужен постоянно действующий облачный ключ.

Trust policy проверяет issuer, audience и claims, ограничивающие repository, workflow, branch или environment; разрешение одного лишь issuer слишком широко. Облачной роли дают минимальные права и TTL. В GitHub Actions `id-token: write` разрешает запрос OIDC token, но само по себе не даёт права изменять облачные ресурсы. [OIDC reference](https://docs.github.com/en/actions/reference/security/oidc).

# Как reusable workflows, GitLab includes и Jenkins Shared Libraries уменьшают дублирование pipeline?

Общую логику оформляют в версионируемый компонент с явными входами и выходами: reusable workflow в GitHub Actions, подключаемую конфигурацию через `include` в GitLab или Shared Library в Jenkins. Проект задаёт параметры, а библиотека поддерживает повторяемый процесс.

Зависимость фиксируют на проверенной версии или commit и обновляют управляемо. Слишком универсальная библиотека со множеством скрытых условий затрудняет диагностику. Документируют требуемые secrets, permissions и артефакты; тестируют изменения общей логики до массового подключения. Общая библиотека выполняемого кода сама становится частью supply chain.

# Как исключить одновременный деплой и продвижение устаревшего pipeline в production?

Развёртывания сериализуют по целевому окружению: используют concurrency groups, resource groups или подходящую блокировку. При этом проверяют **актуальность релиза**: очередь может содержать старый pipeline, который завершился позже нового.

Перед переключением сравнивают желаемую версию с уже развернутой и политикой продвижения, а запись deployment state защищают от гонки. Отмена старой job не отменяет уже отправленный внешний запрос. Поэтому деплой делают идемпотентным и учитывают его фактическое состояние. Один mutex предотвращает одновременность, но не гарантирует правильный порядок версий.

# Как выстроить approval gates и права доступа для критичных окружений?

Для критичных окружений отделяют право менять код от права одобрять и выполнять deployment. Ограничивают branches, identities и workflows, которые могут использовать production credentials; перед одобрением показывают commit, digest, результаты проверок и ожидаемые изменения.

Gate должен защищаться правилами платформы, а не только условием в редактируемом автором job script. Для ручного одобрения задают ответственного и порядок действий при инциденте. Наличие и точные возможности protected environments и approvals зависят от платформы, редакции и тарифа; их проверяют в используемой установке.

# Когда повторять упавшую job, а когда retry скрывает ошибку или повторяет побочный эффект?

Retry подходит для подтверждённого временного сбоя: сетевой ошибки загрузки или потери runner. Его ограничивают числом попыток, общим deadline и backoff. Ошибку теста, компиляции или неверной конфигурации повтор обычно не исправляет.

Перед retry job с внешним эффектом выясняют, успело ли действие выполниться: timeout публикации или деплоя означает неизвестный исход. Нужны idempotency key, проверка существующего результата или безопасное продолжение. Flaky test учитывают отдельно и исправляют причину; автоматический повтор без учёта первой ошибки искажает надёжность pipeline.

# Как измерять длительность, надёжность и стоимость pipeline и находить источник flaky failures?

Измеряют время ожидания runner и исполнения отдельно, длительность критического пути, долю успешных первых попыток, cache hit rate, стоимость compute и частоту повторов. Pipeline с быстрыми jobs, но длинной очередью требует другого решения, чем медленная сборка.

Для flaky failures сохраняют commit, окружение, seed тестов, логи и распределение ошибок по тестам и runners. Сравнивают успех первой попытки с успехом после retry. Улучшение подтверждают данными за несколько типичных запусков; сокращение времени ценой пропущенных проверок оценивают вместе с частотой дефектов после деплоя.
