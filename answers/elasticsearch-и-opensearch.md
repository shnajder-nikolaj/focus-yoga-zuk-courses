# Как Elasticsearch и OpenSearch используют Lucene и чем поисковый индекс отличается от основной БД?

Elasticsearch и OpenSearch предоставляют распределённый поиск и аналитику поверх **Lucene**: документы индексируются по mappings, разбиваются на shards и доступны через query API. Они имеют общую историю, но современные версии развиваются независимо и не обязаны быть взаимозаменяемыми.

Поисковый индекс часто строят как производное представление основной БД: допускают задержку обновления и предусматривают reindex. Эти системы умеют сохранять документы, но не предоставляют автоматически те же многозаписные транзакционные гарантии, что relational database. Источник истины и механизм восстановления индекса определяют явно.

# Как inverted index, analyzer и tokenization обеспечивают полнотекстовый поиск?

**Inverted index** сопоставляет terms со списками документов и дополнительной информацией, например позициями. Вместо просмотра каждого полного текста поиск быстро находит документы, содержащие нужные terms.

**Analyzer** преобразует текст через character filters, tokenizer и token filters: например, разбивает предложение на слова, нормализует регистр и применяет stemming. Анализ при индексации и поиске должен быть совместим по смыслу. Слишком агрессивная нормализация или неверный язык меняют recall и precision. Проверяют реальные tokens через analyze API на примерах пользовательских запросов.

# Чем text, keyword, object и nested различаются при проектировании mapping?

`text` предназначен для анализируемого текста; `keyword` — для точных значений, сортировки и обычных term aggregations. Одно строковое поле можно индексировать несколькими способами через multi-fields.

`object` структурирует вложенные свойства, но массив объектов обычно разворачивается без сохранения независимости каждой пары полей. `nested` индексирует элементы так, чтобы запрос проверял связанные поля внутри одного элемента, ценой дополнительных внутренних документов и запросов. Например, имя одного автора не должно ошибочно сочетаться с возрастом другого. Mapping проектируют до массовой загрузки, ограничивая dynamic field explosion. [Nested OpenSearch](https://docs.opensearch.org/latest/mappings/supported-field-types/nested/).

# Как primary shards и replica shards распределяют данные и обеспечивают отказоустойчивость?

**Primary shard** содержит одну partition индекса, **replica shard** — её дополнительную копию. Запись координирует primary, а replicas участвуют в сохранении данных и могут обслуживать поиск. При отказе подходящую replica повышают до primary по правилам системы.

Реплики размещают на разных nodes и при необходимости в разных zones. Больше shards не означает автоматически выше throughput: у каждого есть overhead, а distributed search объединяет результаты. Число primary shards выбирают по объёму, нагрузке и возможностям последующего split или reindex конкретной версии. [Clusters, nodes и shards](https://www.elastic.co/docs/deploy-manage/distributed-architecture/clusters-nodes-shards).

# Чем refresh, flush и merge отличаются по видимости записи, надёжности и стоимости?

**Refresh** открывает новые Lucene segments для поиска: запись может быть подтверждена, но ещё не появиться в обычном search. Принудительный refresh после каждого документа ухудшает throughput.

**Flush** выполняет Lucene commit и позволяет начать новое поколение translog; надёжность между commits опирается на translog и настройки его синхронизации. **Merge** объединяет segments, сокращает их число и освобождает место от части устаревших данных, потребляя I/O и CPU. Поэтому видимость в поиске, устойчивое сохранение и фоновая оптимизация — разные процессы. [Near real-time search](https://www.elastic.co/docs/manage-data/data-store/near-real-time-search), [translog](https://www.elastic.co/docs/reference/elasticsearch/index-settings/translog).

# Как match, term, filter context и BM25 влияют на совпадения и ranking?

`match` анализирует поисковый текст и строит полнотекстовое условие, а `term` ищет конкретный индексированный term без обычного анализа строки запроса. Поэтому `term` по анализируемому `text` часто не соответствует ожиданию поиска исходной фразы.

**Query context** может вычислять relevance score, а **filter context** проверяет условие без вклада в scoring и подходит, например, для статуса или диапазона дат. **BM25** учитывает частоту term, его редкость и длину документа с определёнными настройками. Качество ranking проверяют на размеченных запросах; высокий score сам по себе не означает правильный бизнес-результат.

# Как проектировать bulk indexing и обрабатывать частичные ошибки без потери документов?

Bulk группирует операции, уменьшая сетевой overhead, но не делает весь набор атомарной транзакцией. Проверяют результат **каждого item**: успешный HTTP-ответ bulk может содержать ошибки отдельных документов.

Batch ограничивают по байтам, количеству документов и concurrency. Временные перегрузки повторяют с backoff, постоянные ошибки mapping выделяют для исправления. Стабильный document ID и контроль версии помогают безопасному повтору и защите от запоздалого события. При асинхронном индексировании сохраняют источник повторной обработки, иначе ответ одной неуспешной партии способен создать незаметную дыру в поиске. [Bulk API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-bulk).

# Как reindex и index aliases позволяют изменить mapping и переключить поиск?

Для несовместимого mapping создают новый versioned index с нужными settings и переносят данные через **reindex** или повторную загрузку из источника истины. Проверяют document counts, ошибки, контрольные запросы и релевантность.

**Alias** даёт приложению стабильное имя, которое переключают на новый индекс согласованной операцией alias API. Reindex сам по себе не гарантирует перенос изменений, появившихся во время копирования: нужен журнал, dual-write с контролем ошибок, догоняющая обработка либо окно остановки записи. Отдельно задают write index и срок сохранения старого индекса. [Index aliases](https://www.elastic.co/docs/manage-data/data-store/aliases).

# Как search_after и Point in Time помогают выполнять глубокую пагинацию?

Большой `from` заставляет shards и coordinator работать с большим числом промежуточных hits. **search_after** продолжает результат по значениям сортировки последнего документа вместо постоянного пропуска всё большего префикса.

Нужен детерминированный sort с tie-breaker. **Point in Time**, или PIT, фиксирует поисковое представление, чтобы параллельные обновления не сдвигали страницы; без него возможны пропуски и повторения. PIT имеет срок жизни и удерживает ресурсы, поэтому его закрывают и продлевают обоснованно. Это последовательная пагинация: произвольный переход на далёкую страницу требует отдельного решения. [Pagination Elasticsearch](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/paginate-search-results).

# Как aggregations, cardinality и high-cardinality fields влияют на память и точность?

**Aggregations** вычисляют buckets и метрики по подходящим документам. Поле с большим числом различных значений способно создать много buckets и дорогую структуру объединения между shards. Для сортировки и агрегаций обычно используют подходящие поля с doc values, а не бездумно включают fielddata для `text`.

`cardinality` обычно является приближённой distinct-оценкой с компромиссом памяти и точности. `terms` по distributed shards тоже может иметь особенности полноты и ошибки counts. Проверяют ограничения buckets, circuit breakers и реальные распределения; для полного обхода групп рассматривают composite aggregation в поддерживаемой версии.

# Как диагностировать red или yellow cluster health, unassigned shards и медленные запросы?

**Yellow** обычно означает, что primary shards распределены, но часть replicas недоступна; **red** — что хотя бы один primary shard не назначен. Из-за этого red может приводить к недоступным данным или частичным результатам.

Проверяют allocation explanation, disk watermarks, capacity, node roles, zone constraints и состояние recovery. Для медленного поиска исследуют slow logs, профили запроса, shard fan-out, CPU, JVM pressure и очереди. Не повышают лимиты вслепую: лишние shards или тяжёлый script могут быть первопричиной. Исправление allocation не заменяет проверку полноты данных и клиентских ошибок.

# Как планировать snapshots, upgrades и перенос между Elasticsearch и OpenSearch с учётом совместимости?

Используют поддерживаемый **snapshot repository** и регулярно проверяют restore; обычная копия data directories работающего кластера не заменяет корректный snapshot. Совместимость snapshot, индексов, plugins и major versions проверяют отдельно для источника и назначения.

Elasticsearch и OpenSearch нельзя считать drop-in заменами любых версий друг друга. Проверяют mappings, analyzers, API clients, security configuration и поддерживаемый migration path; может потребоваться remote reindex или повторная загрузка. До переключения сравнивают запросы и latency, планируют догоняющую индексацию и rollback. [Snapshots Elastic](https://www.elastic.co/docs/deploy-manage/tools/snapshot-and-restore), [миграции OpenSearch](https://docs.opensearch.org/latest/migrate-or-upgrade/).
