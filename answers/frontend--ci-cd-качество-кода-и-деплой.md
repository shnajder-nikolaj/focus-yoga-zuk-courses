# Чем форматирование кода отличается от linting?

Форматирование автоматически приводит код к единому стилю: отступы, кавычки, переносы строк, пробелы, точки с запятой. Обычно не меняет поведение программы. Инструмент - `Prettier`.

Linting выполняет статический анализ кода для обнаружения потенциальных ошибок, небезопасных конструкций и нарушений соглашений. Например, `ESLint` может обнаружить неиспользуемые переменные, некорректное использование React Hooks или необработанные промисы при соответствующей конфигурации.

Основное различие: форматирование отвечает за внешний вид кода, linting - преимущественно за его корректность и качество.

# Как разграничить ответственность ESLint и Prettier?

ESLint должен проверять качество и корректность кода, а Prettier - его форматирование.

Практическая конфигурация:

- `ESLint` - правила JavaScript, TypeScript, React, React Hooks и ограничения архитектуры
- `Prettier` - отступы, кавычки, переносы строк и другие правила форматирования
- `eslint-config-prettier` - отключение правил ESLint, конфликтующих с Prettier

Проверки выполняются независимо:

- `eslint .` - анализ кода
- `prettier . --check` - проверка форматирования

В современных версиях ESLint встроенные правила форматирования объявлены устаревшими, поэтому разделение ответственности соответствует развитию инструментов.&#x20;

# Как запретить импорт из внутренних модулей соседней feature?

Используют архитектурные ограничения импортов, которые проверяются линтером.

Например, в Feature-Sliced Design каждая feature предоставляет публичный API через `index.ts`. Другие модули должны импортировать её функциональность через этот API, не обращаясь к внутренним файлам.

```
// Разрешено
import { LoginForm } from '@/features/auth';

// Запрещено
import { LoginForm } from '@/features/auth/ui/LoginForm';
```

Для проверки подходят:

- `no-restricted-imports` в ESLint - запрет определённых путей и шаблонов
- `eslint-plugin-boundaries` - проверка зависимостей между архитектурными слоями и элементами
- `dependency-cruiser` - анализ графа модулей и ограничений зависимостей

Важно учитывать алиасы и относительные пути: запрет только шаблона `@/features/*/*` можно обойти через относительный импорт.

# Как обнаруживать циклические зависимости?

Циклическая зависимость возникает, когда модули прямо или косвенно импортируют друг друга.

Например: `A -> B -> C -> A`.

Для обнаружения используют:

- `eslint-plugin-import` с правилом `import/no-cycle`
- `Madge` с параметром `--circular`
- `dependency-cruiser` с правилом `no-circular`

Инструменты строят граф импортов и ищут циклы.

Циклы могут приводить к проблемам инициализации, когда модуль обращается к ещё не инициализированному экспорту, а также усложняют тестирование и изменение архитектуры.

Для устранения обычно выделяют общую функциональность в независимый модуль или изменяют направление зависимостей.

Не каждый цикл вызывает ошибку выполнения: ES Modules поддерживают циклические связи, но корректность зависит от порядка инициализации и использования экспортов.

# Как проверять неиспользуемые exports и зависимости?

Используют статический анализ импортов, экспортов и зависимостей проекта.

Основные инструменты:

- `Knip` - выявляет неиспользуемые файлы, экспорты и зависимости, включая многие случаи использования в конфигурациях и скриптах
- `depcheck` - анализирует зависимости из `package.json`, но может пропускать неявные способы использования
- `ESLint` и `typescript-eslint` - обнаруживают неиспользуемые переменные и импорты, но стандартные правила не гарантируют обнаружения всех неиспользуемых экспортов

Например, `Knip` можно запускать командой `npx knip`.

Ограничение: статический анализ не всегда распознаёт динамические импорты, обращения через строки, runtime-плагины и публичные API библиотек.

Поэтому автоматическое удаление найденных экспортов и зависимостей требует проверки реального использования.

# Как настроить pre-commit hooks без чрезмерного замедления работы?

Pre-commit hooks запускают автоматические проверки перед созданием коммита.

Типичная комбинация - `Husky` и `lint-staged`:

- `Husky` регистрирует Git hooks
- `lint-staged` запускает проверки только для файлов, добавленных в staging area
- `ESLint --fix` исправляет поддерживаемые нарушения
- `Prettier --write` форматирует изменённые файлы

Например, конфигурация `lint-staged`:

```
{
  "*.{js,jsx,ts,tsx}": [
    "eslint --fix",
    "prettier --write"
  ],
  "*.{json,css,md}": "prettier --write"
}
```

Чтобы hooks оставались быстрыми, не следует запускать полную сборку, E2E-тесты и проверку всего репозитория перед каждым коммитом.

Полноценные проверки должны выполняться в CI, поскольку локальные hooks можно обойти, например через `git commit --no-verify`.

# Что такое typecheck как отдельный CI-этап?

Typecheck - независимая проверка типов TypeScript без генерации JavaScript.

Обычно выполняется командой:

```
tsc --noEmit
```

TypeScript анализирует совместимость типов, интерфейсы, вызовы функций и другие конструкции. При ошибках команда завершается с ненулевым кодом, что приводит к падению соответствующего CI-job.

Выделение typecheck в отдельный этап полезно, потому что:

- Сборщики вроде Vite обычно транспилируют TypeScript без полноценной проверки типов
- Ошибки типов обнаруживаются независимо от сборки
- Результаты проверки можно выполнять параллельно с linting и тестами

Для монорепозитория с TypeScript Project References может использоваться `tsc --build` с соответствующей конфигурацией проектов.

# Какие проверки стоит включить в quality gate?

Quality gate - набор обязательных условий, без выполнения которых изменение нельзя объединить с основной веткой или выпустить.

Типичные проверки:

- Formatting - соответствие правилам Prettier
- Linting - отсутствие нарушений ESLint установленной критичности
- Typecheck - отсутствие ошибок TypeScript
- Unit/integration tests - успешное прохождение тестов
- Build - успешная production-сборка
- Security scanning - отсутствие уязвимостей выше принятого порога риска
- Architecture checks - отсутствие запрещённых импортов и зависимостей
- Code review - обязательное одобрение изменений

Дополнительно применяют пороги покрытия тестами, ограничения размера bundle и E2E-тесты для критических сценариев.

Важно, чтобы quality gate был автоматизированным и воспроизводимым, а обязательные проверки нельзя было обойти обычным merge без необходимых прав.

# Как организовать code review и согласовать критерии качества?

Code review - проверка изменений другими разработчиками перед их объединением с основной веткой.

Критерии следует зафиксировать в `CONTRIBUTING.md`, документации проекта или шаблоне pull request.

Проверяют прежде всего:

- Корректность бизнес-логики и обработку ошибок
- Соответствие архитектуре проекта
- Безопасность и обработку пользовательских данных
- Читаемость и поддерживаемость кода
- Наличие необходимых тестов
- Влияние на производительность и доступность интерфейса

Форматирование, linting и проверка типов должны выполняться автоматически, а не тратить время ревьюеров.

Практически полезны небольшие pull requests, обязательные одобрения, `CODEOWNERS`, защищённые ветки и понятные правила разрешения замечаний.

# Что такое статический анализ безопасности зависимостей и кода?

Статический анализ безопасности ищет потенциальные уязвимости без выполнения приложения.

Основные направления:

SCA (Software Composition Analysis) - анализ сторонних зависимостей. Инструменты сопоставляют установленные версии пакетов с базами известных уязвимостей.

Примеры: `npm audit`, `Dependabot`, `Snyk`, `OSV-Scanner`.

SAST (Static Application Security Testing) - анализ исходного кода на потенциально опасные конструкции.

Примеры: `Semgrep`, `CodeQL`, security-правила ESLint.

SAST может обнаруживать небезопасную работу с пользовательским вводом, потенциальные XSS и использование опасных API.

Главное ограничение - статический анализ не гарантирует отсутствия уязвимостей. Возможны ложные срабатывания, пропущенные ошибки и уязвимости, проявляющиеся только при выполнении приложения.

# Как настроить единые правила качества в монорепозитории?

В монорепозитории общие правила выносят в централизованные конфигурации, которые используют все приложения и пакеты.

Обычно создают:

- Общую конфигурацию ESLint
- Единые настройки Prettier
- Базовый `tsconfig.base.json`
- Общие правила тестирования
- Архитектурные ограничения между пакетами

Версии инструментов фиксируют через `package.json`, lockfile и поле `packageManager`. Для управления зависимостями используют workspaces, например `pnpm workspaces`.

Nx или Turborepo позволяют запускать проверки только для затронутых проектов и переиспользовать результаты кеширования.

При этом не обязательно применять одинаковые правила ко всем пакетам: базовая конфигурация может расширяться настройками для React-приложений, Node.js-сервисов и библиотек.

# Какие этапы должен содержать pipeline frontend-приложения?

Типичный CI/CD pipeline состоит из следующих этапов:

1. Install - установка зависимостей с использованием lockfile
2. Quality - форматирование, ESLint, TypeScript и архитектурные проверки
3. Test - unit- и integration-тесты, при необходимости E2E
4. Build - production-сборка приложения
5. Security - анализ зависимостей, исходного кода и контейнерного образа
6. Package - создание версионированного Docker image или другого артефакта
7. Deploy - развёртывание в staging или production
8. Smoke tests - проверка работоспособности развёрнутой версии
9. Monitoring - отслеживание ошибок и состояния приложения

Независимые проверки можно выполнять параллельно.

Важный принцип - build once, deploy many: один проверенный артефакт продвигается между окружениями без повторной сборки. Для этого конфигурацию, зависящую от окружения, отделяют от сборки.

# Чем continuous integration отличается от continuous delivery и deployment?

Continuous Integration (CI) - регулярное объединение изменений в общую кодовую базу с автоматическими проверками, тестами и сборкой.

Continuous Delivery - практика, при которой приложение после успешных проверок постоянно находится в состоянии готовности к релизу. Развёртывание в production может требовать ручного подтверждения.

Continuous Deployment - автоматическое развёртывание каждого изменения, успешно прошедшего pipeline, без обязательного ручного подтверждения.

Главное отличие:

- CI - автоматически проверяет интеграцию изменений
- Continuous Delivery - обеспечивает готовность к выпуску
- Continuous Deployment - автоматически выпускает изменения

Continuous Deployment требует надёжных проверок, мониторинга и механизма отката.

# Как организовать кеш npm/pnpm в GitLab CI или GitHub Actions?

Кеширование зависимостей ускоряет CI, позволяя повторно использовать ранее загруженные пакеты.

В GitHub Actions используется `actions/setup-node` с параметром `cache`.

Например:

```
- uses: actions/setup-node@v7
  with:
    node-version: 24
    cache: npm

- run: npm ci
```

Для pnpm необходимо предварительно установить совместимую версию pnpm и указать `cache: pnpm`.

В GitLab CI используют `cache` с ключом, зависящим от lockfile:

```
cache:
  key:
    files:
      - package-lock.json
  paths:
    - .npm/

script:
  - npm ci --cache .npm --prefer-offline
```

Рекомендуется кешировать npm cache или pnpm store, а не `node_modules`. Это позволяет повторно использовать скачанные пакеты, сохраняя чистую установку.

Ключ кеша должен учитывать lockfile, а при необходимости также версию Node.js, package manager и платформу. Кеш не должен быть источником истины для зависимостей.&#x20;

# Чем `npm ci` предпочтительнее `npm install` в воспроизводимой сборке?

`npm ci` предназначен для чистой установки зависимостей в CI.

Отличия от `npm install`:

- Требует существующий `package-lock.json` или `npm-shrinkwrap.json`
- Устанавливает версии согласно lockfile
- Завершается ошибкой, если lockfile несовместим с `package.json`
- Удаляет существующий `node_modules` перед установкой
- Не изменяет `package.json` и lockfile

`npm install` может обновлять lockfile и изменять разрешённое дерево зависимостей.

Главное преимущество `npm ci` - предсказуемость установки.

Однако для полной воспроизводимости также необходимо фиксировать версии Node.js, npm, конфигурацию установки и учитывать влияние install-скриптов и внешних ресурсов.&#x20;

# Как подготовить multi-stage Dockerfile для React SPA?

Multi-stage build разделяет сборку приложения и его выполнение.

Для React SPA обычно используются две стадии:

1. Node.js - установка зависимостей и создание production-сборки
2. Nginx - раздача готовых статических файлов

Пример для приложения на Vite:

```
# Stage 1: Build
FROM node:24-alpine AS build

WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci

COPY . .
RUN npm run build

# Stage 2: Runtime
FROM nginx:stable-alpine

COPY nginx.conf /etc/nginx/conf.d/default.conf

COPY --from=build /app/dist /usr/share/nginx/html

EXPOSE 80
```

В production-образ попадают только Nginx, конфигурация и готовые файлы приложения. Node.js, исходники и инструменты сборки не требуются.

Преимущества:

- Меньший размер образа
- Меньшая поверхность атаки
- Более быстрое распространение артефакта
- Разделение build-time и runtime-зависимостей

Для production следует дополнительно фиксировать версии базовых образов, предпочтительно через digest, использовать `.dockerignore` и проверять конфигурацию Nginx.&#x20;

# Почему Nginx часто используют для раздачи статической сборки?

Nginx - высокопроизводительный HTTP-сервер, подходящий для отдачи HTML, CSS, JavaScript и других статических ресурсов.

Его преимущества:

- Эффективная обработка большого количества соединений
- Низкие накладные расходы при раздаче файлов
- Поддержка HTTP-кеширования
- Возможность настройки gzip и Brotli при наличии соответствующих модулей
- TLS-терминация и reverse proxy
- Настройка security headers и SPA fallback

React SPA после production-сборки обычно не требует Node.js для выполнения: JavaScript работает в браузере.

При этом Nginx не обязателен - статическое приложение также можно размещать непосредственно на CDN или специализированном статическом хостинге.

# Как настроить fallback на `index.html` для SPA routes?

При использовании `BrowserRouter` маршрутизация выполняется в браузере.

Например, пользователь открывает `/profile/settings`. Сервер пытается найти такой файл, но соответствующего файла не существует.

Необходимо возвращать `index.html`, чтобы React Router обработал маршрут самостоятельно.

Пример Nginx:

```
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    location ^~ /assets/ {
        try_files $uri =404;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

Директива `try_files` сначала проверяет существование файла или директории, а при отсутствии выполняет внутреннее перенаправление на `index.html`.

Важно: отсутствующие JS/CSS-файлы должны возвращать `404`, а не HTML. Иначе браузер может получить HTML вместо JavaScript и сообщить о MIME type error.

API-маршруты также должны обрабатываться отдельно.

Для неизвестных SPA-маршрутов сервер с такой конфигурацией вернёт HTTP `200`, даже если React покажет страницу Not Found. Это нужно учитывать при SEO и серверном мониторинге.&#x20;

# Как корректно кэшировать `index.html` и хэшированные JS/CSS-файлы?

HTML и хэшированные статические ресурсы должны иметь разные стратегии кеширования.

Для `index.html`:

```
Cache-Control: no-cache
```

Браузер может сохранить файл, но перед повторным использованием должен проверить его актуальность у сервера.

Для хэшированных ресурсов:

```
Cache-Control: public, max-age=31536000, immutable
```

Например, файл `app.a31bc9.js` содержит хэш содержимого. При изменении кода сборщик создаст новый URL, поэтому старую версию можно кешировать надолго.

Почему это важно:

- Пользователь получает актуальный HTML
- Неизменённые JS/CSS загружаются из кеша
- Новые версии ресурсов загружаются только при изменении их URL

Критический момент: старые хэшированные файлы желательно сохранять некоторое время после релиза. Иначе ранее загруженный HTML или работающая вкладка могут обратиться к уже удалённому ресурсу.

Service Worker и CDN могут иметь дополнительные уровни кеширования, которые необходимо учитывать отдельно.&#x20;

# Что такое immutable Docker image и зачем фиксировать digest?

Immutable Docker image - неизменяемый артефакт контейнера, содержимое которого идентифицируется криптографическим digest.

Docker image можно адресовать через тег:

```
frontend:1.4.0
```

Но тег может быть переназначен на другой образ.

Digest однозначно идентифицирует конкретное содержимое образа:

```
frontend@sha256:<digest>
```

Фиксация digest позволяет:

- Разворачивать именно проверенный образ
- Исключать неожиданную замену содержимого под тем же тегом
- Обеспечивать предсказуемый rollback
- Улучшать прослеживаемость артефактов

Digest фиксирует идентичность образа, но сам по себе не подтверждает, что образ безопасен или создан доверенной сборкой.

Также нужно учитывать, что фиксация digest базового образа исключает автоматическое получение его обновлений безопасности.&#x20;

# Как хранить секреты CI без включения их в frontend bundle?

Секреты должны храниться в защищённых хранилищах CI/CD, например GitHub Actions Secrets, GitLab CI/CD Variables или внешнем secret manager.

Основные правила:

- Ограничивать доступ к секретам по окружениям и ролям
- Использовать masked/protected variables там, где это поддерживается
- Предпочитать краткоживущие credentials через OIDC
- Не выводить секреты в логи
- Не передавать секреты в Docker через `ARG` или `ENV`
- Не включать секреты в frontend-переменные сборки

Например, переменные с префиксом `VITE_` в Vite доступны клиентскому коду и могут попасть в JavaScript bundle.

Любые данные, переданные в браузер, потенциально доступны пользователю.

Поэтому приватные API-ключи и токены должны использоваться на backend. Frontend обращается к backend, а тот выполняет запрос к защищённому внешнему сервису.

Если секрет нужен только во время Docker-сборки, используют BuildKit secret mounts.&#x20;

# Как безопасно передать runtime config статическому приложению?

Runtime config позволяет изменять конфигурацию приложения без повторной сборки.

Например, один Docker image может использовать разные API endpoints в staging и production.

Один из способов - предоставлять конфигурацию через `config.json`:

```
{
  "apiBaseUrl": "https://api.example.com",
  "environment": "production"
}
```

Перед инициализацией React приложение загружает этот файл:

```
const config = await fetch('/config.json', {
  cache: 'no-store'
}).then((response) => {
  if (!response.ok) {
    throw new Error('Failed to load config');
  }

  return response.json();
});
```

На практике нужно валидировать структуру конфигурации, например через Zod, и корректно обрабатывать ошибки загрузки.

Важные требования:

- Не хранить в конфигурации секреты
- Запретить длительное кеширование файла
- Ограничить список разрешённых параметров
- Защитить изменение конфигурации на стороне сервера
- Не вставлять непроверенные значения в исполняемый JavaScript или HTML

Runtime config подходит для публичных URL, идентификаторов окружений и настроек интерфейса, но не является механизмом передачи секретов.

# Чем blue-green deployment отличается от canary release?

Оба подхода позволяют снижать риски при выпуске новых версий приложения.

Blue-green deployment использует два независимых окружения:

- Blue - текущая production-версия
- Green - новая версия приложения

После проверки Green трафик переключается на него. При проблемах можно вернуть трафик на Blue.

Canary release постепенно направляет часть пользователей на новую версию, например 5%, 20%, 50%, 100%.

Если метрики ухудшаются, rollout останавливают или откатывают.

Главное различие:

- Blue-green - переключение между двумя версиями целиком
- Canary - постепенное увеличение доли трафика новой версии

Для SPA важно учитывать кеширование: CDN, браузеры и открытые вкладки могут продолжать использовать старую версию даже после переключения окружений.

# Как организовать feature flags и постепенный rollout?

Feature flags позволяют включать и отключать функциональность без нового деплоя.

Например, приложение получает конфигурацию:

```
{
  "newCheckoutEnabled": true
}
```

На основании флага React показывает новый или старый интерфейс.

Для постепенного rollout используют платформы вроде `LaunchDarkly`, `Unleash` или собственный сервис.

Типичный механизм:

1. Новая функция развёрнута, но отключена
2. Функция включается для ограниченной группы пользователей
3. Собираются метрики ошибок и поведения
4. Доля пользователей постепенно увеличивается
5. При проблемах функция отключается без rollback всего приложения

Для процентного rollout используют стабильное распределение пользователей, например хэш от идентификатора пользователя и идентификатора флага. Это позволяет сохранять назначенный вариант между запросами.

Важно:

- Проверять права доступа на backend
- Не считать клиентские флаги механизмом безопасности
- Предусматривать поведение при недоступности сервиса флагов
- Удалять устаревшие флаги после завершения rollout

# Как выполнить откат релиза при ошибке?

Rollback - возврат приложения к предыдущей стабильной версии.

Надёжный подход - хранить готовые артефакты каждого релиза и развёртывать их повторно без пересборки.

Типичный процесс:

1. Мониторинг обнаруживает критическую ошибку
2. Новое развёртывание останавливается
3. Трафик возвращается на предыдущую стабильную версию
4. Выполняются smoke tests
5. Проверяется восстановление метрик

В Kubernetes можно использовать `kubectl rollout undo`, если сохранена подходящая история ревизий.

Для статического frontend достаточно переключить CDN или сервер на предыдущий набор файлов.

Особенно важно учитывать совместимость frontend и backend. Старое приложение должно продолжать работать с актуальным API.

Также нельзя преждевременно удалять хэшированные файлы старой версии: они могут требоваться уже открытым вкладкам пользователей.

# Как организовать smoke tests после деплоя?

Smoke tests - небольшой набор быстрых проверок, подтверждающих, что развёрнутое приложение выполняет основные функции.

Для frontend обычно проверяют:

- Главная страница возвращает успешный HTTP-ответ
- `index.html` и основные JS/CSS-файлы доступны
- Приложение успешно запускается в браузере
- Основные маршруты открываются
- Критические API-запросы работают
- Нет критических JavaScript-ошибок

Для реализации используют `Playwright`, HTTP-проверки и синтетический мониторинг.

Например, после деплоя Playwright открывает production URL и проверяет наличие ключевого элемента интерфейса.

Smoke tests должны проверять развёрнутую версию, а не локальную сборку.

Если тесты не проходят, pipeline помечает релиз как неуспешный и может инициировать автоматический rollback.

# Что такое readiness/liveness checks и применимы ли они к статическому frontend?

Liveness check определяет, работает ли контейнер. При неуспешной проверке Kubernetes может перезапустить его.

Readiness check определяет, готов ли контейнер принимать трафик. Если проверка не проходит, Kubernetes исключает Pod из доступных endpoints Service.

Для статического frontend на Nginx проверки применимы, но имеют ограничения.

Например:

- Liveness - Nginx отвечает на HTTP-запрос
- Readiness - сервер доступен и способен отдавать необходимые файлы приложения

Однако успешный HTTP `200` от Nginx не гарантирует, что React успешно запустится в браузере.

JavaScript может завершаться с ошибкой, API может быть недоступен, а CSP - блокировать необходимые ресурсы.

Поэтому health checks инфраструктуры дополняют browser-based smoke tests.

Если приложение размещено непосредственно на CDN без управляемых контейнеров, Kubernetes readiness/liveness probes не нужны.

# Как обеспечивать безопасность supply chain сборки?

Software supply chain security - защита всей цепочки создания и доставки приложения: исходного кода, зависимостей, инструментов сборки, CI/CD и конечных артефактов.

Основные меры:

- Lockfile - фиксация дерева зависимостей
- SCA - поиск известных уязвимостей в зависимостях
- Dependency pinning - фиксация версий инструментов, Docker images и CI actions
- Least privilege - минимальные разрешения CI-токенов
- Secret management - безопасное хранение credentials
- SBOM - формирование перечня компонентов программного продукта
- Artifact signing - криптографическая подпись артефактов
- Build provenance - сведения о происхождении сборки и условиях её создания

Дополнительно применяют защищённые ветки, обязательный code review и изолированные CI runners.

Для подписей и attestations можно использовать `Sigstore` и `Cosign`. Проверяемое происхождение сборки поддерживается в подходах SLSA.

Например, npm Trusted Publishing позволяет публиковать пакеты из поддерживаемых CI-систем через OIDC без долгоживущих npm-токенов.

Ключевой принцип: в production должен попадать только проверенный артефакт, полученный из доверенного исходного кода через контролируемый pipeline.&#x20;

# Как диагностировать проблему, если сайт доступен, но приложение не загружается?

Если HTML доступен, но React не запускается, сначала используют Chrome DevTools - Console и Network.

Последовательность диагностики:

1. Network - проверить загрузку JS/CSS, HTTP-статусы и MIME types
2. Console - проверить JavaScript-ошибки и сообщения браузера
3. CSP - убедиться, что политики безопасности не блокируют скрипты и запросы
4. Runtime config - проверить наличие и корректность конфигурации
5. API - проверить ошибки запросов, CORS и авторизацию
6. Caching - исключить несовпадение версий HTML и JS
7. Service Worker - проверить, не отдаёт ли он устаревшие ресурсы
8. Deployment - убедиться, что все файлы нужной версии опубликованы

Типичные симптомы:

- `404` при загрузке JS - файл отсутствует или указан неправильный путь
- `Unexpected token '<'` - вместо JavaScript сервер часто возвращает HTML
- `Failed to fetch dynamically imported module` - динамический chunk недоступен
- `Refused to execute script` - возможная проблема CSP или MIME type
- `TypeError` при инициализации - ошибка приложения, конфигурации или несовместимость API

Если локально всё работает, следует сравнить production-сборку, переменные окружения, `base`/`publicPath`, конфигурацию сервера и CDN.

# Какие ошибки возникают из-за несовпадения версий HTML и JS после деплоя?

Проблема возникает, когда браузер получает HTML и JavaScript из разных версий приложения.

Например:

1. Пользователь открыл старую версию SPA
2. Выпущена новая версия
3. Старые хэшированные JS-файлы удалены
4. Приложение пытается загрузить старый динамический chunk
5. Сервер возвращает `404`

Возможные ошибки:

- `ChunkLoadError`
- `Failed to fetch dynamically imported module`
- `Unexpected token '<'`
- Ошибки выполнения из-за несовместимости кода, конфигурации или API

Проблема может возникнуть и при некорректном кешировании `index.html`, когда старый HTML ссылается на удалённые ресурсы.

Способы предотвращения:

- Использовать хэшированные имена JS/CSS
- Настроить revalidation для `index.html`
- Сохранять старые ресурсы на период совместимости
- Выполнять атомарную публикацию новой версии
- Обеспечивать обратную совместимость API
- Корректно обрабатывать ошибки загрузки динамических импортов

При необходимости приложение может предложить пользователю обновить страницу.

# Как настроить CSP и security headers на Nginx?

CSP (Content Security Policy) ограничивает источники, из которых браузеру разрешено загружать и выполнять ресурсы.

Это дополнительная защита от XSS и некоторых других атак.

Пример Nginx:

```
add_header Content-Security-Policy
  "default-src 'self';
   script-src 'self';
   style-src 'self';
   img-src 'self' data:;
   connect-src 'self' https://api.example.com;
   object-src 'none';
   base-uri 'self';
   frame-ancestors 'none'"
  always;

add_header X-Content-Type-Options "nosniff" always;

add_header Referrer-Policy
  "strict-origin-when-cross-origin" always;

add_header X-Frame-Options "DENY" always;
```

Назначение заголовков:

- `Content-Security-Policy` - ограничивает загрузку и выполнение ресурсов
- `X-Content-Type-Options` - запрещает MIME sniffing для соответствующих типов ресурсов
- `Referrer-Policy` - управляет передачей информации в `Referer`
- `X-Frame-Options` - ограничивает встраивание страницы в iframe; современный аналог - `frame-ancestors` в CSP
- `Strict-Transport-Security` - требует использование HTTPS для последующих соединений с хостом

HSTS настраивают отдельно для HTTPS, например:

```
add_header Strict-Transport-Security
  "max-age=31536000; includeSubDomains" always;
```

`includeSubDomains` допустим, только если все соответствующие поддомены поддерживают HTTPS.

Важно: CSP должна соответствовать реальным ресурсам приложения. Сторонние API, шрифты, изображения и используемые стили могут потребовать дополнительных разрешений.

По возможности следует избегать `unsafe-inline` и `unsafe-eval`. Для необходимых inline-скриптов используют nonce или hash.

Перед включением строгой политики полезно проверить её через `Content-Security-Policy-Report-Only`.&#x20;

# Как установить performance budget и контролировать его в CI?

Performance budget - набор количественных ограничений на размер приложения и показатели его производительности.

Примеры ограничений:

- Initial JavaScript - не более 200 KB в сжатом виде
- Initial CSS - не более 50 KB
- `LCP` - не более 2.5 секунды
- `INP` - не более 200 мс
- `CLS` - не более 0.1

Размеры здесь приведены как пример бюджета. Реальные ограничения выбирают с учётом продукта и устройств пользователей.

Для автоматической проверки используют:

- `size-limit` или `bundlesize` - контроль размера JavaScript bundle
- `Lighthouse CI` - проверка производительности страницы
- Анализатор bundle - обнаружение тяжёлых зависимостей и роста отдельных chunks

В CI задают пороги: если размер bundle превышен или измеренные показатели не соответствуют требованиям, проверка завершается ошибкой.

Важно различать лабораторные и реальные показатели. Lighthouse CI выполняет синтетические измерения, а реальные Core Web Vitals собираются по данным пользователей, обычно с оценкой 75-го перцентиля.

Результаты Lighthouse могут колебаться из-за условий запуска, поэтому проверки желательно выполнять в стабильном окружении, использовать несколько прогонов и разумные пороги.

Основная задача performance budget - обнаруживать регрессии производительности до попадания изменений в production.
