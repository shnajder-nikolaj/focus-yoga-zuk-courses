# Как браузер находит IP-адрес сервера по доменному имени?

Браузер использует DNS (Domain Name System) - систему преобразования доменных имён в IP-адреса.

Процесс разрешения имени:

1. Браузер проверяет собственный DNS-кеш, затем при необходимости обращается к системному DNS-резолверу
2. Если адрес неизвестен, запрос отправляется рекурсивному DNS-резолверу
3. Резолвер проверяет кеш. При отсутствии записи последовательно обращается к корневым DNS-серверам, серверам доменной зоны (например, `.com`) и авторитативному серверу домена
4. Авторитативный сервер возвращает DNS-запись с IP-адресом
5. Резолвер передаёт результат клиенту, после чего браузер может установить соединение с сервером

Браузер также может использовать DNS-over-HTTPS (DoH), а IPv4- и IPv6-адреса могут запрашиваться параллельно.

# Как работает DNS и что такое TTL записи?

DNS (Domain Name System) - распределённая иерархическая система, которая сопоставляет доменные имена с DNS-записями, включая IP-адреса серверов.

DNS использует несколько уровней серверов:

- Root DNS - указывают серверы доменов верхнего уровня
- TLD DNS - указывают авторитативные серверы конкретных доменов
- Authoritative DNS - хранят DNS-записи домена и предоставляют авторитативные ответы
- Recursive Resolver - выполняет разрешение имён от имени клиента и кеширует результаты

TTL (Time To Live) - время в секундах, в течение которого DNS-запись может храниться в кеше.

Например, при `TTL = 300` резолвер может использовать кешированную запись до 5 минут без повторного обращения к авторитативному серверу.

После истечения TTL запись необходимо получить заново перед дальнейшим использованием.

Важно: изменение DNS-записи не означает немедленного обновления адреса у всех пользователей. Старые значения могут сохраняться в кешах до истечения их TTL.

# Чем записи A, AAAA, CNAME и TXT отличаются?

- A - сопоставляет доменное имя с IPv4-адресом, например `example.com → 192.0.2.1`
- AAAA - сопоставляет доменное имя с IPv6-адресом, например `example.com → 2001:db8::1`
- CNAME - создаёт псевдоним другого доменного имени. Например, `www.example.com → example.com`. Для получения IP-адреса необходимо разрешить целевое имя
- TXT - хранит текстовые данные. Используется для подтверждения владения доменом, SPF, DKIM и других механизмов

Особенность CNAME: имя, для которого задана CNAME-запись, не должно иметь другие DNS-записи. Поэтому стандартный CNAME нельзя использовать в корне зоны, где обязательно присутствуют записи `SOA` и `NS`.

# Что такое TCP three-way handshake?

TCP three-way handshake - процедура установления TCP-соединения, при которой клиент и сервер синхронизируют начальные номера последовательности и подтверждают возможность двустороннего обмена данными.

Процесс состоит из трёх шагов:

1. SYN - клиент отправляет запрос на установление соединения со своим начальным номером последовательности
2. SYN-ACK - сервер подтверждает получение SYN и передаёт собственный начальный номер последовательности
3. ACK - клиент подтверждает SYN сервера, после чего соединение считается установленным с обеих сторон

После handshake можно передавать данные через TCP.

Процедура обычно требует одного RTT (Round-Trip Time) - времени прохождения пакета до сервера и ответа обратно.

TCP handshake не обеспечивает шифрование. Для HTTPS поверх TCP дополнительно используется TLS handshake.

# Чем TCP отличается от UDP?

TCP (Transmission Control Protocol) - протокол транспортного уровня, обеспечивающий надёжную, упорядоченную передачу потока байтов.

TCP предоставляет:

- Установление соединения через handshake
- Подтверждение получения данных через ACK
- Повторную передачу потерянных данных
- Сохранение порядка байтов
- Управление потоком и перегрузкой сети

UDP (User Datagram Protocol) - транспортный протокол, передающий независимые датаграммы без установления соединения.

UDP не гарантирует доставку, порядок или отсутствие дубликатов и не реализует встроенное восстановление потерь.

Главное отличие: TCP предоставляет гарантии надёжного упорядоченного потока, а UDP оставляет реализацию необходимых гарантий приложению или протоколу поверх него.

UDP используется в DNS, WebRTC и QUIC. При этом QUIC самостоятельно реализует надёжную доставку, контроль перегрузки и другие механизмы поверх UDP.

# Что такое congestion control и head-of-line blocking?

Congestion control - механизм управления скоростью передачи данных, предотвращающий перегрузку сети.

В TCP отправитель регулирует объём неподтверждённых данных с помощью congestion window (cwnd).

Принцип работы:

1. Отправитель постепенно увеличивает количество передаваемых данных
2. Оценивает состояние сети по ACK, потерям пакетов и другим сигналам
3. При признаках перегрузки уменьшает скорость отправки
4. При улучшении условий снова увеличивает её

Конкретное поведение зависит от алгоритма, например `CUBIC` или `BBR`.

Head-of-line blocking (HOL) - ситуация, когда потеря или задержка одного элемента блокирует обработку следующих элементов, даже если они уже получены.

Например, TCP гарантирует упорядоченный поток байтов. Если один сегмент потерян, последующие байты не могут быть переданы приложению до восстановления пропущенных данных.

В HTTP/2 это особенно заметно: несколько HTTP-потоков используют одно TCP-соединение, поэтому потеря TCP-сегмента может задержать все потоки.

HTTP/3 на QUIC устраняет HOL blocking между независимыми потоками на транспортном уровне, хотя блокировка внутри отдельного потока остаётся возможной.

# Для чего нужен TLS handshake?

TLS handshake - процедура согласования защищённого соединения между клиентом и сервером.

Его основные задачи:

1. Согласовать версию TLS и криптографические параметры
2. Аутентифицировать сервер с помощью сертификата
3. Выполнить криптографический обмен для получения общего секрета
4. Сформировать симметричные ключи шифрования
5. Подтвердить целостность и подлинность согласования

После handshake данные передаются в зашифрованном виде с защитой целостности.

В TLS 1.3 обычно используется эфемерный обмен ключами `(EC)DHE`, обеспечивающий Forward Secrecy - компрометация долгосрочного приватного ключа сервера не позволяет расшифровать ранее записанный трафик.

TLS 1.3 обычно требует одного RTT для завершения handshake. При возобновлении сессии возможна передача ранних данных `0-RTT`, но она имеет ограничения безопасности, включая риск повторного воспроизведения запросов.

# Что проверяет браузер в TLS-сертификате?

Браузер проверяет, можно ли доверять сертификату сервера и соответствует ли он посещаемому сайту.

Основные проверки:

- Доменное имя - запрашиваемый hostname должен присутствовать в `Subject Alternative Name (SAN)`
- Срок действия - текущая дата должна находиться между `Not Before` и `Not After`
- Цепочка доверия - сертификат должен вести к доверенному корневому центру сертификации
- Цифровые подписи - подписи сертификатов в цепочке должны быть криптографически корректными
- Назначение сертификата - сертификат должен допускать серверную TLS-аутентификацию
- Отзыв и прозрачность - применяются проверки статуса отзыва и Certificate Transparency в соответствии с политикой браузера

Дополнительно TLS handshake подтверждает, что сервер владеет приватным ключом, соответствующим сертификату.

При критической ошибке браузер блокирует соединение или показывает предупреждение безопасности.

# Чем HTTPS отличается от HTTP на транспортном уровне?

HTTP - протокол прикладного уровня для обмена запросами и ответами.

HTTPS - HTTP, передаваемый через защищённое TLS-соединение.

Основные различия:

- HTTP/1.1 без TLS обычно работает поверх TCP на порту `80`. Данные передаются без шифрования
- HTTPS с HTTP/1.1 или HTTP/2 работает через TLS поверх TCP, обычно на порту `443`
- HTTPS с HTTP/3 использует QUIC поверх UDP. TLS 1.3 встроен в QUIC

TLS обеспечивает:

- Конфиденциальность - шифрование данных
- Целостность - защиту от незаметного изменения
- Аутентификацию - проверку подлинности сервера

Важно: HTTPS не означает обязательное использование TCP. HTTP/3 работает через QUIC поверх UDP.

# Что такое SNI и ALPN?

SNI (Server Name Indication) - расширение TLS, позволяющее клиенту сообщить серверу доменное имя, к которому он подключается.

Это необходимо, когда на одном IP-адресе размещено несколько HTTPS-сайтов: сервер может выбрать подходящий сертификат.

Обычно SNI передаётся в `ClientHello` открытым текстом. Расширение ECH (Encrypted ClientHello) позволяет скрывать внутренний SNI, если поддерживается клиентом и серверной инфраструктурой.

ALPN (Application-Layer Protocol Negotiation) - расширение TLS для согласования прикладного протокола.

Например, клиент предлагает:

`h2`, `http/1.1`

Сервер выбирает поддерживаемый вариант, например `h2`.

Разница: SNI помогает определить, к какому домену обращается клиент, а ALPN - какой прикладной протокол будет использоваться поверх защищённого соединения.

# Чем HTTP/2 multiplexing отличается от HTTP/1.1?

В HTTP/1.1 запросы и ответы обычно обрабатываются последовательно внутри одного соединения.

Даже при использовании pipelining ответы должны возвращаться в порядке запросов. Поэтому браузеры обычно используют несколько TCP-соединений для параллельной загрузки ресурсов.

HTTP/2 multiplexing позволяет передавать несколько независимых HTTP-потоков через одно TCP-соединение.

Механизм работы:

1. Каждый запрос получает собственный `stream ID`
2. Данные разбиваются на бинарные фреймы
3. Фреймы разных потоков могут чередоваться в одном соединении
4. Получатель восстанавливает данные каждого потока независимо

Это уменьшает потребность в отдельных соединениях и устраняет блокировку на уровне последовательной обработки HTTP/1.1-запросов.

Ограничение: HTTP/2 по-прежнему зависит от TCP. Потеря TCP-сегмента может заблокировать доставку данных всех HTTP-потоков из-за транспортного HOL blocking.

# Почему HTTP/3 использует QUIC поверх UDP?

HTTP/3 использует QUIC поверх UDP, чтобы устранить ограничения TCP, особенно head-of-line blocking между независимыми HTTP-потоками.

QUIC самостоятельно реализует:

- Надёжную доставку данных
- Независимые потоки
- Управление перегрузкой и потоком
- Обнаружение потерь и повторную передачу
- Шифрование с использованием TLS 1.3
- Миграцию соединения при изменении IP-адреса или порта клиента

Основное преимущество: потеря данных одного QUIC-потока не требует блокировать доставку данных других потоков.

Дополнительно QUIC объединяет установление защищённого соединения и криптографическое согласование, сокращая задержку относительно последовательных TCP и TLS handshake.

UDP используется потому, что позволяет реализовать эти механизмы в QUIC без зависимости от встроенной семантики TCP и без необходимости изменять TCP-стеки операционных систем.

# Что такое keep-alive и connection pooling?

Keep-alive - механизм повторного использования установленного сетевого соединения для нескольких запросов.

В HTTP/1.1 постоянные соединения используются по умолчанию, если клиент или сервер не запрашивает закрытие.

Это позволяет избежать повторных TCP и TLS handshake для каждого HTTP-запроса.

Не следует путать HTTP keep-alive с TCP keepalive - механизмом отправки служебных проб для обнаружения неработающих соединений.

Connection pooling - управление набором соединений для их повторного использования.

Пул соединений позволяет:

- Сократить расходы на создание соединений
- Ограничить количество одновременных подключений
- Повторно использовать свободные соединения
- Управлять временем простоя и жизненным циклом соединений

Например, клиент может переиспользовать TCP/TLS-соединение для последовательных запросов, а HTTP/2 дополнительно позволяет отправлять несколько запросов параллельно через одно соединение.

Разница: keep-alive обеспечивает возможность сохранения соединения, а connection pooling управляет его повторным использованием и распределением между запросами.

# Что такое reverse proxy и как он участвует в маршрутизации запросов?

Reverse proxy - промежуточный сервер, который принимает запросы клиентов и перенаправляет их внутренним серверам приложения.

Например:

`Browser → Nginx → Backend`

Клиент взаимодействует с reverse proxy и обычно не знает, какой внутренний сервер обрабатывает запрос.

Маршрутизация может выполняться по:

- Домену (`Host` или HTTP/2 `:authority`)
- URL-пути (`/api`, `/static`)
- HTTP-заголовкам
- Другим правилам конфигурации

Дополнительные возможности:

- TLS termination - расшифровка HTTPS на прокси
- Load balancing - распределение запросов между серверами
- Caching - кеширование ответов
- Rate limiting - ограничение частоты запросов
- Request forwarding - передача запросов с добавлением служебных заголовков, например `X-Forwarded-For`

Пример: Nginx может направлять `/api/*` на backend, а `/static/*` - на сервер статических файлов.

# Чем балансировка нагрузки отличается от CDN?

Load Balancing - распределение входящих запросов или соединений между несколькими серверами.

Основные задачи:

- Равномерное распределение нагрузки
- Предотвращение перегрузки отдельных серверов
- Повышение отказоустойчивости
- Исключение недоступных серверов из распределения

Популярные алгоритмы: `Round Robin`, `Least Connections`, хеширование по ключу.

CDN (Content Delivery Network) - географически распределённая сеть серверов, которая доставляет контент пользователям из подходящих точек присутствия (PoP), часто используя кеширование.

Основные задачи:

- Снижение задержки доставки контента
- Уменьшение нагрузки на origin-сервер
- Кеширование статических и, при соответствующей настройке, динамических ответов
- Повышение доступности и устойчивости доставки контента

Главное отличие: балансировщик распределяет нагрузку между серверами, а CDN оптимизирует доставку контента через распределённую инфраструктуру.

CDN также может использовать балансировку нагрузки внутри своей сети или между origin-серверами.

# Что такое Web PKI и как работает цепочка доверия сертификатов?

Web PKI (Web Public Key Infrastructure) - инфраструктура открытых ключей, позволяющая браузерам проверять подлинность HTTPS-серверов с помощью цифровых сертификатов.

Основные элементы:

- Root CA - корневой центр сертификации, сертификат которого находится в доверенном хранилище браузера или ОС
- Intermediate CA - промежуточный центр, которому делегировано право выдавать сертификаты
- Leaf Certificate - конечный сертификат конкретного сайта

Типичная цепочка доверия:

`Root CA → Intermediate CA → Website Certificate`

Как работает проверка:

1. Сервер предоставляет свой сертификат и обычно промежуточные сертификаты
2. Браузер строит цепочку до доверенного корневого сертификата
3. Проверяет цифровые подписи, сроки действия, ограничения и назначение сертификатов
4. Проверяет соответствие доменного имени сертификату
5. При успешной проверке допускает установление защищённого соединения

Ключевой принцип: браузеру не требуется заранее доверять каждому сайту. Достаточно доверять корневому CA, от которого можно построить корректную цепочку доверия.

При этом доверие к CA само по себе не отменяет проверку домена и других ограничений сертификата.

# Какие сетевые события могут вызвать ошибку `ERR_CONNECTION_RESET`?

`ERR_CONNECTION_RESET` - ошибка Chromium-браузеров, обычно означающая, что сетевое соединение было принудительно сброшено до завершения обмена данными.

На уровне TCP это часто связано с получением пакета с флагом RST (Reset).

Возможные причины:

- Сервер принудительно закрыл TCP-соединение
- Reverse proxy или балансировщик сбросил соединение
- Firewall, антивирус или сетевой фильтр отправил TCP RST
- Прокси или VPN вмешался в соединение
- Сервер завершил соединение из-за ограничений ресурсов или ошибок
- Межсетевое устройство сбросило простаивающее соединение
- Изменение сетевого состояния привело к сбросу существующего соединения

Важно: обычное корректное завершение TCP-соединения через `FIN` не эквивалентно сбросу через `RST`.

Также не следует путать `ERR_CONNECTION_RESET` с `ERR_CONNECTION_TIMED_OUT`: при timeout соединение не получает ожидаемого ответа за установленное время, тогда как reset означает его аварийное прекращение.

# Чем DNS-запрос отличается от HTTP-запроса?

DNS-запрос используется для получения информации о доменном имени, например его IP-адреса.

Пример:

`example.com → 192.0.2.1`

DNS работает на прикладном уровне и обычно использует UDP или TCP на порту `53`. Также существуют защищённые варианты: DNS-over-TLS и DNS-over-HTTPS.

HTTP-запрос используется для получения ресурсов или выполнения операций на веб-сервере.

Пример:

`GET /users HTTP/1.1`

HTTP передаёт методы, заголовки, тело запроса и получает ответы с кодами состояния, заголовками и необязательным телом.

Основное отличие: DNS определяет, как разрешить доменное имя, а HTTP определяет, как клиент взаимодействует с веб-сервером.

Обычно DNS-разрешение предшествует HTTP-запросу, но оно может не выполняться непосредственно перед каждым запросом, если адрес уже известен из кеша или соединение переиспользуется.
