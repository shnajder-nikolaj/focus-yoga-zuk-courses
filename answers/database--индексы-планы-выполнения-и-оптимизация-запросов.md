# Как B-tree index ускоряет поиск и почему он увеличивает стоимость записи?

B-tree хранит упорядоченную структуру ключей, позволяя находить нужный диапазон и часто поддерживать сортировку без полного чтения таблицы. Польза зависит от доли выбираемых строк и стоимости доступа к самим данным.

При insert/update/delete индекс тоже обслуживается: расходуются CPU, I/O, WAL и место, возможны page splits. Поэтому индекс не является бесплатным ускорением всех запросов. Для чтения большой доли таблицы sequential scan может быть дешевле, чем множество переходов через индекс.

# Как composite index использует порядок колонок при equality, range и ORDER BY?

Для B-tree порядок колонок определяет, какие equality-условия и первый range эффективно ограничивают участок чтения и какую сортировку даёт scan. Например, `(tenant_id, created_at, id)` часто подходит для tenant-фильтра и упорядоченной истории.

Правило leading columns не является абсолютным запретом использовать остальные: PostgreSQL 18 поддерживает предусмотренный planner skip scan при подходящем распределении. Решение проверяют планом, учитывая predicates, sort direction и cardinality. Просто поставить «самое уникальное поле первым» недостаточно. [Multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html).

# Как partial, expression и covering indexes отличаются по применению?

**Partial index** хранит только строки, удовлетворяющие predicate, например активные записи; запрос должен позволять planner доказать применимость этого условия. **Expression index** хранит результат выражения, например `lower(email)`.

**Covering index** содержит дополнительные данные для подходящего чтения, в PostgreSQL часто через `INCLUDE`, уменьшая необходимость обращаться к heap. Каждый вариант увеличивает стоимость записи и размер. Совпадение выражения, null semantics и параметры запроса проверяют на реальном плане. [Partial](https://www.postgresql.org/docs/current/indexes-partial.html), [expression indexes](https://www.postgresql.org/docs/current/indexes-expressional.html).

# Когда Hash, GIN, GiST или BRIN index уместны на примере PostgreSQL?

Hash index в PostgreSQL предназначен для equality-поиска. GIN полезен для подходящих многозначных данных и operators, например containment в jsonb или полнотекстового поиска. GiST предоставляет framework для поддерживаемых задач, включая геометрию и диапазоны.

BRIN хранит сводки по физическим блокам и может быть эффективен для больших таблиц с корреляцией значения и порядка хранения. Выбирают также operator class и extension, если нужна. Название типа индекса не гарантирует поддержку любого выражения. [Index types PostgreSQL](https://www.postgresql.org/docs/current/indexes-types.html).

# Как selectivity, cardinality и statistics влияют на выбор плана запроса?

Planner оценивает число строк и стоимость операций по statistics и модели ресурсов. Selectivity показывает долю подходящих данных, cardinality — количество различных значений или ожидаемых строк в конкретном контексте.

Устаревшая статистика, сильная корреляция колонок и skew способны дать неверные оценки и плохой JOIN order. Проверяют `ANALYZE`, распределение и при необходимости extended statistics. Само расхождение estimate не всегда критично: важно, привело ли оно к дорогому выбору. Индекс не обязан использоваться, если scan дешевле.

# Чем EXPLAIN отличается от EXPLAIN ANALYZE и какие риски есть при выполнении запроса?

`EXPLAIN` строит план с оценками без обычного выполнения запроса. `EXPLAIN ANALYZE` действительно запускает его и добавляет фактические измерения; `BUFFERS` помогает исследовать работу с блоками.

Для изменяющего или тяжёлого запроса это реальная нагрузка и возможные изменения данных. Транзакция с rollback не отменяет любой внешний эффект, например действие вызываемого кода. Используют контролируемую среду и данные, понимая ограничения. Planner cost имеет условные единицы и не равен миллисекундам. [Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html).

# Как читать estimated rows, actual rows, loops и время узлов execution plan?

Сравнивают estimated и actual rows, чтобы найти неверную оценку, затем учитывают `loops`: часто actual rows/time показываются в среднем на одно выполнение узла. Маленькое число строк при большом числе loops может означать огромную общую работу.

Время родителя может включать потомков, поэтому его нельзя просто сложить по всему дереву. Изучают filters, rows removed, buffers, sort и spill вместе. Узел с наибольшим видимым временем не всегда является первопричиной: она может быть в неверном JOIN order или повторных обращениях.

# Как nested loop, hash join и merge join отличаются по требованиям к данным?

Nested loop запускает внутренний путь для строк внешнего; он хорош для небольшого внешнего набора и дешёвого indexed lookup, но опасен при ошибочно большой cardinality. Hash join строит hash table и подходит equality-сопоставлению, требуя памяти и иногда spill.

Merge join использует упорядоченные входы и может потребовать предварительной сортировки. Выбор зависит от объёма, predicates, ordering и ресурсов. Нельзя объявить один алгоритм всегда быстрым: сначала проверяют оценки и форму доступа к каждому входу.

# Почему функции, приведения типов и шаблоны поиска могут мешать использованию индекса?

Если условие применяет функцию к колонке, обычный индекс исходного значения может не соответствовать выражению. Неявный cast, collation, operator class и форма шаблона также меняют доступные пути.

Например, `lower(email)` может использовать expression index, а leading-wildcard поиск часто требует специализированного механизма вместо обычного B-tree. Иногда условие можно выразить диапазоном исходных значений без изменения смысла, особенно аккуратно для времени. Проверяют фактическое преобразование, не считая любую функцию безусловным запретом индекса.

# Как сортировка, pagination и index-only scan влияют на объём работы БД?

Подходящий index order позволяет избежать отдельной сортировки и рано завершить чтение для `LIMIT`. Большой `OFFSET` всё равно может требовать пройти пропускаемые записи; keyset pagination переносит продолжение в условие диапазона.

Index-only scan требует нужных данных в индексе и поддерживаемого access method. В PostgreSQL проверка MVCC visibility также зависит от visibility map, поэтому heap fetches могут оставаться даже у covering index. Смотрят реальный план и состояние обслуживания таблицы. [Index-only scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html).

# Как выявлять лишние индексы и создавать новый индекс с учётом блокировок?

Сравнивают usage за представительский период, размер, стоимость записи и пересечение с другими индексами. Учитывают reset статистики, редкие важные запросы, replicas и роль индекса в constraints; нулевой `idx_scan` сам по себе не является основанием удаления.

Создание тоже нагружает систему. В PostgreSQL `CREATE INDEX CONCURRENTLY` уменьшает блокировку обычных writes, но имеет ограничения и может оставить невалидный индекс при неудаче. Проверяют статус, I/O, свободное место и процедуру восстановления. [CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html).

# Как проверять SQL-оптимизацию на реальных данных без ухудшения других запросов?

Сохраняют результаты и планы исходного запроса, выбирают representative parameters и данные, затем меняют одну существенную причину и сравнивают latency, buffers, rows и нагрузку. Проверяют как прогретый, так и нужный холодный сценарий.

Новый индекс или переписанный JOIN может ускорить один endpoint и замедлить writes или другие планы. Поэтому оценивают общий workload, хвост задержек и correctness. Производственные проверки проводят с ограниченным риском и наблюдением, а не запускают тяжёлый эксперимент без бюджета ресурсов.
