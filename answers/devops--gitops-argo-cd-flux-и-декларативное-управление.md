# Какие принципы OpenGitOps отличают GitOps от хранения deployment scripts в Git?

OpenGitOps задаёт четыре принципа: **декларативное desired state**, его версионированное и неизменяемое хранение, автоматическое получение агентами и непрерывное согласование с фактическим состоянием.

Скрипт `kubectl apply` в Git сам по себе не обеспечивает GitOps: если его запускают один раз и больше не сравнивают состояние, drift останется незамеченным. Репозиторий фиксирует желаемый результат и историю изменения намерений; контроллер выполняет reconciliation. Доступ к репозиторию становится частью управления production и требует соответствующих правил review. [Принципы OpenGitOps](https://opengitops.dev/).

# Как reconciliation loop сравнивает desired state с live state и исправляет drift?

Контроллер получает описание **desired state**, наблюдает **live state**, вычисляет различия и выполняет действия, приближающие систему к желаемому состоянию. Цикл повторяется по расписанию и событиям, поэтому восстанавливается после временных ошибок.

Изменение, сделанное вручную, может быть отменено, если входит в область управления контроллера и включено соответствующее исправление drift. Не все поля должны принадлежать Git: например, число реплик может регулировать autoscaler. Владение полями, исключения сравнения и mutating webhooks согласуют заранее, иначе несколько контроллеров способны бесконечно перезаписывать друг друга.

# Как разделить обязанности CI и GitOps-контроллера при выпуске новой версии?

**CI** проверяет код, собирает и публикует артефакт, затем предлагает изменение desired state с новым digest, например pull request в deployment-репозиторий. После review это изменение становится разрешённой версией окружения.

**GitOps-контроллер** получает состояние и применяет его в кластере, проверяя результат и последующий drift. CI при такой схеме не обязан иметь прямой административный доступ к production. Доступ к registry, репозиторию и Kubernetes API распределяют отдельно. Автообновление образов должно оставлять управляемую запись о том, какая версия и почему продвинута.

# Как Application, Project и ApplicationSet организуют управление приложениями в Argo CD?

`Application` связывает источник manifests, Helm chart или другого описания с целевым кластером, namespace и sync policy. **Project**, представленный ресурсом `AppProject`, группирует приложения и ограничивает допустимые repositories, destinations и виды ресурсов.

`ApplicationSet` генерирует набор `Application` по шаблону и generators, например для нескольких кластеров. Поэтому изменение шаблона может затронуть много окружений. Проверяют разрешения Project и область генерации, а не полагаются только на разделение namespaces. Слишком широкий default project ослабляет изоляцию. [Projects Argo CD](https://argo-cd.readthedocs.io/en/stable/user-guide/projects/).

# Как source-controller, kustomize-controller и helm-controller взаимодействуют во Flux?

`source-controller` получает и публикует artifacts источников, например Git repositories или Helm repositories. `kustomize-controller` строит и применяет Kubernetes manifests через ресурс Flux `Kustomization`, а `helm-controller` управляет жизненным циклом релизов через `HelmRelease`.

Контроллеры взаимодействуют через Kubernetes resources, ссылки и status conditions. Отдельный reconciliation каждого слоя помогает повторять операции и видеть, где возник сбой: получение источника, построение или применение. Ресурс Flux `Kustomization` и файл Kustomize `kustomization.yaml` — разные сущности. [Основные понятия Flux](https://fluxcd.io/flux/concepts/).

# Как auto-sync, self-heal и prune в Argo CD влияют на ручные изменения и удаление ресурсов?

**Auto-sync** автоматически применяет расхождение с источником при выполнении условий политики. `selfHeal` включает автоматическое исправление подходящего drift в live state. `prune` разрешает удалять управляемые ресурсы, исчезнувшие из desired state.

В Argo CD pruning и self-healing не следует считать автоматически включёнными вместе с базовым auto-sync. `allowEmpty` отдельно регулирует защиту при пустом наборе желаемых ресурсов. Политики проверяют в установленной версии; неверный путь к manifests с разрешённым массовым удалением особенно опасен. [Automated Sync Policy](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/).

# Почему Synced и Healthy отражают разные свойства приложения?

**Synced** означает, что сравниваемая конфигурация live resources соответствует desired state с учётом правил diff. **Healthy** отражает оценку рабочего состояния ресурсов, например готовность Deployment по известным контроллеру правилам.

Приложение может быть Synced, но иметь неготовые Pods; может обслуживать пользователей, оставаясь OutOfSync после ручного изменения. Даже Healthy не подтверждает корректность оплаты или другого бизнес-сценария. Для custom resources могут понадобиться отдельные health checks, а после синхронизации нужны наблюдение метрик и функциональные проверки.

# Как организовать репозитории, overlays и продвижение версий между GitOps-окружениями?

Репозитории делят по границам доступа и ответственности; приложения, окружения и кластеры могут находиться в одном или нескольких repositories. Общую основу дополняют небольшими overlays или Helm values, избегая копирования всей конфигурации.

Продвижение фиксирует уже проверенный digest, а не пересобирает код для каждого окружения. Review должен показывать итоговые manifests и изменение значимых параметров. Параметры окружений и версии зависимостей делают явными. Слишком сложная генерация скрывает фактическое desired state и усложняет аудит; monorepo и несколько repositories имеют разные компромиссы, универсального формата нет.

# Как управлять секретами в GitOps с помощью SOPS или внешнего secret manager?

**SOPS** позволяет хранить зашифрованные значения в Git; контроллер получает право расшифрования через KMS или другой ключевой механизм. Во Flux расшифрование настраивают для `Kustomization`. Ключи не помещают рядом с ciphertext и ограничивают круг identities, способных ими пользоваться.

При внешнем secret manager в Git хранят ссылки и политики, а отдельный механизм получает секрет в runtime. Проверяют, где появляется plaintext: в Kubernetes API, памяти, логах и резервных копиях. Шифрование Git-файла не заменяет RBAC, ротацию и защиту хранилища кластера. [Flux и SOPS](https://fluxcd.io/flux/guides/mozilla-sops/).

# Как sync waves, hooks и dependsOn помогают учитывать зависимости ресурсов?

В Argo CD **sync waves** задают очередность групп ресурсов, а **hooks** выполняют действия в фазах синхронизации, например предварительную проверку. Во Flux `dependsOn` позволяет отложить reconciliation `Kustomization` до готовности зависимой `Kustomization`.

Порядок создания не равен готовности бизнес-сервиса: нужны корректные health checks и совместимость версий. Миграцию в hook делают безопасной для повторного выполнения и отдельно учитывают её необратимые эффекты. Циклические зависимости блокируют прогресс; строгая последовательность всех компонентов без необходимости замедляет восстановление. [Argo CD waves и hooks](https://argo-cd.readthedocs.io/en/stable/user-guide/sync-waves/), [Flux dependencies](https://fluxcd.io/flux/components/kustomize/kustomizations/#dependencies).

# Как выполнить аварийное ручное изменение или rollback, не вступая в конфликт с reconciliation?

Предпочтительный rollback — проверенное изменение desired state в Git на совместимую предыдущую версию. Контроллер получает его обычным reconciliation. Git revert не отменяет миграции данных и внешние эффекты новой версии.

Для срочного ручного вмешательства временно приостанавливают соответствующее согласование на правильном уровне, фиксируют причину, меняют состояние и затем переносят итог в Git. У приложений, управляемых ApplicationSet, настройки дочернего Application могут быть перезаписаны. В Argo CD операция rollback из истории приложения недоступна при включённом auto-sync; это отличается от изменения версии через Git. [Политика auto-sync](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/).

# Как восстановить GitOps-управление после потери кластера и ограничить полномочия контроллеров?

Готовят bootstrap минимального контроллера, доступ к репозиторию, registry и ключам расшифрования, затем восстанавливают инфраструктурные зависимости и приложения. Git описывает ресурсы, но обычно не содержит актуальные данные persistent volumes, внешних БД и secret manager — их восстанавливают отдельными процедурами.

Контроллеры и service accounts получают права только на нужные clusters, namespaces и типы ресурсов. При multi-tenancy ограничивают доступ к sources и возможность создавать привилегированные workloads. Учение проводят с чистым кластером и проверяют весь пользовательский путь: наличие manifests в Git ещё не означает готовность к восстановлению.
