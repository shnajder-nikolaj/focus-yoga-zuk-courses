# Что такое compound components и когда они удобны?

Compound Components - паттерн проектирования, при котором несколько связанных компонентов образуют единый интерфейс и совместно управляют состоянием и поведением.

Вместо одного компонента с большим количеством пропсов используются специализированные подкомпоненты.

```
<Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Trigger value="profile">Профиль</Tabs.Trigger>
    <Tabs.Trigger value="settings">Настройки</Tabs.Trigger>
  </Tabs.List>

  <Tabs.Content value="profile">Профиль</Tabs.Content>
  <Tabs.Content value="settings">Настройки</Tabs.Content>
</Tabs>
```

Принцип работы:

- Родительский компонент управляет общим состоянием.
- Подкомпоненты получают доступ к состоянию и действиям через `Context` или переданные пропсы.
- Потребитель самостоятельно определяет структуру и расположение элементов.

Когда удобны:

- Компонент состоит из нескольких логически связанных частей.
- Требуется гибкая композиция без большого количества пропсов.
- Несколько элементов должны согласованно управлять общим состоянием.

Типичные примеры: `Tabs`, `Accordion`, `Select`, `Menu`, `Dialog`.

Основной недостаток - усложнение внутренней реализации, особенно управления состоянием, доступностью и взаимодействием подкомпонентов.

# Что такое headless components?

Headless Components - компоненты или хуки, которые реализуют поведение и управление состоянием, но не навязывают конкретную визуальную структуру и стили.

Они могут предоставлять:

- Состояние и методы его изменения.
- Обработчики событий.
- Атрибуты доступности (`ARIA`).
- Управление фокусом и клавиатурной навигацией.

Например, `useSelect()` может управлять выбранным значением, открытием списка и навигацией по вариантам, а внешний компонент самостоятельно определяет разметку и стили.

Преимущества:

- Независимость логики от внешнего вида.
- Возможность использовать одну реализацию поведения в разных дизайн-системах.
- Упрощение тестирования логики.
- Большая свобода кастомизации.

Недостаток - потребитель должен самостоятельно реализовать представление и корректно применить предоставленные свойства.

Headless-подход особенно полезен при разработке UI-библиотек и дизайн-систем. Примеры: `Radix Primitives`, `React Aria`, `Headless UI`.

# Как разделять логику, представление и получение данных в компоненте?

Разделение строится вокруг трёх зон ответственности:

1. Получение данных - запросы к API, кэширование, загрузка, ошибки и обновление данных.
2. Логика - обработка пользовательских действий, вычисление производного состояния, правила взаимодействия.
3. Представление - отображение данных и генерация событий.

Пример организации:

```
function useUser(id: string) {
  return useQuery({
    queryKey: ["user", id],
    queryFn: () => userApi.getById(id),
  });
}

function useUserProfile(id: string) {
  const query = useUser(id);

  return {
    ...query,
    displayName: query.data?.name.trim() ?? "",
  };
}

function UserProfileView({ name }: { name: string }) {
  return <h2>{name}</h2>;
}

function UserProfile({ id }: { id: string }) {
  const { data, isPending, isError, displayName } =
    useUserProfile(id);

  if (isPending) return <Loader />;
  if (isError) return <ErrorMessage />;

  return <UserProfileView name={displayName} />;
}
```

Здесь:

- `useUser` отвечает за серверные данные.
- `useUserProfile` подготавливает данные для интерфейса.
- `UserProfileView` отвечает только за отображение.
- `UserProfile` связывает слои и обрабатывает состояния загрузки и ошибок.

Бизнес-правила, не зависящие от React, лучше выносить в обычные TypeScript-функции или сервисы.

Важно: разделение не обязательно означает отдельный файл для каждого слоя. Простая локальная логика может оставаться внутри компонента. Выделять абстракции стоит тогда, когда это улучшает читаемость, тестируемость или повторное использование.

# Что такое HOC и где он всё ещё полезен?

Higher-Order Component (HOC) - функция, которая принимает React-компонент и возвращает новый компонент с дополнительным поведением.

```
function withLoading<P extends object>(
  Component: React.ComponentType<P>
) {
  return function Wrapped(
    props: P & { isLoading: boolean }
  ) {
    const { isLoading, ...rest } = props;

    if (isLoading) return <Loader />;

    return <Component {...(rest as P)} />;
  };
}
```

HOC реализует композицию компонентов, позволяя добавлять общее поведение без изменения исходного компонента.

Где полезен:

- Поддержка существующих библиотек и legacy-кода.
- Добавление общей обёртки к нескольким компонентам.
- Интеграция со сторонними API, предоставляющими HOC.
- Реализация функциональности, которую удобнее выразить на уровне компонента, а не хука.

Недостатки:

- Дополнительные уровни вложенности в React DevTools.
- Возможные конфликты имён пропсов.
- Усложнение типизации.
- Необходимость учитывать передачу `ref` и статических свойств.

В современном React повторно используемую логику состояния чаще выделяют в кастомные хуки. Однако хуки не заменяют HOC полностью: HOC может изменять саму структуру рендеринга.

# В каких случаях применяют render props?

Render Props - паттерн, при котором компонент получает функцию через пропс и вызывает её для формирования UI.

Функция получает данные или методы от компонента и возвращает React-элементы.

```
<MouseTracker>
  {({ x, y }) => (
    <p>
      X: {x}, Y: {y}
    </p>
  )}
</MouseTracker>
```

`MouseTracker` управляет отслеживанием координат, но не определяет, как они должны отображаться.

Применяют, когда:

- Нужно передать потребителю управление отображением.
- Один компонент предоставляет состояние нескольким вариантам интерфейса.
- Необходимо реализовать гибкий API для динамического содержимого.
- Используется библиотека, предоставляющая render props.

В отличие от обычного `children`, render prop позволяет передать в функцию актуальные данные компонента.

Недостатки - дополнительная вложенность JSX и создание функции при каждом рендере, что может влиять на мемоизацию дочерних компонентов.

Для повторного использования логики в функциональных компонентах обычно удобнее кастомные хуки. Render props остаются полезны, когда требуется именно гибкая настройка рендеринга через API компонента.

# Как проектировать API переиспользуемого компонента?

API компонента - набор пропсов, событий, методов и правил поведения, через которые другие части приложения взаимодействуют с ним.

Основные принципы:

1. Предсказуемость. Названия и поведение пропсов должны соответствовать привычным React-соглашениям: `value`, `defaultValue`, `onValueChange`, `disabled`.
2. Минимальность. Предоставлять только необходимые возможности, не добавляя настройки на каждый потенциальный случай.
3. Композиция. Для гибкого содержимого использовать `children`, слоты или compound components.
4. Контролируемость. Если состояние должно управляться извне, предусмотреть контролируемый API.
5. Типобезопасность. Использовать TypeScript, объединения типов и ограничения для недопустимых комбинаций пропсов.
6. Доступность. Поддерживать корректную HTML-семантику, клавиатуру, `ARIA` и `ref`.
7. Совместимость. По возможности использовать привычные имена и поведение нативных элементов.

Пример:

```
type ButtonProps =
  React.ComponentPropsWithRef<"button"> & {
    variant?: "primary" | "secondary";
    size?: "sm" | "md" | "lg";
    loading?: boolean;
  };
```

Компонент наследует стандартные свойства `<button>` и добавляет только собственные настройки.

Главный критерий: потребитель должен понимать, как использовать компонент, без знания его внутренней реализации.

Хороший API ограничивает недопустимые состояния, но не мешает обычным сценариям использования.

# Как строить контролируемые модальные окна, вкладки и выпадающие списки?

Основной принцип - Single Source of Truth: для каждого состояния должен существовать один источник истины.

В контролируемом компоненте значение хранится у родителя, а дочерний компонент получает его и сообщает о необходимых изменениях через callback.

```
function Example() {
  const [open, setOpen] = useState(false);

  return (
    <Dialog
      open={open}
      onOpenChange={setOpen}
    >
      <Dialog.Trigger>Открыть</Dialog.Trigger>
      <Dialog.Content>Содержимое</Dialog.Content>
    </Dialog>
  );
}
```

Здесь `Dialog` не должен самостоятельно изменять переданный `open`. При необходимости закрытия он вызывает `onOpenChange(false)`, а родитель решает, обновлять ли состояние.

Типичный API:

- Модальные окна: `open`, `defaultOpen`, `onOpenChange`.
- Вкладки: `value`, `defaultValue`, `onValueChange`.
- Выпадающие списки: `open`, `onOpenChange`, `value`, `onValueChange` - если есть выбор значения.

Для поддержки обоих режимов можно реализовать компонент с внутренним состоянием:

- Controlled: передан `value` или `open`, состояние задаёт родитель.
- Uncontrolled: используется `defaultValue` или `defaultOpen`, состояние хранит компонент.

Важно корректно различать отсутствие пропса и допустимые значения вроде `false` или пустой строки. Не следует переключать режим управления во время жизненного цикла компонента.

Также необходимо учитывать доступность: управление фокусом, клавиатурную навигацию, `ARIA`, закрытие через `Escape` и согласованность визуального состояния.

# Как построить компонент с поддержкой `ref` и пользовательских атрибутов?

Компонент должен принимать стандартные свойства соответствующего HTML-элемента и передавать `ref` нужному DOM-узлу.

В React 19+ функциональные компоненты могут получать `ref` как обычный пропс.

```
type InputProps =
  React.ComponentPropsWithRef<"input"> & {
    label: string;
  };

function Input({ label, ref, ...props }: InputProps) {
  const id = useId();

  return (
    <label>
      {label}
      <input
        {...props}
        id={props.id ?? id}
        ref={ref}
      />
    </label>
  );
}
```

Такой компонент поддерживает:

- Стандартные атрибуты: `type`, `name`, `required`, `disabled`.
- Пользовательские атрибуты: `data-*`, `aria-*`.
- События: `onChange`, `onBlur`, `onFocus`.
- Передачу `ref` для доступа к DOM-элементу.

Для React 18 и более ранних версий используется `React.forwardRef()`.

Если требуется предоставить только определённые операции вместо прямого доступа к DOM, можно использовать `useImperativeHandle()`.

Важный момент: порядок распространения пропсов через `{...props}` определяет, какие значения имеют приоритет. При необходимости компонент должен объединять собственные и пользовательские обработчики, а не случайно перезаписывать их.&#x20;

# Чем компонентная композиция предпочтительнее глубокой иерархии наследования?

Композиция позволяет собирать сложные компоненты из небольших независимых частей через `children`, пропсы и вложенность JSX.

```
function Card({ children }: React.PropsWithChildren) {
  return <section className="card">{children}</section>;
}

<Card>
  <CardHeader />
  <CardContent />
  <CardActions />
</Card>
```

В отличие от наследования, компоненты не обязаны расширять базовые классы и зависеть от их внутренних методов.

Преимущества композиции:

- Меньшая связанность компонентов.
- Независимая замена и тестирование частей.
- Повторное использование без сложной иерархии классов.
- Более явный поток данных через пропсы.
- Отсутствие проблем переопределения методов базовых классов.

Глубокое наследование создаёт сильную зависимость дочерних классов от деталей реализации родителей. Изменение базового класса может неожиданно повлиять на множество наследников.

React изначально ориентирован на композицию. Даже при использовании классов наследование обычно ограничивается `React.Component`, а повторное использование поведения организуется другими механизмами.

# Как организовать compound-компоненты с Context без лишних рендеров?

Compound-компоненты часто используют `Context` для передачи общего состояния без явной передачи пропсов на каждом уровне.

```
const TabsContext = createContext<TabsContextValue | null>(
  null
);

function Tabs({ children }: PropsWithChildren) {
  const [activeTab, setActiveTab] = useState("first");

  const contextValue = useMemo(
    () => ({ activeTab, setActiveTab }),
    [activeTab]
  );

  return (
    <TabsContext.Provider value={contextValue}>
      {children}
    </TabsContext.Provider>
  );
}
```

Проблема в том, что при изменении значения Context все компоненты, читающие этот Context, могут перерендериться, даже если используют только часть значения.

Для оптимизации:

1. Стабилизировать значение Context. Использовать `useMemo` и при необходимости `useCallback`, чтобы не создавать новые ссылки без изменения данных.
2. Разделять контексты. Например, `TabsStateContext` для состояния и `TabsActionsContext` для методов.
3. Локализовать состояние. Не помещать все состояния подкомпонентов в один общий Context.
4. Использовать селекторы. Для сложного состояния применять внешнее хранилище с подпиской на отдельные значения или подходящие библиотеки с context selectors.
5. Применять `React.memo` там, где это оправдано. Он помогает пропускать рендеры при неизменных пропсах, но не предотвращает обновления компонента, который непосредственно читает изменившийся Context.

Важно понимать, что `useMemo` устраняет лишние обновления из-за изменения ссылок, но не предотвращает рендеры при реальном изменении состояния.

Оптимизировать Context следует на основании профилирования: для небольшого числа подкомпонентов обычного Context часто достаточно.&#x20;

# Как поддерживать обратную совместимость API библиотеки компонентов?

Обратная совместимость означает, что существующий код потребителей продолжает работать после обновления библиотеки без обязательных изменений.

Основные подходы:

1. Сохранять публичные контракты. Не менять без необходимости имена пропсов, типы, события, значения по умолчанию и ожидаемое поведение.
2. Использовать SemVer. Исправления выпускать в `patch`, обратно совместимые возможности - в `minor`, несовместимые изменения - в `major`.
3. Постепенно устаревать API. Помечать старые возможности через `@deprecated`, документировать замену и предоставлять переходный период.
4. Поддерживать адаптеры. Временно преобразовывать старые пропсы в новый API.
5. Тестировать публичное поведение. Проверять не только рендеринг, но и взаимодействия, доступность, типы и совместимость с поддерживаемыми версиями React.
6. Предоставлять инструкции миграции. Для крупных изменений использовать changelog, migration guides и codemods.

Например, при замене `isOpen` на `open` можно временно поддерживать оба пропса, заранее определив их приоритет и поведение при одновременной передаче.

Важно: несовместимость может возникнуть не только при изменении TypeScript-типов. Изменения DOM-структуры, CSS-классов, поведения клавиатуры и порядка вызовов событий тоже способны сломать существующие интеграции.

# Как избежать чрезмерного количества boolean props?

Большое количество boolean props создаёт множество комбинаций состояний, часть которых может быть бессмысленной или противоречивой.

Например:

```
<Button
  primary
  secondary
  danger
  outlined
/>
```

Непонятно, какой стиль должен иметь приоритет.

Способы решения:

1\. Использовать варианты вместо нескольких флагов.

```
<Button variant="primary" size="lg" />
```

2. Применять discriminated unions. TypeScript позволяет описывать взаимоисключающие состояния и ограничивать недопустимые комбинации.
3. Использовать композицию. Вместо множества настроек содержимого передавать `children`, слоты или compound components.
4. Разделять разные сценарии. Если режимы существенно отличаются по поведению, иногда лучше создать отдельные компоненты.

При этом boolean props сами по себе не являются проблемой.

`disabled`, `required`, `readOnly`, `loading` - понятные независимые состояния, для которых boolean подходит естественным образом.

Критерий: если комбинации флагов трудно объяснить, проверить или типизировать, API стоит пересмотреть.

# Когда лучше разделять крупный компонент на подкомпоненты?

Компонент стоит разделять, когда внутри него появляются несколько независимых зон ответственности.

Основные признаки:

- Компонент содержит несколько самостоятельных частей интерфейса.
- Разные части имеют собственное состояние и обработчики.
- Логику сложно тестировать изолированно.
- Изменение одной функциональности регулярно затрагивает несвязанные участки.
- Большие условные блоки затрудняют понимание рендеринга.
- Части интерфейса могут повторно использоваться.
- Требуется изолировать обновления ресурсоёмких частей UI.

Например, страницу профиля можно разделить на:

```
function ProfilePage() {
  return (
    <ProfileLayout>
      <ProfileHeader />
      <ProfileDetails />
      <ProfileSettings />
    </ProfileLayout>
  );
}
```

При этом разделять компонент исключительно из-за количества строк не обязательно.

Хорошая граница разделения - самостоятельная ответственность, понятный API и возможность понимать подкомпонент независимо от остальной реализации.

Избыточное дробление тоже вредно: оно увеличивает количество файлов, переходов между ними и связей через пропсы.

# Как применять SOLID в React и TypeScript без избыточной абстракции?

SOLID - пять принципов проектирования, помогающих уменьшать связанность кода и упрощать его изменение.

В React их можно применять следующим образом.

1\. Single Responsibility Principle (SRP)

Компонент должен иметь одну основную ответственность.

Например, `UserList` отображает пользователей, а `useUsers` управляет их загрузкой.

Не обязательно выносить каждый обработчик в отдельный хук. Важно разделять независимые причины изменений.

2\. Open/Closed Principle (OCP)

Компонент должен допускать расширение поведения без постоянного изменения своей реализации.

В React это достигается через `children`, композицию, слоты и конфигурационные пропсы.

Например, универсальный `Dialog` позволяет передавать произвольное содержимое, а не содержит отдельную ветку условий для каждого сценария.

3\. Liskov Substitution Principle (LSP)

Компонент или реализация, используемые вместо другой, должны сохранять ожидаемый контракт.

Например, кастомный `Button`, предоставляющий API обычной кнопки, должен корректно поддерживать `disabled`, `onClick`, `ref` и клавиатурное взаимодействие.

4\. Interface Segregation Principle (ISP)

Потребители не должны зависеть от интерфейсов, которые им не нужны.

Вместо большого типа с десятками несвязанных настроек полезно создавать небольшие интерфейсы и объединять их по необходимости.

5\. Dependency Inversion Principle (DIP)

Высокоуровневая логика не должна жёстко зависеть от конкретной реализации инфраструктуры.

Например, бизнес-логика может зависеть от интерфейса `UserRepository`, а конкретная реализация выполняет HTTP-запросы.

Это позволяет менять источник данных и тестировать логику независимо от сети.

Главное правило: применять SOLID для решения реальных проблем связанности и сложности, а не создавать интерфейсы, фабрики и дополнительные слои для каждого компонента.

# Как проектировать error boundaries и обработку ошибок между слоями?

Error Boundary - React-компонент, который перехватывает ошибки рендеринга дочернего дерева и отображает запасной интерфейс (`fallback`) вместо повреждённой части UI.

В React Error Boundary реализуется через классовый компонент с `getDerivedStateFromError` и/или `componentDidCatch`. Также можно использовать библиотеку `react-error-boundary`.

Обработку ошибок лучше разделять по слоям.

1\. Слой получения данных

Обрабатывает сетевые ошибки, таймауты, ошибки авторизации и некорректные ответы сервера.

Например, TanStack Query предоставляет `isError`, `error` и механизмы повторных запросов.

Ожидаемые ошибки обычно преобразуются в понятные состояния интерфейса.

2\. Бизнес-логика

Обрабатывает ожидаемые нарушения бизнес-правил.

Например, невозможность выполнить операцию из-за недостаточного баланса не обязательно должна приводить к срабатыванию Error Boundary.

Такие ситуации лучше представлять типизированными результатами или доменными ошибками.

3\. React UI

Error Boundary перехватывает неожиданные ошибки дочерних компонентов во время рендеринга и поддерживаемых фаз жизненного цикла.

Границы размещают вокруг независимых частей приложения: страниц, маршрутов, виджетов или сложных функциональных блоков.

При ошибке пользователь должен видеть понятный `fallback` и, когда это возможно, иметь возможность повторить действие.

4\. Глобальная обработка

Используется для логирования, мониторинга и диагностики необработанных ошибок.

В React 19 доступны обработчики `onCaughtError`, `onUncaughtError` и `onRecoverableError` при создании корня приложения.

Ограничения Error Boundary:

- Не перехватывает обычные ошибки в обработчиках событий.
- Не перехватывает произвольные ошибки асинхронных callback-функций.
- Не обрабатывает ошибки серверного рендеринга обычным клиентским механизмом.
- Не перехватывает собственные ошибки.

Исключение - некоторые ошибки, выброшенные внутри функции `startTransition`, могут обрабатываться Error Boundary.

Для ошибок событий и асинхронных операций нужны отдельные механизмы обработки.

Важно: ожидаемые бизнес-ошибки не следует автоматически превращать в ошибки рендеринга. Error Boundary предназначен прежде всего для изоляции неожиданных сбоев UI.&#x20;

# Как выделить границы ответственности между React UI и бизнес-логикой?

Главный принцип - бизнес-правила не должны зависеть от React и способа отображения данных.

Ответственность можно разделить следующим образом.

React UI:

- Отображение данных.
- Обработка пользовательских событий.
- Управление визуальным состоянием.
- Фокус, анимации, доступность.
- Вызов операций приложения.

Бизнес-логика:

- Проверка бизнес-правил.
- Расчёты.
- Определение допустимых операций.
- Преобразование доменных данных.
- Выполнение бизнес-сценариев.

Инфраструктура:

- HTTP-запросы.
- Работа с хранилищами.
- Интеграции с внешними сервисами.

Пример бизнес-функции:

```
type Order = {
  total: number;
  status: "new" | "paid";
};

function canCancelOrder(order: Order): boolean {
  return order.status === "new";
}
```

React-компонент использует результат:

```
function OrderActions({ order }: { order: Order }) {
  return (
    <button disabled={!canCancelOrder(order)}>
      Отменить заказ
    </button>
  );
}
```

Функцию `canCancelOrder` можно тестировать без React.

Для сложных сценариев между UI и доменной логикой может существовать слой приложения, который координирует запросы, бизнес-операции и обновление состояния.

При этом UI-логика может оставаться в компонентах или хуках. Например, управление открытием меню или активной вкладкой не требует отдельного бизнес-сервиса.

Такое разделение упрощает тестирование, повторное использование бизнес-правил и изменение интерфейса без переписывания доменной логики.

# Как безопасно вывести HTML, полученный из внешнего источника?

По умолчанию React экранирует текстовые значения внутри JSX.

```
<div>{externalContent}</div>
```

Если `externalContent` содержит строку `<script>alert(1)</script>`, она будет отображена как текст, а не интерпретирована как HTML.

Поэтому если HTML-разметка не нужна, безопаснее использовать обычный текстовый вывод.

Если разметку необходимо сохранить, требуется очистка HTML - санитизация.

Например, с использованием DOMPurify:

```
import DOMPurify from "dompurify";

function HtmlContent({ html }: { html: string }) {
  const sanitized = DOMPurify.sanitize(html);

  return (
    <div
      dangerouslySetInnerHTML={{
        __html: sanitized,
      }}
    />
  );
}
```

Санитизация должна удалять опасные конструкции:

- Обработчики событий вроде `onerror` и `onclick`.
- Опасные URL-схемы, например `javascript:`.
- Потенциально исполняемую разметку и другие XSS-векторы.

Дополнительные меры:

- Использовать проверенную библиотеку, а не регулярные выражения.
- Ограничивать допустимые HTML-теги и атрибуты.
- Не изменять очищенный HTML небезопасными преобразованиями после санитизации.
- Использовать Content Security Policy (`CSP`) как дополнительный уровень защиты.
- При серверной санитизации учитывать безопасность и актуальность DOM-окружения библиотеки.

Важно: санитизация HTML не гарантирует безопасность при последующем использовании результата в других контекстах, например внутри JavaScript или CSS.

Для каждого контекста вывода действуют собственные правила безопасности.&#x20;

# Почему `dangerouslySetInnerHTML` требует особой обработки?

`dangerouslySetInnerHTML` позволяет вставлять HTML-разметку непосредственно в DOM, минуя стандартное экранирование текстового содержимого React.

```
<div
  dangerouslySetInnerHTML={{
    __html: html,
  }}
/>
```

Основной риск - Cross-Site Scripting (XSS).

Если злоумышленник контролирует передаваемую HTML-строку, он может внедрить опасные атрибуты или элементы.

Например:

```
<img src="invalid" onerror="alert('XSS')" />
```

При вставке такого HTML браузер может выполнить обработчик `onerror`.

При этом вставленные через `innerHTML` теги `<script>` обычно не исполняются, но это не делает механизм безопасным: существуют другие способы выполнения вредоносного JavaScript.

Правила безопасного использования:

1. Не передавать непроверенные данные напрямую.
2. Очищать HTML с помощью DOMPurify или аналогичного проверенного санитайзера.
3. По возможности ограничивать допустимые элементы и атрибуты.
4. Использовать Trusted Types при наличии соответствующей политики безопасности.
5. Не применять этот API, если достаточно обычного JSX.

Также `dangerouslySetInnerHTML` нельзя одновременно использовать с `children` у одного DOM-элемента.

Ключевое отличие: React по умолчанию защищает текстовый вывод экранированием, но при использовании `dangerouslySetInnerHTML` ответственность за безопасность вставляемой разметки переходит к разработчику.&#x20;

# Как организовать хранение переводов в React-приложении?

Для локализации React-приложений обычно используют библиотеки вроде `react-i18next`, `FormatJS` или `Lingui`.

Переводы рекомендуется хранить отдельно от компонентов, группируя их по языкам и функциональным областям.

Пример структуры:

```
src/
  locales/
    ru/
      common.json
      auth.json
      profile.json
    en/
      common.json
      auth.json
      profile.json
```

Пример файла `ru/auth.json`:

```
{
  "login": "Войти",
  "logout": "Выйти",
  "welcome": "Привет, {{name}}!"
}
```

Использование с `react-i18next`:

```
function AuthHeader() {
  const { t } = useTranslation("auth");

  return <h1>{t("login")}</h1>;
}
```

Основные принципы организации:

1. Namespaces. Разделять переводы по функциональным областям, чтобы не создавать один огромный словарь.
2. Стабильные ключи. Использовать понятные идентификаторы вместо прямого обращения к тексту как к ключу.
3. Интерполяция. Передавать динамические значения через параметры перевода.
4. Pluralization. Учитывать правила множественного числа конкретного языка.
5. Fallback. Настраивать резервный язык для отсутствующих переводов.
6. Lazy Loading. При необходимости загружать переводы отдельных разделов по требованию.

Для чисел, дат, валют и относительного времени следует использовать `Intl` или подходящие средства библиотеки локализации.

Не рекомендуется собирать предложения из отдельных переведённых слов: порядок слов и грамматические конструкции различаются между языками.

Важно учитывать не только тексты, но и локализацию атрибутов доступности, направление письма (`dir`) и форматирование данных.

# Как распознать God Component и God Hook?

God Component - компонент, который сосредоточил слишком много независимых обязанностей и фактически управляет значительной частью приложения.

God Hook - кастомный хук с аналогичной проблемой: он объединяет множество несвязанных состояний, эффектов и операций.

Основные признаки:

- Большое количество независимых `useState`, `useEffect` и обработчиков.
- Работа сразу с несколькими API или бизнес-сущностями.
- Множество условных сценариев.
- Сильная зависимость от глобального состояния.
- Большое количество возвращаемых значений или пропсов.
- Сложность тестирования отдельных возможностей.
- Изменения в несвязанных функциях регулярно затрагивают один и тот же файл.

Например, хук `useDashboard`, который одновременно управляет авторизацией, фильтрами, загрузкой аналитики, уведомлениями и модальными окнами, вероятно, имеет слишком широкую ответственность.

Как исправлять:

1. Выделять независимую бизнес-логику в обычные функции и сервисы.
2. Разделять хуки по функциональным обязанностям.
3. Выделять самостоятельные части UI в подкомпоненты.
4. Переносить состояние ближе к месту его использования.
5. Оставлять в родительском компоненте координацию между частями.

При этом размер файла и количество строк сами по себе не определяют наличие проблемы.

Основной критерий: если компонент или хук имеет много независимых причин для изменения, его ответственность, вероятно, слишком широка.

# Когда RxJS оправдан в React-приложении?

RxJS - библиотека реактивного программирования для работы с потоками значений и асинхронными событиями через `Observable`.

Она полезна, когда приложение должно координировать сложные последовательности событий во времени.

Типичные сценарии:

- Обработка потоковых данных через WebSocket.
- Объединение событий из нескольких источников.
- Сложные цепочки асинхронных операций.
- Управление отменой и переключением запросов.
- Обработка высокочастотных пользовательских событий.
- Реализация сложных событийных моделей.

Например, для поиска с автодополнением:

```
searchInput$.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(query => searchApi(query))
);
```

Здесь:

- `debounceTime(300)` ожидает паузу во вводе.
- `distinctUntilChanged()` пропускает повторяющиеся значения.
- `switchMap()` переключается на новый внутренний поток и отменяет подписку на предыдущий.

Реальная отмена HTTP-запроса зависит от используемого API и механизма отмены внутри `searchApi`.

Интеграция с React:

React-компонент или кастомный хук подписывается на `Observable` и обновляет состояние при получении новых значений.

Подписки необходимо очищать при размонтировании, обычно через функцию очистки `useEffect`.

При использовании внешнего реактивного хранилища также может применяться `useSyncExternalStore`, если реализован соответствующий контракт подписки и получения снимка состояния.

Когда RxJS избыточен:

- Простые HTTP-запросы.
- Обычное локальное состояние.
- Несколько независимых обработчиков событий.
- Стандартные сценарии серверного кэширования, которые уже решаются TanStack Query или аналогичными инструментами.

RxJS добавляет собственную модель асинхронности, операторы и правила управления подписками.

Он оправдан, когда сложность взаимодействующих событий действительно требует потоковой модели, а обычные хуки и промисы становятся трудными для сопровождения.

# Как реализовать модальное окно с Portal и focus trap?

Модальное окно должно отображаться поверх основного интерфейса, ограничивать взаимодействие с фоновым содержимым и корректно управлять фокусом.

Для реализации используются два механизма.

1\. Portal

`createPortal()` позволяет физически разместить DOM-элементы модального окна вне обычной DOM-иерархии родительского компонента.

```
import { createPortal } from "react-dom";

function Modal({ open, children }: ModalProps) {
  if (!open) return null;

  return createPortal(
    <div className="modal-overlay">
      <div
        role="dialog"
        aria-modal="true"
        aria-label="Диалоговое окно"
      >
        {children}
      </div>
    </div>,
    document.body
  );
}
```

Portal помогает избежать проблем с ограничениями родительских контейнеров, например `overflow: hidden`, и упрощает размещение модального окна поверх страницы.

При этом события React продолжают распространяться по React-дереву, а не по физической DOM-иерархии.

2\. Focus Trap

Focus trap удерживает клавиатурный фокус внутри открытого диалогового окна.

Основной алгоритм:

1. При открытии сохранить элемент, который имел фокус.
2. Переместить фокус на подходящий элемент внутри модального окна.
3. При `Tab` переходить между фокусируемыми элементами внутри модального окна.
4. При `Shift + Tab` поддерживать обратный порядок переходов.
5. Не допускать выхода фокуса за пределы открытого окна.
6. При закрытии восстановить фокус на исходном элементе, если он ещё существует и доступен.

Для полноценной реализации обычно используют готовые механизмы управления фокусом, например `focus-trap` или `focus-trap-react`, поскольку необходимо учитывать динамические элементы, вложенные модальные окна и другие особенности DOM.

Дополнительные требования:

- `role="dialog"` и `aria-modal="true"`.
- Доступное название через `aria-labelledby` или `aria-label`.
- Закрытие по `Escape`, если сценарий это допускает.
- Недоступность фонового интерфейса для взаимодействия, например с использованием `inert`.
- Блокировка прокрутки страницы при необходимости.
- Корректная очистка обработчиков и восстановление состояния при размонтировании.

Важно, что Portal сам по себе не реализует focus trap и не обеспечивает доступность. Он отвечает только за размещение DOM-узлов. Управление фокусом и модальным поведением необходимо реализовывать отдельно.

В браузерах также существует нативный `<dialog>` с методом `showModal()`, который предоставляет встроенное модальное поведение. При использовании кастомного Portal эти механизмы нужно обеспечить самостоятельно.&#x20;
