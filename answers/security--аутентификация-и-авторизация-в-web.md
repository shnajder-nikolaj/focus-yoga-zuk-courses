# Security: Аутентификация и авторизация в Web

# Как не допустить передачи секретов в клиентский бандл?

Клиентский код полностью доступен пользователю, поэтому любые секреты, попавшие в JavaScript-бандл, HTML или публичные файлы, считаются раскрытыми.

Для защиты необходимо:

- Хранить секреты (`API_SECRET`, приватные ключи, пароли БД) только на сервере
- Использовать серверные переменные окружения, не экспортируя их в клиентский код
- Выполнять операции с секретами через backend или BFF (Backend for Frontend)
- Проверять production-бандл и source maps на утечки
- Использовать secret scanning в CI/CD

Переменные окружения с префиксами вроде `VITE_`, `NEXT_PUBLIC_` или `PUBLIC_` в соответствующих фреймворках предназначены для публичных значений.

Важно: минификация, обфускация и отсутствие переменной в Git не защищают секрет, если он попал в клиентский бандл.

# Как реализовать защищённый маршрут без ложного чувства безопасности?

Protected Route на фронтенде управляет доступом к интерфейсу, но не обеспечивает реальную защиту данных.

Правильная реализация предполагает два уровня:

1. Frontend - проверяет состояние аутентификации, показывает загрузку, перенаправляет неавторизованных пользователей на страницу входа и скрывает недоступные элементы интерфейса.
2. Backend - независимо проверяет сессию или токен и права пользователя при каждом обращении к защищённым ресурсам.

При серверном рендеринге доступ также проверяют до передачи защищённых данных клиенту.

Сервер возвращает `401 Unauthorized`, если пользователь не аутентифицирован, и `403 Forbidden`, если у него недостаточно прав.

Главное: пользователь может изменить JavaScript, обойти frontend guard или вызвать API напрямую. Поэтому защита маршрута не заменяет серверную авторизацию.

# Почему не стоит хранить чувствительные токены в localStorage без анализа угроз?

`localStorage` доступен JavaScript-коду текущего origin. При успешной XSS-атаке злоумышленник может прочитать токены и передать их на внешний сервер.

Основные риски:

- Токены доступны любому выполняемому в этом origin JavaScript, включая скомпрометированные сторонние скрипты
- Данные сохраняются после перезагрузки и закрытия браузера
- У хранилища нет встроенного механизма истечения срока действия
- Украденный bearer token можно использовать независимо от браузера до истечения срока или отзыва

Альтернативы зависят от архитектуры: хранение access token в памяти JavaScript уменьшает время его доступности, а BFF с серверным хранением токенов и `HttpOnly` cookie предотвращает их прямое чтение из JavaScript.

Однако `HttpOnly` не устраняет XSS полностью: вредоносный скрипт всё ещё может отправлять запросы от имени пользователя. Cookie-based аутентификация также требует защиты от CSRF.

# Какие данные следует удалять при выходе пользователя из системы?

При logout необходимо удалить локальное состояние аутентификации и аннулировать серверные учётные данные, позволяющие продолжать сессию.

Обычно очищают:

- Access token и refresh token, если они хранятся на клиенте
- Серверную сессию и связанную с ней cookie
- Кэш пользовательских API-запросов (`TanStack Query`, `SWR`, Apollo)
- Данные пользователя в `Redux`, `Zustand` и других хранилищах
- Чувствительные записи в `localStorage`, `sessionStorage` и `IndexedDB`
- Пользовательские данные в `Cache Storage`, если они там сохранялись

При этом нельзя без необходимости удалять общие настройки приложения или данные других пользователей.

Важно: удаление токена из браузера не делает его недействительным. Сервер должен отзывать сессию и refresh token. Уже выданный stateless JWT может оставаться действительным до истечения срока, если не предусмотрен механизм отзыва.

# Чем аутентификация отличается от авторизации?

Аутентификация (Authentication) - проверка того, кем является пользователь. Например, вход через пароль, passkey или SSO.

Авторизация (Authorization) - определение того, какие действия разрешены аутентифицированному пользователю.

Пример:

- Аутентификация подтверждает, что пользователь - `user123`
- Авторизация проверяет, может ли `user123` удалить документ `document456`

Успешная аутентификация не означает наличие всех прав. Авторизация должна проверяться сервером для каждого защищённого действия и ресурса.

# Как работает серверная сессия с HttpOnly cookie?

При входе сервер проверяет учётные данные, создаёт сессию и возвращает браузеру идентификатор в cookie:

```
Set-Cookie: __Host-session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
```

Дальнейший механизм:

1. Браузер автоматически отправляет cookie в подходящих HTTP-запросах.
2. Сервер извлекает идентификатор сессии.
3. Находит сессию в серверном хранилище, например Redis или базе данных.
4. Проверяет срок действия, пользователя и необходимые права.
5. При logout удаляет или аннулирует сессию.

`HttpOnly` запрещает JavaScript читать cookie через `document.cookie`, но не препятствует отправке запросов с этой cookie.

Идентификатор должен быть криптографически случайным и непредсказуемым. После входа или повышения привилегий его следует обновлять для защиты от session fixation.

Преимущество: сервер контролирует жизненный цикл сессии и может немедленно её отозвать.

# Чем session cookie отличается от persistent cookie?

Session cookie не содержит атрибутов `Expires` и `Max-Age`. Обычно удаляется после завершения браузерной сессии.

Persistent cookie содержит `Expires` или `Max-Age`, определяющие срок хранения.

Пример:

```
Set-Cookie: session=abc; HttpOnly; Secure; Path=/
```

```
Set-Cookie: session=abc; HttpOnly; Secure; Max-Age=604800; Path=/
```

Во втором случае cookie имеет срок жизни 7 дней.

Нюанс: современные браузеры могут восстанавливать session cookies при восстановлении предыдущей сессии браузера.

Также срок хранения cookie не равен сроку действия авторизации: серверная сессия может истечь раньше, даже если cookie остаётся в браузере.

# Что означают атрибуты cookie `HttpOnly`, `Secure`, `SameSite`, `Domain` и `Path`?

- `HttpOnly` - запрещает JavaScript читать или изменять cookie через обычные браузерные API. Cookie продолжает автоматически отправляться в HTTP-запросах.
- `Secure` - разрешает передачу cookie только по HTTPS, за исключением специальных правил для localhost.
- `SameSite` - определяет, когда cookie отправляется в cross-site запросах:
  - `Strict` - только в same-site контексте.
  - `Lax` - также при определённых межсайтовых навигациях верхнего уровня, например переходе по ссылке с GET.
  - `None` - разрешает cross-site передачу, требует `Secure`.
- `Domain` - определяет домен и его поддомены, которым отправляется cookie. Без этого атрибута cookie привязана только к установившему её хосту.
- `Path` - ограничивает отправку cookie определёнными URL-путями, например `/api`.

Важно: `Domain` и `Path` определяют область отправки cookie, но не являются полноценными границами безопасности.

Для чувствительных host-only cookies полезен префикс `__Host-`: он требует `Secure`, `Path=/` и отсутствия `Domain`.

# Что такое access token и refresh token?

Access token - учётные данные, позволяющие обращаться к защищённым API. Обычно имеет короткий срок действия и ограниченный набор полномочий (`scope`, `audience`).

Refresh token - учётные данные, используемые для получения нового access token без повторной интерактивной аутентификации пользователя.

Типичный сценарий:

1. Пользователь проходит аутентификацию.
2. Клиент получает access token и, если предусмотрено, refresh token.
3. Access token используется для вызовов API.
4. После его истечения клиент обращается к серверу авторизации с refresh token.
5. Сервер проверяет refresh token и выдаёт новый access token.

Refresh token обычно живёт дольше, поэтому его компрометация особенно опасна. Для публичных OAuth-клиентов современные требования предусматривают ротацию refresh token или криптографическую привязку токена к отправителю.

Оба токена могут быть как JWT, так и непрозрачными строками (`opaque tokens`).

# Какие преимущества и риски у JWT?

JWT (JSON Web Token) - формат токена, содержащего набор утверждений (`claims`). Обычно он подписан, что позволяет проверить его целостность и происхождение.

Преимущества:

- Самодостаточность - необходимые claims могут содержаться непосредственно в токене
- Возможность локальной проверки подписи без запроса к серверу авторизации
- Удобство использования в распределённых системах
- Поддержка стандартных claims: `iss`, `sub`, `aud`, `exp`, `nbf`

Риски:

- Подписанный JWT не скрывает данные
- Украденный bearer token можно использовать до истечения срока или отзыва
- Немедленный отзыв stateless JWT требует дополнительных механизмов
- Ошибки проверки подписи, алгоритма или claims приводят к уязвимостям
- Устаревшие роли и права могут оставаться в действующем токене

Сервер должен проверять подпись, допустимый алгоритм, `iss`, `aud`, срок действия и другие обязательные ограничения.

JWT не обязательно лучше серверной сессии. Он полезен там, где действительно нужна передача проверяемых claims между сервисами.

# Почему JWT не обязан быть зашифрованным?

JWT - это формат представления claims, который может использовать подпись или шифрование в зависимости от задачи.

Наиболее распространённый вариант - JWS (JSON Web Signature). Его содержимое кодируется через `Base64URL`, но не шифруется.

Это означает:

- Содержимое payload может прочитать любой обладатель токена
- Подпись защищает содержимое от незаметного изменения
- Конфиденциальность данных обеспечивается отдельно, например через HTTPS при передаче

Если данные внутри токена должны быть скрыты от его обладателя, используют JWE (JSON Web Encryption).

Обычно достаточно подписанного JWT без чувствительной информации в payload.

# Чем подпись JWT отличается от шифрования полезной нагрузки?

Подпись (JWS) обеспечивает целостность и подтверждение происхождения данных.

Сервер подписывает заголовок и payload криптографическим ключом. Получатель проверяет подпись и убеждается, что содержимое не было изменено.

При этом payload остаётся читаемым.

Шифрование (JWE) обеспечивает конфиденциальность. Payload преобразуется в зашифрованные данные, которые можно прочитать только при наличии соответствующего ключа.

Ключевое различие:

- Подпись отвечает на вопрос: «Можно ли доверять происхождению и целостности данных?»
- Шифрование отвечает на вопрос: «Может ли посторонний прочитать данные?»

JWE с аутентифицированным шифрованием также защищает целостность шифротекста, но само по себе не всегда подтверждает личность издателя токена.

Если нужны оба свойства, возможно использование подписанного JWT внутри зашифрованного JWT.

# Как организовать ротацию refresh token?

Refresh Token Rotation - механизм, при котором каждый успешный refresh выдаёт новый refresh token, а предыдущий становится недействительным.

Алгоритм:

1. Клиент отправляет текущий refresh token.
2. Сервер проверяет его действительность.
3. Атомарно помечает старый токен использованным.
4. Выдаёт новую пару access token и refresh token.
5. Сохраняет связь нового токена с исходной token family.

Если ранее использованный refresh token предъявляется повторно, это может свидетельствовать о его краже.

В таком случае сервер может аннулировать всю token family и потребовать повторной аутентификации.

Важные детали:

- Обновление должно быть атомарным, чтобы исключить одновременное успешное использование одного токена
- Refresh tokens желательно хранить на сервере в виде хешей
- Нужно учитывать сетевые повторы и параллельные запросы
- Допустимое окно повторов, если используется, должно быть строго ограничено и учитывать риск replay-атак
- Необходимы абсолютный срок жизни и/или таймаут неактивности

# Как избежать гонок при параллельном обновлении access token?

Проблема возникает, когда несколько запросов одновременно обнаруживают истёкший access token и пытаются обновить его одним refresh token.

При ротации первый запрос может успешно обновить токены, а остальные получат ошибку из-за уже использованного refresh token.

Основное решение - Single Flight: для одного контекста авторизации одновременно выполняется только один refresh-запрос.

Алгоритм:

1. Первый запрос запускает refresh и сохраняет общий `Promise`.
2. Остальные запросы ожидают тот же `Promise`.
3. После успешного обновления все используют новый access token.
4. Общий `Promise` очищается в `finally`.
5. При неустранимой ошибке обновления сессия завершается.

Для нескольких вкладок нужна дополнительная координация через `BroadcastChannel`, Web Locks или другой механизм.

Если refresh выполняется на сервере, используют блокировки или координацию на уровне сессии, особенно при нескольких экземплярах backend.

Важно: одного frontend mutex недостаточно для защиты от повторного использования токена на сервере.

# Почему проверка прав только на фронтенде небезопасна?

Frontend выполняется в среде, полностью контролируемой пользователем.

Пользователь может:

- Изменить состояние приложения через DevTools
- Удалить проверки ролей в JavaScript
- Вызвать API напрямую через `curl` или Postman
- Подменить идентификаторы ресурсов в запросах

Например, скрытая кнопка удаления не защищает endpoint `DELETE /api/users/123`.

Авторизация должна выполняться на сервере для каждого защищённого действия. Сервер проверяет не только роль пользователя, но и его право на конкретный ресурс.

Это также предотвращает IDOR/BOLA - уязвимости, при которых пользователь получает доступ к чужим объектам через изменение идентификатора.

Frontend-проверки нужны для UX, но не являются границей безопасности.

# Что такое RBAC и ABAC?

RBAC (Role-Based Access Control) - модель управления доступом на основе ролей.

Пользователю назначается роль, а роли соответствует набор разрешений.

Например:

- `admin` - управление пользователями
- `editor` - создание и изменение документов
- `viewer` - просмотр документов

ABAC (Attribute-Based Access Control) - модель, в которой решение принимается на основе атрибутов пользователя, ресурса, действия и окружения.

Пример правила:

```
user.department == document.department
AND user.clearance >= document.classification
AND action == "read"
```

Различия:

- RBAC проще реализовать и администрировать, но при сложных правилах может возникнуть избыточное количество ролей
- ABAC гибче и позволяет учитывать контекст, но сложнее в тестировании, аудите и сопровождении

На практике модели часто комбинируют: роль определяет базовые полномочия, а дополнительные правила проверяют владение ресурсом, принадлежность организации и другие условия.

# Как работает OAuth 2.0 Authorization Code Flow с PKCE?

Authorization Code Flow с PKCE позволяет клиенту получить токены через сервер авторизации, не передавая пароль пользователя приложению.

PKCE защищает authorization code от использования посторонним клиентом, который перехватил код.

Последовательность:

1. Клиент генерирует случайный `code_verifier`.
2. Вычисляет `code_challenge = BASE64URL(SHA256(code_verifier))`.
3. Перенаправляет пользователя на authorization server, передавая `client_id`, `redirect_uri`, `scope`, `state`, `code_challenge` и `code_challenge_method=S256`.
4. Пользователь аутентифицируется и подтверждает запрошенный доступ при необходимости.
5. Authorization server перенаправляет браузер на зарегистрированный `redirect_uri` с одноразовым `authorization_code`.
6. Клиент отправляет код и исходный `code_verifier` на token endpoint.
7. Сервер сравнивает вычисленный из `code_verifier` challenge с сохранённым и при успешной проверке выдаёт токены.

Перехваченного authorization code недостаточно для обмена, если атакующий не знает `code_verifier`.

Важно: PKCE не заменяет серверную авторизацию, валидацию `redirect_uri` или защиту от XSS. Для публичных OAuth-клиентов PKCE обязателен согласно актуальным рекомендациям безопасности OAuth.

# Чем OAuth 2.0 отличается от OpenID Connect?

OAuth 2.0 - протокол делегированной авторизации. Он позволяет приложению получить ограниченный доступ к ресурсам пользователя без передачи приложению его пароля.

OpenID Connect (OIDC) - протокол аутентификации, построенный поверх OAuth 2.0.

Главное отличие - OIDC добавляет ID Token, содержащий подтверждённые сведения о событии аутентификации и идентичности пользователя.

Основные токены:

- `access_token` - используется для доступа к защищённым API
- `id_token` - предназначен для клиента и содержит claims о пользователе и аутентификации

OIDC также стандартизирует `UserInfo Endpoint`, discovery metadata и механизмы проверки идентичности.

Важно: access token сам по себе не является универсальным доказательством аутентификации пользователя для клиента. Для этого в OIDC используется ID Token с обязательной проверкой подписи и claims.

# Зачем нужны `state` и `nonce` при SSO?

`state` - случайное значение, позволяющее связать ответ authorization server с конкретным запросом авторизации.

Клиент отправляет `state` при начале входа, а затем сравнивает полученное значение с сохранённым.

Это помогает защищаться от CSRF и подмены ответа в OAuth-процессе.

`nonce` - уникальное значение, связывающее ID Token с конкретным запросом аутентификации в OpenID Connect.

Клиент передаёт `nonce` при авторизации и проверяет соответствующий claim в полученном ID Token.

Это помогает обнаруживать replay и подмену ID Token.

Ключевое различие:

- `state` связывает authorization response с исходным запросом
- `nonce` связывает ID Token с исходным запросом аутентификации

Оба значения должны быть непредсказуемыми, уникальными для соответствующей операции и проверяться клиентом. При корректной реализации PKCE также обеспечивает защиту от ряда атак на OAuth-ответы.

# Как организовать logout и отзыв сессии?

Logout должен завершать авторизацию не только визуально, но и на стороне сервера.

Для серверных сессий:

1. Клиент вызывает logout endpoint.
2. Сервер аннулирует текущую сессию.
3. Сервер удаляет session cookie через `Set-Cookie` с `Max-Age=0`, используя соответствующие `Path` и `Domain`.
4. Клиент очищает пользовательское состояние и кэш.
5. Дальнейшие запросы с прежним идентификатором сессии отклоняются.

При token-based аутентификации дополнительно отзывают refresh token или всю token family.

Особенность JWT: если access token проверяется полностью локально и не существует механизма отзыва, он может продолжать работать до `exp`.

Для немедленного отзыва используют denylist, проверку версии сессии или централизованное состояние авторизации.

При SSO важно различать:

- Local logout - выход из конкретного приложения
- Single Logout - координированное завершение сессий приложений и/или Identity Provider

Выход из приложения не обязательно завершает SSO-сессию у Identity Provider.

# Что такое silent refresh и какие ограничения браузера на него влияют?

Silent refresh - получение нового access token без интерактивного входа пользователя.

Основные подходы:

1. Refresh token - клиент или BFF обращается к token endpoint и обновляет токены без перенаправления пользователя.
2. Silent authentication - приложение запускает OIDC-авторизацию с `prompt=none`, исторически часто через скрытый `iframe`, используя существующую сессию Identity Provider.

Второй способ ограничивается браузерами:

- Блокировка сторонних cookies может сделать сессию Identity Provider недоступной внутри `iframe`
- `SameSite` ограничивает передачу cookie в cross-site контекстах
- `CSP frame-ancestors` и `X-Frame-Options` могут запрещать встраивание страниц
- Политики изоляции хранилищ могут нарушать механизмы, зависящие от общего состояния

Поэтому silent authentication через скрытый iframe нельзя считать надёжным универсальным способом.

В современных приложениях часто используют Authorization Code + PKCE с refresh token rotation либо BFF, который обновляет токены на сервере.

# Как устроить авторизацию через BFF, не выдавая токены JavaScript-коду?

BFF (Backend for Frontend) - серверный компонент, выступающий посредником между браузером, сервером авторизации и защищёнными API.

Архитектура:

1. Браузер инициирует вход через BFF.
2. BFF выполняет Authorization Code Flow с PKCE.
3. BFF получает access token и refresh token.
4. Токены сохраняются на сервере, например в защищённом хранилище сессий.
5. Браузеру выдаётся только идентификатор сессии в `HttpOnly; Secure` cookie.
6. Браузер обращается к BFF с cookie.
7. BFF проверяет сессию и отправляет запрос к API, добавляя access token на серверной стороне.

Таким образом, JavaScript не получает OAuth-токены и не может напрямую их прочитать.

Преимущества: меньший риск кражи токенов через XSS, централизованное обновление токенов и управление сессиями.

Ограничения: требуется серверная инфраструктура, защита cookie-based запросов от CSRF и авторизация на уровне API. XSS по-прежнему может инициировать действия от имени пользователя через BFF.

# Какие ошибки возникают при cross-domain cookie и CORS?

Cross-origin запросы с cookie требуют согласованной настройки браузера и сервера.

Типичные ошибки:

- Отсутствует `credentials: 'include'` в `fetch` для cross-origin запроса
- Сервер возвращает `Access-Control-Allow-Origin: *` вместе с credentials
- Отсутствует `Access-Control-Allow-Credentials: true`
- `SameSite=Lax` или `Strict` препятствует передаче cookie в cross-site запросе
- Для `SameSite=None` не установлен `Secure`
- Атрибуты `Domain` или `Path` не соответствуют адресу запроса
- Не обработан preflight-запрос `OPTIONS`
- Сторонние cookies заблокированы браузером

Для credentialed CORS сервер должен возвращать конкретный разрешённый origin, а не `*`.

Пример:

```
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Vary: Origin
```

Также нужно корректно обрабатывать `Access-Control-Allow-Methods` и `Access-Control-Allow-Headers` при preflight.

Важно различать:

- Origin - схема, хост и порт
- Site - схема и регистрируемый домен

Поэтому `app.example.com` и `api.example.com` являются разными origins, но при одинаковой схеме обычно относятся к одному site.

CORS не является механизмом аутентификации или авторизации. Он регулирует доступ браузерного JavaScript к ответам другого origin, а не защищает API от прямых запросов.

# Как интегрировать SSO, если приложение размещено на другом поддомене?

Например:

```
app.example.com
api.example.com
auth.example.com
```

Обычно используют OpenID Connect Authorization Code Flow с PKCE.

Последовательность:

1. Пользователь открывает `app.example.com`.
2. Приложение перенаправляет его на `auth.example.com`.
3. Identity Provider проверяет существующую SSO-сессию или выполняет вход.
4. Пользователь возвращается на зарегистрированный `redirect_uri` приложения.
5. Backend или BFF обменивает authorization code на токены.
6. Приложение создаёт собственную сессию.

SSO-сессия у Identity Provider и сессия приложения могут быть независимыми.

Для cookie важно учитывать:

- Между поддоменами одного site обычно не требуется `SameSite=None`
- При cross-origin запросах через `fetch` необходимо `credentials: 'include'` и корректная настройка CORS
- Cookie без `Domain` доступна только своему хосту, но браузер всё равно может отправлять её этому хосту при запросах с другого поддомена
- `Domain=example.com` расширяет область действия cookie на поддомены, увеличивая риски

Предпочтительно использовать host-only cookies и не делиться одной session cookie между приложениями без необходимости.

Если Identity Provider расположен на другом site, надёжнее использовать полноценные браузерные перенаправления, а не полагаться на сторонние cookies внутри iframe.

# Как правильно защитить серверные мутации в cookie-based аутентификации?

При cookie-based аутентификации браузер автоматически прикладывает cookie к подходящим запросам.

Это создаёт риск CSRF: вредоносный сайт может попытаться заставить браузер авторизованного пользователя выполнить изменение данных.

Для защиты серверных мутаций (`POST`, `PUT`, `PATCH`, `DELETE`) используют несколько механизмов:

- CSRF-токены - сервер проверяет непредсказуемый токен, связанный с сессией, либо корректно защищённый stateless-токен
- `SameSite=Lax` или `Strict` - ограничивает передачу cookies в cross-site запросах
- Проверка `Origin` - сервер разрешает изменения только с доверенных origins
- Fetch Metadata - анализирует заголовки вроде `Sec-Fetch-Site` для блокировки подозрительных cross-site запросов
- Корректная CORS-политика - ограничивает разрешённые origins и заголовки

Дополнительно:

- `GET`, `HEAD` и другие безопасные методы не должны изменять состояние
- Сервер должен проверять `Content-Type` и отклонять неподдерживаемые форматы
- Для критических операций могут требоваться повторная аутентификация или подтверждение действия

Важно: `HttpOnly` защищает cookie от прямого чтения JavaScript, но сам по себе не защищает от CSRF.

# Что такое CSRF-токен и как он соотносится с SameSite cookie?

CSRF-токен - непредсказуемое значение, которое сервер использует для проверки того, что изменяющий состояние запрос инициирован в допустимом контексте приложения.

Типичная схема Synchronizer Token Pattern:

1. Сервер создаёт CSRF-токен, связанный с пользовательской сессией.
2. Приложение получает его через доверенный канал.
3. Клиент передаёт токен в заголовке, например `X-CSRF-Token`.
4. Сервер проверяет соответствие токена текущей сессии.
5. Запросы без корректного токена отклоняются.

Атакующий сайт обычно может инициировать запрос с cookie пользователя, но не может прочитать CSRF-токен приложения из-за Same-Origin Policy.

`SameSite` и CSRF-токен решают связанную задачу разными способами:

- `SameSite` ограничивает автоматическую отправку cookie в cross-site контекстах
- CSRF-токен позволяет серверу проверять дополнительное подтверждение допустимости запроса

`SameSite` не заменяет CSRF-токены во всех сценариях. Например, поддомены одного site могут рассматриваться как same-site даже при различающихся origins.

Для cookie-based аутентификации надёжная защита обычно сочетает CSRF-токены, `SameSite` и проверку `Origin` или Fetch Metadata.
