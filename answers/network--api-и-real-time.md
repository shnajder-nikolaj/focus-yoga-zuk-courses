# Какие ограничения описывает REST?

REST (Representational State Transfer) - архитектурный стиль построения распределённых систем, определяющий шесть ограничений:

1. Client-Server - клиент и сервер разделены по ответственности и могут развиваться независимо.
2. Stateless - каждый запрос содержит всю необходимую информацию для обработки. Сервер не зависит от состояния предыдущих запросов клиента.
3. Cacheable - ответы должны явно определять возможность кеширования, чтобы уменьшать нагрузку и задержки.
4. Uniform Interface - единообразное взаимодействие через идентификаторы ресурсов, их представления и стандартную семантику операций. Включает самоописываемые сообщения и HATEOAS (переходы между состояниями приложения через гиперссылки).
5. Layered System - система может состоять из промежуточных слоёв: прокси, балансировщиков, шлюзов и кешей.
6. Code on Demand (необязательное) - сервер может передавать клиенту исполняемый код.

REST не привязан строго к HTTP или JSON, хотя HTTP чаще всего используется для реализации REST API.

# Чем RESTful API отличается от RPC?

RESTful API ориентирован на ресурсы и операции над ними, а RPC (Remote Procedure Call) - на удалённый вызов функций.

Например:

- REST: `GET /users/42`, `DELETE /users/42`
- RPC: `getUser(42)`, `deleteUser(42)` или `POST /users/delete`

В REST действие выражается через семантику HTTP-метода, а ресурс - через URL. В RPC клиент вызывает конкретную операцию, передавая аргументы.

REST удобен для ресурсных API с единообразными операциями и HTTP-кешированием. RPC удобен для сложных бизнес-операций, которые плохо представляются стандартными действиями над ресурсами.

RPC также может использовать HTTP в качестве транспорта.

# Как проектировать ресурсные URL?

URL должен идентифицировать ресурс, а не действие над ним.

Основные принципы:

- Использовать существительные: `/users`, `/orders`
- Для коллекций придерживаться единого соглашения, например множественного числа: `/users`
- Для конкретного ресурса использовать идентификатор: `/users/42`
- Для связанных ресурсов использовать вложенность: `/users/42/orders`
- Для фильтрации и сортировки применять query-параметры: `/users?role=admin&sort=name`
- Не включать стандартные CRUD-действия в URL: `/getUsers`, `/deleteUser`

Операции определяются HTTP-методами: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`.

Не стоит создавать чрезмерно глубокую вложенность. Если ресурс имеет самостоятельный жизненный цикл, ему обычно подходит собственный URL.

# Зачем применять REST?

REST позволяет создавать API с предсказуемым интерфейсом, используя стандартные возможности HTTP.

Основные преимущества:

- Масштабируемость - stateless-взаимодействие упрощает распределение запросов между серверами.
- Кеширование - HTTP-кеши позволяют уменьшать количество запросов к серверу.
- Независимость клиента и сервера - реализация одной стороны может изменяться без изменения другой при сохранении контракта.
- Единообразие - стандартные HTTP-методы, статусы и заголовки упрощают интеграцию.
- Совместимость - можно использовать существующую HTTP-инфраструктуру.

REST особенно удобен для CRUD API и ресурсно-ориентированных систем.

Ограничение: при сложных связанных данных клиенту иногда приходится выполнять несколько запросов или получать больше данных, чем необходимо.

# Как реализовать пагинацию с offset и cursor?

Offset-based pagination использует количество пропускаемых записей и размер страницы.

Пример: `GET /users?limit=20&offset=40`.

Сервер пропускает 40 записей и возвращает следующие 20.

Преимущества: простая реализация, возможность переходить к конкретной странице.

Недостатки: большой `OFFSET` может снижать производительность, а добавление или удаление записей между запросами приводит к пропускам или дубликатам.

Cursor-based pagination использует указатель на позицию в упорядоченном наборе данных.

Пример: `GET /users?limit=20&after=abc123`.

Сервер возвращает следующую порцию данных после позиции, закодированной в курсоре. Обычно курсор содержит значения полей сортировки, например `createdAt` и `id`.

Преимущества: эффективна для больших наборов данных и устойчивее к изменениям записей перед текущей позицией.

Недостатки: сложнее реализация, нет удобного произвольного перехода к странице.

Для cursor-пагинации необходим стабильный детерминированный порядок, например сортировка по `createdAt` и `id`. Курсор должен соответствовать выбранным фильтрам и сортировке.

# Как проектировать сортировку и фильтрацию API?

Сортировку и фильтрацию обычно передают через query-параметры.

Пример:

`GET /products?category=books&minPrice=100&sort=-price,name&limit=20`

Здесь:

- `category=books` - фильтрация по категории.
- `minPrice=100` - фильтрация по минимальной цене.
- `sort=-price,name` - сначала цена по убыванию, затем имя по возрастанию.
- `limit=20` - ограничение количества результатов.

Сервер должен использовать разрешённый список полей сортировки и фильтрации, проверять типы и диапазоны параметров.

Важно определить стабильный порядок результатов, особенно при пагинации. Если значения сортировки совпадают, дополнительным критерием может служить уникальный `id`.

Нельзя напрямую подставлять пользовательские параметры в SQL без проверки и безопасного построения запроса.

# Как договориться об общем формате ошибок API?

Необходимо определить единый контракт ошибок: HTTP-статус, машиночитаемый идентификатор, описание и дополнительные данные.

Стандартный вариант - RFC 9457 Problem Details с `Content-Type: application/problem+json`.

Пример:

```
{
  "type": "https://api.example.com/problems/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "Email has invalid format",
  "code": "INVALID_EMAIL",
  "requestId": "req-123"
}
```

Поля `type`, `title`, `status`, `detail` определены стандартом, а `code` и `requestId` - пользовательские расширения.

Важно:

- Использовать корректные HTTP-статусы: `400`, `401`, `403`, `404`, `409`, `422`, `500`.
- Предусмотреть стабильный идентификатор ошибки, на который может ориентироваться клиент.
- Для ошибок валидации передавать сведения о конкретных полях.
- Не раскрывать внутренние детали сервера, SQL-запросы и stack traces.

Клиент должен принимать решения по статусу и машинному идентификатору, а не парсить текст сообщения.

# Как API обеспечивает идемпотентность повторного POST-запроса?

Идемпотентность означает, что повторное выполнение операции не изменяет результат её воздействия на систему после первого успешного применения.

`POST` по умолчанию не идемпотентен. Например, повторное создание платежа может привести к двойному списанию.

Для защиты применяется Idempotency-Key:

1. Клиент генерирует уникальный ключ и отправляет его вместе с `POST`.
2. Сервер проверяет, обрабатывался ли этот ключ.
3. Если нет - выполняет операцию и сохраняет её результат.
4. Если да - возвращает сохранённый результат без повторного выполнения операции.

Например: `Idempotency-Key: 8e2f-1234`.

Важно атомарно согласовать выполнение операции и фиксацию ключа, учитывать параллельные запросы, ограничивать срок хранения ключей и проверять совпадение параметров повторного запроса.

Одинаковый ключ с другим содержимым запроса должен приводить к ошибке, а не повторно использовать старый результат.

# Как организовать версионирование API?

Версионирование API позволяет изменять контракт, не нарушая работу существующих клиентов.

Основные подходы:

- URL versioning - `/api/v1/users`, `/api/v2/users`
- Header versioning - передача версии через заголовок, например `API-Version: 2`
- Media type versioning - `Accept: application/vnd.example.v2+json`

Версия обычно меняется при несовместимых изменениях: удалении полей, изменении их типов или семантики операций.

Добавление необязательного поля часто совместимо со старым клиентом, если он корректно обрабатывает неизвестные поля.

При выпуске новой версии важно обеспечить переходный период, документировать изменения и заранее объявлять прекращение поддержки старой версии.

Версионирование не заменяет проектирование обратной совместимости.

# Что такое OpenAPI и как использовать контракт для генерации типов?

OpenAPI - стандарт машиночитаемого описания HTTP API. Контракт в YAML или JSON определяет endpoints, методы, параметры, схемы запросов, ответов и ошибок.

На основе контракта можно автоматически генерировать:

- TypeScript-типы данных и API-ответов.
- Типизированные HTTP-клиенты.
- Документацию.
- Моки и проверки соответствия API контракту.

Например, `openapi-typescript` генерирует TypeScript-типы, а `Orval` может генерировать клиентские функции и хуки.

Типичный процесс: бэкенд публикует OpenAPI-контракт, фронтенд генерирует типы, а CI проверяет их актуальность при изменениях API.

Важно: TypeScript-типы работают только во время разработки. Они не проверяют реальные данные сервера во время выполнения. Для этого необходима runtime-валидация.

# Что такое GraphQL schema, query и mutation?

GraphQL - язык запросов к API, позволяющий клиенту указывать, какие данные он хочет получить.

Основные понятия:

- Schema - типизированный контракт API. Определяет доступные сущности, их поля, аргументы и операции.
- Query - операция чтения данных. Клиент выбирает необходимые поля ответа.
- Mutation - операция изменения данных, например создания, обновления или удаления сущностей.

Пример GraphQL-запроса:

```
query {
  user(id: "42") {
    id
    name
    email
  }
}
```

Сервер возвращает только запрошенные поля.

Обработка полей обычно выполняется через resolvers - функции, которые получают значения соответствующих полей.

В отличие от REST, где структура ответа определяется endpoint, в GraphQL клиент выбирает структуру данных в пределах доступной схемы.

# Что такое N+1 проблема в GraphQL?

N+1 - проблема производительности, при которой получение списка сущностей приводит к большому количеству дополнительных запросов к источнику данных.

Например, клиент запрашивает 100 пользователей и их заказы:

1. Выполняется 1 запрос для получения пользователей.
2. Для каждого пользователя отдельно запрашиваются заказы.
3. В результате выполняется 101 запрос.

Причина - независимое выполнение resolver-функций, каждая из которых обращается к базе данных.

Основные решения:

- DataLoader - объединяет загрузку данных по нескольким ключам в один пакетный запрос и кеширует результаты в рамках запроса.
- Batching - получение связанных данных сразу для нескольких сущностей.
- JOIN - получение связанных записей одним SQL-запросом.
- Prefetching - предварительная загрузка необходимых связей.

Важно, что проблема N+1 не уникальна для GraphQL, но возникает особенно часто из-за вложенных запросов и независимых resolvers.

# Как GraphQL subscriptions отличаются от обычных запросов?

Query и mutation обычно возвращают результат выполнения одной операции, после чего запрос завершается.

Subscription создаёт долгоживущее взаимодействие, при котором сервер отправляет новые результаты по мере возникновения событий.

Например, клиент подписывается на новые сообщения:

```
subscription {
  messageAdded {
    id
    text
  }
}
```

При появлении сообщения сервер отправляет данные подписанным клиентам.

Для транспорта часто используется WebSocket, хотя возможны и другие механизмы, например SSE.

Subscriptions обычно работают через систему событий или Pub/Sub.

Важно: сама GraphQL subscription не гарантирует сохранение истории, повторную доставку потерянных событий или автоматическое восстановление состояния после переподключения. Эти механизмы необходимо реализовывать отдельно.

# Когда GraphQL подходит лучше REST?

GraphQL особенно полезен, когда клиенты имеют разные потребности в данных и работают со сложными связанными сущностями.

Подходящие сценарии:

- Несколько клиентов - web, mobile, desktop - запрашивают разные наборы полей.
- Необходимо получать связанные данные одним запросом.
- Структура данных сложная и содержит много вложенных сущностей.
- Требуется единая точка доступа к нескольким бэкенд-сервисам.
- Фронтенд часто меняет состав запрашиваемых данных.

GraphQL уменьшает проблемы overfetching (избыточные данные) и underfetching (необходимость дополнительных запросов).

Недостатки: усложняется кеширование на уровне HTTP, контроль сложности запросов, авторизация на уровне полей и оптимизация resolvers.

Для простых CRUD API REST зачастую проще в реализации и сопровождении.

# Как работают gRPC и Protocol Buffers?

gRPC - фреймворк удалённого вызова процедур (RPC), позволяющий клиенту вызывать методы серверного сервиса через сеть.

Protocol Buffers (Protobuf) - формат бинарной сериализации данных и язык описания их структуры.

Работа происходит следующим образом:

1. Разработчик описывает сообщения и методы сервиса в `.proto` файле.
2. Генератор создаёт клиентский и серверный код.
3. Клиент вызывает метод через сгенерированный интерфейс.
4. Данные сериализуются в бинарный формат Protobuf и передаются серверу.
5. Сервер обрабатывает вызов и возвращает результат.

Стандартный gRPC использует HTTP/2, поддерживает мультиплексирование, метаданные, дедлайны и четыре типа вызовов:

- Unary - один запрос и один ответ.
- Server streaming - один запрос и поток ответов.
- Client streaming - поток запросов и один ответ.
- Bidirectional streaming - двунаправленный обмен потоками.

Protobuf обеспечивает компактное представление данных и типизированный контракт. При изменении схемы важно сохранять совместимость полей и не переиспользовать старые номера удалённых полей.

# Какие сложности возникают при прямом gRPC из браузера?

Обычный gRPC использует возможности HTTP/2, к которым браузерные API не предоставляют необходимого низкоуровневого доступа, включая управление HTTP/2-фреймами и trailers.

Поэтому браузер не может напрямую использовать стандартный gRPC-протокол как нативный клиент.

Для решения применяется gRPC-Web:

- Использует адаптированный протокол.
- Работает через совместимый сервер или прокси, например Envoy.
- Поддерживает unary-вызовы и server streaming.
- В стандартной реализации не поддерживает client streaming и bidirectional streaming.
- Требует корректной настройки CORS при кросс-доменных запросах.

Дополнительно необходимо учитывать генерацию клиентского кода, обработку ошибок и совместимость инфраструктуры с gRPC-Web.

# Как защититься от некорректных данных, пришедших с сервера?

Данные сервера следует считать недоверенными, даже если API принадлежит собственному приложению.

TypeScript не проверяет данные во время выполнения. Например, объявление `User` не гарантирует, что API действительно вернул объект нужной структуры.

Основные меры:

- Runtime-валидация - проверять входящие данные с помощью Zod, Valibot или JSON Schema.
- Проверка типов - учитывать отсутствующие поля, `null`, неверные типы и неожиданные значения.
- Безопасная обработка ошибок - не допускать падения всего интерфейса из-за некорректного ответа.
- Защита от XSS - не вставлять серверные строки как HTML без надёжной санитизации.
- Контроль URL и внешних данных - проверять допустимые протоколы, форматы и диапазоны значений.

Пример с Zod:

```
const UserSchema = z.object({
  id: z.number(),
  name: z.string(),
});

const user = UserSchema.parse(response.data);
```

Если ответ не соответствует схеме, возникнет ошибка валидации, которую можно обработать.

Важно: клиентская валидация защищает интерфейс, но не заменяет серверную проверку данных и авторизацию.

# Что такое contract testing между фронтендом и бэкендом?

Contract testing - тестирование соответствия API согласованному контракту между клиентом и сервером.

Контракт определяет:

- Доступные endpoints и методы.
- Форматы запросов и ответов.
- Обязательные и необязательные поля.
- Типы данных.
- Возможные ошибки и статусы.

Например, фронтенд ожидает, что `GET /users/42` возвращает объект с полями `id: number` и `name: string`.

Contract test проверяет, что бэкенд действительно способен предоставить такой ответ.

Распространённые подходы:

- Consumer-driven contracts - клиент описывает свои ожидания, а сервер проверяет их выполнение. Например, через Pact.
- Schema-based testing - стороны проверяются на соответствие общей OpenAPI-схеме.

Такие проверки обычно запускаются в CI, позволяя обнаружить несовместимые изменения до развёртывания.

В отличие от E2E-тестов, contract testing проверяет совместимость интерфейсов, а не весь пользовательский сценарий.

# Чем polling отличается от long polling?

Polling - периодический опрос сервера через обычные HTTP-запросы.

Например, клиент каждые 5 секунд отправляет `GET /notifications`.

Недостаток: запросы выполняются даже при отсутствии изменений, создавая лишнюю нагрузку.

Long polling - клиент отправляет запрос, а сервер удерживает его до появления новых данных или истечения таймаута.

Последовательность:

1. Клиент отправляет запрос.
2. Сервер ожидает событие.
3. При появлении события возвращает ответ.
4. Клиент сразу создаёт следующий запрос.

Long polling уменьшает задержку доставки событий и количество бесполезных запросов.

Однако каждое получение данных по-прежнему требует HTTP-запроса, а сервер должен управлять долгоживущими запросами и таймаутами.

# Как работает WebSocket handshake?

WebSocket handshake - процедура установления WebSocket-соединения поверх HTTP.

В классическом варианте HTTP/1.1:

1. Клиент отправляет HTTP-запрос `GET` с заголовками `Upgrade: websocket`, `Connection: Upgrade` и `Sec-WebSocket-Key`.
2. Сервер проверяет запрос, права доступа и поддержку протокола.
3. Сервер возвращает `101 Switching Protocols` и вычисленный `Sec-WebSocket-Accept`.
4. После успешного handshake соединение используется для обмена WebSocket-фреймами.

Пример:

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
```

Для защищённого соединения применяется `wss://`, использующий TLS.

В HTTP/2 и HTTP/3 WebSocket также может устанавливаться через Extended CONNECT, без классического механизма `101 Switching Protocols`.

Важно проверять `Origin` и аутентификацию при установлении соединения, поскольку браузерный WebSocket не использует обычный механизм CORS для защиты handshake.

# Чем WebSocket отличается от HTTP request/response?

Классическая HTTP-модель строится вокруг запроса клиента и ответа сервера.

WebSocket создаёт постоянное двунаправленное соединение, в котором обе стороны могут инициировать отправку сообщений независимо.

Основные отличия:

- HTTP - отдельные запросы и ответы. WebSocket - непрерывный обмен сообщениями.
- HTTP - клиент инициирует запрос. WebSocket - сервер может самостоятельно отправлять события.
- WebSocket не требует повторять HTTP-заголовки для каждого сообщения.
- WebSocket поддерживает текстовые и бинарные сообщения.

WebSocket использует упорядоченную и надёжную передачу данных через TCP либо соответствующий транспорт при работе поверх новых версий HTTP.

WebSocket удобен для чатов, совместного редактирования и интерактивных приложений.

При этом он требует самостоятельного управления жизненным циклом соединения, переподключением и восстановлением данных.

# Какие проблемы возникают при разрыве WebSocket-соединения?

Основные проблемы:

- Потеря событий - сервер мог отправить сообщения, пока клиент был отключён.
- Неопределённость доставки - клиент не знает, обработал ли сервер последнее отправленное сообщение.
- Дублирование - повторная отправка сообщений может привести к повторному выполнению операций.
- Устаревшее состояние - данные интерфейса перестают соответствовать состоянию сервера.
- Потеря подписок - после переподключения может потребоваться повторная подписка на каналы.
- Необнаруженный разрыв - соединение может выглядеть открытым, хотя фактически уже не работает.

Для решения используют reconnect, heartbeat, идентификаторы сообщений, подтверждения обработки, повторное получение пропущенных событий и синхронизацию состояния.

Сам WebSocket не гарантирует доставку сообщений между разными соединениями.

# Как реализовать reconnect с backoff и jitter?

При разрыве соединения клиент должен автоматически переподключаться, но без чрезмерного количества запросов.

Exponential backoff увеличивает задержку после каждой неудачной попытки:

\\[ delay = \min(maxDelay,\ baseDelay \cdot 2^{attempt}) \\]

Например: 1, 2, 4, 8, 16 секунд.

Jitter добавляет случайность, чтобы множество клиентов не пыталось переподключиться одновременно.

Пример:

```
const maxDelay = 30_000;
const baseDelay = 1_000;

const delay =
  Math.random() *
  Math.min(maxDelay, baseDelay * 2 ** attempt);
```

Это реализация full jitter.

Дополнительно необходимо:

- Ограничивать максимальную задержку.
- Сбрасывать счётчик попыток после стабильного соединения.
- Не переподключаться при намеренном закрытии.
- Обрабатывать ошибки авторизации отдельно.
- После reconnect восстанавливать подписки и пропущенные данные.

# Как обрабатывать дубли и пропуски событий при переподключении?

Нельзя рассчитывать, что WebSocket автоматически восстановит все сообщения после разрыва.

Для надёжной обработки используют идентификаторы событий и механизм replay.

Последовательность:

1. Сервер назначает событиям уникальные ID или монотонные sequence numbers.
2. Клиент сохраняет позицию последнего корректно обработанного события.
3. После reconnect передаёт эту позицию серверу.
4. Сервер отправляет пропущенные события из сохранённого журнала.
5. Клиент игнорирует уже обработанные события.

Например, если клиент получил событие №105, после переподключения он запрашивает события начиная с №106.

Для защиты от дубликатов применяются deduplication и идемпотентная обработка.

Если история событий недоступна, клиент должен запросить актуальный snapshot состояния и продолжить получение событий с согласованной позиции.

Важно, чтобы идентификаторы и порядок были определены в рамках конкретного потока или канала. Глобальная последовательность не всегда необходима.

# Когда Server-Sent Events удобнее WebSocket?

Server-Sent Events (SSE) - механизм передачи событий от сервера клиенту через долгоживущий HTTP-ответ с типом `text/event-stream`.

SSE предпочтительнее, когда требуется только однонаправленная передача данных от сервера клиенту.

Примеры:

- Уведомления.
- Обновление статуса задач.
- Потоковое отображение ответов.
- Мониторинг и журналы событий.
- Обновление новостных лент.

Преимущества:

- Использует обычный HTTP.
- Поддерживается браузерным `EventSource`.
- Предусматривает автоматическое переподключение.
- Поддерживает идентификаторы событий для восстановления потока.

Если клиенту также необходимо постоянно отправлять сообщения серверу, WebSocket обычно удобнее.

# Какие ограничения у EventSource?

`EventSource` - браузерный API для получения Server-Sent Events.

Основные ограничения:

- Однонаправленность - сервер отправляет данные клиенту, но не наоборот.
- GET-запрос - стандартный `EventSource` не позволяет отправить тело запроса через `POST`.
- Заголовки - стандартный конструктор не позволяет произвольно задавать HTTP-заголовки, например `Authorization`.
- Текстовый формат - SSE передаёт UTF-8-текст, а не бинарные сообщения.
- Ограничение соединений - при HTTP/1.1 браузеры обычно ограничивают число одновременных SSE-соединений примерно шестью на браузер и домен. При HTTP/2 ограничение определяется согласованным числом потоков.

Для авторизации можно использовать cookies с настройкой `withCredentials`, соблюдая требования CORS и безопасности.

`EventSource` автоматически пытается восстановить соединение и может отправлять `Last-Event-ID`, если сервер передавал идентификаторы событий.

# Что такое heartbeat/ping-pong для долгоживущего соединения?

Heartbeat - периодическая проверка доступности соединения.

Она необходима, поскольку TCP/WebSocket-соединение может фактически перестать работать без немедленного уведомления приложения.

В WebSocket существуют специальные управляющие фреймы:

- Ping - проверка доступности второй стороны.
- Pong - ответ на полученный ping.

Если pong не поступает за заданное время, сервер может считать соединение неработоспособным и закрыть его.

В браузерном WebSocket API нет прямого доступа к протокольным ping/pong-фреймам - браузер обрабатывает их самостоятельно. Для контроля соединения со стороны JavaScript можно реализовать heartbeat на уровне сообщений приложения.

В SSE для поддержания активности часто отправляют комментарии, например `: heartbeat`, которые не вызывают пользовательских событий.

Слишком частые проверки увеличивают нагрузку, поэтому интервал выбирают с учётом таймаутов инфраструктуры.

# В каких случаях применяется WebRTC?

WebRTC (Web Real-Time Communication) - набор технологий для передачи аудио, видео и произвольных данных между участниками с минимальной задержкой.

Основные сценарии:

- Аудио- и видеозвонки.
- Видеоконференции.
- Демонстрация экрана.
- P2P-передача файлов.
- Интерактивные приложения и игры.

WebRTC предоставляет:

- `getUserMedia()` - доступ к камере и микрофону.
- `RTCPeerConnection` - установление соединения и передача медиапотоков.
- `RTCDataChannel` - обмен произвольными данными.

WebRTC старается установить прямое соединение между участниками, но при сетевых ограничениях может передавать трафик через TURN-сервер.

Медиа передаётся в зашифрованном виде.

В групповых видеоконференциях часто применяют SFU-серверы, пересылающие медиапотоки между участниками, вместо создания полного набора P2P-соединений.

# Как работают signaling, ICE, STUN и TURN на высоком уровне?

Эти механизмы используются для установления WebRTC-соединения между участниками, находящимися в разных сетях.

Signaling - процесс обмена служебной информацией, необходимой для установки соединения.

Обычно передаются SDP offer/answer и ICE candidates. Для signaling можно использовать WebSocket, HTTP или другой транспорт. WebRTC не определяет обязательный signaling-протокол.

ICE (Interactive Connectivity Establishment) - механизм поиска и проверки возможных сетевых маршрутов между участниками.

STUN - протокол, помогающий определить внешний IP-адрес и порт, видимые за NAT.

TURN - сервер, через который передаётся трафик, если прямое соединение установить не удалось.

Общая последовательность:

1. Участники обмениваются SDP через signaling.
2. ICE собирает возможные адреса и маршруты подключения.
3. STUN помогает получить внешние сетевые адреса.
4. ICE проверяет доступные пары кандидатов и выбирает рабочий маршрут.
5. Если прямой маршрут недоступен, может использоваться TURN.
6. После установления защищённого соединения начинается передача данных.

STUN сам по себе не гарантирует возможность P2P-соединения, поскольку NAT и сетевые экраны могут блокировать прямое взаимодействие.

# Как организовать realtime-обновления при нескольких вкладках?

Если каждая вкладка самостоятельно создаёт WebSocket или SSE-соединение, увеличивается количество подключений, нагрузка на сервер и расход ресурсов.

Возможны два основных подхода.

1\. Независимые соединения

Каждая вкладка открывает собственное соединение.

Плюсы: простота реализации и независимость вкладок.

Минусы: дублирование событий и повышенная нагрузка.

2\. Общее соединение

Одно соединение используется несколькими вкладками:

- `SharedWorker` может поддерживать общее WebSocket-соединение и передавать данные вкладкам.
- `BroadcastChannel` позволяет вкладкам обмениваться событиями.
- Одна вкладка может быть выбрана лидером, поддерживать соединение и пересылать сообщения остальным.

При использовании вкладки-лидера необходимо предусмотреть её закрытие, выбор нового лидера и предотвращение одновременного появления нескольких активных лидеров.

Для синхронизации состояния также важно использовать идентификаторы событий, устранять дубли и корректно восстанавливать пропущенные обновления.

Выбор зависит от масштаба: для небольшого приложения независимые соединения могут быть достаточными, а при большом количестве вкладок общий канал позволяет сократить потребление ресурсов.
