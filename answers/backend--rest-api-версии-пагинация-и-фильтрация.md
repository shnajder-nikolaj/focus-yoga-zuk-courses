# Какие ограничения REST важны при проектировании ресурсного HTTP API?

REST описывает client-server разделение, stateless-взаимодействие, cacheability, layered system и uniform interface; code-on-demand является необязательным ограничением. В полном определении uniform interface включает ресурсы, представления, самодостаточные сообщения и hypermedia-переходы.

На практике ресурсные HTTP API часто реализуют часть этого подхода. JSON и существительные в URL сами по себе не делают API полностью RESTful. Для проектирования важно явно определить ресурсы, семантику операций, состояние процесса и правила кэширования.

# Как выбирать ресурсы, URI и вложенность без копирования структуры таблиц?

Ресурс представляет понятие, с которым работает клиент: заказ, загрузку, резерв или длительную операцию. URI выбирают устойчивым, не раскрывая физические таблицы и внутреннюю схему хранения. Вложенность полезна для отношения владения, но слишком длинная цепочка усложняет доступ и эволюцию.

Например, строки заказа доступны через `/orders/{id}/items`, а самостоятельная операция экспорта может иметь `/exports/{id}`. Проверка доступа к вложенному ресурсу должна подтверждать связь с родителем; форма пути не обеспечивает её автоматически.

# Как различать семантику GET, POST, PUT, PATCH и DELETE в изменяющем API?

`GET` предназначен для чтения без запрошенного изменения состояния. `PUT` создаёт или заменяет представление ресурса по известному URI, `PATCH` применяет описанное изменение, `POST` выполняет обработку по контракту ресурса, `DELETE` удаляет связь URI с текущей функциональностью ресурса.

Идемпотентность метода касается повторного намеренного эффекта, а не одинакового status или body. PATCH не является автоматически идемпотентным: «увеличить на один» отличается от «установить значение». [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html), [PATCH](https://www.rfc-editor.org/rfc/rfc5789.html).

# Как проектировать создание ресурса и длительную операцию через 201 и 202?

`201 Created` сообщает, что ресурс создан; его местоположение обычно передают через `Location` и при необходимости возвращают представление. `202 Accepted` означает, что обработка принята, но ещё не завершена и может закончиться отказом.

Для длительной операции возвращают идентификатор или URI состояния с допустимыми переходами, ошибкой, результатом и возможностью отмены, если она поддерживается. Принятие должно опираться на надёжно сохранённую работу, а не detached promise в памяти процесса.

# Как HTTP-статусы помогают различать ошибки доступа, конфликт и неверные данные?

`401` обычно означает необходимость подходящей аутентификации, `403` — запрет операции для установленного контекста. `404` может обозначать отсутствие ресурса или предусмотренное сокрытие его существования. `409` подходит для конфликта с текущим состоянием, `412` — для невыполненного HTTP-precondition.

Неверный синтаксис часто возвращают как `400`, а семантически недопустимое содержимое — по согласованному контракту, например `422`. Ошибка сервера не должна маскироваться как неверный ввод. Помимо статуса нужен устойчивый машинный код и безопасные детали.

# Как реализовать keyset pagination с устойчивой сортировкой и непрозрачным cursor?

Задают полный устойчивый порядок с уникальным tie-breaker. Для PostgreSQL при `ORDER BY created_at DESC, id DESC` следующая страница может использовать `WHERE (created_at, id) < (:time, :id)` и ограниченный `LIMIT`.

Cursor кодирует checkpoint и связь с фильтром/сортировкой; он не должен превращаться в способ подменить tenant или SQL. Изменяемые ключи сортировки всё равно могут вызывать пропуски или повторы — для строгого снимка нужна отдельная гарантия. Непрозрачность cursor не заменяет авторизацию. [Правила page tokens](https://google.aip.dev/158).

# Когда offset pagination приемлема и как изменения данных влияют на страницы?

Offset удобен для небольших наборов, административных списков и перехода к номеру страницы. Большой offset может требовать пропустить много строк, поэтому его стоимость растёт даже при небольшом `LIMIT`.

Если перед текущей позицией добавили или удалили запись, следующие страницы могут повторять или пропускать элементы. Устойчивый `ORDER BY` необходим, но не обеспечивает snapshot между запросами. Для больших изменяемых потоков чаще подходит keyset; точные страницы иногда требуют материализованного набора результатов.

# Как проектировать фильтрацию и сортировку с ограничением сложности запросов?

Разрешают только известные поля, операторы и направления сортировки, ограничивают число условий, глубину, размер списков и page size. Значения параметризуют, а динамические SQL identifiers выбирают по whitelist.

Проверяют, что доступные комбинации используют приемлемые индексы и не создают неограниченный scan или JOIN. Семантика времени, null, регистра и сочетания `AND/OR` должна быть явной. Tenant/access-фильтр добавляет сервер; клиент не должен иметь возможность снять его параметром.

# Как ETag и If-Match защищают REST-ресурс от lost update?

Сервер возвращает validator версии представления через `ETag`; изменяющий запрос передаёт `If-Match`. При несовпадении precondition отклоняется, обычно с `412`, чтобы клиент перечитал состояние вместо перезаписи чужого изменения.

Проверку и изменение нужно связать атомарно, например через version predicate в БД. Простое сравнение header перед независимым `UPDATE` оставляет гонку. Для `If-Match` применяется strong comparison; слабый ETag для этой цели не подходит. [Conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match).

# Как выбрать стратегию версионирования REST API и организовать deprecation?

Версию можно указывать в URI, header или media type; каждый способ имеет последствия для клиентов, маршрутизации, кэшей и документации. Важнее согласованная политика совместимости и наличие периода перехода.

Сначала поддерживают обе формы, наблюдают использование и предупреждают потребителей, затем по объявленным условиям выводят старую. Версия не оправдывает бесконечную поддержку всех вариантов. Изменение бизнес-смысла или security policy тоже оценивают как потенциально несовместимое, даже если JSON-схема совпала.

# Как обеспечить повторяемость POST-операции и согласовать её с HTTP-семантикой?

На уровне приложения POST можно защитить idempotency key: сервер атомарно связывает ключ, смысл запроса и сохранённый результат. Повтор того же намерения возвращает прежний исход, а другой payload под тем же ключом отклоняется.

Это контракт конкретной операции, а не изменение общей семантики HTTP-метода. Указывают область ключа, срок хранения и поведение конкурирующих запросов. Если первый вызов завершился timeout, нельзя автоматически создавать новый ключ: прежний эффект мог уже произойти.

# Как тестировать REST API на совместимость, ошибки и некорректные комбинации параметров?

Проверяют нормальный путь, отсутствующие и запрещённые ресурсы, ошибки формата, конфликт версии и повтор изменяющей операции. Для списков нужны пустой набор, одинаковые значения сортировки, конец страниц, неверный cursor и изменение данных между запросами.

Используют схему и потребительские сценарии, но также проверяют авторизацию и фактическое состояние БД. Некорректные сочетания фильтров должны давать предсказуемый отказ, а не дорогое случайное выполнение. Реальные старые clients помогают обнаружить изменения, незаметные по diff типов.
