# Как выбрать между готовой компонентной библиотекой и собственным UI Kit?

Готовая библиотека подходит, когда важны скорость разработки, стандартные компоненты и минимальные затраты на поддержку. Например, MUI, Ant Design или Mantine.

Собственный UI Kit оправдан, когда продукт имеет уникальный дизайн, специфические требования или компоненты должны переиспользоваться между несколькими проектами.

Основные критерии выбора:

- Кастомизация - насколько легко адаптировать компоненты под дизайн.
- Доступность (a11y) - поддержка клавиатуры, скринридеров и ARIA.
- Стоимость поддержки - кто исправляет ошибки и обеспечивает совместимость.
- Масштабируемость - насколько удобно развивать и переиспользовать компоненты.
- Зависимости - насколько библиотека привязывает проект к конкретным технологиям.

Часто оптимален гибридный подход: использовать headless-компоненты для поведения и доступности, а собственные стили и design tokens - для внешнего вида.

# Что такое design token и как связать его с CSS custom properties?

Design token - именованное значение дизайн-системы, описывающее цвет, отступ, типографику, радиус или другое визуальное свойство.

Вместо использования конкретных значений напрямую компоненты обращаются к токенам.

Например:

```
:root {
  --color-primary: #2563eb;
  --color-text: #111827;
  --spacing-md: 16px;
}

.button {
  background: var(--color-primary);
  padding: var(--spacing-md);
}
```

CSS custom properties (`--color-primary`) являются способом реализации токенов в браузере. Сами design tokens могут храниться в JSON и преобразовываться в CSS, Swift или другие форматы.

Обычно выделяют три уровня:

- Primitive tokens - базовые значения: `blue-500`, `spacing-4`.
- Semantic tokens - назначение: `color-text-primary`, `color-background`.
- Component tokens - значения конкретного компонента: `button-background-primary`.

Это позволяет менять визуальную систему без переписывания компонентов.

# Как устроить темизацию и переключение светлой/тёмной темы?

Темизацию удобно строить на CSS custom properties, определяя одинаковые семантические токены с разными значениями для каждой темы.

```
:root {
  --color-bg: #ffffff;
  --color-text: #111111;
}

[data-theme="dark"] {
  --color-bg: #111111;
  --color-text: #ffffff;
}

body {
  background: var(--color-bg);
  color: var(--color-text);
}
```

Переключение выполняется изменением атрибута:

```
document.documentElement.dataset.theme = "dark";
```

Для полноценной реализации необходимо:

- Хранить предпочтение пользователя, например в `localStorage`.
- Учитывать системную тему через `prefers-color-scheme`, если пользователь не выбрал тему явно.
- Применять тему до первой отрисовки, чтобы избежать мерцания (FOUC).
- Проверять контрастность текста, границы и состояния компонентов в обеих темах.

Лучше хранить предпочтение как `light`, `dark` или `system`. В режиме `system` интерфейс автоматически реагирует на изменение системной темы.

# Как реализовать составной компонент Select с клавиатурным управлением?

Compound Component - паттерн, при котором сложный компонент состоит из связанных подкомпонентов, совместно использующих состояние.

Например:

```
<Select.Root value={value} onValueChange={setValue}>
  <Select.Trigger />
  <Select.Content>
    <Select.Item value="react">React</Select.Item>
    <Select.Item value="vue">Vue</Select.Item>
  </Select.Content>
</Select.Root>
```

Общее состояние передаётся через React Context. Обычно оно содержит выбранное значение, состояние открытия, активный элемент и методы управления.

Клавиатурное управление:

- `Enter` / `Space` - открытие списка и подтверждение выбора.
- `ArrowUp` / `ArrowDown` - перемещение между вариантами.
- `Escape` - закрытие без изменения выбора.
- `Home` / `End` - переход к первому или последнему элементу.
- `Tab` - переход к следующему элементу интерфейса.
- Typeahead - поиск варианта по вводимым символам.

Для доступности используют паттерн select-only combobox с `role="combobox"`, `aria-expanded`, `aria-controls`, всплывающим `role="listbox"` и элементами `role="option"`.

Фокус можно оставлять на combobox, передавая активный вариант через `aria-activedescendant`. При этом необходимо прокручивать активный элемент в видимую область.

Важно различать активный элемент и выбранное значение: перемещение стрелками не обязательно должно изменять подтверждённый выбор.

Если особая стилизация и поведение не нужны, предпочтительнее нативный `<select>`.&#x20;

# Что такое headless UI и чем он отличается от styled component library?

Headless UI - подход, при котором библиотека предоставляет поведение, состояние и доступность компонентов, но практически не определяет их внешний вид.

Например, Radix Primitives и Headless UI.

Styled component library - библиотека готовых компонентов с предопределённым дизайном, например MUI или Ant Design.

Основные различия:

- Headless UI - больше свободы стилизации, но требуется самостоятельно реализовать визуальную систему.
- Styled library - быстрее создавать интерфейсы, но сложнее добиться нестандартного дизайна.

Оба подхода могут поддерживать клавиатурную навигацию, ARIA и управление состоянием.

Headless UI особенно полезен при создании собственного UI Kit, поскольку позволяет отделить поведение компонента от его представления.

# Как документировать варианты UI-компонента в Storybook?

Storybook позволяет создавать изолированные примеры компонентов - `stories`, демонстрирующие разные свойства и состояния.

Для каждого компонента обычно документируют:

- Variants - `primary`, `secondary`, `danger`.
- Sizes - `small`, `medium`, `large`.
- States - `default`, `hover`, `focus`, `disabled`, `loading`, `error`.
- Содержимое - короткие и длинные тексты, наличие иконок.
- Темы и адаптивность - светлая/тёмная тема, мобильные размеры.
- Accessibility - клавиатурное управление и доступные имена.

Для управления параметрами используют `args` и `argTypes`.

```
const meta = {
  component: Button,
  args: {
    children: "Сохранить",
  },
  argTypes: {
    variant: {
      control: "select",
      options: ["primary", "secondary", "danger"],
    },
  },
} satisfies Meta<typeof Button>;

export default meta;
```

`Controls` позволяет изменять параметры интерактивно, а `Autodocs` - автоматически формировать документацию на основе stories и метаданных.

Дополнительно можно использовать `play`-функции для тестирования взаимодействий и инструменты визуального регрессионного тестирования.&#x20;

# Как поддерживать версионирование и changelog UI Kit?

Для версионирования UI Kit обычно используют Semantic Versioning (SemVer) в формате `MAJOR.MINOR.PATCH`.

- MAJOR - несовместимые изменения публичного API.
- MINOR - новая функциональность с обратной совместимостью.
- PATCH - исправления ошибок без нарушения совместимости.

Например:

- `1.2.0` - добавлен новый вариант `Button`.
- `1.2.1` - исправлено отображение `Button`.
- `2.0.0` - удалён ранее доступный prop.

Changelog должен фиксировать добавленные возможности, исправления, устаревшие API и breaking changes с инструкциями по миграции.

Автоматизировать выпуск версий можно через Changesets или semantic-release в CI/CD.

Для монорепозитория важно определить стратегию версионирования: общая версия всех пакетов или независимые версии каждого пакета.

# Как избежать breaking changes в публичном API компонентов?

Breaking change - изменение, которое нарушает совместимость с существующим использованием компонента.

Чтобы снизить риск:

- Сохранять совместимость props - не удалять и не переименовывать существующие свойства без необходимости.
- Не менять поведение по умолчанию - например, значение `variant` или способ обработки событий.
- Использовать deprecation - сначала помечать API устаревшим, затем удалять в следующей major-версии.
- Поддерживать совместимость типов - изменения TypeScript-типов тоже могут ломать потребителей.
- Тестировать публичный API - проверять props, события, `ref`, стили и основные сценарии использования.
- Документировать миграцию - предоставлять инструкции и, когда возможно, codemods.

Особенно важно учитывать не только JavaScript API, но и структуру DOM, CSS-классы, CSS custom properties и семантику доступности, если потребители от них зависят.

Полностью избежать breaking changes не всегда возможно. В таких случаях изменения выпускают в новой major-версии.

# Как проектировать компоненты с поддержкой разных локалей и RTL?

Компоненты должны быть независимы от конкретного языка и направления текста.

Основные принципы:

- Не хардкодить тексты - передавать строки через props или систему переводов.
- Использовать `Intl` - для форматирования дат, чисел и валют.
- Поддерживать `dir` - направление текста должно корректно наследоваться или задаваться явно.
- Использовать логические CSS-свойства - `margin-inline-start` вместо `margin-left`.
- Учитывать длину переводов - размеры элементов не должны зависеть от фиксированной длины текста.
- Проверять доступность - переводить `aria-label`, подсказки и сообщения об ошибках.

Для компонентов с иконками важно учитывать направление: например, стрелка перехода назад в RTL-интерфейсе обычно направлена вправо.

При этом не все элементы следует зеркально отражать. Логотипы, фотографии, некоторые графики и индикаторы воспроизведения могут сохранять исходную ориентацию.

# Какие проблемы решают design tokens?

Design tokens решают проблему несогласованности визуальных значений между компонентами, проектами и платформами.

Основные преимущества:

- Единообразие - одинаковые цвета, отступы и типографика во всём интерфейсе.
- Централизованное управление - изменение токена распространяется на все его использования.
- Темизация - возможность менять значения токенов для разных тем и брендов.
- Масштабируемость - новые компоненты используют существующие правила дизайна.
- Синхронизация дизайна и кода - токены можно экспортировать из инструментов дизайна и преобразовывать в CSS или другие форматы.

Особенно полезны семантические токены: вместо привязки к `blue-500` компонент использует `color-action-primary`.

Это позволяет менять палитру, не изменяя назначение цвета в компонентах.

# Чем i18n отличается от l10n?

i18n (internationalization) - подготовка приложения к поддержке разных языков и региональных настроек.

Включает:

- Вынос текстов из кода.
- Поддержку Unicode и RTL.
- Использование локализуемых форматов дат, чисел и валют.
- Архитектуру для загрузки переводов.

l10n (localization) - адаптация приложения под конкретный язык или регион.

Включает перевод текстов, настройку форматов, единиц измерения, региональных обозначений и других культурных особенностей.

Разница: i18n создаёт техническую возможность локализации, а l10n реализует её для конкретной локали.

Например, поддержка `Intl.DateTimeFormat` - часть i18n, а отображение даты в формате, принятом для `de-DE`, - результат l10n.

# Как работать с плюрализацией и ICU MessageFormat?

Плюрализация - выбор правильной формы сообщения в зависимости от количества.

Простое условие `count === 1` недостаточно, поскольку разные языки имеют разные правила множественного числа.

Например, русский язык:

- `1 товар`
- `2 товара`
- `5 товаров`
- `21 товар`

ICU MessageFormat позволяет описывать такие правила декларативно:

```
{count, plural,
  one {# товар}
  few {# товара}
  many {# товаров}
  other {# товара}
}
```

Здесь:

- `count` - количество.
- `plural` - выбор формы по правилам локали.
- `one`, `few`, `many`, `other` - категории множественного числа.
- `#` - подстановка форматированного количества.

JavaScript предоставляет `Intl.PluralRules` для определения категории, но не реализует полноценный ICU MessageFormat. Для обработки сообщений обычно используют библиотеки локализации.

Также ICU поддерживает `select` для выбора текста по категориальному значению.

Важно переводить целые сообщения, а не склеивать строки из отдельных фрагментов: порядок слов и грамматика зависят от языка.&#x20;

# Как форматировать даты, числа и валюты для разных локалей?

В JavaScript используется встроенный API `Intl`, который учитывает региональные правила форматирования.

Даты:

```
const formatter = new Intl.DateTimeFormat("ru-RU", {
  day: "numeric",
  month: "long",
  year: "numeric",
  timeZone: "Europe/Moscow",
});

formatter.format(new Date());
```

Числа:

```
new Intl.NumberFormat("de-DE").format(1234567.89);
// "1.234.567,89"
```

Валюты:

```
new Intl.NumberFormat("en-US", {
  style: "currency",
  currency: "USD",
}).format(1234.5);
// "$1,234.50"
```

Важные особенности:

- Локаль определяет формат отображения.
- `timeZone` определяет часовой пояс при форматировании даты.
- Код `currency` определяет валюту, но не выполняет конвертацию.
- Для денежных расчётов необходимо учитывать точность чисел, а не полагаться на форматирование.

Данные лучше хранить в независимом от локали формате, а локализовать только при отображении.&#x20;

# Как строить интерфейс с поддержкой RTL?

RTL (Right-to-Left) - направление интерфейса справа налево, используемое, например, для арабского и иврита.

Основные шаги:

1. Установить направление документа:
   ```
   <html lang="ar" dir="rtl">
   ```
2. Использовать логические CSS-свойства:
   ```
   .card {
     padding-inline-start: 16px;
     margin-inline-end: 8px;
     text-align: start;
   }
   ```
3. Адаптировать навигацию, порядок элементов и направленные иконки.
4. Изолировать фрагменты с другим направлением через `<bdi>`, `dir="ltr"` или `dir="auto"`.
5. Тестировать смешанный текст, содержащий арабские, латинские символы, числа и знаки пунктуации.

Важно: RTL не означает простое зеркальное отражение всего интерфейса. Направление контента и логика отдельных элементов могут отличаться.

Не стоит глобально использовать `transform: scaleX(-1)` или без необходимости менять `flex-direction`. Это может приводить к неправильному отображению текста и элементов.

# Как организовать переключение языка без потери состояния формы?

Главное правило - состояние формы должно быть отделено от локализованных текстов.

Например, в React Hook Form значения хранятся внутри экземпляра формы, а переводы используются только для отображения подписей, подсказок и ошибок.

При переключении языка необходимо:

- Обновлять переводы без размонтирования формы.
- Не пересоздавать форму из-за изменения `key`, зависящего от языка.
- Не вызывать `reset()` при изменении локали без необходимости.
- Хранить значения независимо от языка, например даты в стандартном формате.
- Обновлять локализованные сообщения валидации.

В React особенно важно сохранять идентичность компонента формы в дереве, иначе его локальное состояние может сброситься.

Если переключение языка требует полной перезагрузки страницы, черновик формы необходимо предварительно сохранить и восстановить после загрузки.

# Как правильно обрабатывать длинные переводы в адаптивной верстке?

Длина текста может существенно отличаться между языками, поэтому интерфейс должен адаптироваться к содержимому.

Основные практики:

- Использовать гибкие размеры вместо фиксированных `width` и `height`.
- Разрешать тексту переноситься на несколько строк.
- Применять `min-width: 0` для flex/grid-элементов, которые должны сжиматься.
- Использовать `overflow-wrap: anywhere` для длинных неразрывных строк, когда это необходимо.
- Не размещать критически важные тексты внутри элементов с принудительным `text-overflow: ellipsis`.
- Проверять интерфейс при увеличении масштаба и размера шрифта.

Для тестирования полезна псевдолокализация - автоматическое удлинение строк и замена символов для выявления проблем вёрстки до появления реальных переводов.

Главный принцип - контент определяет необходимое пространство, а не обрезается ради сохранения фиксированного размера компонента.

# Как проектировать пустые, ошибочные и загрузочные состояния интерфейса?

Интерфейс должен явно показывать пользователю, что происходит с данными и какие действия доступны.

Loading state - данные загружаются.

- Использовать skeleton для предсказуемой структуры контента.
- Показывать spinner для локальных операций без фиксированной структуры.
- Не блокировать весь интерфейс, если можно продолжать взаимодействие.

Empty state - запрос завершён успешно, но данных нет.

- Объяснять, почему ничего не отображается.
- Различать отсутствие данных и отсутствие результатов фильтрации.
- Предлагать подходящее действие: создать элемент, изменить фильтры или сбросить поиск.

Error state - операция завершилась ошибкой.

- Показывать понятное сообщение без технических подробностей.
- Предлагать повторить действие или восстановить работу.
- Сохранять введённые пользователем данные.

Важно не заменять существующий контент загрузочным индикатором при каждом фоновом обновлении. Лучше сохранить данные и ненавязчиво показать процесс обновления.

# Чем optimistic UI отличается от pessimistic UI?

Optimistic UI - интерфейс обновляется до получения подтверждения от сервера, предполагая успешное выполнение операции.

Например, пользователь ставит лайк, и счётчик увеличивается мгновенно.

Если сервер возвращает ошибку, изменение откатывается (rollback).

Pessimistic UI - интерфейс обновляется только после подтверждения успешного выполнения операции сервером.

Основные различия:

- Optimistic - быстрый отклик, но требуется обработка ошибок, откат изменений и согласование с серверным состоянием.
- Pessimistic - проще обеспечить согласованность с сервером, но пользователь ждёт завершения запроса.

Optimistic UI подходит для действий с высокой вероятностью успеха и возможностью безопасного отката: лайки, переключатели, изменение порядка элементов.

Pessimistic UI предпочтителен для критичных операций, например финансовых транзакций, где нельзя показывать окончательный успех до подтверждения сервера.

# Как реализовать undo для пользовательских действий?

Undo - механизм отмены ранее выполненного действия, позволяющий восстановить предыдущее состояние.

Основные подходы:

1\. Отложенное выполнение

Действие визуально применяется сразу, но запрос на сервер выполняется после небольшой задержки.

Если пользователь нажимает Undo, ожидающий запрос отменяется.

2\. Компенсирующее действие

Операция уже выполнена на сервере, поэтому Undo отправляет обратную операцию.

Например, удалённый элемент восстанавливается отдельным запросом.

3\. История состояний

Для сложных редакторов используется стек истории:

- `undoStack` - предыдущие состояния или обратные операции.
- `redoStack` - отменённые действия, доступные для повторения.

При каждом новом действии сохраняется информация, необходимая для отмены.

Важно учитывать, что отмена интерфейсного изменения не всегда отменяет побочные эффекты на сервере. Например, уже отправленное письмо нельзя гарантированно отозвать.

# Как снизить вероятность двойной отправки формы?

Основной способ - блокировать повторную отправку, пока предыдущая операция выполняется.

Например, в React Hook Form используется `formState.isSubmitting`.

```
const {
  handleSubmit,
  formState: { isSubmitting },
} = useForm();

return (
  <form onSubmit={handleSubmit(onSubmit)}>
    <button type="submit" disabled={isSubmitting}>
      Сохранить
    </button>
  </form>
);
```

Дополнительные меры:

- Показывать состояние загрузки и обратную связь пользователю.
- Защищаться от повторного запуска обработчика на уровне логики приложения.
- Не использовать `debounce` как единственный механизм защиты.
- Для критичных операций применять idempotency key на сервере.

Idempotency key позволяет серверу распознавать повторную отправку одной логической операции и не выполнять её повторно.

Важно: блокировка кнопки защищает только интерфейс. Она не гарантирует отсутствие дублирования запросов при повторных попытках, сетевых сбоях или нескольких вкладках.

# Как оформлять ошибки сети так, чтобы пользователь мог восстановить работу?

Ошибки должны объяснять проблему и предоставлять понятный способ продолжить работу.

Основные принципы:

- Понятное сообщение - вместо `NetworkError` показывать «Не удалось загрузить данные».
- Восстановление - предоставлять кнопку «Повторить».
- Сохранение состояния - не удалять введённые данные или уже загруженный контент.
- Различение ошибок - по-разному обрабатывать отсутствие сети, таймаут, ошибки авторизации и ошибки сервера.
- Автоматические повторы - использовать для временных сбоев, когда повтор операции безопасен.

Для повторных запросов обычно применяют exponential backoff - увеличение задержки между попытками.

Например: 1, 2, 4 секунды.

Однако автоматически повторять неидемпотентные операции опасно без серверной защиты от дублирования.

Если ошибка возникает при фоновом обновлении, лучше оставить ранее загруженные данные на экране и показать уведомление, чем полностью заменять интерфейс экраном ошибки.

# Как поддерживать навигацию и доступность на мобильных устройствах?

Мобильная доступность включает управление касанием, клавиатурой, скринридером и другими вспомогательными технологиями.

Основные требования:

- Touch targets - интерактивные элементы должны иметь достаточную область нажатия и расстояние между собой.
- Семантический HTML - использовать `<button>`, `<a>`, `<nav>`, `<label>` по назначению.
- Клавиатурная навигация - обеспечивать логичный порядок фокуса и видимый индикатор.
- Screen readers - предоставлять доступные названия, роли и состояния элементов.
- Адаптивность - поддерживать увеличение текста и масштабирование без потери функциональности.
- Focus management - корректно перемещать и возвращать фокус при открытии и закрытии модальных окон.
- Reduced motion - учитывать `prefers-reduced-motion`.

Нужно также учитывать экранную клавиатуру: она может уменьшать доступную область экрана и перекрывать поля или кнопки.

Для мобильной навигации важно сохранять предсказуемость. Например, кнопка «Назад» должна возвращать пользователя в ожидаемое место, а не сбрасывать весь процесс заполнения формы.

# Как проектировать состояние `loading`, `empty`, `error`, `success`?

Лучше использовать явную модель состояний, а не набор независимых boolean-переменных.

Например:

```
type AsyncState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: Error };
```

Такой подход исключает противоречивые комбинации вроде одновременных `isLoading === true` и `isError === true` в модели взаимоисключающих состояний.

Логика переходов:

```
idle
  ↓
loading
  ├── success
  └── error
        ↓
      loading
```

Empty часто является частным случаем успешного состояния: запрос завершился, но массив данных пуст.

```
if (state.status === "success") {
  return state.data.length === 0
    ? <EmptyState />
    : <DataList data={state.data} />;
}
```

При работе с серверным состоянием важно различать первичную загрузку и фоновое обновление.

Например, TanStack Query позволяет одновременно иметь ранее полученные данные и выполнять новый запрос через `isFetching`.

Поэтому реальная модель может быть сложнее простой последовательности состояний: существующие данные можно продолжать показывать даже во время обновления или после ошибки повторного запроса.

# Когда хранить состояние фильтров в URL, а когда локально?

URL подходит для состояния, которое должно сохраняться при обновлении страницы, передаваться по ссылке и восстанавливаться через историю браузера.

Например:

```
/products?category=books&sort=price&page=2
```

В URL обычно хранят:

- Поисковый запрос.
- Выбранные категории.
- Сортировку.
- Пагинацию.
- Применённые фильтры.

Локальное состояние подходит для временных UI-настроек, которые не должны влиять на адрес страницы.

Например:

- Открыт ли выпадающий список фильтров.
- Значение фильтра до нажатия «Применить».
- Состояние модального окна.
- Временный ввод внутри компонента.

Для синхронизации используют `URLSearchParams` и API роутера.

Важно учитывать:

- Источник истины - применённые фильтры не должны независимо храниться и в URL, и в локальном состоянии без механизма синхронизации.
- Историю браузера - для промежуточного ввода часто используют `replace`, чтобы не создавать отдельную запись для каждого символа.
- Сериализацию - массивы, числа и значения по умолчанию нужно преобразовывать предсказуемо.
- Безопасность - чувствительные данные нельзя помещать в URL, поскольку они могут попасть в историю, логи и другие системы.

Основной критерий: если пользователь должен иметь возможность поделиться текущим состоянием страницы или восстановить его после перезагрузки, состояние стоит хранить в URL.
